먼저 읽을 것: .NET 진단 도구, 게임 서버 토폴로지, 서비스 호출: 타임아웃·재시도·데드라인

핵심 요약

관측성은 서버를 멈추거나 디버거를 붙이지 않고, 밖으로 내보낸 신호만으로 안에서 무슨 일이 있었는지 알아내는 능력이다. 신호는 세 가지다. 지표는 숫자를 모아 무엇이 이상한지 알려 주고, 로그는 사건을 적어 그때 왜 그랬는지 알려 주고, 추적은 요청 하나가 거친 경로를 이어 어디서 느렸는지 알려 준다. 셋은 서로를 대신하지 못하고, 같은 추적 ID로 묶여 있어야 서로 건너다닐 수 있다.

경보는 사용자가 실제로 느끼는 것에 건다. "로그인이 2초 넘게 걸리는 비율"이 오르면 사람을 깨우고, CPU나 큐 길이 같은 원인 쪽 숫자는 대시보드에 두고 원인을 찾을 때 본다. 원인마다 경보를 걸면 경보가 너무 많아져 정작 중요한 경보를 아무도 보지 않게 된다.

동작 원리

세 신호는 다른 질문에 답한다

신호담는 것답하는 질문비용약점
지표시간별로 모은 숫자(횟수, 현재값, 분포)무엇이, 언제부터, 얼마나 이상한가싸다. 요청이 늘어도 저장량이 거의 그대로다개별 요청을 모른다. 왜 그런지는 말하지 않는다
로그시각과 필드가 붙은 사건 하나하나그때 무슨 일이 있었나, 어떤 값이었나비싸다. 요청 수에 비례해 늘어난다양이 많으면 찾지 못한다. 경로를 잇지 않는다
추적요청 하나가 거친 구간(span)의 나무어느 서비스, 어느 구간에서 시간을 썼나중간. 보통 일부 요청만 남긴다표본에 안 잡힌 요청은 볼 수 없다

순서는 대개 지표 → 추적 → 로그다. 지표가 이상을 알리고, 그 시각의 느린 추적 하나를 골라 어느 구간인지 본 뒤, 그 구간의 로그에서 원인을 읽는다. 좁혀 가는 절차 자체는 느린 서버 진단이 다룬다. 이 문서는 그 절차가 가능하도록 평소에 무엇을 어떻게 남겨 두는지를 다룬다. 한 프로세스 안을 들여다보는 도구(카운터, 덤프, 프로파일)는 .NET 진단 도구에 있다.

로그는 문장이 아니라 필드로 남긴다

"계정 a91의 로그인이 680ms 걸림"처럼 값을 문장에 끼워 넣으면 사람은 읽기 쉽지만 기계는 찾기 어렵다. "680ms 넘게 걸린 로그인만 보여 줘"를 하려면 문장을 다시 쪼개야 한다. 구조화 로그는 메시지 틀과 값을 따로 남긴다. 저장소는 {"msg":"로그인 완료","account":"a91","elapsedMs":680,"trace":"4bf9…"}처럼 필드를 받아 필드로 찾는다.

.NET의 ILogger는 메시지 틀의 {이름} 자리를 필드로 남긴다. 문자열 보간($"...")으로 미리 합치면 필드가 사라지고, 그 수준의 로그가 꺼져 있어도 문자열을 만드는 비용을 낸다. 자주 찍는 로그는 LoggerMessage 소스 생성기로 미리 만들어 두면 할당 없이 빠르게 찍힌다. 

public static partial class LoginLog
{
    [LoggerMessage(EventId = 2001, Level = LogLevel.Warning,
        Message = "플랫폼 인증 지연 {Provider} {ElapsedMs}ms")]
    public static partial void SlowPlatformAuth(ILogger logger, string provider, long elapsedMs);
}

// 틀린 예: 필드가 사라지고, Warning이 꺼져 있어도 문자열을 만든다
logger.LogWarning($"플랫폼 인증 지연 {provider} {elapsed}ms");

// 맞는 예: Provider, ElapsedMs가 필드로 남는다
LoginLog.SlowPlatformAuth(logger, provider, elapsed);

로그 수준은 팀이 기준을 정해 둬야 의미가 있다.

수준남기는 것운영에서
Error요청이나 작업이 실패했고 누군가 봐야 하는 일늘 켠다. 한 번의 실패에 한 줄
Warning실패는 아니지만 예상 밖인 일. 재시도 성공, 시한 근접, 대체값 사용늘 켠다
Information상태가 바뀌는 주요 사건. 서버 시작·종료, 배포, 설정 변경켠다. 요청마다 찍지는 않는다
Debug, Trace코드 흐름과 중간값끈다. 문제를 볼 때 일부 서버나 계정만 잠깐 켠다

로그마다 상관 ID를 붙인다. 요청 하나에서 나온 로그를 서버 여러 대에 걸쳐 모으려면 같은 ID가 있어야 한다. 추적을 쓰면 trace ID가 그 역할을 한다. 게이트웨이에서 처음 만든 ID를 모든 서버 호출과 메시지에 실어 보내고(게임 서버 토폴로지), 각 서버는 받은 ID를 로그 범위(scope)에 넣어 그 요청의 모든 줄에 자동으로 붙게 한다.

로그가 장애를 키울 수 있다

장애가 나면 오류 로그가 한꺼번에 쏟아진다. 초당 수만 줄의 예외와 스택이 디스크와 네트워크를 채우고, 로그를 쓰는 스레드가 막혀 요청 처리까지 느려진다. 그래서 로그에도 상한을 둔다.

  • 같은 오류는 묶는다. 같은 이벤트 ID가 1초에 100번 나면 처음 몇 줄과 "같은 오류 9,812회 생략"만 남긴다.
  • 정상 요청은 표본만 남긴다. 성공한 요청은 1%만 자세히 남기고, 실패와 느린 요청은 모두 남긴다.
  • 쓰기는 비동기로, 큐는 유한하게. 로그 큐가 차면 기다리지 않고 버린다. 버린 개수는 지표로 센다. 로그 때문에 게임 로직이 멈추는 것보다 로그를 잃는 편이 낫다.

지표는 종류가 셋이고, 분포는 히스토그램으로 남긴다

종류뜻예
카운터늘기만 하는 누적 횟수. 보는 쪽이 초당 증가량으로 바꾼다처리한 패킷 수, 로그인 실패 수
게이지지금 이 순간의 값. 오르내린다동접 수, 큐 길이, 열린 연결 수
히스토그램값이 어느 구간에 몇 번 떨어졌는지 센다응답 시간, 틱 처리 시간, 패킷 크기

시간 같은 값은 평균을 남기지 말고 히스토그램으로 남긴다. 평균은 꼬리를 숨기고, 서버별 p99는 합칠 수 없다. 히스토그램은 구간별 횟수라서 서버 여러 대의 것을 더한 뒤 전체 p99를 계산할 수 있다(느린 서버 진단). 무엇을 잴지는 요청을 받는 쪽은 RED, 자원 쪽은 USE 틀로 정한다. 그 틀도 같은 문서에 있다. 

using System.Diagnostics.Metrics;

public sealed class LoginMetrics
{
    static readonly Meter Meter = new("Game.Login");
    static readonly Counter<long> Failures = Meter.CreateCounter<long>("login.failures");
    static readonly Histogram<double> Duration =
        Meter.CreateHistogram<double>("login.duration", unit: "ms");

    public static void Record(double ms, string? failReason, string provider)
    {
        // 태그는 값의 종류가 몇 개로 정해진 것만 붙인다
        Duration.Record(ms, new KeyValuePair<string, object?>("provider", provider));
        if (failReason is not null)
            Failures.Add(1, new KeyValuePair<string, object?>("reason", failReason));
    }
}

태그에 캐릭터 ID를 넣으면 지표 저장소가 무너진다

지표 저장소는 이름과 태그 값의 조합마다 시계열을 하나씩 만든다. provider 태그 값이 3가지면 시계열 3개다. 여기에 account 태그를 붙이면 계정 수만큼 시계열이 생긴다. 계정이 백만이면 백만 개다. 태그 값 종류의 수를 카디널리티라고 하고, 이것이 폭발하면 저장소 비용이 치솟고 조회가 멈춘다.

태그에는 값의 종류가 정해져 있고 적은 것만 넣는다. 서버 종류, 지역, 패킷 종류, 실패 이유 같은 것이다. 캐릭터 ID, 계정 ID, 판 ID, 원본 오류 메시지는 넣지 않는다. "누가"는 지표가 아니라 로그와 추적이 답할 질문이다. 존 번호나 채널 번호도 수천 개로 늘 수 있다면 조심한다.

추적은 요청 하나가 거친 구간을 나무로 잇는다

추적(trace) 하나는 요청 하나이고, 그 안의 구간 하나하나가 span이다. span은 시작·끝 시각, 이름, 태그와 함께 자기 ID와 부모 span의 ID를 든다. 서버를 넘어갈 때는 trace ID와 지금 span ID를 요청 헤더에 실어 보낸다. 이것이 컨텍스트 전파이고, 표준 형식이 W3C Trace Context의 traceparent 헤더다. 받는 서버는 그 값을 부모로 삼아 자기 span을 연다. 메시지 큐를 지날 때도 메시지 헤더에 같은 값을 실어야 추적이 끊기지 않는다.

.NET에서 span은 System.Diagnostics.Activity다. ActivitySource.StartActivity로 열고 using으로 닫는다. ASP.NET Core와 HttpClient, gRPC는 들어오고 나가는 요청에서 Activity를 자동으로 만들고 traceparent를 주고받는다. 직접 짠 TCP·UDP 프로토콜은 자동으로 되지 않으므로, 패킷 헤더에 trace ID를 넣는 자리를 직접 만든다. 

using System.Diagnostics;

static readonly ActivitySource Source = new("Game.Login");

async Task<bool> VerifyPlatformAsync(string provider, string ticket, CancellationToken ct)
{
    using var span = Source.StartActivity("platform.verify");
    span?.SetTag("provider", provider);   // 수집기가 없으면 span은 null이다
    var ok = await _platform.VerifyAsync(ticket, ct);
    if (!ok) span?.SetStatus(ActivityStatusCode.Error);
    return ok;
}

추적은 표본을 남기고, 표본 고르는 시점이 둘이다

모든 요청의 추적을 남기면 로그보다 비싸진다. 그래서 일부만 남긴다.

방식언제 고르나장점단점
머리 표본요청이 들어오는 순간 정해진 비율로 고르고, 그 결정을 뒤로 전파한다싸고 단순하다. 고르지 않은 요청은 기록 비용도 안 든다느리거나 실패할 요청인지 아직 모른다. 드문 오류를 놓친다
꼬리 표본요청이 끝난 뒤 수집기가 span을 모아 본 다음 고른다느린 요청, 오류 난 요청을 골라 남길 수 있다모든 span을 일단 수집기로 보내고 잠시 들고 있어야 한다

수집기가 신호를 받아 저장소로 나눈다

OpenTelemetry는 세 신호를 내보내는 API와 형식을 언어마다 같게 맞춘 표준이다. 서버는 OpenTelemetry SDK로 지표·추적·로그를 같은 형식(OTLP)으로 내보내고, 그 사이에 수집기(Collector)를 둔다. 수집기가 받아서 표본을 고르고, 민감한 필드를 지우고, 지표는 지표 저장소로, 추적은 추적 저장소로, 로그는 로그 저장소로 나눠 보낸다. 저장소를 바꿔도 서버 코드는 그대로이고, 꼬리 표본도 수집기에서 한다. .NET은 Meter와 ActivitySource, ILogger를 그대로 쓰고, OpenTelemetry SDK가 그것들을 구독해 내보낸다.

경보는 SLO에 건다

사용자가 느끼는 품질을 숫자로 정한 것이 SLI(서비스 수준 지표)다. "로그인 요청 가운데 2초 안에 성공한 비율"이 SLI이고, 그 목표치 "30일 동안 99.9%"가 SLO다. 100%에서 SLO를 뺀 나머지가 오류 예산이다. 99.9%면 한 달(30일 = 43,200분)에 약 43분어치 실패를 써도 된다는 뜻이다.

SLO한 달 오류 예산
99%약 7시간 12분
99.9%약 43분
99.99%약 4분 19초

경보는 예산을 빨리 태울 때 건다. "지난 1시간 동안 예산을 평소의 14배 속도로 쓰고 있다"면 며칠 안에 예산이 바닥나니 사람을 깨운다. 느리게 태우고 있으면 근무 시간에 볼 일감으로 남긴다. 예산이 남아 있으면 배포를 계속하고, 바닥나면 새 기능 배포를 멈추고 안정화에 쓴다. 이렇게 하면 "얼마나 안정적이어야 하나"를 감이 아니라 숫자로 다툰다.

경보는 증상에 걸고, 원인은 대시보드에 둔다. CPU 90%는 증상이 아니다. CPU가 90%여도 사용자가 느끼는 지연이 그대로면 깨울 이유가 없고, CPU가 30%인데 락 때문에 로그인이 멈출 수도 있다. 원인마다 경보를 걸면 하룻밤에 수십 개가 울리고, 사람은 곧 경보를 무시하기 시작한다(경보 피로). 울린 경보는 모두 사람이 무언가를 해야 하는 것이어야 하고, 할 일이 적힌 문서를 경보에 붙여 둔다.

선택 기준

알고 싶은 것쓰는 신호주의
지금 이상한가, 언제부터인가지표평소 값이 있어야 비교된다. 장애 전부터 쌓아 둔다
어느 서비스, 어느 구간이 느린가추적꼬리 표본이나 오류 우선 표본이 있어야 느린 요청이 남는다
그 요청에서 무슨 값이 오갔나로그trace ID가 붙어 있어야 그 요청의 줄만 모은다
특정 계정이 겪은 일로그, 추적지표 태그로 풀지 않는다. 카디널리티가 폭발한다
사람을 깨울지SLO 기반 지표증상에만 건다. 원인 지표는 대시보드로

대시보드는 위에서 아래로 좁혀 가게 짠다. 맨 위에는 SLO와 오류 예산, 그 아래에 서비스별 RED, 그 아래에 자원별 USE를 둔다. 장애 때 대시보드를 위에서부터 훑으면 "사용자가 느끼나 → 어느 서비스인가 → 어떤 자원인가" 순서로 내려간다. 배포와 설정 변경 시각을 같은 그래프에 세로선으로 표시하면 "그때 무엇이 바뀌었나"가 한눈에 보인다.

게임 서버에서는

  • 틱 시간을 히스토그램으로 남긴다. 존 서버의 핵심 지표는 틱 하나를 처리하는 데 걸린 시간이다(서버 틱 루프). 틱 예산이 50ms인데 p99가 45ms면 아직 괜찮아 보여도 곧 넘친다. 틱 예산을 넘긴 횟수를 카운터로 따로 세면 경보 기준이 된다.
  • 동접은 존·채널 단위 게이지로 본다. 전체 동접만 보면 한 채널에 몰린 것을 모른다. 다만 존·채널 수가 수천이라면 태그 대신 상위 몇 곳만 따로 내보내거나 분포로 본다.
  • 패킷 종류별 처리량과 처리 시간을 센다. 패킷 종류는 수백 개 안쪽이라 태그로 넣어도 된다. 특정 패킷만 갑자기 늘면 클라이언트 버그나 매크로를 의심한다(레이트 리밋과 입장 대기열).
  • 매칭 대기 시간은 SLI로 삼기 좋다. "매칭 요청 가운데 60초 안에 판이 잡힌 비율"은 플레이어가 직접 느끼는 숫자다(매치메이킹).
  • 운영 로그와 게임 행동 로그를 섞지 않는다. 운영 로그는 엔지니어가 장애를 보려고 남기고, 며칠에서 몇 주 보관하고, 형식을 자유롭게 바꾼다. 아이템 획득·거래·재화 변동 같은 행동 로그는 감사와 CS, 복구에 쓰이고, 몇 년씩 보관하며, 스키마를 함부로 바꾸면 안 된다(백업과 복구, CQRS와 이벤트 소싱). 둘은 저장소도 파이프라인도 따로 둔다. 행동 로그는 유실되면 안 되므로 운영 로그처럼 넘칠 때 버리지 않는다.
  • 개인정보와 비밀은 로그에 남기지 않는다. 이메일, 전화번호, IP, 결제 정보는 남기지 않거나 가려서 남기고, 토큰과 비밀번호는 어떤 수준에서도 찍지 않는다(시크릿과 키 관리). 수집기에서 한 번 더 걸러 낸다.

주의 사항

  • 관측 코드도 비용이다. 패킷 하나마다 span을 열고 로그를 찍으면 처리 시간보다 기록 시간이 길어진다. 틱 안의 뜨거운 경로에서는 카운터와 히스토그램 정도만 쓰고, span은 요청 단위로만 연다.
  • 시계가 서버마다 다르다. 추적의 span 시각은 각 서버의 벽시계로 찍힌다. 서버끼리 시계가 수 밀리초 어긋나면 자식 span이 부모보다 먼저 시작한 것처럼 보이기도 한다(시계와 타이머). 시간 계산은 한 서버 안의 구간 길이로 한다.
  • 지표 이름과 태그는 처음에 정해 둔다. 서비스마다 login_time, loginDuration, auth.latency처럼 제각각이면 모아 볼 수 없다. 이름 규칙과 단위(ms인지 s인지)를 문서로 정하고, OpenTelemetry의 의미 규약(semantic conventions)이 있는 것은 그것을 따른다.
  • 장애 때 관측 시스템도 같이 무너질 수 있다. 로그 폭주로 수집기가 밀리면 정작 필요한 순간에 아무것도 안 보인다. 관측 경로는 게임 서버와 다른 자원에 두고, 수집기가 밀린 정도(버린 개수)도 지표로 본다.
