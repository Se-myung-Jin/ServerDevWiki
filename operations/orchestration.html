먼저 읽을 것: 배포 파이프라인, 세션 기반과 지속 세계, GC 모드와 멈춤

핵심 요약

컨테이너는 산출물과 그것이 도는 데 필요한 실행 환경(런타임, 라이브러리, 설정 파일의 자리)을 이미지 하나로 묶는다. 같은 이미지는 개발 PC에서도 운영 서버에서도 같은 모양으로 뜬다. 가상 머신과 달리 운영체제 커널은 호스트와 함께 쓰고, 프로세스를 격리하고 자원을 제한하는 것은 커널 기능(네임스페이스, cgroups)이 맡는다. 그래서 몇 초 안에 뜨고 가볍다.

오케스트레이터는 컨테이너를 여러 대의 서버에 어떻게 띄울지 맞춰 주는 시스템이다. 사람이 "이 이미지를 세 개 띄워 둬라"라고 원하는 상태를 적으면, 오케스트레이터는 실제 상태를 계속 보며 차이를 메운다. 하나가 죽으면 다시 띄우고, 서버가 하나 빠지면 다른 서버로 옮긴다. 대표가 쿠버네티스다.

이 모델은 언제 지워도 되는 프로세스를 전제한다. 로그인, 로비, 상점 API 같은 상태 없는 서버에는 그대로 맞는다. 플레이어가 붙어 있는 게임 서버는 지워도 되는 시점을 서버만 알기 때문에, 그 사정을 아는 전용 도구나 직접 만든 관리 계층을 얹는다.

동작 원리

이미지는 계층으로 쌓이고, 컨테이너는 그 위의 프로세스다

이미지는 읽기 전용 계층을 차례로 쌓은 것이다. 운영체제 기본 파일, .NET 런타임, 서버 실행 파일이 각자 한 층이다. 서버 코드만 바뀌면 맨 위층만 새로 만들고 아래층은 캐시를 다시 쓴다. 컨테이너는 그 이미지 위에 쓰기용 얇은 층을 하나 얹고 프로세스를 띄운 것이다. 컨테이너를 지우면 그 쓰기 층도 사라진다. 그래서 남겨야 할 것(로그, 덤프, 저장 데이터)은 컨테이너 안이 아니라 바깥 볼륨이나 다른 서비스로 보낸다.

가상 머신컨테이너
격리 단위운영체제 전체(커널 포함)프로세스. 커널은 호스트와 함께 쓴다
뜨는 시간수십 초에서 분대개 몇 초. 앱 기동 시간이 대부분이다
격리 강도강하다커널 취약점은 함께 탄다
자원 제한가상 CPU·메모리를 할당cgroups로 CPU 시간과 메모리 상한을 건다

자원 제한이 서버 코드에 영향을 준다. 메모리 상한을 넘으면 커널이 프로세스를 강제로 끝낸다(종료 코드 137, 시그널과 프로세스 종료). .NET 런타임은 컨테이너의 메모리·CPU 제한을 읽어 GC 힙 상한과 서버 GC 힙 수를 맞추는데, 그 값이 게임 서버에 맞는지는 따로 확인해야 한다(GC 모드와 멈춤). CPU 상한은 "코어 몇 개"가 아니라 "일정 시간당 쓸 수 있는 CPU 시간"이라서, 상한에 닿으면 남은 시간 동안 스레드가 멈춰 틱이 튄다.

오케스트레이터는 원하는 상태와 실제 상태의 차이를 메운다

쿠버네티스에서 자주 만나는 개념은 몇 개 되지 않는다.

개념하는 일
Pod함께 뜨고 함께 지워지는 컨테이너 묶음. 배치와 재시작의 단위다
Deployment"이 이미지의 Pod를 N개 유지"라는 원하는 상태. 이미지를 바꾸면 하나씩 바꿔 끼운다(롤링 업데이트)
Service바뀌는 Pod 주소들 앞에 고정 주소를 하나 세운다. 준비된 Pod로만 보낸다
자원 요청과 한도요청(request)은 배치할 때 확보할 양, 한도(limit)는 넘으면 막히거나 종료되는 선
HorizontalPodAutoscaler(HPA)CPU 사용률이나 직접 내보낸 지표를 보고 Pod 수를 늘리고 줄인다
StatefulSetPod마다 고정 이름과 고정 저장소를 준다. 순서대로 띄우고 순서대로 내린다
PodDisruptionBudget노드 정비처럼 계획된 축출 때 동시에 빠질 수 있는 Pod 수에 상한을 건다

준비 프로브와 생존 프로브는 다른 것을 묻는다

오케스트레이터는 서버 안을 모른다. 그래서 서버에 주기적으로 물어본다. 묻는 질문이 둘이고, 실패했을 때 하는 일이 다르다.

프로브묻는 것실패하면게임 서버에서 넣을 것
준비 프로브(readiness)지금 새 요청을 받아도 되나서비스 목록에서 뺀다. 프로세스는 그대로 둔다기획 데이터 로드 완료, DB 연결, 드레이닝 중이면 실패로 응답
생존 프로브(liveness)살아는 있나, 멈춰 버리지 않았나컨테이너를 재시작한다틱 루프가 마지막으로 돈 시각. 외부 의존(DB)은 넣지 않는다
시작 프로브(startup)기동이 끝났나끝날 때까지 다른 프로브를 미룬다맵과 데이터 로드가 긴 서버에 쓴다

흔한 사고는 생존 프로브에 DB 연결 확인을 넣는 것이다. DB가 잠깐 느려지면 모든 서버의 생존 프로브가 함께 실패하고, 오케스트레이터가 멀쩡한 서버를 전부 재시작한다. 장애가 한 곳에서 전체로 번진다. 외부 의존이 안 되면 "새 요청은 받지 마라"(준비 프로브 실패)가 맞는 답이다. 

// 준비 상태는 서버가 직접 들고 있다가 알려 준다.
// 생존 확인은 틱 루프가 최근에 돌았는지만 본다.
builder.Services.AddHealthChecks()
    .AddCheck("ready", () => world.IsReady && !world.IsDraining
        ? HealthCheckResult.Healthy() : HealthCheckResult.Unhealthy(),
        tags: new[] { "ready" })
    .AddCheck("live", () => DateTime.UtcNow - world.LastTickAt < TimeSpan.FromSeconds(10)
        ? HealthCheckResult.Healthy() : HealthCheckResult.Unhealthy(),
        tags: new[] { "live" });

app.MapHealthChecks("/healthz/ready", new() { Predicate = c => c.Tags.Contains("ready") });
app.MapHealthChecks("/healthz/live",  new() { Predicate = c => c.Tags.Contains("live") });

소켓을 직접 다루는 게임 서버라도 프로브용 HTTP 포트 하나는 따로 연다. 게임 포트로 프로브를 받으면 프로브 연결이 게임 세션으로 잡히거나, 게임 프로토콜이 프로브 형식을 모른다.

상태 없는 서버에는 그대로 맞고, 상태 있는 서버에서 어긋난다

Deployment의 롤링 업데이트와 HPA의 축소는 "아무 Pod나 지워도 된다"를 전제한다. 로비나 인증 서버는 요청 하나가 짧고 상태를 바깥(DB, Redis)에 두므로 이 전제가 맞는다. 플레이어가 붙어 있는 서버는 다르다.

  • 축소할 때 고르는 Pod를 서버가 정할 수 없다. HPA가 Pod 수를 줄이면 플레이어가 가득한 Pod가 먼저 지워질 수 있다.
  • 지우기까지 기다려 주는 시간이 짧다. 종료 유예 시간이 기본 30초라서, 판이 끝나기를 기다리기에는 대개 모자란다(세션 빼기와 배포 트리거).
  • 고정 신원이 필요하다. 존 서버는 "3번 존을 맡은 프로세스"라는 이름이 의미를 갖는다. StatefulSet이 고정 이름은 주지만, 그 이름을 어느 존에 붙일지는 여전히 우리가 정한다.
  • UDP와 직접 접속. 게임 클라이언트가 서버에 직접 붙어야 하면, 로드밸런서 뒤의 고정 주소가 아니라 그 Pod가 뜬 노드의 주소와 포트를 알려 줘야 한다. 호스트 포트나 호스트 네트워크를 쓰고, 포트 배정을 관리해야 한다.

그래서 판 단위로 끝나는 세션 서버는 게임 서버 전용 오케스트레이터(쿠버네티스 위의 Agones, 관리형 GameLift)에 맡기는 경우가 많다. 이 도구들은 "할당된 서버는 서버가 끝났다고 알릴 때까지 지우지 않는다"를 상태로 들고 있다. 그 수명 모델과, 끝이 없는 월드 서버에는 이 모델이 왜 그대로 맞지 않는지는 세션 기반과 지속 세계에서 다룬다.

선택 기준

서버 종류맞는 배치이유
로그인, 로비, 상점·우편 APIDeployment + Service + HPA요청이 짧고 상태가 바깥에 있다. 아무 Pod나 지워도 된다
게이트웨이Deployment, 축소는 천천히연결을 들고 있어서 지우면 재접속 폭주가 난다. 드레이닝을 길게 잡는다
판 단위 세션 서버게임 서버 전용 오케스트레이터할당 상태와 종료 신호를 도구가 이해한다
월드·존 서버직접 만든 관리 계층, 또는 전용 컨트롤러끝나는 시점이 없어서 교체 시점과 인계를 우리가 정한다
DB, 메시지 브로커관리형 서비스, 또는 운영 경험이 있을 때만 StatefulSet장애 복구와 백업이 오케스트레이터의 일이 아니다

게임 서버에서는

  • 자원 요청과 한도를 같은 값으로 두는 쪽이 틱에 안전하다. 한도가 요청보다 높으면 노드가 붐빌 때 CPU를 빼앗기고, CPU 한도에 닿으면 남은 주기 동안 멈춘다. 지연에 민감한 시뮬레이션 서버는 CPU를 넉넉히 요청하고, 다른 Pod와 한 노드에 몰리지 않게 배치 규칙을 건다.
  • 노드 정비가 서버를 내린다. 클라우드 노드 교체나 클러스터 업그레이드는 Pod를 축출한다. PodDisruptionBudget으로 한 번에 빠지는 수를 제한하고, 플레이어가 있는 서버는 축출 전에 세션을 빼는 경로를 탄다.
  • 로그와 덤프는 컨테이너 밖으로 보낸다. 크래시로 재시작되면 컨테이너 안의 파일은 함께 사라진다. 로그는 표준 출력으로 내보내 수집기가 가져가게 하고, 덤프는 볼륨에 남긴다(크래시 덤프와 심볼).
  • 설정과 비밀은 이미지에 굽지 않는다. 환경마다 다른 값은 ConfigMap과 비밀 저장소에서 넣는다(시크릿과 키 관리). 그래야 같은 이미지가 모든 환경에 올라간다(배포 파이프라인).

주의 사항

  • 오케스트레이터가 배포 전략을 대신 정하지 않는다. 롤링이든 한꺼번에 교체든 도구는 고를 수 있게 해 줄 뿐이다. 플레이어가 붙은 서버를 어떤 순서로 바꿀지는 무중단 패치에서 정한다.
  • 재시작은 복구가 아니다. 생존 프로브가 실패해 재시작되면 증상은 사라져도 원인은 남는다. 재시작 횟수를 지표로 남기고, 늘어나면 원인을 찾는다.
  • 메모리 한도에 걸린 종료는 예외 로그가 남지 않는다. 커널이 바로 끝내기 때문이다. 재시작 사유(OOMKilled)를 오케스트레이터 쪽에서 확인한다.
  • 컨테이너 격리는 보안 경계로 충분하지 않다. 커널을 함께 쓰므로, 남의 코드를 돌리는 용도라면 더 강한 격리가 필요하다. 이미지는 루트가 아닌 사용자로 실행한다.
