먼저 읽을 것: 무중단 패치, ORM과 저장 설계, DB 확장: 복제와 샤딩

핵심 요약

롤링이나 카나리로 배포하는 동안에는 옛 코드와 새 코드가 함께 돌고, 둘은 같은 데이터베이스를 본다. 스키마를 배포와 같은 순간에 한 번에 바꾸면, 그 순간부터 한쪽 코드가 없는 열을 찾는다. 판이 섞이는 구간이 그대로 장애 구간이 된다.

그래서 스키마 변경을 코드 배포와 떼어 여러 단계로 나눈다. 이 방식을 확장·축소(expand/contract)라고 부른다. 새 모양을 먼저 더하고, 옛 모양과 새 모양을 함께 유지하는 전환기를 두고, 옛 모양을 읽는 코드가 모두 사라진 뒤에 지운다. 전환기에는 두 모양을 함께 유지하는 비용이 들지만, 축소하기 전까지는 언제든 되돌릴 수 있다.

동작 원리

한 번에 바꾸면 두 판이 동시에 정상인 순간이 없다

캐릭터 테이블의 char_name 열을 display_name으로 바꾸는 경우를 보자.

DB에 있는 열옛 코드새 코드
char_name만정상없는 열을 찾는다
display_name만없는 열을 찾는다정상
둘 다정상정상

두 판이 함께 정상인 것은 두 열이 모두 있을 때뿐이다. 확장·축소는 이 "둘 다 있는" 상태를 일부러 만들어, 배포가 진행되는 동안 유지하는 방법이다. 배포를 되돌려도 마찬가지다. 새 코드를 옛 코드로 되돌리는 순간에도 옛 열이 살아 있어야 한다.

확장, 전환기, 축소

  1. 확장. 새 열을 NULL 허용으로 더한다. 기존 것을 바꾸지 않으므로 옛 코드는 아무 영향이 없다. 코드 배포와 같은 날일 필요도 없다.
  2. 두 곳에 쓰기. 새 코드를 배포한다. 쓸 때 두 열에 같은 값을 넣고, 읽기는 아직 옛 열에서 한다. 이때 옛 코드로 되돌려도 옛 열이 정본이므로 문제가 없다.
  3. 백필. 새 열이 비어 있는 기존 행을 옛 열 값으로 채운다. 나눠서 천천히 한다(아래).
  4. 읽기 전환. 두 열이 같은지 확인한 뒤, 읽기를 새 열로 옮기는 코드를 배포한다. 옛 열 쓰기는 한 배포 더 남겨 두면 되돌리기가 쉽다.
  5. 축소. 옛 열 쓰기를 멈추는 코드를 배포하고, 옛 열을 읽거나 쓰는 코드가 어디에도 없다는 것을 확인한 뒤 옛 열을 지운다. 배치 작업, 운영 툴, 통계 쿼리, 다른 팀 서비스까지 확인 대상이다.

백필은 나눠서 천천히 한다

수천만 행을 한 문장으로 갱신하면, 트랜잭션 하나가 오래 잡히고 로그가 한꺼번에 쏟아진다. 그 사이 다른 쓰기는 락을 기다리고, 복제본은 그 로그를 따라잡느라 몇 분씩 뒤처진다(DB 확장). 그래서 기본 키 범위로 잘라 작은 트랜잭션으로 나누고, 묶음 사이에 쉰다. 

-- 한 번에 5000행씩. 이미 채운 행은 건너뛰므로 중간에 멈췄다가 다시 돌려도 된다.
UPDATE characters
   SET display_name = char_name
 WHERE id > @from AND id <= @from + 5000
   AND display_name IS NULL;
  • 묶음 크기와 쉬는 시간은 복제 지연과 락 대기를 보면서 조절한다. 복제 지연이 기준을 넘으면 잠시 멈추게 만들어 둔다.
  • 마지막으로 처리한 키를 기록해 두면, 중간에 끊겨도 이어서 돌릴 수 있다.
  • 백필이 도는 동안에도 두 곳에 쓰기가 켜져 있어야 한다. 그래야 백필이 지나간 행이 그 뒤에 바뀌어도 두 열이 같은 값을 유지한다.

짧은 ALTER 한 줄도 서비스를 멈출 수 있다

스키마를 바꾸는 문장은 실행 시간이 짧아도, 시작하려면 테이블에 대한 독점 락을 잠깐 잡아야 한다. 그런데 그 테이블을 읽는 긴 트랜잭션이 하나 열려 있으면 ALTER는 그 트랜잭션이 끝나기를 기다린다. 문제는 그 뒤다. ALTER가 기다리는 동안 그 테이블에 들어오는 다른 쿼리들도 ALTER 뒤에 줄을 선다. 몇 밀리초짜리 변경이 테이블 전체를 몇 분간 멈춘다.

막는 법은 락 대기 시한을 짧게 두고, 실패하면 다시 시도하는 것이다. PostgreSQL은 SET lock_timeout = '2s', MySQL은 SET SESSION lock_wait_timeout = 2처럼 그 세션에만 건다. 실행 전에 오래 열린 트랜잭션이 없는지도 본다.

변경MySQL 8.0 (InnoDB)PostgreSQL
열 추가ALGORITHM=INSTANT로 메타데이터만 바꾼다11부터 상수 기본값이 있어도 테이블을 다시 쓰지 않는다. 호출할 때마다 값이 바뀌는 기본값(시각 함수 등)은 다시 쓴다
인덱스 추가ALGORITHM=INPLACE, LOCK=NONE으로 쓰기를 막지 않고 만든다CREATE INDEX CONCURRENTLY. 트랜잭션 안에서는 못 쓰고, 실패하면 무효 인덱스가 남아 지워야 한다
열 타입 변경대개 테이블을 복사해 다시 만든다대개 테이블을 다시 쓴다
기존 열에 NOT NULL테이블을 다시 만들 수 있다전체를 훑어 검사한다. CHECK ... NOT VALID를 먼저 걸고 VALIDATE한 뒤 SET NOT NULL을 하면 긴 락을 피한다(12부터)

MySQL에서 ALGORITHM과 LOCK을 적어 두면, 그 방식으로 할 수 없을 때 조용히 테이블 복사로 넘어가지 않고 바로 오류를 낸다. 의도하지 않은 긴 잠금을 막는 안전장치다. 테이블을 다시 만들어야 하는 큰 변경은 gh-ost나 pt-online-schema-change 같은 도구로 그림자 테이블을 만들어 복사한 뒤 바꿔치기한다.

옛 모양을 세워 두는 방법

방법하는 일언제 맞나비용
응용의 이중 쓰기새 코드가 두 모양에 모두 쓴다대부분의 경우. 변경 이력이 코드 저장소에 남는다두 경로가 배포마다 맞아야 한다
트리거한쪽에 들어온 값을 DB가 다른 쪽에도 넣는다옛 코드를 고칠 수 없는데 옛 모양에도 쓰기가 들어올 때로직이 DB 안에 숨는다. 쓰기마다 비용이 붙는다
뷰새 테이블 위에 옛 이름과 구조를 보여 준다옛 코드가 읽기만 할 때(통계, 운영 툴)쓰기는 대개 막힌다

축소 전에 두 모양이 같은지 확인한다

이중 쓰기에 빠진 경로가 하나라도 있으면 두 열의 값이 어긋난다. 축소한 뒤에는 어긋났는지조차 알 수 없다. 읽기를 옮기기 전과 축소하기 전에 비교 쿼리를 돌린다. 

SELECT COUNT(*) FROM characters
 WHERE display_name IS NULL
    OR display_name <> char_name;   -- 0이어야 다음 단계로 간다

0이 아니면 어느 쓰기 경로가 한쪽만 고치는지 찾는다. 대개 배치 작업, 운영 툴의 직접 UPDATE, 저장 프로시저 같은 "코드 밖" 경로다.

마이그레이션 도구는 순서를 기록할 뿐이다

EF Core 마이그레이션이나 Flyway 같은 도구는 어떤 변경을 어떤 순서로 적용했는지 기록해 준다. 무중단으로 나누는 일은 대신해 주지 않는다. EF Core에서 속성 이름을 바꾸면 RenameColumn 한 줄이 생성되는데, 이것이 바로 "한 번에 바꾸기"다. 무중단이 필요하면 생성된 마이그레이션을 위의 단계로 직접 나눈다. 

// 전환기의 엔티티: 두 열을 함께 매핑하고, 쓸 때 둘 다 채운다.
public class Character
{
    public long Id { get; set; }
    [Obsolete("축소 단계에서 지운다")] public string CharName { get; set; } = "";
    public string? DisplayName { get; set; }

    public void Rename(string name)
    {
#pragma warning disable CS0618
        CharName = name;          // 옛 코드가 아직 읽는다
#pragma warning restore CS0618
        DisplayName = name;
    }
}

운영 DB에는 서버가 시작할 때 마이그레이션을 자동 적용하게 두지 않는다. 여러 인스턴스가 한꺼번에 뜨면 동시에 적용하려 들고, 누가 무엇을 언제 바꿨는지가 배포 기록에 남지 않는다. 마이그레이션을 SQL 스크립트로 뽑아(dotnet ef migrations script --idempotent) 검토하고, 배포 파이프라인의 별도 단계에서 적용한다(배포 파이프라인).

선택 기준

변경필요한 단계
NULL 허용 열·새 테이블 추가확장만. 코드는 나중에 써도 된다
열·테이블 삭제코드에서 먼저 쓰지 않게 배포하고, 그다음 축소
열 이름 변경확장 → 이중 쓰기 → 백필 → 읽기 전환 → 축소 전부
열 타입 변경새 열을 더해 이름 변경과 같은 순서로. 제자리 변경은 테이블을 다시 쓴다
테이블 나누기·합치기이중 쓰기와 비교 검증을 길게 둔다
인덱스 추가온라인 방식으로 따로 실행한다. 코드 배포와 묶지 않는다

어떤 경우든 축소는 가장 늦게, 따로 한다. 옛 모양을 읽는 쪽이 이미 나간 클라이언트나 다른 팀 서비스처럼 손댈 수 없는 곳이면, 그쪽이 다 바뀔 때까지 축소를 미룬다. 프로토콜의 "빼는 것은 클라이언트 먼저"와 같은 규칙이다(클라이언트와 서버의 판 호환).

게임 서버에서는

  • 점검이 있어도 걸리는 시간을 먼저 잰다. 점검 시간 안에 끝낼 대량 변경은 운영 데이터 크기의 복제 DB에서 미리 돌려 시간을 잰다. 예상보다 길어지면 점검이 늘어난다. 되돌릴 수 없는 변경 앞에는 백업을 확인한다(백업과 복구).
  • 로그 테이블은 파티션을 미리 만든다. 날짜별 파티션은 배포와 무관하게 정기 작업으로 몇 주 앞까지 만들어 둔다. 새 파티션이 없어 그날 첫 로그 쓰기가 실패하는 사고를 막는다. 오래된 파티션은 행 삭제 대신 파티션째 떼어 낸다.
  • 샤드마다 차례로 적용하고 기록한다. 월드나 샤드마다 DB가 따로면, 한 곳에 먼저 적용해 보고 나머지로 넓힌다. 어느 DB에 어느 마이그레이션까지 적용됐는지 기록하는 테이블을 둔다. 일부 샤드만 바뀐 상태로 오래 두지 않는다.
  • 기획 데이터 ID는 바꾸지 않는다. 아이템 ID나 퀘스트 ID를 재배치하면 저장된 모든 행을 이행해야 한다. ID는 새로 만들고 옛 것은 사용 중지로 둔다(기획 데이터).
  • 저장 코드도 전환기를 견뎌야 한다. 주기 저장 큐에 쌓인 옛 형식 저장 요청이 배포 뒤에 처리될 수 있다. 저장 형식을 바꿀 때는 옛 형식 요청도 받아 처리하게 둔다(ORM과 저장 설계).

주의 사항

  • 확장, 코드 배포, 축소를 한 번의 배포로 묶으면 전환기가 사라진다. 배포 횟수가 느는 것이 이 방식의 비용이다.
  • NOT NULL이나 UNIQUE 같은 제약은 데이터를 다 채운 뒤에 건다. 백필 중에 걸면 아직 비어 있는 행 때문에 쓰기가 실패한다.
  • 열을 지울 때 SELECT *를 쓰는 코드가 있으면, 열 순서나 개수에 기대는 매핑이 조용히 깨진다. 필요한 열을 이름으로 적는다.
  • 확장·축소는 같은 데이터의 모양을 언제 바꾸느냐의 문제다. 데이터를 어디에 나눠 둘지(샤딩·복제)와는 다른 문제다.
