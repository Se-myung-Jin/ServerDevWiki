먼저 읽을 것: 전달 보장과 exactly-once, 서비스 호출: 타임아웃·재시도·데드라인, 큐와 백프레셔

핵심 요약

최소 한 번 전달에서는 확인을 받지 못한 메시지가 다시 온다. 형식이 깨졌거나 버그를 건드리는 메시지는 몇 번을 다시 받아도 실패한다. 이런 메시지를 독 메시지(poison message)라고 한다. 그대로 두면 같은 메시지가 끝없이 돌아와 큐를 붙잡는다.

데드레터 큐(DLQ)는 한 메시지를 받은 횟수가 상한을 넘으면 그 메시지를 따로 옮긴다. 서킷 브레이커는 한 대상으로 가는 호출이 계속 실패하면 한동안 그 대상을 아예 부르지 않는다. 앞쪽은 상한을 메시지 하나에 걸고, 뒤쪽은 대상 하나에 건다. 보는 단위가 달라서 서로를 대신하지 못한다.

둘을 함께 쓸 때 순서가 중요하다. 대상이 통째로 죽어 있는 동안 들어온 메시지를 DLQ로 보내면, 멀쩡한 메시지가 전부 독으로 몰린다. 서킷이 열려 있으면 메시지를 옮기지 말고 소비를 멈춘다.

동작 원리

독 메시지는 큐 하나를 통째로 막는다

DLQ는 실패 횟수가 아니라 받은 횟수를 센다. 브로커는 소비자가 왜 확인을 안 보냈는지 모른다. 처리 도중 프로세스가 죽은 것도, 예외가 난 것도 똑같이 "다시 보냄"이다. 그래서 상한은 일시적인 실패 몇 번을 버틸 만큼 넉넉해야 한다. 보통 3~10 사이에서 시작한다.

브로커마다 DLQ를 두는 자리가 다르다

브로커횟수를 세는 곳옮기는 주체
Amazon SQS재처리 정책(redrive policy)의 maxReceiveCount브로커가 지정한 DLQ로 옮긴다. DLQ에서 원본 큐로 되돌리는 기능도 있다
RabbitMQ쿼럼 큐의 x-delivery-limit상한을 넘거나 거절(reject, requeue=false)된 메시지를 x-dead-letter-exchange로 보낸다
Azure Service Bus큐 설정의 최대 전달 횟수(MaxDeliveryCount)큐마다 딸린 데드레터 하위 큐로 옮긴다
Kafka브로커에는 없다소비자가 직접 센다. 처리에 실패한 레코드를 별도 DLQ 토픽에 쓰고 오프셋을 넘긴다. Kafka Connect에는 오류 레코드를 DLQ 토픽으로 보내는 설정이 있다

Kafka는 로그라서 메시지 하나를 "뺄" 수 없다(메시지 모델 세 갈래). 실패한 레코드에서 멈추면 그 파티션 전체가 멈추고, 건너뛰면 그 레코드는 잊힌다. 그래서 소비자가 몇 번 다시 시도한 뒤 DLQ 토픽에 복사해 두고 다음 오프셋으로 간다. 순서가 중요한 키라면 같은 키의 뒤 레코드도 함께 미뤄야 순서가 어긋나지 않는다.

DLQ로 옮긴 뒤가 진짜 일이다

옮기는 것은 처리가 아니다. 원본 큐에서 빠졌을 뿐, 그 메시지가 시키던 일은 그대로 남아 있다. DLQ를 만들 때 다음을 함께 정한다.

  • 알림: DLQ에 메시지가 하나라도 들어오면 경보를 낸다. 쌓이는 것을 아무도 모르면 DLQ는 쓰레기통이 된다.
  • 원인 기록: 옮길 때 마지막 예외, 시도 횟수, 처음 받은 시각, 원본 큐 이름을 메시지 머리에 붙인다. 나중에 본 사람이 재현할 수 있어야 한다.
  • 재처리 도구: 원인을 고친 뒤 골라서 원본 큐로 되돌리는 도구를 둔다. 되돌린 메시지는 한 번 더 처리되므로 소비자가 멱등해야 한다(멱등 소비자).
  • 보존 기간: DLQ에도 보존 기간이 있다. 원본 큐의 기간보다 길게 둬야 원인을 찾는 동안 사라지지 않는다.

서킷 브레이커는 실패하는 대상을 한동안 부르지 않는다

재시도는 일시적인 실패를 넘기는 장치다(서비스 호출). 대상이 몇 분째 죽어 있으면 재시도는 실패를 늘릴 뿐이다. 매 요청이 타임아웃까지 기다리니 호출한 쪽의 스레드와 커넥션 풀이 바닥나고, 이미 넘어진 대상에는 재시도까지 몰려 회복이 늦어진다. 서킷 브레이커는 이 연쇄를 끊는다.

전이 조건은 네 가지 값으로 정한다.

  • 실패율 기준: 표본 구간 안 호출 가운데 실패 비율이 이 값을 넘으면 연다. 실패 개수가 아니라 비율로 보면 트래픽 크기와 상관없이 같은 뜻이 된다.
  • 최소 요청 수: 표본 구간에 이만큼 호출이 있어야 판단한다. 호출 2개 중 1개 실패로 50%가 나와 서킷이 열리는 일을 막는다.
  • 표본 구간: 실패율을 잴 시간 창이다. 너무 길면 늦게 열리고, 너무 짧으면 순간 잡음에 열린다.
  • 차단 시간: 열린 뒤 반열림으로 가기까지 기다리는 시간이다. 대상이 다시 일어날 시간을 준다.

무엇을 실패로 셀지도 정한다. 타임아웃, 연결 실패, 5xx는 센다. 400 같은 요청 쪽 잘못은 대상이 아프다는 신호가 아니니 세지 않는다.

.NET에서는 복원력 파이프라인에 넣는다

.NET 8부터 쓰는 Microsoft.Extensions.Http.Resilience는 Polly v8 위에 서 있고, 표준 파이프라인에 서킷 브레이커가 이미 들어 있다. 위 네 값이 그대로 옵션 이름이다. Polly의 기본값은 실패율 10%, 최소 요청 100개, 표본 30초, 차단 5초다. 게임 서버의 외부 호출은 트래픽이 작은 경우가 많아 최소 요청 수를 낮춰야 판단이 시작된다. 

builder.Services.AddHttpClient<PaymentClient>()
    .AddStandardResilienceHandler(o =>
    {
        o.CircuitBreaker.FailureRatio = 0.5;                       // 절반 넘게 실패하면
        o.CircuitBreaker.MinimumThroughput = 20;                   // 30초에 20번 이상 불렀을 때만
        o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
        o.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(15); // 15초 동안 부르지 않는다
    });

// 열린 동안의 호출은 BrokenCircuitException으로 바로 실패한다.
try { await payment.VerifyAsync(receipt, ct); }
catch (BrokenCircuitException) { return VerifyResult.RetryLater; } // 대상까지 가지 않았다

서킷 상태는 지표로 내보낸다. "결제 서킷 열림"은 그 자체로 경보다. 서킷이 자주 열렸다 닫히기를 되풀이하면 기준값이 너무 민감하거나 대상이 불안정한 것이다.

둘을 함께 쓰면 순서가 생긴다

받은 횟수 상한은 메시지마다 따로 센다. 대상이 죽어 있는 동안 소비자가 계속 꺼내 실패하면, 들어오는 메시지가 차례로 상한을 채운다. 나쁜 메시지는 하나도 없는데 그 시간의 메시지가 전부 격리된다. 그래서 소비자는 실패를 둘로 나눈다. 대상 쪽 실패(타임아웃, 연결 거부, 서킷 열림)는 메시지 탓이 아니니 확인하지 않고 내려놓은 뒤 소비 자체를 늦추거나 멈춘다. 메시지 쪽 실패(역직렬화 실패, 검증 실패, 같은 예외가 되풀이됨)만 DLQ 대상이다.

열린 동안 무엇을 돌려줄지 정해 둔다

서킷이 열리면 호출한 쪽은 결과 없이 돌아온다. 그 순간 무엇을 할지가 서비스 품질을 정한다.

대체 방법맞는 곳예
기본값없어도 화면이 뜨는 정보추천 상품 목록이 비면 고정 목록을 보여 준다
마지막으로 받은 값조금 낡아도 되는 정보랭킹 서비스가 죽으면 캐시된 순위를 "갱신 지연" 표시와 함께 쓴다
나중에 다시반드시 해야 하지만 지금일 필요는 없는 일지급 요청을 큐에 남겨 두고 서킷이 닫히면 처리한다
기능 끄기대체할 것이 없는 기능결제 검증이 안 되면 상점 구매 버튼을 잠시 막고 공지를 띄운다

선택 기준

상황재시도만DLQ만서킷만함께
잠깐 끊김넘긴다넘긴다열릴 일이 없다넘긴다
메시지 하나가 깨짐끝없이 다시 시도한다그 메시지만 옮긴다잡지 못한다그 메시지만 옮긴다
대상이 몇 분 죽음실패를 늘리며 대상을 더 누른다정상 메시지까지 옮긴다호출을 멈춘다. 메시지는 계속 실패한다소비를 멈췄다가 회복 뒤 이어 간다

메시지를 꺼내 외부를 부르는 소비자라면 셋을 함께 둔다. 요청-응답만 하는 API 호출이라면 재시도와 서킷으로 충분하고, DLQ 자리는 "실패를 기록하고 나중에 다시"가 대신한다.

게임 서버에서는

  • 결제 검증 서버나 플랫폼 API가 죽으면 서킷을 연다. 열린 동안 들어온 영수증은 거절하지 말고 "검증 대기"로 저장한다. 서킷이 닫히면 대기분을 다시 검증하고 지급한다. 거래 번호로 한 번만 지급하므로 다시 해도 안전하다(결제와 영수증 검증).
  • 우편 지급 메시지의 DLQ는 CS가 본다. 아이템 ID가 기획 데이터에서 지워졌거나 캐릭터가 삭제된 경우 메시지는 몇 번을 다시 받아도 실패한다. 이런 메시지가 DLQ로 오면 운영 도구에서 계정, 아이템, 실패 이유를 보여 주고 "대체 지급"이나 "폐기"를 고르게 한다.
  • 채팅 필터 서비스가 죽어도 채팅은 돈다. 서킷이 열리면 로컬 금칙어 목록만으로 거르고, 서비스가 돌아오면 원래 경로로 돌아간다. 필터 때문에 채팅 전체가 멈추면 장애 범위가 커진다.
  • 로직 스레드에서는 서킷 상태만 본다. 서킷이 열렸는지는 값 하나를 읽는 일이라 틱 안에서 해도 된다. 실제 호출은 로직 스레드 밖에서 한다(게임 서버 스레딩 모델).
  • 점검 직후에는 DLQ부터 본다. 새 판의 역직렬화 오류나 바뀐 메시지 형식은 배포 직후 DLQ에 몰린다. 판이 섞이는 동안의 메시지 형식은 클라이언트와 서버의 판 호환과 같은 원칙으로 맞춘다.

주의 사항

  • DLQ로 옮기는 것은 처리가 아니다. 알림과 재처리 절차가 없는 DLQ는 실패를 조용히 숨긴다.
  • 받은 횟수 상한을 1~2로 두지 않는다. 배포 중 재시작이나 순간 장애 한 번에 정상 메시지가 옮겨진다.
  • 재처리 도구로 되돌린 메시지는 두 번째 처리다. 멱등하지 않은 소비자에 되돌리면 이중 지급이 난다.
  • 서킷 브레이커는 원인을 고치지 않는다. 회복할 시간을 벌어 줄 뿐이라, 대상이 그동안 회복하지 않으면 반열림에서 다시 열린다.
  • 서킷을 대상 인스턴스 하나가 아니라 서비스 전체에 하나만 두면, 인스턴스 하나가 아파도 전체 호출이 막힌다. 부하 분산 뒤에 여러 인스턴스가 있다면 단위를 정해 둔다.
  • 열림 동안의 빠른 실패도 재시도 대상으로 잡으면 재시도가 서킷을 계속 두드린다. 서킷 거절은 재시도하지 않는다.
