먼저 읽을 것: 무중단 패치, 프로토콜 설계

핵심 요약

서버 판은 배포가 바꾸고, 클라이언트 판은 사용자가 갱신해야 바뀐다. 서버는 몇 시간이면 새 판으로 모이지만, 클라이언트는 스토어 심사와 단계적 출시, 자동 업데이트를 꺼 둔 사용자 때문에 며칠에 걸쳐 바뀐다. 그래서 판이 섞여 있는 기간은 서버 배포보다 길고, 배포 시스템 혼자 끝내지 못한다.

이 기간을 다루는 방법은 세 갈래다. 옛 판을 받지 않고 업데이트를 요구하는 강제 업데이트, 서버가 여러 판을 함께 받는 범위 지원, 판마다 다른 서버 무리로 보내는 판별 라우팅이다. 어느 쪽이든 판은 접속할 때 한 번 확인하고, 순서는 "더하는 것은 서버 먼저, 빼는 것은 클라이언트 먼저"를 지킨다.

동작 원리

서버 판과 클라이언트 판은 다른 일정으로 바뀐다

서버 쪽에도 기간을 늘리는 것이 있다. 판 단위 세션 서버는 진행 중인 판이 끝날 때까지 옛 판으로 남고(세션 기반과 지속 세계), 카나리는 관찰하는 동안 두 판을 일부러 함께 둔다(무중단 패치). 서버 배포가 끝났다고 프로토콜이 하나가 되지는 않는다.

판은 접속할 때 한 번 확인한다

판 확인은 연결을 맺은 직후, 로그인처럼 비싼 일을 하기 전에 한다. 클라이언트가 첫 메시지에 판 정보를 싣고, 서버는 받아들일지, 업데이트를 요구할지, 다른 서버로 보낼지를 답한다.

싣는 값무엇을 가리나
프로토콜 판 번호메시지 형식이 통하는지. 빌드 번호와 따로 둔다. 빌드는 자주 바뀌어도 프로토콜은 그대로일 수 있다
클라이언트 빌드와 플랫폼플랫폼마다 출시 시점이 다르다. 판별 지표와 버그 추적에도 쓴다
기획 데이터 판(해시)코드는 같아도 테이블이 다를 수 있다. 다르면 데이터만 내려받게 한다(기획 데이터)
 
// 접속 직후 첫 메시지. 로그인 전에 판부터 가린다.
HelloResult Check(Hello h)
{
    var policy = _versionPolicy.Current;           // 중앙 설정. 재배포 없이 바꾼다
    if (h.Protocol < policy.MinProtocol)
        return HelloResult.UpdateRequired(policy.StoreUrl(h.Platform));
    if (h.Protocol > policy.MaxProtocol)
        return HelloResult.Redirect(_router.GroupFor(h.Protocol)); // 새 판 서버 무리로
    if (h.DataHash != _tables.Hash)
        return HelloResult.DataPatch(_tables.Version);
    return HelloResult.Ok;
}

최소·최대 지원 판은 코드에 박지 않고 중앙 설정에 둔다. 옛 판에서 심각한 버그가 발견되면 배포 없이 최소 판만 올려 바로 막을 수 있어야 한다.

판이 맞지 않을 때 고르는 정책

정책하는 일장점비용
강제 업데이트최소 지원 판보다 낮으면 스토어로 보낸다서버가 한 판만 알면 된다심사·출시가 끝나기 전에는 쓸 수 없다. 사용자가 막힌다
범위 지원서버가 N판과 N-1판을 함께 받는다사용자가 막히지 않는다서버 코드가 두 판의 차이를 안다. 시험할 조합이 는다
판별 라우팅클라이언트 판에 맞는 서버 무리로 보낸다서버 코드는 한 판만 안다서버를 두 벌 운영한다. 매칭·파티·거래가 판마다 갈린다

실무에서는 섞어 쓴다. 평소에는 범위 지원으로 한두 판을 받고, 프로토콜을 크게 바꾸는 패치는 판별 라우팅으로 넘기고, 옛 판 비율이 충분히 줄면 최소 지원 판을 올려 강제 업데이트로 끝낸다.

서버가 두 판을 받게 만드는 규칙

범위 지원이 가능하려면 메시지 형식부터 바뀔 것을 전제로 설계해야 한다. 필드는 번호로 식별하고, 지운 번호는 다시 쓰지 않고, 모르는 필드는 무시한다. 이 규칙은 프로토콜 설계가 다룬다. 여기서는 운영에서 자주 부딪히는 두 가지만 짚는다.

  • 새 필드가 없을 때의 동작을 정한다. 옛 클라이언트는 새 필드를 보내지 않는다. 서버는 그 필드가 빠진 요청을 "옛 판의 동작"으로 처리해야 한다. 기본값이 곧 옛 동작이 되게 고른다.
  • 의미를 바꾸지 말고 새로 만든다. 같은 필드에 다른 단위나 다른 뜻을 실으면, 두 판이 같은 값을 서로 다르게 읽는다. 오류가 나지 않고 값만 틀려서 가장 찾기 어렵다.

더하는 것은 서버 먼저, 빼는 것은 클라이언트 먼저

새 메시지나 필드를 더할 때는 서버가 먼저 받을 줄 알아야 한다. 서버를 먼저 배포해 두고, 그 뒤에 새 클라이언트를 낸다. 반대로 하면 새 클라이언트가 옛 서버에 모르는 메시지를 보낸다. 롤링 도중이나 서버를 되돌린 직후에도 이런 일이 생기므로, 서버는 모르는 메시지를 받으면 연결을 끊지 말고 기록한 뒤 버린다.

빼는 것은 거꾸로다. 먼저 클라이언트가 그 메시지를 쓰지 않는 판을 내고, 옛 판 비율이 줄면 최소 지원 판을 올린다. 그 다음에야 서버에서 처리 코드를 지운다. 이 순서는 DB의 확장·축소와 같은 모양이다(스키마 변경과 배포 분리). 두 모양을 함께 받는 기간을 일부러 두고, 옛 쪽이 다 사라진 뒤 정리한다.

스토어 심사와 단계적 출시가 기간을 늘린다

모바일 클라이언트는 서버처럼 원하는 시각에 내보낼 수 없다. 스토어 심사에 걸리는 시간이 매번 다르고, 플랫폼마다 승인 시점도 다르다. 단계적 출시를 쓰면 일부 사용자에게만 먼저 간다. 자동 업데이트를 꺼 둔 사용자는 직접 갱신할 때까지 옛 판에 머문다. 그래서 서버 배포 일정은 "클라이언트가 언제 나갈지 모른다"를 전제로 짠다. 서버를 먼저 올려 두고, 새 기능은 기능 플래그로 꺼 두었다가 클라이언트가 충분히 퍼지면 켠다.

선택 기준

상황고르는 정책
필드 추가처럼 하위 호환이 되는 변경범위 지원. 강제 업데이트할 이유가 없다
옛 판에 보안 문제나 재화 버그최소 지원 판을 올려 즉시 강제 업데이트
메시지 구조를 크게 바꾸는 대형 패치판별 라우팅으로 넘긴 뒤 옛 판 무리를 줄인다
모든 사용자가 같은 규칙을 봐야 하는 대회·시즌 시작점검과 강제 업데이트. 섞인 기간 자체를 없앤다

게임 서버에서는

  • 같은 판끼리만 만나게 한다. 판별 라우팅이나 범위 지원 중에도 매칭, 파티, 거래, 같은 필드 입장은 같은 프로토콜 판끼리 묶는다. 서버마다 판을 달아 두고, 매칭 큐를 판별로 나눈다(매치메이킹). 판이 다른 친구끼리 파티가 안 되는 이유를 화면에 알려 준다.
  • 판별 접속 비율을 지표로 본다. 최소 지원 판을 언제 올릴지는 감이 아니라 숫자로 정한다. 옛 판 접속이 몇 퍼센트 아래로 내려가면 올린다는 기준을 미리 둔다.
  • 업데이트 요구는 친절하게. 끊어 버리지 말고, 이유와 스토어 주소를 담은 응답을 보낸다. 클라이언트는 그 응답을 받는 코드를 첫 판부터 가지고 있어야 한다. 이 경로가 없으면 나중에 업데이트를 요구할 방법이 없다.
  • 데이터만 다른 경우를 따로 다룬다. 코드 판은 같고 기획 테이블만 바뀌었다면 클라이언트 재설치 없이 데이터 패치만 내려받게 한다. 판 확인에서 데이터 해시를 따로 보는 이유다.
  • 서버끼리의 프로토콜도 같은 문제다. 롤링 중에는 게이트웨이와 존 서버, 서버와 서버가 서로 다른 판으로 대화한다. 내부 메시지에도 판 번호와 같은 호환 규칙을 적용한다.

주의 사항

  • 빌드 번호를 프로토콜 판으로 쓰지 않는다. 그러면 메시지가 그대로인 핫픽스 클라이언트도 모두 "다른 판"이 되어 불필요하게 갈린다.
  • 판 확인을 클라이언트에만 맡기지 않는다. 클라이언트가 "업데이트가 필요하다"고 스스로 판단하게 하면, 고쳐진 클라이언트는 확인을 건너뛴다. 판단은 서버가 한다.
  • 범위 지원은 두 판까지로 제한한다. 받는 판이 늘수록 조합 시험이 곱으로 는다.
  • 강제 업데이트는 스토어에 새 판이 실제로 올라간 뒤에 건다. 심사가 끝나지 않은 상태에서 최소 판을 올리면 아무도 접속하지 못한다.
