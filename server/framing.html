먼저 읽을 것: TCP와 UDP · 게임 서버 스레딩 모델

핵심 요약

TCP가 약속하는 것은 바이트가 빠짐없이 순서대로 온다는 것까지다. 보낸 Send 단위가 받는 쪽에 그대로 오지는 않는다(TCP와 UDP). 그래서 바이트 흐름에서 메시지 하나를 잘라 내는 규칙, 곧 프레이밍을 응용이 정해야 한다.

게임 서버의 표준은 길이를 앞에 붙이는 방식이다. 받는 쪽은 받은 바이트를 버퍼에 모으고, 헤더가 다 왔는지, 헤더에 적힌 길이만큼 본문이 다 왔는지를 확인해 하나씩 꺼낸다. 길이 값은 믿지 않고 상한을 검사한다. 한 번 잘못 자르면 그 뒤는 되돌릴 수 없어서 연결을 끊는다.

동작 원리

읽기 한 번에 메시지가 몇 개 들어 있을지 모른다

받는 쪽 루프는 항상 같은 두 질문을 반복한다. 헤더 크기만큼 모였나, 헤더에 적힌 길이만큼 본문이 모였나. 둘 다 맞으면 하나를 꺼내고 다시 처음부터 묻는다. 한 번 읽은 것에서 여러 개가 나올 수 있으니 꺼낼 것이 없을 때까지 돈다. 모자라면 남은 바이트를 버퍼에 그대로 두고 다음 읽기를 기다린다.

.NET에서는 System.IO.Pipelines가 이 누적 버퍼를 대신 관리한다. PipeReader가 지금까지 받은 바이트를 ReadOnlySequence<byte>로 넘기고, 응용은 어디까지 썼는지만 알려 준다. 

const int HeaderSize = 4;            // 길이 2바이트 + 메시지 종류 2바이트
const int MaxBodySize = 16 * 1024;   // 이보다 크다고 적혀 오면 끊는다

async Task ReadLoopAsync(PipeReader reader)
{
    while (true)
    {
        ReadResult result = await reader.ReadAsync();
        ReadOnlySequence<byte> buffer = result.Buffer;

        // 한 번 읽은 것에서 여러 개가 나올 수 있다
        while (TryReadMessage(ref buffer, out ushort type, out ReadOnlySequence<byte> body))
            Dispatch(type, body);    // body는 AdvanceTo 전까지만 유효하다. 넘길 거면 복사한다

        // 꺼낸 데까지는 버리고, 끝까지 들여다봤으니 더 올 때까지 기다리게 한다
        reader.AdvanceTo(buffer.Start, buffer.End);
        if (result.IsCompleted) break;   // 상대가 FIN을 보냈다
    }
    await reader.CompleteAsync();
}

bool TryReadMessage(ref ReadOnlySequence<byte> buffer, out ushort type, out ReadOnlySequence<byte> body)
{
    type = 0; body = default;
    if (buffer.Length < HeaderSize) return false;            // 헤더가 덜 왔다

    Span<byte> header = stackalloc byte[HeaderSize];
    buffer.Slice(0, HeaderSize).CopyTo(header);              // 헤더가 두 조각에 걸쳐 있을 수 있다
    int length = BinaryPrimitives.ReadUInt16LittleEndian(header);
    type = BinaryPrimitives.ReadUInt16LittleEndian(header[2..]);
    if (length > MaxBodySize) throw new InvalidDataException("body too large");

    if (buffer.Length < HeaderSize + length) return false;   // 본문이 덜 왔다
    body = buffer.Slice(HeaderSize, length);
    buffer = buffer.Slice(HeaderSize + length);
    return true;
}

AdvanceTo의 두 인자가 핵심이다. 첫째는 "여기까지는 다 썼으니 버려도 된다", 둘째는 "여기까지는 들여다봤다"는 뜻이다. 반쪽 메시지를 남겨 둔 채 둘째 인자를 끝으로 주면, 다음 ReadAsync는 새 바이트가 올 때까지 기다린다. 둘째 인자를 빼먹으면 같은 반쪽을 계속 다시 받아 CPU를 태운다.

Pipelines를 쓰지 않으면 세션마다 수신 버퍼를 두고 직접 관리한다. 꺼낸 앞부분을 버린 뒤 남은 바이트를 앞으로 당기거나, 원형 버퍼로 감아 쓴다. 버퍼를 메시지마다 새로 할당하지 않고 ArrayPool에서 빌려 쓰는 것이 보통이다(메모리 할당자, Span과 ref struct).

약속은 문서와 코드 한곳에 적고, 클라이언트와 서버가 같은 정의를 쓰게 한다. 직렬화 형식(Protobuf, MessagePack, 직접 만든 이진 형식)은 본문 안의 일이고, 프레이밍은 그 바깥에서 본문이 어디서 끝나는지만 정한다.

한 번 어긋나면 되돌릴 수 없다

길이 접두 방식에는 다시 맞출 기준점이 없다. 한 번 잘못 자르면 본문 중간을 다음 헤더로 읽고, 거기 적힌 아무 값을 길이로 쓴다. 파싱은 멈추지 않고 계속 엉뚱한 자리를 자른다. 그래서 증상이 보이는 곳은 원인에서 한참 떨어져 있고, 대개 "가끔 이상한 패킷이 온다"로 나타난다.

그러므로 헤더가 말이 안 되면(길이가 상한을 넘거나, 모르는 메시지 종류이거나, 본문 파싱이 실패하면) 그 연결을 바로 끊는다. 건너뛰고 계속 읽으려 해도 다음 메시지의 시작을 찾을 방법이 없다.

게임 서버에서는

  • 길이 값은 공격 경로다. 헤더에 4GB를 적어 보내는 클라이언트가 있다고 가정한다. 상한 검사 없이 그 크기로 버퍼를 할당하면 패킷 하나로 서버 메모리가 바닥난다. 길이를 읽자마자 상한과 비교하고, 넘으면 할당 전에 끊는다.
  • 덜 온 메시지도 자원을 잡는다. 헤더에 큰 길이를 적고 본문을 아주 천천히 보내면 서버는 그 버퍼를 계속 들고 기다린다. 세션별 수신 버퍼에 상한을 두고, 메시지 하나가 일정 시간 안에 다 오지 않으면 끊는다. 쌓인 양을 다루는 방법은 큐와 백프레셔에서 다룬다.
  • 보낼 때도 경계를 지킨다. 여러 스레드가 한 소켓에 각자 Send를 부르면 두 메시지의 바이트가 섞여 나갈 수 있다. 세션마다 송신 큐를 하나 두고 한 곳에서만 보낸다. 논블로킹 send는 일부만 보내고 돌아올 수 있으니 남은 바이트를 이어 보내야 한다.
  • 받은 순간 처리하지 않고 넘긴다. I/O 스레드는 메시지를 잘라 게임 로직 큐로 넘기기만 하고, 처리는 로직 스레드가 한다(게임 서버 스레딩 모델). 이때 ReadOnlySequence는 다음 읽기에서 덮어쓰이므로 꺼낸 본문을 복사하거나 바로 역직렬화한다.
  • 쪼개고 붙여 보는 시험을 따로 둔다. 같은 바이트열을 한 바이트씩 나눠 넣고, 여러 메시지를 한 번에 넣고, 헤더 중간에서 끊어 넣는 시험을 만든다. Pipe에 직접 조각을 써 넣으면 소켓 없이도 재현된다.

주의 사항

  • 로컬에서 잘 돈다는 것은 근거가 아니다. 작은 메시지가 빠른 망을 지나면 대개 한 번에 하나씩 도착해, 프레이밍이 틀려도 드러나지 않는다. 부하가 걸려 여러 메시지가 한 번에 나가거나 지연으로 나뉘어 올 때 터진다.
  • 헤더도 나뉘어 온다. 본문만 나뉜다고 생각하고 헤더는 한 번에 읽힌다고 가정하면, 헤더 4바이트가 2바이트씩 두 번에 오는 순간 깨진다.
  • UDP에는 이 문제가 없다. 데이터그램 하나가 메시지 하나다. 대신 한 데이터그램 안에 여러 메시지를 묶어 보낸다면 그 안에서는 길이로 다시 나눠야 한다.
  • 0바이트 읽기는 메시지가 아니다. 상대가 연결을 닫았다는 뜻이다. 이때 버퍼에 덜 온 메시지가 남아 있으면 그대로 버리고 세션을 정리한다(TCP 연결 관리).
