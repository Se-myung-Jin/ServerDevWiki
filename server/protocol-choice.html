먼저 읽을 것: TCP와 UDP · 메시지 경계와 프레이밍

핵심 요약

게임 하나가 프로토콜 하나를 쓰지 않는다. 로그인과 상점은 HTTP로, 채팅과 거래는 TCP나 신뢰 채널로, 위치와 입력은 UDP 비신뢰 채널로 보낸다. 데이터마다 잃어도 되는지, 늦어도 되는지, 어디까지 순서가 맞아야 하는지가 다르기 때문이다.

프로토콜 고르기는 전송 계층만의 문제가 아니다. 먼저 누가 결과를 정하는지(서버 권위)를 나누고, 데이터마다 채널을 정하고, 바이트로 바꾸는 직렬화 포맷을 고르고, 클라이언트와 서버의 버전이 달라도 통하도록 호환 규칙을 정한다. 이 네 가지가 한 묶음이다.

동작 원리

누가 정하는지부터 나눈다

결과에 영향을 주는 것은 서버가 정하고, 클라이언트는 입력을 보내고 결과를 받는다. 클라이언트는 사용자의 손에 있어서 언제든 조작될 수 있기 때문이다.

무엇클라이언트가 보내는 것서버가 하는 일
이동입력(방향, 속도)이나 희망 위치속도와 충돌을 검증하고 확정 위치를 돌려준다
공격 · 피격"이 방향으로 쐈다"명중과 피해를 판정한다
아이템 · 재화요청만지급과 차감을 정하고 저장한다
이펙트 · 소리 · UI없음관여하지 않는다. 클라이언트가 알아서 그린다

서버가 정하면 왕복 시간만큼 결과가 늦게 보인다. 이것을 감추려고 클라이언트가 결과를 먼저 그려 보고 나중에 서버 값으로 맞추는데, 그 방식은 상태 동기화에서 다룬다. 서버를 아예 거치지 않는 P2P는 서버 비용과 지연이 줄지만 판정을 참가자가 나눠 갖는다. 연결 방법과 장단점은 NAT 뒤에서 직접 연결하기에 있다.

데이터마다 채널을 나눈다

잃어도 되는지만으로는 부족하다. "순서가 어디까지 맞아야 하나"도 따로 정해야 한다. 순서를 넓게 맞출수록 하나를 잃었을 때 함께 기다리는 범위가 넓어진다.

전달 방식잃으면순서맞는 데이터
비신뢰그대로 잃는다맞추지 않는다매번 새로 보내는 소리 신호, 효과
순번만(sequenced)그대로 잃는다옛것이 늦게 오면 버린다위치, 입력. 최신 하나만 쓴다
신뢰 · 비순서다시 보낸다도착한 대로 넘긴다서로 독립인 확정 이벤트(피격, 획득 알림)
신뢰 · 순서다시 보낸다채널 안에서 맞춘다채팅, 거래 단계, 인벤토리 변경

C#의 LiteNetLib는 이 넷에 가까운 전달 방식(Unreliable, Sequenced, ReliableUnordered, ReliableOrdered, ReliableSequenced)을 메시지마다 고르게 하고, ENet은 채널 번호로 나눠 채널마다 순서를 따로 맞춘다. 신뢰 채널을 직접 만드는 방법은 TCP와 UDP에서 다뤘다.

직렬화 포맷은 크기, 속도, 호환을 맞바꾼다

포맷성질호환맞는 자리
JSON텍스트. 사람이 읽을 수 있고 도구가 많다. 크고 해석이 느리다이름으로 찾으므로 필드를 더하기 쉽다. 형식 검사는 없다웹 API, 설정, 운영 도구

많이 쓰는 구성은 섞는 것이다. 대부분의 메시지는 스키마 기반 포맷으로 정의해 호환을 맡기고, 초당 수십 번 오가는 이동 패킷만 직접 짠 바이너리로 줄인다. 크기를 줄이기 전에 보낼 대상부터 줄이는 것이 먼저다(관심 영역과 브로드캐스트).

버전이 다른 상대와도 통해야 한다

패치 직후에는 옛 클라이언트와 새 서버가 동시에 존재한다. 서버를 한 대씩 바꾸는 동안에는 서버끼리도 버전이 섞인다. 그래서 메시지 형식은 처음부터 바뀔 것을 전제로 정한다.

  • 필드는 번호로 식별하고 번호를 다시 쓰지 않는다. 지운 필드의 번호는 남겨 두고(Protocol Buffers의 reserved) 새 필드에는 새 번호를 준다. 옛 번호를 다른 뜻으로 다시 쓰면 옛 상대가 엉뚱한 값으로 읽는다.
  • 새 필드는 없어도 동작해야 한다. 옛 클라이언트는 새 필드를 보내지 않는다. 받는 쪽은 기본값으로 처리할 수 있어야 한다.
  • 의미를 바꾸려면 필드를 새로 만든다. 단위를 초에서 밀리초로 바꾸는 식의 변경은 같은 필드에서 하지 않는다.
  • 접속할 때 프로토콜 버전을 주고받는다. 지원 범위 밖이면 업데이트를 요구하고 끊는다. 메시지 종류 번호와 길이는 프레임 헤더에 둔다.

배포 순서와 함께 맞물리는 호환 전략은 프로토콜 호환에서 다룬다.

HTTP, WebSocket, gRPC는 자리가 정해져 있다

요청 하나에 응답 하나로 끝나는 기능은 HTTP API가 맞는다. 로드 밸런서, 캐시, 인증 도구를 그대로 쓸 수 있다(HTTP 버전). 서버 사이의 호출은 스키마가 있고 한 연결에 여러 호출을 섞는 gRPC가 흔하다. gRPC는 HTTP/2가 필요해서, 브라우저에서는 gRPC-Web과 중계 프록시를 거친다.

브라우저는 TCP·UDP 소켓을 직접 열 수 없다. Unity WebGL 빌드도 마찬가지라 실시간 통신은 WebSocket(TCP 위의 양방향 메시지)을 쓴다. 비신뢰 전송이 필요하면 HTTP/3 위의 WebTransport가 데이터그램을 제공한다.

결정 순서는 이렇다. 서버가 판정할 것을 정한다. 데이터를 잃어도 되는지, 늦어도 되는지, 순서 범위로 나눠 채널을 정한다. 대부분은 스키마 기반 포맷으로 정의하고 뜨거운 경로만 손으로 줄인다. 마지막으로 버전 규칙을 정한다.

게임 서버에서는

  • 패킷 정의는 한 곳에 두고 코드를 생성한다. .NET 서버와 Unity 클라이언트가 같은 스키마 파일에서 클래스를 생성하면 양쪽 정의가 어긋나는 사고가 없다. 손으로 두 벌을 맞추면 필드 순서 하나가 바뀌어도 빌드는 통과하고 실행 중에 값이 틀어진다.
  • 직렬화에서 할당을 줄인다. 리플렉션 기반 직렬화는 느리고 AOT 환경에서 깨질 수 있다. 소스 생성기를 쓰는 라이브러리(MessagePack-CSharp, Google.Protobuf의 생성 코드)를 쓰고, 버퍼는 풀에서 빌려 IBufferWriter<byte>에 바로 쓴다(JIT와 AOT, ref struct와 Span).
  • 받은 값은 모두 검증한다. 서버 권위라도 역직렬화한 값의 범위를 보지 않으면 소용이 없다. 길이 필드가 엄청나게 크거나, 수량이 음수거나, 좌표가 맵 밖이면 처리하기 전에 거른다.
  • 모르는 메시지 종류를 받으면 기록하고 버린다. 새 버전 상대가 보낸 메시지일 수 있다. 바로 예외를 던져 연결을 끊으면 버전이 섞인 기간 동안 접속이 무더기로 끊긴다. 대신 반복되면 조작을 의심해 끊는다.

주의 사항

  • 포맷부터 바꾸는 것은 순서가 틀렸다. JSON을 바이너리로 바꿔 절반으로 줄이는 것보다, 보낼 대상과 빈도를 줄이는 쪽이 훨씬 크게 줄어든다.
  • float을 그대로 보내면 정밀도를 낭비한다. 화면에서 1cm 차이를 구분하지 못한다면 4바이트 float 대신 범위를 정한 16비트 정수로 충분하다. 대신 범위와 단위를 양쪽이 같이 알아야 한다.
  • HTTP를 실시간 동기화에 쓰지 않는다. 매 요청에 헤더가 붙고 서버가 먼저 보낼 수 없다. 서버가 밀어 줘야 하는 데이터는 연결을 유지하는 채널로 보낸다.
