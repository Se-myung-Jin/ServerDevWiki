먼저 읽을 것: 게임 서버 스레딩 모델 · 시계와 타이머

핵심 요약

틱 루프는 정해진 간격마다 게임 세상을 한 단계씩 진행하는 루프다. 한 틱 안에서 그동안 쌓인 입력을 반영하고, 이동·전투·AI를 정해진 시간 간격(dt)만큼 계산하고, 바뀐 것을 모아 보낸다. 초당 틱 수가 틱레이트이고, 20Hz면 틱 하나에 50ms가 주어진다.

그 50ms가 틱 예산이다. 한 틱의 일이 예산 안에 끝나면 남는 시간을 쉬고, 넘기면 다음 틱이 밀린다. 밀림을 어떻게 처리하느냐, 쉬는 시간을 얼마나 정확히 지키느냐가 틱 루프 설계의 대부분이다.

동작 원리

한 틱 안에서 하는 일

순서하는 일주의할 점
1. 입력 반영I/O 스레드가 넣어 둔 작업 큐를 비우며 이동 요청, 스킬 사용 같은 입력을 꺼낸다틱 시작 시점까지 들어온 것만 처리한다. 처리하는 동안 새로 온 것은 다음 틱 몫이다
2. 시뮬레이션이동, 충돌, 전투 판정, 버프 만료, AI를 고정된 dt로 한 단계 진행한다틱 안에서는 모두가 같은 "현재 시각"(틱 번호 × dt)을 쓴다
3. 비동기 결과 반영DB 조회처럼 다른 스레드에 넘겼던 일의 결과를 받아 적용한다그사이 대상이 사라졌을 수 있으니 다시 확인한다(스레딩 모델)
4. 송신이번 틱에 바뀐 상태를 세션별로 모아 한 번에 보낸다관찰자마다 보낼 범위를 고른다(관심 영역과 브로드캐스트)
5. 대기다음 틱 목표 시각까지 쉰다"적어도 그만큼"만 지켜지므로 목표 시각 기준으로 계산한다

시뮬레이션이 쓰는 시각은 벽시계가 아니라 틱 번호다. 버프가 "3초 뒤 만료"라면 60틱(20Hz 기준) 뒤에 만료된다. 같은 틱에 일어난 일은 모두 같은 시각에 일어난 것으로 친다. 이렇게 하면 입력을 기록해 두고 같은 순서로 다시 넣었을 때 같은 결과가 나와, 재현과 리플레이가 쉬워진다.

목표 시각을 기준으로 쉬고, 밀리면 따라잡는다

const int TickRate = 20;
long tickTicks = Stopwatch.Frequency / TickRate;     // 한 틱의 길이(Stopwatch 단위)
long start = Stopwatch.GetTimestamp();
long tick = 0;

while (running)
{
    long target = start + tick * tickTicks;          // 이번 틱의 목표 시각
    long now = Stopwatch.GetTimestamp();

    if (now - target > tickTicks * MaxCatchUpTicks)  // 너무 밀렸다: 따라잡기를 포기한다
    {
        skipped += (now - target) / tickTicks;
        start = now - tick * tickTicks;              // 기준을 지금으로 다시 잡는다
        target = now;
    }

    if (now < target)
        WaitUntil(target);                           // 남은 시간만 쉰다

    long begin = Stopwatch.GetTimestamp();
    RunTick(tick);                                   // 입력 → 시뮬레이션 → 송신
    RecordTick(Stopwatch.GetElapsedTime(begin),      // 틱에 걸린 시간
               lateBy: begin - target);              // 목표보다 늦게 시작한 정도
    tick++;
}

밀린 틱을 어떻게 처리할지는 세 가지가 있다.

방식어떻게맞는 곳위험
따라잡기쉬지 않고 밀린 틱을 연달아 돌려 목표 시각을 회복한다가끔 한 번 튀는 경우. 시뮬레이션 시간이 실제 시간과 맞는다틱마다 예산을 넘기면 따라잡을수록 더 밀린다
건너뛰기밀린 틱을 버리고 기준 시각을 지금으로 다시 잡는다계속 과부하일 때. 게임 시간이 잠깐 느려지는 쪽을 택한다그 구간만큼 게임 안 시간이 실제보다 덜 흐른다
dt 늘리기늦은 만큼 다음 틱의 dt를 키운다클라이언트 렌더링 루프dt가 바뀌면 결과가 실행 시간에 따라 달라진다. 서버에는 맞지 않는다

따라잡기만 쓰면 죽음의 나선에 빠질 수 있다. 틱 하나가 늘 예산보다 오래 걸리면 밀린 틱을 연달아 돌리는 동안 또 밀리고, 따라잡을 틱 수가 계속 늘어난다. 서버는 쉬지 않고 돌지만 게임은 점점 뒤처진다. 그래서 따라잡을 틱 수에 상한을 두고, 넘으면 건너뛰기로 바꾼다. 위 코드의 MaxCatchUpTicks가 그 상한이다.

고정 간격이어야 결과가 정해진다

dt가 틱마다 다르면 같은 입력에도 결과가 달라진다. 빠르게 움직이는 물체는 dt가 크면 벽을 뚫고 지나가고, 가속도를 쓰는 계산은 dt를 어떻게 나눴느냐에 따라 최종 위치가 조금씩 다르다. 서버가 고정 dt를 쓰면 실행 속도와 상관없이 같은 입력에서 같은 결과가 나온다. 클라이언트가 서버 결과를 예측하고 맞추는 일도 이 고정 간격 위에서 성립한다(상태 동기화, 입력 기록 재생).

쉬는 시간을 정확히 지키려면

남은 시간만큼 Thread.Sleep을 부르면 Windows 기본 해상도에서는 최대 15ms 넘게 늦게 깬다(시계와 타이머). 50ms 틱이면 틱 하나에 30%가 흔들린다. 흔한 대처는 다음과 같다.

  • 조금 일찍 깨서 나머지를 기다린다. 목표보다 몇 ms 앞까지만 자고, 남은 짧은 시간은 Thread.Yield나 SpinWait로 시계를 보며 기다린다. 정확하지만 그동안 코어 하나를 쓴다.
  • 고해상도 타이머를 쓴다. Windows의 고해상도 대기 타이머나 프로세스 단위 timeBeginPeriod(1)로 오차를 1ms 근처로 줄인다. Linux는 기본 타이머가 이미 정밀한 편이다.
  • 오차를 받아들이고 목표 시각만 지킨다. 매 틱이 몇 ms씩 흔들려도 목표 시각 기준으로 계산하면 평균 간격은 정확하다. 10~20Hz 틱에서는 이것으로 충분한 경우가 많다.

Task.Delay나 PeriodicTimer로 틱을 돌리면 깨어난 뒤 스레드 풀 차례까지 기다려야 하고, 매 틱 다른 스레드에서 돌 수 있다. 상태를 한 스레드만 만지는 구조라면 틱 루프는 전용 스레드에서 직접 돈다.

선택 기준

틱레이트는 반응성과 비용을 맞바꾼다

틱레이트틱 예산흔히 쓰는 곳특징
10~20Hz100~50msMMORPG, 필드 이동 위주한 틱에 많은 대상을 처리할 여유가 있다. 클라이언트가 보간으로 부드럽게 보인다
20~30Hz50~33ms액션, MOBA, 배틀로얄판정 지연과 서버 비용의 절충
60~128Hz17~8ms경쟁 FPS, 격투입력이 결과에 빨리 반영된다. 서버 CPU와 대역폭이 틱레이트에 비례해 든다

틱레이트를 두 배로 올리면 입력이 다음 틱을 기다리는 시간은 절반으로 줄지만, 시뮬레이션 횟수와 송신량이 두 배가 되어 서버 한 대가 맡을 수 있는 인원이 거의 절반이 된다. 사람이 느끼는 지연에는 망 왕복과 클라이언트 쪽 버퍼도 들어가므로, 틱레이트만 올려서 얻는 차이는 생각보다 작을 수 있다.

예산을 다 쓰도록 잡지도 않는다. 평소 틱 시간이 예산의 절반에서 70% 정도에 머물러야 순간적인 몰림과 GC 멈춤을 흡수한다. 평소에 90%를 쓰는 서버는 이벤트 한 번에 밀리기 시작한다.

게임 서버에서는

  • 틱 시간을 분포로 남긴다. 틱마다 걸린 시간, 예산을 넘긴 횟수, 목표 시각보다 늦게 시작한 정도, 건너뛴 틱 수를 기록한다. 평균 틱 시간이 낮아도 가끔 튀는 틱이 사용자에게는 "렉"이다. 예산을 넘긴 틱에서는 어느 단계(입력, 시뮬레이션, 송신)가 오래 걸렸는지도 같이 남긴다.
  • 입력에 틱 번호를 붙인다. 클라이언트가 "몇 번째 틱에 낸 입력"인지 적어 보내면, 서버는 망 흔들림으로 몰려 온 입력을 원래 틱에 맞춰 반영하거나 적은 수를 버퍼에 쌓아 고르게 꺼낸다. 너무 늦게 온 입력은 버리는 기준도 정해 둔다.
  • 여러 존을 한 루프에 태울 때는 무거운 존이 다른 존을 끌어내린다. 존 열 개를 한 스레드의 틱 루프에서 차례로 돌리면, 공성전이 벌어진 존 하나가 예산을 다 써서 나머지 아홉 존까지 늦어진다. 존마다 루프를 따로 두거나, 존 단위로 틱 시간을 재서 무거운 존을 다른 스레드나 서버로 옮긴다.
  • 시스템마다 주기를 다르게 둔다. 모든 일을 매 틱 할 필요는 없다. 이동과 전투는 매 틱, AI 판단은 두세 틱에 한 번, 저장 예약과 통계는 몇 초에 한 번처럼 나눈다. 같은 주기의 일이 한 틱에 몰리지 않도록 대상마다 시작 틱을 흩어 둔다.
  • 긴 일은 여러 틱에 나눈다. 수천 명에게 보상 지급하기처럼 한 번에 하면 예산을 넘는 일은 틱마다 일정량씩 처리한다. 클라이언트의 프레임 루프와는 목적이 다르다. 클라이언트는 화면 갱신에 맞춰 돌고 dt가 매번 바뀐다(Unity 실행 순서).

주의 사항

  • 틱 안에서 벽시계를 읽지 않는다. 같은 틱의 판정마다 DateTime.UtcNow를 읽으면 같은 순간에 일어난 일이 서로 다른 시각을 갖고, 재현도 안 된다. 틱 시작에 한 번 정한 시각을 모두가 쓴다.
  • 쉬는 동안 받은 입력은 다음 틱에 처리된다. 입력이 반영되기까지 평균 반 틱, 최대 한 틱을 기다린다. 틱레이트가 낮을수록 이 대기가 길다.
  • 틱 루프 스레드에서 기다리는 호출을 하지 않는다. 동기 DB 호출이나 Task.Result 하나가 그 틱을 통째로 늘린다. 기다림은 다른 스레드에 맡기고 결과를 큐로 받는다.
  • CPU 사용률로 여유를 판단하지 않는다. 틱 루프는 쉬는 시간이 있어서 CPU 사용률이 낮게 나온다. 여유는 틱 시간이 예산의 몇 퍼센트인지로 본다.
