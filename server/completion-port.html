먼저 읽을 것: I/O 모델 · 커널 오브젝트와 핸들

핵심 요약

완료 알림 기반 서버는 소켓마다 읽기·쓰기를 걸어 두고, 커널이 끝낸 일을 완료 큐에 쌓으면 적은 수의 작업 스레드가 꺼내 처리하는 구조다. 연결마다 스레드를 붙이지 않으므로 연결이 만 개여도 스레드는 코어 수 근처에 머문다.

Windows의 IOCP(I/O Completion Port)가 대표다. 패턴 이름으로는 완료를 받아 처리하는 Proactor이고, Linux epoll처럼 준비를 받아 내가 읽는 Reactor와 짝을 이룬다. 둘의 차이는 버퍼를 언제 내주느냐에서 갈린다.

동작 원리

완료가 큐에 쌓이고, 스레드가 꺼내 간다

  1. CreateIoCompletionPort로 완료 포트를 만들고, 소켓을 그 포트에 묶는다. 이때 소켓마다 완료 키를 준다. 보통 세션 객체를 가리키는 값이다.
  2. WSARecv·WSASend에 버퍼와 OVERLAPPED를 넘겨 요청을 걸고 바로 돌아온다.
  3. 커널이 일을 끝내면 완료 패킷(완료 키, 옮긴 바이트 수, OVERLAPPED 주소)을 큐에 넣는다.
  4. 작업 스레드들은 GetQueuedCompletionStatus(여러 개를 한 번에 받는 …Ex)에서 기다리다가 하나가 깨어나 꺼낸다.
  5. 처리가 끝나면 다음 수신을 다시 걸고 큐로 돌아가 기다린다.

꺼낸 쪽은 완료 키로 어느 연결의 일인지, OVERLAPPED 주소로 어느 요청이었는지 안다. 그래서 OVERLAPPED를 맨 앞에 품은 요청 구조체를 만들어 두고, 받은 주소에서 그 구조체를 되찾는 방식이 흔하다. 큐에 직접 패킷을 넣는 PostQueuedCompletionStatus로 종료 신호나 다른 스레드의 작업을 같은 스레드들에게 넘기기도 한다.

깨우는 수를 커널이 조절한다

완료 포트를 만들 때 동시 실행 수를 정한다(0이면 코어 수). 커널은 이 포트에서 일하고 있는 스레드가 그 수에 닿으면 대기 중인 스레드를 더 깨우지 않는다. 깨워 봐야 코어를 두고 다투며 전환만 늘기 때문이다(PCB와 컨텍스트 스위칭).

처리 중인 스레드가 락이나 동기 I/O에서 막히면 커널은 그 스레드를 일하는 수에서 뺀다. 그러면 대기 중이던 다른 스레드가 깨어나 코어를 채운다. 그래서 미리 만들어 두는 스레드는 동시 실행 수보다 여유 있게 잡는다. 막혔던 스레드가 풀리면 잠시 상한을 넘겨 돌 수도 있다.

대기 스레드를 최근에 잠든 것부터 깨우는 것도 같은 목적이다. 방금까지 돌던 스레드는 스택과 데이터가 아직 캐시에 남아 있을 가능성이 크고, 오래 잠든 스레드는 그대로 쉬게 둘 수 있다.

Proactor는 완료를, Reactor는 준비를 받는다

구분ProactorReactor
받는 알림완료: 이미 읽어 두었다준비: 지금 읽으면 막히지 않는다
읽기는 누가커널이 끝냈다알림을 받은 뒤 내가 한다
대표 구현IOCP, io_uringepoll, kqueue, select
버퍼는 언제요청을 걸 때 미리 내준다읽을 때 잠깐 쓴다
시스템 콜요청 걸기, 완료 받기기다리기, 읽기

실무에서 가장 크게 다른 것은 버퍼다. Proactor는 수신을 걸어 두는 동안 버퍼를 커널에 맡겨야 하므로, 연결이 만 개면 만 개의 버퍼가 동시에 묶인다. Reactor는 준비된 소켓만 읽으므로 버퍼 몇 개를 돌려 쓸 수 있다.

관리되는 런타임은 버퍼를 고정해야 한다

커널은 요청을 걸 때 받은 주소에 그대로 쓴다. GC가 압축하면서 그 버퍼를 옮기면 커널은 이미 다른 객체가 들어선 자리에 데이터를 쓴다. 그래서 걸어 둔 동안은 버퍼를 고정한다. 고정된 객체는 옮길 수 없어서, 힙 곳곳에 박혀 있으면 그 사이 빈칸이 메워지지 않는다(단편화, GC 기초).

방법어떻게효과
큰 버퍼를 잘라 쓴다큰 배열 하나를 미리 잡고 연결마다 구간을 나눠 준다고정되는 객체가 하나뿐이고 힙 한쪽에 모인다

선택 기준

언제 이 구조를 고르나

  • 연결 수가 스레드로 감당되지 않을 때다. 연결이 수십~수백 개면 연결마다 스레드가 더 읽기 쉽다. 수천을 넘으면 스택 메모리와 전환 비용이 일하는 시간보다 커진다.
  • Windows 서버라면 사실상 이것이다. Windows에는 epoll이 없고, select는 연결이 많으면 느리다. Linux라면 epoll 기반 Reactor가 기본이고, 완료 방식이 필요하면 io_uring을 본다.
  • 대가는 코드 구조다. 한 요청의 흐름이 "걸기"와 "완료 처리"로 쪼개지고, 완료 처리는 아무 작업 스레드에서나 돈다. 같은 세션의 수신 완료와 송신 완료가 두 스레드에서 동시에 처리될 수 있다는 것을 늘 의식해야 한다.

게임 서버에서는

  • 세션마다 수신은 하나만 걸어 둔다. 수신을 둘 걸면 완료가 다른 스레드에서 거의 동시에 처리되어 바이트 순서가 뒤바뀔 수 있다. 하나를 처리하고 다음을 거는 순서를 지킨다. 송신도 세션마다 진행 중인 것을 하나로 두고, 그동안 생긴 패킷은 송신 큐에 모았다가 끝나면 한꺼번에 보낸다.
  • 작업 스레드에서 게임 로직을 오래 돌리지 않는다. 작업 스레드는 코어 수만큼만 있으므로 하나가 DB를 기다리면 그만큼 모든 연결의 수신 처리가 밀린다. 받은 패킷은 파싱해서 로직 쪽 큐에 넘기고 바로 돌아온다(게임 서버 스레딩 모델).
  • .NET은 IOCP를 직접 감춘다. Windows의 비동기 소켓은 내부에서 IOCP를 쓰고, 완료되면 await 뒤 코드를 스레드 풀에서 이어 실행한다. SocketAsyncEventArgs는 요청 객체를 재사용해 할당을 없애는 예전 방식이고, 지금은 Memory<byte>를 받는 ReceiveAsync가 ValueTask로 같은 효과를 낸다(Task와 ValueTask).
  • 세션을 닫을 때 걸어 둔 요청부터 정리한다. 소켓을 닫으면 걸려 있던 요청이 실패로 완료되어 큐에 들어온다. 세션 객체를 먼저 풀어 버리면 그 완료를 처리하는 스레드가 이미 사라진 객체를 만진다. 걸어 둔 요청 수를 세어 0이 된 뒤에 세션을 반납한다.

주의 사항

  • IOCP와 epoll은 같은 것의 플랫폼 차이가 아니다. 하나는 완료를, 하나는 준비를 알린다. 그 차이가 버퍼를 언제 얼마나 잡느냐를 바꾼다.
  • 동시 실행 수와 만드는 스레드 수는 다른 값이다. 앞의 것은 코어 수에 맞추고, 뒤의 것은 처리 중에 막힐 일을 생각해 더 잡는다.
  • 완료가 바로 끝나도 큐에 들어올 수 있다. 요청이 즉시 성공해도 기본으로는 완료 패킷이 큐에 들어온다. 즉시 끝난 결과를 그 자리에서 처리하면서 큐에서도 다시 처리하면 같은 데이터를 두 번 다룬다. 즉시 성공 시 큐를 건너뛰는 설정(FILE_SKIP_COMPLETION_PORT_ON_SUCCESS)을 쓸 때만 그 자리에서 처리한다.
