먼저 읽을 것: 완료 알림 기반 서버 · 동기화 객체 · 캐시 일관성과 false sharing

핵심 요약

게임 서버의 상태는 서로 얽혀 있다. 공격 한 번이 공격자, 대상, 주변 몬스터, 파티, 드롭 아이템을 함께 바꾼다. 락을 잘게 나누면 데드락과 경합이 따라오고, 크게 걸면 결국 한 번에 한 스레드만 돈다.

그래서 많은 게임 서버가 상태를 고치는 스레드를 하나로 정한다(단일 쓰기 스레드). 다른 스레드는 할 일을 큐에 넣기만 한다(커맨드 패턴). 락이 통째로 사라지고 순서가 정해지는 대신, 그 스레드가 쓰는 코어 하나가 처리량의 상한이 된다. 상한에 닿으면 상태를 조각으로 나눠 조각마다 쓰기 스레드를 둔다.

마지막 모델은 단일 쓰기 스레드를 조각 수만큼 늘린 것이다. 조각마다 전용 스레드를 둘 수도 있고, 스레드 풀이 큐를 하나씩 맡아 돌리되 같은 큐를 두 스레드가 동시에 잡지 않게만 할 수도 있다. 뒤의 방식을 strand, 잡 큐 직렬화라고 부르고, 조각끼리 메시지로만 주고받게 하면 액터 모델이 된다.

단일 쓰기 스레드의 흐름

I/O 스레드(완료 알림 기반 서버의 작업 스레드)는 바이트를 받아 패킷으로 자른 뒤 작업 큐에 넣고 바로 돌아간다. 로직 스레드는 큐에서 하나씩 꺼내 처리한다. 정해진 간격(틱)마다 이동, 전투, AI를 한 번씩 돌리는 루프와 함께 쓰는 경우가 많다(서버 틱 루프).

이렇게 하면 세 가지를 얻는다.

  • 락이 필요 없다. 상태를 만지는 스레드가 하나뿐이라 데드락도, 경합도, 락 순서 규칙도 없다.
  • 순서가 하나로 정해진다. 큐에서 꺼낸 순서가 곧 일어난 순서다. 두 플레이어가 같은 아이템을 동시에 줍는 경우도 먼저 꺼낸 쪽이 가져간다.
  • 재현이 쉬워진다. 큐에 들어간 입력을 순서대로 기록해 두면 같은 입력으로 같은 결과를 다시 만들 수 있다. 동시성 버그에서 가장 힘든 "다시 안 일어난다"가 사라진다.

한 코어가 상한이고, 긴 작업 하나가 전체를 멈춘다

로직 스레드가 한 틱에 처리할 수 있는 양이 서버 전체의 처리량이다. 코어를 32개 꽂아도 상태 변경은 한 코어에서 돈다. 그리고 큐는 하나라서, 어떤 일 하나가 10ms를 쓰면 그 뒤의 모든 일이 10ms 늦어진다.

그래서 이 구조에서는 로직 스레드에서 기다리는 일을 하지 않는다. DB 조회, 파일 쓰기, 외부 API, 무거운 길찾기는 다른 스레드에 넘기고, 결과는 메시지로 작업 큐에 다시 넣는다. 결과를 받은 시점에 상태가 그사이 바뀌었을 수 있으므로(대상이 이미 죽었거나 로그아웃했거나), 결과를 반영하기 전에 다시 확인한다.

단일 쓰기 스레드는 느린 구조가 아니다

여러 코어가 같은 데이터에 쓰면, 그 데이터를 담은 캐시 라인의 소유권이 코어 사이를 계속 오간다. 쓸 때마다 다른 코어의 사본을 무효로 만들어야 해서 접근마다 캐시 미스가 난다(캐시 일관성과 false sharing). 락까지 더하면 락 변수 자체가 그 왕복의 중심이 된다.

쓰는 스레드가 하나면 이 왕복이 없다. 상태가 그 코어의 캐시에 머물러 있어 공유 상태를 많이 고치는 작업에서는 한 스레드가 여러 스레드보다 빠른 경우도 있다. 읽기는 여러 코어가 사본을 나눠 가져도 서로를 무효로 만들지 않으므로, 읽기만 하는 일(통계 집계, 조회)은 다른 스레드에 줘도 된다. 단, 로직 스레드가 고치는 중인 데이터를 동시에 읽으면 반쯤 바뀐 값을 볼 수 있으니 스냅숏을 넘기는 식으로 나눈다.

선택 기준

상한에 닿으면 무엇을 하나

방법어떻게언제 맞나
무거운 일만 뺀다DB·직렬화·압축·길찾기를 다른 스레드로시간을 쓰는 것이 몇 가지 작업에 몰려 있을 때. 대개 이것부터다
공간으로 나눈다맵·채널·던전 인스턴스마다 쓰기 스레드나 직렬 큐지역 사이 상호작용이 드물 때
기능으로 나눈다전투, 거래, 채팅, 길드를 따로기능 사이 의존이 얕을 때
데이터 병렬한 틱 안의 독립 계산(AI 판단, 시야 계산)을 여러 스레드에 나눴다가 모은다읽기 위주의 계산이 크고 결과 반영만 직렬로 하면 될 때

나누기 전에 먼저 잰다. 틱마다 어떤 일이 시간을 쓰는지 프로파일링하면 대개 몇 가지 무거운 작업이 대부분을 차지한다. 그것만 빼도 상한이 크게 오른다.

나누면 경계를 넘는 일이 새로 생긴다. 지역 A의 플레이어가 지역 B의 플레이어와 거래하면, 두 쓰기 스레드가 함께 바꿔야 한다. 둘 다 되거나 둘 다 안 되게 하려면 한쪽이 상대에게 메시지를 보내고, 확인을 받고, 실패하면 되돌리는 절차가 필요하다. 한 스레드 안에서는 순서만 지키면 끝나던 일이 왕복 몇 번짜리 절차로 바뀐다. 이 비용 때문에 경계를 자주 넘는 기능은 나누지 않고 한 조각에 둔다. 프로세스나 서버 단위로 나누는 이야기는 확장과 샤딩에서 다룬다.

게임 서버에서는

  • C#에서 await 뒤는 다른 스레드다. 로직 스레드에서 await db.LoadAsync()를 하면, 이어지는 코드는 따로 정해 두지 않는 한 스레드 풀 스레드에서 돈다. 그 코드가 게임 상태를 고치면 단일 쓰기 규칙이 조용히 깨진다. 결과는 작업 큐에 메시지로 넣거나, 로직 스레드로 돌아오는 전용 동기화 컨텍스트를 둔다(동기화 컨텍스트).
  • 틱 초과를 지표로 남긴다. 틱 하나가 정한 시간(예: 50ms)을 넘긴 횟수와 가장 오래 걸린 작업을 기록해 둔다. 상한에 다가가는 것은 평균 CPU 사용률보다 이 값에서 먼저 보인다.
  • 큐는 여러 스레드가 넣고 하나가 뺀다. 이 모양에 맞는 다중 생산자·단일 소비자 큐를 쓴다. .NET이라면 System.Threading.Channels의 SingleReader = true 옵션이나 ConcurrentQueue가 출발점이다(스택과 큐, 동시성 자료구조).
  • 작업 하나의 길이가 응답 시간을 정한다. 길드 전체 순회나 대량 아이템 지급처럼 한 번에 오래 걸리는 작업은 여러 틱에 나눠 처리한다. 그동안 다른 요청이 같은 대상을 바꿀 수 있으니 중간 상태를 고려해 설계한다.

주의 사항

  • "락이 없다"는 상태 변경에 대한 말이다. 작업 큐 자체는 여러 스레드가 동시에 넣으므로 스레드 안전해야 하고, 안에서는 원자적 연산이나 짧은 락을 쓴다. 넣고 빼는 순간에만 잠깐 쓰이므로 상태 전체에 거는 락과는 경합 정도가 다르다(원자적 연산과 메모리 순서).
  • 나누는 것을 먼저 하면 대개 후회한다. 나눈 뒤에는 경계를 넘는 모든 기능에 절차가 붙고 되돌리기 어렵다. 무거운 작업을 빼서 얼마나 벌 수 있는지 먼저 본다.
  • 로직 스레드에서 블로킹 호출을 하면 서버 전체가 멈춘다. 동기 DB 호출, Thread.Sleep, Task.Result 하나가 그 시간 동안 모든 플레이어를 세운다.
