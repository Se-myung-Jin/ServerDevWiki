먼저 읽을 것: 대칭 암호와 비대칭 암호 · 해시와 비밀번호 저장 · HTTP와 그 변천

핵심 요약

디지털 서명은 개인 키를 가진 쪽만 만들 수 있고, 공개 키를 가진 누구나 확인할 수 있는 값이다. 서명이 맞으면 내용이 바뀌지 않았고, 그 개인 키의 주인이 만들었다는 것이 보장된다. 서명은 내용을 감추지 않는다.

TLS는 서명과 키 합의를 엮어 안전한 통신로를 만든다. 서버는 인증서로 "이 공개 키는 이 도메인의 것"임을 보이고, 그 키로 핸드셰이크에 서명한다. 양쪽은 임시 키 합의로 세션 키를 만들고, 본문은 AEAD로 암호화한다. TLS 1.3은 이 과정을 한 번의 왕복으로 끝낸다.

인증서 검증을 건너뛰면 이 구조 전체가 무너진다. 암호화는 되지만 누구와 암호화하는지 모르게 된다.

동작 원리

서명은 "개인 키로 암호화"가 아니다

서명을 "개인 키로 암호화하고 공개 키로 복호화한다"고 설명하는 경우가 많다. 교과서식 RSA에서는 수식 모양이 비슷해 그렇게 보이지만, 실제 RSA 서명은 패딩 방식이 암호화와 다르다. ECDSA와 Ed25519에는 아예 암호화 연산이 없다. 정확한 설명은 "개인 키로 서명값을 만들고, 공개 키로 서명이 맞는지 확인한다"이다.

서명은 메시지 전체가 아니라 해시에 붙는다. 비대칭 연산이 느리기 때문이다. 그래서 해시가 약해지면 서명도 같이 약해진다. 충돌하는 두 문서를 만들 수 있으면 한쪽에 받은 서명을 다른 쪽에 그대로 옮길 수 있다(해시와 비밀번호 저장).

서명은 HMAC과 달리 부인 방지가 된다. HMAC 키는 양쪽이 같이 갖고 있어 어느 쪽이 만들었는지 가릴 수 없다. 개인 키는 한쪽만 갖고 있으므로 서명이 맞으면 그쪽이 만든 것이다.

서명 방식특징주의
RSA-PSS오래 쓰였고 호환성이 넓다3072비트 이상이어야 128비트 수준. 서명이 크다

인증서는 공개 키에 붙은 보증서다

공개 키만 받아서는 그것이 진짜 서버의 키인지 모른다. 인증서는 인증 기관(CA)이 "이 공개 키는 example.com의 것"이라고 서명해 준 문서다. 클라이언트는 다음을 모두 확인한다.

  • 서명을 따라 올라가면 중간 CA를 거쳐 OS나 브라우저가 미리 믿기로 한 루트 CA에 닿는가
  • 인증서의 이름(SAN)이 접속한 도메인과 맞는가
  • 유효 기간 안인가, 폐기되지 않았는가
  • 서버가 그 인증서의 개인 키를 실제로 가졌는가(핸드셰이크 서명으로 확인)

인증서 수명은 점점 짧아지고 있다. Let's Encrypt 인증서는 90일이고, CA/브라우저 포럼은 2025년에 공개 인증서의 최대 유효 기간을 몇 년에 걸쳐 47일까지 줄이기로 정했다. 손으로 갱신하는 운영은 더는 버티지 못한다. 갱신을 자동화하고 만료를 감시한다.

TLS 1.3은 한 번의 왕복으로 연결을 맺는다

핸드셰이크가 정하는 것은 세 가지다. 어떤 알고리즘을 쓸지, 상대가 진짜인지, 이번 연결의 세션 키가 무엇인지다. 세션 키는 회선으로 오가지 않는다. 양쪽이 임시 키 합의(ECDHE)로 각자 계산한다.

TLS 1.3은 정적 RSA 키 전송, CBC, RC4, SHA-1 같은 옛 선택지를 모두 뺐다. 남은 암호 조합은 AEAD 몇 개뿐이라 설정 실수의 여지가 크게 줄었다. QUIC(HTTP/3)은 TLS 1.3을 전송 계층에 넣어 같은 핸드셰이크를 쓴다(HTTP와 그 변천).

전방 비밀성과 0-RTT의 대가

예전 TLS는 서버의 RSA 공개 키로 세션 키를 직접 잠가 보내는 방식을 허용했다. 그러면 누군가 통신을 몽땅 기록해 두었다가 나중에 서버 개인 키를 손에 넣는 순간 과거 통신이 전부 풀린다. 임시 키 합의는 연결이 끝나면 비밀 수를 버리므로 이 공격이 통하지 않는다. 이것이 전방 비밀성이고, TLS 1.3은 이 방식만 남겼다.

TLS 1.3에는 다시 접속할 때 첫 패킷에 데이터를 실어 보내는 0-RTT가 있다. 이전 연결에서 받아 둔 키를 쓰므로 왕복 하나를 아낀다. 대신 이 데이터는 공격자가 그대로 복사해 다시 보내도 서버가 막지 못한다. 0-RTT로는 몇 번 받아도 결과가 같은 요청(조회)만 받는다. 결제나 아이템 지급 요청은 절대 받지 않는다.

검증을 끄는 코드가 가장 흔한 구멍이다

// 하지 말 것: 모든 인증서를 통과시킨다. 개발 중에 넣고 그대로 배포되는 일이 많다
var handler = new HttpClientHandler
{
    ServerCertificateCustomValidationCallback =
        HttpClientHandler.DangerousAcceptAnyServerCertificateValidator
};

// 자체 TCP 프로토콜을 TLS로 감쌀 때: 이름을 지정하고 기본 검증을 그대로 쓴다
await using var ssl = new SslStream(networkStream);
await ssl.AuthenticateAsClientAsync(new SslClientAuthenticationOptions
{
    TargetHost = "login.example-game.com",   // 인증서 이름과 비교된다
    EnabledSslProtocols = SslProtocols.Tls13 | SslProtocols.Tls12,
}, ct);

개발 서버의 자체 서명 인증서 때문에 검증을 끄고 싶으면, 끄는 대신 개발용 루트 인증서를 개발 기기에만 설치한다. 검증을 끄는 코드는 빌드 설정과 무관하게 아예 남기지 않는 편이 안전하다.

선택 기준

상황쓰는 것
클라이언트 ↔ 로그인·결제·웹 APITLS 1.3(최소 1.2), 공인 인증서, 자동 갱신
서버 ↔ 서버(내부망)mTLS: 양쪽이 인증서를 내고 서로 확인한다. 내부 CA나 서비스 메시가 발급한다
클라이언트 ↔ 게임 서버 TCPSslStream으로 감싼 TLS
클라이언트 ↔ 게임 서버 UDPDTLS·QUIC, 또는 TLS로 받은 세션 키로 AEAD(운용 모드와 인증 암호)
배포물·공지·설정 위변조 방지Ed25519나 ECDSA 서명, 클라이언트에 공개 키 내장

인증서 고정(피닝)은 클라이언트가 특정 인증서나 공개 키만 믿게 하는 것이다. CA가 잘못 발급한 인증서나 중간자 프록시를 막지만, 서버 키를 바꾸는 순간 고정된 클라이언트가 모두 접속하지 못한다. 고정한다면 인증서가 아니라 공개 키(SPKI)를 고정하고, 예비 키를 함께 넣어 두고, 강제 업데이트 경로가 있는 클라이언트에만 쓴다.

게임 서버에서는

  • 로그인 폭주는 TLS 핸드셰이크 비용으로도 온다. 연결마다 서명과 키 합의가 한 번씩 든다. ECDSA 인증서가 RSA보다 서버 쪽 서명 비용이 싸고, 세션 재개(티켓)를 켜면 재접속 비용이 준다. TLS 종료를 게이트웨이나 로드밸런서에 모으는 구성이 흔하다(게임 서버 토폴로지).
  • 패치 매니페스트와 공지에 서명한다. 클라이언트 실행 파일에 서명 확인용 공개 키를 넣고, 서버가 내려주는 매니페스트·공지·원격 설정의 서명을 확인한다. CDN이나 웹 서버가 뚫려도 가짜 파일을 밀어 넣지 못한다. 키 교체를 대비해 공개 키를 두 개 넣어 둔다.
  • 서명 개인 키는 빌드 서버에 두지 않는다. HSM이나 클라우드 키 관리 서비스에 두고 서명 요청만 보낸다. 이 키가 새면 모든 클라이언트가 공격자의 배포물을 믿는다.
  • 인증서 만료는 전체 장애다. 로그인 서버 인증서 하나가 만료되면 모든 플레이어가 동시에 접속하지 못한다. 만료 30일, 7일 전에 경보를 걸고, 갱신을 자동화한다(배포 파이프라인).
  • TLS는 통신로만 지킨다. 클라이언트 자체가 공격자의 손에 있으면 TLS 안쪽 내용은 그 사람이 다 본다. 패킷 조작 방어는 서버 검증이 맡는다(게임 보안과 치트 대응).

주의 사항

  • "HTTPS니까 안전하다"는 인증서를 확인했을 때만 맞다. 경고를 무시하거나 검증 콜백이 항상 true를 돌려주면 중간자와 안전하게 통신하게 된다.
  • 서명한 데이터는 누구나 읽는다. 서명은 위조를 막을 뿐이다. 내용을 감추려면 암호화를 따로 한다.
  • ECDSA를 직접 다루면 난수를 조심한다. 서명 두 개에 같은 난수가 쓰이면 개인 키가 계산된다. 실제로 이 실수로 서명 키가 통째로 유출된 사례가 있다. 라이브러리 기본값을 쓰거나 Ed25519를 고른다.
  • 인증서 검증은 이름 확인까지 포함한다. 체인만 확인하고 이름을 안 보면, 공격자가 자기 도메인으로 정상 발급받은 인증서도 통과한다.
