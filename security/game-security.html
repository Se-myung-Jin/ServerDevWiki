먼저 읽을 것: 스냅샷과 상태 동기화, 운용 모드와 인증 암호, 인증과 세션 토큰

핵심 요약

클라이언트는 공격자 손에 있다. 메모리를 고치고, 패킷을 바꾸고, 클라이언트를 통째로 다시 만들어 붙일 수 있다. 그래서 원칙이 하나로 모인다. 결과에 닿는 것은 서버가 정한다. 클라이언트가 보내는 것은 "하고 싶은 일"이지 "일어난 일"이 아니다.

암호화와 난독화는 이 원칙을 대신하지 못한다. 암호화는 경로 위의 제3자를 막고, 난독화와 무결성 검사는 분석을 늦출 뿐이다. 그 위에 서버 검증과 사후 탐지가 있어야 한다.

동작 원리

신뢰 경계는 서버 입구에 있다

클라이언트가 보내는 것서버가 하는 일
이동 입력, 목표 지점지난 위치와 경과 시간으로 갈 수 있는 거리인지, 지형을 뚫지 않는지 본다
스킬 사용쿨다운, 자원, 사거리, 시야를 서버가 가진 값으로 다시 구한다
"맞혔다", "주웠다", "깼다"받지 않는다. 판정과 지급은 서버가 한다
상점 구매 요청가격과 재고는 서버 테이블에서 읽는다(기획 데이터). 클라이언트가 보낸 가격은 무시한다
화면·소리 설정그대로 받는다. 결과에 닿지 않는다

위치와 판정을 서버가 정하는 구조, 클라이언트 예측과 서버 재조정은 스냅샷과 상태 동기화에서 다룬다. 여기서는 그 위에서 무엇을 더 막는지를 본다.

암호화가 막는 것과 못 막는 것

공격패킷 암호화로 막히나막는 장치
경로 위에서 엿보기막힌다기밀성
경로 위에서 바꾸기인증 태그가 있으면 막힌다AEAD(AES-GCM, ChaCha20-Poly1305)
가로챈 패킷 다시 보내기순번이 있어야 막힌다패킷 순번을 nonce와 검증에 넣는다
클라이언트 메모리 조작못 막는다서버 검증
고친 클라이언트가 만든 패킷못 막는다서버 검증, 사후 탐지

패킷을 만들려면 키가 클라이언트 메모리에 있어야 한다. 그래서 클라이언트를 통제하는 사람은 키를 꺼내거나 암호화 직전의 값을 고친다. 그래도 암호화는 필요하다. 공용 와이파이에서 세션을 훔치거나 패킷을 바꿔치기하는 공격은 치트와 별개로 막아야 한다. 키는 하드코딩하지 않고 로그인 때 TLS 위에서 세션마다 받는다(서명과 TLS).

보내지 않은 정보는 훔칠 수 없다

월핵, 레이더, ESP 같은 정보 치트는 클라이언트가 이미 받은 데이터를 보여 줄 뿐이다. 서버가 막을 수 있는 방법은 보이지 않는 것을 보내지 않는 것이다. 관심 영역 밖, 벽 뒤, 은신 상태의 적은 보내지 않는다(관심 영역과 브로드캐스트). 경쟁 FPS에서는 서버가 시야를 계산해 보낼지 정하기도 하는데, 지연 때문에 모서리에서 갑자기 나타나지 않도록 조금 일찍 보내는 여유를 둔다. 드롭 테이블, 다음 보스 패턴, 상자 내용물처럼 미리 알면 이득인 것도 결과가 정해진 뒤에 보낸다.

난수는 서버에서, 예측할 수 없게

드롭, 강화 성공, 크리티컬처럼 결과에 닿는 난수는 서버에서 굴린다. 빠른 난수 생성기는 출력을 얼마간 모으면 내부 상태가 복원되고, 그 뒤 값이 전부 계산된다. 시각으로 시드를 잡으면 시드 자체가 추측된다. 결과에 닿는 자리는 예측하기 어려운 생성기를 쓰고, 뽑기처럼 분쟁이 날 수 있는 결과는 기록을 남긴다. 생성기의 종류와 결정론적 재현은 난수 생성에서 다룬다.

선택 기준

모든 것을 매 틱 완벽하게 검증하면 서버 비용이 감당되지 않는다. 되돌릴 수 없는 정도에 따라 검증 강도를 나눈다.

대상검증 방식
재화, 아이템, 거래, 경쟁 결과예외 없이 서버가 판정한다. 트랜잭션과 로그를 남긴다
전투 판정서버가 판정한다. 지연 보상을 쓰면 되감기 허용 폭에 상한을 둔다
이동속도 상한과 지형 충돌을 확인하고, 벗어나면 서버 위치로 되돌린다
요청 빈도패킷 종류별 상한(레이트 리밋)
손해가 작은 것(감정 표현, 꾸미기)범위만 본다

그래도 남는 것은 사후 탐지로 잡는다. 실시간 검증이 "있을 수 없는 일"을 막는다면, 사후 탐지는 "있을 수는 있지만 사람 같지 않은 일"을 찾는다.

게임 서버에서는

  • 봇과 매크로는 통계로 찾는다. 입력 간격의 분산, 하루 접속 시간, 같은 경로 반복, 사냥 효율, 거래 상대 관계를 본다. 리밋에 자주 걸리는 것도 신호다. 한 지표로 단정하지 않고 여러 지표를 묶어 점수를 매긴다.
  • 경제 공격이 피해가 가장 크다. 아이템 복제는 대개 동시 요청과 재접속 타이밍을 노린다(동시성 제어와 데드락). 아이템마다 고유 ID를 두면 같은 ID가 두 곳에 나타나는 것으로 복제를 찾는다(분산 ID 생성). 재화 원장과 잔액을 대조해 설명되지 않는 증가를 찾는다.
  • 결제는 영수증을 서버가 검증한다. 앱 마켓 영수증을 클라이언트가 "결제했다"며 보내면, 서버가 마켓 API로 확인하고 영수증 ID를 한 번만 쓰게 기록한다. 환불 알림을 받아 회수하는 흐름도 둔다. 스토어별 검증과 환불 추적은 결제와 영수증 검증에서 다룬다.
  • 밴은 바로 하지 않을 때가 많다. 탐지 즉시 밴하면 치트 제작자가 무엇에 걸렸는지 바로 알고 고친다. 확실한 경제 피해는 즉시 막고, 치트 프로그램 사용은 모아 두었다가 한 번에 처리하는 방식(밴 웨이브)을 섞는다.
  • 안티치트는 시간 벌기다. 클라이언트 무결성 검사, 난독화, 커널 수준 안티치트는 치트 제작 비용을 올린다. 커널 수준은 탐지력이 높은 대신 시스템 안정성과 개인 정보 부담이 크다. 어느 것도 서버 검증을 대체하지 않는다.
  • 감사 로그를 남긴다. 재화·아이템 변화, 거래, GM 명령, 결제는 누가, 언제, 어디서, 무엇을 했는지 남긴다. 탐지, 복구, 분쟁 대응이 모두 이 로그에서 시작한다(백업과 복구).

주의 사항

  • "클라이언트를 믿지 않는다"의 범위는 "결과에 닿는가"로 정한다. 닿으면 서버가 정한다.
  • 서버 검증에 걸린 요청은 조용히 버리고 기록한다. 실패 이유를 자세히 돌려주면 치트 제작자에게 경계값을 알려 준다.
  • 정상 플레이어도 지연 때문에 이상하게 보일 수 있다. 순간 이동 판정은 지연 폭을 감안하고, 의심만으로 처벌하지 않는다.
  • 패킷 구조를 바꾸거나 암호화를 강화하는 것은 치트 대응이 아니라 지연 작전이다. 판정 구조가 클라이언트 신뢰에 기대고 있으면 그것부터 고친다.
