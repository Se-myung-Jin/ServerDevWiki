먼저 읽을 것: 대칭 암호와 비대칭 암호

핵심 요약

AES는 16바이트 블록 하나를 암호화하는 함수일 뿐이다. 긴 데이터를 블록으로 나눠 어떻게 이어 붙일지는 운용 모드가 정한다. 모드를 잘못 고르면 AES를 쓰고도 패턴이 드러난다.

암호화는 내용을 가릴 뿐 변조를 막지 않는다. 내용을 몰라도 비트를 뒤집을 수 있고, 받는 쪽은 그것이 원래 값인지 알 수 없다. 그래서 지금은 암호화와 무결성 검사를 한 번에 하는 AEAD(AES-GCM, ChaCha20-Poly1305)를 기본으로 쓴다.

AEAD에도 지켜야 할 규칙이 하나 있다. 같은 키로 같은 논스를 두 번 쓰면 안 된다. 재사용하면 기밀성과 무결성이 함께 무너진다.

CBC는 마지막 블록을 채우는 패딩이 필요하다. 받는 쪽이 "패딩이 틀렸다"와 "인증이 틀렸다"를 다르게 응답하면, 공격자는 그 차이만으로 암호문을 한 바이트씩 풀어낸다. 이것이 패딩 오라클이다. TLS 1.3이 CBC를 아예 뺀 이유 가운데 하나다.

논스를 다시 쓰면 무너진다

CTR과 GCM은 키와 논스로 키스트림을 만들어 평문에 XOR한다. 같은 키와 논스를 두 번 쓰면 같은 키스트림이 두 번 나온다. 두 암호문을 XOR하면 키스트림이 지워지고 두 평문의 XOR이 남는다. 한쪽 평문을 조금이라도 알면 다른 쪽이 풀린다.

GCM은 더 나쁘다. 논스가 겹친 두 메시지로 인증 키까지 계산해 낼 수 있어서, 이후에는 공격자가 아무 메시지나 위조해 통과시킨다. 기밀성과 무결성이 함께 사라진다.

흔한 사고는 프로세스 재시작에서 난다. 키는 설정 파일에 그대로 두고 카운터만 메모리에서 0으로 돌아가면, 재시작 전에 쓴 논스를 처음부터 다시 쓴다. 해법은 둘 중 하나다. 연결이나 세션마다 새 키를 만들거나, 카운터를 키와 같은 수명으로 영속화한다.

논스를 무작위로 뽑아도 된다. 다만 96비트 무작위 논스는 생일 문제 때문에 같은 키로 약 232개 메시지까지만 쓰라는 것이 GCM 규격의 권고다. 메시지가 많은 통신은 카운터 논스가 안전하다.

AEAD는 암호화하지 않는 부분도 묶는다

AEAD는 받는 쪽에서 태그를 먼저 검사하고, 맞을 때만 평문을 내준다. 라이브러리가 이 순서를 지켜 준다. 직접 CBC와 HMAC을 조합하던 시절에는 "암호화 후 MAC"인지 "MAC 후 암호화"인지, MAC에 IV가 들어가는지를 매번 따져야 했다. 그 실수가 AEAD로 사라진다. 

using System.Buffers.Binary;
using System.Security.Cryptography;

// 연결마다 새로 받은 256비트 세션 키. 논스는 방향 + 시퀀스로 만든다.
sealed class PacketCipher(byte[] key, uint direction) : IDisposable
{
    readonly AesGcm _gcm = new(key, tagSizeInBytes: 16);   // .NET 8+ 생성자
    ulong _sendSeq;

    public void Seal(ReadOnlySpan<byte> header, ReadOnlySpan<byte> body,
                     Span<byte> cipher, Span<byte> tag, out ulong seq)
    {
        seq = _sendSeq++;                      // 키 하나로 절대 되돌아가지 않는다
        Span<byte> nonce = stackalloc byte[12];
        BinaryPrimitives.WriteUInt32BigEndian(nonce, direction);
        BinaryPrimitives.WriteUInt64BigEndian(nonce[4..], seq);
        _gcm.Encrypt(nonce, body, cipher, tag, associatedData: header);
    }

    public void Dispose() => _gcm.Dispose();
}

방향 값을 논스에 넣는 이유가 있다. 클라이언트와 서버가 같은 세션 키로 각자 0번부터 세면, 양쪽의 0번 패킷이 같은 논스를 쓴다. 방향을 다르게 두거나 방향별로 키를 따로 만든다(TLS는 방향별 키를 쓴다).

선택 기준

  • 기본은 AES-256-GCM이다. 서버 CPU에는 거의 언제나 AES 가속이 있다.
  • AES 가속이 없는 기기가 많으면 ChaCha20-Poly1305를 쓴다. .NET의 ChaCha20Poly1305는 OS가 지원할 때만 쓸 수 있으니 IsSupported를 확인한다.
  • 논스를 셀 수 있으면 카운터를, 셀 수 없으면 무작위를 쓴다. 무작위 논스는 키당 메시지 수 상한을 지키고, 넘기 전에 키를 바꾼다.
  • CBC와 CTR은 새로 쓰지 않는다. 옛 데이터를 읽어야 할 때만 남겨 두고, 다시 쓸 때는 AEAD로 옮긴다.

게임 서버에서는

  • UDP 패킷은 시퀀스 번호를 논스로 쓴다. 이미 붙어 있는 번호를 논스로 쓰면 논스를 따로 보낼 필요가 없고, 겹치지 않는다는 조건도 자연히 지켜진다. 세션 키는 접속마다 새로 받으므로 재접속해서 번호가 0으로 돌아가도 안전하다.
  • 재전송 공격은 암호화가 막지 않는다. 정상 패킷을 그대로 다시 보내면 태그가 맞는다. 받은 시퀀스 번호를 창(window)으로 기억해 이미 받은 번호와 너무 오래된 번호를 버린다. 자세한 판정은 게임 보안과 치트 대응에서 다룬다.
  • 태그가 틀린 패킷은 조용히 버리고 센다. 오류 내용을 돌려주면 공격자에게 단서가 된다. 세션별 실패 횟수가 늘면 끊고 기록한다.
  • 패킷마다 할당하지 않는다. AesGcm 객체를 연결마다 하나 두고, 버퍼는 Span과 풀에서 빌린다(ref와 Span). AesGcm 인스턴스는 스레드 안전하지 않으니 연결을 처리하는 스레드 하나만 쓴다.
  • 저장 데이터 암호화도 같은 규칙이다. DB 컬럼이나 세이브 파일을 암호화할 때 행마다 무작위 논스를 만들어 암호문 앞에 붙여 저장한다. 고정 IV를 쓰는 코드가 가장 흔한 실수다.

주의 사항

  • 기밀성과 무결성은 따로 챙겨야 하는 성질이다. 암호화만 하면 내용은 가려도 바뀐 것을 모른다. 인증 태그가 붙는 방식을 기본으로 쓴다.
  • 논스는 비밀이 아니지만 유일해야 한다. 평문으로 보내도 되고, 대신 같은 키로 절대 다시 쓰면 안 된다. CBC의 IV는 여기에 더해 예측할 수 없어야 한다.
  • 태그를 잘라 쓰지 않는다. GCM 태그를 짧게 하면 위조 확률이 커진다. 16바이트를 그대로 쓴다.
  • 복호화 실패를 무시하고 진행하지 않는다. 예외를 삼키고 빈 값으로 처리하는 코드가 있으면 태그 검사는 의미가 없다.
