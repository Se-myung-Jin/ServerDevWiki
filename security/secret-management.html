먼저 읽을 것: 대칭 암호와 비대칭 암호, 서명과 TLS, Generic Host와 DI

핵심 요약

시크릿은 그 값을 아는 것만으로 권한이 생기는 값이다. DB 접속 문자열, 외부 API 키, 서명용 개인 키, 인증서 키, 결제 서버 키가 여기에 든다. 암호 알고리즘이 아무리 강해도 키가 새면 끝이므로, 키를 어디에 두고 어떻게 바꾸는지가 실제 보안을 정한다.

원칙은 셋이다. 코드와 저장소에 넣지 않는다. 필요한 프로세스만 꺼내 쓰게 하고 누가 꺼냈는지 남긴다. 그리고 언제든 바꿀 수 있게 만든다. 마지막이 가장 자주 빠진다. 바꿀 수 없는 키는 새는 순간 사고를 막을 방법이 없다.

동작 원리

저장소에 들어간 시크릿은 지워지지 않는다

설정 파일에 접속 문자열을 넣고 커밋한 뒤, 다음 커밋에서 지워도 그 값은 깃 기록에 그대로 남는다. 저장소를 받은 모든 사람, 포크, CI 캐시, 백업에 사본이 있다. 기록을 다시 써서 지우는 것은 사본까지 지우지 못한다. 그래서 커밋된 시크릿은 새었다고 보고 즉시 회전한다. 기록 정리는 그다음 일이다.

저장소 호스팅 서비스의 시크릿 스캐닝과 푸시 차단, 커밋 전 훅에서 도는 검사 도구를 켜 두면 흔한 형식(클라우드 키, 개인 키 헤더, 접속 문자열)은 올라가기 전에 걸린다. 걸리지 않는 형식이 있으니 마지막 방어선일 뿐이다.

환경 변수는 파일보다 낫지만 숨겨 주지는 않는다

환경 변수로 넘기면 저장소에는 안 들어간다. 하지만 같은 사용자나 관리자는 실행 중인 프로세스의 환경을 읽을 수 있고, 자식 프로세스에 그대로 물려지며, 크래시 덤프에 통째로 담긴다(크래시 덤프). "시작할 때 설정을 전부 로그로 찍는" 코드 한 줄이 환경 변수를 로그 시스템으로 옮겨 놓기도 한다.

컨테이너 오케스트레이터의 시크릿 객체도 기본은 비슷하다. 파일이나 환경 변수로 넣어 주는 전달 수단이지, 저장 시 암호화와 접근 감사는 따로 설정해야 한다.

비밀 저장소는 접근을 좁히고 기록을 남긴다

Azure Key Vault, AWS Secrets Manager, HashiCorp Vault 같은 비밀 저장소는 하는 일이 비슷하다. 시크릿을 암호화해 보관하고, 누가 어떤 시크릿을 읽을 수 있는지 정책으로 정하고, 읽을 때마다 감사 로그를 남기고, 값의 버전을 관리한다. 서버는 시작할 때나 주기적으로 필요한 것만 꺼낸다.

남는 문제는 "저장소에 접속할 자격 증명은 어디 두나"다. 클라우드에서는 워크로드 신원으로 푼다. 관리 ID나 IAM 역할처럼 플랫폼이 그 VM이나 컨테이너에 신원을 붙여 주고, 프로세스는 짧게 사는 토큰을 받아 저장소에 접근한다. 프로세스가 들고 있는 장기 시크릿이 하나도 없게 된다. DB 접속도 같은 방식으로 비밀번호 없이 토큰으로 인증할 수 있는 곳이 늘고 있다.

한 단계 더 가면 동적 시크릿이다. 저장소가 요청을 받을 때마다 수명이 짧은 DB 계정을 새로 만들어 주고, 시간이 지나면 지운다. 새어도 곧 쓸모없어지고, 누가 언제 받은 계정인지 추적된다.

회전은 두 키를 겹쳐 두는 기간으로 한다

토큰 서명 키, 패킷 암호화의 서버 간 공유 키, DB 비밀번호 모두 같은 모양이다. DB라면 계정을 둘 두고 번갈아 비밀번호를 바꾸거나, 새 비밀번호를 추가로 허용한 뒤 옮긴다. JWT 서명 키는 키 ID(kid)를 붙여 검증하는 쪽이 여러 공개 키 가운데 고르게 한다(인증과 세션 토큰).

회전을 연습해 두지 않으면 정작 키가 샜을 때 손으로 하다가 장애를 낸다. 정기 회전은 보안보다 이 연습의 의미가 크다.

봉투 암호화: 데이터 키를 마스터 키로 감싼다

DB 컬럼 암호화, 백업 파일 암호화, 저장된 결제 정보처럼 "저장된 것"을 암호화할 때 쓰는 구조다. 데이터 키는 대칭 키라 빠르고(대칭 암호와 비대칭 암호), 마스터 키는 KMS가 쥐고 사용 기록을 남긴다. 데이터를 훔쳐 가도 KMS 권한이 없으면 풀지 못한다.

새는 경로는 대개 정해져 있다

  • 로그. 접속 문자열을 담은 예외 메시지, 요청 헤더 전체 로깅, 설정 덤프. 로그 시스템은 접근 권한이 넓고 보존 기간이 길다.
  • 크래시 덤프와 힙 덤프. 메모리에 있던 키와 토큰이 그대로 담긴다. 덤프 파일도 시크릿처럼 다룬다.
  • 클라이언트 빌드. 게임 클라이언트나 앱에 넣은 키는 꺼내진다. 그래서 그것은 시크릿이 아니다.
  • 복사해 둔 곳. 메신저, 티켓, 위키, 개인 메모. 사고 대응 중에 가장 많이 퍼진다.

선택 기준

방식좋은 점남는 위험쓰는 곳
설정 파일·코드간단하다저장소 기록에 영원히 남는다쓰지 않는다
개발용 사용자 시크릿저장소 밖, 개인 PC에만평문 파일이다로컬 개발
환경 변수·오케스트레이터 시크릿배포 도구가 넣어 준다덤프·자식 프로세스·로그로 샌다작은 서비스, 과도기
비밀 저장소 + 워크로드 신원장기 자격 증명이 없다, 감사·버전저장소 장애 시 시작 불가운영 서버 전반
동적 시크릿수명이 짧고 사용자별로 추적된다설정과 운영이 복잡하다DB 접근이 많은 큰 조직

.NET에서는 개발 중에 dotnet user-secrets로 저장소 밖 파일에 두고, 운영에서는 설정 제공자로 비밀 저장소를 연결해 같은 IConfiguration 키로 읽는다. 코드는 값이 어디서 왔는지 모른다. 

var builder = Host.CreateApplicationBuilder(args);

if (builder.Environment.IsProduction())
{
    // 관리 ID로 인증하므로 이 코드에 비밀번호가 없다
    builder.Configuration.AddAzureKeyVault(
        new Uri(builder.Configuration["KeyVault:Uri"]!),
        new DefaultAzureCredential());
}

// 개발에서는 user-secrets, 운영에서는 Key Vault의 "ConnectionStrings--GameDb"가 같은 키로 들어온다
string cs = builder.Configuration.GetConnectionString("GameDb")!;

게임 서버에서는

  • 클라이언트에 들어간 키는 시크릿이 아니다. 패킷 암호화 키를 클라이언트에 박아 두면 꺼내진다. 세션 키는 로그인 때 서버가 나눠 주고, 클라이언트에는 검증용 공개 키만 넣는다(게임 보안과 치트 대응).
  • 서버 역할마다 DB 계정을 나눈다. 게임 서버, 로그 수집기, 운영 도구가 같은 계정을 쓰면 하나가 새어도 전부 열린다. 계정이 나뉘어 있으면 회전도 하나씩 할 수 있다.
  • 서버 간 공유 키에도 회전 경로를 만든다. 로그인 서버가 발급하고 게임 서버가 검증하는 입장 토큰 키, 게이트웨이와 존 서버 사이의 키는 키 ID를 붙여 두 개를 동시에 받게 만든다. 점검 없이 바꿀 수 있어야 한다.
  • 운영자 접근을 감사한다. 운영 DB 비밀번호를 사람에게 나눠 주지 않는다. 운영 도구나 임시 권한 발급을 거치게 하고, 누가 언제 무엇을 조회했는지 남긴다.
  • 결제·플랫폼 키는 따로 둔다. 스토어 서버 API 키와 결제 대행사 서명 키는 결제를 처리하는 서비스만 읽게 한다(결제와 영수증 검증).

주의 사항

  • 커밋된 시크릿은 기록을 지우기 전에 먼저 회전한다. 순서가 바뀌면 지우는 동안에도 열려 있다.
  • 시작할 때 설정 전체를 로그로 찍지 않는다. 찍어야 하면 값이 아니라 키 이름과 출처만 남긴다.
  • SqlClient는 기본 설정(Persist Security Info=False)에서 연결을 연 뒤 ConnectionString 속성에서 비밀번호를 뺀다. 다른 드라이버도 같은지 확인하고, 접속 문자열을 예외 메시지에 넣지 않는다.
  • 비밀 저장소가 죽으면 서버가 뜨지 못한다. 시작 시 읽어 메모리에 들고 있게 하고, 갱신 실패는 경고로만 처리한다.
  • 개발·스테이징·운영의 시크릿을 같은 값으로 두지 않는다. 개발 환경은 보통 가장 허술하게 관리된다.
