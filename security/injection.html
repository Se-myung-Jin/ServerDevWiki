먼저 읽을 것: SQL과 키, ORM과 저장 설계

핵심 요약

인젝션은 사용자가 넣은 값이 명령의 구조로 해석되어 생긴다. SQL, 셸 명령, 파일 경로, 로그 형식, HTML이 모두 같은 모양이다. 데이터와 명령이 한 문자열에 섞여 있으면, 받는 쪽은 어디까지가 구조이고 어디부터가 값인지 구분할 수 없다.

막는 법은 하나다. 구조를 먼저 확정하고 값은 따로 넘긴다. 위험한 문자를 거르거나 이스케이프하는 방식은 빠뜨린 경우가 남는다. 구조와 값을 분리하면 값이 무엇이든 구조가 될 길이 없다.

동작 원리

값이 구조가 되는 순간

파라미터 바인딩은 구조와 값을 프로토콜 수준에서 따로 보내거나, 드라이버가 형식에 맞게 값을 안전하게 끼워 넣는다. 어느 쪽이든 개발자가 이스케이프를 고민할 일이 사라진다. "미리 컴파일된 쿼리"라서 안전한 것이 아니라 값이 값 칸으로 넘어가서 안전한 것이다.

C#에서 안전한 쪽과 위험한 쪽

// 안전: Dapper 파라미터
var c = await conn.QuerySingleOrDefaultAsync<Character>(
    "SELECT * FROM characters WHERE name = @name", new { name });

// 안전: EF Core 보간 문자열은 파라미터로 바뀐다
var list = db.Characters.FromSql($"SELECT * FROM characters WHERE name = {name}").ToList();

// 위험: 문자열을 먼저 만들어 Raw에 넘기면 그대로 SQL이 된다
var sql = $"SELECT * FROM characters WHERE name = '{name}'";
var bad = db.Characters.FromSqlRaw(sql).ToList();

EF Core의 FromSql·FromSqlInterpolated·ExecuteSql는 보간 자리를 파라미터로 바꾼다. 같은 보간 문자열이라도 변수에 먼저 담아 FromSqlRaw에 넘기면 이미 완성된 문자열이라 파라미터가 되지 않는다. 코드 리뷰에서 Raw가 붙은 호출은 따로 본다.

값 자리에 못 들어가는 것은 허용 목록으로

컬럼 이름, 정렬 방향, 테이블 이름은 구조라서 파라미터로 넘길 수 없다. 랭킹 화면에서 "정렬 기준"을 받는다면, 받을 수 있는 값을 미리 정해 두고 그 중 하나로 바꿔 끼운다. 문자를 거르는 것이 아니라 정해 둔 것 중에서 고른다. 

static readonly Dictionary<string, string> SortColumns = new()
{
    ["level"] = "level", ["power"] = "combat_power", ["name"] = "name",
};
string column = SortColumns.TryGetValue(req.Sort, out var c) ? c : "level";
string dir = req.Desc ? "DESC" : "ASC";
string sql = $"SELECT name, level FROM characters ORDER BY {column} {dir} LIMIT @n";

저장 프로시저도 같은 규칙을 따른다. 프로시저 안에서 문자열을 이어 붙여 EXEC나 sp_executesql로 실행하면, 프로시저를 쓴다는 사실만으로는 안전하지 않다. 그 안에서도 값은 파라미터로 넘긴다.

SQL 말고도 같은 구조가 있다

자리섞이는 것분리하는 법
OS 명령명령과 인자셸을 거치지 않는다. ProcessStartInfo.ArgumentList에 인자를 하나씩 넣는다
파일 경로디렉터리 구조와 이름입력으로 경로를 만들지 않고 ID로 찾는다. 꼭 써야 하면 Path.GetFullPath 결과가 허용한 루트 밑인지 확인한다(../ 경로 탐색)
로그로그 형식과 기록 내용구조적 로깅(logger.LogInformation("chat {Text}", text))을 쓰고, 텍스트 로그에는 줄바꿈을 치환한다. 줄바꿈이 들어가면 가짜 로그 줄을 만들 수 있다
HTML마크업과 텍스트출력할 때 인코딩한다(웹 공격)
NoSQL 질의질의 연산자와 값JSON 본문을 그대로 질의 객체로 쓰지 않는다. 연산자($ne 같은 것)가 값 자리에 들어오면 조건이 바뀐다
LDAP·XPath필터 구조와 값라이브러리의 파라미터·인코딩 함수를 쓴다

역직렬화: 데이터가 타입을 고르게 두면 안 된다

직렬화된 데이터 안에 "이 타입으로 만들어라"는 정보가 있고 서버가 그대로 따르면, 공격자가 위험한 부수 효과가 있는 타입을 골라 만들게 할 수 있다. BinaryFormatter가 대표적이다. .NET 5부터 사용 경고가 붙었고, .NET 9에서는 구현이 빠져 호출하면 예외를 던진다.

JSON도 타입 정보를 따르면 같다. Newtonsoft.Json의 TypeNameHandling을 None 이외로 두고 외부 입력을 읽으면 위험하다. 다형 역직렬화가 필요하면 System.Text.Json의 [JsonDerivedType]처럼 허용한 타입 목록 안에서만 고르게 한다. 게임 패킷은 MessagePack이나 Protobuf로 정한 스키마에 맞춰 읽는다.

선택 기준

방법평가이유
구조와 값 분리(파라미터, 인자 목록)근본 대책값이 구조가 될 수 없다
허용 목록구조를 입력으로 골라야 할 때의 대책정해 둔 것만 통과한다
이스케이프불완전문맥, 인코딩, DB 설정마다 규칙이 달라 빠지는 경우가 남는다
위험 문자 차단 목록불완전정상 이름(O'Brien)을 막고, 우회 표현은 놓친다
최소 권한 DB 계정두 번째 방어선뚫려도 할 수 있는 일이 줄어든다

입력 검증(길이, 형식, 허용 문자)은 따로 한다. 그것은 잘못된 값을 일찍 돌려보내는 장치이지 인젝션 방어가 아니다. 방어는 분리로 한다.

게임 서버에서는

  • GM 툴과 운영 웹이 가장 위험하다. 검색 조건을 자유롭게 받으려고 SQL을 조립하는 코드가 많다. 운영 도구일수록 DB 권한이 크므로 파라미터와 허용 목록을 더 엄격히 쓴다.
  • 채팅 명령어 파서. /give 아이템 수량 같은 명령을 서버가 해석할 때, 인자를 그대로 SQL이나 스크립트에 넣지 않는다. 숫자는 숫자로 파싱하고, 아이템은 기획 테이블 ID로 찾는다.
  • 닉네임·길드명은 저장할 때와 출력할 때 둘 다 본다. 저장은 파라미터로, 출력은 그 출력 형식(HTML, 로그, CSV)에 맞게 인코딩한다. DB에서 읽은 값도 입력이다. 꺼내서 다시 SQL에 이어 붙이면 넣을 때 없던 인젝션이 꺼낼 때 생긴다.
  • DB 계정을 용도별로 나눈다. 게임 서버 계정은 필요한 테이블에 읽기·쓰기만, 통계 서버는 읽기 전용 복제본만 준다. 테이블 삭제나 권한 변경은 마이그레이션 계정만 한다.
  • DB 오류를 클라이언트에 그대로 보내지 않는다. 오류 문구에 테이블 이름이나 쿼리 조각이 실려 나가면 다음 시도의 지도가 된다. 클라이언트에는 오류 코드만, 상세는 서버 로그에 남긴다.

주의 사항

  • ORM을 쓴다고 안전한 것이 아니다. FromSqlRaw, ExecuteSqlRaw, 문자열로 만든 OrderBy 필드명이 남은 구멍이다.
  • 동적으로 조립해야 하는 부분이 남으면 그 자리를 목록으로 관리하고 허용 목록으로 막았는지 확인한다.
  • 숫자 입력도 문자열로 이어 붙이면 인젝션이 된다. "숫자라서 괜찮다"는 형식 검증이 실제로 있을 때만 맞다.
