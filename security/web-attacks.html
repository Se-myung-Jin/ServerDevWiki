먼저 읽을 것: 인젝션, 인증과 세션 토큰, HTTP와 그 변천

핵심 요약

XSS(교차 사이트 스크립팅)는 인젝션이 브라우저에서 일어나는 것이다. 사용자가 넣은 값이 다른 사람의 화면에서 스크립트로 해석되어, 그 사람 권한으로 실행된다. 막는 자리는 출력하는 쪽이다.

CSRF(교차 사이트 요청 위조)는 결이 다르다. 브라우저가 쿠키를 자동으로 붙여 보내는 성질을 빌려, 로그인된 사용자가 모르는 요청을 보내게 한다. 공격자는 응답을 읽지 못하지만 요청은 처리된다. 막는 자리는 요청을 받는 쪽이다.

동작 원리

XSS: 값이 스크립트로 해석된다

종류어떻게 들어가나피해 범위
저장형게시글, 닉네임처럼 서버에 저장된 값이 나중에 보는 사람 화면에 나온다그 화면을 보는 모두. 가장 위험하다
반사형요청 주소에 실린 값이 응답에 그대로 나온다조작된 링크를 누른 사람
DOM 기반서버를 거치지 않고 페이지 스크립트가 주소나 입력값을 innerHTML 같은 곳에 넣는다링크를 누른 사람. 서버 로그에 흔적이 없을 수 있다

실행된 스크립트는 그 사이트의 출처로 돈다. 화면을 바꿔 비밀번호를 받아 내고, 사용자 이름으로 요청을 보내고, 스크립트가 읽을 수 있는 토큰을 가져간다.

막는 법은 출력 문맥에 맞는 인코딩이다. HTML 본문에서는 <, & 같은 문자를 문자 참조로 바꾸면 되지만, 속성값, URL, 스크립트 블록 안은 규칙이 각각 다르다. 그래서 같은 값을 입력 단계에서 한 번 걸러서는 안 되고, 출력하는 자리마다 그 문맥에 맞게 처리한다. Razor, React 같은 템플릿은 기본으로 인코딩한다. 위험한 자리는 그것을 끄는 곳(Html.Raw, dangerouslySetInnerHTML, innerHTML)이다. 스크립트 블록이나 onclick 속성처럼 값이 그대로 코드가 되는 자리에는 사용자 값을 아예 넣지 않는다.

뚫렸을 때를 대비한 층도 둔다. 세션 쿠키에 HttpOnly를 붙이면 스크립트가 쿠키를 읽지 못한다. 다만 스크립트는 여전히 그 사용자로서 요청을 보낼 수 있으므로 피해를 줄일 뿐이다. CSP(콘텐츠 보안 정책)로 실행할 수 있는 스크립트의 출처를 제한하고 인라인 스크립트를 막으면, 심긴 스크립트가 실행되지 않는다.

CSRF: 브라우저를 빌린다

대책하는 일한계
CSRF 토큰서버가 준 값을 폼이나 헤더에 함께 보내게 한다. 다른 사이트는 그 값을 모른다XSS가 있으면 같은 출처 스크립트가 토큰을 읽는다
SameSite 쿠키다른 사이트에서 시작된 요청에 쿠키를 붙이지 않는다. Strict는 전부, Lax는 최상위 이동의 GET만 허용한다기본값이 브라우저마다 다르다. Chromium 계열은 지정이 없으면 Lax로 취급하지만 모든 브라우저가 그렇지는 않다
Origin·Referer 확인요청이 어느 출처에서 왔는지 본다헤더가 빠지는 경우의 처리를 정해야 한다
상태 변경에 GET 금지주소를 여는 것만으로 실행되지 않게 한다POST도 다른 사이트에서 만들어 보낼 수 있다

쿠키 대신 Authorization 헤더로 토큰을 보내는 API는 브라우저가 자동으로 붙이지 않으므로 CSRF 대상이 아니다. 대신 그 토큰을 스크립트가 읽을 수 있는 곳에 두면 XSS에 약해진다(인증과 세션 토큰).

CORS는 방어가 아니다

흔한 오해가 "CORS를 막아 두면 다른 사이트가 우리 API를 못 부른다"는 것이다. 브라우저는 기본으로 다른 출처의 응답을 스크립트가 읽지 못하게 막는다(동일 출처 정책). CORS는 그 제한을 서버가 풀어 주는 규칙이다. 단순한 폼 요청은 CORS와 상관없이 날아가 처리되므로 CSRF를 막지 못한다. 오히려 Access-Control-Allow-Origin에 요청 출처를 그대로 되돌려 주면서 자격 증명을 허용하면 아무 사이트나 응답을 읽게 된다.

SSRF: 서버가 대신 요청한다

"이 이미지 URL을 받아 와라", "이 웹훅 주소로 알려라"처럼 서버가 사용자가 준 주소로 요청을 보내는 기능이 있으면, 그 주소를 내부망(관리 API, 클라우드 메타데이터 주소 169.254.169.254)으로 바꿔 서버를 대신 부릴 수 있다. 허용 도메인 목록, 내부 대역 차단, 리다이렉트 재검사로 막는다. 이름 해석 결과가 바뀌는 경우(DNS 리바인딩)까지 고려하면, 해석한 IP를 확인한 뒤 그 IP로 접속한다.

게임 서버에서는

  • 웹 표면이 생각보다 넓다. 계정 사이트, 결제 페이지, 쿠폰 입력, 커뮤니티, GM 툴, 운영 대시보드가 모두 웹이다. 게임 서버 개발자가 같이 만드는 경우가 많다.
  • GM 툴이 저장형 XSS의 표적이다. 플레이어가 지은 닉네임, 길드명, 신고 사유, 채팅 로그가 GM 툴 화면에 그대로 나온다. 높은 권한을 가진 운영자의 브라우저에서 스크립트가 돌면 피해가 크다. GM 툴도 인코딩과 CSP를 똑같이 건다.
  • 게임 안 웹 뷰. 공지, 이벤트 페이지, 채팅을 웹 뷰로 보여 주면 그 안도 브라우저다. 닉네임이나 채팅을 HTML로 끼워 넣을 때 인코딩을 빠뜨리면 클라이언트 안에서 스크립트가 돈다.
  • 결제와 쿠폰은 CSRF 대책을 건다. 쿠폰 사용, 선물 보내기, 이메일 변경처럼 상태를 바꾸는 요청에는 토큰과 SameSite를 함께 둔다. 이메일·비밀번호 변경은 현재 비밀번호를 다시 묻는다.
  • 웹훅과 이미지 주소는 SSRF를 본다. 길드 엠블럼을 URL로 받거나 디스코드 웹훅을 등록받는 기능은 서버가 그 주소로 나간다.

주의 사항

  • 입력 검증만으로 XSS를 막지 못한다. 같은 값도 HTML 본문, 속성, URL, 스크립트 안에서 처리법이 다르다.
  • HttpOnly는 쿠키 탈취를 막을 뿐, XSS로 그 사용자 대신 요청을 보내는 것은 막지 못한다.
  • CSRF 토큰을 GET 주소에 싣지 않는다. 주소는 로그, Referer, 브라우저 기록으로 샌다.
  • CORS 설정에서 출처를 그대로 반사하거나 *와 자격 증명을 함께 쓰지 않는다.
