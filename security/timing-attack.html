먼저 읽을 것: 해시와 비밀번호 저장, 인증과 세션 토큰

핵심 요약

보통의 비교는 다른 바이트를 만나는 순간 멈춘다. 빨리 끝내려는 최적화인데, 비밀 값을 비교할 때는 얼마나 오래 걸렸는지가 몇 바이트가 맞았는지를 알려 준다. 이렇게 실행 시간으로 비밀을 알아내는 것이 타이밍 공격이다.

막는 법은 비밀에 따라 실행 경로가 달라지지 않게 하는 것이다. 비교는 끝까지 하고 마지막에 한 번 판정한다. .NET에서는 CryptographicOperations.FixedTimeEquals를 쓴다.

동작 원리

빨리 끝나는 것이 정보다

한 바이트씩 확정해 나가므로 시도 횟수가 크게 줄어든다. 바이트 하나의 후보가 256개, 길이가 16이면 전수 조사는 25616이지만, 한 자리씩 맞히면 256 × 16 번(측정 반복을 곱해서)이면 된다.

차이는 나노초 단위로 작다. 그래도 같은 요청을 수천, 수만 번 보내 평균을 내면 잡음이 줄어 드러난다. 네트워크 너머라서 못 잰다는 말은 "어렵다"이지 "불가능하다"가 아니다.

끝까지 비교하고 마지막에 한 번 판정한다

// 틀린 예: 다른 바이트를 만나면 바로 돌아간다
static bool NaiveEquals(ReadOnlySpan<byte> a, ReadOnlySpan<byte> b)
{
    if (a.Length != b.Length) return false;
    for (int i = 0; i < a.Length; i++)
        if (a[i] != b[i]) return false;     // 여기서 시간이 샌다
    return true;
}

// 맞는 예: 라이브러리 함수를 쓴다
bool ok = CryptographicOperations.FixedTimeEquals(expectedTag, receivedTag);

상수 시간 비교는 모든 바이트의 XOR을 OR로 모아 두었다가 마지막에 0인지만 본다. 중간에 분기가 없다. 직접 짜면 컴파일러나 JIT가 단축 평가를 되살릴 수 있어서, 라이브러리 구현은 최적화와 인라인을 막아 둔다. 그래서 직접 짜지 않고 라이브러리 함수를 쓴다.

길이는 감춰지지 않는다. 두 값의 길이가 다르면 FixedTimeEquals도 바로 false를 돌려준다. MAC 태그나 해시처럼 길이가 고정된 값을 비교하면 문제가 없다.

어디에 쓰나

비교 대상상수 시간이 필요한가이유
MAC·HMAC 태그필요하다맞는 태그를 한 바이트씩 알아내면 고친 메시지가 검증을 통과한다
API 키, 웹훅 서명, 입장 토큰필요하다비밀 값 자체를 한 바이트씩 알아낼 수 있다
비밀번호KDF가 대부분 막는다입력을 솔트와 함께 느린 해시로 바꾼 뒤 비교하므로 입력과 비교 위치가 이어지지 않는다. 그래도 마지막 해시 비교는 라이브러리 검증 함수에 맡긴다
사용자 ID, 공개 값필요 없다비밀이 아니다

토큰을 저장소 키로 조회하는 방식(GET token:…)은 비교가 저장소 안에서 일어난다. 해시 테이블 조회라 바이트 단위로 새지는 않지만, 걱정되면 토큰의 해시를 키로 쓴다.

시간이 새는 다른 자리

계정이 있는지가 샌다. 로그인 처리에서 없는 계정이면 바로 실패를 돌려주고, 있는 계정이면 느린 비밀번호 해시를 돌린다면 응답 시간이 수십 밀리초 다르다. 이것으로 가입된 이메일을 골라낼 수 있다. 없는 계정에도 미리 만들어 둔 더미 해시로 같은 검증을 한 번 돌려 시간을 맞춘다.

캐시 접근 패턴도 샌다. 비밀 값에 따라 다른 메모리 위치를 읽으면 같은 코어를 쓰는 다른 프로세스가 캐시 적중 여부로 그것을 알아낸다(메모리 계층과 캐시). 표 조회식 AES 구현이 이것으로 공격당했고, 지금의 CPU 명령(AES-NI)과 암호 라이브러리는 비밀에 따라 메모리 접근이 달라지지 않게 만든다. 서버 코드에서 할 일은 검증된 라이브러리를 쓰는 것이다.

선택 기준

대응하는 일역할
상수 시간 비교시간 차이 자체를 없앤다근본 대책
시도 횟수 제한여러 번 재지 못하게 한다측정 반복을 막는다. 무차별 대입에도 듣는다
무작위 지연잡음을 더한다보조 수단. 반복 측정으로 평균이 나오므로 단독으로는 약하다

비밀 값을 비교하는 자리는 무조건 상수 시간 비교를 쓴다. 비용이 거의 없으므로 "공격이 현실적인가"를 따질 필요가 없다.

게임 서버에서는

  • 결제·플랫폼 웹훅 서명. 결제 대행사가 보낸 콜백의 HMAC 서명을 검증할 때 ==나 string.Equals로 비교하지 않는다. 바이트 배열로 바꿔 FixedTimeEquals로 비교한다.
  • 서버 간 인증 키. 내부 API 키나 GM 툴의 관리자 키 비교도 같다. 내부망이라도 키는 비밀이다.
  • 로그인 응답 시간 맞추기. 없는 계정, 잠긴 계정, 비밀번호 틀림이 같은 메시지와 비슷한 시간으로 응답하게 한다.
  • 실패 횟수 제한과 함께 쓴다. 같은 계정이나 같은 IP의 반복 시도를 제한하면 측정 자체가 어려워진다(레이트 리밋).

주의 사항

  • string.Equals, SequenceEqual, ==는 상수 시간이 아니다. SequenceEqual은 벡터화되어 있어 차이가 작을 뿐 일찍 끝난다.
  • 상수 시간 비교 함수를 직접 짜지 않는다. 최적화가 의도를 지울 수 있다.
  • 비교 전에 하는 일도 본다. 비밀 값을 Base64로 디코딩하다 형식 오류로 일찍 실패하는 경로도 시간 차이를 만든다.
