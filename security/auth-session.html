먼저 읽을 것: 서명과 TLS, 해시와 비밀번호 저장, Redis 활용

핵심 요약

인증은 "너는 누구냐"를 확인하는 일이고, 인가는 "그래서 이것을 해도 되냐"를 정하는 일이다. 로그인은 인증이고, GM 명령을 쓸 수 있는지 보는 것은 인가다. 인증이 맞아도 인가 검사를 빠뜨리면 남의 캐릭터를 조회하는 API가 그대로 열린다.

로그인 뒤의 상태를 들고 다니는 방법은 둘이다. 서버 세션은 상태를 서버 저장소에 두고 클라이언트에는 추측할 수 없는 식별자만 준다. 자기완결 토큰(대표가 JWT)은 사용자 정보를 토큰 안에 넣고 서명한다. 앞쪽은 지우면 즉시 무효가 되고, 뒤쪽은 저장소 없이 어느 서버든 검증할 수 있다. 무효화 속도와 저장소 의존을 맞바꾸는 셈이다.

JWT의 서명은 위조를 막을 뿐 내용을 감추지 않는다. 본문은 Base64url로 인코딩되어 있어 누구나 풀어 읽는다.

JWT는 서명이고, 검증하는 쪽이 규칙을 정한다

JWT는 헤더.본문.서명 세 조각이다. 헤더에 서명 알고리즘이 적혀 있는데, 이것을 그대로 믿으면 두 가지 사고가 난다.

  • alg: none. "서명 없음"이라고 적힌 토큰을 통과시키는 구현이 실제로 있었다.
  • 알고리즘 혼동. RS256(공개 키 검증)으로 발급하는 서버에 HS256(대칭 키)이라고 적어 보내면, 공개 키를 대칭 키 자리에 그대로 넣어 검증하는 구현이 있었다. 공개 키는 누구나 아니까 누구나 서명할 수 있게 된다.

막는 법은 하나다. 검증하는 쪽이 허용할 알고리즘과 키를 고정한다. 발급자(iss), 대상(aud), 만료(exp)도 함께 확인한다. 대상 확인을 빼면 다른 서비스용으로 발급한 토큰이 이 서비스에서도 통한다. 

builder.Services.AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddJwtBearer(o =>
    {
        o.MapInboundClaims = false;
        o.TokenValidationParameters = new TokenValidationParameters
        {
            ValidateIssuer = true,   ValidIssuer = "https://login.example.com",
            ValidateAudience = true, ValidAudience = "game-api",
            ValidateLifetime = true, ClockSkew = TimeSpan.FromSeconds(30),
            ValidateIssuerSigningKey = true,
            IssuerSigningKey = loginServerPublicKey,           // 받아 둔 공개 키
            ValidAlgorithms = new[] { SecurityAlgorithms.EcdsaSha256 } // 헤더를 믿지 않는다
        };
    });

기본 ClockSkew는 5분이라 만료 직후에도 5분 동안 통과한다. 액세스 토큰을 짧게 쓰려면 이 값도 줄인다.

짧은 액세스 토큰과 회전하는 리프레시 토큰

토큰의 약점은 무효화다. 그래서 수명을 둘로 나눈다. 액세스 토큰은 5~15분 정도로 짧게 두고, 길게 사는 리프레시 토큰으로 새 액세스 토큰을 받는다. 리프레시 토큰은 서버가 저장소에 기록해 두므로, 차단은 다음 갱신 시점에 걸린다. 결국 상태를 조금은 서버가 들고 있게 된다.

리프레시 토큰은 쓸 때마다 새것으로 바꾼다(회전). 이미 바꾼 옛 토큰이 다시 들어오면 누군가 훔쳐 쓴 것이므로, 그 계보의 토큰을 전부 무효로 만들고 다시 로그인시킨다. 이것이 재사용 탐지다.

선택 기준

상황맞는 쪽
서비스가 하나고 즉시 차단이 중요하다서버 세션
여러 서비스가 같은 로그인 결과를 믿어야 한다짧은 JWT + 서버에 기록하는 리프레시 토큰
게임 서버 입장짧은 1회용 입장 토큰, 입장 뒤에는 연결 자체가 세션
외부 플랫폼 계정플랫폼이 준 증명을 서버가 플랫폼에 직접 확인한다

"토큰이 요즘 방식"이라서 고르면 안 된다. 무효화가 늦다는 대가를 감당할 수 있는지가 먼저다.

게임 서버에서는

  • 입장 토큰은 짧고 1회용이다. 로그인 서버가 계정, 대상 서버, 만료(수십 초)를 저장소에 적고 무작위 토큰을 준다. 게이트웨이는 꺼내면서 지운다(Redis라면 GETDEL). 그 뒤로는 연결 자체가 세션이라 패킷마다 토큰을 다시 보내지 않는다(게임 서버 토폴로지).
  • 플랫폼 로그인은 서버가 플랫폼에 확인한다. Steam 세션 티켓이나 OAuth/OIDC의 ID 토큰을 클라이언트가 넘기면, 서버가 플랫폼 API나 플랫폼의 공개 키로 직접 검증한다. 클라이언트가 "검증됐다"고 알려 주는 값은 믿지 않는다.
  • 중복 로그인은 한 곳에서 정한다. 계정마다 현재 세션 위치를 한 군데에 두고, 새 로그인이 오면 옛 연결을 끊고 넘긴다. 위치를 기록하는 방법은 Redis 활용에 있다.
  • 인가는 서버가 매번 확인한다. "내 캐릭터 정보" API에 캐릭터 ID를 받는다면, 그 캐릭터가 이 계정 소유인지 서버가 다시 본다. GM 권한은 별도 역할로 두고 운영 도구 쪽에서만 받는다.
  • 계정 탈취에 대비한다. 2단계 인증, 새 기기·새 지역 로그인 알림, 비밀번호 변경 시 모든 세션과 리프레시 토큰 무효화를 둔다. 로그인 실패 시도는 계정과 IP 단위로 제한한다(레이트 리밋).

주의 사항

  • JWT 본문에 비밀번호 해시, 내부 등급, 개인 정보를 넣지 않는다. 서명은 무결성이지 기밀성이 아니다.
  • 토큰 헤더의 alg를 믿지 않는다. 검증하는 쪽이 알고리즘과 키를 고정한다.
  • 세션 식별자와 토큰은 암호용 난수로 만든다. 자동 증가 번호나 시각 기반 값은 추측된다(난수 생성).
  • 로그에 토큰 원문을 남기지 않는다. 로그를 볼 수 있는 사람이 곧 그 계정 주인이 된다.
  • 로그아웃은 클라이언트에서 토큰을 지우는 것으로 끝나지 않는다. 서버 쪽 세션이나 리프레시 토큰도 지운다.
