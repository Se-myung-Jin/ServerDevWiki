먼저 읽을 것: 해시 테이블 · 대칭 암호와 비대칭 암호

핵심 요약

암호학적 해시는 임의 길이 입력을 고정 길이 값으로 줄이는 일방향 함수다. 키가 없고, 같은 입력이면 누구나 같은 값을 얻는다. 되돌리는 절차가 없으니 암호화의 한 종류가 아니다.

누구나 계산할 수 있으므로 해시만으로는 변조를 막지 못한다. 공격자가 내용을 바꾸고 해시를 다시 계산해 붙이면 된다. 변조를 막으려면 키를 아는 쪽만 만들 수 있는 값, 곧 HMAC이나 서명이 필요하다.

비밀번호 저장은 요구가 반대다. 일반 해시는 빠른 것이 장점인데, 비밀번호에서는 그것이 공격자에게 유리하다. 그래서 사용자마다 다른 솔트를 섞고, 일부러 느리고 메모리를 많이 쓰는 함수(Argon2id, scrypt, bcrypt, PBKDF2)를 쓴다.

동작 원리

해시 테이블의 해시와는 요구가 다르다

해시 테이블은 키를 칸에 고르게 뿌리기만 하면 된다(해시 테이블). xxHash나 MurmurHash는 그 목적으로 빠르게 만든 함수라, 공격자가 같은 값을 내는 입력을 일부러 만들 수 있다. 보안에 쓰는 해시는 그런 입력을 찾는 일이 현실적으로 불가능해야 한다.

성질뜻깨지면
역상 저항해시값만 보고 입력을 찾지 못한다저장된 값에서 원문이 복구된다
제2 역상 저항주어진 입력과 같은 해시를 내는 다른 입력을 찾지 못한다특정 파일을 같은 해시의 가짜로 바꾼다
충돌 저항같은 해시를 내는 두 입력을 아무거나 찾지 못한다두 문서를 미리 짜고 한쪽에 받은 서명을 다른 쪽에 옮긴다

충돌 저항이 가장 먼저 깨진다. 생일 문제 때문에 n비트 해시의 충돌은 약 2n/2번 시도로 찾을 수 있다. 앞의 두 성질은 약 2n번이 든다. 실제로 MD5는 2004년, SHA-1은 2017년에 실제 충돌이 공개됐다. 두 함수는 서명과 무결성 용도로 더는 쓰지 않는다.

비밀번호에는 솔트와 느린 함수를 쓴다

SHA-256은 GPU 한 장으로 초당 수십억 번 계산된다. 유출된 DB에 SHA-256 비밀번호가 들어 있으면 흔한 비밀번호는 거의 다 풀린다. 비밀번호용 함수는 반복 횟수나 메모리 사용량을 조절할 수 있게 만들어, 하드웨어가 빨라지면 비용을 올린다.

메모리를 많이 쓰게 하는 것은 따로 노리는 바가 있다. 공격자는 GPU나 전용 칩으로 같은 계산을 수천 개씩 동시에 돌린다. 한 번 계산하는 데 메모리가 수십 MB 들면 칩 하나에 올릴 수 있는 계산 수가 확 준다. 그래서 반복만 늘리는 PBKDF2보다 메모리도 쓰는 Argon2id나 scrypt를 먼저 권한다.

권고 수치는 하드웨어가 빨라지면서 계속 올라간다. 저장값에 함수 이름, 매개변수, 솔트를 함께 적어 두면, 로그인에 성공한 순간 새 매개변수로 다시 해시해 옛 사용자도 자연히 옮겨 간다. 

using System.Security.Cryptography;

const int Iterations = 600_000;   // 함께 저장해 두고 올릴 수 있게 한다

static string Hash(string password)
{
    byte[] salt = RandomNumberGenerator.GetBytes(16);
    byte[] hash = Rfc2898DeriveBytes.Pbkdf2(
        password, salt, Iterations, HashAlgorithmName.SHA256, 32);
    return $"pbkdf2-sha256${Iterations}${Convert.ToBase64String(salt)}${Convert.ToBase64String(hash)}";
}

static bool Verify(string password, string stored)
{
    var p = stored.Split('$');
    int iter = int.Parse(p[1]);
    byte[] salt = Convert.FromBase64String(p[2]);
    byte[] expected = Convert.FromBase64String(p[3]);
    byte[] actual = Rfc2898DeriveBytes.Pbkdf2(
        password, salt, iter, HashAlgorithmName.SHA256, expected.Length);
    return CryptographicOperations.FixedTimeEquals(actual, expected);  // 상수 시간 비교
}

ASP.NET Core Identity의 PasswordHasher는 이 형식을 대신 관리해 준다. PBKDF2(HMAC-SHA512)를 쓰고, 프레임워크 버전이 올라갈 때마다 기본 반복 횟수를 올려 왔다. Argon2id를 쓰려면 검증된 외부 라이브러리(libsodium 바인딩 등)를 쓴다. 비교에 FixedTimeEquals를 쓰는 이유는 타이밍 공격에서 다룬다.

페퍼는 DB 밖(비밀 저장소, HSM)에 둔 비밀 키다. 해시 결과를 이 키로 한 번 더 HMAC하거나 암호화해 두면, DB만 유출된 경우 공격자는 키 없이 대입을 시작할 수도 없다. 키를 바꾸기 어렵다는 비용이 있어 필수는 아니다.

무결성에는 키를 섞은 HMAC을 쓴다

"키 + 메시지"를 그냥 SHA-256에 넣으면 안전해 보이지만 틀렸다. SHA-256, SHA-1, MD5는 블록을 앞에서부터 이어 압축하는 구조라서, 해시값을 내부 상태로 삼아 뒤에 내용을 더 붙인 메시지의 올바른 해시를 키 없이 계산할 수 있다. 이것이 길이 확장 공격이다.

HMAC은 키를 안쪽과 바깥쪽에 두 번 섞는 표준 구성이라 이 공격에 걸리지 않는다. .NET에서는 HMACSHA256.HashData(key, data)를 쓴다. 키가 양쪽에 똑같이 있으므로 HMAC은 "우리 둘 중 하나가 만들었다"까지만 보장한다. 누가 만들었는지 제3자에게 증명하려면 서명을 쓴다(서명과 TLS).

게임 서버에서는

  • 로그인 폭주 때는 해시 비용이 CPU를 먹는다. 한 번에 50ms 드는 해시를 초당 2천 건 처리하면 코어 100개가 필요하다. 점검 직후 로그인은 대기열로 속도를 맞추고(레이트 리밋과 입장 대기열), 해시는 로직 스레드가 아닌 별도 작업자에서 돌린다. 비용을 낮춰 맞추지 않는다.
  • 플랫폼 로그인을 쓰면 비밀번호를 받지 않는다. 스토어나 외부 계정으로 로그인하면 서버는 비밀번호 대신 토큰을 검증한다. 직접 계정을 운영할 때만 이 저장 규칙이 필요하다(인증과 세션 토큰).
  • 패치 파일은 해시 목록에 서명한다. 매니페스트에 파일마다 SHA-256을 적고, 매니페스트 전체를 서명한다. 클라이언트는 서명을 확인한 뒤 파일 해시를 비교한다. 해시만 같은 서버에서 받아 비교하면 서버나 CDN이 뚫렸을 때 막지 못한다.
  • 기획 데이터 버전 비교에는 SHA-256으로 충분하다. 클라이언트와 서버 테이블이 같은지 확인하는 용도는 위조 방어가 아니라 식별이다(기획 데이터와 데이터 주도 설계).
  • 로그와 분석 데이터의 개인 정보는 해시만으로 가려지지 않는다. 전화번호나 이메일처럼 후보가 적은 값은 전부 해시해 보면 풀린다. 비밀 키를 섞은 HMAC으로 가리고, 그 키를 분석 쪽에 주지 않는다.

주의 사항

  • 되돌릴 수 없다는 것이 알아낼 수 없다는 뜻은 아니다. 입력 후보가 적으면 전부 대입해 맞춰 본다. 짧은 비밀번호, 생일, 전화번호가 그렇다.
  • 솔트가 약한 비밀번호를 지켜 주지는 않는다. 솔트는 표를 돌려 쓰는 것만 막는다. 한 사람을 겨냥한 대입은 느린 함수와 비밀번호 정책, 로그인 시도 제한이 막는다.
  • 비밀번호를 암호화해서 저장하지 않는다. 복호화 키가 있으면 운영자와 공격자 모두 원문을 꺼낼 수 있다. 원문을 다시 보여 줄 일이 없으므로 해시로 충분하다.
  • 해시값 비교에 ==나 SequenceEqual을 쓰지 않는다. 틀린 위치에서 일찍 끝나는 비교는 시간으로 정보를 흘린다. CryptographicOperations.FixedTimeEquals를 쓴다.
