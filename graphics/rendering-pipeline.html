먼저 읽을 것: 실행 루프와 FixedUpdate, 관심 영역과 브로드캐스트

핵심 요약

클라이언트의 한 프레임은 CPU와 GPU가 나눠 맡는다. CPU는 게임 로직을 돌리고, 보이는 것을 골라, 그리라는 명령(드로 콜)을 만들어 넘긴다. GPU는 그 명령을 받아 정점을 옮기고, 삼각형을 픽셀로 쪼개고, 픽셀마다 색을 정해 화면 버퍼에 합친다. 단계 순서는 정해져 있고, 단계마다 비용이 늘어나는 기준이 다르다.

그래서 프레임이 떨어졌을 때 첫 질문은 "무엇을 고칠까"가 아니라 "어느 쪽이 막혔나"다. 해상도를 낮춰서 빨라지면 GPU의 픽셀 쪽이고, 그대로면 CPU 쪽이다. 서버 프로그래머가 이 구조를 알아야 하는 이유는, 서버가 보내는 엔티티 수가 곧 클라이언트의 CPU 비용이 되기 때문이다.

동작 원리

한 프레임을 CPU와 GPU가 나눠 맡는다

CPU 쪽에서 비싼 것은 물체 수다. 물체마다 위치를 갱신하고, 시야 안인지 검사하고, 드로 콜을 하나씩 만든다. 드로 콜 하나를 만들 때마다 드라이버가 상태를 검사하고 명령을 채우는 비용이 붙는다. GPU 쪽에서 비싼 것은 정점 수와 픽셀 수다. 같은 장면이라도 해상도가 두 배면 픽셀 처리량이 네 배가 된다.

단계마다 비용이 느는 기준이 다르다

단계어디서무엇에 비례하나늘어나는 경우
게임 로직, 애니메이션CPU움직이는 물체 수캐릭터가 몰린 장면, 뼈가 많은 모델
보이는 것 고르기CPU장면의 물체 수넓은 시야, 많은 소품
드로 콜 제출CPU그릴 물체 수와 재질 종류제각각 다른 장비를 한 캐릭터들
정점 처리GPU정점 수상세한 모델을 멀리서도 그대로 그릴 때
픽셀 처리GPU픽셀 수 × 덧그린 횟수고해상도, 반투명 이펙트가 겹칠 때
출력 병합GPU픽셀 수반투명을 여러 겹 섞을 때

같은 픽셀을 여러 번 칠하는 것을 덧그리기(overdraw)라 한다. 불투명한 물체는 깊이 비교로 가려진 픽셀을 일찍 버릴 수 있지만, 반투명 이펙트는 뒤의 색과 섞어야 해서 겹칠 때마다 다시 칠한다. 스킬 이펙트가 한 화면에 수십 개 터지는 전투에서 프레임이 떨어지는 흔한 원인이다.

CPU와 GPU는 엇갈려 함께 돈다

CPU는 GPU가 앞 프레임을 그리는 동안 다음 프레임의 명령을 만든다. 그래서 둘 중 느린 쪽이 프레임 시간을 정한다. CPU가 12ms, GPU가 20ms면 프레임은 20ms이고, CPU는 매 프레임 8ms를 기다린다. 이때 CPU 쪽을 아무리 줄여도 빨라지지 않는다. 엇갈려 도는 만큼 입력이 화면에 나오기까지 프레임이 더 걸리는데, 이 지연은 프레임 표시와 지연에서 다룬다.

고치기 전에 어느 쪽이 막혔는지 가린다

프레임이 떨어지면 먼저 시험 하나로 볼 곳을 좁힌다. 한 번에 하나만 바꾸고, 바꿀 때마다 다시 잰다. 짐작으로 고치면 막히지 않은 쪽을 고치느라 시간을 쓴다.

시험결과뜻
해상도를 반으로빨라진다GPU 픽셀 쪽이 막혔다
해상도를 반으로그대로다CPU 쪽이거나 GPU 정점 쪽이다
화면에 나오는 물체 수를 줄인다빨라진다CPU의 로직·드로 콜 쪽이다
모델을 단순한 것으로 바꾼다빨라진다GPU 정점 쪽이다

시험으로 방향을 잡은 뒤에는 엔진 프로파일러(Unity의 Profiler와 Frame Debugger 등)로 CPU 시간과 GPU 시간을 나눠 본다. "CPU 시간이 GPU를 기다리는 데 쓰였다"는 표시가 보이면 GPU 쪽이 막힌 것이다.

묶어서 그리면 드로 콜이 준다

같은 재질의 물체를 한 번에 보내면 드로 콜 수가 준다. 움직이지 않는 물체를 미리 하나로 합치는 배칭, 같은 모델을 위치만 바꿔 여러 개 한 번에 그리는 인스턴싱이 대표적이다. 나무 천 그루, 같은 몬스터 백 마리는 인스턴싱으로 몇 번의 드로 콜로 줄어든다. 반대로 캐릭터마다 다른 장비와 재질을 입고 있으면 묶을 수 없어 물체 수만큼 드로 콜이 나간다.

게임 서버에서는

  • 서버가 보낸 엔티티 수가 클라이언트의 CPU 비용이 된다. 서버가 시야 안 캐릭터 300명을 보내면 클라이언트는 300명의 위치를 보간하고, 애니메이션을 돌리고, 드로 콜을 만든다. 서버 쪽 대역폭은 견뎌도 저사양 기기의 CPU가 먼저 무너진다. 관심 영역 반경과 "한 화면에 보여 줄 최대 인원"은 클라이언트 팀과 함께 정한다(관심 영역과 브로드캐스트). 가까운 순으로 상위 N명만 자세히 보내고 나머지는 갱신 주기를 낮추는 식으로 서버가 나눠 줄 수 있다.
  • 클라이언트 프레임이 떨어지면 네트워크 동작도 흔들린다. 입력을 프레임마다 모아 보내는 클라이언트는 프레임이 반으로 떨어지면 전송 횟수도 반이 된다. 보간과 예측도 프레임 단위로 돌아서 화면이 뚝뚝 끊긴다(실행 루프와 FixedUpdate). 공성전이나 이벤트에서 "렉" 제보가 몰리면 서버 지표와 함께 클라이언트 프레임 통계를 같이 본다.
  • 서버에는 렌더링이 없다. 서버는 화면을 그리지 않으므로 이 파이프라인의 GPU 쪽 전부가 빠진다. Unity나 Unreal로 만든 전용 서버도 헤드리스(그래픽 없는) 빌드로 돌려 물리, 충돌, 게임 로직만 남긴다. 서버의 틱 비용은 클라이언트의 프레임 비용과 전혀 다른 곳에서 나오므로, 클라이언트 프로파일 결과를 서버 용량 계산에 그대로 쓰지 않는다.
  • 보이지 않는 것은 보내지 않는다. 클라이언트가 시야 밖을 그리지 않는 것은 성능 문제지만, 서버가 시야 밖 정보를 보내지 않는 것은 보안 문제다. 클라이언트가 그리지 않는 데이터도 메모리에 있으면 벽 투시 치트가 읽어 간다(게임 보안과 치트 대응).

주의 사항

  • "FPS가 낮다"는 말만으로는 어느 쪽이 막혔는지 모른다. 같은 저프레임이라도 CPU 쪽이면 서버가 보내는 엔티티 수가 원인일 수 있고, GPU 쪽이면 이펙트나 해상도 문제다.
  • 평균 프레임률이 아니라 프레임 시간의 분포를 본다. 평균 60fps라도 가끔 100ms짜리 프레임이 끼면 끊겨 보인다(프레임 표시와 지연).
  • 개발 PC에서 재는 숫자는 저사양 모바일 기기와 몇 배씩 다르다. 서버가 보낼 양을 정할 때는 목표 최저 사양 기기에서 잰 값을 기준으로 삼는다.
