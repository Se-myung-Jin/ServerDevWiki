먼저 읽을 것: 참조 지역성

핵심 요약

복잡도 표만 보면 연결 리스트가 중간 삽입·삭제에서 유리하다. 하지만 실측에서는 대개 배열(동적 배열)이 이긴다. 연결 리스트의 O(1)에는 "위치를 이미 알면"이라는 조건이 붙고, 노드가 흩어져 있어 접근마다 캐시 미스를 내기 때문이다.

그래서 기본은 배열이다. 연결 리스트는 노드 참조를 이미 들고 있고, 원소 주소가 바뀌면 안 되는 좁은 자리에서만 고른다. 연속 배치가 왜 빠른지는 참조 지역성에서 다뤘다. 여기서는 연산별 비용과 고르는 기준을 본다.

동작 원리

표에서 연결 리스트가 이기는 칸은 "위치를 알면 중간에 넣기·빼기" 하나뿐이다. 그 위치를 찾는 데 순회가 필요하면 같은 O(n)이 되고, 그때는 캐시 덕분에 배열이 빠르다. 배열의 중간 삽입도 실제로는 메모리 블록을 한 번 미는 연속 복사라 생각보다 싸다. 원소가 수천 개 정도면 대개 배열 쪽이 낫다.

왜 하필 두 배로 늘리나

동적 배열은 용량이 차면 더 큰 버퍼를 새로 잡고 원소를 옮긴다. 그 순간은 O(n)이지만, 전체 삽입 횟수로 나누면 한 번당 상수가 된다(분할 상환).

두 배로 늘리면 n개를 넣는 동안 옮긴 원소의 합이 1 + 2 + 4 + … (n보다 작은 2의 거듭제곱까지) < 2n이다. 넣는 n번을 더해도 전체 비용이 3n 미만이라 한 번당 상수다. 반대로 일정한 개수씩(예: 10개씩) 늘리면 재할당이 n/10번 일어나고 매번 옮기는 양이 커져 전체가 O(n²)이 된다. 늘리는 배수가 1.5여도 상환 O(1)은 유지된다. 배수는 메모리 낭비와 재할당 빈도 사이의 조절이다.

연결 리스트가 실제로 나은 자리

상황왜 연결 리스트인가
노드 참조를 이미 들고 있고, 그 자리에서 자주 넣고 뺀다찾는 비용 없이 링크만 바꾸면 된다
원소 주소가 바뀌면 안 된다배열은 재할당하면 원소가 옮겨 가지만 노드는 제자리에 있다
노드를 통째로 다른 목록으로 옮긴다포인터만 바꾸면 되고 복사가 없다
객체 안에 링크를 둔다(침입형 리스트)노드를 따로 할당하지 않는다. C++ 서버의 세션·타이머 목록에서 흔하다

대표적인 예가 LRU 캐시다. 해시맵이 키에서 노드 참조를 바로 주므로 리스트를 훑을 일이 없고, 쓴 노드를 맨 앞으로 옮기는 일은 앞뒤 링크만 바꾸면 끝난다. 두 자료구조가 서로의 약점(해시맵은 순서가 없고, 리스트는 찾기가 느리다)을 메운다.

선택 기준

상황C#에서 고를 것
대부분의 경우, 순회가 주된 작업List<T>. 크기를 대략 알면 new List<T>(capacity)로 미리 잡는다
크기가 고정이고 할당을 아끼고 싶다배열 T[], 잠깐 쓰는 구간은 Span<T>
순서가 상관없고 중간 삭제가 잦다List<T> + 맨 끝 원소와 바꿔서 지우기(아래). O(1)
노드 참조를 들고 중간 삽입·삭제, 주소 유지LinkedList<T>. 재 보고 고른다
정렬된 상태를 유지하며 넣고 뺀다SortedSet<T>·SortedDictionary(트리 기반, 트리와 이진 탐색 트리)
 
// 순서가 상관없는 목록에서 i번째를 O(1)로 지운다: 맨 끝 원소를 그 자리로 옮기고 끝을 지운다
static void RemoveAtSwapBack<T>(List<T> list, int i)
{
    int last = list.Count - 1;
    list[i] = list[last];
    list.RemoveAt(last);   // 끝에서 지우는 것은 옮길 원소가 없다
}

게임 서버에서는

  • 틱마다 도는 목록은 배열로 둔다. 몬스터·투사체·버프 목록은 매 틱 전부 훑는다. 삽입·삭제보다 순회가 압도적으로 많으니 List<T>에 두고, 죽은 원소는 위의 바꿔서 지우기로 O(1)에 뺀다.
  • 순회 중에 목록을 고치지 않는다. foreach로 List<T>를 도는 중에 추가·삭제하면 InvalidOperationException이 난다. 뒤에서부터 인덱스로 돌며 지우거나, 지울 것을 모아 두었다가 루프가 끝난 뒤 RemoveAll로 한 번에 지운다. 앞에서부터 RemoveAt을 반복하면 O(n²)이 된다.
  • 지연에 민감한 경로는 용량을 미리 잡는다. 끝 삽입이 상환 O(1)이어도 재할당이 걸리는 그 한 번은 O(n)이고, 큰 배열이면 LOH 할당까지 붙는다. 접속자 수처럼 상한을 아는 목록은 시작할 때 용량을 잡아 둔다.
  • 복사 없이 빠르게 훑으려면 CollectionsMarshal.AsSpan(list). 내부 배열을 Span<T>로 직접 본다. 값 타입 원소를 제자리에서 고칠 수 있고 경계 검사도 줄지만, 그동안 목록에 원소를 넣거나 빼면 안 된다.

주의 사항

  • 복잡도 표만으로는 고를 수 없다. n이 작으면 상수가 지배하고, 배열의 상수가 가장 작다. 같은 O(n)이라도 배열 순회가 몇 배 빠르다.
  • 상환 O(1)은 "매번 싸다"가 아니다. 재할당이 걸리는 한 번은 O(n)이다. 평균이 아니라 최악의 지연이 중요한 자리면 미리 잡는다.
  • 배열에서 원소의 위치나 참조를 오래 들고 있지 않는다. 재할당되면 원소가 옮겨 가고, 중간 삭제가 일어나면 인덱스가 밀린다. 오래 가리켜야 하면 안정된 ID나 핸들을 쓴다(메모리 배치와 자료구조).
