먼저 읽을 것: 서버 틱 루프 · 대리자와 이벤트

핵심 요약

커맨드 패턴은 메서드 호출을 객체로 만드는 것이다. "누가, 무엇을, 어떤 값으로" 할지를 객체 하나에 담아 두면 그 호출을 큐에 넣고, 나중에 실행하고, 기록해 두고, 거꾸로 되돌릴 수 있다. 바로 부르는 호출로는 할 수 없는 일들이다.

기록한 커맨드를 처음 상태 위에서 다시 실행하면 리플레이가 된다. 상태를 프레임마다 통째로 적는 것보다 훨씬 적게 저장한다. 다만 리플레이는 같은 처음 상태와 같은 입력에서 비트 단위로 같은 결과가 나올 때(결정론)만 성립한다. 결정론이 하나라도 깨지면 재생은 몇 틱 뒤부터 원래와 다른 게임이 된다.

동작 원리

호출이 객체가 되면 실행 시점과 대상을 나중에 정한다

바로 player.Move(dir)를 부르면 호출은 그 자리에서 끝난다. new MoveCommand(playerId, dir)를 만들면 그 호출은 값이 되어 다른 곳으로 넘길 수 있다. 네트워크 스레드가 받은 요청을 커맨드로 만들어 큐에 넣고, 로직 스레드가 틱마다 꺼내 실행하는 구조가 그대로 이것이다. 만드는 쪽은 언제 실행될지 모르고, 실행하는 쪽은 누가 만들었는지 몰라도 된다.

실행 메서드가 대상을 인자로 받게 하면 같은 커맨드를 어떤 캐릭터에도 쓸 수 있다. 플레이어 입력과 AI가 만드는 지시가 같은 모양이 되므로, 자리를 비운 플레이어의 캐릭터에 AI를 붙이거나 봇으로 부하 시험을 돌리는 일이 커맨드를 만드는 쪽만 바꿔서 된다. 

public interface ICommand
{
    int ActorId { get; }
    bool Validate(World world);   // 서버가 먼저 판정한다
    void Execute(World world);
}

public sealed record MoveCommand(int ActorId, Vector2 Dir) : ICommand
{
    public bool Validate(World w) => w.TryGet(ActorId, out var a) && a.IsAlive && Dir.LengthSquared() <= 1.0001f;
    public void Execute(World w) => w.Get(ActorId).Velocity = Dir * w.Get(ActorId).Speed;
}

// 로직 스레드의 틱
while (queue.TryDequeue(out var cmd))
{
    if (!cmd.Validate(world)) { metrics.Rejected++; continue; }
    cmd.Execute(world);
    recorder.Write(world.Tick, cmd);
}

되돌리려면 바뀐 것만 기억해 둔다

커맨드에 Undo를 붙이면 되돌리기가 된다. 유닛을 옮기는 커맨드라면 실행할 때 옮기기 전 위치를 자기 안에 담아 두었다가, 되돌릴 때 그 값으로 돌려놓는다. 객체 상태를 통째로 복사해 두지 않는다. 커맨드는 대개 상태의 작은 부분만 고치므로, 바꾼 값만 담는 편이 훨씬 싸다.

여러 단계를 되돌리려면 실행한 커맨드를 목록에 쌓고 현재 위치를 함께 둔다. 되돌리기는 현재 위치의 커맨드를 되돌리고 위치를 한 칸 뒤로 옮긴다. 다시 하기는 위치를 앞으로 옮기고 그 커맨드를 다시 실행한다. 되돌린 상태에서 새 커맨드를 실행하면 위치 뒤에 남은 것은 버린다.

여기서 커맨드는 두 종류로 갈린다. 버튼에 걸어 두는 커맨드는 "무엇을 할 수 있는가"를 나타내므로 하나를 만들어 두고 계속 쓴다. 되돌리기용 커맨드는 "그때 일어난 한 번의 동작"이므로 실행할 때마다 새로 만들고 그 안에 되돌릴 값을 담는다.

리플레이는 상태 대신 커맨드를 적는다

무엇을 적나저장량되살리는 법깨지는 조건
틱마다 상태 전체엔티티 수 × 틱 수. 길어질수록 크게 는다원하는 틱의 상태를 바로 읽는다거의 없다. 저장 공간이 문제다
처음 상태 + 틱별 커맨드입력 수만큼. 상태보다 몇 자릿수 작다처음부터 시뮬레이션을 다시 돌린다결정론이 하나라도 어긋나면 갈라진다
주기적 상태 + 사이의 커맨드둘 사이가까운 상태에서 시작해 커맨드를 돌린다갈라져도 다음 상태 지점에서 다시 맞춰진다

재생은 특별한 경로가 아니다. 평소 시뮬레이션을 돌리면서 네트워크 대신 기록에서 커맨드를 꺼내 같은 틱에 넣는 것뿐이다. 그래서 재생이 원래와 똑같이 흐르는지가 곧 시뮬레이션이 결정론적인지를 확인하는 시험이 된다. 셋째 방식처럼 상태를 가끔 함께 적으면 중간부터 볼 수 있고, 원래 상태의 해시와 재생 중 상태의 해시를 비교해 어느 틱에서 갈라졌는지 찾을 수 있다.

게임 서버에서는

  • 요청은 커맨드로 받아 틱에서 실행한다. I/O 스레드가 패킷을 파싱해 커맨드를 만들고 존의 큐에 넣는다. 월드 상태는 로직 스레드만 고치므로 락이 필요 없다(게임 서버 스레딩 모델). 큐가 길어지면 받는 쪽을 늦추는 장치도 커맨드 큐 앞에 둔다(백프레셔).
  • 실행 전에 서버가 검증한다. 커맨드는 "하겠다"는 요청이지 결과가 아니다. 쿨다운, 사거리, 자원, 생존 여부를 서버 상태로 다시 확인하고 통과한 것만 실행한다. 기록은 무슨 일이 있었는지를 남길 뿐, 그 일이 유효했는지를 정하지 않는다(게임 보안).
  • 입력 로그 재생으로 버그를 다시 일으킨다. 문제가 난 존의 시작 상태와 그 뒤 커맨드를 남겨 두면 개발 장비에서 같은 틱을 다시 돌려 볼 수 있다. 드물게 나는 크래시나 아이템 복제처럼 재현이 어려운 버그에 특히 쓸모가 있다. 시각이나 외부 응답 같은 값까지 커맨드로 기록해야 재생이 맞는다. 같은 로그를 부하를 만들려고 다시 트는 쓰임은 목적이 달라서 부하 시험과 트래픽 재생에서 다룬다.
  • C#에서는 할당을 줄인다. 커맨드마다 클래스를 new하면 초당 수만 개가 GC로 간다(GC 기초). 자주 오는 커맨드는 구조체로 만들어 종류 번호와 함께 링 버퍼에 담거나, 풀에서 꺼내 쓴다(struct 설계).
  • 결정론적 락스텝은 커맨드만 주고받는다. 모든 참가자가 같은 커맨드로 같은 시뮬레이션을 돌리면 상태를 보낼 필요가 없다. 대신 결정론이 깨지면 바로 갈라진다. 서버가 상태를 보내는 방식과의 비교는 스냅샷과 상태 동기화에서 다룬다.

주의 사항

  • 되돌리기를 서버 롤백으로 착각하지 않는다. 커맨드의 Undo는 편집기나 턴제 게임의 되돌리기에 쓴다. 다른 플레이어에게 이미 보인 결과, DB에 쓴 결과, 다른 서버에 보낸 메시지는 Undo로 되돌아오지 않는다.
  • 커맨드 안에 객체 참조를 담지 않는다. 큐에서 기다리는 동안 대상이 죽거나 다른 존으로 갈 수 있다. ID를 담고 실행할 때 다시 찾는다. 기록도 ID여야 다른 프로세스에서 재생된다.
  • 기록 형식에 버전을 붙인다. 커맨드의 필드나 실행 규칙이 바뀌면 예전 기록은 새 코드에서 다르게 재생된다. 재생하려면 기록을 만든 빌드가 필요하다는 점을 전제로 둔다.
  • 모든 호출을 커맨드로 만들지 않는다. 미루거나, 기록하거나, 되돌릴 필요가 없는 호출을 커맨드로 감싸면 코드만 길어진다.
