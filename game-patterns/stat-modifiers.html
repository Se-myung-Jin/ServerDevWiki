먼저 읽을 것: 상태 폭발과 계층형 FSM · 기획 데이터와 데이터 주도 설계

핵심 요약

캐릭터의 공격력은 하나의 숫자로 저장해 두는 값이 아니다. 기본값에 장비, 버프, 패시브가 붙인 모디파이어를 정해진 순서로 쌓아 얻는 계산 결과다. 같은 모디파이어라도 어떤 순서로 쌓느냐에 따라 결과가 달라지므로 순서는 공식으로 못 박는다.

모디파이어는 붙인 출처와 함께 들고 있다가 출처가 사라질 때 함께 뺀다. 같은 버프가 다시 걸리면 갱신할지, 중첩할지, 강한 것만 남길지를 버프마다 정한다. 최종값은 저장하지 않고 필요할 때 처음부터 다시 계산한다. 현재 값에서 거꾸로 빼고 나누는 식으로 되돌리면 오차가 쌓이고 복구할 수 없는 경우가 생긴다.

동작 원리

최종 스탯은 저장하지 않고 계산한다

스탯 하나는 기본값과 모디파이어 목록으로 이루어진다. 기본값은 레벨, 종족, 영구 성장처럼 잘 바뀌지 않는 것에서 온다. 모디파이어는 장비를 끼거나 버프가 걸릴 때 목록에 들어가고, 벗거나 끝날 때 빠진다. 최종값은 이 둘에서 언제든 다시 만들어 낼 수 있는 파생 데이터다.

그래서 최종값을 "현재 공격력"이라는 필드에 직접 더하고 빼는 구조는 피한다. 버프 셋이 겹친 뒤 가운데 하나가 먼저 끝나면, 지금 값에서 그 몫만 정확히 걷어 내기가 어렵다. 목록에서 그 항목만 지우고 다시 계산하면 문제가 사라진다.

모디파이어는 세 층으로 쌓는다

흔한 공식은 모디파이어를 종류별로 모아 층마다 한 번씩 적용한다. 

최종 = (기본 + Σ고정) × (1 + Σ퍼센트) × Π(1 + 곱)
종류쌓는 법예성질
고정 합모두 더한다무기 공격력 +20뒤의 퍼센트를 함께 받는다
퍼센트 합산퍼센트끼리 먼저 더한 뒤 한 번 곱한다+10%, +20% → ×1.3개수가 늘어도 효과가 선형으로 는다
곱연산하나씩 곱한다최종 피해 ×1.5여러 개가 겹치면 기하급수로 커진다

퍼센트를 합산 층과 곱 층으로 나누는 이유는 밸런스다. 대부분의 퍼센트 효과를 합산 층에 넣으면 아이템을 많이 모아도 값이 폭주하지 않는다. 곱 층은 드물고 강한 효과에만 쓴다.

순서를 바꾸면 값이 달라진다

기획 문서의 "+10%"가 합산 층인지 곱 층인지 적혀 있지 않으면, 구현하는 사람마다 다르게 넣는다. 그래서 모디파이어 종류에 이름을 붙이고, 데이터 테이블의 열로 종류를 고르게 한다(기획 데이터와 데이터 주도 설계).

모디파이어는 출처와 함께 든다

모디파이어마다 누가 붙였는지를 적어 둔다. 출처는 장비 슬롯, 버프 인스턴스, 패시브 스킬 같은 식별자다. 장비를 벗거나 버프가 끝나면 그 출처의 모디파이어를 모두 지우고 다시 계산한다. 

enum ModKind { Flat, PercentAdd, PercentMult }

readonly record struct Modifier(ModKind Kind, float Value, long SourceId);

sealed class Stat(float baseValue)
{
    readonly List<Modifier> _mods = new();
    bool _dirty = true;
    float _cached;

    public float Value => _dirty ? Recalculate() : _cached;

    public void Add(Modifier m) { _mods.Add(m); _dirty = true; }

    public void RemoveSource(long sourceId)
    {
        if (_mods.RemoveAll(m => m.SourceId == sourceId) > 0) _dirty = true;
    }

    float Recalculate()
    {
        float flat = 0, percent = 0, mult = 1;
        foreach (var m in _mods)
        {
            switch (m.Kind)
            {
                case ModKind.Flat:        flat += m.Value; break;
                case ModKind.PercentAdd:  percent += m.Value; break;
                case ModKind.PercentMult: mult *= 1 + m.Value; break;
            }
        }
        _cached = (baseValue + flat) * (1 + percent) * mult;
        _dirty = false;
        return _cached;
    }
}

제거할 때 지금 값에서 나누거나 빼서 되돌리지 않는다는 점이 중요하다. 곱 모디파이어를 나눠서 걷어 내면 부동소수 오차가 조금씩 남는다. ×0 같은 효과(공격력 0으로 만드는 디버프)는 나눠서 되돌릴 수조차 없다. 목록에서 지우고 처음부터 다시 쌓으면 이런 문제가 없다.

같은 버프가 또 걸리면

버프가 이미 걸려 있는데 같은 것이 다시 오면 무엇을 할지가 버프마다 다르다. 규칙은 버프 데이터에 열로 둔다.

규칙다시 걸리면흔한 예
갱신효과는 그대로, 지속 시간만 처음으로 되돌린다대부분의 단일 강화 버프
스택 중첩스택 수가 하나 늘고 효과가 스택 수만큼 커진다. 최대 스택이 있다출혈 5중첩, 분노 스택
독립 인스턴스시전자마다 따로 걸리고 따로 끝난다여러 사람이 건 지속 피해
강한 것만같은 그룹에서 가장 센 하나만 적용하고 나머지는 대기한다이동 속도 감소 여러 개
거부이미 있으면 새로 걸리지 않는다면역, 쿨다운 성격의 디버프

"같은 버프"의 기준도 정해야 한다. 버프 ID가 같으면 같은지, 시전자까지 같아야 같은지, 서로 다른 버프라도 같은 그룹이면 묶는지를 정한다. 강한 것만 남기는 규칙에서는 센 버프가 먼저 끝났을 때 대기하던 약한 버프가 이어서 살아나야 한다. 그래서 적용하지 않는 버프도 목록에서 지우지 않고 들고 있는다.

언제 다시 계산하나

다시 계산하는 시점은 두 가지 방식이 있다. 하나는 읽을 때마다 계산하는 방식이다. 모디파이어가 몇 개 안 되면 이쪽이 가장 단순하고 틀릴 곳이 없다. 다른 하나는 위 코드처럼 더티 플래그를 두는 방식이다. 모디파이어가 바뀔 때 표시만 해 두고, 다음에 읽을 때 한 번 계산한 뒤 캐시를 쓴다. 피격 판정마다 공격력과 방어력을 읽는 전투에서는 이쪽이 싸다.

스탯끼리 기대는 관계가 있으면 더티 표시도 그 관계를 따라 번진다. 공격력이 힘에서 나오면, 힘이 바뀔 때 공격력도 다시 계산해야 한다.

이 관계는 고리가 없어야 한다. "체력의 10%만큼 공격력 증가"와 "공격력의 10%만큼 체력 증가"가 함께 걸리면, 어느 쪽을 먼저 계산하느냐에 따라 값이 달라지거나 서로를 끝없이 다시 계산한다. 이런 효과는 상대 스탯의 최종값이 아니라 기본값을 참조하게 하거나, 계산 단계를 층으로 나눠 앞 층의 값만 읽게 해서 고리를 끊는다.

상한과 반올림은 정한 자리에서 한 번

스탯에는 대개 상한과 하한이 있다. 이동 속도는 일정 값을 넘지 않고, 쿨타임 감소는 40%에서 멈추고, 방어력은 음수가 되지 않는다. 문제는 어디서 자르느냐다. 이동 속도 퍼센트 합을 +50%에서 자르더라도 그 뒤에 곱 층의 ×1.2가 남아 있으면 최종값은 상한을 넘는다. 최종값을 자르면 넘지 않는 대신, 곱 효과가 상한에 묻혀 아무 일도 하지 않는 구간이 생긴다. 둘 다 쓸 수 있는 선택이므로 스탯마다 자르는 자리를 공식에 적어 둔다.

퍼센트 합이 −100% 아래로 내려가는 경우도 막는다. 둔화를 여러 개 받아 합이 −120%가 되면 곱하는 값이 음수가 되어 캐릭터가 뒤로 걷는다. 합 단계에서 하한을 두거나 최종값을 0으로 자른다.

반올림도 같다. 층마다 반올림할지, 마지막에 한 번만 할지에 따라 1씩 차이가 난다. 서버가 float로 계산하고 클라이언트가 double로 계산해도 경계값에서 반올림 결과가 갈린다. 그래서 많은 서버가 퍼센트를 만분율 정수(1만 = 100%)로 들고 정수 연산으로 계산한다. 같은 입력이면 어느 기계에서나 같은 결과가 나오기 때문이다(수의 표현).

만료와 상태 이상

버프는 대개 시간이 지나면 끝난다. 버프마다 끝나는 시각을 적어 두고, 타이머 구조가 그 시각에 제거를 부른다. 버프마다 OS 타이머를 따로 만드는 것은 피한다(타이머 자료구조). 제거는 모디파이어 목록에서 그 출처를 지우는 일과 같으므로 앞의 방식이 그대로 쓰인다.

기절, 침묵, 이동 불가 같은 상태 이상은 수치가 아니라 켜고 끄는 표시다. 상태 이상은 FSM 상태가 아니라 집합으로 둔다고 했는데(상태 폭발과 계층형 FSM), 그 집합도 출처별로 든다. 기절 둘이 겹쳤다가 하나가 먼저 풀렸을 때 "기절 해제"로 표시를 지워 버리면 남은 기절이 사라진다. 상태 이상마다 걸어 둔 출처의 수를 세거나 출처 목록을 들고, 0이 될 때만 끈다.

게임 서버에서는

  • 계산 권한은 서버에 있다. 피해 판정에 쓰는 값은 서버가 계산한 값뿐이다. 클라이언트가 보낸 공격력을 믿으면 고친 클라이언트가 그대로 이긴다. 클라이언트는 툴팁과 캐릭터 창을 그리려고 같은 공식으로 계산하거나 서버가 내려 준 최종값을 쓴다. 같은 공식을 따로 구현하면 툴팁과 실제 피해가 어긋나므로, C# 서버와 Unity 클라이언트라면 공식 코드를 공유 어셈블리로 함께 쓰는 방법이 흔하다.
  • 최종값은 DB에 저장하지 않는다. 저장하는 것은 기본값의 근거(레벨, 영구 성장), 장착한 장비, 남은 버프의 출처와 끝나는 시각이다. 로그인할 때 이것으로 최종값을 다시 만든다. 최종값을 저장해 두면 공식이나 아이템 수치를 패치한 뒤에도 옛 값이 남아, 같은 장비를 낀 두 캐릭터의 공격력이 달라진다.
  • 공식 상수는 기획 데이터에 둔다. 힘 1당 공격력 몇, 쿨타임 감소 상한 몇 퍼센트 같은 상수를 코드에 박으면 수치 조정마다 빌드와 배포가 필요하다. 테이블에서 읽고, 서버 시작 때 범위를 검사한다(기획 데이터와 데이터 주도 설계).
  • 계산 내역을 남길 수 있게 만든다. "피해가 이상하게 들어갔다"는 문의를 받으면 최종값만으로는 원인을 찾을 수 없다. 디버그 옵션으로 어떤 출처의 모디파이어가 어느 층에서 얼마를 더했는지 전투 로그에 남기게 해 두면, 기획 의도와 구현의 차이를 바로 짚을 수 있다.
  • 바뀐 스탯만 보낸다. 더티 표시는 클라이언트 동기화에도 쓴다. 틱 끝에서 이번 틱에 값이 바뀐 스탯만 모아 보내면 패킷이 줄어든다(스냅샷과 상태 동기화).

주의 사항

  • 지금 값에서 역연산으로 버프를 걷어 내지 않는다. 오차가 쌓이고 ×0이나 상한에 걸린 값은 되돌릴 수 없다. 목록에서 지우고 다시 계산한다.
  • "+10%"의 층을 문서와 데이터에 적는다. 합산인지 곱인지 정하지 않으면 사람마다 다르게 구현한다.
  • 상한과 하한을 자르는 자리를 스탯마다 정한다. 자르는 자리가 다르면 같은 모디파이어에서 다른 값이 나온다. 퍼센트 합이 −100% 아래로 내려가는 경우도 막는다.
  • 스탯끼리 서로를 참조하는 고리를 만들지 않는다. 상대 스탯의 기본값만 읽게 하거나 계산 층을 나눈다.
  • 상태 이상 해제는 출처를 따진다. 겹쳐 걸린 것 중 하나가 풀렸다고 표시를 통째로 지우지 않는다.
  • 캐시를 쓰면 더티 표시를 빠뜨리는 곳이 버그가 된다. 모디파이어를 바꾸는 경로를 Add와 RemoveSource 같은 몇 개의 메서드로 모으고, 목록을 밖에서 직접 고치지 못하게 막는다.
