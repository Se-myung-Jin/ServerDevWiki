먼저 읽을 것: 서버 틱 루프 · 프로토콜 선택 · 커맨드 패턴과 리플레이

핵심 요약

서버가 게임 상태를 정하고(서버 권한), 클라이언트는 입력만 보낸다. 체력이나 위치를 클라이언트가 정하지 않으니 그 값을 고쳐서 얻을 것이 없다. 그대로 두면 키를 누른 뒤 화면이 바뀌기까지 왕복 시간이 그대로 보이므로, 클라이언트 쪽에 세 가지를 붙인다.

대상기법화면에 보이는 시점
내 캐릭터클라이언트 예측 + 서버 재조정지금(서버보다 앞선다)
다른 캐릭터엔티티 보간조금 지난 시점(받아 둔 두 스냅샷 사이)
서버의 히트 판정지연 보상(되감기)쏜 사람이 보던 시점으로 되돌려 판정

그래서 한 화면 안에 서로 다른 시점이 섞인다. 내 캐릭터는 현재, 남의 캐릭터는 과거다. 동기화 설계는 이 시간차를 어디에 감추고 누구에게 불리하게 둘지를 정하는 일이다.

동작 원리

내 캐릭터는 응답을 기다리지 않고 먼저 움직인다

클라이언트는 입력을 서버로 보내면서 같은 입력을 자기 쪽 시뮬레이션에도 바로 적용한다. 이것이 클라이언트 예측이다. 화면은 곧바로 반응하고 서버의 답은 나중에 온다. 예측이 맞으려면 클라이언트와 서버가 같은 이동 코드를 같은 고정 간격으로 돌려야 한다.

서버 응답이 오면 아직 처리되지 않은 입력만 다시 적용한다

서버는 상태를 보낼 때 그 클라이언트의 입력을 몇 번까지 처리했는지 순번을 함께 적는다. 클라이언트는 이를 받아 재조정한다. 받은 상태를 내 캐릭터의 진짜 상태로 놓고, 그 순번까지의 입력 복사본을 버리고, 남은 입력을 그 위에 다시 적용한다. 예측이 맞았다면 화면의 위치가 그대로이고, 서버가 다르게 판정했다면(벽에 막혔다, 넉백을 맞았다) 서버 값에서 다시 계산한 위치로 맞춰진다. 

void OnServerState(PlayerState s, uint lastProcessedInput)
{
    _pending.RemoveWhile(i => i.Seq <= lastProcessedInput);   // 서버가 반영한 입력은 버린다
    var state = s;
    foreach (var input in _pending)                             // 남은 입력을 다시 적용한다
        state = Movement.Step(state, input, FixedDt);           // 서버와 같은 코드, 같은 dt
    _predicted = state;
}

어긋남이 크면 순간 이동처럼 보인다. 그래서 차이가 작을 때는 화면에 그리는 위치만 몇 프레임에 걸쳐 새 값으로 끌어당기고, 차이가 정해 둔 거리보다 크면 바로 옮긴다. 시뮬레이션 상태는 즉시 바꾸고, 부드럽게 만드는 것은 그리기 쪽에서만 한다.

다른 캐릭터는 받아 둔 두 스냅샷 사이를 보간한다

남의 캐릭터는 입력을 모르니 예측할 수 없다. 속도와 방향으로 다음 위치를 짐작하는 방법(외삽, 데드 레커닝)은 차량이나 투사체처럼 움직임이 이어지는 대상에는 통하지만, 달리다 멈추고 급히 방향을 꺾는 플레이어에게는 자주 틀린다. 그래서 다음을 짐작하는 대신 이미 받은 두 스냅샷 사이를 보간한다. 화면에 나오는 것은 실제로 일어난 움직임이고, 다만 보간 지연만큼 늦다.

스냅샷이 늦게 오거나 빠지면 그리는 시점 앞에 다음 스냅샷이 없어진다. 이때 잠깐만 외삽하고, 정해 둔 시간을 넘으면 멈춰 세운다. 버퍼를 늘리면 끊김이 줄고 지연이 늘어난다. 이 맞바꿈은 화면 쪽에서도 같은 모양으로 나온다(프레임 페이싱).

외삽은 물리 시뮬레이션을 맞추지 못한다. 앞질러 그린 물체는 바닥을 뚫거나 충돌 반응을 놓치고, 이어진 물체 사이의 구속도 지키지 못한다. 물리가 중요한 객체일수록 보간에 기댄다.

지연 보상: 서버가 쏜 사람의 시점으로 되감는다

보간 때문에 내가 조준한 적은 이미 과거의 위치다. 서버가 현재 위치로 판정하면 정확히 맞혀도 빗나간다. 지연 보상은 서버가 틱마다 각 캐릭터의 판정 상자 위치를 짧게 기록해 두었다가, 발사 요청이 오면 "그 클라이언트의 지연 + 보간 지연"만큼 과거의 위치로 되돌려 판정하는 방법이다. 쏜 사람은 보이는 대로 맞힌다.

대가는 맞는 쪽이 진다. 벽 뒤로 이미 숨었는데 맞는 일이 생긴다. 그래서 되감는 한도(대개 수백 ms)를 두고, 지연이 너무 큰 클라이언트는 그 한도 안에서만 보상한다. 되감기는 히트 판정에만 쓰고 이동이나 다른 상태에는 쓰지 않는다.

스냅샷을 작게 만든다: 델타와 관심 영역

기법하는 일필요한 것
델타 압축클라이언트가 마지막으로 받았다고 확인한 스냅샷과의 차이만 보낸다클라이언트별 확인 순번, 서버 쪽 기준 스냅샷 보관
양자화위치를 cm, 각도를 몇 비트로 줄여 담는다양쪽이 같은 규칙으로 풀어야 예측이 어긋나지 않는다
관심 영역그 클라이언트 근처의 엔티티만 담는다(관심 영역과 브로드캐스트, 존 경계는 월드 분할)들어오고 나가는 엔티티의 생성·삭제 통보
우선순위·전송률 차등가까운 것은 자주, 먼 것은 가끔 보낸다엔티티별 마지막 전송 틱

델타는 기준이 되는 스냅샷을 클라이언트가 실제로 받았을 때만 쓸 수 있다. 확인되지 않은 스냅샷을 기준으로 차이를 보내면, 그 기준을 잃은 클라이언트는 풀 수 없다. 그래서 확인이 끊기면 전체 스냅샷을 보낸다. 스냅샷은 금방 낡는 데이터라 재전송이 의미 없으므로 UDP 위에서 보내고, 빠진 것은 다음 스냅샷으로 덮는다(프로토콜 선택). 틱 레이트와 스냅샷 전송률을 따로 정하는 이유는 서버 틱 루프에서 다뤘다.

선택 기준

방식주고받는 것맞는 게임약점
스냅샷 + 예측·보간입력은 위로, 상태는 아래로FPS, 액션, MMO 전투. 서버가 진실을 가져야 하는 게임대역폭이 엔티티 수에 비례한다. 화면 시점이 섞인다
결정론적 락스텝모든 참가자의 입력만(커맨드)유닛 수천 개의 RTS, 격투 게임(롤백 넷코드)결정론이 깨지면 갈라진다. 가장 느린 참가자에 맞춰지거나 롤백 비용이 든다. 상태가 모두에게 있어 맵 핵에 약하다
요청·응답(턴제, 비실시간)행동 요청과 결과카드, 퍼즐, 수집형의 대부분실시간 움직임이 없을 때만 맞는다

게임 서버에서는

  • 이동 코드를 클라이언트와 공유한다. 예측은 클라이언트가 서버와 같은 결과를 낼 때만 맞는다. 이동·충돌 코드를 한 라이브러리로 두고 양쪽에서 같은 고정 간격으로 돌린다. C# 서버와 Unity 클라이언트라면 같은 어셈블리를 공유하기 쉽다(Unity와 .NET).
  • 입력은 검증하고 결과는 서버가 낸다. 클라이언트가 보낸 이동 입력이 속도 한계를 넘거나, 순번이 건너뛰거나, 초당 개수가 너무 많으면 버린다. 클라이언트가 위치를 직접 보내는 설계는 위치 조작을 막을 수 없다(게임 보안).
  • MMO는 엔티티 수가 대역폭을 정한다. 한 화면에 수백 명이 모이는 공성전에서는 관심 영역, 전송률 차등, 양자화를 함께 쓴다. 그래도 넘치면 먼 캐릭터의 갱신을 줄이고, 줄인 사실은 보간 지연을 늘려 감춘다.
  • 틱 레이트를 지연 보상과 함께 정한다. 서버가 되감을 수 있는 정밀도는 기록 간격이 정한다. 틱이 20Hz면 50ms 단위로만 되감기 때문에 사이를 보간해 판정해야 한다. 기록 버퍼 크기는 "최대 보상 시간 ÷ 틱 간격"이다.

주의 사항

  • 예측 범위를 넓히지 않는다. 내 이동처럼 내가 결과를 대부분 정하는 것만 예측한다. 다른 사람과 부딪히는 일, 아이템 획득, 처치처럼 서버 판정에 달린 것을 예측하면 되돌릴 때 더 크게 어긋난다.
  • 재조정은 시뮬레이션 상태를 바로 바꾼다. 부드럽게 보이려고 시뮬레이션 값 자체를 천천히 옮기면 남은 입력을 다시 적용한 결과가 서버와 계속 어긋난다. 끌어당기기는 그리는 위치에만 한다.
  • 보간 지연은 반응성을 깎는다. 지연을 너무 크게 잡으면 남의 행동이 늦게 보이고 지연 보상이 되감아야 할 시간도 길어진다. 스냅샷 간격에 맞춰 최소한으로 둔다.
  • 서버 시각과 클라이언트 시각을 맞춘다. 보간과 지연 보상은 "몇 번째 틱의 상태인가"로 계산한다. 스냅샷에 틱 번호를 넣고, 클라이언트는 벽시계가 아니라 추정한 서버 틱으로 그리는 시점을 정한다(시계와 타이머).
