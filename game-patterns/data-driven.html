먼저 읽을 것: 불변과 null 다루기 · volatile과 Interlocked

핵심 요약

데이터 주도 설계는 아이템 능력치, 몬스터 배치, 스킬 계수, 드롭 확률 같은 수치와 목록을 코드 밖의 테이블로 빼는 방식이다. 기획자는 코드를 고치지 않고 값을 바꾸고, 서버는 그 테이블을 읽어 규칙을 실행한다. 프로그래머가 맡는 일은 값을 받아들이는 통로다. 읽고, 검증하고, 바꿔 끼우는 과정을 믿을 수 있게 만든다.

통로가 허술하면 데이터 한 줄이 서버를 죽인다. 없는 아이템을 가리키는 드롭 행, 합이 100%를 넘는 확률표, 음수 쿨타임은 컴파일러가 잡아 주지 않는다. 그래서 서버는 로드할 때 테이블 전체를 검증하고, 실패하면 시작하지 않는다. 운영 중에 바꿀 때는 새 테이블을 따로 만들어 검증을 통과한 뒤에만 참조 하나를 바꾼다.

동작 원리

시트에서 서버 메모리까지

무엇을 테이블로 빼나

테이블로 빼는 것은 자주 바뀌고 코드의 흐름을 바꾸지 않는 값이다. 능력치, 계수, 쿨타임, 보상 목록, 스폰 위치와 주기, 확률표가 여기에 든다. 이런 값이 코드 안에 있으면 수치 하나를 고칠 때마다 빌드와 배포가 필요하고, 기획자는 프로그래머를 기다린다. 값이 밖으로 나가면 바뀌는 속도가 기획의 속도가 된다.

비헤이비어 트리와 상태 기계도 같은 방식으로 에셋으로 뺄 수 있다. 서버가 트리 에셋을 읽어 실행하는 이야기는 비헤이비어 트리에서 다뤘다.

형식은 쓰는 자리에 따라 고른다

형식좋은 점약한 점
엑셀·스프레드시트 원본기획자가 편집하기 쉽다. 수식과 서식을 쓴다서버가 직접 읽으면 안 된다. 병합된 칸, 숨은 열, 셀 서식에 따라 값이 달라진다
CSV단순하고, 버전 관리에서 줄 단위 차이가 잘 보인다타입과 중첩이 없다. 쉼표와 줄바꿈이 든 값은 따옴표 규칙에 기댄다
JSON중첩 구조와 목록을 담는다. 도구가 많다크고, 파싱이 느리다. 숫자 정밀도는 파서마다 다르다
바이너리(MessagePack, FlatBuffers 등)작고 빠르다. FlatBuffers는 파싱 없이 바로 읽는다사람이 읽을 수 없어, 원본과 내보내기 도구를 함께 관리해야 한다

흔한 구성은 원본은 시트로 두고, 내보내기 도구가 검증 가능한 중간 형식이나 바이너리를 만드는 것이다. 버전 관리에는 원본과 함께 내보낸 결과도 남긴다. 그래야 어느 배포에 어떤 값이 나갔는지 되짚을 수 있다.

코드 생성으로 타입을 붙인다

시트의 머리 행에 열 이름과 타입을 적어 두면, 도구가 그것을 읽어 행 하나에 해당하는 C# 타입과 로더를 만든다. 코드는 row["Damage"] 같은 문자열 조회 대신 row.Damage를 쓰게 되고, 열 이름이 바뀌면 컴파일이 깨져 바로 드러난다. 런타임 리플렉션으로 열을 맞추는 방식보다 빠르고 Native AOT에서도 막히지 않는다(리플렉션과 소스 생성기). 

// 도구가 만든 코드. 직접 고치지 않는다
public sealed record ItemRow(int Id, string Name, int Damage, int DropGroupId);

public sealed class GameData
{
    public required FrozenDictionary<int, ItemRow> Items { get; init; }
    public required FrozenDictionary<int, DropGroupRow> DropGroups { get; init; }
}

같은 생성기가 클라이언트 쪽 코드도 만들면, 두 쪽이 같은 스키마에서 나온 타입을 쓴다.

로드할 때 전부 검증하고, 실패하면 멈춘다

검증은 값 하나를 볼 때가 아니라 로드할 때 한꺼번에 한다. 런타임에 "이 아이템 ID가 있나"를 그때그때 확인하는 코드는 빠뜨리기 쉽고, 빠뜨린 곳은 특정 몬스터를 잡았을 때만 터진다.

  • 참조가 맞는지 본다. 드롭 그룹이 가리키는 아이템, 스킬이 가리키는 효과, 퀘스트가 가리키는 NPC가 모두 실제로 있어야 한다.
  • 범위를 본다. 확률은 0과 1 사이, 확률표의 합은 정해진 값, 쿨타임과 레벨은 음수가 아니어야 한다.
  • 키와 필수값을 본다. ID가 겹치지 않고, 빈 칸이 기본값 0으로 조용히 바뀌지 않아야 한다.
  • 관계를 본다. 진화 단계나 선행 퀘스트에 고리가 없어야 한다(그래프 표현과 탐색).

하나라도 틀리면 서버는 시작하지 않는다. 오류는 처음 하나에서 멈추지 말고 전부 모아 파일 이름, 행, 열과 함께 출력한다. 잘못된 데이터로 떠서 플레이어의 아이템을 망가뜨리는 것보다 시작하지 못하는 편이 훨씬 싸다. 같은 검증을 빌드 파이프라인에서도 돌리면, 서버에 닿기 전에 걸러진다.

읽기 전용으로 공유한다

로드가 끝난 테이블은 아무도 고치지 않는다. 그러면 모든 존 스레드가 락 없이 같은 테이블을 읽을 수 있다. 행 타입은 init 속성이나 record로 두고, 컬렉션은 읽기 전용 형태로 내보낸다. .NET 8의 FrozenDictionary는 만들 때 시간을 더 쓰는 대신 조회를 빠르게 하는 읽기 전용 사전이라, 한 번 만들고 계속 읽는 기획 테이블에 맞는다(불변과 null 다루기).

테이블의 값을 게임 객체가 고쳐 쓰면 안 된다. 아이템 하나에 강화 수치를 더하려고 테이블의 행을 바꾸면, 같은 아이템을 가진 모든 플레이어가 바뀐다. 테이블은 원형이고, 플레이어마다 다른 값은 플레이어 쪽 객체에 따로 둔다.

핫 리로드는 참조 하나를 바꾼다

public static class Data
{
    static GameData _current = null!;
    public static GameData Current => Volatile.Read(ref _current);

    public static bool TryReload(string path, ILogger log)
    {
        var next = GameDataLoader.Load(path, out var errors);   // 옆에 새로 만든다
        if (errors.Count > 0) { log.LogError("reload rejected: {Errors}", errors); return false; }
        Interlocked.Exchange(ref _current, next);              // 검증을 통과하면 한 번에 바꾼다
        return true;
    }
}

// 쓰는 쪽: 한 번의 처리 안에서는 처음 잡은 테이블만 본다
var data = Data.Current;
var item = data.Items[itemId];
var group = data.DropGroups[item.DropGroupId];

기존 테이블을 그 자리에서 고치면, 읽던 스레드가 반쯤 바뀐 테이블을 본다. 새 테이블을 따로 다 만들고 검증한 뒤 참조 하나를 원자적으로 바꾸면, 읽는 쪽은 v1 전체나 v2 전체 중 하나만 본다(volatile과 Interlocked). 쓰는 쪽은 처리 하나를 시작할 때 참조를 지역 변수로 한 번만 잡는다. 같은 처리 안에서 Data.Current를 두 번 읽으면 그 사이에 교체가 일어나 v1의 아이템과 v2의 드롭 그룹을 섞을 수 있다.

바꿔도 이미 진행 중인 것은 옛 값을 쓴다. 시전 중인 스킬, 이미 생성된 몬스터, 진행 중인 퀘스트는 생성할 때 읽은 값을 들고 있다. 이것을 즉시 바꿀지 다음 생성부터 반영할지 정해 두어야 한다. 행을 지우는 리로드는 특히 위험하다. 플레이어가 가진 아이템이 가리키는 ID가 사라지기 때문이다. 지우지 말고 사용 중지 표시를 붙이는 쪽이 안전하다. 서버 설정 값의 갱신은 Generic Host와 의존성 주입의 IOptionsMonitor가 맡고, 기획 테이블처럼 서로 얽힌 큰 묶음은 위처럼 통째로 바꾼다.

클라이언트와 서버의 테이블이 다를 때

클라이언트도 같은 테이블을 들고 화면에 수치를 보여 준다. 패치 타이밍이 어긋나면 클라이언트는 공격력 100이라 보여 주고 서버는 120으로 계산한다. 판정은 언제나 서버 테이블이 기준이다. 접속할 때 테이블 버전이나 파일 해시를 주고받아 다르면 패치를 요구하거나 경고를 남긴다. 테이블 묶음마다 해시를 따로 두면 무엇이 어긋났는지 좁힐 수 있다.

선택 기준

바뀌는 것둘 자리이유
수치, 목록, 확률, 배치데이터규칙은 같고 값만 바뀐다. 기획자가 직접 조정한다
몇 가지 정해진 동작 중 고르기데이터의 열거값 + 코드의 구현"효과 종류 = 회복"처럼 종류만 데이터가 고르고, 동작은 코드가 정한다
조건과 분기가 계속 늘어나는 규칙코드데이터 안에 조건식 언어를 만들기 시작하면 타입도 디버거도 테스트도 없는 스크립트가 된다

데이터로 표현할 수 있는 범위를 넓힐수록 기획의 자유는 늘지만, 검증할 수 있는 범위는 좁아진다. 경계는 "검증기가 이 값을 보고 틀렸다고 말할 수 있는가"로 정한다. 말할 수 없으면 그 규칙은 코드로 둔다.

게임 서버에서는

  • 서버는 자기 테이블만 믿는다. 클라이언트가 보내는 값 가운데 테이블에서 나오는 것(가격, 대미지, 쿨타임)은 받지 않고 서버가 직접 찾는다. 클라이언트 테이블은 고칠 수 있다고 가정한다(게임 보안).
  • 큰 테이블은 프로세스에 한 벌만 둔다. 존이 여럿이어도 테이블은 읽기 전용이라 함께 쓸 수 있다. 맵 높이 정보나 경로 그래프처럼 아주 큰 데이터는 바이너리로 내보내 메모리 맵으로 붙이면, 같은 머신의 여러 서버 프로세스가 물리 메모리를 함께 쓴다(메모리 맵 파일).
  • 데이터 배포를 코드 배포와 나눈다. 수치 조정은 서버 바이너리를 다시 빌드하지 않고 데이터 묶음만 배포한다. 묶음에 버전을 붙여 어느 서버가 어떤 데이터를 쓰는지 보이게 하고, 문제가 생기면 이전 묶음으로 되돌린다(배포 파이프라인).
  • 리로드는 모든 서버에 같이 일어나게 한다. 서버마다 다른 시점에 바뀌면, 존을 옮긴 플레이어가 다른 값을 겪는다. 리로드 명령과 결과(성공, 실패, 쓰는 버전)를 모아서 확인한다.

주의 사항

  • 빈 칸을 0으로 읽지 않는다. 파서가 빈 값을 조용히 기본값으로 바꾸면 쿨타임 0의 스킬이 생긴다. 필수 열이 비면 오류로 처리한다.
  • 부동소수 값은 내보낼 때 형식을 고정한다. 문화권 설정에 따라 소수점이 쉼표로 읽히는 일이 있다. 파싱은 CultureInfo.InvariantCulture로 한다.
  • ID를 재사용하지 않는다. 지운 아이템의 ID를 새 아이템에 주면, DB에 남아 있던 옛 아이템이 새 아이템으로 바뀐다.
  • 테이블 객체를 고쳐 쓰지 않는다. 원형을 바꾸면 그 행을 쓰는 모든 것이 바뀐다. 플레이어별 값은 따로 둔다.
