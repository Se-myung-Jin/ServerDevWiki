먼저 읽을 것: 인터페이스와 추상 클래스 · Generic Host와 의존성 주입

핵심 요약

서비스 로케이터는 인터페이스로 서비스를 찾아 주는 전역 등록소다. 부르는 쪽은 Services.Get<IAudit>()처럼 인터페이스만 알고, 어떤 구현이 들어 있는지, 그 객체가 어디서 만들어졌는지는 모른다. 시작할 때 구현을 등록해 두면 코드 어디서나 꺼내 쓸 수 있다.

편한 만큼 대가가 있다. 클래스가 무엇에 기대는지가 생성자나 매개변수에 드러나지 않고 메서드 본문 깊숙이 숨는다. 등록을 빠뜨린 실수는 컴파일할 때가 아니라 그 줄이 실행될 때 드러난다. 그래서 의존성은 되도록 인자나 생성자로 넘기고, 로케이터는 여러 단계를 지나야 닿는 횡단 관심사에만 쓴다.

동작 원리

부르는 쪽은 구현도 위치도 모른다

public static class Services
{
    static IAudit _audit = NullAudit.Instance;   // 등록 전에도 null이 아니다

    public static IAudit Audit => _audit;
    public static void Provide(IAudit? audit) => _audit = audit ?? NullAudit.Instance;
}

sealed class NullAudit : IAudit
{
    public static readonly NullAudit Instance = new();
    public void Write(in AuditRecord r) { }      // 아무것도 하지 않는다
}

// 어디서든
Services.Audit.Write(new AuditRecord(playerId, "trade", itemId));

싱글턴과 닮았지만 같지 않다. 싱글턴은 클래스 스스로 자기 인스턴스가 하나뿐이라고 정하고 직접 만든다. 로케이터는 서비스 클래스를 건드리지 않는다. 바깥 코드가 구현을 골라 넣으므로 실행 중에 바꾸거나 시험용 대역으로 갈아 끼울 수 있다. 다만 전역에서 닿을 수 있다는 성질은 싱글턴과 똑같다.

등록은 언제, 어떻게 하나

방식장점단점
시작 코드가 직접 넣는다(Provide)단순하다. 무엇이 들어갔는지 한 곳에서 보인다등록 순서를 사람이 맞춰야 한다
설정 파일로 구현 타입을 고른다재빌드 없이 바꾼다리플렉션으로 만들어 느리고, 오타가 실행 중에야 드러난다(리플렉션과 소스 생성기)
처음 찾을 때 만든다(지연 생성)쓰지 않는 서비스는 만들지 않는다첫 호출이 느리고, 여러 스레드가 동시에 처음 부르면 경쟁이 생긴다

못 찾았을 때 무엇을 할지 정해 둔다

정책동작맞는 곳
null을 돌려준다부르는 쪽마다 null을 확인해야 한다. 하나라도 빠뜨리면 NullReferenceException이다쓰지 않는 편이 낫다
바로 예외를 던진다등록 누락을 시작하자마자 알 수 있다없으면 서버가 돌 수 없는 서비스(DB, 설정)
널 서비스(Null Object)를 준다아무 일도 하지 않는 구현이 대신 불린다. 부르는 쪽은 확인할 것이 없다없어도 기능이 도는 서비스(오디오, 통계, 감사 로그)

널 서비스는 일부러 기능을 끄는 데도 쓴다. 부하 시험에서 감사 로그를 끄거나, 단위 시험에서 외부 통보를 막을 때 널 구현을 넣으면 된다. 다만 꼭 있어야 하는 서비스에 널 구현이 들어가면 기능이 조용히 사라진다. 그런 서비스는 시작할 때 등록을 확인하고 없으면 멈추게 한다.

범위를 어디까지 열지 고른다

전역 하나로 열면 어디서든 닿지만, 존마다 다른 구현을 쓸 수 없고 시험끼리 상태를 나눠 쓴다. 존이나 세션처럼 범위를 가진 객체가 자기 로케이터를 들고, 그 안의 코드가 거기서 찾게 하면 범위를 좁힐 수 있다. 상속받는 기반 클래스에 보호된 접근자를 두어 파생 클래스에서만 닿게 하는 방법도 있다. 범위를 좁힐수록 숨은 의존이 퍼지는 범위도 좁아진다.

의존성 주입과 무엇이 다른가

둘 다 "구현을 바깥에서 정한다"는 점은 같다. 차이는 누가 꺼내 오느냐다. 로케이터는 쓰는 쪽이 등록소에 가서 꺼낸다. 의존성 주입은 조립하는 쪽이 필요한 것을 생성자로 넣어 준다. 그래서 주입에서는 의존이 시그니처에 드러나고, 컨테이너가 시작할 때 빠진 등록을 찾아낼 수 있다. .NET의 DI 컨테이너와 수명 규칙은 Generic Host와 의존성 주입에서 다뤘다.

DI 컨테이너인 IServiceProvider를 클래스에 넘겨 놓고 그 안에서 GetService를 부르면, 컨테이너를 쓰고 있어도 하는 일은 로케이터다. 의존이 다시 본문 안으로 숨는다.

선택 기준

상황고를 것이유
쓰는 곳이 몇 군데이고 넘기기 쉽다인자나 생성자로 넘긴다의존이 보이고 시험하기 쉽다. 로케이터를 쓸 이유가 없다
애플리케이션을 DI 컨테이너로 조립한다생성자 주입빠진 등록과 수명 실수를 컨테이너가 잡아 준다
로그, 지표, 시계처럼 거의 모든 곳에서 쓴다범위를 좁힌 로케이터나 정적 진입점모든 생성자에 같은 인자를 끌고 다니는 비용이 더 크다
엔진이 객체를 만들어 생성자를 쓸 수 없다로케이터Unity 컴포넌트처럼 생성자 주입이 막힌 곳이다

게임 서버에서는

  • 횡단 관심사에만 쓴다. 로그, 지표, 감사 기록, 현재 시각, 설정 조회는 전투, 거래, 우편 어디서나 필요하다. 이런 것을 생성자마다 넘기면 거의 모든 클래스가 같은 인자를 받는다. 게임 규칙이 기대는 핵심 객체(월드, 인벤토리, 저장소)는 로케이터로 숨기지 않고 넘긴다.
  • 시각을 서비스로 두면 시험과 재생이 쉬워진다. 코드가 DateTime.UtcNow를 직접 부르면 시간에 따라 결과가 달라진다. .NET 8의 TimeProvider처럼 시각을 서비스로 두고 틱 시각을 돌려주게 하면, 시험에서는 시각을 마음대로 옮기고 리플레이에서는 기록된 시각을 넣을 수 있다(커맨드 패턴과 리플레이).
  • 시험 대역으로 갈아 끼운다. 결제 검증, 외부 인증, 푸시 통보처럼 바깥으로 나가는 서비스를 가짜 구현으로 바꿔 끼우면 단위 시험이 네트워크 없이 돈다. 다만 전역 로케이터를 바꾸는 시험은 병렬로 돌면 서로를 덮어쓴다. 시험마다 범위가 따로인 로케이터를 쓰거나 그런 시험을 직렬로 돌린다.
  • 등록은 시작할 때 끝내고 이후로는 읽기만 한다. 여러 로직 스레드가 읽는 도중에 다른 스레드가 구현을 바꾸면 경쟁이 생긴다. 실행 중 교체가 필요하면 새 객체를 만들어 참조 하나를 원자적으로 바꾸는 방식으로 한다(volatile과 Interlocked).

주의 사항

  • 의존이 숨는다. 클래스 시그니처만 보고는 무엇이 필요한지 알 수 없다. 재사용하거나 시험하려면 본문을 다 읽어야 한다.
  • 등록 누락은 실행 중에 드러난다. 드물게 타는 경로에서 찾는 서비스라면 출시 뒤에야 터진다. 시작할 때 필요한 서비스를 모두 꺼내 보는 검사를 둔다.
  • 꼭 있어야 하는 서비스에 널 구현을 기본값으로 두지 않는다. 저장이나 결제가 조용히 아무 일도 하지 않게 된다.
  • 모든 것을 로케이터에 넣으면 전역 변수 모음이 된다. 숨은 의존이 코드 전체로 퍼지면 순서를 바꾸거나 떼어 내기 어려워진다.
