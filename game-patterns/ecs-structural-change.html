먼저 읽을 것: ECS 저장 구조 · 커맨드 패턴과 리플레이 · 서버 틱 루프

핵심 요약

컴포넌트 값을 바꾸는 일과 엔티티의 구성을 바꾸는 일은 무게가 다르다. 엔티티를 만들고 지우는 일, 컴포넌트를 붙이고 떼는 일을 구조 변경이라고 부른다. 구조 변경은 저장소에서 행을 옮기므로, 순회 도중 그 자리에서 하면 순회하던 저장소가 발밑에서 바뀐다.

그래서 ECS 구현들은 구조 변경을 명령으로 쌓아 두었다가 정해진 자리에서 한꺼번에 반영한다. Unity는 엔티티 커맨드 버퍼, flecs는 지연 모드, Bevy는 Commands다. 미룬다고 변경이 싸지지는 않는다. 언제 일어나는지가 한곳에 모일 뿐이다.

동작 원리

값을 바꾸는 것과 구성을 바꾸는 것

연산구조 변경인가저장소에서 일어나는 일
컴포넌트 값 쓰기 (체력 -10)아니다그 자리의 값만 바뀐다
엔티티 생성·파괴그렇다테이블에 행을 더하거나 빼고, 빈자리를 끝 행으로 메운다
컴포넌트 붙이기·떼기그렇다아키타입이 바뀌어 다른 테이블로 행을 옮긴다
공유 컴포넌트 값 바꾸기 (Unity)그렇다공유 값마다 청크가 나뉘므로 다른 청크로 옮긴다
켜고 끄는 컴포넌트 토글 (Unity)아니다청크 안의 비트 하나만 바뀐다

옮기는 비용 자체는 ECS 저장 구조에서 봤다. 여기서는 그 일을 언제 하느냐를 본다.

순회하던 저장소를 그 자리에서 고치면 안 된다

시스템이 테이블을 앞에서부터 돌다가 지금 엔티티를 지운다고 하자. 빈자리는 마지막 행으로 메워진다. 순회 위치는 다음 칸으로 넘어가므로 옮겨 온 엔티티를 건너뛴다. 컴포넌트를 붙여 다른 테이블로 옮기면, 그 테이블을 나중에 돌 때 같은 엔티티를 두 번 만날 수도 있다. 배열이 재할당되면 들고 있던 참조가 해제된 메모리를 가리킨다.

컨테이너를 돌면서 그 컨테이너를 고칠 때와 같은 문제다(반복자 무효화). C#의 List<T>는 이것을 예외로 잡아 주지만, ECS 저장소는 보통 성능 때문에 검사하지 않는다.

잡 안의 구조 변경은 동기점을 부른다

여러 스레드에 잡을 나눠 시스템을 돌리는 엔진에서는 문제가 더 커진다. 다른 잡이 지금 읽고 있는 청크를 옮기면 그 잡이 깨진다. 그래서 Unity는 구조 변경을 메인 스레드에서만 직접 실행하게 한다.

메인 스레드가 구조 변경을 하려면 그 저장소를 쓰는 잡이 모두 끝나야 한다. 메인 스레드가 기다리는 이 자리를 동기점(sync point)이라고 한다. 기다리는 동안 작업 스레드가 놀기 때문에, 구조 변경을 틱 여기저기서 하면 병렬화의 이득이 사라진다.

커맨드 버퍼에 쌓았다가 정해진 자리에서 반영한다

커맨드 버퍼는 AddComponent, DestroyEntity 같은 호출을 그 자리에서 실행하지 않고 기록해 둔다. 나중에 메인 스레드가 기록을 재생한다. 커맨드 패턴을 저장소 변경에 쓴 것이다. 

partial struct DeathSystem : ISystem
{
    public void OnUpdate(ref SystemState state)
    {
        var ecb = SystemAPI.GetSingleton<EndSimulationEntityCommandBufferSystem.Singleton>()
                           .CreateCommandBuffer(state.WorldUnmanaged);

        foreach (var (hp, entity) in SystemAPI.Query<RefRO<Health>>().WithEntityAccess())
        {
            if (hp.ValueRO.Value <= 0)
                ecb.DestroyEntity(entity);   // 지금 지우지 않고 기록만 한다
        }
        // 기록한 명령은 시뮬레이션 그룹 끝에서 한꺼번에 재생된다
    }
}
  • Unity Entities: 기본 월드에 재생 담당 시스템이 미리 있다. 초기화·시뮬레이션 그룹에는 시작과 끝에 하나씩, 표시 그룹에는 시작에만 있다. 어느 시스템의 버퍼에 기록하느냐로 반영 시점을 고른다. 잡 안에서는 ParallelWriter로 기록한다.
  • flecs: ecs_defer_begin과 ecs_defer_end 사이의 연산이 기록됐다가 끝에서 실행된다. 시스템 안에서는 기본으로 지연 모드라 구조 변경이 저절로 미뤄지고, 값 쓰기는 그대로 된다.
  • Bevy: 시스템은 Commands에 기록하고, 스케줄러가 시스템 사이에 넣는 동기점에서 반영된다.

미룬 명령은 쌓는 동안 보이지 않는다

기록만 했으므로 같은 틱의 뒤 시스템은 아직 옛 구성을 본다. 파괴를 기록한 엔티티는 동기점까지 살아서 쿼리에 걸리고, 생성을 기록한 엔티티는 아직 없다.

Unity의 커맨드 버퍼가 생성 명령에 돌려주는 Entity는 재생 전까지 진짜가 아닌 임시 값이다. 같은 버퍼의 뒤 명령에서만 쓸 수 있고, 다른 곳에 저장해 두면 재생 뒤 아무것도 가리키지 않는다. flecs에서는 지연 구간 중에 지워진 엔티티를 향한 명령이 반영 때 무시된다.

순서는 저절로 정해지지 않는다

여러 스레드가 한 버퍼에 동시에 기록하면 기록 순서가 잡 스케줄링에 따라 달라진다. Unity의 ParallelWriter가 명령마다 정렬 키를 받는 이유다. 재생 전에 그 키로 정렬하므로, 스케줄링과 상관없는 값(쿼리 안의 청크 인덱스 등)을 키로 주면 재생 순서가 매번 같다. 결정론이 필요한 리플레이나 락스텝 계열 동기화에서는 이 순서가 결과를 가른다.

자주 켜고 끄는 표시는 구조 변경을 피한다

기절·은신 같은 상태를 컴포넌트를 붙이고 떼는 것으로 표현하면 바뀔 때마다 행이 이사한다. 대안은 셋이다.

  • 켜고 끄는 컴포넌트: Unity의 IEnableableComponent는 청크 안의 비트만 바꾼다. 엔티티는 제자리에 있고 쿼리에서만 빠진다. 잡에서 바로 토글할 수 있다.
  • 값 필드: StunUntilTick 같은 값을 두고 시스템이 조건으로 거른다. 구조 변경은 전혀 없지만, 쿼리가 대상을 줄여 주지 못한다.
  • sparse 저장: 그 컴포넌트만 sparse set에 둬서 붙이고 떼도 다른 컴포넌트가 옮겨지지 않게 한다(ECS 저장 구조).

게임 서버에서는

  • 구조 변경은 틱 경계에 모은다. 틱 하나를 "입력 반영 → 시뮬레이션 → 명령 재생 → 스냅샷"으로 나누면, 시뮬레이션 중에는 엔티티 집합이 고정된다. 이번 틱에 죽은 몬스터는 이번 틱의 모든 시스템에서 아직 존재하고, 다음 틱부터 없다. 규칙이 이렇게 하나로 정해지면 "죽은 대상에게 피해가 들어가는" 종류의 버그가 줄어든다.
  • 네트워크에서 온 생성·삭제도 같은 길로 보낸다. 접속, 퇴장, 소환 요청은 I/O 스레드에서 바로 저장소를 고치지 말고 큐에 넣었다가 틱 시작에 반영한다(게임 서버 스레딩 모델).
  • 스냅샷은 동기점 뒤에 만든다. 반영 전 상태로 스냅샷을 만들면 클라이언트는 이미 죽은 엔티티를 한 틱 더 본다. 반영 뒤에 만들어야 생성과 삭제가 그 틱의 스냅샷에 맞게 들어간다(스냅샷과 상태 동기화).
  • 동기점 수를 잰다. 시스템마다 다른 재생 지점을 쓰면 동기점이 늘고 작업 스레드가 자주 논다. 재생 지점을 틱당 한두 곳으로 모은다.

주의 사항

  • 미루는 것과 없애는 것은 다르다. 커맨드 버퍼는 구조 변경을 한곳에 모을 뿐이다. 재생할 때 행을 옮기는 비용은 그대로 든다.
  • 커맨드 버퍼가 돌려준 임시 엔티티를 저장하지 않는다. 재생 뒤에는 쓸모없는 값이다. 진짜 엔티티는 재생 뒤에 다시 찾는다.
  • 같은 틱 안에서 "파괴했으니 없다"고 가정하지 않는다. 동기점 전까지 그 엔티티는 쿼리에 그대로 걸린다. 중복 처리를 막으려면 파괴 예정 표시를 함께 둔다.
  • 병렬 기록의 순서를 고정한다. 정렬 키 없이 여러 스레드가 기록하면 실행마다 결과가 달라져 재현이 안 된다.
