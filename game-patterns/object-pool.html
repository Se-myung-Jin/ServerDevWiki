먼저 읽을 것: 메모리 할당자 · GC 동작과 세대

핵심 요약

오브젝트 풀은 자주 만들고 버리는 객체를 버리지 않고 모아 두었다가 다시 빌려주는 장치다. 빌릴 때 새로 할당하지 않으니 할당 비용과 GC가 할 일이 줄어든다. 대신 객체의 수명을 런타임 대신 코드가 직접 관리하게 된다.

그래서 GC 언어에서 사라졌던 버그가 돌아온다. 반납한 객체를 옛 참조로 계속 쓰는 반납 후 사용, 같은 객체를 두 번 넣는 이중 반납, 이전 사용자가 남긴 값을 그대로 쓰는 초기화 누락이다. 풀은 측정으로 할당이 문제라고 확인된 곳에만 쓰고, 이 세 가지를 막는 규칙을 함께 둔다.

동작 원리

빌리고 돌려주는 구조

가장 단순한 풀은 스택 하나다. 빌리면 꺼내고, 돌려받으면 넣는다. 방금 반납한 객체가 먼저 나가므로 캐시에 남아 있을 가능성이 높다. 고정된 배열에 객체를 미리 만들어 두고 빈 칸끼리 번호로 잇는 프리 리스트도 같은 일을 한다. 프리 리스트는 몬스터나 투사체처럼 개수 상한이 정해진 것을 담을 때 쓰기 좋다. 

public sealed class Pool<T> where T : class, IResettable, new()
{
    readonly Stack<T> _free = new();
    readonly int _max;
    public Pool(int max) => _max = max;

    public T Rent() => _free.Count > 0 ? _free.Pop() : new T();

    public void Return(T item)
    {
        item.Reset();                       // 이전 사용자의 값과 참조를 지운다
        if (_free.Count < _max) _free.Push(item);   // 넘치면 버리고 GC에 맡긴다
    }
}

이 풀은 스레드 안전하지 않다. 한 존 스레드 안에서만 쓰는 풀이라면 이대로 충분하고 가장 빠르다.

초기화는 반납할 때 한다

빌린 쪽이 매번 필요한 값을 덮어쓴다면 초기화를 빌릴 때 해도 결과는 같아 보인다. 그래도 반납할 때 지우는 쪽이 낫다. 풀에 들어 있는 동안 객체가 쥔 참조는 GC 입장에서 살아 있는 참조다. 반납한 패킷 객체가 세션이나 큰 배열을 가리킨 채로 풀에 있으면, 그 객체들이 회수되지 않는다(GC 언어의 메모리 누수). 반납할 때는 참조 필드를 비우고 컬렉션은 Clear()로 비운다. 컬렉션을 새로 만들지 않는 것은 담아 둔 용량을 다시 쓰기 위해서다.

빌릴 때 하는 일은 그 사용에 필요한 값을 넣는 것뿐이다. 반납 때 지웠으니 "직전 사용자의 값이 남았나"를 빌리는 쪽이 걱정하지 않아도 된다.

반납 후 사용과 이중 반납

풀링한 객체는 GC가 지켜 주던 성질 하나를 잃는다. 객체가 살아 있는 동안 그 참조는 늘 같은 대상을 가리킨다는 성질이다. 반납한 뒤에도 콜백이나 다른 객체가 옛 참조를 쥐고 있으면, 그 참조는 이제 다른 사용자에게 빌려준 객체를 가리킨다. 예외도 크래시도 나지 않고, 엉뚱한 플레이어의 데이터가 바뀐다. C++의 해제 후 사용과 같은 모양의 버그다(미정의 동작).

같은 객체를 두 번 반납하면 스택에 같은 객체가 두 번 들어간다. 이후 서로 다른 두 사용자가 그 객체 하나를 함께 받는다. 막는 방법은 세 가지다.

  • 객체에 상태를 둔다. 빌려준 상태인지 표시해 두고, 이미 풀에 있는 객체가 반납되면 바로 예외를 던진다. 디버그 빌드에서는 반드시 켠다.
  • 오래 쥘 것은 참조 대신 핸들로 준다. 핸들은 칸 번호와 세대 번호의 쌍이다. 칸이 재사용될 때마다 세대를 올리면, 옛 핸들로 찾을 때 세대가 맞지 않아 걸러진다(메모리 배치와 자료구조).
  • 소유자를 한 명으로 정한다. 객체를 반납할 책임이 누구에게 있는지 하나로 정해 둔다. 넘겨받은 쪽이 반납하는지, 넘긴 쪽이 반납하는지가 코드마다 다르면 이중 반납이 생긴다.

크기 상한과 줄이기

상한 없는 풀은 최대 순간치만큼 메모리를 영원히 쥔다. 이벤트 한 번에 투사체가 만 개 생겼다가 사라지면, 풀은 만 개를 계속 들고 있다. 상한을 두어 넘치는 반납은 버리고, 오래 쓰이지 않은 객체는 주기적으로 조금씩 놓아 준다. 상한은 평소 동시 사용량에 여유를 더한 정도로 잡고, 지표로 확인해 고친다.

스레드 사이에서 쓸 때

여러 스레드가 하나의 풀을 쓰면 락이나 원자 연산이 필요하고, 그 비용이 할당 비용을 넘어설 수 있다. 흔한 해법은 스레드마다 풀을 따로 두는 것이다. 한 존이 한 스레드에서 돈다면 존마다 풀을 두면 된다. 빌린 스레드와 반납하는 스레드가 다르면 반납이 한쪽 풀에만 쌓이고 다른 쪽은 계속 새로 만든다. 이럴 때는 공유 풀을 쓴다. ConcurrentBag<T>는 스레드별 목록을 두고 같은 스레드가 넣고 꺼낼 때 가장 빠르다. 다른 스레드의 목록에서 훔쳐 오는 경로는 그보다 느리다(동시성 자료구조).

.NET이 주는 풀

풀담는 것알아 둘 점
ArrayPool<T>.Shared배열스레드별 캐시와 코어별 스택을 둔 공유 풀이다. 요청보다 큰 배열이 올 수 있다. 반납할 때 기본으로 내용을 지우지 않는다(ref와 Span)
ArrayPool<T>.Create(...)배열최대 길이와 크기별 개수를 정한 전용 풀이다. 공유 풀의 크기 구간이 맞지 않을 때 쓴다
ObjectPool<T>
(Microsoft.Extensions.ObjectPool)		일반 객체정책(IPooledObjectPolicy<T>)이 만들기와 반납을 정한다. 정책의 Return이 false를 돌려주면 그 객체는 버린다. 기본 보관 개수는 프로세서 수의 두 배다
StringBuilder 풀문자열 조립같은 패키지의 StringBuilderPooledObjectPolicy가 너무 커진 빌더는 버린다
 
byte[] buf = ArrayPool<byte>.Shared.Rent(size);
try
{
    int n = Serialize(packet, buf.AsSpan(0, size));  // 길이는 따로 들고 다닌다
    Send(buf.AsSpan(0, n));
}
finally
{
    ArrayPool<byte>.Shared.Return(buf);              // 이 줄 뒤로는 buf를 쓰지 않는다
}

선택 기준

대상풀링이유
패킷·직렬화 버퍼, 큰 배열한다크고 자주 만든다. 85,000바이트를 넘는 배열은 큰 객체 힙으로 가서 2세대 수거를 앞당긴다
투사체, 이펙트, 스폰이 잦은 몬스터한다개수 상한이 있고, 생성 비용에 초기 설정이 무겁다
작고 짧게 사는 객체(작은 메시지, 임시 계산값)하지 않는다0세대 할당과 수거가 매우 싸다. 풀 관리가 더 비싸다. 구조체로 바꾸는 쪽이 먼저다(struct와 class 고르기)
오래 쥐고 다른 객체를 자주 가리키게 되는 객체조심한다풀의 객체는 오래 살아 2세대로 간다. 여기에 새 객체 참조를 넣으면 카드 마킹 때문에 0세대 수거가 그 영역을 매번 훑는다

풀은 할당이 문제라는 측정이 있을 때 넣는다. 할당량과 GC 횟수를 먼저 재고(.NET 진단 도구), 할당을 많이 하는 경로를 고른 뒤, 풀을 넣고 다시 잰다. C++ 서버라면 같은 판단을 할당기 비용으로 한다. 범용 할당기가 이미 크기별 캐시를 두므로, 전용 풀이 이기는 곳은 크기가 고정되고 개수가 많은 객체다(메모리 할당자).

게임 서버에서는

  • 패킷 버퍼가 가장 흔한 대상이다. 수신 버퍼, 송신 버퍼, 직렬화용 임시 버퍼는 초당 수만 번 만들어진다. 세션마다 큰 수신 버퍼를 따로 할당하는 대신 풀에서 빌리면 접속자 수가 출렁여도 GC가 덜 흔들린다.
  • 비동기 송신이 끝나기 전에 반납하지 않는다. SendAsync에 넘긴 버퍼는 송신이 끝날 때까지 운영체제와 런타임이 쓴다. 호출 직후 반납하면, 다음에 빌린 쪽이 쓴 값이 이전 패킷에 섞여 나간다. 반납은 송신 완료 콜백이나 await 뒤에 한다. 송신이 예외로 끝나도 반납되게 finally에 둔다(비동기에서 예외 다루기).
  • 몬스터와 투사체는 존마다 풀을 둔다. 존 스레드 안에서만 빌리고 돌려주면 락이 필요 없다. 리스폰은 풀에서 꺼내 초기 상태를 다시 넣는 일이 된다. 다른 객체가 몬스터를 가리킬 때는 참조 대신 엔티티 ID나 핸들을 쓴다.
  • 풀도 지표로 본다. 빌려준 수, 풀에 남은 수, 새로 만든 수, 상한 때문에 버린 수를 남긴다. 빌려준 수가 내려오지 않고 계속 오르면 반납이 빠진 경로가 있다. 새로 만든 수가 계속 오르면 상한이 작거나 반납이 다른 풀로 가고 있다.

주의 사항

  • 반납 뒤에는 그 참조를 쓰지 않는다. 반납한 변수에 null을 넣어 두면 실수로 쓸 때 바로 터진다. 남몰래 다른 사용자의 데이터를 바꾸는 것보다 낫다.
  • 예외 경로에서도 반납한다. try/finally나 using으로 감싸지 않으면 예외가 날 때마다 풀이 하나씩 마른다. 마른 풀은 결국 새로 만드는 풀이 된다.
  • 민감한 값은 지우고 돌려준다. ArrayPool은 기본으로 내용을 지우지 않는다. 토큰이나 개인 정보가 들어 있던 버퍼는 Return(buf, clearArray: true)로 돌려준다.
  • 풀이 할당보다 빠르다고 가정하지 않는다. 작은 객체는 런타임의 할당이 더 빠를 때가 많다. 넣기 전과 뒤를 잰다.
