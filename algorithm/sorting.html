먼저 읽을 것: 복잡도 표기

핵심 요약

비교로 정렬하는 한 최악에 Ω(n log n)보다 빠를 수 없다. 더 빠르려면 비교가 아닌 정보(값의 범위, 자릿수)를 써야 한다.

퀵 정렬은 최악이 O(n²)인데도 라이브러리의 기본이다. 상수가 작고 제자리에서 연속 구간을 순서대로 나누기 때문이다. 최악은 피벗 선택과 인트로소트로 막는다.

동작 원리

최악 보장 · 메모리 · 안정성 셋으로 견준다

표를 외우는 것보다 각 칸의 이유가 중요하다. 퀵의 최악은 피벗이 매번 최소·최대로 잡힐 때다. 이미 정렬된 배열에서 첫 원소를 피벗으로 쓰면 그렇게 된다. 병합이 O(n) 메모리를 쓰는 것은 합칠 때 임시 배열이 필요해서다. 선택·힙이 불안정한 것은 멀리 떨어진 원소끼리 교환하기 때문이다.

퀵 정렬은 나누면서 정렬하고, 병합 정렬은 합치면서 정렬한다

퀵이 기본인 이유설명
상수가 작다비교와 교환이 단순하다
캐시를 잘 쓴다연속된 구간을 앞뒤에서 순서대로 훑는다
추가 메모리가 적다제자리에서 나눈다. 병합처럼 임시 배열로 옮겼다 가져오지 않는다
최악이 잘 안 온다무작위 피벗이나 세 값의 중앙값을 쓰면 확률이 아주 낮다

인트로소트는 셋을 이어 붙여 최악을 막는다

인트로소트(introsort)는 퀵 정렬, 힙 정렬, 삽입 정렬을 상황에 따라 바꿔 쓰는 혼합 정렬이다. 이름은 "자기 상태를 들여다보는(introspective) 정렬"에서 왔다. 정렬하는 도중에 재귀가 얼마나 깊어졌는지 스스로 확인하고, 퀵 정렬이 최악으로 흘러가는 낌새가 보이면 그 구간만 다른 정렬로 넘긴다. 평균은 퀵 정렬만큼 빠르고 최악도 O(n log n)으로 묶인다.

조건무엇으로왜
시작퀵 정렬평균이 가장 빠르다
재귀 깊이가 한계(대략 2 × log n)를 넘는다힙 정렬최악을 O(n log n)으로 막는다
구간이 작아진다(원소 십여 개)삽입 정렬작은 n에서는 상수가 이긴다

C++의 std::sort와 .NET의 Array.Sort·List<T>.Sort가 이 구조이고, 둘 다 같은 값의 원래 순서를 지키지 않는다. 표준 라이브러리가 모두 인트로소트는 아니다. Java의 Arrays.sort는 기본형 배열에 이중 피벗 퀵 정렬을, 객체 배열에 안정 정렬인 TimSort를 쓴다.

비교로는 n log n 아래로 못 내려간다

n개를 늘어놓는 방법은 n! 가지다. 비교 한 번의 결과는 참·거짓 둘뿐이라 남은 경우의 수를 많아야 절반으로만 줄인다. 모든 순서를 구분하려면 최소 log₂(n!)번이 필요하고, 그 값이 n log n에 비례한다(결정 트리의 높이).

넘으려면 비교 대신 키 값을 위치로 바로 환산해야 한다.

알고리즘조건복잡도
계수 정렬값이 정수이고 범위 k가 좁다O(n + k)
기수 정렬자릿수 d가 고정된 정수나 문자열O(d × (n + k))
버킷 정렬값이 고르게 분포한다평균 O(n)

셋 다 값의 범위에 매인다. 0에서 100 사이면 계수 정렬이 압도적이지만, 범위가 넓으면 카운터 배열만으로 메모리가 터진다.

같은 키의 원래 순서에 뜻이 있을 때 안정성이 필요하다

같은 값끼리 원래 순서가 유지되는 것이 안정 정렬이다. 여러 기준으로 차례차례 정렬할 때 필요하다. 이름으로 정렬한 뒤 부서로 정렬하면, 같은 부서 안에 이름 순서가 남아야 한다. 다만 안정성에 기대기보다 비교자에 다음 기준을 넣는 편이 안전하다. 순서를 코드에 적어 두면 어느 정렬 함수를 부르든 결과가 같다.

선택 기준

상황C#에서 고를 것비고
대부분의 경우Array.Sort, List<T>.Sort인트로소트. 불안정. 제자리
같은 키의 순서를 지켜야 한다OrderBy·ThenBy(LINQ), 또는 비교자에 다음 기준 추가LINQ 정렬은 안정이지만 새 배열을 만든다(지연 실행)
배열 일부만 정렬Array.Sort(arr, index, length), Span<T>.Sort()복사 없이 구간만
n개 중 상위 k개만크기 k 힙(PriorityQueue)O(n log k). 전체 정렬 O(n log n)보다 싸다
작은 범위의 정수 키계수 정렬을 직접등급·레벨처럼 값이 수십 가지뿐일 때

게임 서버에서는

// 랭킹 정렬: 점수 내림차순, 동점이면 먼저 달성한 순, 그래도 같으면 ID 순
ranking.Sort((a, b) =>
{
    int c = b.Score.CompareTo(a.Score);
    if (c != 0) return c;
    c = a.AchievedAt.CompareTo(b.AchievedAt);
    return c != 0 ? c : a.PlayerId.CompareTo(b.PlayerId);
});
  • 랭킹은 비교자로 동점을 끝까지 가른다. List<T>.Sort는 불안정해서 점수만 비교하면 동점자의 순서가 정렬할 때마다 바뀔 수 있다. 클라이언트에 보이는 순위가 새로고침마다 뒤바뀌는 버그가 된다. 위처럼 마지막에 ID까지 비교해 순서를 하나로 고정한다.
  • 매 틱 전체를 다시 정렬하지 않는다. 순위가 조금씩만 바뀌는 데이터는 바뀐 원소만 옮기거나(삽입 정렬이 거의 정렬된 입력에서 빠르다), 정렬 구조(정렬 트리)에 넣어 둔다.
  • 비교자는 일관돼야 한다. a < b이고 b < c인데 c < a인 비교자는 정렬을 깨뜨린다. 흔한 예가 실수를 <·> 연산자로 직접 비교하는 비교자다. NaN은 어느 값과 비교해도 거짓이라 순서가 꼬인다(double.CompareTo는 NaN을 가장 작은 값으로 일관되게 다루므로 이것을 쓴다). 비교하는 도중에 값이 바뀌는 필드(실시간 점수 등)를 키로 쓰는 것도 같은 문제를 낸다. .NET은 비교자가 일관되지 않으면 예외를 던지거나 이상한 결과를 낸다.

주의 사항

  • 최악 O(n²) 하나로 병합 정렬이 낫다고 말할 수 없다. 상수와 메모리 접근을 함께 봐야 하고, 최악은 피벗 선택으로 거의 없앨 수 있다.
  • 선형 시간 정렬은 아무 데나 쓰지 못한다. 키를 위치로 바로 환산할 수 있어야 하고, 조건이 안 맞으면 비교 정렬로 돌아간다.
  • 셸 정렬은 복잡도를 한 값으로 외우지 않는다. 간격 수열에 따라 O(n²)부터 O(n log² n)까지 달라진다. 필기 시험에서 자주 틀리는 칸이다.
