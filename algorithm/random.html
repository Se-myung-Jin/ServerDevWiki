먼저 읽을 것: 탐색과 재귀 · 수의 표현

핵심 요약

컴퓨터의 난수는 대부분 의사 난수다. 내부 상태 몇 바이트에 정해진 계산을 반복해 무작위처럼 보이는 수열을 낸다. 같은 시드로 시작하면 언제나 같은 수열이 나온다. 이 성질은 리플레이와 절차적 생성에는 장점이고, 결과를 맞히려는 사람에게는 약점이다. 출력 몇 개만 보면 상태를 되살려 다음 수를 맞힐 수 있는 생성기도 많다.

그래서 쓰임에 따라 둘을 나눈다. 게임 판정과 시뮬레이션은 빠른 의사 난수로, 세션 토큰과 키처럼 맞히면 안 되는 값은 OS의 엔트로피에서 뽑는 암호학적 난수로 만든다(대칭 암호와 비대칭 암호, 해시와 비밀번호 저장). 그리고 좋은 생성기를 써도 쓰는 방법이 틀리면 확률이 틀어진다. 범위로 자르는 나머지 연산, 잘못된 셔플, 가중치 뽑기가 흔한 자리다.

주기는 수열이 처음으로 되풀이되기까지의 길이다. 주기가 길다고 예측하기 어려운 것은 아니다. 메르센 트위스터는 주기가 엄청나게 길지만 암호용이 아니다. 예측 불가능성은 CSPRNG만 보장한다.

.NET의 Random은 생성자에 따라 알고리즘이 다르다

일반 Random 인스턴스는 스레드 안전하지 않다. 여러 스레드가 한 인스턴스를 동시에 부르면 내부 상태가 깨지고, 그 뒤로 0만 계속 돌려주는 상태에 빠지기도 한다. 예외가 나지 않아 한참 뒤에야 "드롭이 안 나온다"로 발견된다.

범위로 자르는 순간 확률이 기운다

0~255를 고르게 내는 바이트 하나로 0~99를 만들려고 b % 100을 하면 고르지 않다. 0~55는 세 번(0, 100, 200), 56~99는 두 번씩만 나온다. 앞쪽 값이 1.5배 잘 나온다. 범위 크기가 원래 범위를 나누어떨어지지 않으면 언제나 생기는 나머지 편향이다. 원래 범위가 2³²처럼 커도 편향은 작아질 뿐 0이 아니다.

해결은 넘치는 구간을 버리고 다시 뽑는 것(거부 표본)이다. Random.Next(max)와 RandomNumberGenerator.GetInt32는 이것을 이미 해 주므로, 직접 %로 자르지 말고 범위를 받는 메서드를 쓴다.

셔플은 남은 것 중에서만 고른다

바른 방법은 피셔-예이츠 셔플이다. 뒤에서부터 i번 칸을 0~i 중 아무 칸과 바꾼다. 경우의 수가 n × (n−1) × … × 1 = n!로 순열 수와 정확히 같아서 모든 순열이 한 번씩 나온다. 그림의 잘못된 방식과 한 글자 차이(범위를 0~n−1로 두느냐 0~i로 두느냐)다. 

// 피셔-예이츠. .NET 8부터는 Random.Shuffle(span)이 같은 일을 한다
static void Shuffle<T>(Span<T> items, Random rng)
{
    for (int i = items.Length - 1; i > 0; i--)
    {
        int j = rng.Next(i + 1);           // 0..i, 이미 자리 잡은 뒤쪽은 고르지 않는다
        (items[i], items[j]) = (items[j], items[i]);
    }
}

비교 함수가 무작위로 답하는 정렬(Sort((a, b) => rng.Next(-1, 2)))도 흔한 실수다. 정렬 알고리즘은 비교가 일관된다고 가정하므로 결과가 고르지 않고, 구현에 따라 예외가 나기도 한다.

가중치 뽑기는 누적 표나 별칭 표로 한다

방법준비한 번 뽑기맞는 곳
누적 합 + 이분 탐색가중치를 차례로 더한 표 O(n)0~합계 사이 수를 뽑아 상한 탐색 O(log n)대부분의 보상표. 가중치를 바꾸면 표를 다시 만든다
별칭 방법(alias method)칸마다 "내 값 또는 별칭" 둘로 나눈 표 O(n)칸 하나와 동전 하나 O(1)같은 표에서 아주 많이 뽑을 때
앞에서부터 빼 나가기없다O(n)항목이 몇 개뿐일 때

누적 표의 상한 탐색은 탐색과 재귀에서 다룬 그대로다. 가중치는 정수로 두면 합계와 경계가 정확하다. 실수 가중치를 더해 가면 오차가 쌓여 마지막 항목이 표기보다 조금 덜 나오거나, 뽑은 값이 합계와 같아지는 경계에서 범위를 벗어난다(수의 표현).

같은 시드로 같은 결과를 내려면 순서까지 같아야 한다

시드를 기록하면 같은 전투, 같은 던전 생성을 다시 만들 수 있다. 버그 재현, 리플레이, 서버의 결과 검증이 이 성질에 기댄다. 조건은 셋이다.

  • 같은 알고리즘. 런타임 버전이나 플랫폼에 따라 바뀔 수 있는 표준 라이브러리 생성기 대신, 알고리즘이 고정된 생성기(xoshiro, PCG 등)를 코드에 직접 넣는다.
  • 같은 호출 순서. 생성기 하나를 여러 용도가 나눠 쓰면, 이펙트 하나가 난수를 한 번 더 뽑는 순간 뒤의 모든 결과가 달라진다. 드롭용, 전투용, 생성용처럼 용도마다 생성기를 따로 둔다.
  • 같은 계산. 정수 생성기는 어디서나 같은 수를 내지만, 그 값을 float로 바꿔 삼각 함수나 누적 계산을 하면 CPU, 컴파일러 최적화, 수학 라이브러리 구현에 따라 끝자리가 달라진다. 결정적이어야 하는 판정은 정수나 고정 소수점으로 한다.

게임 서버에서는

  • 결과를 정하는 난수는 서버가 뽑는다. 드롭, 치명타, 강화 성공을 클라이언트가 뽑아 알려 주면 조작된 클라이언트는 언제나 성공을 보낸다. 클라이언트는 연출만 한다.
  • 맞히면 안 되는 값은 CSPRNG로 만든다. 세션 토큰, 재접속 토큰, 비밀번호 재설정 코드, 암호화 키를 Random으로 만들면 출력 몇 개로 다음 값을 맞힐 수 있다. RandomNumberGenerator를 쓴다(해시와 솔트).
  • 공유 인스턴스를 여러 스레드에서 부르지 않는다. 로직 스레드가 하나면 그 스레드 전용 생성기를 두고, 여러 스레드에서 필요하면 Random.Shared를 쓴다.
  • 확률형 아이템은 표기 확률을 증명할 수 있게 만든다. 국내에서는 2024년 3월부터 확률 표시가 법적 의무다. 보상표를 기획 데이터에서 그대로 읽어 표기와 실제가 같은 원본을 쓰게 하고, 출시 전에 수백만 번 뽑는 시뮬레이션으로 결과 분포가 표기와 맞는지 검증한다. 뽑기 기록은 시드나 결과와 함께 남겨 문의에 답할 수 있게 한다.
  • 천장(보장)은 서버 상태다. "100번 안에 반드시"는 계정별 누적 횟수를 저장소에 두고 매 뽑기에서 갱신하는 규칙이다. 확률표만으로는 표현되지 않으므로 표기 확률에 천장의 효과를 어떻게 반영할지도 함께 정한다.

주의 사항

  • 시드에 시각을 쓰면 예측된다. 서버 시작 시각이나 접속 시각으로 시드를 잡으면 범위가 좁아 몇 초 안에 전부 시도해 볼 수 있다. 재현이 목적이면 시드를 무작위로 뽑아 기록한다.
  • "무작위로 보인다"는 검증이 아니다. 결과를 몇 번 눈으로 보는 것으로는 편향을 찾지 못한다. 앞의 셔플 편향도 수천 번 돌려 빈도를 세야 보인다.
  • 독립 시행은 기억이 없다. 1% 확률을 100번 뽑아도 한 번 이상 나올 확률은 약 63%다. "100번이면 한 번은 나온다"를 약속하고 싶다면 그것은 확률이 아니라 천장으로 설계한다.
