먼저 읽을 것: 정렬

핵심 요약

이분 탐색은 정렬된 데이터의 가운데를 보고 절반을 통째로 버린다. 100만 개에서 20번이면 끝난다. 원리는 단순한데 구현이 자주 틀린다. 중간값 계산 · 경계 · 종료 조건 셋만 제대로 잡으면 된다.

그리고 이분 탐색은 정렬된 배열 전용이 아니다. "이 값이면 되는가"라는 판정이 한 방향으로만 바뀌면(단조), 답 자체를 이분할 수 있다. 재귀는 탐색을 쓰는 자연스러운 방법이지만, 깊이가 입력을 따라 커지면 반복으로 바꾼다.

동작 원리

반열린 구간 하나로 경계를 통일한다

자리무엇이 틀리나어떻게 쓰나
중간값(lo + hi) / 2는 두 값을 더하다 정수가 넘칠 수 있다lo + (hi - lo) / 2
경계닫힌 구간과 반열린 구간을 섞으면 한 칸씩 어긋난다하나를 정해 끝까지. 반열린 구간이 실수가 적다
종료 조건구간이 줄지 않는 갱신(lo = mid)이 섞이면 무한 루프매 단계 구간이 반드시 줄어드는지 확인한다
 
// lower bound: target 이상인 첫 위치. 없으면 a.Length
static int LowerBound(int[] a, int target)
{
    int lo = 0, hi = a.Length;           // [lo, hi)
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] < target) lo = mid + 1;
        else hi = mid;
    }
    return lo;
}
// upper bound 는 조건만 a[mid] <= target 으로 바꾼다. 두 값의 차가 target 의 개수다.

찾는 값이 여럿이거나 없을 때 무엇을 돌려줄지를 정의로 고정한다. 하한(lower bound)은 그 값 이상인 첫 위치, 상한(upper bound)은 그 값보다 큰 첫 위치다. 둘의 차가 곧 그 값의 개수이고, 없으면 하한이 "넣어야 할 자리"가 된다. 범위 조회가 이 두 값으로 끝난다.

.NET의 Array.BinarySearch·List<T>.BinarySearch는 찾으면 그 인덱스를, 못 찾으면 넣어야 할 자리의 비트 보수(~index, 음수)를 돌려준다. 같은 값이 여럿이면 그중 어느 것을 돌려줄지는 정해져 있지 않다. 첫 위치가 필요하면 위처럼 하한을 직접 쓴다.

판정이 단조면 답을 이분한다

"최소 몇이면 되는가"를 바로 구하기 어려울 때, "x로 되는가"를 판정하는 함수가 x가 커질수록 "안 된다 → 된다"로 한 번만 바뀐다면 x를 이분 탐색한다. 최적화 문제를 판정 문제로 바꾸는 방법이고, 매개변수 탐색이라고 부른다.

예를 들어 "서버 N대로 모든 존을 감당하려면 서버당 최대 부하를 얼마로 잡아야 하나"는, 부하 한도 x를 정하면 "x로 N대 안에 나눠 담을 수 있는가"를 O(존 수)로 판정할 수 있다. x를 이분하면 O(존 수 × log 범위)에 최솟값이 나온다.

정렬돼 있어야 하고, 가운데로 바로 갈 수 있어야 한다

이분 탐색은 임의 접근이 되는 정렬된 배열에서만 성립한다. 연결 리스트는 가운데로 바로 못 가서 의미가 없다. 정렬이 안 돼 있으면 정렬부터 해야 하니, 한 번만 찾을 것이면 그냥 선형 탐색이 낫다. 여러 번 찾을 때 정렬 비용을 회수한다. 넣고 빼기가 섞이면서 찾아야 하면 배열 대신 균형 트리를 쓴다.

재귀는 깊이를 보고 쓴다

탐색은 재귀로 쓰면 읽기 쉽다. 문제는 깊이다. 깊이가 log n이면(이분 탐색, 균형 트리 순회) 재귀로 둬도 된다. 깊이가 입력 크기를 따라가면(긴 리스트, 편향 트리, 깊은 그래프) 호출 스택이 넘치고, .NET에서는 잡을 수도 없이 프로세스가 끝난다. 그때는 명시적 스택을 둔 반복문으로 바꾼다. 이유와 대응은 호출 스택에서, 그래프의 BFS·DFS는 그래프 표현과 탐색에서 다뤘다.

백트래킹은 안 될 가지를 일찍 자른다

가능한 선택을 하나씩 해 보고, 조건을 어기는 순간 그 가지 아래는 더 보지 않고 되돌아오는 탐색이 백트래킹이다. 순열·조합 만들기, 스도쿠 같은 제약 문제가 여기 해당한다. 전부 해 보면 지수 시간이지만, 일찍 자를수록(가지치기) 실제로 보는 경우가 크게 준다. 최악은 여전히 지수라, 입력 크기가 작다는 보장이 있을 때만 쓴다.

선택 기준

상황고를 것

게임 서버에서는

  • 구간 테이블은 이분 탐색으로 찾는다. 누적 경험치 → 레벨, 점수 → 등급, 누적 확률 → 보상(난수 생성) 같은 기획 테이블은 정렬된 경계값 배열이다. 매번 앞에서부터 훑지 말고 상한(upper bound)으로 구간을 찾는다. 확률 뽑기도 누적 확률 배열에 난수를 넣어 이분하면 O(log n)이다.
  • 시간순 로그에서 구간을 자른다. 시각으로 정렬된 이벤트 로그에서 "10:00~10:05 사이"는 시작 시각의 하한과 끝 시각의 하한 두 번으로 끝난다.
  • 외부 데이터를 재귀로 따라가지 않는다. 클라이언트가 보낸 중첩 구조, 유저가 만든 연결 데이터는 깊이를 공격자가 정할 수 있다. 반복문으로 바꾸거나 깊이 상한을 둔다.

주의 사항

  • 경계 관례를 정하지 않고 쓰면 틀린다. 반열린 구간 하나를 정해 하한·상한을 그것으로만 쓰는 편이 안전하다.
  • 이분 탐색의 조건은 단조여야 한다. 판정이 "된다 → 안 된다 → 된다"처럼 오가면 이분 탐색이 엉뚱한 답을 낸다.
  • 재귀가 항상 나쁜 것이 아니다. 깊이가 얕으면 읽기 쉬운 쪽이 낫다. 바꾸는 것은 넘칠 위험이 있을 때다.
