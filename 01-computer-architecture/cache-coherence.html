먼저 읽을 것: 메모리 계층과 캐시

핵심 요약

멀티코어에서는 코어마다 자기 캐시(L1, L2)를 가진다. 한 코어가 어떤 라인에 쓰면, 같은 라인을 보관하던 다른 코어의 사본은 무효가 된다. 이 규칙을 지키는 것이 캐시 일관성 프로토콜이고, 대표가 MESI다.

무효화의 단위는 변수가 아니라 라인이다. 그래서 논리적으로 아무 관계 없는 두 변수라도 한 라인에 있으면 서로의 사본을 계속 무효로 만든다. 각 코어는 접근할 때마다 라인을 다시 가져온다. 이것이 false sharing이다.

동작 원리

MESI: 라인마다 네 가지 상태를 둔다

각 코어의 캐시는 라인마다 아래 상태 중 하나를 기록한다. 코어끼리는 버스나 인터커넥트로 서로의 요청을 보고 상태를 바꾼다.

상태뜻이 코어가 쓸 수 있나
Modified이 코어만 가지고 있고, 고쳐서 메모리와 값이 다르다바로 쓴다
Exclusive이 코어만 가지고 있고, 메모리와 값이 같다바로 쓴다(M으로 바뀜)
Shared여러 코어가 같은 값을 가지고 있을 수 있다다른 사본을 무효화한 뒤에 쓴다
Invalid사본이 무효다라인을 다시 가져와야 한다

핵심은 쓰려면 그 라인을 독점(M 또는 E)해야 한다는 것이다. S나 I 상태에서 쓰려는 코어는 "가져오면서 소유권도 달라"는 요청(RFO, Read For Ownership)을 보내고, 다른 코어의 사본은 I가 된다. Intel은 MESIF, AMD는 MOESI처럼 상태를 하나 더 둔 변형을 쓰지만, 쓰기 전에 독점해야 한다는 원칙은 같다.

라인 소유권이 코어 사이를 오가며 매 접근이 미스가 된다

코어 A가 변수 x를, 코어 B가 변수 y를 각자 갱신한다고 하자. 둘이 같은 64바이트 라인에 있으면, A가 쓸 때마다 B의 사본이, B가 쓸 때마다 A의 사본이 무효가 된다.

순서일어나는 일A의 라인B의 라인
1A가 x를 쓴다MI
2B가 y를 쓰려고 RFO → A의 사본 무효화, 라인이 B로 넘어간다IM
3A가 다시 x를 쓰려고 RFO → B의 사본 무효화MI
…매 쓰기가 코어 간 라인 이동이 된다

락도 없고 경합도 없다. 코드만 보면 완벽히 병렬인데 느려진다. L1 히트였어야 할 쓰기가 매번 다른 코어의 캐시에서 라인을 끌어오는 작업이 되기 때문이다.

읽기만 하면 문제가 없다

여러 코어가 같은 라인을 읽기만 할 때는 저마다 S 상태 사본을 보관해도 무효화가 오가지 않는다. 한 코어가 쓰는 순간 나머지 사본이 무효가 된다. 그래서 쓰는 쪽이 하나만 있어도 false sharing이 생기고, 아무도 쓰지 않으면 여러 코어가 같은 라인을 읽어도 상관없다.

같은 변수를 여러 코어가 실제로 나눠 쓰는 것은 true sharing이다. 이쪽은 데이터를 떼어 놓아도 해결되지 않는다. 공유 자체를 줄이거나(스레드별로 모았다가 합치기) 설계를 바꿔야 한다.

선택 기준

떼어 놓으면 메모리를 더 쓴다

스레드별 카운터나 누적값처럼 코어마다 따로 쓰는 값은 캐시 라인 크기로 떼어 놓는다. 패딩을 넣거나, 배열 대신 스레드 로컬에 두고 마지막에 합친다.

대신 스레드 수만큼 라인을 차지한다. 경합이 실제로 관측된 자리에만 적용한다. 측정 없이 모든 필드에 패딩을 붙이면 캐시에 들어가는 유효 데이터가 줄어 오히려 효율이 떨어진다.

방법언제대가
스레드 로컬에 모았다가 마지막에 합치기중간 값을 다른 스레드가 볼 필요가 없을 때합치는 시점에만 동기화. 가장 먼저 고려한다
패딩으로 라인 떼어 놓기여러 스레드가 계속 읽어 가야 하는 값(큐의 head/tail, 통계 카운터)스레드 수 × 라인 크기만큼 메모리
쓰는 필드와 읽는 필드 분리자주 바뀌는 필드와 읽기 전용 필드가 한 객체에 섞여 있을 때객체 구조가 둘로 나뉜다

패딩 폭도 실측 대상이다

Intel 계열은 라인 하나를 가져올 때 128바이트로 짝이 되는 옆 라인까지 함께 가져오는 경우가 있다(인접 라인 프리페치). 그래서 64바이트로 떼어 놓아도 옆 라인이 함께 적재되면서 경합이 다시 생길 수 있다. 이 때문에 128바이트로 맞추는 라이브러리도 있다.

C++17의 std::hardware_destructive_interference_size가 이 폭을 나타내는 표준 상수다. 다만 컴파일 시점 상수라 실행할 머신에서 잰 값이 아니다. 참고 값으로 쓰고 실측을 대신하지 않는다.

게임 서버에서는

가장 흔한 형태는 스레드 번호로 인덱싱하는 통계 배열이다. IO 스레드마다 받은 패킷 수를 세려고 long[]을 만들면, long 8개가 한 라인에 들어가 IO 스레드끼리 서로를 무효화한다. 

// 문제: 스레드마다 자기 칸만 쓰지만 칸들이 한 캐시 라인에 붙어 있다
long[] recvCount = new long[ioThreadCount];
// IO 스레드 t 에서: recvCount[t]++;

// 해결 1: 구조체 크기를 라인보다 크게 잡아 칸 사이를 띄운다
[StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedCounter
{
    [FieldOffset(0)] public long Value;
}
PaddedCounter[] recvCount = new PaddedCounter[ioThreadCount];
// IO 스레드 t 에서: recvCount[t].Value++;

// 해결 2: 스레드 로컬에 모았다가 가끔 한 번만 합친다
[ThreadStatic] static long t_recvCount;
static long s_totalRecv;
// IO 스레드에서:       t_recvCount++;
// 같은 IO 스레드가 1초마다: Interlocked.Add(ref s_totalRecv, t_recvCount); t_recvCount = 0;
  • 작업 큐의 head와 tail: 생산자는 tail을, 소비자는 head를 쓴다. 둘이 한 라인에 있으면 생산자와 소비자가 서로를 무효화한다. .NET의 ConcurrentQueue도 내부에서 head와 tail 사이에 패딩을 둔다.
  • 세션 객체: 네트워크 스레드가 갱신하는 필드(마지막 수신 시각, 수신 바이트)와 로직 스레드가 갱신하는 필드(위치, 상태)가 한 객체에 붙어 있으면 같은 현상이 생긴다. 스레드별로 쓰는 필드를 나눠 둔다.
  • 락 객체 배열: 샤드별 락을 배열에 촘촘히 두면, 서로 다른 샤드의 락끼리 같은 라인을 쓰게 된다.

주의 사항

  • "공유 변수가 없으니 동시성 문제도 없다"고 보면 이 현상을 설명할 수 없다. false sharing은 정확성이 아니라 성능을 떨어뜨린다. 결과는 언제나 맞게 나오므로 테스트를 아무리 돌려도 드러나지 않는다.
  • 전용 도구로 찾는다. Linux의 perf c2c는 어느 캐시 라인에서 경합이 일어났는지, 그 라인의 어느 위치를 어느 스레드가 읽고 썼는지까지 짚어 준다. 같은 변수를 실제로 나눠 쓰는 true sharing과도 구분해 준다. "프로파일러에 안 보인다"고만 알고 있으면 찾을 수 있는 문제를 찾지 않고 넘긴다.
  • 코어를 늘렸는데 처리량이 안 늘면 의심한다. 스레드 수를 늘릴수록 오히려 느려지거나 제자리라면, 락 경합과 함께 false sharing을 후보에 넣는다.
  • 라인 크기를 상수로 박지 않는다. 64는 x86-64의 값이다. 메모리 계층과 캐시의 주의 사항에 실행 중 확인 방법이 있다.
