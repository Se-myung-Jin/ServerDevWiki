먼저 읽을 것: 수의 표현

핵심 요약

엔디안은 여러 바이트로 된 값을 메모리에 담을 때 어느 바이트를 먼저 놓는가를 정하는 규칙이다. 낮은 주소에 최하위 바이트를 두면 리틀 엔디안, 최상위 바이트를 두면 빅 엔디안이다.

1바이트씩 읽는 값에는 정할 순서가 없으므로 문제가 되지 않는다. int·short·float처럼 여러 바이트를 묶어 하나로 읽는 값만 영향을 받는다.

동작 원리

같은 값, 같은 4바이트, 순서만 다르다

호스트 바이트 오더는 CPU가 정한다. x86·x64는 리틀 엔디안이다. ARM은 양쪽을 다 지원하지만 Android·iOS·ARM 서버 모두 리틀 엔디안으로 동작한다. 반면 네트워크 바이트 오더는 빅 엔디안으로 정해져 있어서, IP·TCP 헤더 같은 표준 프로토콜 필드는 빅 엔디안으로 쓴다. C에서는 htons·htonl·ntohs·ntohl로 바꾼다(h = host, n = network, s = short, l = long).

바이트 배열의 경계를 넘을 때만 드러난다

같은 머신 안에서는 읽는 쪽과 쓰는 쪽이 같은 규칙을 쓰므로 순서를 의식할 일이 없다. 값이 바이트 배열로 바뀌는 경계를 넘을 때 비로소 양쪽 규칙이 달라질 수 있고, 달라지면 같은 바이트를 다른 값으로 읽는다.

  • 네트워크로 보낼 때
  • 파일에 저장할 때
  • 같은 메모리를 다른 타입으로 다시 읽을 때 (byte[]를 int로, 또는 그 반대로)

마지막은 한 머신 안에서도 생긴다. 네트워크로 보내지 않아도 바이트 배열을 거치면 순서를 정해야 한다.

선택 기준

이진 포맷을 정할 때는 바이트 오더를 명시한다. 프로토콜 문서에 "모든 정수는 리틀 엔디안" 같은 한 줄을 반드시 둔다. 코드에서는 순서가 이름에 드러난 API를 쓴다. 그러면 호스트 순서를 확인할 필요가 없다.

C# API순서쓸 곳
BinaryPrimitives.ReadInt32LittleEndian / WriteInt32BigEndian 등이름에 적힌 대로패킷·파일 포맷. 가장 권장
BitConverter.GetBytes / ToInt32호스트 순서같은 머신 안에서만. 프로토콜에는 쓰지 않는다
MemoryMarshal.Read<T> · 구조체 캐스팅호스트 순서성능이 꼭 필요하고 양쪽 순서가 같다고 문서로 못 박은 경우
IPAddress.HostToNetworkOrder네트워크(빅 엔디안)표준 프로토콜 필드를 직접 다룰 때

직렬화 라이브러리를 쓰면 포맷이 순서를 정한다. 예를 들어 MessagePack은 명세상 빅 엔디안이고, Protocol Buffers의 고정 길이 필드와 FlatBuffers는 리틀 엔디안이다. 라이브러리끼리 맞추면 신경 쓸 일이 없고, 직접 파싱할 때만 명세를 확인한다.

텍스트 포맷(JSON 등)은 이 문제가 없다. UTF-8 텍스트는 바이트 단위로 읽기 때문이다. 상호운용성이 중요하면 텍스트를 고를 수 있지만, 크기가 커지고 파싱 비용이 든다.

구조체를 그대로 보내면 엔디안만 위험한 것이 아니다. 패딩도 언어와 플랫폼이 정한다. 둘이 겹치므로 수신 쪽 레이아웃과 일치한다는 보장이 없다.

게임 서버에서는

  • 패킷 길이 필드가 뒤집히면 연결이 터진다. 길이 10을 리틀 엔디안 0A 00 00 00으로 보냈는데 받는 쪽이 빅 엔디안으로 읽으면 0x0A000000(167,772,160, 약 1.7억)이 된다. 수신 버퍼를 그 크기로 잡으려다 메모리가 터지거나, 데이터가 다 올 때까지 영원히 기다린다. 길이 필드에는 반드시 상한 검사를 둔다.
  • 다른 언어로 만든 쪽과 붙을 때 사고가 난다. Java의 DataOutputStream과 ByteBuffer, Netty의 ByteBuf는 기본이 빅 엔디안이다. C# 서버가 BitConverter(리틀 엔디안)로 읽으면 값이 뒤집힌다. 운영 툴, 결제·인증 같은 외부 서버, 다른 팀의 C++ 서버(htonl을 쓰는 레거시)와 붙는 지점을 먼저 확인한다.
  • C# 서버와 Unity 클라이언트끼리는 우연히 맞는다. 둘 다 리틀 엔디안 머신에서 돌기 때문에 BitConverter로 짜도 동작한다. 동작한다는 것이 맞게 짰다는 뜻은 아니다. 나중에 다른 언어의 클라이언트나 툴이 붙을 때를 위해 BinaryPrimitives로 순서를 코드에 드러낸다.

주의 사항

  • 같은 순서끼리 통신하면 버그가 드러나지 않는다. 지금의 PC(x86-64), 콘솔(PS5·Xbox는 x86-64, Switch는 ARM), 모바일(ARM)은 모두 리틀 엔디안이라 변환을 빼먹어도 대개 잘 돈다. 깨지는 것은 상대가 빅 엔디안 포맷을 쓸 때다. 표준 네트워크 프로토콜, 빅 엔디안이 기본인 언어·라이브러리, 일부 파일 포맷이 그렇다. 하드웨어가 같아도 포맷이 다르면 깨진다.
  • 문자열이 안전한 것은 인코딩이 바이트 단위일 때뿐이다. UTF-8과 ASCII는 바이트 하나씩 해석하므로 순서를 정할 것이 없다. UTF-16과 UTF-32는 2·4바이트를 묶어 읽으므로 엔디안이 있고, 그래서 UTF-16LE와 UTF-16BE가 따로 있으며 파일 앞머리의 BOM이 어느 쪽인지 알려 준다. C#의 string은 메모리에서 UTF-16이지만, Encoding.UTF8로 바꿔 보내면 이 문제가 없다. Encoding.Unicode(UTF-16LE)나 BigEndianUnicode로 직렬화할 때만 순서를 맞춰야 한다.
  • float·double도 엔디안을 따른다. 정수만 뒤집고 실수를 빼먹는 실수가 흔하다. BinaryPrimitives.WriteSingleLittleEndian처럼 실수용 API도 있다.
