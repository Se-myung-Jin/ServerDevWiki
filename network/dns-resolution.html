먼저 읽을 것: TCP 연결 관리

핵심 요약

주소창에 입력한 뒤 화면이 표시되기까지는 이름 해석 → 연결 맺기 → 암호화 → 요청과 응답 → 그리기 순서로 단계가 여럿이다. 면접에서 단골로 나오는 질문이고, 실무에서는 장애를 단계로 좁히는 지도가 된다.

첫 단계인 DNS는 이름을 IP 주소로 바꾼다. 한곳에 모아 둔 표가 아니라 이름을 마디로 나눠 아래로 맡겨 둔 분산 구조라, 처음 묻는 이름은 여러 번 되물어야 답이 나온다. 대신 단계마다 답을 TTL 동안 담아 두므로, 레코드를 고쳐도 바로 반영되지 않는다.

동작 원리

가까운 캐시부터 묻고, 없으면 위임을 따라 내려간다

프로그램과 OS는 리졸버에게 "답을 구해서 달라"고 한 번 묻는다. 이것이 재귀 질의다. 리졸버는 그 답을 구하려고 루트, TLD, 권한 서버에 차례로 묻는데, 각 서버는 아는 데까지만 알려 주고 다음 서버를 가리킨다. 이것이 반복 질의다. 루트 서버는 개별 도메인의 주소를 갖고 있지 않다. 가진 것은 .com을 맡은 서버 목록이고, 그 위임을 따라 내려가야 답이 나온다.

DNS 질의는 대개 UDP 53번 포트로 한 번 주고받고 끝난다. 응답이 크거나 잘리면 TCP로 다시 묻는다. 최근에는 질의를 암호화하는 DNS over HTTPS·TLS도 쓴다.

TTL은 답을 주는 쪽이 정하고, 받은 쪽은 그동안 다시 묻지 않는다

답에는 TTL(초 단위)이 붙어 오고, 리졸버와 OS는 그 시간 동안 같은 이름을 다시 묻지 않는다. 그래서 TTL은 바꾼 주소가 퍼지는 데 걸리는 최대 시간이기도 하다. 서버를 옮길 계획이면 며칠 전에 TTL을 짧게(예: 60초) 줄여 두고, 옮긴 뒤 안정되면 다시 늘린다. 이미 긴 TTL로 퍼진 값은 고쳐도 만료될 때까지 남는다.

이름을 알아낸 뒤에도 왕복이 여러 번 남는다

  1. 이름 해석. 캐시에 없으면 리졸버까지, 더 나아가 권한 서버까지 다녀온다.
  2. 다음 홉 찾기. 같은 망의 게이트웨이 MAC 주소를 모르면 ARP로 묻는다(주소와 전달).
  3. TCP 연결. 3-way 핸드셰이크로 한 번 왕복한다(TCP 연결 관리).
  4. TLS 핸드셰이크. TLS 1.3이면 한 번, 1.2면 두 번 왕복한다(서명과 TLS).
  5. 요청과 응답. 서버 처리 시간이 여기 더해진다.
  6. 그리기. 받은 문서를 해석하며 딸린 자원(스크립트, 이미지)을 다시 요청한다. 이미 연결이 있으면 1~4를 건너뛴다.

1~4는 거의 전부 왕복 횟수 × 거리로 정해진다. 그래서 연결을 재사용하고(keep-alive, 커넥션 풀), 사용자 가까이 서버를 두는 것(CDN, 지역 서버)이 효과가 크다.

curl -w로 단계별 시간(time_namelookup, time_connect, time_appconnect, time_starttransfer)을 한 번에 찍으면 어느 칸이 길어졌는지 바로 보인다. 이름 대신 IP를 직접 넣어 보는 것도 빠른 확인이다. 다만 가상 호스트나 TLS 인증서 이름 때문에 이름이 멀쩡해도 IP로는 실패할 수 있으니, 그 결과만으로 단정하지 않는다.

게임 서버에서는

  • .NET은 DNS 결과를 스스로 캐시하지 않는다. Dns.GetHostAddressesAsync는 OS 리졸버에 그대로 묻는다. Windows는 DNS 클라이언트 서비스가 캐시해 주지만, Linux 컨테이너는 대개 OS 캐시가 없어 호출마다 리졸버까지 간다. 외부 API를 자주 부르는 서버라면 연결을 재사용해 이름 해석 자체를 줄인다.
  • HttpClient를 오래 쓰면 DNS 변경을 못 본다. HttpClient를 하나 공유하는 것은 맞지만(커널 오브젝트와 핸들), 풀에 있는 연결은 기본적으로 계속 재사용되어 대상 서버가 IP를 바꿔도 옛 IP로 간다. SocketsHttpHandler.PooledConnectionLifetime을 몇 분으로 잡아 연결이 주기적으로 새로 맺히게 하거나, IHttpClientFactory를 쓴다.
  • 로그인 서버 주소를 DNS로 옮긴다. 클라이언트는 고정 IP 대신 도메인으로 로그인 서버에 붙게 하고, 서버 이전이나 장애 전환 때 레코드를 바꾼다. 이때 TTL이 곧 전환 시간이라, 전환이 잦은 레코드는 TTL을 짧게 유지한다. 대신 리졸버 부하와 해석 횟수가 는다.
  • DNS 장애가 접속 장애로 보인다. 서버는 멀쩡한데 "접속이 안 된다"는 문의가 몰리면, 특정 통신사·지역 리졸버 문제일 수 있다. 클라이언트에 마지막으로 성공한 IP를 기억해 두는 대체 경로를 두기도 한다.

주의 사항

  • 레코드를 고쳐도 바로 바뀌지 않는다. 리졸버, OS, 프로그램, 커넥션 풀이 각자 담아 둔 값을 만료될 때까지 쓴다. 장애 대응 중 "고쳤는데 안 바뀐다"는 대개 이것이다.
  • 루트 서버가 모든 답을 갖고 있는 것이 아니다. 루트는 TLD 서버의 위치만 안다. 답은 위임을 따라 내려간 권한 서버에 있다.
  • IP로 붙는 것은 DNS 문제만 거른다. 인증서 이름, 가상 호스트, 로드 밸런서 규칙은 이름을 기준으로 동작하므로, IP로 실패했다고 서버 문제라고 단정하지 않는다.
