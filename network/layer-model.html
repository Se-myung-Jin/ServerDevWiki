핵심 요약

네트워크를 층으로 나누면 아래 층을 몰라도 위 층을 쓸 수 있다. HTTP를 쓰는 코드는 그 아래가 와이파이인지 광케이블인지 알 필요가 없다. 각 층은 바로 아래 층이 주는 기능만 믿고 자기 일을 한다.

나눠 두면 진단도 쉬워진다. 문제가 어느 층의 것인지 좁힐 수 있다. 이름이 안 풀리면 응용 층, 포트에 연결이 안 되면 전송 층, 아예 닿지 않으면 그 아래다. 이야기할 때는 OSI 7계층의 번호로 층을 가리키고, 실제로 도는 것은 TCP/IP 4계층 구조다.

OSI는 개념을 구분하려고 설계한 참조 모델이고, TCP/IP는 동작하는 구현에서 나온 실제 구조다. 순서도 TCP/IP가 앞선다. TCP/IP는 1970년대부터 쓰였고, OSI는 1980년대에 표준이 됐다. 구현으로 자리 잡은 것은 TCP/IP지만, "L4 로드밸런서", "L7 방화벽"처럼 층을 가리킬 때는 지금도 OSI 번호를 쓴다. 층을 부르는 공통 언어로 남은 것이다.

내려가면서 붙이고 올라가면서 뗀다

각 층은 자기 헤더만 본다. 라우터는 3계층 헤더만 보고 다음 홉을 정하고, 그 안에 든 것이 TCP인지 UDP인지 알 필요가 없다. 스위치는 2계층 프레임만 보고 포트를 고른다. 그래서 장비를 "몇 계층 장비"라고 부른다. 그 장비가 어디까지 열어 보는지를 가리키는 말이다.

장비·기능보는 층무엇으로 판단하나
스위치L2목적지 MAC 주소
라우터L3목적지 IP 주소
L4 로드밸런서L4IP와 포트. 연결 단위로 서버를 고른다. 내용은 보지 않는다

단, ping(ICMP)을 막아 둔 서버가 많다. ping이 안 된다고 경로가 끊겼다고 단정하지 말고, 실제 포트로 연결을 시도해 본다(nc -vz host port, PowerShell Test-NetConnection host -Port port).

게임 서버에서는

  • 게임 프로토콜은 응용 층에 있다. 서버와 클라이언트가 정한 패킷 형식(헤더, opcode, 본문)은 TCP나 UDP 위에 얹는 응용 층 규칙이다. TCP가 바이트를 순서대로 날라 줄 뿐 메시지 경계는 모르므로, 메시지를 나누는 일은 응용이 한다(메시지 경계와 프레이밍).
  • 로드밸런서의 층이 세션 유지 방식을 정한다. 게임 서버처럼 오래 붙어 있는 TCP 연결은 L4 로드밸런서가 연결 단위로 서버에 붙여 주면 끝난다. 웹 API 서버는 L7에서 경로별로 나눌 수 있다. 실시간 UDP는 연결이라는 개념이 없어서, 로드밸런서가 출발 주소·포트 쌍을 기억해 같은 서버로 보내야 한다.
  • .NET의 Socket은 전송 층 입구다. SocketType.Stream + ProtocolType.Tcp, SocketType.Dgram + ProtocolType.Udp로 층을 고르고, 그 아래(IP, 이더넷)는 OS 커널이 맡는다. 소켓도 커널 오브젝트라 디스크립터 한도를 따른다(커널 오브젝트와 핸들).

주의 사항

  • 계층 이름을 순서대로 외우는 것만으로는 설명이 아니다. 왜 나눴는지(아래를 몰라도 위를 쓰게), 무엇이 실제로 도는지(TCP/IP)가 함께 있어야 뜻이 통한다.
  • TCP/IP에 세션·표현 층이 없다고 그 일이 사라진 것은 아니다. 압축·암호화·연결 상태 관리는 응용 프로토콜이나 라이브러리가 한다.
  • 모든 프로토콜이 한 층에 딱 들어가지는 않는다. TLS는 TCP 위, 응용 아래에 끼어 있고(TLS), ARP는 IP 주소를 다루면서 프레임에 바로 실린다. 층 구분은 설명을 위한 단순화다.
