핵심 요약

HTTP는 요청과 응답을 주고받는 응용 계층 규칙이고, 상태를 기억하지 않는다(무상태). 서버는 앞 요청과 뒤 요청을 서로 모르므로, 로그인 같은 상태는 쿠키나 토큰에 실어 매 요청마다 다시 보낸다.

버전의 변천은 한 축으로 요약된다. 한 번에 여러 요청을 어떻게 보낼 것인가, 다시 말해 앞의 하나가 늦어 뒤가 전부 기다리는 head-of-line(HOL) 블로킹을 어느 계층에서 없앴느냐의 역사다.

동작 원리

버전마다 같은 문제를 한 계층씩 아래에서 풀었다

버전여러 요청을 어떻게바뀐 것남은 문제

HTTP/2가 응용 계층의 줄 세우기를 없앴지만, 그 아래 TCP는 무엇을 나르는지 모르고 바이트를 순서대로만 올려 준다. 그래서 스트림을 나눠 놓아도 TCP 한 줄에서 막힌다. HTTP/3은 전송 계층 자체를 QUIC으로 바꿔 이 마지막 줄을 끊었다. 왜 TCP가 잃은 것을 기다리는지는 TCP와 UDP에서 다룬다.

1.1 시절의 우회법은 2에서 손해가 된다

한 연결에 한 줄이니 브라우저는 도메인당 연결을 여섯 개쯤 열었다. 그래서 자원을 여러 도메인에 흩어 두고(도메인 샤딩), 작은 파일을 하나로 합치고, 이미지를 한 장에 몰아 담았다. HTTP/2에서는 요청이 싸져서 이 기법이 거꾸로 손해다. 연결을 여럿 열면 혼잡 제어가 각자 따로 돌아 효율이 떨어지고, 합친 파일은 일부만 바뀌어도 통째로 다시 받아야 한다.

게임 서버에서는

  • API 서버도 연결 재사용이 성능의 절반이다. 클라이언트·서버 양쪽에서 HttpClient를 공유해 연결을 재사용하지 않으면, 요청마다 TCP·TLS 핸드셰이크 왕복을 다시 낸다(이름 해석과 연결까지).
  • 상태를 서버 메모리에 두지 않는다. 로그인 상태를 API 서버 한 대의 메모리에 두면 그 서버로만 요청이 가야 해서 늘리기 어렵다. 세션은 Redis 같은 공유 저장소에 두거나 토큰으로 들고 다니게 해, 어느 서버가 받아도 처리되게 한다.
  • 재시도는 멱등한 요청만. 모바일 망에서 응답을 못 받았다고 상점 구매 요청을 그대로 다시 보내면 두 번 결제될 수 있다. GET은 다시 보내도 되지만, 결제처럼 상태를 바꾸는 요청은 요청 ID를 붙여 서버가 중복을 걸러야 한다.
  • .NET은 HTTP/2·3을 지원한다. Kestrel과 HttpClient는 HTTP/2를 지원하고, HTTP/3은 OS가 QUIC(msquic)을 지원하는 환경에서 켤 수 있다. gRPC는 HTTP/2가 필요하므로, 앞단 로드 밸런서가 HTTP/2를 끝까지 넘겨주는지 확인한다.

주의 사항

  • 무상태는 응답 뒤에 연결을 끊는다는 뜻이 아니다. 서버가 요청 사이의 문맥을 기억하지 않는다는 뜻이고, 연결 유지는 다른 축이다. 1.1부터는 연결을 재사용하는 쪽이 기본이다.
  • 로그인 상태는 서버가 기억하는 것이 아니다. 매 요청에 실려 오는 쿠키·토큰이 상태를 나른다. 그래서 서버를 늘릴 때 그 정보를 어디서 확인할지가 문제가 된다.
  • HTTPS의 보안은 TLS가 한다. HTTP 자체에는 암호화가 없다. 인증서와 핸드셰이크는 서명과 TLS에서 다룬다.
