먼저 읽을 것: 컴파일과 링킹 · 가상 메모리

핵심 요약

프로그램을 실행하면 커널이 새 주소 공간을 만들고, 실행 파일의 각 부분을 그 공간에 매핑만 걸어 둔 뒤 시작 지점으로 제어를 넘긴다. 내용을 통째로 읽어 올리지 않는다. 실제로 읽는 것은 그 페이지에 처음 접근할 때다. 그래서 큰 프로그램도 시작이 빠르다.

공유 라이브러리를 쓰는 프로그램은 그 사이에 동적 링커가 한 번 더 일한다. 필요한 라이브러리를 찾아 매핑하고, 프로그램이 부를 함수의 실제 주소를 표에 채운다.

동작 원리

매핑을 먼저 걸고 내용은 나중에 읽는다

  1. 커널이 실행 파일 헤더를 읽어 형식(Linux는 ELF, Windows는 PE)과 시작 주소를 확인한다.
  2. 새 주소 공간과 페이지 테이블을 만든다.
  3. 텍스트·데이터 부분을 주소 공간에 매핑한다. 아직 읽지 않는다.
  4. 초기값 없는 전역(BSS)은 파일에 내용이 없으므로 0으로 채울 페이지로 잡는다.
  5. 스택을 잡고 인자와 환경 변수를 올린다.
  6. 동적 링커가 필요하면 링커부터 실행한다. 링커가 공유 라이브러리를 찾아 매핑하고 주소를 맞춘 뒤에 프로그램의 시작 지점으로 넘긴다.
  7. 실행하면서 처음 접근하는 페이지마다 폴트가 나고, 그때 디스크(대개는 이미 페이지 캐시)에서 읽어 온다.

Linux에서는 실행 파일에 적힌 동적 링커(ld-linux-x86-64.so.2)를 커널이 함께 매핑해 먼저 실행한다. Windows는 새 프로세스 안에서 ntdll.dll의 로더가 같은 일을 한다. 주소 공간 각 영역의 성질은 프로세스 메모리 구성에서 다룬다.

동적 링커는 정해진 순서로 라이브러리를 찾는다

순서Linux (ld.so)Windows (기본 안전 검색)
1실행 파일에 박힌 RPATH (RUNPATH가 없을 때만)실행 파일이 있는 폴더
2LD_LIBRARY_PATH 환경 변수시스템 폴더(System32)
3실행 파일에 박힌 RUNPATHWindows 폴더
4/etc/ld.so.cache에 등록된 경로현재 작업 폴더
5기본 경로(/lib, /usr/lib)PATH 환경 변수

RPATH와 RUNPATH는 둘 다 실행 파일에 넣는 검색 경로지만 자리가 다르다. RPATH는 LD_LIBRARY_PATH보다 먼저, RUNPATH는 그 뒤에 본다. 요즘 링커는 기본으로 RUNPATH를 넣으므로, 환경 변수로 다른 라이브러리를 지정하면 그쪽이 이긴다. 순서가 중요한 이유는 같은 이름의 라이브러리가 여러 곳에 있을 수 있어서다. 개발 머신에서는 다른 경로의 라이브러리를 우연히 찾아 동작하다가, 운영 서버에서는 찾지 못하거나 다른 버전을 찾는다. Windows에서 실행 폴더가 먼저인 것은 편리하지만, 그 폴더에 같은 이름의 악성 DLL을 넣어 두는 공격(DLL hijacking)의 통로이기도 하다.

함수 주소는 첫 호출 때 채우기도 한다

이렇게 미뤄 두는 방식을 지연 바인딩이라고 한다. 쓰지 않는 함수는 찾지 않으니 시작이 빠르다. 반대로 시작할 때 전부 채우는 즉시 바인딩도 있다(Linux의 -z now, LD_BIND_NOW). Windows는 기본으로 적재할 때 가져올 함수 표(IAT)를 모두 채우고, 따로 지정한 DLL만 첫 호출 때 불러온다(delay-load).

두 번 실행해도 코드는 하나만 올라간다

영역두 인스턴스 사이왜
텍스트 · 읽기 전용 데이터물리 메모리에 하나만 두고 공유한다읽기 전용이라 나눠 써도 안전하다
공유 라이브러리 코드프로그램이 달라도 같은 파일이면 공유한다같은 이유
쓰기 가능한 데이터 · GOT처음에는 공유하고, 쓰면 나뉜다쓰는 순간 그 페이지만 복사한다(copy-on-write)
힙 · 스택처음부터 따로실행 중에 만들어진다

오래 켜 두는 서버는 시작 시간보다 실행 중의 예측 가능성과 보안이 중요해서 즉시 바인딩이 잘 맞는다. 보안을 강화한 빌드 설정에서는 이미 기본값인 경우가 많다.

게임 서버에서는

  • .NET 서버는 한 단계가 더 있다. 실행 파일(apphost)이 hostfxr → hostpolicy → coreclr 순서로 런타임을 올리고, 그다음에 내 어셈블리를 읽는다. 어셈블리와 메서드는 처음 쓸 때 읽히고 JIT 컴파일된다. 그래서 오픈 직후 첫 요청들이 느리다. ReadyToRun으로 미리 컴파일해 두거나, 오픈 전에 주요 경로를 한 번씩 실행하는 warm-up을 둔다.
  • 네이티브 라이브러리는 첫 호출 때 찾는다. P/Invoke로 부르는 네이티브 라이브러리가 없으면 시작이 아니라 그 함수를 처음 부르는 순간 DllNotFoundException이 난다. 서버 시작 단계에서 필요한 네이티브 함수를 한 번씩 불러 확인하면 배포 사고를 일찍 잡는다.
  • 배포 전에 의존을 확인한다. Linux에서는 ldd ./server로 어떤 라이브러리를 어디서 찾는지, 못 찾는 것이 있는지(not found) 바로 보인다. 컨테이너 베이스 이미지를 바꿀 때 특히 본다.

주의 사항

  • "실행 파일을 메모리에 올린다"는 말은 매핑을 가리킨다. 내용은 접근할 때 읽어 온다. 그래서 프로세스가 차지한 메모리는 실행 파일 크기와 맞지 않는다.
  • 공유는 물리 메모리에서 일어난다. 두 인스턴스의 가상 주소가 같든 다르든 공유는 그대로다. 페이지 테이블이 같은 물리 페이지를 가리킬 뿐이고, 두 프로세스는 서로의 존재를 모른다.
  • LD_LIBRARY_PATH로 운영 문제를 덮지 않는다. 당장은 라이브러리를 찾게 해 주지만, 그 환경 변수가 빠진 실행 경로(서비스 관리자, 크론)에서는 다시 깨진다. 실행 파일에 검색 경로를 넣거나 표준 경로에 설치한다.
