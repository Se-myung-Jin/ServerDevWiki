먼저 읽을 것: 프로세스 메모리 구성

핵심 요약

C·C++ 소스는 전처리 · 컴파일 · 어셈블 · 링킹 네 단계를 거쳐 실행 파일이 된다. 앞의 셋은 소스 파일 하나씩 따로 처리하고, 링킹에서 처음 하나로 합친다.

단계를 아는 것이 실용적인 이유는 오류 때문이다. 어느 단계에서 났는지 알면 고칠 곳이 정해진다. 타입 오류는 컴파일, 정의를 못 찾는 오류는 링킹, 실행할 때 라이브러리를 못 찾는 오류는 적재 단계다.

동작 원리

파일마다 따로 만들고 마지막에 합친다

단계하는 일여기서 나는 오류
전처리#include를 펼치고 매크로를 치환한다헤더를 찾을 수 없다
컴파일문법과 타입을 확인하고 어셈블리를 만든다문법 오류, 타입 불일치, 선언되지 않은 이름
어셈블어셈블리를 기계어 목적 파일로 바꾸고, 아직 모르는 주소는 재배치 항목으로 남긴다드물다
링킹목적 파일과 라이브러리를 모아 심볼(함수·전역 변수 이름)을 해석하고 주소를 확정한다정의를 찾을 수 없다(undefined reference, LNK2019), 중복 정의(LNK2005)

컴파일 단계는 파일 하나만 보기 때문에 선언과 정의를 나눠 쓴다. 다른 파일의 함수가 어떻게 생겼는지(선언)만 알면 목적 파일을 만들 수 있고, 실제 위치는 링커가 채운다.

반대로 헤더에 함수 본문을 넣고 여러 소스에서 포함하면, 목적 파일마다 같은 심볼이 생겨 링킹에서 중복 정의가 된다. 정의를 소스로 옮기거나 inline을 붙여 "여러 개 있어도 하나로 친다"고 알려 준다.

링킹 시점을 언제로 잡느냐

구분정적 링킹동적 링킹
언제 합치나빌드할 때 실행 파일 안으로실행할 때(적재 시점이나 첫 호출 때) 메모리에서
함수 호출직접 호출주소 표를 거치는 간접 호출(Linux는 PLT·GOT, Windows는 IAT)
실행 파일 크기커진다작다
라이브러리 수정다시 빌드해야 한다파일만 바꾸면 된다
여러 프로그램이 쓸 때각자 사본을 갖는다물리 메모리에 하나만 두고 나눠 쓴다
배포파일 하나면 끝난다의존 라이브러리가 대상 환경에 함께 있어야 한다

동적 라이브러리는 실행할 때마다 다른 주소에 올라갈 수 있어서, 호출하는 쪽 코드에 주소를 미리 적어 둘 수 없다. 그래서 주소를 별도의 표에 두고 코드는 그 표를 거쳐 간접 호출한다. 코드를 고치지 않고 표만 고치기 때문에 코드 페이지를 여러 프로세스가 그대로 나눠 쓸 수 있다. 실제로 표를 채우는 과정은 프로그램이 올라가는 과정에서 다룬다.

C#에는 링킹 단계가 따로 없다

C# 컴파일러는 소스를 기계어가 아니라 IL로 바꿔 어셈블리(.dll)에 담는다. 다른 어셈블리의 타입은 이름과 시그니처로만 기록해 두고, 실제로 찾아 연결하는 일은 실행 중에 런타임이 한다. 그래서 C#의 "링크 오류"는 실행 중에 난다. 참조한 어셈블리가 없으면 FileNotFoundException, 버전이 달라 메서드가 없으면 MissingMethodException·TypeLoadException이 처음 그 코드를 실행하는 순간 터진다. 동적 링킹의 버전 불일치와 같은 성질의 문제다.

반대로 .NET의 Native AOT 배포는 정적 링킹에 가깝다. 쓰는 코드만 남기고(trimming) 런타임까지 실행 파일 하나에 넣는다.

선택 기준

우선하는 것고를 것대가
배포 단순함, 대상 환경 무관정적 링킹파일이 커지고, 라이브러리 보안 패치마다 다시 빌드해 배포해야 한다
라이브러리만 교체, 메모리 공유동적 링킹대상 환경에 맞는 버전이 없으면 시작조차 못 한다

컨테이너로 배포하면 환경을 통째로 싣고 가므로 동적 링킹의 약점이 줄어든다. 반대로 실행 파일 하나로 묶어 배포하는 흐름(Go, Rust, .NET Native AOT)도 있다. 어느 쪽이 기본인지는 언어와 배포 방식에 달렸다.

게임 서버에서는

  • Linux C++ 서버의 단골 배포 사고는 glibc 버전이다. 최신 배포판에서 빌드한 실행 파일을 오래된 서버에 올리면 GLIBC_2.34 not found 같은 메시지와 함께 시작하지 못한다. 빌드 환경을 운영 환경과 같은 베이스 이미지로 맞추거나, 가장 오래된 대상 환경에서 빌드한다.
  • Windows에서는 런타임 DLL이 빠진다. C++ 서버를 새 머신에 올렸더니 vcruntime140.dll이 없다며 뜨지 않는 경우다. Visual C++ 재배포 패키지를 설치 단계에 넣거나 런타임을 정적으로 링크(/MT)한다.
  • .NET 서버는 빌드가 통과해도 실행 중에 깨질 수 있다. 같은 패키지의 다른 버전을 프로젝트마다 참조하면, 서버가 그 코드 경로를 처음 탈 때 MissingMethodException이 난다. 시작 시점이 아니라 특정 기능을 처음 쓸 때 터지므로, 패키지 버전은 솔루션 전체에서 한곳(Directory.Packages.props)으로 묶는다.

주의 사항

  • "정의를 찾을 수 없다"는 컴파일러가 아니라 링커가 내는 메시지다. 그 메시지가 나왔다면 컴파일은 이미 통과했다. 헤더를 포함했다는 것과 구현을 링커에 넘겼다는 것은 다른 이야기라, 그 함수가 들어 있는 소스나 라이브러리가 링크 대상에 들어갔는지를 확인한다.
  • C++ 이름 장식(name mangling)이 원인일 때도 있다. C++ 컴파일러는 오버로딩을 위해 심볼 이름에 인자 타입을 섞어 넣는다. C로 만든 라이브러리를 C++에서 부를 때 extern "C"가 빠지면 이름이 달라져 정의를 못 찾는다.
  • 동적 라이브러리 버전 문제는 빌드 때 드러나지 않는다. 실행할 때 비로소 나타나므로, 빌드 환경과 배포 환경이 다르면 배포한 뒤에야 알게 된다.
