먼저 읽을 것: 가상 메모리 · 페이지 폴트와 스래싱

핵심 요약

메모리 할당이 성공했다는 것은 주소 공간에 자리를 예약받았다는 뜻이지 물리 메모리를 받았다는 뜻이 아니다. 물리 페이지는 그 주소에 처음 접근할 때 붙는다.

그래서 프로세스 메모리를 볼 때 VIRT(예약한 전체)와 RES(실제로 붙은 것)가 크게 벌어진다. 어느 값을 보느냐에 따라 "누수다", "정상이다"가 갈린다. 원리는 가상 메모리와 페이지 폴트에서 다뤘다. 여기서는 실제로 숫자를 읽고 진단하는 법을 본다.

동작 원리

예약이 먼저 끝나고 물리 페이지는 나중에 붙는다

할당 함수가 성공을 돌려주는 시점에 커널은 그 주소 범위를 이 프로세스 것으로 기록했을 뿐이다. 처음 접근하면 마이너 폴트가 나고, 그때 0으로 채운 물리 페이지가 붙는다. 대부분의 프로그램이 예약한 것을 다 쓰지 않으므로, 미리 붙이면 물리 메모리가 금방 바닥나기 때문이다.

부족할 때 언제 드러나는지는 OS마다 다르다. Linux는 기본 설정에서 예약을 넉넉히 허용(overcommit)하므로 쓰는 순간 모자라고, OOM killer가 프로세스를 끝낸다. Windows는 할당(커밋)할 때 쓸 수 있는 양을 따져 할당 시점에 실패시킨다(프로세스 메모리 구성).

.NET 서버는 VIRT가 원래 크다

.NET GC는 힙으로 쓸 주소 범위를 처음에 크게 예약해 두고, 필요할 때 실제 메모리를 붙인다. .NET 7부터는 기본으로 수백 GB를 예약하므로 VIRT가 물리 메모리보다 훨씬 커도 정상이다. 반대로 RES는 GC가 압축과 해제를 하면 줄어들 수 있지만, GC는 다음 할당에 쓰려고 일부를 바로 돌려주지 않고 들고 있다.

서버 GC(<ServerGarbageCollector>true, ASP.NET Core의 기본)는 코어마다 힙을 하나씩 두어서, 코어가 많은 머신일수록 RES가 크다. 작은 컨테이너에서 메모리가 빠듯하면 GCHeapCount로 힙 수를 줄이거나, .NET 6부터 있는 GCConserveMemory로 GC가 더 자주 압축하게 할 수 있다.

컨테이너에서는 "사용량"이 페이지 캐시를 포함한다

컨테이너의 메모리 사용량(cgroup의 memory.current, 모니터링의 container_memory_usage_bytes)에는 그 컨테이너가 읽고 쓴 파일의 페이지 캐시가 들어간다. 로그를 많이 쓰는 서버는 이 값이 limit 근처까지 오르는데, 캐시는 필요하면 비워지므로 곧바로 위험한 것은 아니다. Kubernetes가 OOM과 축출을 판단할 때 쓰는 값은 캐시 중 비울 수 있는 부분을 뺀 working set(container_memory_working_set_bytes)이다. 알람도 이 값으로 건다.

게임 서버에서는

  • 미리 건드려서(warm-up) 폴트를 오픈 전으로 옮긴다. 서버가 시작할 때 맵 데이터, 세션 풀, 버퍼 풀을 미리 만들고 한 번씩 써 두면, 물리 페이지가 붙는 비용이 접속자가 몰리기 전에 끝난다. 오픈 직후 몇 분만 틱이 튀는 증상의 흔한 해법이다. 대신 시작이 느려지고, 실제로 안 쓸 메모리까지 미리 차지한다.
  • 메모리 알람은 RES와 GC 힙으로 건다. VIRT로 알람을 걸면 .NET 서버는 켜자마자 울린다. 같은 동접에서 RES가 시간에 따라 오르는지, 오르는 것이 GC 힙인지 네이티브인지를 나눠 본다.
  • 컨테이너 limit은 RES의 최고점에 여유를 둔다. limit을 평균 사용량에 맞추면 GC 직전의 최고점이나 접속 폭주 때 OOMKilled로 내려간다. .NET은 limit을 읽어 GC 힙 상한을 잡지만, 스레드 스택과 네이티브 버퍼까지 합친 프로세스 전체가 limit을 넘으면 죽는다.

주의 사항

  • 할당 반환값만 확인해서는 안전하지 않다. Linux에서는 할당이 성공한 뒤 쓰는 순간 OOM killer가 프로세스를 끝낼 수 있다. 오류를 받아 처리할 기회가 없다. 프로세스마다 /proc/<pid>/oom_score로 점수가 매겨지고, 점수가 가장 높은 것이 먼저 죽는다.
  • 해제했는데 RES가 안 줄어드는 것은 대개 누수가 아니다. 할당자나 GC가 다음 요청에 쓰려고 들고 있는 것이다(메모리 할당자). 누수인지는 같은 부하에서 계속 오르는지로 판단한다.
  • VIRT가 큰 것은 64비트에서 문제가 아니다. 주소 공간이 바닥나는 것은 32비트 프로세스의 이야기다(32비트와 64비트).
