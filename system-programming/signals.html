먼저 읽을 것: 프로세스 간 통신 · 크래시 덤프와 심볼

핵심 요약

시그널은 커널이 프로세스에 보내는 번호 하나짜리 알림이다. 프로세스가 무엇을 하고 있든 끼어든다. 시그널마다 기본 동작이 정해져 있고, 대부분은 프로세스를 끝내는 것이다. 처리기를 등록하면 기본 동작 대신 내 코드가 돈다. SIGKILL과 SIGSTOP만은 막을 수 없다.

서버가 챙길 것은 셋이다. SIGTERM을 받아 정상 종료 경로로 내려가기, 끊긴 소켓에 썼다고 SIGPIPE로 죽지 않기, 죽은 프로세스의 종료 코드에서 어떤 시그널로 죽었는지 읽어 내기다.

처리기 안에서는 거의 아무것도 못 한다

시그널은 아무 지점에나 끼어든다. malloc이 내부 락을 잡고 있는 도중일 수도 있다. 그때 처리기에서 다시 malloc이나 printf, 락을 쓰는 함수를 부르면 자기 자신을 기다리며 멈추거나 자료구조가 깨진다. 처리기 안에서 불러도 되는 것은 async-signal-safe로 정해진 몇몇 함수(write, _exit 등)뿐이다.

그래서 처리기는 표시만 남기고 바로 돌아오는 것이 정석이다. volatile sig_atomic_t 플래그를 세우거나, 파이프나 eventfd에 1바이트를 써서 메인 루프가 깨어나게 한다. Linux의 signalfd는 시그널 자체를 파일 디스크립터로 읽게 해 준다. .NET 런타임은 이 일을 안에서 대신 하고, 등록한 처리기는 보통 스레드에서 불러 준다. 그래서 C# 처리기에서는 일반 코드를 써도 된다.

끊긴 소켓에 쓰면 프로세스가 죽을 수 있다

상대가 연결을 끊은(RST를 보낸) 소켓에 다시 쓰면 쓰기 호출은 EPIPE로 실패하고, 그와 함께 SIGPIPE가 온다. 기본 동작이 종료라서, 처리하지 않은 네이티브 서버는 클라이언트 하나가 끊긴 탓에 통째로 죽는다. 로그에는 아무것도 남지 않는다.

막는 방법은 세 가지다. 시작할 때 signal(SIGPIPE, SIG_IGN)으로 무시하거나, Linux에서는 send에 MSG_NOSIGNAL을 주거나, macOS·BSD에서는 소켓에 SO_NOSIGPIPE를 켠다. 그러면 오류만 돌아오고 프로세스는 산다. .NET 런타임은 시작할 때 SIGPIPE를 무시하도록 해 두므로 SocketException으로 받는다. Windows에는 이 시그널이 없고 오류 코드만 온다.

종료 코드로 죽은 이유를 읽는다

프로세스가 스스로 끝나면 exit에 넘긴 값(0~255)이 종료 코드다. 시그널로 끝나면 셸과 컨테이너 런타임은 128 + 시그널 번호로 보여 준다. 그래서 숫자만 보고 원인을 가를 수 있다.

종료 코드뜻먼저 볼 것
137SIGKILL(128 + 9)메모리 부족으로 OOM killer가 끝냈는지(Kubernetes의 OOMKilled, dmesg), 종료 유예 시간을 넘겼는지. SIGTERM이 서버까지 전달되지 않아도(아래 PID 1 문제) 유예 시간 뒤 이렇게 끝난다
143SIGTERM(128 + 15)을 처리하지 않아 기본 동작으로 끝남신호는 왔지만 받아서 정리한 뒤 스스로 끝내는 코드가 없다
139SIGSEGV(128 + 11)네이티브 라이브러리의 잘못된 메모리 접근. 덤프의 네이티브 스택
134SIGABRT(128 + 6)런타임이 스스로 중단했다. Linux에서 처리되지 않은 .NET 예외가 흔히 이렇게 끝난다

게임 서버에서는

  • SIGTERM을 정상 종료 경로에 잇는다. .NET Generic Host는 SIGTERM을 받아 IHostApplicationLifetime.ApplicationStopping을 알리고 각 서비스의 StopAsync를 부른다. 기다리는 상한은 HostOptions.ShutdownTimeout이다. Host 없이 짠 서버는 PosixSignalRegistration.Create(PosixSignal.SIGTERM, ...)로 받고, 처리기에서 context.Cancel = true를 주면 기본 종료가 일어나지 않아 내 순서대로 정리할 수 있다. 무엇을 어떤 순서로 정리하는지는 드레이닝에서 다룬다.
  • 유예 시간을 넘기지 않게 정리 순서를 잡는다. Kubernetes는 SIGTERM을 보내고 terminationGracePeriodSeconds(기본 30초)가 지나면 SIGKILL을 보낸다. 잃으면 안 되는 저장부터 하고, 오래 걸리는 정리는 뒤로 둔다. 정리가 본래 길다면 유예 시간과 ShutdownTimeout을 함께 늘린다.
  • 컨테이너의 PID 1은 시그널을 다르게 받는다. PID 1은 처리기를 등록하지 않은 시그널의 기본 동작이 적용되지 않는다. ENTRYPOINT를 셸 형식으로 쓰면 셸이 PID 1로 남는 경우가 많고, 셸은 SIGTERM을 자식인 서버에 넘겨주지 않는다. 서버는 신호를 못 받은 채 30초 뒤 SIGKILL로 죽는다. exec 형식(["dotnet", "Server.dll"])으로 서버를 PID 1로 두거나, tini 같은 작은 init(docker run --init)을 앞에 둔다.
  • Windows에는 시그널 대신 다른 통로가 있다. 콘솔 프로그램은 Ctrl+C·창 닫기·로그오프·종료를 콘솔 컨트롤 이벤트(SetConsoleCtrlHandler, .NET의 Console.CancelKeyPress)로 받고, 서비스는 서비스 제어 관리자의 중지 요청으로 받는다. .NET의 PosixSignalRegistration은 Windows에서 SIGINT·SIGQUIT·SIGTERM을 콘솔 이벤트에 대응시켜, 같은 코드로 양쪽을 받게 해 준다.

주의 사항

  • 정리 코드가 반드시 돈다고 믿지 않는다. SIGKILL, 전원 차단, 커널 패닉에서는 아무것도 돌지 않는다. 잃으면 안 되는 상태는 종료 때가 아니라 평소에 저장한다.
  • kill -9를 습관으로 쓰지 않는다. 서버를 내릴 때는 기본 kill(SIGTERM)을 보내고 기다린다. 처음부터 -9를 쓰면 정상 종료 경로가 한 번도 쓰이지 않아, 그 코드가 망가져도 아무도 모른다.
  • 같은 시그널은 쌓이지 않는다. 처리하기 전에 같은 표준 시그널이 여러 번 오면 한 번으로 합쳐진다. 시그널 횟수를 세는 설계는 하지 않는다.
