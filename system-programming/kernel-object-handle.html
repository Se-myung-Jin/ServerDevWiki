먼저 읽을 것: 커널 경계와 시스템 콜

핵심 요약

커널 오브젝트는 커널이 만들어 들고 있는 자원이다. 파일, 소켓, 프로세스, 스레드, 뮤텍스, 이벤트, IOCP가 모두 여기에 해당한다.

응용은 그 실체에 직접 닿지 못하고 핸들이라는 번호표로만 가리킨다. Windows는 이 번호를 핸들, Linux는 파일 디스크립터라고 부른다. 커널이 실체를 쥐고 있어야 응용이 실수해도 커널 자료가 망가지지 않는다.

동작 원리

핸들은 포인터가 아니라 표의 칸 번호다

핸들은 프로세스마다 따로 있는 표(Windows의 핸들 테이블, Linux의 파일 디스크립터 테이블)의 색인이다. 포인터와 다른 점은 이렇다.

  • 다른 프로세스에 값을 넘겨도 쓸 수 없다. 표가 다르기 때문이다. 넘기려면 커널에 복제를 요청한다. Windows는 DuplicateHandle, Linux는 Unix 도메인 소켓으로 디스크립터를 실어 보낸다(SCM_RIGHTS).
  • 커널이 매번 표에서 찾아 확인한다. 표에 없는 값은 오류로 돌아온다(Windows ERROR_INVALID_HANDLE, Linux EBADF).
  • 번호표마다 권한이 붙는다. 같은 파일이라도 읽기 전용으로 연 핸들로는 쓸 수 없다.
  • 응용이 실체의 주소를 모르니 임의로 고칠 수 없다.

Linux는 남은 번호 중 가장 작은 것을 새 디스크립터로 준다. 그래서 닫은 번호가 곧바로 다음 open이나 accept에 다시 배정된다. 이 성질이 아래 주의 사항의 "닫은 핸들 재사용" 버그를 만든다.

참조 횟수가 수명을 정한다

커널 오브젝트에는 참조 횟수가 붙어 있다. 핸들을 만들거나 복제하면 오르고, 닫으면 내려간다. 0이 되어야 실제로 없어진다.

  • 파일을 만든 쪽이 닫아도 다른 프로세스가 열어 두었으면 살아 있다(파일 시스템의 "지운 파일이 계속 공간을 차지한다"와 같은 원리).
  • 스레드·프로세스 핸들을 닫아도 그 스레드·프로세스가 끝나지 않는다. 참조가 하나 줄 뿐이다.
  • 닫지 않으면 오브젝트가 남는다. 이것이 핸들 누수다.

한 프로세스가 가질 수 있는 수에 한도가 있다

환경한도넘으면
Linux프로세스당 열린 디스크립터 수(ulimit -n). 배포판 기본 소프트 한도는 1024인 경우가 많다EMFILE, "Too many open files". 소켓도 디스크립터라 accept가 실패한다
Windows프로세스당 약 1,600만(224)으로 매우 크다한도보다 먼저 커널 메모리와 성능이 무너진다

Linux에서는 소켓 하나가 디스크립터 하나라서 동접이 곧 디스크립터 수다. 동접 수천 명을 받는 서버는 기본 한도 1024에 바로 닿는다. systemd 서비스면 LimitNOFILE, 컨테이너면 런타임의 nofile 설정으로 한도를 올린다.

한도는 소프트와 하드 두 개다. 프로세스는 소프트 한도를 하드 한도까지는 스스로 올릴 수 있고, .NET 런타임은 Linux에서 시작할 때 이 일을 해 둔다. 그래서 .NET 서버에서는 소프트 한도 1024보다 하드 한도가 실제 상한이고, 올려야 할 것도 하드 한도다. 실제 값은 /proc/<pid>/limits의 "Max open files"로 확인한다.

선택 기준

이름으로 여는 쪽과 복제해 받는 쪽

구분이름 있는 오브젝트이름 없는 오브젝트
다른 프로세스에서이름으로 연다핸들을 복제해 받아야 한다
같은 이름이 있으면기존 것을 연다(충돌 가능)충돌이 없다
노출이름을 아는 누구나 열 수 있다넘겨준 쪽만 쓴다

이름은 편한 만큼 노출된다. 서버 중복 실행 막기처럼 일부러 이름으로 찾아야 하는 경우가 아니면 복제 쪽이 통제하기 쉽다(동기화 객체의 이름 붙인 Mutex).

게임 서버에서는

  • .NET에서 핸들은 SafeHandle이 쥔다. FileStream, Socket, Process, 이름 붙인 Mutex 같은 객체는 안에 SafeHandle을 들고 있고, Dispose할 때 핸들을 닫는다. 그러니 using으로 감싸는 것이 핸들 누수 대책의 전부다(IDisposable). Dispose를 빠뜨리면 GC의 종료자가 언젠가 닫아 주지만, 언제일지 모르고 그 사이 한도에 닿는다.
  • 세션 객체가 남으면 소켓도 남는다. 접속이 끊긴 세션을 사전에서 빼지 않으면 그 안의 Socket도 닫히지 않는다. 동접은 그대로인데 디스크립터 수가 계속 오르면 정리되지 않은 세션을 의심한다(메모리 누수).
  • HttpClient를 요청마다 만들지 않는다. 외부 API(결제, 인증)를 부를 때마다 새로 만들고 버리면 소켓이 쌓인다. 하나를 공유하거나 IHttpClientFactory를 쓴다.
  • 수를 지표로 남긴다. Linux는 ls /proc/<pid>/fd | wc -l이나 lsof -p <pid>, Windows는 작업 관리자의 핸들 열이나 Process.HandleCount. 동접 그래프와 나란히 두면 누수가 바로 보인다.

주의 사항

  • 핸들 값은 정수지만 주소가 아니다. 프로세스를 넘어가면 의미가 없고, 더하거나 크기를 비교해서 쓸 값도 아니다.
  • 닫은 핸들 값을 다시 쓰면 커널이 막아 주지 못한다. 비워진 번호는 다음 오브젝트에 다시 배정된다. 이미 닫은 번호로 close를 한 번 더 부르면, 그사이 다른 스레드가 연 소켓을 닫아 버린다. 오류 없이 엉뚱한 연결이 끊기는, 찾기 아주 어려운 버그다. 닫은 뒤에는 변수를 무효 값으로 바꿔 둔다.
  • 핸들 누수는 메모리 누수보다 늦게 보인다. 메모리는 늘어나는 것이 그래프에 보이지만, 핸들은 세어 보지 않으면 한도에 닿아 장애가 날 때까지 모른다.
