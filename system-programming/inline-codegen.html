먼저 읽을 것: 컴파일과 링킹 · 함께 보면 좋은 것: JIT와 AOT

핵심 요약

인라인은 함수 호출을 그 자리에 본문으로 펼쳐 넣는 최적화다. 호출 비용이 사라지는 것보다 다른 최적화가 걸릴 수 있게 되는 것이 더 크다.

코드 생성은 다른 방향의 같은 생각이다. 실행 중에 타입을 탐색해 알아내는 대신(리플렉션), 빌드 때 필요한 코드를 만들어 둔다(소스 제너레이터). 탐색 비용이 사라지고 AOT에서도 동작한다.

동작 원리

호출 경계가 사라지면 다른 최적화가 걸린다

그래서 인라인이 막히면 그 뒤의 최적화가 줄줄이 사라진다. 가상 호출이 비싼 것도 대개 간접 점프 자체보다 펼치지 못해서다(가상 함수와 다형성). .NET JIT는 실행 중에 한 타입만 오는 것을 관측하면 그 타입으로 가정하고 펼친 뒤, 아니면 원래 경로로 돌아가는 코드를 만든다(guarded devirtualization, .NET 8부터 동적 PGO가 기본). C++도 final이나 링크 시간 최적화(LTO)·PGO로 일부 가상 호출을 펼친다.

언제나 펼치지는 않는다. 본문이 크면 코드가 불어나 명령 캐시 적중률이 떨어지므로, 컴파일러는 크기와 호출 빈도를 보고 판단한다. [MethodImpl(MethodImplOptions.AggressiveInlining)]이나 C++ inline은 요청이지 명령이 아니다.

실행 중에 탐색하는 쪽과 빌드 때 만들어 두는 쪽

구분리플렉션소스 제너레이터
언제 알아내나실행 중에 타입을 탐색한다빌드 때 그 타입 전용 코드를 만든다
실행 중 비용탐색과 동적 호출 비용이 든다일반 코드라 추가 비용이 없다
AOT·트리밍참조가 정적으로 안 보여 잘려 나갈 수 있다그대로 동작한다
오류 시점실행 중에 드러난다대개 컴파일에서 걸린다

직렬화가 대표적인 자리다. System.Text.Json의 소스 생성 모드나 MessagePack-CSharp의 AOT 코드 생성은, 실행 중에 속성을 탐색하는 대신 빌드 때 그 타입 전용 읽기·쓰기 코드를 만들어 둔다. 반대로 대상 타입이 몇 개 없고 호출도 드물면, 늘어난 빌드 시간과 구성 복잡도를 회수하지 못한다.

주의 사항

  • 인라인은 호출 비용을 없애려고 하는 것이 아니다. 요즘 CPU에서 호출 자체는 비싸지 않다. 실제로 빨라지는 것은 그 뒤에 걸리는 최적화 때문이다.
  • 게임 서버의 패킷 직렬화는 코드 생성 쪽이 기본이다. 매 패킷 리플렉션으로 필드를 찾으면 할당과 탐색 비용이 쌓인다. 직렬화 라이브러리의 코드 생성 기능을 쓰고, Native AOT로 배포할 계획이 있으면 처음부터 리플렉션 의존을 피한다.
