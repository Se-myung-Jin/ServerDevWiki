먼저 읽을 것: 트랜잭션과 ACID · 로그와 지속성

핵심 요약

DB 확장은 쉬운 순서가 정해져 있다. 먼저 쿼리와 인덱스를 고치고, 더 큰 서버로 올리고(수직 확장), 읽기를 복제본으로 나누고, 큰 테이블을 한 서버 안에서 파티션으로 자른다. 그래도 쓰기를 한 서버가 못 받으면 데이터를 여러 서버로 나누는 샤딩으로 간다.

뒤로 갈수록 DB가 해 주던 일을 응용이 떠맡는다. 복제본은 값이 늦게 도착하므로 "방금 쓴 값이 안 보이는" 일을 다뤄야 한다. 샤드를 넘는 거래는 한 트랜잭션으로 묶이지 않는다. 그래서 확장은 나누는 기술보다, 나눈 뒤 넘나드는 작업을 어떻게 줄이느냐의 문제다. 서버 전체를 어떻게 나누는지는 확장과 샤딩에서 다루고, 여기서는 DB 쪽만 본다.

동작 원리

커넥션 풀은 DB 앞의 줄이다

연결을 맺는 데는 TCP 핸드셰이크, TLS, 인증이 들어간다. 매번 맺고 끊으면 쿼리보다 연결이 더 비싸다. 그래서 응용은 연결을 풀에 두고 빌려 쓴다. .NET의 SqlClient, Npgsql, MySqlConnector는 모두 연결 문자열마다 풀을 하나씩 만들고, 최대 크기 기본값은 100이다. 풀이 다 차면 다음 OpenAsync는 연결이 돌아올 때까지 기다리다가 시간이 지나면(기본 15초 안팎) 예외를 던진다.

풀을 키운다고 빨라지지 않는다. DB가 동시에 실제로 일할 수 있는 양은 코어 수와 디스크가 정한다. 그보다 많은 연결이 동시에 들어가면 DB 안에서 락 경합과 컨텍스트 스위칭만 늘고, 쿼리마다 느려져 연결을 더 오래 붙잡는다. 출발점으로 흔히 쓰는 감각은 "DB 코어 수의 두 배 남짓"이고, 거기서 측정하며 조정한다. 넘치는 요청은 DB 안이 아니라 응용의 풀 앞에서 줄을 서게 두는 편이 DB 처리량을 지킨다.

DB가 보는 연결 수는 서버 대수 × 풀 크기다. 게임 서버 40대가 각자 풀 100을 쓰면 DB에는 4,000개가 붙을 수 있다. PostgreSQL은 연결마다 프로세스를 하나씩 띄우므로(max_connections 기본 100) 앞에 PgBouncer 같은 연결 중계기를 두는 경우가 많다.

풀이 고갈됐을 때 원인이 풀 크기인 경우는 드물다. 느린 쿼리, 트랜잭션을 연 채 외부 호출 기다리기, Dispose되지 않아 돌아오지 않는 연결이 대부분이다. 비동기 코드에서 연결을 연 채 다른 서버 응답을 await하면 그 시간 내내 연결 하나가 묶인다(IDisposable과 결정적 해제).

복제본은 읽기를 나누고, 값이 늦게 도착한다

주 서버가 커밋 응답 전에 복제본을 얼마나 기다리느냐로 세 가지가 나뉜다.

방식커밋 응답 시점쓰기 지연주 서버가 죽으면
비동기(대개 기본)주 서버에만 쓰면 바로없다아직 안 넘어간 커밋을 잃는다
반동기(MySQL semi-sync)복제본 하나 이상이 로그를 받았다고 답하면왕복 한 번받은 복제본으로 넘기면 잃지 않는다. 시간 초과로 비동기로 떨어지면 다시 잃을 수 있다
동기(PostgreSQL synchronous_standby_names)지정한 복제본이 받거나(on) 재생까지 마치면(remote_apply)왕복과 재생잃지 않는다. 대신 그 복제본이 멈추면 쓰기도 멈춘다

"방금 쓴 값이 안 보인다"는 몇 가지 방법으로 다룬다. 가장 흔한 것은 오래된 값이어도 되는 조회만 복제본으로 보내는 것이다. 랭킹 목록, 통계, 다른 사람 프로필은 몇 초 늦어도 된다. 방금 산 아이템 확인처럼 자기 쓰기를 읽는 조회는 주 서버로 보낸다. 쓰기 직후 일정 시간 동안 그 사용자만 주 서버로 보내는 방법, 쓰기 때 받은 로그 위치(MySQL GTID, PostgreSQL LSN)까지 복제본이 따라왔는지 확인하고 읽는 방법도 있다.

페일오버는 유실 구간을 고르는 일이다

주 서버가 죽으면 복제본 하나를 새 주 서버로 올린다. 비동기 복제라면 죽기 직전 커밋 중 복제본에 못 넘어간 것은 사라진다. 응용은 커밋 성공을 받았는데 새 주 서버에는 그 행이 없다. 그래서 재화 지급처럼 잃으면 안 되는 쓰기는 반동기나 동기 복제를 쓰거나, 응용 쪽에 요청 ID를 남겨 나중에 대조할 수 있게 한다.

더 위험한 것은 옛 주 서버가 죽은 것이 아니라 네트워크만 끊긴 경우다. 둘 다 자기가 주 서버라고 믿고 쓰기를 받으면(split brain) 값이 갈라져 합칠 수 없다. 페일오버 도구는 옛 주 서버를 확실히 막는 절차(펜싱)와 함께 써야 한다.

파티셔닝은 한 서버 안에서, 샤딩은 서버를 넘어서 나눈다

구분파티셔닝샤딩
나누는 곳한 DB 인스턴스 안여러 DB 인스턴스
푸는 문제테이블이 너무 커서 읽기와 정리가 느리다한 서버가 쓰기량이나 데이터량을 못 받는다
트랜잭션과 조인그대로 된다샤드를 넘으면 안 되거나 비싸다
누가 관리하나DBMS가 지원한다(range, list, hash)대개 응용이나 미들웨어(Vitess, Citus 등)가 맡는다

파티셔닝은 조건에 파티션 키가 있으면 해당 파티션만 읽는다(파티션 프루닝). 오래된 데이터를 정리할 때 행을 하나씩 지우는 대신 파티션을 통째로 떼어 낸다. 날짜별로 쌓이는 로그와 이력 테이블에 잘 맞는다. 

-- PostgreSQL: 월별 파티션. 석 달 지난 파티션은 DROP 한 번으로 정리한다
CREATE TABLE item_log (
  id         bigint      NOT NULL,
  account_id bigint      NOT NULL,
  logged_at  timestamptz NOT NULL,
  detail     jsonb
) PARTITION BY RANGE (logged_at);

CREATE TABLE item_log_2026_10 PARTITION OF item_log
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

DROP TABLE item_log_2026_07;   -- DELETE 수억 건 대신

샤드 키가 가장 되돌리기 어렵다

샤드 키는 한 요청이 한 샤드 안에서 끝나는 축으로 고른다. 게임에서는 계정 ID나 월드 번호가 자연스럽다. 한 캐릭터의 인벤토리, 우편, 퀘스트는 대부분 그 캐릭터 혼자 쓰기 때문이다. 키를 고르는 방식은 셋이다.

방식어떻게좋은 점약한 점
해시hash(account_id) % N고르게 퍼진다샤드 수를 바꾸면 거의 모든 키가 옮겨 간다
범위ID 1~100만은 샤드 1범위 조회가 한 샤드에서 끝난다새 ID가 늘 마지막 샤드로 몰린다(핫 샤드)
디렉터리키→샤드 표를 따로 둔다옮기고 싶은 키만 옮긴다표 자체가 모든 요청이 거치는 곳이 된다

샤드 수를 나중에 바꾸는 리샤딩은 데이터를 옮기며 서비스를 계속해야 해서 어렵다. 그래서 처음부터 논리 샤드를 넉넉히(예: 1,024개) 만들고 물리 서버 몇 대에 나눠 담는다. 서버를 늘릴 때는 논리 샤드 몇 개를 통째로 옮기면 되고 키 계산은 그대로다. 일관 해싱도 같은 목적으로 쓴다(일관된 해싱).

샤드를 넘는 거래는 한 트랜잭션이 아니다

두 플레이어가 다른 샤드에 있으면 아이템 거래를 하나의 DB 트랜잭션으로 묶을 수 없다. 고전적인 답은 2단계 커밋(2PC)이다. 조정자가 모든 참가자에게 "준비"를 시키고, 모두 준비됐다고 답하면 "커밋"을 보낸다. 준비를 마친 참가자는 결과를 들을 때까지 락을 쥐고 기다려야 하므로, 조정자가 그 사이에 죽으면 참가자들이 멈춘다. 왕복도 두 배다. 그래서 게임 서버에서는 잘 쓰지 않는다.

실무에서는 단계를 나누고 각 단계에 되돌리는 작업을 짝짓는다. 한쪽에서 아이템을 빼서 "거래 중" 상태로 맡겨 두고, 다른 쪽에 넣고, 실패하면 맡긴 것을 돌려준다. 단계마다 거래 ID를 붙여, 같은 단계가 두 번 실행돼도 결과가 같게 만든다. 이 구조가 사가다. 대신 중간 상태가 밖에서 보인다. 빠졌는데 아직 안 들어온 순간을 UI에서 어떻게 보여 줄지도 정해야 한다.

선택 기준

증상먼저 볼 것그다음
특정 쿼리가 느리다실행 계획과 인덱스캐시
읽기가 많아 CPU가 찬다복제본으로 읽기 분리, 캐시수직 확장
테이블이 커서 정리와 스캔이 느리다파티셔닝오래된 데이터 보관소로 이관
쓰기가 한 서버의 한계를 넘는다쓰기 횟수 줄이기(모아서 저장), 로그 DB 분리샤딩
연결 수가 모자라다느린 쿼리, 연 채 기다리는 트랜잭션연결 중계기, 풀 크기

샤딩은 이 표의 맨 끝이다. 한 번 들어가면 응용 코드, 배포, 백업, 운영 도구가 전부 샤드를 알아야 하고, 되돌리기가 매우 비싸다.

게임 서버에서는

  • 기능별로 먼저 나눈다. 계정·결제 DB, 게임(캐릭터) DB, 로그 DB를 처음부터 다른 인스턴스로 둔다. 쓰기 성격과 지속성 요구가 달라서, 같은 서버에 두면 로그 쓰기가 결제 커밋을 늦춘다. 이것만으로 샤딩이 필요 없는 경우가 많다.
  • 월드 단위 DB가 자연스러운 샤드다. 월드(서버)마다 캐릭터가 독립이면 월드 하나가 DB 하나를 쓴다. 대신 서버 통합, 월드 이전 같은 운영 이벤트가 곧 데이터 이관 작업이 된다. 캐릭터 ID를 처음부터 월드 사이에서 겹치지 않게 만들어 두면 통합이 쉽다.
  • 전역으로 봐야 하는 것은 따로 둔다. 계정, 닉네임 중복 검사, 친구 목록, 전체 랭킹은 샤드 키 하나로 안 나뉜다. 작은 전역 DB나 별도 저장소로 떼어 낸다.
  • 복제본 읽기는 기능마다 정한다. 운영 툴 조회, 랭킹 계산, 통계 배치는 복제본으로 보낸다. 로그인 직후 캐릭터 로딩, 구매 직후 확인은 주 서버에서 읽는다. 코드에서 연결 문자열을 둘로 나눠 두고 호출하는 쪽이 고르게 한다.

주의 사항

  • 복제 지연은 없앨 수 없고 다룰 수만 있다. 동기 복제로 없애면 쓰기 지연과 가용성을 대가로 낸다. 지연을 지표로 보고, 몇 초 늦어도 되는 조회만 복제본으로 보낸다.
  • 복제본은 백업이 아니다. 실수로 실행한 DELETE도 그대로 복제된다. 시점 복구용 백업과 로그 보관은 따로 둔다.
  • 샤드마다 ID를 따로 매기면 겹친다. 자동 증가 ID는 샤드마다 1부터 시작한다. 전역에서 유일해야 하는 ID는 샤드 번호를 섞거나 시간 기반 ID를 쓴다.
  • 풀 고갈 예외를 풀 크기로 덮지 않는다. 크기를 늘리면 원인이 가려진 채 DB 부하만 커진다. 연결을 오래 쥔 코드부터 찾는다.
