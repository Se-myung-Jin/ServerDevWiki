핵심 요약

SQL 명령은 무엇을 다루느냐로 나뉜다. 테이블 같은 구조를 만들고 고치면 DDL, 행을 넣고 읽고 고치면 DML, 권한을 주고 거두면 DCL이다. 트랜잭션을 끝내는 COMMIT과 ROLLBACK은 DCL에 넣기도 하고 TCL로 따로 떼기도 한다.

키는 두 가지 일을 나눠 맡는다. 기본 키는 행 하나를 유일하게 가리킨다. 그래서 비거나 겹칠 수 없다. 외래 키는 다른 테이블의 행을 가리키고, 없는 행을 가리키지 못하게 막는다. 이것을 참조 무결성이라 한다.

동작 원리

구조를 바꾸느냐 데이터를 바꾸느냐

구분다루는 것대표 명령되돌릴 수 있나
DDL테이블, 인덱스 같은 구조CREATE, ALTER, DROP, TRUNCATE엔진마다 다르다. MySQL은 실행하면 바로 커밋된다
DML행SELECT, INSERT, UPDATE, DELETE트랜잭션 안이면 되돌린다
DCL권한GRANT, REVOKE해당 없음
TCL트랜잭션 경계BEGIN, COMMIT, ROLLBACK, SAVEPOINT그 자체가 확정과 취소다

실무에서 갈리는 것은 마지막 칸이다. MySQL은 DDL을 실행하는 순간 암시적 커밋이 일어난다. 트랜잭션 안에서 ALTER를 치면 그 앞의 변경까지 함께 확정된다. PostgreSQL과 SQL Server는 대부분의 DDL을 트랜잭션 안에서 되돌릴 수 있다. 같은 마이그레이션 스크립트가 엔진에 따라 반쯤 적용된 채 멈출 수 있다는 뜻이다.

DELETE와 TRUNCATE도 여기서 나뉜다. DELETE는 행을 하나씩 지우며 로그를 남기고, WHERE로 고를 수 있다. TRUNCATE는 테이블을 통째로 비운다. 훨씬 빠르지만 고를 수 없고, MySQL에서는 DDL이라 되돌릴 수 없다.

기본 키는 식별하고 외래 키는 참조한다

기본 키는 후보 가운데서 고른 것이다. 행을 유일하게 가리키는 속성 묶음이 슈퍼키이고, 그중 하나라도 빼면 유일성이 깨지는 최소 묶음이 후보 키다. 후보 키 하나를 기본 키로 정하면 나머지는 대체 키가 되고, 보통 UNIQUE 제약으로 지킨다. 위 그림의 email과 name이 그렇다.

기본 키를 무엇으로 할지는 두 갈래다. 자연 키는 이메일, 캐릭터 이름처럼 업무에 원래 있는 값이다. 대리 키는 자동 증가 숫자나 UUID처럼 식별만을 위해 만든 값이다. 자연 키는 바뀔 수 있다. 캐릭터 이름 변경권을 팔기 시작하면 그 이름을 참조하던 모든 테이블을 고쳐야 한다. 그래서 대부분은 바뀌지 않는 대리 키를 기본 키로 두고, 자연 키에는 UNIQUE를 건다. 대리 키를 무엇으로 만드느냐는 저장 순서와 얽혀 있어 인덱스의 종류와 설계에서 다룬다.

참조된 행이 지워질 때 무엇을 할지 정한다

CASCADE는 편하지만 한 줄의 DELETE가 몇 단계 아래까지 번진다. 계정 → 캐릭터 → 아이템 → 아이템 로그로 이어져 있으면 계정 하나를 지우는 문장이 수만 행을 지우고, 그동안 락을 오래 잡는다.

NULL은 값이 아니라 "모름"이다

NULL과 비교하면 참도 거짓도 아닌 UNKNOWN이 나온다. 이것을 3값 논리라 한다. WHERE는 참인 행만 남기므로 UNKNOWN인 행은 빠진다. 

-- 아무 행도 나오지 않는다. NULL = NULL 은 UNKNOWN 이다
SELECT * FROM characters WHERE guild_id = NULL;
-- 이렇게 쓴다
SELECT * FROM characters WHERE guild_id IS NULL;

-- 함정: 하위 쿼리에 NULL 이 하나라도 있으면 NOT IN 은 아무것도 돌려주지 않는다
SELECT * FROM characters
WHERE character_id NOT IN (SELECT owner_id FROM pets);   -- owner_id 에 NULL 이 있으면 결과 0행
-- NOT EXISTS 는 이 문제가 없다
SELECT * FROM characters c
WHERE NOT EXISTS (SELECT 1 FROM pets p WHERE p.owner_id = c.character_id);

집계도 NULL을 건너뛴다. COUNT(*)는 행을 세고 COUNT(guild_id)는 guild_id가 NULL이 아닌 행만 센다. COUNT(1)이 COUNT(*)보다 빠르다는 말은 근거가 없다. 주요 엔진은 둘을 같게 처리한다.

UNIQUE 제약이 NULL을 어떻게 보느냐도 엔진마다 다르다. MySQL과 PostgreSQL은 NULL끼리 같지 않다고 보아 NULL을 여러 개 허용한다. PostgreSQL 15부터는 UNIQUE NULLS NOT DISTINCT로 하나만 허용하게 바꿀 수 있다. SQL Server의 UNIQUE 제약은 NULL을 하나만 허용하고, 여러 개를 허용하려면 WHERE col IS NOT NULL을 붙인 필터 인덱스를 쓴다.

게임 서버에서는

  • 값은 항상 파라미터로 넘긴다. C# 서버는 Dapper나 EF Core로 쿼리를 보낸다. 캐릭터 이름처럼 사용자가 정하는 값을 문자열로 이어 붙이면 SQL 인젝션이 된다(인젝션). 파라미터 바인딩은 실행 계획을 다시 쓰게 해 주는 효과도 있다(실행 계획과 조인). 
    // Dapper: @name 자리에 값이 따로 전달된다
var c = await conn.QuerySingleOrDefaultAsync<Character>(
    "SELECT character_id, name, level FROM characters WHERE name = @name",
    new { name });
  • 운영 DB에 외래 키를 걸지는 팀마다 다르다. 걸면 잘못된 참조를 DB가 막아 준다. 대신 INSERT마다 부모를 확인하는 비용과 락이 붙고, 테이블이 서로 다른 샤드에 있으면 걸 수조차 없다(DB 확장). 대량 정리 작업도 순서를 맞춰야 한다. 그래서 아이템·로그처럼 쓰기가 많은 테이블은 외래 키 없이 응용이 검사하는 곳이 많다. 그 경우 무결성 책임은 서버 코드로 넘어오고, 고아 행을 찾는 점검 쿼리를 주기적으로 돌려야 한다.
  • 캐릭터 삭제는 지우지 않고 표시만 하는 경우가 많다. 복구 요청, 거래 분쟁, 로그 추적 때문이다. deleted_at 컬럼을 두는 논리 삭제를 쓰면 이름 UNIQUE와 부딪친다. 지운 캐릭터의 이름을 새 캐릭터가 쓸 수 있어야 하기 때문이다. 살아 있는 행에만 UNIQUE를 거는 부분 인덱스로 푼다(인덱스의 종류와 설계).
  • 스키마 변경은 마이그레이션 도구로 순서를 남긴다. 큰 테이블의 ALTER는 테이블을 다시 쓰며 오래 잠글 수 있다. 무중단으로 바꾸는 절차는 운영 분야에서 다룬다(스키마 마이그레이션).

주의 사항

  • DCL은 인가를 다룬다. 누구인지 확인하는 인증과 무엇을 할 수 있는지 정하는 인가는 다르다. 게임 서버 계정에는 필요한 테이블의 DML 권한만 주고, DDL 권한은 마이그레이션 계정에만 둔다.
  • 운영 DB에서 DELETE와 UPDATE는 트랜잭션 안에서 먼저 확인한다. WHERE 없이 실행된 UPDATE는 모든 행을 바꾼다. BEGIN 뒤에 영향받은 행 수를 보고 COMMIT한다.
  • SELECT *를 서버 코드에 두지 않는다. 컬럼이 추가되면 읽는 양이 늘고, 매핑 순서에 기대는 코드가 깨진다. 필요한 컬럼만 적는다.
  • NULL을 허용할지는 처음에 정한다. 나중에 NOT NULL로 바꾸려면 기존 NULL을 모두 채워야 하고, 큰 테이블에서는 그 자체가 큰 작업이다.
