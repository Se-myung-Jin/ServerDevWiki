먼저 읽을 것: SQL과 키

핵심 요약

트랜잭션은 여러 문장을 하나의 작업 단위로 묶은 구간이다. BEGIN으로 열고 COMMIT이나 ROLLBACK으로 닫는다. 그 안의 변경은 전부 반영되거나 전부 없던 일이 된다. 아이템을 넘기는 거래에서 "내 인벤토리에서는 빠졌는데 상대에게는 안 들어간" 상태가 남지 않게 하는 장치다.

ACID 네 글자를 외우는 것보다 각 성질을 무엇이 만드는지 아는 것이 중요하다. 원자성과 지속성은 로그가, 격리성은 락이나 MVCC가 만든다. 일관성만 DB가 혼자 지켜 주지 못한다. 무엇이 올바른 상태인지는 제약 조건과 애플리케이션 코드가 정한다.

동작 원리

열고 닫는 법과 오토커밋

BEGIN;  -- SQL Server는 BEGIN TRANSACTION
UPDATE inventory SET owner_id = 2002 WHERE item_id = 77 AND owner_id = 1001;
UPDATE character  SET gold = gold + 500 WHERE id = 1001;
UPDATE character  SET gold = gold - 500 WHERE id = 2002 AND gold >= 500;
INSERT INTO trade_log (trade_id, item_id, seller, buyer, price) VALUES ('t-9f3a', 77, 1001, 2002, 500);
COMMIT; -- 문제가 있으면 ROLLBACK

트랜잭션을 명시하지 않으면 세 엔진 모두 오토커밋으로 돈다. 문장 하나가 끝날 때마다 바로 커밋된다. 위 거래를 BEGIN 없이 보내면 문장 네 개가 각자 확정되고, 세 번째에서 구매자 골드가 모자라도 앞의 두 문장은 이미 반영돼 있다. 위 예에서 조건부 UPDATE가 0행을 바꿨는지 애플리케이션이 확인하고 롤백하는 것까지가 트랜잭션을 쓰는 쪽의 몫이다.

오류가 났을 때의 동작은 엔진마다 다르다. 이 차이를 모르면 "오류가 났으니 다 롤백됐겠지"라는 가정이 깨진다.

엔진트랜잭션 안에서 문장 하나가 실패하면
MySQL InnoDB대부분 그 문장만 되돌리고 트랜잭션은 계속 열려 있다. 그대로 COMMIT하면 앞의 성공한 문장은 확정된다. 데드락은 예외로 트랜잭션 전체를 롤백한다
PostgreSQL트랜잭션 전체가 실패 상태가 된다. 이후 문장은 모두 거부되고 ROLLBACK만 받는다
SQL Server기본(XACT_ABORT OFF)에서는 오류 종류에 따라 문장만 되돌리기도 한다. SET XACT_ABORT ON이면 실행 중 오류에서 전체를 롤백한다

네 성질은 서로 다른 장치가 만든다

성질보장하는 것무엇이 만드나
원자성(Atomicity)전부 되거나 전부 안 된다되돌릴 정보. InnoDB는 언두 로그에 옛 값을 남기고, PostgreSQL은 옛 행 버전이 테이블에 그대로 있어 실패한 트랜잭션의 새 버전을 보이지 않게 처리한다
일관성(Consistency)규칙을 어긴 상태로 끝나지 않는다기본 키, 외래 키, CHECK, UNIQUE 같은 제약 조건과 애플리케이션의 검사
격리성(Isolation)동시에 도는 트랜잭션이 서로의 중간 상태를 보지 않는다락 또는 MVCC. 얼마나 엄격할지는 격리 수준으로 고른다
지속성(Durability)커밋 응답을 받았으면 장애 뒤에도 남는다커밋 응답 전에 redo 로그(WAL)를 디스크에 확실히 내린다

원자성과 지속성은 같은 로그 체계에서 나온다. 데이터 페이지를 고치기 전에 무엇을 바꿀지 로그에 먼저 적고, 커밋할 때는 로그만 디스크에 내린다. 데이터 파일은 나중에 천천히 내려도 된다. 장애 뒤에는 로그를 보고 커밋된 것은 다시 하고(redo), 커밋되지 않은 것은 되돌린다. 왜 이 방식이 빠르고 안전한지는 로그와 지속성에서 다룬다.

세이브포인트는 안쪽 일부만 되돌린다

BEGIN;
UPDATE character SET gold = gold - 1000 WHERE id = 1001;
SAVEPOINT before_bonus;
INSERT INTO mail (receiver, item_id) VALUES (1001, 501);  -- 우편함이 가득 차 실패
ROLLBACK TO SAVEPOINT before_bonus;                     -- 우편만 취소
COMMIT;                                                  -- 골드 차감은 확정

세이브포인트는 트랜잭션 안에 되돌아갈 지점을 찍어 둔다. 그 지점 뒤의 변경만 취소하고 트랜잭션은 이어 간다. 중첩 트랜잭션과는 다르다. 세이브포인트까지 되돌린 뒤에도 바깥 트랜잭션이 커밋돼야 무엇이든 확정된다. SQL Server는 SAVE TRANSACTION을 쓰고, 안에서 다시 부르는 BEGIN TRANSACTION은 새 트랜잭션이 아니라 @@TRANCOUNT 숫자만 올린다. 안쪽 ROLLBACK은 바깥까지 전부 되돌린다.

트랜잭션은 짧게 둔다

트랜잭션이 열려 있는 동안 비용이 계속 쌓인다.

  • 잡은 락을 계속 쥐고 있다. 같은 행을 원하는 다른 요청이 그동안 줄을 선다(동시성 제어와 데드락).
  • 옛 버전을 치우지 못한다. MVCC는 열려 있는 가장 오래된 트랜잭션이 볼 수 있는 버전을 지우지 못한다. 몇 분짜리 트랜잭션 하나가 DB 전체의 정리를 막는다.
  • 커넥션을 붙잡는다. 트랜잭션 하나에 커넥션 하나가 묶인다. 열려 있는 트랜잭션이 많으면 풀이 바닥난다.

그래서 트랜잭션 안에서는 DB 일만 한다. 외부 HTTP 호출, 다른 서버의 응답 기다리기, 사용자 확인 기다리기는 트랜잭션 밖으로 뺀다. 필요한 값은 미리 읽고 계산해 두고, 트랜잭션은 쓰기만 짧게 묶는다.

DDL은 엔진마다 다르게 묶인다

MySQL에서 CREATE TABLE, ALTER TABLE 같은 DDL은 실행 직전에 열려 있던 트랜잭션을 암묵적으로 커밋하고 그 자체도 바로 확정된다. 롤백을 기대하고 실행하면 되돌릴 수 없다. PostgreSQL은 대부분의 DDL을 트랜잭션 안에서 실행하고 롤백할 수 있다. SQL Server도 대부분의 DDL이 트랜잭션에 묶인다. 스키마 변경 절차를 엔진마다 따로 확인해야 하는 이유다(스키마 마이그레이션).

게임 서버에서는

  • 주고받는 것은 한 트랜잭션에 넣는다. 거래는 양쪽 인벤토리와 골드, 거래 로그까지 한 트랜잭션이다. 우편 수령도 "우편 수령 표시"와 "아이템 지급"을 한 트랜잭션에 넣는다. 둘을 따로 커밋하면 사이에서 서버가 죽었을 때 우편은 남고 아이템도 받은 상태, 혹은 우편은 사라지고 아이템은 못 받은 상태가 된다.
  • 같은 요청이 두 번 와도 한 번만 지급한다. 클라이언트 재전송, 결제 콜백 재시도, 서버의 타임아웃 재시도로 같은 지급 요청이 두 번 올 수 있다. 롤백은 이것을 막아 주지 못한다. 거래 ID나 주문 ID를 유니크 키로 기록하고, 두 번째 삽입이 키 충돌로 실패하면 이미 처리된 요청으로 본다(멱등 소비자).
  • 롤백은 DB 밖의 일을 되돌리지 않는다. 트랜잭션 안에서 다른 서버로 메시지를 보냈거나 클라이언트에 결과를 보냈다면, 롤백해도 그것은 이미 나갔다. 외부로 알리는 일은 커밋 뒤에 하고, 반드시 나가야 하는 알림은 같은 트랜잭션에 이벤트 행으로 적어 두었다가 따로 보낸다(트랜잭셔널 아웃박스).
  • DB가 다르면 한 트랜잭션이 아니다. 게임 DB와 로그 DB, 서로 다른 샤드에 걸친 변경은 하나의 COMMIT으로 묶이지 않는다(DB 확장: 복제와 샤딩). 이때는 보상 단계를 둔 사가로 설계한다(사가).

C# 서버에서는 커넥션의 트랜잭션 객체를 직접 다루는 방식이 가장 예측하기 쉽다.

await using var conn = new MySqlConnection(connString);
await conn.OpenAsync(ct);
await using var tx = await conn.BeginTransactionAsync(ct);

int moved = await conn.ExecuteAsync(       // Dapper
    "UPDATE inventory SET owner_id = @to WHERE item_id = @item AND owner_id = @from",
    new { to, item, from }, tx);
if (moved == 0) { await tx.RollbackAsync(ct); return TradeResult.ItemGone; }

int paid = await conn.ExecuteAsync(
    "UPDATE character SET gold = gold - @price WHERE id = @to AND gold >= @price",
    new { to, price }, tx);
if (paid == 0) { await tx.RollbackAsync(ct); return TradeResult.NotEnoughGold; }

await conn.ExecuteAsync("UPDATE character SET gold = gold + @price WHERE id = @from",
    new { from, price }, tx);
await tx.CommitAsync(ct);
// 커밋하지 않고 tx가 Dispose되면 롤백된다
  • 모든 명령에 같은 트랜잭션을 넘긴다. 같은 커넥션이라도 명령에 트랜잭션을 지정하지 않으면 드라이버에 따라 오류가 나거나 의도와 다르게 동작한다.
  • TransactionScope는 async에서 옵션이 필요하다. TransactionScopeAsyncFlowOption.Enabled를 주지 않으면 await 뒤 다른 스레드로 이어질 때 앰비언트 트랜잭션이 따라가지 않는다(async/await 기초). 스코프 안에서 커넥션을 둘 이상 열면 분산 트랜잭션으로 승격하려 하는데, .NET에서는 7부터 Windows에서만 지원한다. 서버 코드에서는 피한다.
  • EF Core의 SaveChanges는 그 자체로 트랜잭션이다. 한 번의 SaveChanges로 모은 변경은 한 트랜잭션에 들어간다. 여러 번 나눠 부르면서 묶으려면 Database.BeginTransactionAsync로 감싼다.

주의 사항

  • MySQL에서 오류는 트랜잭션을 끝내지 않는다. 실패한 문장만 되돌아가고 트랜잭션은 열린 채다. 예외를 잡았으면 반드시 롤백한다.
  • 열어 두고 잊은 트랜잭션이 가장 위험하다. 예외 경로에서 커밋도 롤백도 하지 않은 커넥션이 풀로 돌아가면, 락과 옛 버전이 그대로 남는다. using으로 수명을 묶는다.
  • 트랜잭션은 같은 요청의 두 번 처리를 막지 않는다. 원자성은 한 번의 실행 안에서만 성립한다. 재시도와 중복 요청은 유니크 키로 막는다.
  • 격리성은 켜고 끄는 값이 아니다. 트랜잭션을 썼다고 다른 트랜잭션의 간섭이 모두 사라지지 않는다. 무엇이 허용되는지는 격리 수준이 정한다(격리 수준과 MVCC).
