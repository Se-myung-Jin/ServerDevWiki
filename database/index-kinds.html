먼저 읽을 것: 인덱스가 빠른 이유와 대가

핵심 요약

클러스터드 인덱스는 행 자체를 키 순서로 저장한다. 인덱스의 잎이 곧 데이터라서 찾으면 거기서 끝나고, 데이터를 두 가지 순서로 동시에 놓을 수 없으니 테이블당 하나뿐이다. 논클러스터드(보조) 인덱스는 키와 행을 찾아갈 위치만 담는다. 여러 개 만들 수 있지만 찾은 뒤 원본을 한 번 더 읽어야 한다.

이 차이가 설계를 정한다. 기본 키를 무엇으로 할지, 복합 인덱스의 컬럼을 어떤 순서로 둘지, 원본을 다시 읽지 않도록 컬럼을 인덱스에 얹을지가 모두 여기서 나온다.

범위 읽기에서 차이가 크다. 클러스터드 인덱스로 character_id 1000~2000을 읽으면 이웃한 페이지를 차례로 읽는다. 보조 인덱스로 같은 범위를 읽으면 잎은 이어져 있어도 가리키는 행은 테이블 곳곳에 흩어져 있다. 행마다 다른 페이지를 읽으러 간다.

무작위 키는 삽입 자리를 흩어 놓는다

클러스터드 인덱스는 키 순서대로 행을 놓으므로, 새 행이 들어갈 자리는 키 값이 정한다. 자동 증가 키라면 늘 맨 오른쪽 잎에 붙는다. 고치는 페이지가 하나라 버퍼 풀에 머물고, 꽉 차면 새 페이지를 이어 붙이면 된다.

무작위 UUID(v4)를 기본 키로 쓰면 새 행이 트리 아무 곳에나 들어간다. 그러면 세 가지가 나빠진다.

  • 들어갈 페이지가 꽉 차 있으면 페이지 분할이 일어난다. 반쯤 빈 페이지 둘이 남아 공간이 늘어난다.
  • 고치는 페이지가 매번 달라 버퍼 풀에 없는 페이지를 디스크에서 읽어 와야 한다. 테이블이 메모리보다 커지면 삽입 속도가 크게 떨어진다.
  • InnoDB에서는 16바이트 키가 모든 보조 인덱스에 복사된다.

해법은 순서가 있는 키다. 앞부분이 시각인 UUIDv7(RFC 9562)이나 Snowflake 계열 ID는 대체로 증가하므로 오른쪽 끝에 붙는다. 외부에 노출할 ID가 추측되면 안 된다면, 클러스터드 키는 순차 정수로 두고 무작위 공개 ID에 UNIQUE 보조 인덱스를 따로 건다. SQL Server의 NEWSEQUENTIALID()도 같은 목적이다. 다만 SQL Server는 uniqueidentifier를 마지막 바이트 묶음부터 비교하므로, C#에서 만든 UUIDv7을 그대로 넣으면 SQL Server 기준으로는 순서가 맞지 않는다. 엔진의 비교 순서에 맞춰 바이트를 배치해야 한다.

순차 키에도 약점은 있다. 모든 삽입이 오른쪽 끝 페이지 하나로 몰려 쓰기가 아주 많으면 그 페이지의 래치가 병목이 된다. SQL Server는 이것을 줄이려고 OPTIMIZE_FOR_SEQUENTIAL_KEY 옵션을 두었다.

복합 인덱스는 앞 컬럼부터 정렬된다

여기서 규칙 셋이 나온다.

  • 왼쪽 접두사만 쓸 수 있다. (a, b, c) 인덱스는 a, (a, b), (a, b, c) 조건에 쓰인다. b나 c만으로는 범위를 좁히지 못한다. MySQL 8.0의 스킵 스캔이나 PostgreSQL처럼 인덱스 전체를 훑는 경우가 있지만, a의 종류가 적을 때만 쓸 만하다.
  • 범위 조건 뒤의 컬럼은 정렬 효과를 잃는다. a = 1 AND b > 10 ORDER BY c라면 b 구간 안에서 c는 정렬돼 있지 않다.
  • 그래서 순서는 등호 → 정렬 → 범위다. 등호는 구간을 한 점으로 좁혀 그 뒤 컬럼의 정렬을 그대로 남긴다. 범위는 구간을 열어 뒤를 흩는다. WHERE guild_id = ? AND level >= ? ORDER BY last_login이라면 정렬을 피하는 (guild_id, last_login, level)과, 범위로 많이 거르는 (guild_id, level, last_login) 가운데 데이터 분포를 보고 고른다.

커버링 인덱스는 원본을 읽지 않는다

쿼리에 필요한 컬럼이 모두 인덱스 안에 있으면 원본 행을 읽으러 가지 않는다. 이것을 커버링 인덱스라 한다. 보조 인덱스의 약점인 두 번째 읽기가 사라진다. InnoDB 보조 인덱스에는 기본 키가 늘 들어 있으므로 기본 키 컬럼은 따로 넣지 않아도 커버된다. 

-- 캐릭터 목록 화면: 이름, 레벨, 직업만 필요하다
-- SQL Server, PostgreSQL 11+: 검색에 쓰지 않는 컬럼은 INCLUDE 로 잎에만 둔다
CREATE INDEX ix_char_account ON characters (account_id) INCLUDE (name, level, class_id);

-- MySQL 은 INCLUDE 가 없어 키 컬럼으로 덧붙인다
CREATE INDEX ix_char_account ON characters (account_id, name, level, class_id);

INCLUDE 컬럼은 중간 노드에 올라가지 않으므로 트리가 덜 커진다. 실행 계획에서 MySQL은 Using index, PostgreSQL은 Index Only Scan, SQL Server는 Key Lookup이 사라진 것으로 확인한다. PostgreSQL의 Index Only Scan은 가시성 맵이 최신이어야 원본을 건너뛴다. VACUUM이 밀려 있으면 이름만 Index Only이고 힙을 계속 읽는다.

선택 기준

무엇을 클러스터드 키로 둘 것인가

  • 짧고 바뀌지 않는 값. InnoDB에서는 모든 보조 인덱스에 복사된다.
  • 대체로 증가하는 값. 삽입이 오른쪽 끝에 몰려 분할과 무작위 읽기가 줄어든다.
  • 범위로 자주 읽는 순서. 한 캐릭터의 아이템을 늘 함께 읽는다면 (character_id, item_uid)를 클러스터드로 두는 것도 방법이다. 한 캐릭터의 아이템이 이웃한 페이지에 모인다.

게임 서버에서는

  • 인벤토리는 (character_id, slot) 순서로 묶는다. 로그인할 때 "이 캐릭터의 아이템 전부"를 읽고, 이동할 때 "이 캐릭터의 이 칸"을 찾는다. 둘 다 character_id가 등호로 앞에 온다. 같은 칸에 두 아이템이 있으면 안 되므로 이 조합에 UNIQUE를 걸면 동시에 같은 칸으로 옮기는 버그를 DB가 막아 준다. 
    CREATE UNIQUE INDEX ux_items_slot ON items (character_id, slot);
  • 랭킹 조회는 점수 내림차순 인덱스로 상위 N개만 읽는다. ORDER BY score DESC LIMIT 100은 (score DESC) 인덱스가 있으면 앞쪽 100개만 읽고 멈춘다. 다만 "내 순위가 몇 등인가"는 내 위까지 전부 세야 해서 인덱스로도 비싸다. 이 부분은 캐시의 정렬 집합이나 주기적인 순위 스냅샷으로 푼다(DB 앞의 캐시).
  • 로그 테이블은 시간으로 파티션을 나눈다. 날짜별이나 월별 파티션으로 나누면 "어제 이 캐릭터의 거래"는 해당 파티션만 읽고, 보관 기한이 지난 데이터는 DELETE 대신 파티션을 통째로 떼어 낸다. 수억 행을 DELETE하는 것보다 훨씬 싸고 로그도 거의 남기지 않는다(DB 확장).
  • 논리 삭제한 캐릭터는 이름 UNIQUE에서 빼야 한다. PostgreSQL과 SQL Server는 부분 인덱스로 살아 있는 행에만 UNIQUE를 건다. MySQL은 부분 인덱스가 없으므로, 삭제할 때 이름을 바꿔 두거나 살아 있을 때만 값이 있는 생성 컬럼에 UNIQUE를 건다. 
    -- PostgreSQL
CREATE UNIQUE INDEX ux_char_name_alive ON characters (name) WHERE deleted_at IS NULL;
  • EF Core를 쓰면 마이그레이션이 만드는 인덱스를 확인한다. 외래 키마다 인덱스가 자동으로 생기고, 복합 인덱스 순서는 직접 지정해야 한다. 생성된 SQL을 리뷰 대상에 넣는다.

주의 사항

  • 클러스터드 키를 나중에 바꾸면 테이블 전체를 다시 쓴다. 처음 정할 때 신중해야 한다.
  • "PK = 클러스터드"는 엔진마다 다르다. InnoDB는 늘 그렇고, SQL Server는 기본값일 뿐이고, PostgreSQL에는 클러스터드가 없다.
  • 복합 인덱스를 컬럼마다 따로 만든 단일 인덱스로 대신할 수 없다. 엔진이 둘을 합쳐 쓰는 경우가 있어도 복합 인덱스 하나보다 느리다.
  • 인덱스에 컬럼을 많이 얹으면 커버링은 되지만 쓰기가 무거워진다. 가장 자주 도는 쿼리에만 쓴다.
