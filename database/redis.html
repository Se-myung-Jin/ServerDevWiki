먼저 읽을 것: DB 앞의 캐시, 동시성 제어와 데드락

핵심 요약

Redis는 메모리에 자료구조를 두는 서버다. 명령은 스레드 하나가 차례로 실행한다. 그래서 명령 하나는 다른 명령과 섞이지 않고 원자적으로 끝난다. INCR 한 줄이 락 없는 카운터가 되고, ZADD 한 줄이 랭킹 갱신이 된다.

같은 성질이 약점도 된다. 오래 걸리는 명령 하나가 그동안 다른 모든 클라이언트를 세운다. 데이터는 기본적으로 메모리에 있고 복제는 비동기라, 원본으로 쓰면 잃을 수 있는 구간이 생긴다. 무엇을 Redis에 맡기고 무엇을 DB에 남길지가 설계의 대부분이다.

동작 원리

스레드 하나가 명령을 차례로 실행한다

막는 명령의 대표가 KEYS다. 모든 키를 한 번에 훑으므로 키가 많으면 수백 밀리초에서 초 단위로 서버가 멈춘다. 운영에서는 커서로 조금씩 나눠 훑는 SCAN을 쓴다. 원소가 수백만 개인 큰 해시나 정렬 집합을 HGETALL이나 DEL로 한 번에 다루는 것도 같다. 큰 키는 UNLINK로 지운다. 키를 먼저 떼어 내고 메모리 해제는 백그라운드 스레드에 넘긴다.

자료구조를 고르면 기능이 명령 하나가 된다

자료구조대표 명령게임 서버에서 쓰는 곳
StringINCR, SET ... NX EX카운터, 레이트 리밋, 락, 짧은 토큰
HashHSET, HINCRBY, HGET세션 정보, 캐릭터 요약(레벨, 위치한 서버)
Sorted SetZADD, ZRANGE ... REV, ZREVRANK랭킹, 점수순 매칭 대기열, 시각순 예약 작업
SetSADD, SISMEMBER, SCARD접속자 목록, 오늘 보상 받은 계정
ListLPUSH, RPOP, BLMOVE단순 작업 큐
StreamXADD, XREADGROUP, XACK처리 확인이 필요한 이벤트 큐

Sorted Set은 원소마다 점수(배정밀도 부동소수)를 붙여 정렬해 둔다. 넣기와 순위 조회가 모두 O(log N)이라 수백만 명 랭킹에서도 "내 순위"를 바로 답한다. 상위 N명은 ZRANGE key 0 N-1 REV로 가져온다. Redis 6.2부터는 이 형태가 권장되고, ZREVRANGE는 호환용으로 남아 있다.

여러 명령을 묶는 세 가지 방법

명령 하나는 원자적이지만, "읽고 판단해서 쓴다"를 두 명령으로 나누면 그 사이에 다른 클라이언트가 끼어든다. DB의 갱신 손실과 같은 문제다(동시성 제어와 데드락).

  • MULTI/EXEC는 모아서 한 번에 실행한다. 그 사이 다른 명령이 끼지 않는다. 하지만 롤백이 없다. 실행 중 한 명령이 타입 오류로 실패해도 나머지는 그대로 반영된다. 또 묶인 명령은 앞 명령의 결과를 보고 분기할 수 없다.
  • WATCH는 낙관적 락이다. 키를 지켜보다가 EXEC 전에 누가 그 키를 바꿨으면 트랜잭션 전체를 버리고 null을 돌려준다. 클라이언트가 처음부터 다시 시도한다. 버전 컬럼으로 하는 낙관적 락과 같은 모양이다.
  • Lua 스크립트는 서버에서 판단까지 한다. EVAL로 보낸 스크립트는 통째로 원자적으로 돈다. 읽고, 조건을 보고, 쓰는 것을 한 번에 할 수 있어 가장 많이 쓴다. Redis 7부터는 스크립트를 이름 붙여 서버에 등록해 두는 Functions(FUNCTION LOAD, FCALL)도 있다. 스크립트가 도는 동안 서버 전체가 멈추므로 짧게 쓴다.
-- 재화가 충분할 때만 차감한다. 읽기와 쓰기 사이에 끼어들 틈이 없다
local cur = tonumber(redis.call('HGET', KEYS[1], 'gold') or '0')
local cost = tonumber(ARGV[1])
if cur < cost then return -1 end
return redis.call('HINCRBY', KEYS[1], 'gold', -cost)

만료는 읽을 때와 주기적으로 지운다

TTL을 건 키는 시각이 되는 순간 지워지지 않는다. 두 길로 지운다. 누가 그 키를 읽으려 할 때 만료됐으면 그 자리에서 지운다(지연 삭제). 그리고 주기적으로 TTL이 있는 키를 표본으로 골라 만료된 것을 지운다. 그래서 만료된 키가 한동안 메모리를 차지할 수 있고, 같은 시각에 대량으로 만료되게 해 두면 그 정리가 한꺼번에 몰린다. TTL에 지터를 주는 이유는 DB 앞의 캐시에서 다룬다.

분산 락은 만료가 있어서 어렵다

서버 여러 대가 같은 일을 한 번만 하게 하려고 Redis로 락을 잡는다. 기본형은 키 하나다. 

SET lock:guild-war:17 <무작위 토큰> NX PX 30000   -- 없을 때만, 30초 뒤 자동 만료

-- 풀 때는 내 토큰일 때만 지운다(Lua로 한 번에)
if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
return 0

만료(PX)를 거는 이유는 락을 잡은 서버가 죽어도 영원히 잠기지 않게 하려는 것이다. 토큰을 확인하고 지우는 이유는, 내 락이 이미 만료되어 다른 서버가 잡은 뒤에 내가 그 락을 지우는 사고를 막으려는 것이다.

문제는 만료와 멈춤이 겹칠 때다. 락을 잡은 서버가 GC나 스왑으로 멈춘 사이 락이 만료되면(GC 모드와 멈춤), 다른 서버가 락을 잡는다. 멈췄던 서버는 깨어나서 자기가 아직 주인이라고 믿고 쓴다. 락만으로는 이 구간을 없앨 수 없다. 그래서 정확성이 걸린 곳에는 펜싱 토큰을 쓴다. 락을 잡을 때마다 증가하는 번호(INCR로 만들 수 있다)를 받고, 실제로 쓰는 저장소가 그 번호를 확인해 옛 번호의 쓰기를 거절한다.

Redis 여러 대의 과반에서 락을 잡는 Redlock은 Redis 한 대가 죽는 경우까지 견디려는 알고리즘이다. 이를 두고 Martin Kleppmann과 Redis 작성자 antirez 사이에 논쟁이 있었다. 비판의 요지는, 시계와 멈춤에 대한 가정이 깨지면 안전하지 않고 펜싱 토큰도 주지 않는다는 것이다. 실무 정리는 이렇다. 같은 일을 두 번 해도 손해가 작은 "효율용" 락이면 Redis 한 대의 락으로 충분하다. 두 번 하면 안 되는 "정확성용"이면 Redis 락에 기대지 말고, DB의 유니크 제약이나 조건부 갱신, 펜싱 토큰으로 막는다.

Pub/Sub은 흘려보내고 Streams는 남긴다

Pub/SubStreams
보관안 한다. 그 순간 구독 중인 쪽에만 보낸다로그로 남긴다. 길이나 ID로 잘라 낸다
끊겼던 구독자끊긴 동안의 메시지를 놓친다마지막으로 읽은 ID부터 이어 읽는다
나눠 받기모든 구독자가 같은 메시지를 받는다소비자 그룹 안에서 메시지를 하나씩 나눠 받는다
처리 확인없다XACK. 확인 안 된 것은 XPENDING으로 보고 XAUTOCLAIM으로 넘긴다
쓰는 곳놓쳐도 되는 알림(공지, 캐시 무효화 신호)놓치면 안 되는 작업(우편 발송, 보상 지급)

Streams도 확인 전에 소비자가 죽으면 다른 소비자가 다시 가져가므로 최소 한 번 전달이다. 받는 쪽은 같은 메시지를 두 번 받아도 괜찮게 짜야 한다(멱등 소비자). 본격적인 메시지 큐와의 비교는 메시지 모델에서 다룬다.

영속성: RDB 스냅숏과 AOF

  • RDB는 주기적인 스냅숏이다. Redis가 fork로 자식 프로세스를 만들고, 자식이 그 순간의 메모리를 파일로 쓴다. 부모와 자식은 처음에 메모리 페이지를 공유하다가, 부모가 고치는 페이지만 복사된다(쓸 때 복사, 가상 메모리). 쓰기가 많은 동안 스냅숏을 뜨면 복사되는 페이지가 늘어 메모리가 크게 오른다. 최대 두 배까지 잡아 두고 여유를 남긴다. 마지막 스냅숏 이후의 변경은 장애 때 잃는다.
  • AOF는 쓰기 명령을 로그로 남긴다. appendfsync everysec이 흔한 기본이다. 1초마다 디스크에 내리므로 장애 때 잃는 것은 대략 마지막 1초다. always는 명령마다 내려 안전하지만 느리다. 로그가 커지면 현재 상태로 다시 써서 줄인다(rewrite).
  • 둘을 함께 켜는 구성이 많다. 재시작할 때는 AOF로 복구하고, RDB는 백업과 복제 초기 동기화에 쓴다. DB의 로그 원리와 같은 맞바꿈이다(로그와 지속성).

복제, Sentinel, Cluster

복제는 비동기다. 주 서버가 응답한 쓰기가 복제본에 닿기 전에 주 서버가 죽으면 그 쓰기는 사라진다. WAIT로 복제본 몇 대가 받을 때까지 기다릴 수는 있지만, 그래도 장애 조치 중 유실이 없다고 보장하지는 않는다. Sentinel은 주 서버를 감시하다 죽으면 복제본을 올리는 장애 조치 담당이다.

Cluster는 데이터를 여러 주 서버에 나눈다. 키를 CRC16으로 해시해 16384개 해시 슬롯 가운데 하나에 넣고, 슬롯을 서버들이 나눠 맡는다. 여러 키를 한 명령이나 한 스크립트로 다루려면 그 키들이 같은 슬롯에 있어야 한다. 다르면 CROSSSLOT 오류가 난다. 키 이름에 중괄호를 쓰면 중괄호 안의 부분만 해시한다. {char:1001}:inv와 {char:1001}:gold는 같은 슬롯에 들어간다. 이것이 해시 태그다.

  • 핫 키: 모두가 읽는 키 하나(전체 랭킹, 이벤트 공지)는 한 서버에만 있어 그 서버만 바빠진다. 서버 로컬 캐시에 잠깐 들고 있거나, 키를 여러 벌로 나눠 둔다.
  • 큰 키: 원소 수백만 개짜리 키는 명령이 느리고, 슬롯 이동과 복제 때 한 덩어리로 움직이며, 메모리가 한 서버로 쏠린다. 시즌별, 구간별로 나눠 담는다.

2024년 Redis 7.4부터 라이선스가 소스 공개 라이선스로 바뀌었고, 이에 리눅스 재단 아래 오픈 소스 포크인 Valkey가 나왔다. Redis 8에는 AGPL이 선택지로 더해졌다. 명령과 프로토콜은 대부분 호환되므로 이 문서의 내용은 둘 다에 해당한다.

게임 서버에서는

  • 동점자 순서는 점수에 섞어 넣는다. 정렬 집합은 점수가 같으면 멤버 이름의 사전 순으로 놓는다. "먼저 달성한 사람이 위"를 원하면 점수와 시각을 하나로 합친다. 예를 들어 점수 × 2^22 + (2^22 − 1 − 시즌 시작 후 경과 초)로 두면 같은 점수에서는 먼저 달성한 쪽이 크다. 2^22초는 약 48일이라 시즌 길이가 그 안이어야 한다. 점수는 배정밀도라 합친 값이 2^53을 넘으면 정수가 정확하지 않으니, 점수 상한을 2^31 안으로 잡는다.
  • 중복 로그인은 키 하나로 막는다. 로그인할 때 SET session:{account} <서버ID:세션ID> EX 60으로 현재 세션을 적고, 접속 중인 서버가 주기적으로 TTL을 늘린다. 새 로그인이 다른 값을 보면 옛 서버에 끊으라고 알린다. 서버가 죽으면 TTL이 지나 자동으로 풀린다.
  • 서버 간 알림은 Pub/Sub, 놓치면 안 되면 Streams. "공지를 띄워라", "이 캐릭터 캐시를 지워라"는 Pub/Sub로 충분하다. 길드 전체 우편이나 보상 지급처럼 놓치면 민원이 되는 일은 Streams나 DB 큐로 보낸다.
  • 매칭 대기열은 정렬 집합으로 둔다. 점수에 MMR을 넣으면 ZRANGE ... BYSCORE로 비슷한 실력대를 꺼낸다. 꺼내고 지우는 것은 Lua로 묶어 두 매칭 서버가 같은 사람을 데려가지 않게 한다.
  • 레이트 리밋은 카운터와 TTL로 만든다. 계정별로 "1분에 채팅 30번"이면 INCR하고 첫 증가 때 EXPIRE를 건다. 두 명령 사이에 서버가 죽으면 만료 없는 키가 남으므로 Lua로 묶거나 SET key 0 EX 60 NX로 먼저 만든 뒤 증가시킨다.
  • StackExchange.Redis는 연결 하나를 공유한다. ConnectionMultiplexer는 스레드 안전하고 비싸게 만들어지므로 프로세스에 하나 두고 계속 쓴다. 요청마다 만들면 연결이 쌓인다. IDatabase는 가볍게 얻어 써도 된다. 비동기 메서드를 쓰면 명령이 자동으로 파이프라이닝되어, 여러 명령을 기다리지 않고 연달아 보낸다. BLPOP 같은 막는 명령은 공유 연결 전체를 묶으므로 이 클라이언트에서는 쓰지 않는다.
// 시작할 때 한 번 만들어 DI에 싱글턴으로 둔다
var mux = await ConnectionMultiplexer.ConnectAsync("redis:6379,abortConnect=false");
services.AddSingleton<IConnectionMultiplexer>(mux);

// 쓰는 쪽
IDatabase db = mux.GetDatabase();
await db.SortedSetAddAsync("rank:season7", charId, encodedScore);
long? rank = await db.SortedSetRankAsync("rank:season7", charId, Order.Descending);  // 0부터

주의 사항

  • 운영에서 KEYS와 큰 키 통째 조회를 쓰지 않는다. 실수로 한 번 부른 것이 전체 서버의 응답을 멈춘다. rename-command나 ACL로 막아 두는 곳도 많다.
  • 캐시가 아닌 데이터가 있으면 메모리 정책을 확인한다. allkeys-lru로 두면 메모리가 찼을 때 세션이나 랭킹도 지워진다. 원본을 담는 인스턴스와 캐시 인스턴스를 나누고, 원본 쪽은 noeviction으로 둔다.
  • Lua 스크립트와 MULTI를 길게 쓰지 않는다. 도는 동안 서버 전체가 멈춘다. 반복이 원소 수에 비례하면 큰 키에서 터진다.
  • Cluster로 옮길 계획이 있으면 처음부터 해시 태그를 고려한다. 한 명령에서 여러 키를 다루는 코드는 슬롯이 갈라지면 깨진다.
  • Redis 락을 정확성의 유일한 장치로 두지 않는다. 만료와 멈춤이 겹치면 주인이 둘이 된다. 아이템 지급처럼 두 번 되면 안 되는 일은 DB 제약으로 한 번 더 막는다.
