먼저 읽을 것: 트랜잭션과 ACID · 인덱스의 종류와 설계

핵심 요약

동시에 도는 트랜잭션을 완전히 한 줄로 세우면 이상한 일은 없지만 느리다. 격리 수준은 그 사이에서 어떤 이상 현상까지 허용할지 고르는 값이다. 엄격할수록 이상 현상이 줄고, 기다림과 재시도가 는다.

MVCC는 이 맞바꿈을 누그러뜨리는 장치다. 값을 덮어쓰지 않고 새 버전을 만들어 두면, 읽는 쪽은 자기 시점의 버전을 읽으면 되므로 쓰는 쪽을 기다리지 않는다. 다만 쓰기끼리의 충돌은 그대로 남고, 같은 이름의 격리 수준이 엔진마다 다른 것을 보장한다. 기본값만 믿고 쓰다 나는 버그가 여기서 나온다.

동작 원리

막아야 할 이상 현상

현상무엇이 일어나나게임 서버 예
더티 리드커밋되지 않은 값을 읽는다. 상대가 롤백하면 없던 값을 근거로 움직인 것이 된다롤백될 강화 성공 결과를 보고 랭킹에 올린다
반복 불가능 읽기같은 행을 두 번 읽었는데 값이 다르다. 사이에 누가 고치고 커밋했다정산 중 처음 읽은 골드와 나중에 읽은 골드가 다르다
팬텀같은 조건으로 두 번 조회했는데 행이 늘거나 줄었다. 사이에 누가 넣거나 지웠다"길드원 수"를 두 번 셌는데 결과가 다르다

SQL 표준은 수준을 이 세 현상만으로 정의한다. 그래서 표에는 갱신 손실과 쓰기 치우침이 없다. 실제 엔진은 MVCC로 격리를 구현하면서 표에 없는 동작을 더 막기도 하고 덜 막기도 한다. 표를 외우는 것보다 쓰는 엔진이 각 수준에서 실제로 무엇을 하는지 아는 쪽이 중요하다.

MVCC는 버전을 사슬로 남긴다

각 버전에는 만든 트랜잭션 번호가 붙는다. 읽기가 시작될 때 "어느 트랜잭션까지 커밋된 것이 보이나"를 담은 스냅샷을 잡고, 그 기준으로 버전을 고른다. 그래서 쓰는 쪽이 작업 중이어도 읽는 쪽은 기다리지 않고, 읽는 쪽 때문에 쓰는 쪽이 막히지도 않는다.

엔진옛 버전을 두는 곳치우는 작업
MySQL InnoDB행에는 최신 값만 두고 옛 값은 언두 로그에 남긴다퍼지(purge) 스레드가 더 이상 아무도 안 보는 언두를 지운다. 밀린 양은 history list length로 본다
PostgreSQL새 버전을 테이블 안에 새 행으로 쓰고 옛 행을 그대로 둔다VACUUM(보통 autovacuum)이 죽은 행을 치운다. 못 치우면 테이블이 부푼다(bloat)
SQL Server스냅샷 기능을 켰을 때만 버전을 남긴다. tempdb의 버전 저장소, 2019부터 가속 복구(ADR)를 켜면 DB 안의 버전 저장소백그라운드 정리 작업

스냅샷을 언제 잡느냐가 수준을 가른다. READ COMMITTED는 문장마다 새 스냅샷을 잡는다. 그래서 같은 트랜잭션 안에서도 두 번째 조회는 그사이 커밋된 값을 본다. REPEATABLE READ(PostgreSQL에서는 스냅샷 격리와 같다)는 트랜잭션의 첫 조회 때 잡은 스냅샷을 끝까지 쓴다.

엔진마다 기본값과 실제 동작이 다르다

엔진기본 수준알아 둘 차이
MySQL InnoDBREPEATABLE READ보통 조회는 스냅샷을 읽어 팬텀이 보이지 않는다. 잠그는 읽기(FOR UPDATE)와 UPDATE는 스냅샷이 아니라 최신 커밋 값을 읽고 넥스트 키 락을 건다. 스냅샷으로 읽고 애플리케이션에서 계산해 쓰면 갱신 손실을 막지 못한다
PostgreSQLREAD COMMITTEDREAD UNCOMMITTED를 지정해도 READ COMMITTED로 돈다. REPEATABLE READ에서는 팬텀이 없고, 같은 행을 다른 트랜잭션이 먼저 고쳤으면 직렬화 실패 오류로 끊어 갱신 손실을 막는다. SERIALIZABLE은 SSI로 쓰기 치우침까지 막는다
SQL ServerREAD COMMITTED기본은 공유 락으로 막는 방식이라 읽기가 쓰기를 기다린다. READ_COMMITTED_SNAPSHOT(RCSI)을 켜면 같은 이름이 버전을 읽는 방식으로 바뀐다. Azure SQL Database는 이것이 기본으로 켜져 있다. SNAPSHOT 수준은 따로 있다
OracleREAD COMMITTEDREAD UNCOMMITTED와 REPEATABLE READ가 없다. SERIALIZABLE은 있지만 실제로는 스냅샷 격리라 쓰기 치우침을 막지 못한다

SERIALIZABLE도 엔진마다 구현이 다르다. PostgreSQL은 SSI(직렬화 가능 스냅샷 격리)로, 잠그지 않고 진행하다가 직렬 실행으로 설명할 수 없는 의존 관계가 생기면 한쪽을 직렬화 실패로 끊는다. MySQL은 오토커밋이 꺼진 상태에서 보통 조회를 공유 락을 거는 읽기(FOR SHARE)로 바꾼다. SQL Server는 범위에 키 범위 락을 건다. 어느 쪽이든 직렬화 실패나 데드락으로 끊긴 트랜잭션을 처음부터 다시 하는 코드가 함께 있어야 한다.

인덱스가 락 범위를 정한다

InnoDB는 락을 행이 아니라 인덱스 레코드에 건다. 조건에 맞는 레코드를 인덱스로 바로 찾으면 그것만 잠그지만, 쓸 만한 인덱스가 없어 전체를 훑으면 훑은 레코드를 모두 잠근다. 결과로는 한 행만 고쳤는데 테이블 전체가 잠긴 것과 비슷해진다.

REPEATABLE READ에서 범위 조건으로 잠그면 찾은 레코드만이 아니라 그 사이 빈 구간까지 막는다. 레코드 사이 틈을 잠그는 것이 갭 락이고, 레코드 락과 그 앞 틈을 합친 것이 넥스트 키 락이다. 사이에 새 행이 들어오지 못하게 막아 잠그는 읽기에서도 팬텀을 막는다. 대신 아무도 같은 행을 건드리지 않는데도 틈이 겹쳐 서로 기다리고, 데드락이 생긴다. READ COMMITTED로 내리면 갭 락이 대부분 꺼진다(외래 키와 중복 키 검사는 남는다).

그래서 "인덱스를 안 걸었더니 데드락이 늘었다"는 일이 생긴다. 성능 문제로 보이지만 실제로는 락 범위 문제다. 무엇이 잠기는지 알려면 실행 계획에서 어느 인덱스를 탔는지 본다(실행 계획과 조인). MySQL 8.0은 performance_schema.data_locks로 지금 걸린 락을 볼 수 있다.

DB 전체 수준을 올리는 것은 마지막이다. 모든 트랜잭션이 비용을 내고, 재시도 코드가 모든 곳에 필요해진다. 수준은 트랜잭션마다 지정할 수 있으므로 필요한 트랜잭션만 올린다.

게임 서버에서는

  • MySQL 기본값에서 생기는 골드 갱신 손실. 서버가 SELECT gold로 읽고 C#에서 빼서 UPDATE ... SET gold = @newGold로 쓰면, REPEATABLE READ라도 동시에 온 두 요청 중 하나의 차감이 사라진다. SET gold = gold - @cost WHERE gold >= @cost처럼 DB가 최신 값으로 계산하게 한다.
  • 정원과 한정 수량은 쓰기 치우침이다. 길드 정원, 레이드 자리, 선착순 보상처럼 "개수를 세고 넣는" 로직은 스냅샷 격리에서 넘친다. 길드 행을 FOR UPDATE로 잠그고 세거나, 길드 행의 member_count를 조건부로 올려 충돌을 한 행에 모은다.
  • 긴 집계 트랜잭션이 DB 전체를 무겁게 한다. 랭킹 정산이나 통계 쿼리가 운영 DB에서 몇십 분 돌면, 그 스냅샷이 필요로 하는 옛 버전을 아무도 지우지 못한다. InnoDB의 history list length가 치솟고 모든 조회가 긴 사슬을 거슬러 가느라 느려진다. 집계는 복제본에서 돌리거나 짧게 나눈다(DB 확장: 복제와 샤딩).
  • SQL Server라면 RCSI를 검토한다. 기본 READ COMMITTED에서는 조회가 갱신의 락을 기다린다. 접속 피크에 캐릭터 조회가 저장 쿼리 뒤에 줄을 서는 일이 RCSI로 크게 준다. 대신 tempdb 버전 저장소 사용량을 지켜본다.
  • 재시도 대상 오류를 정해 둔다. 직렬화 실패(PostgreSQL SQLSTATE 40001), 데드락(MySQL 1213, PostgreSQL 40P01, SQL Server 1205), 스냅샷 갱신 충돌(SQL Server 3960)은 다시 하면 되는 정상 결과다.

주의 사항

  • 같은 이름이 같은 보장이 아니다. MySQL의 REPEATABLE READ와 PostgreSQL의 REPEATABLE READ는 갱신 손실을 다르게 다룬다. 엔진을 옮기거나 둘을 함께 쓰면 격리 가정을 다시 확인한다.
  • MVCC에도 락은 남는다. 풀리는 것은 읽기와 쓰기 사이다. 같은 행을 고치려는 쓰기끼리는 여전히 기다린다.
  • 스냅샷 읽기와 잠그는 읽기를 섞으면 헷갈린다. InnoDB에서 같은 트랜잭션 안의 SELECT와 SELECT ... FOR UPDATE는 서로 다른 값을 볼 수 있다. 하나는 스냅샷을, 하나는 최신 값을 본다.
  • 격리 수준 설정의 범위를 확인한다. 세션 단위로 바꾼 설정은 커넥션 풀에서 다시 빌린 연결에 남을 수 있다. 트랜잭션을 시작할 때 그 트랜잭션에만 지정하는 쪽이 안전하다.
