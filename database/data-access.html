먼저 읽을 것: 트랜잭션과 ACID, 동시성 제어와 데드락

핵심 요약

ORM은 객체와 테이블 사이를 대신 옮겨 준다. EF Core는 객체를 고치면 무엇이 바뀌었는지 추적해 SQL을 만들어 준다. Dapper는 직접 쓴 SQL의 결과를 객체에 채워 주기만 한다. 앞쪽은 덜 쓰고 더 감추고, 뒤쪽은 더 쓰고 덜 감춘다. 무엇을 고르든 어떤 SQL이 몇 번 나가는지는 개발자가 알고 있어야 한다.

게임 서버는 웹 서버와 저장 방식이 다르다. 캐릭터 상태는 서버 메모리에 있고 DB는 그 사본이다. 그래서 변경마다 저장하지 않는다. 바뀐 것만, 모아서, 정해진 때에 저장하고, 거래나 결제처럼 잃으면 안 되는 사건만 그 자리에서 트랜잭션으로 내린다.

변경 추적은 공짜가 아니다

EF Core는 조회한 엔티티마다 처음 값을 따로 기억해 둔다. SaveChanges 때 현재 값과 비교해 바뀐 컬럼을 찾는다. 이 변경 추적 덕분에 객체만 고치면 저장이 되지만, 조회한 행 수만큼 메모리와 비교 비용이 든다. 

// 읽기만 할 목록: 추적하지 않는다
var top = await db.Characters
    .AsNoTracking()
    .Where(c => c.WorldId == worldId)
    .OrderByDescending(c => c.Level)
    .Take(100)
    .Select(c => new RankRow(c.Id, c.Name, c.Level))   // 필요한 컬럼만
    .ToListAsync(ct);

읽기만 하는 조회는 AsNoTracking을 붙인다. 필요한 컬럼만 Select로 뽑으면 추적도 안 되고 읽는 양도 준다. 반대로 추적을 끈 객체를 고쳐도 SaveChanges는 아무것도 저장하지 않는다. 고칠 것은 추적하는 조회로 가져오거나 명시적으로 붙여 준다.

컨텍스트는 짧게, 커넥션은 더 짧게

DbContext는 일 하나 동안만 쓰고 버리는 객체다. 스레드에 안전하지 않아서, 같은 컨텍스트로 두 작업을 동시에 시작하면 예외가 난다. 오래 들고 있으면 추적 중인 엔티티가 계속 쌓이고 옛 값을 캐시처럼 돌려준다.

  • 범위가 있는 곳에서는 DI가 수명을 정한다. ASP.NET Core 요청마다 Scoped로 하나씩 받는다. 생성 비용이 신경 쓰이면 AddDbContextPool로 인스턴스를 재사용한다.
  • 범위가 없는 곳에서는 팩토리로 만든다. 게임 서버의 저장 작업자나 BackgroundService는 요청 범위가 없다. IDbContextFactory<T>를 받아 일 하나마다 CreateDbContextAsync로 만들고 await using으로 닫는다. Singleton이 Scoped를 붙잡는 함정은 Generic Host와 의존성 주입에서 다룬다.
  • 커넥션은 쿼리 직전에 열고 끝나면 바로 닫는다. 닫은 커넥션은 끊기지 않고 풀로 돌아간다. 쿼리 사이에 외부 API 호출이나 긴 계산을 끼우면 그동안 풀의 자리를 하나 차지한다. 풀이 바닥나면 다른 요청이 커넥션을 기다린다(DB 확장: 복제와 샤딩).

많이 바꿀 때는 한 번에 보낸다

객체를 하나씩 불러와 고치고 저장하면 행 수만큼 왕복이 생긴다. 조건으로 정할 수 있는 변경은 DB에서 한 문장으로 끝낸다. 

// EF Core 7+: 엔티티를 불러오지 않고 한 문장으로
await db.Mails
    .Where(m => m.ExpiresAt < now)
    .ExecuteDeleteAsync(ct);

await db.Characters
    .Where(c => c.GuildId == guildId)
    .ExecuteUpdateAsync(s => s.SetProperty(c => c.GuildId, (long?)null), ct);
  • ExecuteUpdate·ExecuteDelete는 변경 추적을 거치지 않는다. 바로 SQL로 나가고 곧바로 반영된다. 같은 컨텍스트가 그 행을 추적하고 있었다면 메모리의 값은 옛 값으로 남는다.
  • SaveChanges도 여러 문장을 묶어 보낸다. 변경이 수십 개면 왕복 몇 번으로 끝난다. 그래도 엔티티마다 추적 비용은 든다.
  • 수만 행을 넣을 때는 대량 적재 경로를 쓴다. SQL Server는 SqlBulkCopy, PostgreSQL은 COPY(Npgsql의 BeginBinaryImportAsync), MySQL은 MySqlConnector의 MySqlBulkCopy나 LOAD DATA다. 행 단위 INSERT보다 수십 배 빠르다. 게임 로그를 모아 넣을 때 쓴다.

관계를 따라가며 행마다 쿼리를 하나씩 더 보내는 N+1은 실행 계획과 조인에서 다룬다.

페이지를 넘길수록 느려지는 OFFSET

OFFSET n은 앞의 n개를 건너뛰는 것이 아니라 읽고 버린다. 랭킹 500페이지를 보여 주려면 만 개를 읽어야 한다. 그사이 새 행이 끼어들면 같은 행이 두 페이지에 나오거나 한 행이 빠지기도 한다.

키셋 페이지네이션(seek 방식)은 마지막으로 본 행의 정렬 키를 다음 요청의 조건으로 쓴다. 정렬 키가 겹칠 수 있으면 유일한 컬럼(id)을 뒤에 붙여 순서를 하나로 정한다. 인덱스는 정렬 순서와 같게 만든다(인덱스의 종류와 설계). 

-- PostgreSQL, MySQL 8: 행 값 비교
SELECT id, name, score FROM ranking
WHERE (score, id) < (@lastScore, @lastId)
ORDER BY score DESC, id DESC
LIMIT 20;

-- SQL Server: 행 값 비교가 없으므로 풀어 쓴다
SELECT TOP (20) id, name, score FROM ranking
WHERE score < @lastScore OR (score = @lastScore AND id < @lastId)
ORDER BY score DESC, id DESC;

키셋은 "37페이지로 바로 가기"를 못 한다. 다음·이전과 무한 스크롤에 맞다. 우편함, 거래소 목록, 로그 조회처럼 앞에서부터 넘겨 보는 화면이 여기에 해당한다.

자주 부르는 쿼리는 미리 번역해 둔다

EF Core는 LINQ 식을 SQL로 번역한 결과를 캐시하지만, 매번 식 트리를 만들고 캐시를 찾는 비용은 남는다. 로그인 때 캐릭터 불러오기처럼 아주 자주 부르는 쿼리는 EF.CompileAsyncQuery로 한 번만 번역해 둔다. 

static readonly Func<GameDb, long, Task<Character?>> LoadCharacter =
    EF.CompileAsyncQuery((GameDb db, long id) =>
        db.Characters.Include(c => c.Items).FirstOrDefault(c => c.Id == id));

게임 서버에서는

  • 바뀐 것만 저장한다. 캐릭터 객체가 바뀐 필드와 아이템 칸을 더티로 표시해 둔다. 저장할 때는 그 부분만 UPDATE한다. 캐릭터 전체를 매번 덮어쓰면 쓰기 양이 늘고, 다른 경로가 고친 컬럼을 옛 값으로 덮는다. 계산으로 다시 만들 수 있는 최종 스탯 같은 값은 저장 대상에서 뺀다(스탯과 버프 계산).
  • 모아서 저장한다. 몬스터를 잡을 때마다 경험치를 저장하면 접속자 수 × 초당 사냥 수만큼 쓰기가 생긴다. 일정 주기, 로그아웃, 존 이동, 서버 종료 때 모아 내린다. 주기는 "서버가 죽으면 몇 초를 잃어도 되는가"로 정한다.
  • 잃으면 안 되는 사건은 즉시 저장한다. 거래, 결제, 강화 결과, 희귀 아이템 획득은 그 자리에서 트랜잭션으로 내린다. 커밋을 확인한 뒤에 메모리와 클라이언트에 반영한다. 반영을 먼저 하면 저장이 실패했을 때 되돌릴 길이 없다.
  • 저장은 로직 스레드 밖에서 한다. 로직 스레드가 DB 응답을 기다리면 그동안 존 전체가 멈춘다. 저장 시점의 값을 복사해 큐에 넣고, 작업자 스레드가 쓰고, 결과는 다시 로직 스레드의 큐로 돌려받는다(게임 서버 스레딩 모델).
  • 저장에 버전을 붙인다. 저장 작업이 겹치거나 순서가 뒤바뀌면 오래된 스냅샷이 새것을 덮을 수 있다. 저장마다 증가하는 버전을 함께 보내고 WHERE version < @v로 늦게 도착한 옛 저장을 버린다(동시성 제어와 데드락). 존 이동 인계도 같은 버전을 쓴다(월드 분할).
  • 저장 실패를 처리하는 길을 정해 둔다. 일시적 오류는 지수 백오프로 재시도한다. 계속 실패하면 해당 캐릭터를 더 바뀌지 않게 잠그고, 스냅샷을 로컬 파일에 남기고, 경보를 띄운다. 실패를 로그만 남기고 넘기면 다음 접속 때 진행이 사라졌다는 문의로 돌아온다.

주의 사항

  • ORM이 만든 SQL을 한 번은 본다. EF Core의 LogTo나 ToQueryString으로 확인한다. 클라이언트 평가로 넘어간 부분이나 예상 밖의 조인은 로그로만 보인다.
  • 추적하는 컨텍스트에 오래된 값이 남는다. 같은 컨텍스트로 같은 행을 다시 조회하면 DB가 아니라 이미 추적 중인 객체가 돌아온다. 다른 곳에서 바뀐 값을 보려면 새 컨텍스트를 쓴다.
  • 지연 로딩을 켜지 않는다. 탐색 속성에 접근할 때마다 쿼리가 나가 N+1이 눈에 안 띄게 생긴다. 필요한 관계는 Include나 Select로 명시한다.
  • LINQ의 지연 실행이 커넥션 수명을 늘린다. IQueryable을 바깥으로 돌려주면 실제 쿼리는 열거하는 쪽에서 나간다. 그때 컨텍스트가 이미 닫혔으면 예외가 나고, 열려 있으면 생각보다 늦게 나간다(LINQ와 지연 실행).
  • 스키마 변경은 코드 배포와 순서를 맞춘다. 마이그레이션을 서버 시작 때 자동으로 돌리면 여러 서버가 동시에 돌리거나, 큰 테이블을 잠근 채 시작이 멈춘다. 운영에서는 따로 검토하고 따로 적용한다(스키마 마이그레이션).
