먼저 읽을 것: DB 확장: 복제와 샤딩 · 트라이와 블룸 필터

핵심 요약

DB 앞에 캐시를 두면 자주 읽는 값을 메모리에서 바로 돌려준다. 응답이 빨라지고 DB가 받는 읽기가 준다. 대신 같은 사실이 두 곳에 생긴다. DB와 캐시는 한 트랜잭션으로 함께 바뀌지 않으므로, 둘 사이가 어긋나는 순간이 반드시 있다. 어긋나면 에러 없이 조용히 틀린 값을 보여 준다.

그래서 캐시를 쓸 때 정할 것은 셋이다. 어느 쪽이 먼저 쓰이는지(읽기·쓰기 방식), 바뀌었을 때 캐시를 어떻게 버리는지(무효화), 많은 요청이 한꺼번에 캐시를 놓칠 때 DB를 어떻게 지키는지(스탬피드와 관통)다.

동작 원리

읽기와 쓰기를 누가 맡느냐로 네 가지가 갈린다

방식읽기쓰기잘 맞는 곳약한 점
캐시 어사이드(look-aside)응용이 캐시를 보고, 없으면 DB에서 읽어 채운다응용이 DB를 고치고 캐시 키를 지운다가장 흔한 기본형무효화를 응용이 빠뜨리기 쉽다
읽기 관통(read-through)캐시 라이브러리가 없으면 직접 로더를 불러 채운다어사이드와 같다로딩 로직을 한곳에 모을 때읽기 쪽만 바뀐다
쓰기 관통(write-through)캐시에서캐시에 쓰면 캐시가 DB에도 동기로 쓴다쓴 값을 곧바로 다시 읽는 곳쓰기마다 두 곳을 기다린다. 안 읽을 값도 캐시에 찬다
쓰기 뒤(write-behind)캐시에서캐시에만 쓰고 DB 반영은 나중에 모아서같은 값을 자주 고치는 곳DB에 닿기 전에 캐시가 죽으면 그 쓰기가 사라진다
 
// 캐시 어사이드. 읽기는 캐시 → DB, 쓰기는 DB → 캐시 삭제
public async Task<Guild> GetGuildAsync(long id)
{
    var key = $"guild:{id}";
    var cached = await _cache.GetAsync<Guild>(key);
    if (cached is not null) return cached;

    var guild = await _db.LoadGuildAsync(id);
    await _cache.SetAsync(key, guild, Ttl(TimeSpan.FromMinutes(5)));
    return guild;
}

public async Task RenameGuildAsync(long id, string name)
{
    await _db.UpdateGuildNameAsync(id, name);   // 먼저 DB
    await _cache.RemoveAsync($"guild:{id}");    // 그다음 캐시를 지운다
}

고치고 나서 지운다. 그래도 틈이 남는다

쓰기 때 캐시를 새 값으로 덮어쓰지 않고 지우는 이유가 있다. 두 요청이 동시에 같은 키를 고치면 DB 반영 순서와 캐시 반영 순서가 엇갈릴 수 있다. DB에는 B가 마지막인데 캐시에는 A가 마지막으로 남는다. 지우기만 하면 다음 읽기가 DB의 최신 값을 다시 가져오므로 이 엇갈림이 없다.

순서도 중요하다. 캐시를 먼저 지우고 DB를 고치면, 그 사이에 들어온 읽기가 아직 안 고친 DB 값을 캐시에 다시 채운다. 그 옛 값은 만료될 때까지 남는다. 그래서 DB를 고친 뒤 캐시를 지우는 순서가 표준이다. 다만 이 순서에도 드문 틈이 하나 남는다.

남은 틈을 줄이는 방법은 몇 가지가 있다. 삭제를 수백 ms 뒤에 한 번 더 하는 지연 이중 삭제, 값에 버전을 붙여 더 낮은 버전으로는 덮어쓰지 못하게 하는 방법, DB의 변경 로그(binlog, WAL)를 구독해 무효화를 한곳에서 내보내는 방법이다. 어느 것을 쓰든 TTL은 마지막 안전망으로 남긴다. 무효화를 빠뜨려도 옛 값이 영원히 남지는 않는다.

한꺼번에 놓치면 DB가 맞는다

인기 있는 키 하나가 만료되는 순간 수백 개 요청이 동시에 캐시를 놓치면, 전부 DB로 가서 같은 쿼리를 돌린다. 키 여러 개가 같은 TTL로 같은 시각에 채워졌다면 한꺼번에 만료된다. 이것이 캐시 스탬피드다. 막는 방법을 함께 쓴다.

방법무엇을 막나어떻게
TTL 지터여러 키의 동시 만료기본 TTL에 ±10~20% 무작위를 더한다(난수 생성)
단일 비행(single flight)한 키에 몰린 동시 로딩키마다 진행 중인 로딩 하나만 두고 나머지는 그 결과를 기다린다. 분산 환경에서는 짧은 분산 락
조기 갱신만료 순간의 공백만료 전에 확률적으로, 또는 남은 시간이 짧으면 한 요청이 미리 다시 채운다
만료된 값 잠깐 쓰기(stale-while-revalidate)로딩 중 대기새 값을 가져오는 동안 옛 값을 계속 돌려준다
 
// 한 프로세스 안의 단일 비행: 같은 키의 로딩은 Task 하나를 나눠 기다린다
private readonly ConcurrentDictionary<string, Lazy<Task<Guild>>> _inflight = new();

Task<Guild> LoadOnceAsync(string key, Func<Task<Guild>> load)
{
    var lazy = _inflight.GetOrAdd(key, _ => new Lazy<Task<Guild>>(async () =>
    {
        try { return await load(); }
        finally { _inflight.TryRemove(key, out _); }
    }));
    return lazy.Value;
}

.NET 9에 나온 HybridCache(Microsoft.Extensions.Caching.Hybrid)는 로컬 메모리와 원격 캐시를 두 층으로 묶고, 같은 키의 동시 로딩을 하나로 합치는 일을 기본으로 해 준다. 직접 만들기 전에 먼저 본다.

없는 키는 캐시를 뚫고 지나간다

존재하지 않는 키를 조회하면 캐시에 채울 것이 없으니 매번 DB까지 간다. 지운 캐릭터 ID를 계속 조회하는 버그나, 무작위 ID를 쏟아붓는 공격이 그렇다. 이것을 캐시 관통이라 한다. "없다"는 사실도 짧은 TTL로 캐시에 넣는 네거티브 캐시가 1차 대책이다. 없는 키의 종류가 너무 많으면 존재하는 키 집합을 블룸 필터에 담아 두고, 필터가 "없다"고 하면 캐시도 DB도 보지 않는다. 블룸 필터는 "없다"만 확실히 답한다.

캐시 서버 자체가 죽으면 그동안 캐시가 받던 읽기가 전부 DB로 온다. 평소 적중률이 95%였다면 DB 읽기가 스무 배로 뛴다. DB가 그것을 받을 수 없으면 캐시 장애가 곧 전체 장애다. 캐시가 없을 때는 요청 수를 제한하거나 일부 기능을 끄는 경로를 미리 둔다(서킷 브레이커).

로컬 캐시와 원격 캐시

구분로컬(프로세스 안 메모리)원격(Redis 등)
속도나노초~마이크로초. 직렬화도 없다네트워크 왕복 한 번(수백 μs~ms)
서버끼리 같은 값인가아니다. 서버마다 따로 만료된다그렇다. 모두 같은 키를 본다
무효화모든 서버에 알려야 한다(Pub/Sub 등)키 하나 지우면 끝난다
메모리서버마다 같은 값을 중복으로 든다. GC 부담한곳에 모인다
맞는 데이터기획 테이블, 거의 안 바뀌는 설정길드 정보, 프로필, 세션

Redis를 쓸 때 알아 둘 설정이 둘 있다. 메모리가 차면 무엇을 버릴지 정하는 maxmemory-policy는 기본이 noeviction이라, 캐시 용도라면 allkeys-lru나 allkeys-lfu로 바꾼다. 영속성(RDB 스냅숏, AOF)은 캐시로만 쓰면 꺼도 되지만, 랭킹이나 세션처럼 원본이 Redis에만 있다면 켜고 AOF를 appendfsync everysec로 둔다. 이때도 마지막 1초쯤은 잃을 수 있다(로그와 지속성).

돈, 재고, 한정 수량보여 주기에만 쓴다. 차감과 판정은 DB 트랜잭션에서초 단위 또는 무효화 필수

TTL은 "틀린 값을 얼마나 오래 보여 줘도 되는가"로 정한다. 짧으면 적중률이 떨어지고, 길면 어긋남이 오래 간다. 적중률과 DB 읽기 수를 지표로 남겨 조정한다.

게임 서버에서는

  • 세션 서버의 메모리가 이미 쓰기 뒤 캐시다. 접속 중인 캐릭터의 경험치, 골드, 인벤토리는 게임 서버 메모리가 원본처럼 들고 있고 DB에는 주기적으로, 또는 로그아웃·존 이동·거래 같은 순간에 저장한다. 서버가 죽으면 마지막 저장 뒤의 변경을 잃는다. 그래서 유료 재화와 거래는 즉시 DB에 쓰고, 경험치 같은 것은 주기 저장으로 둔다(세션 상태와 영속 상태).
  • 그 캐릭터를 가진 서버는 하나여야 한다. 같은 캐릭터를 두 서버가 메모리에 들고 각자 저장하면 나중에 저장한 쪽이 이긴다. 아이템이 복제되거나 사라진다. 캐릭터가 어느 서버에 있는지 한곳에서 정하고, 존 이동 때 소유권을 넘긴다(월드 분할).
  • 랭킹은 Redis 정렬 집합으로 만든다. ZADD로 점수를 넣고 ZREVRANGE로 상위 N명, ZREVRANK로 내 순위를 O(log N)에 얻는다. 동점자 순서는 점수에 달성 시각을 섞어 하나의 숫자로 만든다. 시즌이 끝나면 결과를 DB에 옮겨 둔다.
  • 기획 데이터는 로컬 캐시에 둔다. 모든 서버가 같은 테이블을 읽기 전용으로 들고, 바꿀 때는 통째로 교체한다(기획 데이터와 데이터 주도 설계). 원격 캐시에 둘 이유가 없다.
  • 점검 뒤에는 캐시가 비어 있다. 서버 오픈 순간 모든 플레이어가 동시에 로그인하면 빈 캐시 위로 스탬피드가 온다. 자주 쓰는 데이터를 미리 채우거나, 로그인 대기열로 유입 속도를 조절한다.

주의 사항

  • 캐시는 DB의 대신이 아니다. 캐시가 죽었을 때 DB가 혼자 버틸 수 있는지, 못 버티면 무엇을 끌지 정해 둔다.
  • 캐시에 넣은 객체를 고치지 않는다. 로컬 캐시는 참조를 그대로 돌려주므로, 꺼낸 객체를 고치면 캐시 안의 값도 바뀐다. 불변 객체로 두거나 복사해서 고친다(불변과 null 다루기).
  • 키에 버전을 넣는다. 값의 모양이 바뀌는 배포 뒤에 옛 형식이 캐시에 남아 역직렬화가 실패한다. guild:v2:{id}처럼 형식 버전을 키에 넣으면 배포와 함께 자연히 갈린다.
  • 큰 값 하나를 통째로 캐시하지 않는다. 길드원 500명 목록을 한 키에 넣으면 한 명만 바뀌어도 통째로 다시 만들고 보낸다. 자주 바뀌는 부분과 아닌 부분을 나눈다.
