먼저 읽을 것: 힙과 B-트리 · 메모리 계층 · SQL과 키

핵심 요약

인덱스는 테이블 옆에 정렬된 구조를 하나 더 두는 것이다. 원본 행은 그대로 두고, 찾을 컬럼의 값과 그 행의 위치를 정렬해 따로 유지한다. 정렬돼 있으니 처음부터 끝까지 훑지 않고 몇 단계만 내려가 원하는 범위에 닿는다.

공짜가 아니다. 행을 넣고 고치고 지울 때마다 그 구조도 함께 고쳐야 하고, 디스크와 메모리를 따로 쓴다. 인덱스는 읽기 성능을 쓰기 성능과 공간으로 사는 거래다. 어디에 걸지는 그 거래가 이득인지로 정한다.

동작 원리

줄여야 하는 것은 비교가 아니라 페이지 읽기다

DB는 데이터를 페이지 단위로 읽는다. InnoDB는 16KB, PostgreSQL과 SQL Server는 8KB다. 디스크든 버퍼 풀이든 한 페이지를 가져오는 비용이 그 안에서 키를 비교하는 비용보다 훨씬 크다(메모리 계층). 그래서 인덱스는 비교 횟수가 아니라 트리 높이를 줄이는 구조를 쓴다.

대부분의 엔진은 B+트리를 쓴다. B-트리와 달리 중간 노드에는 길잡이 키만 두고 실제 값은 모두 잎에 둔다. 중간 노드가 가벼워져 한 페이지에 키가 더 많이 들어가고, 가지가 많아질수록 높이는 더 낮아진다. 잎끼리 옆으로 이어져 있어 BETWEEN이나 ORDER BY 같은 범위 읽기는 시작점을 한 번 찾은 뒤 옆으로 훑으면 된다. 트리 자체의 삽입과 분할은 힙과 B-트리에서 다룬다.

해시 인덱스도 있다. 등호 조회는 한 번에 끝나지만 순서가 없어 범위 조회와 정렬에 쓸 수 없다. 그래서 범용 인덱스는 B+트리이고, 해시는 특수한 자리에만 쓴다(인덱스의 종류와 설계).

얼마나 걸러 내느냐가 효과를 정한다

카디널리티는 컬럼에 서로 다른 값이 몇 개 있느냐다. 선택도는 조건 하나가 전체 행 가운데 얼마를 고르느냐다. character_id = 42는 수백만 행 중 하나를 고르니 선택도가 아주 낮고 인덱스 효과가 크다. 성별이나 is_deleted처럼 값이 두세 개뿐인 컬럼은 조건 하나가 절반을 고르므로 거르는 효과가 거의 없다.

조건이 전체의 상당 부분을 고르면 옵티마이저는 인덱스를 버리고 전체 스캔을 고른다. 보조 인덱스로 찾으면 행마다 원본 페이지를 따로 읽으러 가야 한다. 이 무작위 읽기가 쌓이면 테이블을 처음부터 순서대로 읽는 편이 빠르다. 갈림점은 엔진과 데이터 배치에 따라 다르고, 대략 전체의 몇 퍼센트에서 수십 퍼센트 사이다. 이 판단은 통계에 기댄다(실행 계획과 조인).

읽기가 빨라진 만큼 쓰기가 느려진다

비용이 붙는 곳왜
INSERT인덱스마다 정렬된 자리를 찾아 키를 끼워 넣는다. 자리가 꽉 찬 페이지는 둘로 나눈다(페이지 분할)
UPDATE인덱스에 든 컬럼을 바꾸면 옛 키를 지우고 새 키를 넣는다. 인덱스에 없는 컬럼만 바꾸면 인덱스는 그대로다
DELETE인덱스마다 키를 지운다. 빈 공간은 바로 돌아오지 않고 페이지가 성기게 남는다
공간인덱스도 페이지를 쓴다. 인덱스가 여럿이면 원본보다 커지기도 한다
메모리자주 쓰는 인덱스 페이지가 버퍼 풀에 머물러야 빠르다. 인덱스가 늘면 데이터 페이지가 밀려난다
로그인덱스 변경도 로그에 적힌다(로그와 지속성)

인덱스가 다섯 개 걸린 테이블에 행 하나를 넣으면 원본 한 곳과 인덱스 다섯 곳을 고친다. 쓰기가 읽기보다 훨씬 많은 테이블은 인덱스를 늘릴수록 전체가 느려진다.

걸었는데 왜 안 타나

상황예왜 못 쓰나고치는 법
컬럼에 함수나 계산WHERE DATE(created_at) = '2026-10-01'인덱스는 created_at 순서로 정렬돼 있지 DATE() 결과 순서가 아니다범위로 바꾼다: created_at >= '2026-10-01' AND created_at < '2026-10-02'
앞에 와일드카드WHERE name LIKE '%검사'어디서 시작할지 정할 수 없다접두어 검색 '검사%'로 바꾸거나 전문 검색 인덱스
암시적 형변환VARCHAR 컬럼에 숫자 WHERE account_no = 12345컬럼 쪽이 변환되어 함수를 씌운 것과 같아진다넘기는 값의 타입을 컬럼에 맞춘다
낮은 선택도WHERE is_deleted = 0대부분의 행을 고른다다른 조건과 복합 인덱스로 묶거나 부분 인덱스
복합 인덱스의 앞 컬럼 누락(guild_id, level) 인덱스에 WHERE level = 60앞 컬럼 순서로 정렬돼 있어 범위를 좁히지 못한다컬럼 순서를 다시 잡는다(인덱스의 종류와 설계)
OR로 다른 컬럼 연결WHERE name = ? OR email = ?한 인덱스로 둘을 다 못 가린다UNION ALL로 나누거나, 엔진의 인덱스 병합에 맡긴다

암시적 형변환은 C# 서버에서 자주 생긴다. ADO.NET은 C# string을 기본으로 유니코드 문자열(SQL Server의 NVARCHAR)로 보낸다. 컬럼이 VARCHAR면 SQL Server는 컬럼 쪽을 NVARCHAR로 바꿔 비교하고, 데이터 정렬 규칙에 따라 인덱스 탐색이 스캔으로 바뀐다. Dapper에서는 DbString { IsAnsi = true }나 파라미터 타입 지정으로 맞춘다.

선택 기준

  • WHERE에 자주 오고 선택도가 낮은 컬럼이 먼저다.
  • 조인 조건 컬럼에 건다. 외래 키 컬럼은 엔진에 따라 자동으로 인덱스가 생기지 않는다. MySQL InnoDB는 만들어 주고, PostgreSQL과 SQL Server는 직접 만들어야 한다.
  • ORDER BY와 LIMIT이 붙는 컬럼에 걸면 정렬을 건너뛰고 앞쪽 몇 행만 읽고 멈춘다.
  • 쓰기가 압도적인 테이블은 꼭 필요한 것만 둔다. 로그 테이블이 대표적이다.
  • 한 쿼리를 위해 인덱스를 하나씩 만들지 않는다. 복합 인덱스 하나가 여러 쿼리를 받게 설계한다.

게임 서버에서는

  • 로그인 경로의 쿼리는 모두 인덱스로 끝나야 한다. 계정 조회, 캐릭터 목록, 인벤토리 읽기는 접속자 수만큼 몰린다. 서비스 시작이나 점검 후 몰릴 때 하나라도 전체 스캔이면 DB가 먼저 무너진다. 새 쿼리를 넣을 때 실행 계획을 확인하는 것을 절차로 둔다.
  • 로그 테이블은 인덱스를 아낀다. 초당 수천 건씩 쌓이는 아이템·재화 로그에 조회용 인덱스를 여럿 걸면 쓰기가 밀린다. 운영 조회는 따로 복제한 분석용 DB에서 하고, 원본에는 시간과 캐릭터 정도만 건다.
  • 안 쓰는 인덱스를 찾아 지운다. 기능이 바뀌면 그 쿼리를 위해 만든 인덱스가 남는다. PostgreSQL은 pg_stat_user_indexes, SQL Server는 sys.dm_db_index_usage_stats, MySQL은 sys.schema_unused_indexes로 사용 여부를 본다. 통계는 재시작하면 지워지므로 한 주기 이상 지켜본다.
  • 인덱스 추가도 운영 작업이다. 큰 테이블에 인덱스를 만들면 오래 걸리고 쓰기를 막을 수 있다. PostgreSQL의 CREATE INDEX CONCURRENTLY, MySQL의 온라인 DDL, SQL Server의 ONLINE = ON처럼 쓰기를 막지 않는 방식을 쓴다.

주의 사항

  • 인덱스를 걸면 늘 빨라지는 것이 아니다. 옵티마이저가 쓰기로 정해야 효과가 있고, 쓰기는 늘 느려진다.
  • 안 쓰는 인덱스는 순손해다. 쓰기 비용, 공간, 버퍼 풀 자리만 쓰고 돌려주는 것이 없다.
  • 개발 DB에서 빠른 쿼리가 운영에서 느릴 수 있다. 행이 몇백 개면 전체 스캔도 빠르다. 운영 규모의 데이터로 실행 계획을 본다.
  • 같은 앞부분을 가진 인덱스가 겹치지 않는지 본다. (a)와 (a, b)가 함께 있으면 (a)는 대개 필요 없다.
