먼저 읽을 것: 가상 함수와 다형성 · 컴파일과 링킹

핵심 요약

템플릿은 코드를 찍어 내는 틀이다. 정의만으로는 아무 기계어도 생기지 않고, Max<int>처럼 실제 타입으로 쓰이는 순간 그 타입 전용 코드가 만들어진다(인스턴스화). 타입이 컴파일 때 정해지므로 가상 함수와 달리 인라인과 최적화가 그대로 걸린다.

대가는 빌드다. 쓰는 쪽에서 코드를 만들어야 하니 정의가 헤더에 있어야 하고, 같은 실체를 파일마다 다시 만든다. 실행 파일도 커진다. 한편 constexpr은 계산 자체를 컴파일 때로 옮긴다. 조회표나 크기 계산처럼 입력이 고정된 일은 실행 중에 비용이 0이 된다.

동작 원리

쓰인 타입마다 실체가 만들어진다

컴파일러는 Max(3, 4)를 만나면 T를 int로 바꿔 넣은 함수를 만든다. 이 일은 쓰는 쪽 소스 파일 안에서 일어나므로 정의 전체가 보여야 한다. 템플릿 정의를 헤더에 두는 이유다. .cpp에 숨겨 두면 그 파일 밖에서는 실체를 만들 수 없어 링크 오류가 난다.

실체 수는 쓰인 타입 수에 비례한다. 템플릿 하나를 열 가지 타입으로 쓰면 비슷한 기계어가 열 벌 생긴다. 실행 파일이 커지고, 뜨거운 코드가 명령 캐시에 덜 들어간다. 이것이 빌드 시간에 어떻게 쌓이는지, extern template으로 실체를 한 파일에만 만들게 하는 방법은 빌드 시간에서 다룬다.

특정 타입에는 다른 정의를 둔다

방법무엇인가쓸 수 있는 곳
완전 특수화타입 하나에만 다른 정의. template<> struct Hash<PlayerId>클래스 템플릿, 함수 템플릿
부분 특수화조건에 맞는 타입 묶음에 다른 정의. 모든 포인터 타입 Wrapper<T*>클래스 템플릿만
오버로딩함수 템플릿을 하나 더 둔다함수 템플릿의 부분 특수화 대신

표준 라이브러리의 타입 특성(<type_traits>)이 이 장치로 만들어져 있다. std::is_trivially_copyable_v<T>는 타입마다 특수화된 상수라, 컴파일 때 "이 타입을 바이트 복사해도 되나"를 물어볼 수 있다(객체 배치와 타입 특성).

조건 거르기: SFINAE에서 concept로

템플릿에 아무 타입이나 넣으면 본문 깊은 곳에서 "이 타입에는 <가 없다"는 오류가 수백 줄로 나온다. C++20 이전에는 조건에 맞지 않는 후보를 조용히 빼는 규칙(SFINAE, 치환 실패는 오류가 아니다)을 이용해 걸렀다. 동작은 하지만 읽기 어렵다. 

// C++17까지: 반환 타입 자리에 조건을 숨긴다
template<class T>
std::enable_if_t<std::is_integral_v<T>, T> Clamp(T v, T lo, T hi);

// C++20: 요구 조건에 이름을 붙여 앞에 적는다
template<class T>
concept Integral = std::is_integral_v<T>;

template<Integral T>
T Clamp(T v, T lo, T hi);   // Clamp(1.5, 0.0, 1.0) → "Integral을 만족하지 않는다"

concept는 템플릿이 타입에 요구하는 것을 선언에 드러낸다. 조건에 맞지 않으면 어느 조건이 깨졌는지 짧게 알려 주고, 같은 이름의 템플릿 여럿 가운데 조건이 더 구체적인 쪽을 고르는 데도 쓰인다.

if constexpr은 고르지 않은 갈래를 버린다

template<class T>
void Write(Buffer& buf, const T& v) {
    if constexpr (std::is_trivially_copyable_v<T>) {
        buf.Append(&v, sizeof(T));      // 위치, 체력 같은 단순 구조체: 바이트 그대로
    } else {
        v.Serialize(buf);              // 문자열, 컨테이너를 가진 타입: 직접 직렬화
    }
}

조건이 컴파일 때 정해지므로 고르지 않은 갈래는 아예 실체를 만들지 않는다. int로 쓰면 v.Serialize 줄은 컴파일되지 않아서, int에 그런 멤버가 없어도 오류가 아니다. 타입마다 오버로딩을 나누거나 태그 타입을 넘기던 코드를 함수 하나 안의 조건문으로 바꿀 수 있다. 일반 if였다면 두 갈래가 모두 컴파일되어 오류가 난다.

CRTP는 가상 함수 없이 다형성을 낸다

template<class Derived>
struct System {
    void Tick() { static_cast<Derived*>(this)->Update(); }   // 컴파일 때 정해지는 호출
};
struct MoveSystem : System<MoveSystem> { void Update(); };

기반 클래스가 파생 클래스를 템플릿 인자로 받아, 자기 this를 파생 타입으로 바꿔 부른다. 호출할 함수가 컴파일 때 정해지므로 vtable이 없고 인라인이 된다. 대신 System<MoveSystem>과 System<AiSystem>은 서로 다른 타입이라 한 배열에 담을 수 없다. 실행 중에 타입을 바꿔 끼워야 하면 여전히 가상 함수가 필요하다.

constexpr은 계산을 컴파일 때로 옮긴다

키워드뜻쓰는 곳
const초기화한 뒤 바꾸지 않는다. 값은 실행 중에 정해져도 된다읽기 전용 매개변수와 변수(const와 참조)
constexpr 변수값이 컴파일 때 정해져야 한다배열 크기, 템플릿 인자, 조회표
constexpr 함수상수가 필요한 자리에서 부르면 컴파일 때 계산되고, 아니면 보통 함수로 돈다두 용도로 함께 쓰는 계산 함수
consteval (C++20)반드시 컴파일 때 계산된다. 실행 중에 부르면 오류절대 실행 중에 돌면 안 되는 계산(문자열 해시 ID 등)
constinit (C++20)전역·정적 변수가 프로그램 시작 전에 상수로 초기화됨을 보장한다. 값은 나중에 바꿀 수 있다전역 객체끼리 초기화 순서가 꼬이는 문제를 막을 때
 
constexpr std::array<uint32_t, 256> MakeCrcTable() {
    std::array<uint32_t, 256> t{};
    for (uint32_t i = 0; i < 256; ++i) {
        uint32_t c = i;
        for (int k = 0; k < 8; ++k) c = (c & 1) ? 0xEDB88320u ^ (c >> 1) : c >> 1;
        t[i] = c;
    }
    return t;
}
constexpr auto kCrcTable = MakeCrcTable();   // constexpr 변수라 컴파일 때 계산된다

constexpr 함수는 "컴파일 때 계산할 수 있다"는 허락이지 명령이 아니다. 결과를 일반 변수에 받으면 컴파일러는 실행 중에 계산해도 된다. 반드시 컴파일 때 끝내려면 위처럼 constexpr 변수로 받거나 consteval로 선언한다.

선택 기준

상황맞는 쪽이유
타입이 컴파일 때 정해지고 성능이 중요하다템플릿인라인과 최적화가 걸린다
타입이 실행 중에 정해진다가상 함수템플릿은 실행 중에 타입을 바꿀 수 없다
라이브러리 경계 너머로 내보낸다가상 함수(인터페이스)템플릿은 정의를 헤더로 내보내야 한다
실행 파일 크기나 빌드 시간이 문제다타입과 상관없는 부분을 비템플릿 함수로 뺀다타입마다 생기는 코드를 줄인다
서로 다른 타입을 한 컨테이너에 담아 같은 방식으로 부른다std::function 같은 타입 지우기, 또는 가상 함수내부는 간접 호출이라 비용은 가상 함수와 비슷하다

게임 서버에서는

  • 직렬화와 패킷 등록을 템플릿으로 묶는다. 위의 Write처럼 타입 특성으로 바이트 복사와 직접 직렬화를 가르고, 패킷 타입마다 static constexpr uint16_t kId를 두어 처리기 표를 컴파일 때 만든다. 같은 ID가 둘이면 static_assert로 빌드를 실패시킬 수 있다.
  • 고정된 표는 constexpr로 만든다. 레벨별 필요 경험치, CRC 표, 문자열 이름을 해시한 ID처럼 입력이 바뀌지 않는 값은 서버가 뜰 때 계산할 이유가 없다. 기획 데이터처럼 배포 없이 바뀌어야 하는 값은 반대로 파일로 뺀다.
  • 템플릿 코드가 커지면 공통 부분을 뺀다. 컨테이너나 처리기 템플릿 안에서 타입과 상관없는 로직(로그, 검증, 버퍼 관리)까지 모두 템플릿 안에 두면, 타입 수만큼 같은 코드가 복제된다. 그 부분을 일반 함수로 빼 두면 빌드와 실행 파일이 함께 준다.
  • C# 제네릭은 만드는 시점과 방식이 다르다. C#은 제네릭을 중간 언어 하나로 컴파일하고, 실제 코드는 실행 중에 JIT가 만든다. 값 타입(List<int>, List<Vector3>)마다는 전용 코드를 만들어 C++ 템플릿처럼 빠르고, 참조 타입은 모두 코드 한 벌을 나눠 쓴다. 제약은 where T : struct나 .NET 7의 INumber<T>(인터페이스의 정적 추상 멤버)로 적는다. C++의 constexpr 같은 컴파일 시점 계산은 없어서, C# const는 숫자·문자열 같은 기본 값만 담고, 표를 미리 만드는 일은 소스 제너레이터가 맡는다(제네릭, 인라인과 코드 생성).

주의 사항

  • constexpr을 붙였다고 컴파일 때 계산되는 것은 아니다. 상수가 필요한 자리에서 쓰일 때만 그렇다. 확실히 하려면 constexpr 변수로 받거나 consteval을 쓴다.
  • 템플릿 정의를 .cpp에 두면 링크가 깨진다. 다른 파일이 실체를 만들지 못해 "정의되지 않은 참조" 오류가 난다. 정의를 헤더에 두거나, 쓰일 타입을 한 파일에서 명시적으로 인스턴스화한다.
  • 타입에 기대는 이름에는 typename을 붙인다. 템플릿 안에서 T::iterator가 타입인지 값인지 컴파일러가 정의를 보기 전에는 모른다. 타입이면 typename T::iterator로 알려 준다.
  • 템플릿으로 다 해결하려 하지 않는다. 컴파일 시점 계산이 깊어지면 오류 메시지와 빌드 시간이 사람이 감당하기 어려워진다. 실행 중에 한 번 계산해도 되는 일은 그냥 실행 중에 한다.
