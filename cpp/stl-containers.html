먼저 읽을 것: 템플릿과 컴파일 시점 계산 · 배열과 연결 리스트 · 해시 테이블

핵심 요약

컨테이너를 고르는 첫 갈림길은 원소를 연속 메모리에 놓느냐, 노드로 흩어 두느냐다. 연속이면 순회가 빠르고 메모리를 적게 쓴다. 노드면 중간 삽입·삭제가 싸고 원소 주소가 바뀌지 않는다. 두 번째 갈림길은 키로 찾을 때 정렬된 순서가 필요하냐다. 필요하면 트리(map), 아니면 해시(unordered_map)다.

기본값은 vector다. 복잡도 표만 보면 다른 컨테이너가 유리해 보이는 자리에서도, 원소 수가 수천 개 이하라면 캐시 덕에 vector가 이기는 경우가 많다. 원리는 자료구조 분야에서 다뤘고, 여기서는 표준 라이브러리 컨테이너가 실제로 어떻게 생겼는지를 본다.

동작 원리

시퀀스 컨테이너는 메모리 모양이 다르다

컨테이너저장임의 접근끝 삽입앞 삽입중간 삽입·삭제
array고정 크기 연속(크기가 타입의 일부)O(1)크기를 바꿀 수 없다
vector연속, 여분 용량O(1)상환 O(1)O(n)O(n), 뒤 원소를 민다
deque고정 크기 블록 여러 개O(1), 블록 목록을 한 번 더 거친다O(1)O(1)O(n)
list이중 연결 노드불가O(1)O(1)위치를 알면 O(1)
forward_list단일 연결 노드불가불가(끝을 모른다)O(1)앞 노드를 알면 O(1)

list의 "중간 삽입 O(1)"은 위치를 이미 쥐고 있을 때 이야기다. 위치를 찾으려면 노드를 하나씩 따라가야 하고, 노드가 힙 곳곳에 흩어져 있어 따라갈 때마다 캐시 미스가 난다. 원소 하나에 포인터 두 개와 할당 머리 정보까지 붙어 메모리도 몇 배를 쓴다. 왜 연속 배열이 흔히 이기는지는 배열과 연결 리스트에서 다뤘다.

deque의 블록 크기는 구현마다 다르다. libstdc++(GCC)는 512바이트 블록을 쓰지만, MSVC는 16바이트 블록이라 원소가 8바이트를 넘으면 블록 하나에 원소가 하나뿐이다. 그러면 사실상 노드 기반과 비슷해진다. 같은 코드가 플랫폼에 따라 성능이 크게 달라지는 자리다.

vector는 늘어날 때 통째로 옮긴다

용량이 차면 더 큰 배열을 새로 받아 원소를 모두 옮기고 옛 배열을 버린다. 늘리는 배율은 규격이 정하지 않는다. libstdc++와 libc++는 2배, MSVC는 1.5배다. 배율이 일정하니 끝 삽입은 평균 O(1)이지만, 옮기는 그 한 번은 원소 수만큼 걸리고 메모리를 잠깐 두 벌 쓴다.

함수하는 일
reserve(n)용량만 n 이상으로 늘린다. 원소 수(size)는 그대로다. 개수를 대략 알면 미리 불러 재할당을 없앤다
resize(n)원소 수를 n으로 맞춘다. 늘어나면 새 원소를 기본값으로 만든다
shrink_to_fit()남는 용량을 돌려 달라는 요청이다. 구현이 무시해도 된다
clear()원소를 모두 파괴하지만 용량은 남긴다. 같은 vector를 틱마다 다시 쓰면 할당이 없다

옮길 때 원소를 복사할지 이동할지는 원소 타입의 이동 생성자가 noexcept인지로 갈린다. 이동 도중 예외가 나면 원래 상태로 되돌릴 수 없어서, 예외 가능성이 있으면 느려도 복사를 고른다(이동 시맨틱). 재할당이 일어나면 원소 주소가 모두 바뀌어, 들고 있던 포인터와 반복자가 쓸 수 없게 된다(반복자 무효화).

emplace_back(args...)는 인자를 받아 컨테이너 안의 자리에서 바로 원소를 만든다. push_back(T(args...))은 임시 객체를 만든 뒤 옮긴다. 이미 만들어진 객체를 넣는다면 둘은 같다. 차이가 나는 것은 생성자 인자를 넘길 때뿐이고, emplace는 explicit 생성자도 조용히 불러 버리므로 의도하지 않은 변환을 놓칠 수 있다. 인자를 그대로 넘기는 원리는 전달 참조와 완벽 전달에서 다룬다.

vector<bool>은 예외다. 원소를 비트 하나로 압축해 담아, v[i]가 bool&이 아니라 비트를 대신 가리키는 프록시 객체를 돌려준다. bool*로 원소를 가리킬 수 없고 여러 스레드가 다른 원소를 동시에 써도 같은 바이트를 건드린다. 비트 집합이 필요하면 std::bitset이나 vector<uint8_t>를 쓴다.

키로 찾는 컨테이너는 노드 기반이다

컨테이너구조순서조회특징
map, set레드-블랙 트리(사실상 모든 구현)키 정렬O(log n)범위 조회(lower_bound), 정렬 순회. 원소마다 노드
unordered_map, unordered_set버킷 + 노드 사슬없다평균 O(1), 최악 O(n)기본 최대 적재율 1.0. 넘으면 버킷을 늘려 전부 다시 나눈다
flat_map (C++23)정렬된 배열 두 개(키, 값)키 정렬O(log n) 이분 탐색순회와 조회가 캐시에 잘 맞는다. 삽입은 O(n)
열린 주소 해시(Abseil flat_hash_map 등)한 배열에 원소를 직접 담는다없다평균 O(1)표준이 아니다. 노드 할당이 없어 보통 unordered_map보다 빠르다. 대신 재해시하면 원소 주소가 바뀐다

트리와 해시의 원리, 충돌 처리, 재해시 비용은 트리와 이진 탐색 트리와 해시 테이블에서 다뤘다. 표준 컨테이너에서 알아 둘 것은 둘 다 원소마다 힙 할당을 한 번씩 한다는 점이다. 조회 한 번에도 버킷 배열을 읽고 노드로 한 번 더 뛴다. 원소가 수십 개 정도면 정렬된 vector를 이분 탐색하거나 그냥 처음부터 훑는 쪽이 빠른 경우가 흔하다.

map의 비교자는 엄격한 약순서를 지켜야 한다. a < b와 b < a가 동시에 참이 될 수 없어야 하고, 같은 값은 서로 작지 않아야 한다. <=로 비교자를 만들면 같은 키끼리 비교했을 때 참이 나와 이 조건이 깨지고, 그 뒤의 동작은 정해져 있지 않다. 원소가 사라지거나 무한 반복에 빠질 수 있다.

어댑터는 다른 컨테이너를 감싼다

stack, queue, priority_queue는 새 자료구조가 아니라 다른 컨테이너의 인터페이스를 좁힌 것이다. 기본으로 stack과 queue는 deque를, priority_queue는 vector 위에 힙을 얹는다. 꼭대기 보기는 O(1), 넣고 빼기는 O(log n)이다(힙과 B-트리). 감싸는 컨테이너는 템플릿 인자로 바꿀 수 있다.

선택 기준

상황맞는 것이유
대부분의 경우vector상수가 가장 작고 순회가 가장 빠르다
개수가 컴파일 때 정해진다array동적 할당이 없다
상한은 정해져 있고 개수만 바뀐다std::inplace_vector(C++26), 그 전에는 Boost static_vector객체 안에 고정 용량을 품어 할당이 없고, 크기는 vector처럼 늘고 준다
양 끝에서 넣고 뺀다deque, 또는 원형 버퍼앞 삽입이 O(1)이다. MSVC에서는 원형 버퍼가 낫다
원소 주소가 오래 유지돼야 한다노드 기반, 인덱스로 가리키기, 또는 std::hive(C++26)vector는 재할당 때 주소가 바뀐다. hive는 블록에 담아 지운 칸을 재사용하면서 다른 원소를 옮기지 않는다
키로 찾고 순서는 필요 없다unordered_map(성능이 중요하면 열린 주소 해시)평균 O(1)
키로 찾고 정렬 순회·범위 조회가 필요하다map정렬이 유지된다
한 번 만들고 주로 조회만 한다정렬된 vector, flat_map노드가 없어 캐시에 잘 맞는다

어느 크기에서 순위가 뒤집히는지는 원소 크기, 접근 패턴, 할당자에 따라 달라진다. 감으로 고르지 말고, 실제 원소 타입과 실제 개수로 조회·순회·삽입을 재 보고 정한다. 대개 수천 개까지는 vector와 정렬된 배열이 버틴다.

게임 서버에서는

  • 엔티티 표는 해시보다 인덱스가 빠르다. 엔티티 ID → 객체를 unordered_map으로 들면 조회마다 해시와 노드 점프가 든다. ID에 배열 인덱스와 세대 번호를 넣고 vector에 담는 슬롯 맵 방식이면 조회가 배열 접근 한 번이고, 지워진 칸을 재사용해도 옛 ID는 세대 번호가 달라 걸러진다(ECS 저장 구조).
  • map의 [ ]로 조회하지 않는다. players[id]는 키가 없으면 기본값 원소를 만들어 넣는다. 끊긴 플레이어를 조회만 했는데 빈 세션이 쌓인다. 있는지 볼 때는 find나 contains(C++20), 반드시 있어야 하면 at을 쓴다. 넣을 때도 [ ] 대신 try_emplace(없을 때만 만든다)와 insert_or_assign(C++17)으로 뜻을 드러낸다. 문자열 키 표는 투명 비교자와 투명 해시를 주면(C++20 이종 조회) string_view로 찾을 때 임시 std::string을 만들지 않는다.
  • 틱마다 쓰는 임시 컨테이너는 다시 쓴다. 주변 대상 목록이나 송신 대기열을 틱마다 새로 만들면 할당이 반복된다. 멤버로 두고 clear()만 하면 용량이 남아 할당이 없다. 틱 단위로 몽땅 버리는 할당은 std::pmr::monotonic_buffer_resource 같은 영역 할당자로 받기도 한다(메모리 할당자).
  • 복합 키에는 해시를 직접 만든다. (맵 ID, 칸 좌표) 같은 키는 표준 해시가 없다. 필드 해시를 단순히 XOR하면 (1, 2)와 (2, 1)이 같아져 충돌이 몰린다. 섞는 연산(곱하고 이동하기)으로 합친다.
  • C# 컬렉션과 대응이 정확히 같지는 않다. List<T>는 vector와 같은 연속 배열로 2배씩 늘어난다. Dictionary<K,V>는 체이닝이지만 노드를 따로 할당하지 않고 원소를 배열 하나에 담아 번호로 잇기 때문에 unordered_map보다 할당이 적다. SortedDictionary가 map처럼 레드-블랙 트리이고, Queue<T>는 블록이 아니라 원형 배열이다(해시 테이블, 스택과 큐).

주의 사항

  • list의 O(1) 삽입을 근거로 고르지 않는다. 위치를 찾는 비용과 노드마다의 캐시 미스가 그 이득을 대개 넘는다.
  • unordered_map이 항상 빠르지는 않다. 원소가 적으면 정렬된 배열이 낫고, 해시가 나쁘면 한 버킷에 몰려 최악으로 떨어진다. 재해시가 일어나는 그 순간에는 비용이 한꺼번에 든다. 개수를 알면 reserve로 버킷을 미리 잡는다.
  • unordered 컨테이너의 순회 순서에 기대지 않는다. 순서는 구현, 버킷 수, 삽입 이력에 따라 바뀐다. 순서가 결과에 드러나는 곳(저장, 패킷 내용, 결정적 시뮬레이션)에서는 정렬해서 쓴다.
  • 원소 주소를 오래 들고 있지 않는다. vector와 열린 주소 해시는 커질 때 원소를 옮긴다. 오래 가리켜야 하면 인덱스나 ID를 들고, 쓸 때마다 다시 찾는다.
