먼저 읽을 것: 호출 스택 · 초기화

핵심 요약

RAII(Resource Acquisition Is Initialization)는 자원의 수명을 객체의 수명에 묶는 방법이다. 생성자에서 자원을 얻고, 소멸자에서 놓는다. 이름은 "자원 획득은 초기화"지만, 핵심은 뒤쪽인 해제에 있다.

C++은 스코프를 벗어나는 객체의 소멸자를 언어가 반드시 부른다. 정상 반환이든, 중간 return이든, 예외든 상관없다. 그래서 정리 코드를 경로마다 적을 필요가 없고 빠뜨릴 수도 없다. 메모리만이 아니라 파일, 락, 소켓, 트랜잭션처럼 끝을 맺어야 하는 모든 것에 쓴다.

동작 원리

정리하는 코드가 소멸자 한 곳으로 모인다

예외가 나면 C++은 잡히는 곳까지 스택을 되감으며 그 사이에 만들어진 지역 객체의 소멸자를 부른다(호출 스택). 자원을 객체가 들고 있으면 이 되감기가 곧 정리가 된다. 자원을 포인터나 핸들 값으로만 들고 있으면 되감기는 그 값을 지울 뿐 닫아 주지 않는다. 예외 안전성이 RAII 위에서만 성립하는 이유다(예외와 예외 안전성).

감싸는 클래스는 이렇게 생겼다

class File {
public:
    explicit File(const char* path) : fp_(std::fopen(path, "rb")) {
        if (!fp_) throw std::runtime_error("open failed");   // 얻지 못하면 객체가 생기지 않는다
    }
    ~File() { if (fp_) std::fclose(fp_); }                    // 놓는 곳은 여기 한 곳

    File(const File&) = delete;                               // 복사하면 두 객체가 한 파일을 닫는다
    File& operator=(const File&) = delete;
    File(File&& o) noexcept : fp_(std::exchange(o.fp_, nullptr)) {}  // 옮기면 원본은 빈 손
    File& operator=(File&& o) noexcept {
        if (this != &o) { if (fp_) std::fclose(fp_); fp_ = std::exchange(o.fp_, nullptr); }
        return *this;
    }

    std::FILE* get() const { return fp_; }
private:
    std::FILE* fp_;
};

세 가지가 함께 정해진다. 생성자가 실패하면 예외를 던져 반쯤 만들어진 객체가 생기지 않게 하고, 소멸자가 유일한 해제 지점이 되며, 복사를 막아 두 객체가 같은 자원을 두 번 놓지 않게 한다. 넘겨줄 수는 있도록 이동은 열어 두고, 옮긴 뒤 원본은 아무것도 들지 않게 한다(이동 시맨틱). 실제로는 이렇게 직접 짜기보다 삭제자를 붙인 std::unique_ptr로 감싸는 경우가 많다(스마트 포인터와 소유권).

마지막 줄이 RAII를 멤버 단위로 써야 하는 이유다. 생성자 본문에서 날 포인터 둘을 차례로 new 하다가 두 번째에서 예외가 나면, 소멸자가 불리지 않으므로 첫 번째가 샌다. 멤버를 각각 unique_ptr로 두면 만들어진 멤버는 스스로 정리된다. 자원 하나에 객체 하나를 두면 이런 계산이 필요 없다.

C#의 using과 무엇이 다른가

구분C++ RAIIC# using / IDisposable
누가 정리를 부르나언어. 스코프를 벗어나면 자동쓰는 쪽이 using을 적어야 한다. 잊으면 불리지 않는다
멤버로 들고 있으면바깥 객체가 소멸할 때 멤버 소멸자가 저절로 불린다바깥 클래스도 IDisposable이 되어 Dispose를 이어 불러야 한다
메모리같은 소멸자가 함께 놓는다GC가 따로 회수한다. using은 메모리가 아닌 자원만 다룬다
잊었을 때의 보험필요 없다파이널라이저가 있지만 언제 돌지 모른다

실무에서 가장 크게 다른 곳은 둘째 줄이다. C#에서 소켓을 멤버로 든 세션 클래스는 그 자신도 IDisposable이어야 하고, 세션을 든 관리자도 마찬가지다. 사람이 이 사슬을 이어 줘야 한다. C++에서는 멤버 소멸자가 자동으로 불려 사슬이 저절로 이어진다. 결정적 해제와 파이널라이저의 관계는 IDisposable과 결정적 해제에서 다룬다.

게임 서버에서는

  • 락은 가드로만 잡는다. mutex.lock()을 직접 부르면 임계 구역 안의 return 하나, 예외 하나에 락이 풀리지 않고 서버 전체가 멈춘다. 여러 락을 함께 잡을 때는 std::scoped_lock이 순서를 맞춰 데드락을 피한다(데드락).
  • "끝나면 되돌리기"를 객체로 만든다. DB 트랜잭션 가드는 Commit()이 불리지 않은 채 소멸하면 롤백한다. 아이템 지급 중 어느 단계에서 실패해도 반쯤 지급된 상태가 남지 않는다. 틱 시간 측정도 스코프 시작에 객체를 만들고 소멸자에서 걸린 시간을 기록하면 빠지는 경로가 없다.
  • 세션과 소켓의 수명을 하나로 묶는다. 세션 객체가 소켓을 RAII로 들면 세션이 사라질 때 소켓도 닫힌다. 비동기 I/O가 걸려 있는 동안 세션이 사라지지 않게 하는 문제는 스마트 포인터와 소유권의 shared_from_this에서 다룬다.
  • C# 서버에서는 같은 일을 사람이 지킨다. using을 빠뜨린 SqlConnection이나 소켓은 GC가 파이널라이저를 돌릴 때까지 열려 있다. 연결 풀이 바닥나는 장애가 대개 이렇게 생긴다. C# 코드 리뷰에서 IDisposable을 받는 줄마다 using을 확인하는 것은 C++의 RAII를 손으로 대신하는 일이다.

주의 사항

  • 이름 없는 가드는 그 줄에서 바로 사라진다. std::lock_guard<std::mutex>{m};는 임시 객체라 문장이 끝나는 순간 락을 푼다. 보호하려던 다음 줄들은 락 없이 돈다. 가드에는 반드시 이름을 붙인다(std::lock_guard g{m};).
  • 소멸자에서 예외를 던지지 않는다. 소멸자는 따로 적지 않아도 noexcept로 취급되므로, 예외가 소멸자 밖으로 나가면 그 자리에서 std::terminate로 프로그램이 끝난다. 정리 실패는 기록만 하고 삼킨다. 실패를 호출자가 알아야 한다면 Close() 같은 함수를 따로 두고, 소멸자는 그것이 불리지 않았을 때의 안전망으로만 쓴다.
  • RAII는 메모리 관리 기법이 아니다. 수명이 있는 모든 자원에 쓰는 방법이고 메모리는 그중 하나다. 락과 핸들에 쓰지 않으면 절반만 쓰는 셈이다.
  • 전역·정적 객체의 소멸 순서는 파일을 넘으면 정해지지 않는다. 종료할 때 한 전역 객체의 소멸자가 이미 사라진 다른 파일의 전역 객체(로거 등)를 쓰면 종료 중에 죽는다. 서버 수명 동안 살아야 하는 것은 main에서 순서를 정해 만들고 지운다.
