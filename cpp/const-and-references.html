먼저 읽을 것: 호출 스택

핵심 요약

const는 붙은 자리에 따라 고정하는 대상이 다르다. const int* p는 가리키는 값을, int* const p는 포인터 자신을 고정한다. 선언을 오른쪽에서 왼쪽으로 읽으면 헷갈리지 않는다.

함수에 인자를 넘기는 방법은 셋이다. 값으로 복사해 넘기거나, 참조로 원본의 별칭을 넘기거나, 포인터로 주소를 넘긴다. 복사 비용, 원본을 고칠지, 없을 수도 있는지를 보고 고른다. 참조는 널이 될 수 없지만 원본보다 오래 살 수 없다는 점은 포인터와 똑같다.

동작 원리

const는 바로 왼쪽을 고정한다

규칙은 하나다. const는 바로 왼쪽에 있는 것을 고정하고, 왼쪽에 아무것도 없으면 오른쪽 것을 고정한다. 그래서 int* const p는 오른쪽에서 왼쪽으로 "p는 상수인 포인터이고, int를 가리킨다"로 읽힌다. const int& r은 r로 본 대상을 고칠 수 없다는 뜻이다. 참조는 원래 다른 대상으로 다시 묶을 수 없으므로 int& const 같은 표기는 없다.

const 멤버 함수는 "객체를 안 바꾼다"는 약속이다

멤버 함수 뒤에 붙인 const는 그 함수 안에서 this가 const T*가 된다는 뜻이다. 멤버를 고칠 수 없고, const 객체나 const 참조로는 이런 함수만 부를 수 있다. const 유무가 다른 두 멤버 함수는 서로 오버로드가 된다(오버로딩과 오버라이딩).

구멍무슨 일이 생기나
mutable 멤버const 함수 안에서도 고칠 수 있다. 결과 캐시, 통계, 내부 락처럼 바깥에서 보이는 상태는 그대로인 것에만 쓴다
포인터 멤버고정되는 것은 포인터 값뿐이다. 그 포인터가 가리키는 객체는 const 함수 안에서도 고칠 수 있다. const는 포인터 너머로 전파되지 않는다
const_castconst를 떼어 낼 수 있다. 원래 const로 만든 객체를 그렇게 고치면 미정의 동작이다(캐스팅)

멀티스레드에서는 const에 뜻이 하나 더 붙는다. 표준 라이브러리는 같은 객체의 const 멤버 함수를 여러 스레드가 동시에 불러도 안전하다고 가정한다. 그래서 const 함수 안에서 mutable 캐시를 고친다면 그 캐시는 락이나 원자적 변수로 지켜야 한다. "읽기만 하니 안전하겠지"가 깨지는 자리다.

참조는 별칭이고, 포인터는 주소를 담은 변수다

구분참조 T&포인터 T*
널안 된다. 만들 때 반드시 대상이 있어야 한다된다. "없음"을 표현할 수 있다
다른 대상으로 바꾸기안 된다. 한 번 묶이면 끝까지 같은 대상이다된다

원본이 사라지면끊긴 참조가 된다끊긴 포인터가 된다

참조는 "반드시 있다"를 타입으로 말한다. 대신 안전한 포인터가 아니다. 가리키는 대상의 수명을 늘려 주지 않으므로, 원본이 사라진 뒤 쓰면 포인터와 똑같이 미정의 동작이다.

임시 객체는 그 문장이 끝나면 사라진다

함수가 값으로 돌려준 임시 객체는 그 값을 만든 문장(완전한 식)이 끝날 때 파괴된다. 예외가 하나 있다. 임시를 const T&나 T&& 지역 변수에 직접 묶으면 그 참조가 사는 동안 임시도 산다. 이 연장은 처음 묶은 자리에서만 일어난다. 그 참조를 다른 함수에 넘겨 거기서 다시 묶거나, 반환값으로 내보내면 연장되지 않는다. 

std::string MakeName();

const std::string& a = MakeName();          // 괜찮다. a가 사는 동안 임시도 산다
const char* b = MakeName().c_str();          // 끊긴다. 문장이 끝나면 임시 문자열이 사라진다
std::string_view c = MakeName();             // 끊긴다. string_view는 수명을 늘리지 않는다

const std::string& Pick(const std::string& s) { return s; }
const std::string& d = Pick(MakeName());    // 끊긴다. 연장은 Pick의 매개변수에서 끝났다

const std::string& Local() {
    std::string s = "x";
    return s;                                // 끊긴다. 함수가 끝나면 s는 없다
}

C++17의 std::string_view와 C++20의 std::span은 참조처럼 남의 메모리를 들여다보는 타입이다. 빌린 것이므로 원본보다 오래 들고 있으면 안 된다. 컴파일러가 다 잡아 주지 않는다. 최근 GCC·Clang·MSVC는 이런 경우 일부를 경고한다.

const는 기본으로 붙이고 고쳐야 할 때만 뗀다. 컴파일러가 실수로 고치는 코드를 막아 주고, 읽는 사람은 함수 선언만 보고 무엇이 바뀌는지 안다.

게임 서버에서는

  • 패킷 처리기는 const 참조나 뷰로 받는다. void OnMove(Session& s, const MovePacket& p)처럼 바꿀 것(세션)과 읽기만 할 것(패킷)을 시그니처에서 갈라 둔다. 수신 버퍼를 std::span으로 넘겼다면 그 뷰는 처리기가 끝나면 버린다. 다음 수신이 같은 버퍼를 덮어쓰기 때문이다(메시지 경계와 프레이밍).
  • const 조회 함수에 숨은 캐시를 두면 스레드 문제가 된다. 여러 스레드가 읽기 전용이라 믿고 부르는 GetStat() const 안에서 mutable 캐시를 채우면 경쟁 상태가 된다. 캐시를 쓰려면 std::mutex나 std::atomic을 함께 두거나, 계산을 미리 끝내 둔다(원자적 연산과 메모리 순서).
  • C#의 const와 readonly는 C++ const와 범위가 다르다. C#의 const는 컴파일 시점에 정해지는 리터럴 상수뿐이다. readonly 필드는 필드에 다른 참조를 넣는 것만 막고, 그 참조가 가리키는 객체의 내용은 고칠 수 있다. C++의 T* const에 가깝다. C#에는 "객체를 안 바꾸는 메서드"를 표시하는 const 멤버 함수가 없고, 구조체의 readonly 멤버(C# 8)와 readonly struct가 그 역할을 일부 맡는다(불변성과 null).
  • C#의 in과 ref readonly는 const T&와 비슷하다. in 매개변수는 큰 구조체를 복사 없이 읽기 전용으로 넘긴다. 다만 readonly가 아닌 구조체의 메서드를 부르면 컴파일러가 원본을 보호하려고 방어적 복사를 만들어 이득이 사라진다. C++ const 참조에는 이런 숨은 복사가 없다. 대신 C++은 수명을 지켜 주지 않는다(구조체 설계).

주의 사항

  • const는 컴파일러의 검사일 뿐 메모리 보호가 아니다. 고치려는 코드를 컴파일 단계에서 막을 뿐이고, 캐스트나 포인터 별칭으로 우회할 수 있다. 원래 const로 정의한 객체를 우회해 고치면 미정의 동작이다.
  • 값을 const로 반환하지 않는다. const std::string Name()처럼 반환 타입에 const를 붙이면 받는 쪽이 그 값에서 이동하지 못하고 복사하게 된다.
  • 매개변수의 맨 바깥 const는 시그니처에 들어가지 않는다. void f(int)와 void f(const int)는 같은 함수다. 함수 안에서 그 지역 사본을 고치지 않겠다는 표시일 뿐이다.
  • 참조를 멤버로 두면 대입이 막힌다. 참조는 다시 묶을 수 없으므로 참조 멤버가 있는 클래스는 대입 연산자가 자동으로 생기지 않는다. 컨테이너에 넣기 어려워진다. 바꿀 수 있어야 하면 포인터나 std::reference_wrapper를 쓴다.
