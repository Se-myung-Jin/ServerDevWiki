먼저 읽을 것: RAII · 동기화 객체 · 원자적 연산과 메모리 순서

핵심 요약

C++ 표준 라이브러리의 동시성 도구는 두 원칙 위에 있다. 첫째, 락은 직접 잠그고 풀지 않고 가드 객체로 잡는다. 가드가 스코프를 벗어나면 예외가 나도 소멸자가 풀어 준다. RAII를 락에 적용한 것이다. 둘째, 만든 스레드에는 결말을 정해 준다. 기다리든(join) 떼어 내든(detach) 정하지 않은 채 스레드 객체가 소멸하면 프로그램이 std::terminate로 끝난다.

락 없이 같은 변수를 두 스레드가 읽고 쓰는 데이터 경쟁은 미정의 동작이다. "가끔 틀린 값이 읽힌다"가 아니라 프로그램 전체를 믿을 수 없게 된다. 공유하는 값은 락으로 감싸거나 std::atomic으로 만든다. volatile은 C++에서 동기화 수단이 아니다.

동작 원리

스레드에는 결말을 정해 준다

detach는 쉬워 보이지만 수명을 보장할 방법이 없다. 떼어 낸 스레드가 지역 변수를 참조로 캡처했다면, 만든 함수가 끝나는 순간 끊긴 참조를 쓴다. main이 끝나 정적 객체가 파괴되는 동안에도 계속 돌 수 있다. 서버에서는 거의 쓰지 않는다.

스레드 함수 밖으로 예외가 새어 나가도 std::terminate다. 다른 스레드가 그 예외를 대신 받아 주지 않는다. 스레드 진입 함수는 최상단에서 예외를 잡아 기록하거나, 아래의 future로 결과와 예외를 함께 넘긴다.

C++20의 std::jthread는 결말을 소멸자에 맡긴다. 소멸자가 멈춤 요청을 보낸 뒤 join한다. 멈춤 요청은 강제가 아니라 신호다. 스레드 쪽이 stop_token을 확인해야 효과가 있다. 

std::jthread worker([](std::stop_token st) {
    while (!st.stop_requested())
        PollOnce();          // 오래 막히는 호출이면 멈춤 요청을 보지 못한다
});
// worker가 스코프를 벗어나면 request_stop() 뒤 join()이 불린다

PollOnce가 조건 변수에서 무한정 잠들면 멈춤 요청이 와도 깨지 않아 소멸자가 끝나지 않는다. 그런 대기는 stop_token을 받는 std::condition_variable_any::wait로 바꿔, 멈춤 요청이 대기를 깨우게 한다.

락은 가드 객체로 잡는다

std::mutex m;

void Bad()  { m.lock(); Work(); m.unlock(); }   // Work가 던지면 잠긴 채 남는다
void Good() { std::lock_guard lock(m); Work(); } // 어떻게 나가든 소멸자가 푼다

// 두 계정의 잔고를 함께 바꾼다. 잡는 순서를 신경 쓰지 않아도 교착을 피한다
std::scoped_lock both(from.mutex, to.mutex);
가드무엇이 다른가쓰는 곳
std::lock_guard생성자에서 잡고 소멸자에서 푼다. 그 밖에는 아무것도 못 한다짧은 임계 구역. 가장 흔한 선택
std::unique_lock중간에 풀고 다시 잡기, 나중에 잡기, 시간 제한, 소유권 이동이 된다. 대신 잡혀 있는지 기억하는 만큼 조금 무겁다조건 변수와 함께, 락을 함수 밖으로 넘길 때
std::scoped_lock(C++17)여러 뮤텍스를 교착 회피 알고리즘으로 한꺼번에 잡는다. 하나만 넘기면 lock_guard와 같다두 객체를 함께 바꿀 때(데드락)
std::shared_lock + std::shared_mutex(C++17)읽는 쪽 여럿이 함께 잡고, 쓰는 쪽은 혼자 잡는다읽기가 압도적인 표. 경합이 적으면 일반 뮤텍스가 더 빠를 수 있으니 재고 고른다

std::mutex는 재진입되지 않는다. 같은 스레드가 이미 잡은 뮤텍스를 다시 잡으면 미정의 동작이고, 실제로는 대개 자기 자신을 기다리며 멈춘다. std::recursive_mutex가 있지만, 필요해졌다면 락 범위 설계부터 다시 본다. 뮤텍스와 세마포어의 원리는 동기화 객체에서 다룬다.

조건 변수는 술어와 함께 기다린다

std::condition_variable은 std::unique_lock<std::mutex>와 함께 쓴다. 기다리는 동안 락을 풀고, 깨어나면 다시 잡은 상태로 돌아온다. 깨어났다고 조건이 참이라는 보장은 없으므로 cv.wait(lock, [&]{ return !queue.empty(); })처럼 술어를 넘겨 다시 확인하게 한다. 왜 그래야 하는지는 동기화 객체에 있다.

C++에서 자주 틀리는 것은 조건을 바꾸는 쪽이다. 조건 변수에는 기억이 없어서, 상대가 기다리기 시작하기 직전에 보낸 신호는 사라진다. 조건이 std::atomic<bool>이어도 뮤텍스를 잡지 않고 바꾸면, 상대가 조건을 확인한 직후와 잠들기 직전 사이에 바뀌어 신호를 놓친다. 조건은 같은 뮤텍스를 잡고 바꾸고, notify는 락을 푼 뒤에 불러도 된다.

원자 타입과 메모리 순서

std::atomic<T>은 읽기, 쓰기, 증감, 비교 교환을 쪼개지지 않게 하고, 다른 스레드가 보는 순서를 정한다. 연산마다 메모리 순서를 줄 수 있고 기본은 가장 강한 memory_order_seq_cst다. 통계 카운터처럼 순서가 상관없으면 relaxed, 데이터를 준비한 뒤 플래그로 넘기는 경우는 쓰는 쪽 release와 읽는 쪽 acquire를 짝지어 쓴다. 각 순서가 무엇을 보장하는지는 원자적 연산과 메모리 순서, 원자 연산으로 만든 자료구조는 동시성 자료구조에서 다룬다.

std::atomic이 늘 락 없이 도는 것은 아니다. 큰 구조체를 담으면 구현이 안에서 락을 쓴다. is_always_lock_free로 확인한다. C++20부터는 std::atomic<std::shared_ptr<T>>와, 값이 바뀔 때까지 잠드는 wait·notify_one도 있다. 이미 있는 일반 변수를 잠깐만 원자적으로 다루려면 std::atomic_ref(C++20)를 쓴다. 다만 atomic<shared_ptr>는 주요 구현에서 안에 락을 쓰므로 빠른 락 없는 구조가 아니다. 락 없는 구조의 메모리 회수 문제는 C++26의 std::hazard_pointer와 RCU(<rcu>)가 표준 도구로 맡는다.

volatile은 원자성도 순서도 주지 않는다. "컴파일러가 이 읽기를 지우지 말라"는 뜻일 뿐이고, 하드웨어 레지스터를 읽을 때 쓰는 것이다. C#과 Java의 volatile은 획득·해제 순서를 보장하므로 이름만 같고 뜻이 다르다.

한 번만 초기화하기와 스레드 로컬

함수 안의 static 지역 변수는 C++11부터 초기화가 스레드 안전하다. 여러 스레드가 동시에 처음 들어와도 하나만 초기화하고 나머지는 끝날 때까지 기다린다. 싱글턴을 직접 락으로 감쌀 필요가 없다. 함수 밖에서 한 번만 실행할 일은 std::call_once와 std::once_flag로 한다.

thread_local 변수는 스레드마다 따로 생긴다. 스레드가 시작할 때(또는 처음 쓸 때) 만들어지고 스레드가 끝날 때 소멸한다. 스레드별 버퍼나 난수 생성기를 락 없이 두기에 좋다. 단, 스레드 풀에서는 스레드가 계속 재사용되므로 앞 작업이 남긴 값이 다음 작업에 보인다.

결과를 돌려받는 future

std::promise에 값을 넣으면 짝인 std::future에서 get()으로 기다렸다 받는다. 작업 안에서 던진 예외도 같은 통로로 넘어와 get()에서 다시 던져진다. 공유 변수와 조건 변수를 직접 짜는 것보다 실수가 적다. 기다리는 동안 스레드를 잡아 두지 않고 결과가 오면 이어서 실행하려면 코루틴을 쓴다(C++20 코루틴). C++26은 비동기 작업을 조합하는 표준 틀로 std::execution(senders/receivers)을 더했다. future와 async를 대신할 방향이다.

std::async에는 함정이 둘 있다. 기본 실행 정책은 구현이 "새 스레드에서 바로"와 "get()을 부를 때 그 자리에서" 중 고를 수 있다. 반드시 다른 스레드에서 돌려야 하면 std::launch::async를 명시한다. 그리고 std::async가 돌려준 future는 소멸자에서 작업이 끝나기를 기다린다. 돌려받은 값을 버리면 그 줄에서 바로 기다리므로, 비동기로 던졌다고 생각한 일이 동기로 돈다.

게임 서버에서는

  • 락은 스레드 사이의 입구에만 둔다. 게임 상태를 로직 스레드 하나가 고치는 구조라면, 락이 필요한 곳은 I/O 스레드가 작업을 넣는 큐와 결과를 돌려받는 큐뿐이다(게임 서버 스레딩 모델). 상태 곳곳에 std::mutex를 두기 시작하면 데드락과 경합이 따라온다.
  • 작업 스레드의 수명은 jthread로 묶는다. DB 스레드, 로그 스레드를 서버 객체의 멤버 jthread로 두면 서버 객체가 소멸할 때 멈춤 요청과 합류가 저절로 일어난다. 종료 신호를 받았을 때의 순서는 시그널과 프로세스 종료에서 다룬다.
  • std::async로 일을 흩뿌리지 않는다. 구현에 따라 호출마다 스레드를 새로 만들고, 버린 future는 그 자리에서 기다린다. 서버의 백그라운드 작업은 크기를 정한 스레드 풀에 넣는다(스레드 풀과 실행 모델).
  • 데이터 경쟁은 TSan으로 찾는다. 경쟁은 부하가 걸릴 때만 드러나고 재현이 안 된다. 봇 부하 테스트를 TSan 빌드로 한 번씩 돌리면 실제로 겹친 접근을 스택과 함께 알려 준다(미정의 동작).
  • C#에서 넘어오면 다른 점이 몇 가지 있다. C#의 lock은 Monitor라서 같은 스레드가 다시 잡아도 되지만, std::mutex는 다시 잡으면 멈춘다. C#의 lock 블록이 try/finally로 풀리는 것이 C++에서는 lock_guard다. CancellationToken에 해당하는 것이 stop_token이고, 버려도 막히지 않는 Task와 달리 std::async의 future는 버리면 막힌다. volatile은 C#에서는 순서를 보장하지만 C++에서는 보장하지 않는다(C#의 lock, volatile과 Interlocked).

주의 사항

  • 락을 직접 lock()·unlock()하지 않는다. 그 사이에서 예외가 나거나 중간에 return하면 잠긴 채 남는다.
  • 락을 잡은 채 모르는 코드를 부르지 않는다. 콜백, 가상 함수, 로그 함수가 다른 락을 잡으면 잡는 순서가 꼬여 교착이 생긴다. 필요한 값을 복사한 뒤 락을 풀고 부른다.
  • shared_ptr을 쓴다고 스레드 안전해지지 않는다. 참조 횟수의 증감만 원자적이다. 가리키는 객체와, 같은 shared_ptr 변수 자체를 여러 스레드가 바꾸는 것은 따로 보호해야 한다(스마트 포인터와 소유권).
  • 떼어 낸 스레드는 프로그램 종료와 경쟁한다. main이 끝나 전역 객체가 파괴되는 중에도 돌면서 그 객체를 쓴다. 종료가 가끔만 크래시한다면 이것을 본다.
