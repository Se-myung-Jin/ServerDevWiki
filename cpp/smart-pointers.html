먼저 읽을 것: RAII · 이동 시맨틱

핵심 요약

스마트 포인터는 누가 이 자원을 책임지는지를 타입으로 적는 RAII 객체다. std::unique_ptr은 "주인이 하나다", std::shared_ptr은 "여럿이 나눠 갖고 마지막이 치운다", std::weak_ptr은 "가리키지만 주인은 아니다"를 뜻한다. 날 포인터(T*)는 이제 "빌려 볼 뿐 책임지지 않는다"는 뜻으로만 쓴다.

기본은 unique_ptr이다. 크기가 포인터 하나이고 비용이 없으며 소멸 시점이 코드에 보인다. shared_ptr은 편하지만 소유 질문의 답을 미룰 뿐이다. 누가 마지막인지 코드만 보고는 알 수 없게 되고, 서로를 가리키면 영원히 해제되지 않는다.

unique_ptr은 복사가 막혀 있어서 소유를 넘기려면 std::move를 적어야 한다. 코드에서 소유가 옮겨 가는 지점이 글자로 보인다. 삭제자를 바꿔 끼울 수 있어서 메모리가 아닌 자원도 감싼다. fclose를 부르는 상태 없는 함수 객체(struct FileCloser { void operator()(std::FILE* f) const noexcept { std::fclose(f); } };)를 삭제자로 붙인 std::unique_ptr<std::FILE, FileCloser>나, OS 핸들을 닫는 함수 객체를 삭제자로 붙인 것이 그 예다. 삭제자로 함수 포인터를 넘기면 그 포인터만큼 unique_ptr이 커지고, 표준 라이브러리 함수의 주소를 얻는 것(&std::fclose)은 C++20부터 규격이 보장하지 않는다. C API가 T** 출력 인자로 핸들을 돌려줄 때는 C++23 std::out_ptr로 unique_ptr에 바로 받는다. 곧 덮어쓸 버퍼는 C++20 std::make_unique_for_overwrite로 만들면 0으로 채우는 비용을 건너뛴다(커널 오브젝트와 핸들).

제어 블록과 make_shared

shared_ptr은 객체 말고도 제어 블록을 하나 더 쓴다. 강한 참조 수, 약한 참조 수, 삭제자가 여기 있다. std::shared_ptr<T>(new T)로 만들면 객체와 제어 블록을 따로 할당해 두 번 할당한다. std::make_shared<T>()는 둘을 한 덩어리로 한 번에 할당하므로 할당 횟수가 줄고 둘이 메모리에서 붙어 있다(메모리 할당자).

대가도 있다. 한 덩어리라서 따로 놓을 수 없다. 강한 참조가 모두 사라지면 객체의 소멸자는 바로 불리지만, weak_ptr이 하나라도 남아 있으면 제어 블록이 남아야 하므로 객체가 쓰던 메모리까지 함께 남는다. 큰 객체를 오래 사는 weak_ptr이 가리키면 이것이 누수처럼 보인다. 그럴 때는 따로 할당하는 쪽이 낫다. make 함수를 쓸 수 없는 경우도 있다. 삭제자를 직접 지정해야 할 때와 중괄호 초기화로 만들어야 할 때다. 그때는 new로 만든 포인터를 그 문장 안에서 바로 스마트 포인터 생성자에 넘긴다.

서로 가리키면 영원히 남는다

GC가 있는 언어에는 이 문제가 없다. GC는 참조 수가 아니라 뿌리(스택, 정적 변수)에서 닿을 수 있는지를 보므로, 서로를 가리키는 두 객체도 뿌리에서 닿지 않으면 함께 회수한다(GC 기초). 대신 언제 회수될지 모른다. 참조 수 방식은 마지막 참조가 사라지는 순간 정확히 해제하는 대신 고리를 스스로 풀지 못한다.

흔한 모양은 위에서 아래로는 소유, 아래에서 위로는 관찰이다. 부모가 자식을 shared_ptr이나 unique_ptr로, 자식이 부모를 weak_ptr이나 날 포인터로 가리킨다. 어느 쪽을 약하게 둘지가 곧 소유 구조의 설계다.

무엇이 스레드 안전한가

무엇여러 스레드에서
서로 다른 shared_ptr 사본이 참조 수를 바꾸는 것안전하다. 참조 수는 원자적으로 바뀐다
가리키는 객체의 내용안전하지 않다. 객체는 따로 보호해야 한다
같은 shared_ptr 변수 하나를 한쪽이 읽고 한쪽이 대입하는 것안전하지 않다. 각자 사본을 들거나, C++20의 std::atomic<std::shared_ptr<T>>를 쓴다

참조 수가 원자적이라는 것을 "shared_ptr은 스레드 안전하다"로 넓혀 읽는 실수가 많다. 보호되는 것은 수명이지 내용이 아니다(원자적 연산과 메모리 순서).

this를 shared_ptr로 넘겨야 할 때

class Session : public std::enable_shared_from_this<Session> {
public:
    void StartRead() {
        auto self = shared_from_this();                 // 완료될 때까지 나를 살려 둔다
        socket_.async_read_some(buffer_, [self](auto ec, std::size_t n) {
            if (!ec) self->OnRead(n);
        });
    }
};

auto s = std::make_shared<Session>(...);   // 먼저 shared_ptr로 소유돼 있어야 한다
s->StartRead();

비동기 요청을 걸어 두고 함수가 돌아가면, 완료 콜백이 불리기 전에 세션이 사라질 수 있다. 콜백에 날 this를 넘기면 이미 해제된 객체를 만진다. 그래서 콜백이 세션의 shared_ptr을 하나 들고 있게 한다. 이때 std::shared_ptr<Session>(this)로 새로 만들면 제어 블록이 하나 더 생겨 두 무리가 각자 0을 세고 객체를 두 번 지운다. enable_shared_from_this를 상속하면 객체가 자기 제어 블록을 기억해 두었다가 같은 블록의 사본을 내준다. 생성자 안에서는 아직 소유하는 shared_ptr이 없으므로 부를 수 없다(C++17부터 std::bad_weak_ptr 예외).

선택 기준

상황쓸 것
주인이 분명하다(대부분)unique_ptr. 필요하면 소유를 std::move로 넘긴다
함수가 잠깐 쓰기만 한다T&나 T*로 빌려준다. 스마트 포인터를 값으로 넘기지 않는다
누가 마지막일지 정말 정할 수 없다(비동기 콜백, 여러 시스템이 함께 붙잡는 객체)shared_ptr
살아 있으면 쓰고, 없으면 넘어간다(캐시, 관찰자, 부모 역참조)weak_ptr

shared_ptr을 값으로 받는 함수는 부를 때마다 원자적 증가와 감소를 한 번씩 낸다. 소유를 나눠 가질 생각이 없으면 const T&로 받는다. 원자 연산은 여러 코어가 같은 제어 블록을 건드리면 캐시 라인을 두고 다툰다(캐시 일관성과 false sharing).

게임 서버에서는

  • 세션은 shared_ptr이 맞는 드문 자리다. 세션 관리자, 걸려 있는 수신 요청, 송신 요청, 타이머가 저마다 세션을 붙잡고, 누가 마지막일지는 끊기는 순간의 타이밍이 정한다(완료 알림 기반 서버). 콜백은 shared_from_this()로 붙잡고, "살아 있으면 하트비트를 보내라" 같은 타이머는 weak_from_this()로 들어 세션 수명을 늘리지 않는다.
  • 게임 객체는 핸들로 가리킨다. 몬스터·아이템처럼 수만 개가 생겼다 사라지는 객체를 shared_ptr로 서로 가리키면, 어디서 마지막 참조가 풀릴지 몰라 소멸이 틱 중간에 몰려 터지고 고리가 쉽게 생긴다. 엔진과 서버는 보통 배열 인덱스와 세대 번호를 묶은 핸들을 들고, 쓸 때 세대가 맞는지 확인한다. 크기가 작고, 소멸 시점은 소유한 쪽(월드)이 정하며, 고리가 생기지 않는다(메모리 배치와 자료구조).
  • C#은 소유를 적지 않는 대신 다른 곳에서 샌다. GC가 고리를 풀어 주므로 C#에는 weak_ptr이 필요한 자리가 거의 없다. 대신 이벤트 구독, 정적 컬렉션, 캐시가 객체를 뿌리에 붙잡아 두면 GC도 회수하지 못한다. C++의 순환 참조에 해당하는 C#의 누수가 이쪽이다(메모리 누수).

주의 사항

  • 같은 날 포인터로 shared_ptr을 두 번 만들지 않는다. 제어 블록이 둘 생겨 이중 해제가 난다. shared_ptr은 make_shared로 만들고, 이미 소유된 객체의 사본은 기존 shared_ptr을 복사하거나 shared_from_this로 얻는다.
  • shared_ptr을 기본으로 쓰면 소유 설계가 사라진다. "누가 책임지나"를 미루면 소멸 시점을 설명할 수 없는 코드가 된다. 기본은 unique_ptr이고, shared_ptr은 이유를 댈 수 있을 때만 쓴다.
  • 람다에 this를 캡처하면 수명을 보장하지 않는다. 비동기로 나중에 불리는 람다라면 shared_from_this()나 weak_from_this()를 캡처한다(람다와 함수 객체).
  • 소멸이 연쇄로 몰린다. 큰 객체 그래프의 마지막 shared_ptr이 풀리면 그 아래 전부가 그 스레드에서 한꺼번에 소멸한다. 로직 스레드에서 수만 개가 한 번에 지워지면 틱이 튄다. 큰 정리는 다른 스레드로 넘기거나 여러 틱에 나눈다.
