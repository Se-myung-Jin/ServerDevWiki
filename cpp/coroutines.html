먼저 읽을 것: C++ 동시성 · I/O 모델

핵심 요약

코루틴은 실행을 중간에 멈췄다가 나중에 그 자리에서 이어 갈 수 있는 함수다. 본문에 co_await, co_yield, co_return 중 하나라도 있으면 컴파일러가 그 함수를 코루틴으로 바꾼다. 비동기 I/O를 걸고 완료를 기다리는 코드를 콜백으로 쪼개지 않고, 위에서 아래로 읽히는 순차 코드로 쓸 수 있게 해 준다.

C++20 코루틴은 스택 없는(stackless) 코루틴이다. 멈출 때 호출 스택을 통째로 보관하지 않고, 이어 가는 데 필요한 지역 변수와 재개 지점만 코루틴 프레임에 담아 둔다. 프레임은 대개 힙에 할당된다. 멈춘 동안 스택에 있던 것은 사라지므로, 참조로 받은 인자와 임시 객체의 수명을 직접 챙겨야 한다.

동작 원리

멈추면 프레임만 남고, 재개는 깨운 쪽 스레드에서 한다

컴파일러는 코루틴을 상태 기계로 바꾼다. 지역 변수 가운데 중단 지점을 넘어 살아야 하는 것은 프레임으로 옮기고, "몇 번째 중단 지점에서 멈췄나"를 프레임에 적어 둔다. 재개하면 그 번호로 뛰어 이어 간다. 스택을 통째로 바꾸는 스택 있는 코루틴(파이버)과 달리 멈춘 코루틴 하나가 쓰는 메모리는 프레임 크기뿐이라, 수만 개를 띄워도 부담이 작다.

프레임은 기본으로 operator new로 할당된다. 코루틴의 수명이 호출한 함수 안에서 끝나는 것이 확실하면 컴파일러가 할당을 없애고 호출자 스택에 두기도 하지만(HALO), 이것은 최적화이고 보장이 아니다. 세션 루프처럼 오래 사는 코루틴은 할당이 일어난다고 보는 것이 맞다.

세 키워드와 두 약속 객체

요소하는 일
co_await exprexpr이 준비됐는지 묻고, 아니면 멈춘다. 준비되면 그 결과를 값으로 돌려받는다
co_yield v값 하나를 내보내고 멈춘다. 생성기(generator)에서 쓴다
co_return v코루틴을 끝내고 결과를 남긴다
promise_type반환 타입(예: Task<T>) 안에 정의한다. 처음에 바로 멈출지, 결과와 예외를 어디에 둘지, 끝나면 누구를 깨울지를 정한다
awaiterco_await 대상이 제공한다. await_ready(멈출 필요가 있나), await_suspend(멈출 때 할 일, 보통 I/O를 걸고 재개 핸들을 맡긴다), await_resume(재개할 때 돌려줄 값)

C++20은 이 장치만 주고, 실제로 쓰는 Task 타입이나 실행기는 주지 않았다. 그래서 직접 promise_type을 짜거나 라이브러리를 쓴다. 서버에서는 Boost.Asio·독립형 Asio의 awaitable<T>, cppcoro, folly의 coro::Task가 흔하다. 표준에는 C++23에서 값을 차례로 내보내는 std::generator가 처음 들어왔다. 

// Asio: 세션의 읽기 루프를 순차 코드로 쓴다
asio::awaitable<void> ReadLoop(std::shared_ptr<Session> s)   // 값으로 받아 수명을 붙잡는다
{
    std::array<std::byte, 4096> buf;          // 프레임에 담겨 중단을 넘어 산다
    for (;;) {
        std::size_t n = co_await s->socket.async_read_some(
            asio::buffer(buf), asio::use_awaitable);    // 여기서 멈추고, 완료되면 이어 간다
        s->OnBytes({buf.data(), n});
    }
}

asio::co_spawn(ioContext, ReadLoop(session), asio::detached);

예외와 재개 스레드

코루틴 안에서 던진 예외는 promise_type의 unhandled_exception으로 가서 결과에 담기고, 그 코루틴을 co_await한 쪽에서 다시 던져진다. 기다리는 쪽이 없으면(detached로 띄운 경우 등) 라이브러리 정책에 따라 버려지거나 프로그램이 끝나므로, 최상위 루프는 안에서 잡아 기록한다.

어느 스레드에서 이어지는지는 언어가 정하지 않는다. awaiter가 재개 핸들을 누구에게 넘기느냐가 정한다. 보통은 I/O 완료를 받은 스레드가 그 자리에서 재개한다. Asio는 코루틴이 묶인 실행기(executor)로 재개를 보내므로, 실행기를 strand나 한 스레드짜리 io_context로 잡으면 재개 위치를 고정할 수 있다(완료 알림 기반 서버).

선택 기준

게임 서버에서는

  • 세션마다 읽기 루프 하나를 코루틴으로 띄운다. 수신을 걸고, 받고, 프레이밍하고, 다시 거는 일을 for 문 하나로 쓴다(메시지 경계와 프레이밍). 수만 세션이면 코루틴도 수만 개지만, 각자 프레임 하나와 수신 버퍼만 쓴다.
  • 게임 상태는 여전히 로직 스레드에서 고친다. I/O 완료 스레드에서 재개된 코드가 그 자리에서 캐릭터를 고치면 단일 쓰기 규칙이 깨진다. 받은 패킷은 작업 큐에 넣거나, 로직 스레드 실행기로 옮겨 간 뒤 고친다(게임 서버 스레딩 모델).
  • 세션을 shared_ptr 값으로 받는다. 코루틴이 멈춘 동안 세션이 해제되면 재개된 코드가 해제된 객체를 만진다. 매개변수를 shared_ptr 값으로 받으면 그 사본이 프레임에 남아 코루틴이 사는 동안 세션을 붙잡는다(스마트 포인터와 소유권).
  • 짧고 잦은 코루틴의 할당을 잰다. 패킷마다 작은 코루틴을 새로 띄우면 프레임 할당이 그만큼 생긴다. promise_type에 operator new를 두어 풀에서 받거나, 오래 사는 루프 안에서 처리하도록 구조를 바꾼다(메모리 할당자).
  • C#의 async/await와 생각보다 많이 다르다. C#은 컴파일러가 만드는 상태 기계와 Task, 스레드 풀, SynchronizationContext까지 런타임이 함께 준다. 재개 위치는 컨텍스트가 정하고, 서버처럼 컨텍스트가 없으면 스레드 풀에서 이어진다. C++은 타입과 실행기를 고르는 일부터 내 몫이고, GC가 없으니 멈춘 동안의 수명도 내가 챙긴다(async와 await, 동기화 컨텍스트).

주의 사항

  • 참조 매개변수는 첫 중단 뒤에 끊길 수 있다. Task Send(const std::string& msg)를 Send("hi"s)처럼 임시로 부르면, 호출한 문장이 끝나는 순간 임시가 사라지고 프레임에는 끊긴 참조만 남는다. 중단을 넘어 쓸 인자는 값으로 받는다(const와 참조).
  • 람다 코루틴의 캡처는 프레임에 들어가지 않는다. 캡처는 람다 객체의 멤버이고, 코루틴 프레임은 그 람다 객체를 가리킬 뿐이다. 람다 객체가 먼저 사라지면 캡처도 함께 사라진다. 코루틴 람다는 캡처 대신 매개변수로 넘긴다(람다와 함수 객체).
  • 멤버 함수 코루틴의 this도 같다. 객체가 먼저 해제되면 재개된 코드가 끊긴 this를 쓴다. shared_from_this()로 얻은 사본을 지역 변수로 들고 시작한다.
  • 멈춘 코루틴을 아무도 재개하거나 파괴하지 않으면 프레임이 샌다. 코루틴 핸들은 직접 destroy()를 불러야 프레임이 해제된다. 직접 promise_type을 짠다면 RAII로 핸들을 감싼다.
  • 락을 쥔 채 co_await하지 않는다. 멈춘 동안 락이 계속 잡혀 있고, 다른 스레드에서 재개되면 잡은 스레드와 푸는 스레드가 달라져 std::mutex 규칙이 깨진다.
