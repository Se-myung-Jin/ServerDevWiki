먼저 읽을 것: 이동 시맨틱 · 템플릿과 컴파일 시점 계산

핵심 요약

템플릿 함수의 매개변수 T&&는 rvalue 참조가 아니다. T를 추론하는 자리에서 쓰인 T&&는 lvalue도 rvalue도 받는 전달 참조다. lvalue를 넘기면 T가 참조 타입으로 추론되고, 참조 접힘 규칙에 따라 매개변수가 lvalue 참조가 된다.

받은 인자를 다음 함수에 넘길 때 원래의 값 범주를 지키는 것이 완벽 전달이다. 매개변수는 이름이 있어서 함수 안에서는 늘 lvalue다(이동 시맨틱). 그대로 넘기면 rvalue로 받은 것도 복사된다. std::forward<T>(x)는 원래 rvalue였을 때만 rvalue로 바꿔 넘긴다. emplace_back과 make_unique가 생성자 인자를 손실 없이 넘기는 방법이다.

동작 원리

넘긴 값에 따라 T가 달라진다

추론 규칙이 특별한 것은 이 자리뿐이다. T&& 매개변수에 타입이 U인 lvalue를 넘기면 T는 U&로, rvalue를 넘기면 U로 추론된다. 그 결과 생긴 "참조의 참조"는 아래 규칙으로 하나로 접힌다.

참조 접힘은 lvalue 참조가 하나라도 있으면 lvalue 참조다

TT&&를 펼치면접힌 결과
U&U& &&U&
U&&U&& &&U&&
UU&&U&&
U&에 &를 붙임U& &U&

사람이 int& &&를 직접 적을 수는 없다. 이 규칙은 템플릿 치환, auto, 타입 별칭이 참조를 겹쳐 만들 때만 쓰인다.

어디까지가 전달 참조인가

모양전달 참조인가이유
template<class T> void f(T&&)맞다이 호출에서 T를 추론한다
auto&& x = expr;맞다auto도 같은 추론 규칙을 쓴다. 범위 기반 for (auto&& e : c)가 흔한 예다
void f(auto&& x) (C++20)맞다축약 함수 템플릿이라 template<class T> void f(T&&)와 같다. 넘길 때는 std::forward<decltype(x)>(x)다
void f(Item&&)아니다추론이 없다. rvalue만 받는다
template<class T> void f(std::vector<T>&&)아니다T&& 모양이 아니다. vector의 rvalue만 받는다
template<class T> void f(const T&&)아니다const가 붙으면 rvalue 참조다
클래스 템플릿 멤버 void push(T&&)아니다T는 클래스를 만들 때 이미 정해졌다. 이 함수를 부를 때 추론하지 않는다

forward와 move는 같은 캐스트를 다른 조건으로 한다

// std::move: 언제나 rvalue로 바꾼다
template<class T> std::remove_reference_t<T>&& move(T&& x) noexcept;

// std::forward: T가 lvalue 참조면 lvalue로, 아니면 rvalue로 돌려준다
template<class T> T&& forward(std::remove_reference_t<T>& x) noexcept {
    return static_cast<T&&>(x);   // T = U&면 U&, T = U면 U&&
}

둘 다 실제로 옮기는 일은 하지 않는다. std::move는 "이제 옮겨도 된다"를 무조건 붙이고, std::forward는 "원래 옮겨도 되는 것이었다면" 붙인다. 그래서 forward는 템플릿 인자 T를 반드시 적어야 한다. T에 원래의 범주가 담겨 있기 때문이다. 전달 참조에는 forward, 내가 소유한 값을 넘겨줄 때는 move다.

가변 인자와 함께 쓰면 생성자 인자를 그대로 넘긴다

template<class T, class... Args>
std::unique_ptr<T> MakeUnique(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));   // 인자마다 따로 forward
}

auto m = MakeUnique<Monster>(name, Vec3{1, 2, 3}, 100);
// name은 lvalue라 복사로, Vec3{...}는 임시라 이동으로, 100은 int로 Monster 생성자에 간다

Args&&... args는 인자 묶음 하나하나를 전달 참조로 받고, std::forward<Args>(args)...는 각 인자에 자기 Args를 짝지어 펼친다. vector::emplace_back, std::make_shared, std::thread의 생성자가 모두 이 모양이다(STL 컨테이너 고르기).

반환도 범주를 지키려면 decltype(auto)

감싸는 함수가 안쪽 함수의 반환값을 그대로 돌려줄 때, 반환 타입을 auto로 두면 참조가 떨어져 값으로 복사된다. decltype(auto)는 반환식의 타입을 참조까지 그대로 쓴다. Get(i)가 Item&를 돌려주면 감싼 함수도 Item&를 돌려준다. 대신 지역 변수를 괄호로 감싸 return (local);로 쓰면 지역 변수의 참조를 돌려주는 끊긴 참조가 된다. C++23의 std::forward_like는 감싼 객체의 값 범주에 맞춰 그 멤버를 넘긴다. deducing this로 받은 self의 멤버를 돌려줄 때 쓴다.

게임 서버에서는

  • 객체 풀과 생성 함수는 인자를 전달로 받는다. pool.Create<Monster>(args...)가 받은 인자를 std::forward로 풀 안의 자리에 그대로 넘기면, 이름·스킬 목록 같은 무거운 인자를 임시로 넘겼을 때 복사 없이 이동으로 끝난다(메모리 할당자). 받은 인자를 const Args&...로 받으면 임시도 전부 복사된다.
  • 로그와 이벤트 발행 래퍼에 쓴다. Publish<E>(args...)가 이벤트 객체를 그 자리에서 만들어 큐에 넣으면, 부르는 쪽은 생성자 인자만 넘기고 임시 이벤트 객체를 만들었다 옮기는 일이 없다. 로그 함수가 형식 문자열과 인자를 다음 단계로 넘길 때도 같다.
  • C#에는 이 개념이 없다. C#은 클래스가 참조로 오가고 값의 범주라는 구분이 없어서, 인자를 "원래 모양 그대로" 넘길 문제가 생기지 않는다. ref, in, out은 전달 방식을 부르는 쪽이 직접 적는 것이고, 제네릭이 추론해 주는 것이 아니다. C++의 emplace에 해당하는 일은 대개 생성 비용이 작아 따로 필요하지 않다.

주의 사항

  • 전달 참조 생성자는 복사 생성자를 가로챈다. template<class T> Player(T&& name)를 두면, const가 아닌 Player lvalue를 복사할 때 T = Player&로 정확히 맞는 이 템플릿이 const Player&를 받는 복사 생성자보다 먼저 골라진다. 그러고는 Player를 이름 문자열로 만들려다 오류나 엉뚱한 동작이 된다. C++20 requires로 자기 타입을 빼 둔다(!std::is_same_v<std::remove_cvref_t<T>, Player>, 오버로딩과 오버라이딩).
  • 같은 인자를 두 번 forward하지 않는다. 첫 번째 forward가 이동시켰다면 두 번째는 이미 옮겨진 객체를 넘긴다. 여러 곳에 써야 하면 마지막 한 번만 forward하고 앞에서는 lvalue로 쓴다.
  • auto&&로 받은 것은 std::forward<decltype(x)>(x)로 넘긴다. 제네릭 람다의 auto&& 매개변수도 같다. 이름 붙은 T가 없으니 decltype으로 범주를 꺼낸다.
  • 완벽 전달이 완벽하지 않은 경우가 있다. 중괄호 초기화 목록 {1, 2}, 이름이 같은 오버로드 함수, 비트 필드는 전달 참조로 추론할 수 없어 컴파일 오류가 난다. 널 포인터를 0이나 NULL로 넘기면 정수로 추론되어 포인터 매개변수에 맞지 않는다. nullptr을 쓴다. 부르는 쪽에서 타입을 적어 넘긴다.
