먼저 읽을 것: const와 참조 · 정렬과 패딩

핵심 요약

C 스타일 캐스트 (T)x는 무엇을 하려는지 적지 않는다. 되는 변환을 찾아 그냥 되게 만든다. C++은 이것을 네 가지 이름 있는 캐스트로 나눴다. static_cast는 관련 있는 타입 사이의 변환, dynamic_cast는 실행 중에 확인하는 다운캐스트, const_cast는 const 떼고 붙이기, reinterpret_cast는 비트를 그대로 다른 타입으로 보기다.

이 중 실행 중에 확인하는 것은 dynamic_cast 하나뿐이다. static_cast로 기반 포인터를 파생 포인터로 내리면 아무것도 확인하지 않는다. 실제 객체가 그 타입이 아니면 미정의 동작이다.

동작 원리

네 캐스트는 하는 일과 검사가 다르다

캐스트하는 일검사틀리면
static_cast숫자 타입 변환, 상속 계층 위아래 이동, void*에서 원래 타입으로, enum과 정수컴파일 때 관련이 있는지만 본다관련 없는 타입이면 컴파일 오류. 다운캐스트가 틀리면 미정의 동작
dynamic_cast다형 타입의 다운캐스트와 옆 가지로의 캐스트실행 중에 실제 타입을 확인한다포인터면 nullptr, 참조면 std::bad_cast 예외
const_castconst·volatile을 떼거나 붙인다없다원래 const인 객체를 고치면 미정의 동작
reinterpret_cast포인터를 다른 포인터나 정수로, 그 반대로없다다른 타입으로 읽으면 대개 미정의 동작

위로 올라가는 변환(파생 → 기반)은 캐스트 없이 암묵적으로 된다. 캐스트를 써야 하는 곳은 그 반대 방향이고, 거기서 무엇을 고르느냐가 안전을 가른다.

static_cast는 믿고, dynamic_cast는 확인한다

dynamic_cast가 확인하려면 객체에 실행 시간 타입 정보(RTTI)가 붙어 있어야 한다. 가상 함수가 하나라도 있는 다형 타입이어야 쓸 수 있는 이유다. 확인은 가상 함수 표에 딸린 타입 정보를 따라가며 계층을 훑는 일이라 static_cast보다 비싸다. 계층이 깊거나 다중 상속이면 더 비싸지고, 공유 라이브러리를 넘나들면 타입 이름 문자열 비교까지 할 수 있다. -fno-rtti로 빌드하면 아예 쓸 수 없다.

static_cast 다운캐스트는 확신이 있을 때만 쓴다. 그 확신이 타입 태그나 설계로 보장될 때다. dynamic_cast가 코드 곳곳에 보이면 설계를 의심한다. "이 객체가 무슨 타입이냐"를 묻고 분기하는 코드는 대개 가상 함수 하나로 바꿀 수 있다(가상 함수와 다형성).

const_cast와 reinterpret_cast는 컴파일러를 멈추게 할 뿐 규칙을 바꾸지 않는다

const_cast로 const를 떼는 것 자체는 허용된다. 하지만 원래 const로 정의한 객체를 그렇게 고치면 미정의 동작이다. 안전한 경우는 원래 const가 아닌 객체를 누군가 const 참조로 넘겨받았을 때뿐이다. 대개는 const를 붙이지 않은 옛 API를 부를 때 쓰이고, 그 밖의 쓰임은 설계 문제의 신호다.

reinterpret_cast는 포인터를 다른 타입의 포인터로 바꿀 수는 있어도, 그 포인터로 읽어도 된다는 보장은 주지 않는다. C++에는 엄격한 앨리어싱 규칙이 있다. 어떤 객체는 그 타입(또는 부호만 다른 타입, char·unsigned char·std::byte)으로만 읽을 수 있다. 컴파일러는 float*와 int*가 같은 메모리를 가리키지 않는다고 가정하고 읽기 순서를 바꾸거나 값을 레지스터에 남겨 둔다. 규칙을 어긴 코드는 디버그 빌드에서 맞고 최적화 빌드에서 틀린다. 

float f = 1.0f;
uint32_t bad  = *reinterpret_cast<uint32_t*>(&f);   // 앨리어싱 위반. 미정의 동작
uint32_t ok1;  std::memcpy(&ok1, &f, sizeof f);      // 바이트를 복사한다. 컴파일러가 대개 명령 하나로 줄인다
uint32_t ok2 = std::bit_cast<uint32_t>(f);           // C++20. 크기가 같은 타입끼리 비트를 그대로 옮긴다

정렬도 문제다. 정렬되지 않은 주소를 uint32_t*로 바꿔 읽으면 x86에서는 대개 느려지기만 하지만, 일부 ARM과 SIMD 명령에서는 예외가 난다(정렬과 패딩).

C 스타일 캐스트는 되는 것을 아무거나 고른다

(T)x는 const_cast, static_cast, static_cast + const_cast, reinterpret_cast, reinterpret_cast + const_cast 순으로 맞춰 보고 처음 되는 것을 쓴다. 숫자 변환을 하려다 타입이 바뀌면 조용히 reinterpret_cast가 된다. const도 말없이 떨어진다. dynamic_cast는 후보에 없어서 확인도 일어나지 않는다. 그리고 코드에서 검색이 안 된다. 이름 있는 캐스트는 _cast로 찾을 수 있다.

파생 → 기반캐스트 없이 된다
기반 → 파생, 타입이 보장된다static_cast
기반 → 파생, 확실하지 않다dynamic_cast 뒤에 nullptr 확인
타입을 묻고 분기한다가상 함수로 바꾼다

게임 서버에서는

  • 수신 버퍼를 구조체 포인터로 바꿔 읽지 않는다. auto* p = reinterpret_cast<const MovePacket*>(buf);는 서버 코드에서 흔하지만 문제가 셋 겹친다. 엄격한 앨리어싱 위반이고, 버퍼 위치가 구조체 정렬과 맞는다는 보장이 없고, 패딩과 엔디안이 컴파일러와 CPU에 따라 달라진다. 필드마다 바이트를 읽어 조립하거나 memcpy로 정렬된 지역 구조체에 복사한다(엔디안과 바이트 오더, 메시지 경계와 프레이밍). C++23의 std::start_lifetime_as<T>는 바이트 위에 객체 수명을 시작해 별칭 문제를 규격 안에서 푼다. 다만 정렬과 엔디안은 여전히 책임져야 하고, 표준 라이브러리 구현이 아직 고르지 않다.
  • 메시지 종류 분기에 dynamic_cast 사슬을 쓰지 않는다. 받은 메시지 객체를 dynamic_cast<MoveMsg*>, dynamic_cast<AttackMsg*>로 차례로 시험하면 메시지마다 계층 확인을 여러 번 한다. 헤더의 메시지 번호로 처리기 표를 찾는 쪽이 빠르고 분명하다.
  • C#의 캐스트는 항상 확인한다. C++의 static_cast는 확인하지 않는다. C#의 (Player)e는 실제 타입이 다르면 InvalidCastException을 던지고, as는 null을, is 패턴은 false를 준다. C#에 익숙한 사람이 C++에서 같은 감각으로 static_cast 다운캐스트를 쓰면 예외 대신 엉뚱한 메모리를 읽는다. C#의 as에 해당하는 것은 dynamic_cast다.
  • C#에도 reinterpret_cast 같은 자리가 있다. MemoryMarshal.Cast, MemoryMarshal.Read<T>, Unsafe.As는 바이트 범위를 다른 타입으로 다시 본다. 런타임이 앨리어싱 최적화를 C++만큼 공격적으로 하지 않지만 엔디안과 구조체 배치 문제는 똑같이 남는다(Span과 ref struct). 숫자 변환도 비슷하다. C#의 (int)longValue는 기본이 unchecked라 static_cast처럼 조용히 잘린다. checked 문맥에서만 넘침을 예외로 알려 준다.

주의 사항

  • static_cast가 빠른 것은 확인을 건너뛰기 때문이다. 그 확인이 필요한 자리였다면 빨라진 것이 아니라 버그를 숨긴 것이다.
  • dynamic_cast는 다형 타입에만 쓸 수 있다. 가상 함수가 없는 클래스에 쓰면 컴파일 오류다. 다운캐스트가 필요한데 가상 함수가 없다면 그 계층이 다형성을 염두에 두고 설계되지 않았다는 뜻이다.
  • 숫자 static_cast는 범위를 검사하지 않는다. static_cast<int>(3e10)처럼 표현할 수 없는 실수를 정수로 바꾸면 미정의 동작이다. 더 작은 정수 타입으로 바꾸면 위쪽 비트가 잘린다(수의 표현).
  • C 스타일 캐스트와 함수형 캐스트 T(x)는 같은 규칙이다. int(x)도 C 스타일 캐스트와 똑같이 아무 변환이나 고른다.
