먼저 읽을 것: 컴파일과 링킹

핵심 요약

C++ 빌드가 느린 것은 컴파일러 구현이 아니라 구조 때문이다. #include는 헤더를 텍스트로 펼쳐 넣으므로, 같은 헤더가 그것을 포함한 소스 파일 수만큼 다시 컴파일된다.

여기에 템플릿이 더해진다. 템플릿은 쓰인 타입마다 따로 실체를 만들어야 해서, 같은 템플릿을 여러 파일에서 쓰면 같은 일을 파일마다 되풀이한다(템플릿과 컴파일 시점 계산).

동작 원리

같은 헤더가 파일 수만큼 다시 컴파일된다

표준 라이브러리 헤더 하나만 넣어도 펼쳐진 결과는 수만 줄로 부푼다. 정작 쓰는 것은 함수 하나여도 그렇다. 얼마나 부푸는지는 전처리 결과를 직접 뽑아 보면 바로 보인다(g++ -E, cl /P).

무엇에 시간이 드나왜
헤더 반복 처리포함한 파일마다 다시 읽고 파싱한다
템플릿 실체화쓰인 타입 조합마다, 그리고 쓰인 파일마다 코드를 만든다
인라인 함수본문이 헤더에 있어야 해서 헤더가 커진다
링킹파일마다 만든 같은 템플릿 실체 중 하나만 남기는 일이 마지막에 몰린다. 링크 시간 최적화(LTO)를 켜면 최적화까지 이 단계로 넘어온다

코어를 늘려도 어느 지점부터는 잘 줄지 않는다. 컴파일은 파일마다 따로라 병렬로 돌릴 수 있지만, 링킹은 실행 파일 하나를 만드는 마지막 단계라 그 앞의 컴파일이 다 끝나기를 기다린다. lld·mold 같은 최근 링커는 내부에서 여러 스레드를 쓰지만, 단계 자체가 빌드 끝에 하나로 남는 구조는 같다.

다른 언어는 어떻게 피하나

C#·Java·Rust 같은 언어는 텍스트를 펼치지 않는다. 다른 모듈을 쓸 때 소스가 아니라 이미 컴파일된 형태의 인터페이스(C#은 어셈블리의 메타데이터)를 읽는다. 그래서 프로젝트가 커져도 같은 코드를 파일마다 다시 파싱하는 일이 없다.

C++에도 C++20부터 모듈이 들어왔지만, 기존 코드와 서드파티 라이브러리가 헤더로 되어 있어 옮겨 가는 데 시간이 걸린다.

선택 기준

펼쳐지는 양을 줄여야 빌드가 짧아진다

방법어떻게대가
전방 선언헤더에서 포인터·참조로만 쓰는 타입은 #include 대신 class Foo;로 선언만 한다정의가 필요한 소스 쪽으로 포함을 옮겨야 한다
구현 숨기기(pImpl)멤버를 별도 구현 클래스로 옮기고 헤더에는 포인터 하나만 둔다간접 참조가 한 단계 늘고 할당이 하나 더 생긴다
미리 컴파일된 헤더(PCH)자주 쓰는 헤더 묶음을 한 번만 처리해 저장해 둔다구성이 복잡하고, PCH에 든 헤더가 바뀌면 전체를 다시 빌드한다
단위 묶기(unity build)여러 소스를 하나로 합쳐 컴파일해 헤더 처리 횟수를 줄인다한 줄만 고쳐도 묶음 전체를 다시 하고, 파일끼리 이름이 충돌할 수 있다
모듈처리 결과를 재사용한다도구와 기존 코드의 지원이 필요하다

전방 선언이 가장 싸고 효과가 확실하다. 헤더 하나가 무거운 헤더를 포함하지 않게 되면, 그 헤더를 포함한 모든 소스가 함께 가벼워진다.

게임 서버에서는

  • C++ 서버는 빌드 시간이 개발 속도를 정한다. 패킷 정의나 공용 타입처럼 거의 모든 소스가 포함하는 헤더를 고치면 사실상 전체 빌드가 된다. 이런 헤더는 가볍고 안정적으로 유지하고, 자주 바뀌는 내용(밸런스 상수 등)은 헤더 밖 데이터로 뺀다.
  • 캐시와 분산 빌드를 함께 쓴다. 같은 입력이면 이전 결과를 재사용하는 컴파일 캐시(ccache, sccache)와 여러 머신에 컴파일을 나눠 주는 분산 빌드(IncrediBuild, FASTBuild)는 구조를 고치지 않고 얻는 이득이다. 다만 링킹은 여전히 한 머신에 남는다.
  • C# 서버도 빌드가 느려질 수 있다. 원인은 헤더가 아니라 프로젝트 수, 분석기(analyzer)와 소스 제너레이터, 증분 빌드를 깨는 설정이다. dotnet build -bl로 빌드 로그를 남겨 어느 프로젝트·작업이 오래 걸리는지 본다.

주의 사항

  • 헤더 가드는 소스 파일 하나 안에서만 중복을 막는다. 같은 소스가 같은 헤더를 두 번 포함해도 한 번만 펼쳐진다는 뜻이지, 다른 소스가 그 헤더를 펼치는 일까지 막지는 않는다. 소스가 100개면 100번 처리되는 것은 그대로다.
  • 최적화 수준을 낮춰도 원인은 그대로다. 빌드는 빨라지지만 실행 성능이 떨어지고, 펼쳐지는 양은 줄지 않는다.
  • 증분 빌드가 잘 되려면 의존이 얕아야 한다. 헤더 하나를 고치면 그것을 직간접으로 포함한 모든 소스가 다시 컴파일된다. 많이 포함되는 헤더일수록 덜 바뀌어야 한다.
