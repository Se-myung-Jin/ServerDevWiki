먼저 읽을 것: 프로세스와 스레드 · PCB와 컨텍스트 스위칭

핵심 요약

스레드 풀은 미리 만들어 둔 스레드를 빌려 쓰고 돌려받는 구조다. 스레드 생성·소멸 비용을 없애고, 동시에 실행되는 스레드 수에 상한을 둔다.

둘 중 상한이 더 중요하다. 요청이 몰릴 때 스레드를 무한정 만들면 전환 비용과 스택 메모리가 먼저 한계에 닿는다. 풀은 넘치는 요청을 큐에서 기다리게 만들어 시스템이 버티게 한다.

동작 원리

스레드를 매번 만들면 두 번 손해를 본다

먼저 생성 비용이 든다. 스택을 잡고 커널에 스레드를 등록하는 일을 요청마다 되풀이한다.

더 큰 문제는 스레드를 만드는 데 제한이 없으면 동시 실행 수에도 제한이 없다는 점이다. 요청 만 개가 들어오면 스레드 만 개가 생기고, 그때부터 CPU는 일을 하는 대신 컨텍스트 스위칭에 시간을 쓴다. 스레드마다 잡히는 스택 예약 공간(네이티브 기준 Windows 1MB, Linux 8MB. 프로세스와 스레드 참고)도 그만큼 늘어난다.

풀은 둘을 함께 해결한다. 스레드는 재사용되고, 풀 크기가 곧 동시 실행 상한이 된다.

커널이 모르는 흐름은 블로킹 호출에서 함께 멈춘다

스레드 위에서 다시 가벼운 실행 흐름(코루틴, 그린 스레드)을 돌리는 방식도 있다. 커널이 직접 관리하는 스레드와는 성질이 다르다.

구분커널 스레드유저 레벨 흐름 (코루틴)
누가 스케줄하나커널프로그램(런타임) 자신
전환 비용커널에 들어갔다 나오고, 캐시와 TLB도 영향을 받는다레지스터 몇 개를 바꾸는 함수 호출에 가깝다
코어를 여럿 쓰나쓴다흐름 자체로는 못 쓴다. 런타임이 여러 커널 스레드에 나눠 올려야 쓴다(M:N)
하나가 블로킹되면다른 스레드는 계속 실행된다같은 커널 스레드에 올라 있던 흐름 전부가 멈춘다

코루틴 하나가 블로킹 호출에 들어가 같은 커널 스레드의 흐름이 전부 멈추는 일이 실무에서 가장 잦다. 커널은 코루틴을 모르므로, 그 안에서 어느 흐름이 기다리는지 보지 못한다. 그래서 코루틴을 쓰는 환경에서는 입출력을 비동기로 바꿔 두고, 동기로 기다리는 호출을 섞지 않는 것을 규칙으로 삼는다.

C#의 async/await는 이 표의 중간쯤에 있다. 컴파일러가 메서드를 상태 기계로 바꾸고, await 이후 이어지는 코드는 보통 .NET 스레드 풀의 아무 스레드에서 실행된다. 그래서 여러 코어를 쓰지만, 풀 스레드를 동기 대기로 붙잡으면 아래의 풀 고갈이 그대로 생긴다.

선택 기준

풀 크기는 작업 성격이 정한다

작업 성격풀 크기 출발점이유
CPU를 계속 쓰는 계산코어 수 근처그 이상은 전환만 늘린다
대기가 긴 작업(블로킹 IO, 외부 호출)코어 수보다 많이기다리는 동안 비는 CPU를 다른 스레드가 채운다. 얼마나 더 둘지는 대기 비율이 정한다
비동기 IO로 바꾼 작업코어 수 근처로 충분기다리는 동안 스레드를 붙잡지 않는다

"코어 수"가 물리 코어인지 논리 코어인지도 따로 정해야 한다(논리 코어와 하이브리드 코어). 표의 값은 출발점이고, 결론은 실제 부하로 재서 낸다.

풀에 블로킹 작업을 섞으면 풀이 고갈된다

풀 스레드가 전부 긴 대기에 묶이면 짧은 작업도 큐에서 밀린다. 겉으로는 CPU 사용률이 낮은데 응답은 느려진다.

  1. 기다리는 코드를 비동기로 바꾼다. 비동기 호출을 동기로 기다리는 코드(.Result, .Wait())에서 이 문제가 가장 자주 생긴다.
  2. 바꿀 수 없으면 성격이 다른 작업을 다른 풀이나 전용 스레드로 나눈다. 대신 풀마다 스레드를 따로 잡아 메모리를 더 쓴다.

게임 서버에서는

  • .NET 스레드 풀 고갈은 "느린 증가"로 드러난다. .NET 스레드 풀은 최소 스레드 수(기본은 논리 코어 수)까지는 즉시 스레드를 내주지만, 그 이상은 천천히 늘린다. 그래서 동기 대기가 섞인 서버는 부하가 몰리는 순간 수 초 동안 응답이 멈췄다가 서서히 풀린다. ThreadPool.SetMinThreads로 최소값을 올리는 것은 증상 완화이고, 근본 해결은 .Result·.Wait()를 없애는 것이다. dotnet-counters의 스레드 풀 큐 길이로 확인한다.
  • 게임 로직 루프는 풀에 맡기지 않는다. 매 틱 도는 루프를 Task.Run으로 풀 스레드에 올리면 다른 작업과 스레드를 다투고, 틱 지연이 풀 상태에 따라 흔들린다. 로직 스레드는 전용 스레드(new Thread 또는 TaskCreationOptions.LongRunning)로 두고, DB·외부 호출처럼 기다리는 일만 비동기로 풀에 넘긴다.
  • Unity 코루틴은 메인 스레드 하나에서 돈다. 위 표의 유저 레벨 흐름에 해당한다. 코루틴 안에서 동기 네트워크 호출이나 파일 읽기를 하면 그동안 프레임 전체가 멈춘다. 클라이언트 코드를 리뷰할 때 같은 기준으로 본다.

주의 사항

  • 스레드 풀이 주는 것은 생성 비용 절감만이 아니다. 동시 실행 수에 상한을 두는 쪽이 더 크다. 상한이 없으면 부하가 몰릴 때 시스템이 스스로 멈춰 선다.
  • 코루틴이 가볍다는 말은 전환 비용을 가리킨다. 전환이 싸다고 기다리는 일까지 싸지지는 않는다.
  • 큐에 상한이 없으면 문제를 미룰 뿐이다. 풀이 동시 실행을 막아도 대기 큐가 무한하면 메모리가 대신 터진다. 큐 길이를 지표로 보고, 넘치면 요청을 거절하는 지점을 정해 둔다.
