먼저 읽을 것: 커널 경계와 시스템 콜

핵심 요약

파일 시스템은 이름과 데이터를 따로 관리한다. 데이터 위치와 속성은 inode(NTFS에서는 MFT 레코드) 같은 구조에 담고, 디렉터리는 이름과 그 구조의 번호를 잇는 표일 뿐이다.

하드 링크가 왜 같은 파일인지, 열어 둔 파일을 지워도 왜 읽히는지, 이름 바꾸기가 왜 빠른지가 이 분리 하나로 설명된다.

동작 원리

디렉터리는 이름과 번호를 잇는 표다

이름을 바꾸는 일은 디렉터리 표의 한 줄을 고치는 것이라 파일 크기와 무관하게 빠르다. 같은 파일 시스템 안에서 옮기는 일도 마찬가지다. 다른 파일 시스템(다른 디스크·볼륨)으로 옮기면 복사 후 삭제가 되어 크기만큼 시간이 든다.

이름 하나를 지운다고 파일이 사라지지 않는다

inode에는 자기를 가리키는 이름이 몇 개인지 세는 링크 수가 있다. 이 값이 0이 되고 그 파일을 열어 둔 프로세스도 없을 때 비로소 데이터 블록이 해제된다.

  • 하드 링크를 만들면 디렉터리 항목이 하나 늘고 링크 수가 올라간다.
  • 이름 하나를 지워도 다른 이름이 남아 있으면 데이터는 그대로다.
  • 열어 둔 파일을 지우면 이름은 사라지지만, 열어 둔 쪽이 참조를 들고 있어 계속 읽고 쓸 수 있다. 닫는 순간 없어진다.

마지막 동작은 Linux·macOS의 규칙이다. Windows는 다르다. 다른 프로세스가 삭제 공유(FILE_SHARE_DELETE) 없이 열어 둔 파일은 지울 수 없고 "다른 프로세스가 사용 중" 오류가 난다. .NET의 FileStream도 기본으로는 삭제 공유를 허용하지 않는다.

하드 링크심볼릭 링크
정체같은 inode를 가리키는 또 하나의 이름경로 문자열을 담은 별개의 작은 파일
원본 이름을 지우면데이터가 그대로 남는다끊어진다(대상 없음)
다른 파일 시스템으로못 만든다. inode 번호는 한 파일 시스템 안에서만 뜻이 있다만들 수 있다
디렉터리에못 만든다(순환 방지)만들 수 있다

쓰는 도중에 전원이 나가면 구조가 깨진다

파일에 쓰는 일은 한 번에 끝나지 않는다. 데이터 블록을 쓰고, inode를 고치고, 빈 블록 목록을 갱신해야 한다. 중간에 멈추면 구조가 깨진 채로 남는다.

저널링은 할 일을 먼저 저널에 기록해 두고 실제로 하는 방식이다. 중간에 멈춰도 기록을 보고 마저 하거나 되돌릴 수 있어서, 부팅할 때 파일 시스템 전체를 검사하지 않아도 된다. 다만 ext4의 기본 설정과 NTFS는 메타데이터만 저널에 남긴다. 그래서 구조는 온전한데 파일 내용은 반쯤 쓰인 상태가 나올 수 있다.

페이지 캐시가 읽기와 쓰기 사이에 있다

OS는 읽은 블록을 메모리(페이지 캐시)에 남겨 두고 다음 요청에 쓴다. 쓰기도 일단 페이지 캐시에 받아 두고 나중에 디스크로 내린다. 그래서 쓰기 호출이 돌아왔다고 디스크에 저장된 것이 아니다. 확실히 내리려면 fsync(Windows는 FlushFileBuffers)를 따로 요청해야 하고, 그 요청은 느리다.

선택 기준

언제 확실히 내릴 것인가

방법얻는 것대가
그냥 쓴다빠르다전원이 나가거나 OS가 죽으면 최근 쓰기를 잃는다
매번 확실히 내린다잃지 않는다쓰기마다 디스크를 기다린다
묶어서 주기적으로 내린다대부분의 속도를 유지한다주기 안에 쓴 것은 잃을 수 있다

데이터베이스는 로그(WAL)를 먼저 확실히 내리고 본체는 나중에 내린다. 여러 트랜잭션의 로그를 한 번에 묶어 내려서(group commit), 잃지 않으면서도 매번 따로 기다리지 않는다. 얼마나 묶을지는 잃어도 되는 양이 정한다. 재화·결제처럼 잃으면 안 되는 쓰기는 매번 내리거나 DB에 맡기고, 로그처럼 조금 잃어도 되는 쓰기는 묶는다.

게임 서버에서는

// 설정·스냅샷 파일을 안전하게 교체한다: 임시 파일에 쓰고, 디스크까지 내리고, 이름을 바꾼다
var tmp = path + ".tmp";
using (var fs = new FileStream(tmp, FileMode.Create, FileAccess.Write))
{
    fs.Write(data);
    fs.Flush(flushToDisk: true);        // Flush()만 부르면 OS 페이지 캐시까지만 간다
}
File.Move(tmp, path, overwrite: true);  // 같은 파일 시스템 안이라 이름만 바뀐다
  • 파일을 덮어쓰지 말고 바꿔 끼운다. 기존 파일을 열어 덮어쓰다가 죽으면 반쯤 쓰인 파일이 남는다. 위처럼 임시 파일을 완성한 뒤 이름을 바꾸면, 읽는 쪽은 항상 옛 파일이나 새 파일 중 하나를 본다. Linux에서는 이 교체가 rename 한 번이라 원자적이다. Windows도 같은 볼륨 안이면 대개 한 번에 바뀌지만 보장이 Linux만큼 명확하지 않다. 백업 파일까지 남기며 바꿔 끼우려면 File.Replace를 쓴다.
  • Flush()와 Flush(true)는 다르다. .NET의 Flush()는 .NET 버퍼를 OS로 넘길 뿐이고, 디스크까지 내리는 것은 Flush(flushToDisk: true)다.
  • 지운 로그가 디스크를 계속 차지한다. Linux에서 로그 파일을 rm으로 지워도 서버 프로세스가 열어 두고 있으면 공간이 돌아오지 않는다. lsof +L1로 "지워졌지만 열린" 파일을 찾고, 로그 교체는 서버가 파일을 다시 열도록 하는 방식(새 파일로 전환, copytruncate 등)으로 한다.

주의 사항

  • 파일을 지웠는데 여유 공간이 안 늘면 누군가 열어 두고 있는 것이다. 링크 수가 0이 되어도 열어 둔 프로세스가 있으면 블록이 해제되지 않는다. 그쪽이 파일을 닫거나 끝나야 해제된다.
  • 하드 링크와 심볼릭 링크는 이름만 비슷하다. 하드 링크는 같은 실체의 또 다른 이름이고, 심볼릭 링크는 경로를 적어 둔 별개의 파일이다. 대상이 사라졌을 때 동작이 다르다.
  • 이름 바꾸기까지 확실히 남기려면 디렉터리도 내려야 한다. Linux에서 rename 직후 전원이 나가면, 디렉터리 변경이 아직 디스크에 없을 수 있다. 엄밀한 내구성이 필요하면 디렉터리도 fsync한다.
