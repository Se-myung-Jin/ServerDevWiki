먼저 읽을 것: 페이징과 TLB

핵심 요약

페이지 폴트는 접근한 가상 페이지가 지금 물리 메모리에 매핑돼 있지 않을 때 CPU가 일으키는 예외다. 고장이 아니라 가상 메모리가 동작하는 방식 그 자체다. 프로그램을 처음 실행할 때도, 새로 받은 메모리를 처음 쓸 때도 폴트가 난다.

폴트가 난다는 것 자체는 문제가 아니다. 디스크까지 내려가는 폴트가 너무 잦아질 때 문제가 된다. 일하는 시간보다 페이지를 나르는 시간이 길어진 상태가 스래싱이다.

동작 원리

폴트라고 다 같은 폴트가 아니다

종류무슨 상황인가비용
마이너 폴트페이지가 물리 메모리 어딘가에 있거나 새로 0으로 채워 주면 되는 경우. 처음 쓰는 힙, copy-on-write, 다른 프로세스가 이미 올려 둔 공유 라이브러리매핑만 걸면 끝난다. 새 페이지를 0으로 채우는 시간까지 대략 마이크로초 수준
메이저 폴트디스크에서 읽어 와야 한다. 스왑으로 내려간 페이지, 아직 안 읽은 실행 파일·메모리 매핑 파일디스크 접근이 붙는다. SSD라도 수십 마이크로초 이상, HDD면 밀리초
잘못된 접근할당되지 않은 주소이거나, 읽기 전용 페이지에 쓰는 것처럼 권한이 맞지 않다OS가 처리할 수 없다. Linux는 SIGSEGV, Windows는 Access Violation으로 프로세스가 죽는다

잘못된 접근도 하드웨어 입장에서는 같은 페이지 폴트로 들어온다. OS가 폴트 처리기에서 주소와 권한을 확인한 뒤 "고칠 수 없다"고 판정하는 것이다. 널 포인터 역참조가 여기 해당한다. C#에서는 결과가 다르다. .NET 런타임이 널 참조로 생긴 이 폴트를 받아 NullReferenceException으로 바꿔 던지므로, 잡을 수 있는 예외가 된다. 프로세스가 바로 죽는 것은 네이티브 코드(P/Invoke, unsafe)에서 잘못된 주소를 건드렸을 때다.

메이저 폴트가 늘면 물리 메모리가 모자라다는 뜻이다. 진단할 때는 전체 폴트 수가 아니라 메이저 폴트 수를 본다.

교체 알고리즘은 다음에 안 쓸 것을 고르는 문제다

물리 메모리가 꽉 찼는데 새 페이지를 올려야 하면, 이미 올라와 있는 페이지 하나를 내보내야 한다.

알고리즘고르는 방식문제
FIFO먼저 들어온 것부터자주 쓰는 페이지도 순서가 되면 나간다. 벨라디 이상이 생긴다
최적(OPT)앞으로 가장 늦게 쓸 것미래를 알아야 해서 구현할 수 없다. 비교 기준으로만 쓴다
LRU가장 오래 안 쓴 것접근할 때마다 순서를 갱신해야 해서 그대로 구현하기 비싸다
시계(Clock)참조 비트를 보며 한 바퀴 돈다LRU를 싸게 흉내 낸다

LRU를 그대로 쓰는 OS는 드물다. 메모리 접근은 하드웨어가 하므로 소프트웨어가 접근마다 순서를 고칠 수 없다. 하드웨어는 페이지 테이블 항목에 참조 비트를 세워 주기만 하고, OS는 그 비트로 LRU를 근사한다. 시계 알고리즘이 교과서의 대표이고, Linux는 활성·비활성 목록을 두는 식으로 같은 근사를 한다.

FIFO는 프레임을 늘렸는데 폴트가 오히려 늘어나는 경우가 있다. 이것이 벨라디 이상이다. LRU에는 이런 일이 없다. 프레임을 하나 늘리면, 늘리기 전에 담고 있던 페이지를 그대로 담은 채 하나가 더 들어가기 때문이다.

스래싱은 스스로를 키운다

최근 한동안 실제로 접근한 페이지를 모은 것을 워킹셋이라고 한다. 참조 지역성 덕분에 이 집합은 주소 공간 전체보다 훨씬 작다. 실행 중인 프로세스들의 워킹셋 합이 물리 메모리를 넘으면 악순환이 시작된다.

선택 기준

스래싱은 튜닝이 아니라 메모리 문제다

교체 알고리즘을 바꿔서 해결되지 않는다. 원인은 워킹셋 합이 물리 메모리보다 크다는 것이라, 손댈 곳은 셋뿐이다.

방법누가 하나
동시에 도는 프로세스·작업 수를 줄인다운영자, 오케스트레이터(배치 수 조정)
프로그램이 한 번에 접근하는 데이터 범위(워킹셋)를 줄인다개발자
물리 메모리를 늘린다운영자(인스턴스 크기)

교과서에서는 OS가 일부 프로세스를 통째로 내려놓아 나머지를 살린다고 설명한다. 하지만 현대 Linux는 프로세스를 통째로 스왑 아웃하지 않는다. 스왑으로 버티다가 메모리가 바닥나면 OOM killer가 프로세스 하나를 골라 죽인다. 컨테이너에서는 메모리 limit을 넘는 순간 바로 죽는다(OOMKilled).

게임 서버에서는

  • 스왑에 들어가는 순간 틱이 무너진다. 메이저 폴트 하나가 틱 시간 전체를 먹을 수 있다. 실시간 게임 서버는 스왑을 끄거나 최소로 두고, 메모리 사용량에 여유를 둔 채 운영한다. 지연이 이유 없이 튀면 메이저 폴트 수부터 본다(Linux ps -o min_flt,maj_flt, /proc/vmstat의 pgmajfault, Windows 성능 카운터 Hard Faults/sec).
  • 컨테이너 메모리 limit은 GC 설정과 함께 본다. .NET은 컨테이너 메모리 limit을 읽어 GC 힙 상한을 잡는다. 그래도 네이티브 메모리, 스레드 스택, 버퍼 풀까지 합친 프로세스 전체가 limit을 넘으면 OOMKilled다. 필요하면 GCHeapHardLimit(또는 GCHeapHardLimitPercent)로 힙 상한을 명시한다.
  • 서버 시작 직후의 느림은 마이너 폴트일 수 있다. 큰 풀이나 맵 데이터를 처음 만지면 페이지마다 마이너 폴트가 난다. 오픈 직후 첫 몇 분만 느리다면 시작 단계에서 풀을 미리 채우고 한 번씩 접근해 두는(warm-up) 방식으로 비용을 오픈 전으로 옮긴다.

주의 사항

  • 페이지 폴트는 오류가 아니다. 폴트가 없으면 가상 메모리가 동작하지 않는다. 문제는 메이저 폴트의 빈도다.
  • CPU 사용률이 낮다고 여유가 있다는 뜻은 아니다. 스래싱 중인 시스템은 대부분의 흐름이 디스크를 기다리느라 사용률이 낮게 보인다. 그 상태에서 부하를 더 주면 더 나빠진다.
  • 메모리 사용량 지표를 구분한다. 가상 메모리 크기(VSZ, Private Bytes)가 아니라 실제로 물리 메모리를 차지한 양(RSS, Working Set)이 스래싱과 OOM에 직접 관련된다.
