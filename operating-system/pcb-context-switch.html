먼저 읽을 것: 프로세스와 스레드

핵심 요약

컨텍스트 스위칭은 실행 중인 흐름의 상태를 저장하고 다음 흐름의 상태를 복원해 CPU의 주인을 바꾸는 일이다. 저장할 상태를 담아 두는 커널 자료구조가 프로세스는 PCB(Process Control Block), 스레드는 TCB(Thread Control Block)다.

직접 비용보다 간접 비용이 크다. 레지스터를 저장하고 복원하는 일 자체는 짧게 끝난다. 문제는 그 뒤에 남는다. 새 흐름이 캐시를 밀어내고, 프로세스가 바뀌면 TLB까지 다시 채워야 한다.

동작 원리

PCB에는 무엇이 들어가나

항목왜 필요한가
프로세스 식별자(PID)누구인지 구분한다
상태 (준비 · 실행 · 대기 등)다시 스케줄할 수 있는지 판단한다
프로그램 카운터, 레지스터 값멈춘 지점부터 이어서 실행한다
페이지 테이블 주소이 프로세스의 주소 변환 규칙을 가리킨다
열린 파일 목록어떤 자원을 쥐고 있는지 알고, 끝날 때 되돌려 받는다
스케줄링 정보우선순위, 지금까지 쓴 CPU 시간

PCB와 TCB는 담는 것이 나뉜다. 주소 공간과 열린 파일 목록처럼 스레드끼리 함께 쓰는 것은 프로세스 쪽에, 레지스터와 스택 포인터처럼 스레드마다 다른 것은 스레드 쪽에 둔다. Linux는 이 둘을 따로 두지 않고 스레드마다 같은 구조체(task_struct)를 쓰되, 같은 프로세스의 스레드끼리 주소 공간 구조를 가리키는 포인터를 공유하는 방식으로 같은 효과를 낸다.

프로세스를 바꿀 때는 페이지 테이블 주소를 담은 레지스터(x86의 CR3)를 교체한다. 그러면 같은 가상 주소가 다른 물리 페이지로 번역된다. 메모리 내용을 옮기는 것이 아니라 주소를 해석하는 규칙을 바꾸는 것이다.

프로세스 상태는 정해진 길로만 옮겨 다닌다

입출력만 대기로 보내는 것이 아니다. 락을 잡지 못해 잠든 흐름도 같은 자리로 간다. 이 구분을 진단에 그대로 쓴다. CPU 사용률은 낮은데 응답이 느리면 흐름들이 대기 상태에 오래 머무는 것이므로, 스레드를 늘리기 전에 무엇을 기다리는지부터 본다.

진짜 비용은 캐시와 TLB가 밀려나면서 생긴다

새 흐름이 실행되기 시작하면 이전 흐름이 쓰던 캐시 내용이 밀려난다. 다음 실행은 차가운 캐시에서 시작하고, 한동안 메모리까지 다녀오는 접근이 늘어난다.

비용스레드 → 같은 프로세스의 스레드프로세스 → 다른 프로세스
레지스터 저장·복원, 커널 진입있음있음
캐시 오염있음있음 (작업 집합이 완전히 달라 더 크다)
주소 공간 교체없음있음. 앞 프로세스의 TLB 항목을 쓸 수 없다

요즘 CPU는 TLB 항목에 주소 공간 번호(x86의 PCID)를 붙여 두기 때문에 전환할 때마다 TLB를 통째로 비우지는 않는다. 그래도 한 TLB를 여러 주소 공간이 나눠 쓰게 되므로 항목을 두고 다투는 것은 남는다. 직접 비용은 대략 마이크로초 단위이고, 캐시와 TLB를 다시 채우는 간접 비용은 작업 집합 크기에 따라 그보다 커질 수 있다.

선택 기준

스레드를 늘리면 어느 지점부터 처리량이 꺾인다

CPU를 계속 쓰는 스레드가 코어 수를 넘어서면 같은 일을 하는 데 전환 횟수만 늘어난다. 각 스레드가 받는 시간 조각이 짧아지고, 조각마다 차가운 캐시에서 다시 시작한다. 여기에 락 경합이 겹치면 기다리는 스레드를 재우고 깨우는 일이 잦아지고, 그것이 또 전환이다.

작업 성격스레드 수
CPU를 계속 쓴다코어 수 근처가 상한 (어느 코어 수인지도 확인한다)
기다리는 시간이 길다스레드를 늘리기보다, 기다리는 일을 비동기 입출력으로 넘기고 워커는 코어 수만큼 둔다

게임 서버에서는

  • 전환 횟수를 지표로 본다. Linux는 /proc/<pid>/status의 voluntary_ctxt_switches(스스로 기다리러 간 횟수)와 nonvoluntary_ctxt_switches(선점당한 횟수), 또는 pidstat -w로 본다. Windows는 성능 카운터의 "Context Switches/sec"를 본다. 자발적 전환이 많으면 락·입출력 대기, 비자발적 전환이 많으면 스레드가 코어보다 많다는 신호다.
  • 틱 스레드는 끊기지 않게 둔다. 게임 로직 스레드가 다른 스레드와 같은 코어를 두고 다투면, 틱 중간에 선점되어 틱 시간이 흔들린다. 로직 스레드 수를 코어보다 적게 두고, 무거운 배치 작업은 따로 떼어 낸다.
  • .NET 스레드 풀에서 블로킹하지 않는다. 풀 스레드에서 .Result나 Thread.Sleep으로 기다리면 그 스레드가 대기 상태로 묶이고, 풀은 스레드를 더 만들어 메운다. 전환과 스레드가 함께 늘어난다(스레드 풀과 실행 모델).

주의 사항

  • 컨텍스트 스위칭은 메모리 내용을 바꾸지 않는다. 레지스터 값과 주소 변환 대상만 바꾼다. 메모리에 있는 데이터는 그 자리에 그대로 있다.
  • 시스템 콜이 곧 컨텍스트 스위칭은 아니다. 시스템 콜은 같은 스레드가 커널 모드로 들어갔다 나오는 모드 전환이다. 그 안에서 기다리게 되어 다른 스레드로 넘어갈 때만 컨텍스트 스위칭이 일어난다(커널 경계와 시스템 콜).
  • 스레드를 늘렸는데 느려지면 대부분 이 비용이다. 전환 비용과 캐시 오염이 처리량 증가분을 넘어서는 지점이 있다.
