먼저 읽을 것: GC 동작과 세대 · 서버 틱 루프

핵심 요약

GC가 객체를 옮기고 참조를 고치는 동안에는 응용 스레드를 세워야 한다. 이 멈춤은 없앨 수 없다. GC 모드는 멈춤을 어디에 얼마나 나눠 낼지를 고르는 설정이다. 워크스테이션 GC는 힙 하나를 짧게 자주 거두고, 서버 GC는 코어마다 힙과 GC 스레드를 두어 많이 모아 한꺼번에 거둔다.

백그라운드 GC는 2세대의 표시 작업을 응용과 나란히 돌려 긴 멈춤을 짧은 멈춤 여럿으로 바꾼다. 그래도 시작과 끝의 짧은 멈춤이 남고, 0세대와 1세대 수거는 언제나 전부 세운다. 게임 서버의 멈춤을 줄이는 근본 방법은 모드가 아니라 2세대로 올라가는 객체를 줄이는 것이다.

서버 GC는 GC 작업을 여러 코어가 나눠 하므로 같은 양을 더 빨리 거둔다. 대신 예산이 커서 한 번에 거둘 양이 많고, 힙이 여럿이라 메모리를 더 쓴다. 코어가 32개인 기계에서 힙 32개가 각자 0세대 예산을 잡는 식이다. .NET 8에서 선택 기능으로 들어온 DATAS(Dynamic Adaptation To Application Sizes)는 힙 하나로 시작해 부하에 따라 힙 수와 예산을 늘리고 줄인다. .NET 9부터 서버 GC를 켜면 DATAS가 기본으로 켜진다. 서버 GC 자체가 기본이 된 것은 아니다.

백그라운드 GC는 2세대 표시만 겹친다

동시(concurrent) GC가 켜져 있으면(기본값) 2세대 수거는 백그라운드 GC로 돈다. 전용 스레드가 응용과 나란히 2세대를 표시하고, 응용 스레드는 그동안 계속 할당하고 실행한다. 다만 완전히 겹치지는 않는다.

  • 시작할 때 뿌리를 잡는 짧은 멈춤이 있다.
  • 끝날 때 그사이 바뀐 참조를 정리하는 짧은 멈춤이 있다.
  • 백그라운드 GC가 도는 동안 0세대 예산이 차면 그 자리에서 0·1세대 수거(전경 GC)를 한다. 이것은 응용 스레드를 전부 세운다.
  • 백그라운드 GC는 압축하지 않는다. 단편화가 쌓이면 결국 압축하는 블로킹 2세대 GC가 돈다.

그래서 백그라운드 GC는 "긴 멈춤 하나를 짧은 멈춤 여럿으로 바꾸는 장치"다. 2세대가 커질수록 표시에 오래 걸리고, 그 사이 전경 GC도 여러 번 끼어든다.

컨테이너에서는 상한이 달라진다

.NET 런타임은 컨테이너의 메모리 제한을 읽어, 따로 정하지 않으면 그 75%를 GC 힙 상한으로 잡는다. CPU 제한도 읽어 서버 GC의 힙 수를 그에 맞춘다. 문제는 코어는 많이 주고 메모리는 적게 준 경우다. 힙마다 예산을 잡는 서버 GC가 상한에 금방 닿아 GC가 잦아진다. 이때는 DATAS를 쓰거나, GCHeapCount로 힙 수를 줄이거나, 워크스테이션 GC와 비교해 고른다(컨테이너와 오케스트레이션).

어느 모드든 멈춤의 길이를 정하는 것은 살아 있는 객체의 양이다. 2세대로 올라가는 객체를 줄이면 모든 모드에서 멈춤이 짧아지고, 모드를 바꾸는 것은 그 위에서의 미세 조정이다(GC 동작과 세대).

게임 서버에서는

  • 멈춤은 틱 예산에서 빠진다. 30Hz 틱이면 한 틱이 약 33ms다. GC 멈춤이 20ms면 그 틱에 쓸 시간이 13ms로 줄고, 멈춤이 틱보다 길면 틱 하나를 통째로 놓친다. 평균 틱 시간은 멀쩡한데 가끔 튀는 틱이 GC 시각과 겹치면 이것이 원인이다(서버 틱 루프, 느린 서버 진단). 여러 기능을 한 프로세스에 모으면 이 멈춤도 함께 겪는다(프로세스 경계).
  • 멈춤은 분포로 잰다. GC.GetGCMemoryInfo()의 PauseDurations, GC.GetTotalPauseDuration()(.NET 7), 이벤트 추적의 GC 시작·끝 시각을 틱 시간 기록과 나란히 남긴다. 평균 멈춤으로는 문제의 한 번이 보이지 않는다.
  • 대량 로딩 뒤에는 정리할 기회를 준다. 서버 시작 때 기획 데이터를 다 읽은 직후라면, 접속을 받기 전에 GC를 한 번 돌려 임시 객체를 치우고 남을 것을 2세대로 보내 두는 것이 나을 수 있다. 실행 중에 직접 GC를 부르는 것과는 다른 경우다.
  • NoGCRegion은 아주 짧은 구간에만 쓴다. 보스전 판정처럼 몇 ms 안에 끝나는 구간에서 할당량을 미리 알 때 쓸 수 있다. 할당량을 넘으면 구간이 깨지고, 끝낸 직후에는 미뤄 둔 GC가 몰려 올 수 있다.

주의 사항

  • 서버 GC가 늘 빠르지는 않다. 처리량은 오르지만 메모리가 늘고, 한 번에 거둘 양이 많아 멈춤이 길어질 수 있다. 꼬리 지연이 중요한 서버에서는 반대 결과가 나오기도 한다.
  • 백그라운드 GC는 멈춤을 없애지 않는다. 0·1세대 수거는 언제나 전부 세우고, 단편화가 쌓이면 압축하는 블로킹 GC가 돈다.
  • 지연 모드를 오래 켜 두지 않는다. LowLatency와 SustainedLowLatency는 GC를 미루는 것이라, 미룬 만큼 메모리가 늘고 결국 더 큰 GC가 온다.
  • 설정 이름은 버전마다 조금씩 다르다. 환경 변수 접두사는 .NET 5부터 DOTNET_이고, 그 전에는 COMPlus_였다. 지금도 둘 다 읽지만 새 설정은 DOTNET_으로 적는다.
