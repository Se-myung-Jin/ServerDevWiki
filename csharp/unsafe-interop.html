먼저 읽을 것: GC 동작과 세대 · IDisposable과 결정적 해제 · ref와 Span

핵심 요약

C#은 두 곳에서 관리 세계 밖으로 나간다. 하나는 unsafe 코드다. 포인터를 직접 쓰고, 주소를 더하고, GC가 모르는 메모리를 다룬다. 다른 하나는 네이티브 상호 운용이다. C나 C++로 만든 라이브러리 함수를 부르는 P/Invoke와, 반대로 네이티브 쪽이 C# 함수를 부르게 하는 함수 포인터가 여기 든다.

경계를 넘을 때마다 비용이 든다. 인자를 네이티브가 이해하는 모양으로 바꾸는 마샬링, 스레드를 GC가 건드리지 못하는 상태로 바꾸는 전환, 넘긴 버퍼를 GC가 옮기지 못하게 하는 고정이다. 그리고 런타임이 막아 주던 실수가 돌아온다. 범위 밖 접근과 해제 후 사용은 예외가 아니라 메모리 손상이 된다.

동작 원리

경계를 넘는 호출 한 번에 일어나는 일

스레드 상태를 바꾸는 ③이 필요한 이유는 GC 때문이다. GC는 압축하기 전에 모든 관리 스레드를 멈춰 세운다. 네이티브 코드를 실행 중인 스레드는 관리 객체를 만지지 않으므로 기다릴 필요가 없다. 그래서 들어갈 때 "나는 지금 네이티브에 있다"고 표시해 두면, 그 스레드가 오래 걸리는 압축 라이브러리 안에 있어도 GC는 나머지 스레드만 세우고 진행한다. 대신 표시를 바꾸는 일 자체가 호출마다 수 ns를 더한다.

unsafe: 포인터와 고정

// 프로젝트에 <AllowUnsafeBlocks>true</AllowUnsafeBlocks> 가 있어야 한다
static unsafe uint Checksum(byte[] data)
{
    uint sum = 0;
    fixed (byte* p = data)          // 이 블록 동안만 data를 고정한다
    {
        for (int i = 0; i < data.Length; i++)
            sum += p[i];            // 범위 검사가 없다. 넘으면 남의 메모리를 읽는다
    }
    return sum;                     // 블록을 나가면 고정이 풀린다
}

관리 힙의 배열에 포인터를 얻으려면 fixed로 고정해야 한다. GC가 압축하며 배열을 옮기면 포인터가 옛 주소를 가리키기 때문이다. fixed는 그 블록 동안만 고정하고, 고정한 사실을 스택에 기록만 하므로 싸다. 다만 고정된 객체가 0세대 한가운데 오래 남으면 그 주변을 압축하지 못한다(GC 동작과 세대). 오래 고정해야 하는 버퍼는 POH에 만들거나 네이티브 메모리로 잡는다.

포인터 없이도 대부분의 일은 된다. 스택 버퍼는 stackalloc을 Span<T>에 받으면 unsafe 없이 쓰고, 바이트를 구조체로 다시 보는 일은 MemoryMarshal이 한다(ref와 Span). 이 방법들은 범위 검사를 유지한다. 포인터는 그 검사를 벗어나야 할 이유가 측정으로 확인됐을 때 쓴다.

GC가 모르는 메모리

방법무엇을 하나알아 둘 점
NativeMemory.Alloc, Free (.NET 6)C의 malloc·free에 해당한다. AlignedAlloc으로 정렬도 정한다GC가 모른다. 해제를 잊으면 프로세스가 끝날 때까지 남는다
Marshal.AllocHGlobal, FreeHGlobal예전부터 있던 같은 일새 코드는 NativeMemory를 쓴다
GC.AddMemoryPressure네이티브로 크게 잡은 양을 GC에 알린다작은 관리 객체가 큰 네이티브 메모리를 쥐고 있을 때, GC가 그 객체를 빨리 거두도록 재촉한다
SafeHandle 파생 타입네이티브 자원 하나를 감싸 해제를 보장한다파이널라이저를 스스로 가져 바깥 클래스가 직접 짤 필요가 없다(IDisposable과 결정적 해제)

네이티브 메모리는 GC 지표에 잡히지 않는다. GC 힙은 그대로인데 프로세스 메모리만 오르면 이쪽을 의심한다(GC 언어의 메모리 누수, 할당과 실제 확보).

P/Invoke: DllImport에서 LibraryImport로

// .NET 7 이후: 마샬링 코드를 빌드 때 소스 생성기가 만든다
internal static unsafe partial class Zstd   // byte* 매개변수가 있어 unsafe가 필요하다
{
    [LibraryImport("libzstd", EntryPoint = "ZSTD_compress")]
    internal static partial nuint Compress(byte* dst, nuint dstCap,
                                          byte* src, nuint srcSize, int level);

    [LibraryImport("libzstd", StringMarshalling = StringMarshalling.Utf8)]
    internal static partial nint ZSTD_getErrorName(nuint code);   // 문자열은 변환 비용이 든다
}

DllImport는 처음 부를 때 런타임이 마샬링 스텁을 실행 중에 만든다. Native AOT처럼 실행 중에 코드를 만들 수 없는 환경과 맞지 않고, 스텁이 무엇을 하는지 보이지도 않는다. LibraryImport는 같은 스텁을 소스 생성기가 빌드 때 C# 코드로 만들어 둔다. 생성된 코드를 열어 보면 어떤 인자가 복사되고 고정되는지 그대로 보인다(리플렉션과 소스 생성기, JIT와 AOT).

넘기는 것마샬링비용
int, double, 포인터, nint블리터블. 그대로 넘긴다거의 없다
블리터블 필드만 든 구조체그대로 넘긴다. 참조로 넘기면 고정만 한다작다
블리터블 원소의 배열, Span고정하고 첫 원소 주소를 넘긴다작다. 고정하는 동안 GC가 옮기지 못한다
stringUTF-8이나 UTF-16 사본을 만들어 넘긴다호출마다 할당과 복사
bool, char네이티브 쪽 크기가 정해져 있지 않아 변환한다작지만 크기를 명시해야 틀리지 않는다
참조 필드가 든 구조체, 클래스필드마다 변환한 사본을 만든다크다. 경계에서 피한다

라이브러리 이름은 확장자를 빼고 적는다. 런타임이 Windows에서는 libzstd.dll, Linux에서는 libzstd.so, macOS에서는 libzstd.dylib를 찾는다. 이름이 플랫폼마다 크게 다르면 NativeLibrary.SetDllImportResolver로 직접 고른다.

네이티브가 C#을 부를 때: 함수 포인터

네이티브 라이브러리가 콜백을 받는 경우(로그 콜백, 진행 알림)에는 C# 9의 함수 포인터 delegate* unmanaged[Cdecl]<int, void>와 [UnmanagedCallersOnly]를 쓴다. 대리자를 넘기던 예전 방식은 대리자 객체가 GC로 회수되면 네이티브가 끊긴 주소를 부르는 문제가 있었다. UnmanagedCallersOnly가 붙은 정적 메서드는 객체가 없어 그런 일이 없고, 그 주소를 그대로 넘긴다. 대신 그 메서드 안에서 예외가 밖으로 새면 네이티브 스택을 되감을 방법이 없어 프로세스가 끝난다. 안에서 모두 잡는다.

선택 기준

상황쓸 것
버퍼를 빠르게 다룬다먼저 Span, MemoryMarshal, BinaryPrimitives. 범위 검사가 남는다
측정해 보니 범위 검사가 병목이다그 함수 안에서만 unsafe와 포인터
C 라이브러리를 부른다LibraryImport, 블리터블 인자, 핸들은 SafeHandle
아주 짧고 막히지 않는 네이티브 함수를 초당 수백만 번 부른다[SuppressGCTransition]을 검토한다. 스레드 상태 전환을 건너뛴다
큰 버퍼를 오래 고정해야 한다POH(GC.AllocateArray(..., pinned: true))나 NativeMemory

SuppressGCTransition은 위험한 최적화다. 그 함수가 실행되는 동안 스레드가 여전히 "관리 코드 실행 중"으로 보이므로, GC는 그 함수가 끝날 때까지 기다린다. 오래 걸리거나 막히는 함수에 붙이면 모든 스레드가 GC 멈춤에서 함께 기다린다. 몇십 ns 안에 끝나는 함수에만 붙인다.

게임 서버에서는

  • 네이티브 라이브러리는 덩어리로 부른다. 압축(zstd, LZ4), 암호(OpenSSL), 물리·길찾기(Recast) 같은 네이티브 라이브러리를 패킷마다 작은 단위로 부르면 경계 비용이 본체를 넘는다. 틱 끝에 모인 버퍼를 한 번에 압축하거나, 경로 탐색 요청을 모아 한 호출로 넘기는 식으로 경계를 넘는 횟수를 줄인다.
  • 경계의 인자는 블리터블로 설계한다. 문자열과 클래스를 넘기면 호출마다 사본이 생긴다. 바이트 버퍼와 길이, 정수 ID, 블리터블 구조체만 오가게 경계를 설계하면 마샬링이 고정 한 번으로 줄어든다(객체 배치와 타입 특성).
  • 크래시가 네이티브 쪽이면 관리 스택만으로는 안 보인다. 네이티브 라이브러리 안에서 난 접근 위반은 .NET 예외로 잡히지 않고 프로세스를 끝낸다. 덤프를 남기고, 네이티브 스택까지 보려면 그 라이브러리의 심볼도 함께 보관한다(크래시 덤프와 심볼).
  • unsafe 코드는 한곳에 모은다. 패킷 직렬화의 뜨거운 경로처럼 꼭 필요한 곳만 작은 클래스로 감싸고, 나머지 코드는 그 안전한 겉면만 쓴다. 문제가 생기면 볼 곳이 그 클래스뿐이다.

주의 사항

  • unsafe 안에서는 C++의 미정의 동작이 돌아온다. 범위 밖 쓰기는 옆 객체나 GC가 관리하는 정보를 덮고, 그 결과는 엉뚱한 곳의 크래시나 GC 도중의 손상으로 나타난다(미정의 동작).
  • 고정이 풀린 뒤에 포인터를 쓰지 않는다. fixed 블록 밖으로 포인터를 내보내거나 필드에 저장하면, 다음 GC가 배열을 옮긴 뒤 옛 주소를 쓴다.
  • 네이티브가 버퍼를 나중에 쓰면 호출 동안의 고정으로는 모자란다. 비동기 API에 넘긴 버퍼는 완료될 때까지 고정돼 있어야 한다. POH나 네이티브 메모리로 잡는다.
  • bool과 long의 크기를 확인한다. Windows의 C long은 4바이트, Linux 64비트는 8바이트다. C 헤더의 타입을 그대로 옮기지 말고 크기가 정해진 타입(int, nint, CLong)으로 맞춘다.
