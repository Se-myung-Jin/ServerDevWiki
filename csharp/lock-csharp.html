먼저 읽을 것: 동기화 객체 · 데드락

핵심 요약

C#의 lock 문은 새 장치가 아니라 Monitor.Enter와 Monitor.Exit를 try/finally로 감싼 것이다. 블록을 어떻게 빠져나가든 락이 풀린다. Monitor는 같은 스레드가 다시 잡아도 막히지 않는 재진입 락이고, 경합이 없으면 객체 헤더 한 칸만 건드리고 끝난다.

제약은 하나에서 나온다. 잡은 스레드가 풀어야 한다. await 뒤의 코드는 다른 스레드에서 이어질 수 있으므로 lock 안에서는 await를 쓸 수 없다. 비동기 구간을 보호해야 하면 소유자가 없는 SemaphoreSlim을 쓴다.

동작 원리

lock은 Monitor 호출로 바뀐다

// 작성한 코드
lock (_gate)
{
    _count++;
}

// 컴파일러가 바꾼 코드(C# 4 이후)
bool taken = false;
try
{
    Monitor.Enter(_gate, ref taken);
    _count++;
}
finally
{
    if (taken) Monitor.Exit(_gate);
}

taken 변수가 있는 이유는 Enter와 try 사이에서 예외가 끼어드는 경우까지 막으려는 것이다. 락을 실제로 잡았을 때만 푼다. 예외, return, break 어느 길로 나가도 finally가 돈다.

락은 배제만 주지 않는다. 락에 들어가는 지점은 획득, 나오는 지점은 해제 순서를 가진다. 그래서 임계 구역 안의 읽기와 쓰기가 구역 밖으로 밀려 나가지 않고, 앞 스레드가 구역 안에서 쓴 값을 다음 스레드가 본다(원자적 연산과 메모리 순서). lock으로 감싼 필드에 volatile을 따로 붙일 필요가 없는 이유다.

경합이 없으면 객체 헤더만 바꾼다

관리 힙의 모든 객체는 앞에 객체 헤더라는 한 워드를 달고 있다. 해시 코드나 락 상태가 여기 들어간다. 경합이 없으면 Monitor는 이 칸에 자기 스레드 번호를 원자적으로 써넣는 것으로 끝난다. 같은 스레드가 다시 잡으면 같은 칸의 재진입 횟수만 올린다.

남이 쥐고 있으면 곧바로 잠들지 않고 잠깐 돌며 다시 확인한다. 임계 구역이 짧으면 그사이 풀리기 때문이다. 그래도 못 잡으면 객체에 동기화 블록(sync block)을 붙이고 커널 이벤트로 잠든다. 이렇게 커지는 것을 인플레이션이라 부른다. 해시 코드를 이미 꺼낸 객체나 Monitor.Wait를 쓴 객체는 헤더에 자리가 모자라 처음부터 동기화 블록을 단다. 잠들고 깨는 비용은 PCB와 컨텍스트 스위칭에서 다뤘다.

.NET 9의 System.Threading.Lock

.NET 9와 C# 13부터는 락 전용 타입 System.Threading.Lock이 있다. 필드를 이 타입으로 선언하고 lock 문에 넘기면 컴파일러가 Monitor 대신 EnterScope()로 얻은 범위 객체를 using으로 감싸 쓴다. 객체 헤더를 빌려 쓰지 않는 전용 구현이라 더 가볍고, 같은 스레드의 재진입도 된다. 

private readonly Lock _gate = new();   // .NET 9 / C# 13

public void Add(int n)
{
    lock (_gate)          // _gate.EnterScope()를 using으로 감싼 코드가 된다
    {
        _total += n;
    }
}

함정이 하나 있다. 이 전용 경로는 lock에 넘긴 식의 정적 타입이 정확히 Lock일 때만 쓰인다. object 변수에 담아 넘기면 같은 객체가 Monitor로 잠긴다. 한쪽은 Lock으로, 다른 쪽은 object로 잠그면 두 경로가 서로를 막지 못한다. 컴파일러가 이 변환에 경고(CS9216)를 낸다.

await는 lock 안에 들어갈 수 없다

Monitor와 Lock은 모두 잡은 스레드를 기억하고, 다른 스레드가 Exit를 부르면 SynchronizationLockException을 던진다. await 뒤의 코드는 스레드 풀의 아무 스레드에서나 이어질 수 있다(동기화 컨텍스트). 그래서 컴파일러가 lock 블록 안의 await를 아예 오류(CS1996)로 막는다.

비동기 구간을 하나씩만 들어가게 하려면 SemaphoreSlim(1, 1)을 쓴다. 세마포어는 소유자를 기억하지 않으므로 다른 스레드가 풀어도 된다. 대신 재진입이 없다. 같은 흐름이 두 번 들어가려 하면 자기 자신을 기다리며 멈춘다. 

private readonly SemaphoreSlim _io = new(1, 1);

public async Task SaveAsync(Data d, CancellationToken ct)
{
    await _io.WaitAsync(ct);
    try
    {
        await _db.WriteAsync(d, ct);   // 여기서 다른 스레드로 넘어가도 괜찮다
    }
    finally
    {
        _io.Release();
    }
}

무엇으로 잠그나

락 객체는 나만 아는 것으로

락 대상문제
this그 인스턴스를 가진 바깥 코드도 같은 객체를 잠글 수 있다. 내 임계 구역이 남의 코드 때문에 길어지거나 교착된다
typeof(Foo)타입 객체는 프로세스 전체가 공유한다
문자열 리터럴인터닝 때문에 전혀 관계없는 코드의 같은 문자열과 한 객체다
공개 필드, 컬렉션 자체남이 잡을 수 있다. 컬렉션은 내부 구현이 자기를 잠그기도 한다
값 형식lock 문은 컴파일 오류다. Monitor.Enter(int)를 직접 부르면 매번 다른 상자로 박싱되어 아무것도 막지 못한다(박싱)

기본은 private readonly object _gate = new();, .NET 9 이후라면 private readonly Lock _gate = new();다. 바깥에서 볼 수 없으니 누가 이 락을 잡는지 이 클래스 안만 보면 다 안다.

게임 서버에서는

  • 락은 스레드 사이의 입구에만 둔다. 게임 상태를 로직 스레드 하나가 고치는 구조라면 락이 필요한 곳은 작업 큐와 결과 큐뿐이다(게임 서버 스레딩 모델). 캐릭터, 인벤토리, 파티마다 lock을 두기 시작하면 잡는 순서가 엇갈려 교착이 생기고, 틱마다 경합 비용이 쌓인다.
  • lock 안에서 부르는 것을 줄인다. 로그 출력, DB 호출, 이벤트 발행, 가상 메서드처럼 안에서 무엇을 할지 모르는 호출은 다른 락을 잡을 수 있다. 필요한 값을 복사해 락을 풀고 나서 부른다(데드락).
  • 경합은 카운터로 본다. dotnet-counters의 Monitor 락 경합 횟수가 틱마다 수천씩 오르면 어딘가에서 같은 락을 두고 다투고 있다. 어느 락인지는 추적으로 좁힌다(.NET 진단 도구).
  • 교착은 덤프에서 확인한다. 서버가 멈추면 덤프를 뜨고 SOS의 syncblk로 어느 스레드가 어느 락을 쥐었는지, clrstack -all로 누가 무엇을 기다리는지 본다(크래시 덤프와 심볼). thin lock 상태의 락은 syncblk에 나오지 않으니 스택과 함께 본다.
  • C++의 std::mutex와 재진입 규칙이 다르다. C#의 lock은 같은 스레드가 다시 잡아도 되지만 std::mutex는 멈춘다. 두 언어로 같은 구조를 옮길 때 재진입에 기대던 코드가 C++에서 교착된다(C++ 동시성).

주의 사항

  • lock이 지켜 주는 것은 블록 안뿐이다. 블록 안에서 꺼낸 리스트를 블록 밖에서 순회하면 그때부터는 아무도 막아 주지 않는다. 밖으로 넘길 것은 사본으로 넘긴다.
  • 재진입이 된다고 기대지 않는다. 같은 락을 여러 층에서 잡으면 어디까지가 임계 구역인지 코드에서 보이지 않는다. 공개 메서드만 잡고 내부 메서드는 "이미 잡혀 있다"는 전제로 짠다.
  • .Result나 .Wait()를 lock 안에서 부르지 않는다. await는 컴파일러가 막지만 동기 대기는 막지 않는다. 기다리는 작업이 같은 락을 필요로 하면 서로를 기다리며 멈춘다.
  • Lock과 object를 섞지 않는다. 같은 Lock 인스턴스를 어떤 곳은 Lock 타입으로, 어떤 곳은 object로 잠그면 서로 다른 장치로 잠긴다.
