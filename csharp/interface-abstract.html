먼저 읽을 것: 박싱 · 제네릭

핵심 요약

인터페이스는 무엇을 할 수 있는지(능력)를, 추상 클래스는 무엇인지(정체와 공통 골격)를 말한다. 관계없는 여러 타입에 같은 능력을 붙일 때는 인터페이스, 공통 상태와 구현을 물려줄 때는 추상 클래스다. 다중 상속이 되느냐는 그 결과이지 고르는 기준이 아니다.

비용도 다르다. 인터페이스 호출은 가상 호출보다 한 단계를 더 거쳐 대상을 찾고, 구조체를 인터페이스 타입으로 다루면 박싱이 일어난다. 대개는 문제가 안 되지만, 틱마다 수십만 번 도는 경로에서는 제네릭 제약이나 sealed로 그 비용을 없앤다.

기본 인터페이스 메서드(C# 8)는 공개 인터페이스에 멤버를 더해도 기존 구현이 깨지지 않게 하려고 들어왔다. 다만 그 기본 구현은 인터페이스 타입으로 부를 때만 보인다. Monster m으로 들고 있으면 m.Describe()가 컴파일되지 않고, ((IDescribable)m).Describe()여야 한다. 그리고 구조체가 기본 구현을 쓰면 그 호출에서 박싱된다. 상태를 둘 수 없으니 "골격을 물려주는" 추상 클래스를 대신하지는 못한다.

인터페이스 호출은 한 단계를 더 거친다

.NET 런타임은 인터페이스 호출을 가상 스텁 디스패치로 처리한다. 처음에는 호출 지점이 "지난번에 본 타입이면 그 구현으로" 가는 스텁을 쓰고, 여러 타입이 섞여 들어오면 타입과 인터페이스 멤버로 구현을 찾는 일반 경로로 바뀐다. 그래서 한 자리에 늘 같은 타입이 오면 가상 호출과 거의 같고, 수십 가지 타입이 번갈아 오면 눈에 띄게 느려진다. 최근 .NET은 동적 PGO로 자주 오는 타입을 관측해 "그 타입이면 직접 호출"을 넣기도 한다. 가상 호출과 비가상화 일반은 가상 함수와 다형성에서 C++와 함께 다뤘다.

구조체가 인터페이스를 구현할 때

struct Damage : IComparable<Damage> { public int Value; public int CompareTo(Damage o) => Value.CompareTo(o.Value); }

IComparable<Damage> boxed = dmg;          // 박싱. 힙에 사본이 생긴다
int a = boxed.CompareTo(other);           // 인터페이스 호출

static T Max<T>(T x, T y) where T : IComparable<T>
    => x.CompareTo(y) >= 0 ? x : y;       // T가 struct면 박싱 없이 Damage.CompareTo를 직접 부른다

구조체를 인터페이스 타입 변수에 담거나 인터페이스 매개변수로 넘기면 박싱되고, 그 뒤로는 상자 안의 사본을 고친다. 원본은 바뀌지 않는다. 같은 일을 제네릭 제약으로 받으면 JIT가 구조체 전용 코드를 만들어 직접 호출한다(제네릭). List<T>.Enumerator가 구조체이고 foreach가 그것을 직접 쓰는 것도 같은 이유다. IEnumerable<T>로 받아 순회하면 열거자가 박싱된다.

구현이 하나뿐이고 바뀔 계획도 없는 곳에 인터페이스를 미리 만들 필요는 없다. 한 층이 늘고 호출이 간접이 될 뿐이다. 두 번째 구현이나 테스트 대역이 필요해질 때 뽑아내도 늦지 않다.

게임 서버에서는

  • 틱마다 도는 호출은 인터페이스 뒤에 숨기지 않는다. 수만 개 엔티티를 IUpdatable 목록으로 들고 Update()를 부르면 호출마다 스텁을 거치고, 종류가 섞여 있어 예측도 잘 안 된다. 종류별 목록으로 나눠 구체 타입으로 돌리면 간접 호출이 사라지고 인라인도 된다(메모리 배치와 자료구조).
  • 상속 계층에 끝이 있으면 sealed를 붙인다. sealed class Monster로 두면 JIT가 그 타입으로의 가상 호출과 인터페이스 호출을 직접 호출로 바꾸고 인라인할 수 있다. 타입 검사(is Monster)도 단순 비교 하나가 된다.
  • 패킷 처리기 등록은 인터페이스 하나로 충분하다. IPacketHandler<T>를 메시지마다 구현하게 하고, 등록할 때 번호로 찾는 표에 넣는다. 처리기 호출은 패킷당 한 번이라 간접 호출 비용이 문제 되지 않는다. 비용을 신경 쓸 곳은 처리기 안의 로직이다.

주의 사항

  • 기본 인터페이스 메서드는 구현 클래스 변수로 부를 수 없다. 인터페이스 타입으로 바꿔야 보이고, 구조체는 그 과정에서 박싱된다.
  • 공개 인터페이스에 멤버를 더하는 것은 깨지는 변경이다. 다른 팀이나 다른 어셈블리가 구현하고 있다면 기본 구현을 주거나 새 인터페이스로 나눈다.
  • 구조체를 인터페이스로 받아 고치면 원본이 안 바뀐다. 박싱된 사본을 고친 것이기 때문이다. 변경이 필요한 구조체는 제네릭 제약과 ref로 넘긴다.
  • 추상 클래스 생성자에서 가상 메서드를 부르지 않는다. C#은 파생 클래스의 오버라이드가 불리는데, 그 시점에 파생 클래스 생성자 본문은 아직 돌지 않았다. C++과 동작이 반대다(가상 함수와 다형성).
