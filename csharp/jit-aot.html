먼저 읽을 것: 컴파일과 링킹 · 프로그램이 올라가는 과정

핵심 요약

JIT(Just-In-Time)는 실행하면서 중간 코드(.NET의 IL)를 기계어로 바꾸고, AOT(Ahead-Of-Time)는 실행 전에 미리 바꿔 둔다.

JIT는 시작이 느린 대신 실제로 실행되는 모습을 보고 다시 최적화할 수 있다. AOT는 시작이 빠르고 예측 가능한 대신 그 정보를 쓰지 못하고, 실행 중에 코드를 만들어 내는 기능을 잃는다. 시작 속도와 최고 성능이 맞바뀐다. 오래 도는 게임 서버는 JIT 쪽이 기본이고, 시작이 잦거나 JIT를 금지하는 플랫폼은 AOT를 쓴다.

JIT가 AOT보다 빠를 수 있는 이유는 실행 중에만 아는 정보가 있기 때문이다. 어떤 분기가 주로 참인지, 인터페이스 호출에 실제로 어떤 타입이 오는지를 보면, 자주 오는 타입을 먼저 확인하고 그 메서드를 인라인하는 식으로 코드를 좁게 만들 수 있다. 정적 컴파일은 모든 경우를 감당해야 해서 보수적으로 만든다.

그 정보는 저절로 생기지 않는다. 처음 만든 코드에 계측을 넣어 분기 방향과 호출 대상 타입을 모으고, 다시 컴파일할 때 그 기록을 쓴다. .NET에서는 이것을 동적 PGO(Profile-Guided Optimization)라 부르고, .NET 8부터 기본으로 켜져 있다.

.NET은 같은 메서드를 여러 번 컴파일한다

.NET은 티어드 컴파일을 쓴다. 메서드가 처음 불리면 최적화를 거의 하지 않고 빨리 만든 코드(Tier0)로 실행한다. 자주 불리는 메서드만 골라 계측 정보를 반영해 제대로 최적화한 코드(Tier1)로 다시 컴파일하고 바꿔 끼운다. 오래 도는 루프는 실행 도중에 최적화 코드로 갈아타는 방식(OSR)으로 같은 혜택을 받는다. OSR은 .NET 7부터 x64와 Arm64에서 기본으로 켜져 있다.

ReadyToRun은 빌드할 때 미리 기계어를 만들어 어셈블리에 함께 담는 방식이다. 시작할 때 JIT를 거의 건너뛰지만 런타임과 JIT는 그대로 있어서, 자주 불리는 메서드는 나중에 Tier1로 다시 컴파일된다. Native AOT는 JIT를 아예 빼고 실행 파일 하나로 만든다. 시작과 메모리 사용량은 가장 작지만, 실행 정보로 다시 최적화하는 단계도 함께 없어진다.

AOT는 실행 중에 정해지는 것을 미리 알아야 한다

Native AOT와 Unity의 IL2CPP(IL을 C++로 바꿔 미리 컴파일한다, Unity의 C#)는 빌드 때 필요한 기계어를 전부 만들어 둔다. 그래서 실행 중에 새 코드가 필요한 기능이 막힌다.

막히거나 달라지는 것왜대응
Reflection.Emit, 동적 프록시만들 코드가 빌드 때 없다빌드 때 코드를 만드는 소스 생성기로 바꾼다
Expression.Compile같은 이유인터프리터로 돌아 느려지거나 동작하지 않는다. 뜨거운 경로에서 쓰지 않는다
실행 중에 정해지는 값 타입 제네릭(MakeGenericType 등)값 타입은 인자마다 기계어가 따로 필요한데, 어떤 조합이 올지 빌드 때 모른다쓰는 조합을 코드에 드러내 둔다. Unity는 2022부터 느린 공용 경로(full generic sharing)로 실패를 줄였다
문자열로 타입을 찾아 쓰는 코드코드에 참조가 안 보여 쓰지 않는 코드를 지우는 단계(trimming, code stripping)에서 잘려 나간다.NET은 [DynamicallyAccessedMembers]와 게시 때 나오는 trim 경고, Unity는 link.xml·[Preserve]

실무에서 가장 자주 터지는 곳은 직렬화다. 리플렉션으로 타입을 훑는 직렬화 라이브러리는 필요한 타입이 잘려 나가 빌드는 통과하고 실행할 때 실패한다. System.Text.Json의 소스 생성 모드나 MessagePack의 코드 생성처럼 직렬화 코드를 빌드 때 만들어 두는 방식으로 바꾼다.

게임 서버에서는

  • 배포 직후 첫 접속자가 Tier0 코드를 만난다. 패킷 처리, 직렬화, AI 틱처럼 뜨거운 경로가 처음 몇 분은 덜 최적화된 코드로 돌아 틱이 튄다. 포트를 열기 전에 뜨거운 경로를 가짜 입력으로 몇천 번 돌려 두고, 그 뒤에 readiness 체크를 통과시켜 트래픽을 받는다. PublishReadyToRun을 켜면 이 구간이 더 짧아진다.
  • 벤치마크는 워밍업 뒤에 잰다. 초반 구간을 섞어 재면 Tier0 코드가 섞여 실제보다 느리게 나온다. BenchmarkDotNet이 측정 전에 워밍업을 돌리는 이유다. 직접 만든 측정 코드도 같은 메서드를 충분히 돌린 뒤의 구간만 본다.
  • 클라이언트와 서버가 같은 코드를 쓰면 AOT 제약을 기준으로 맞춘다. Unity 클라이언트(IL2CPP)와 .NET 서버가 패킷 정의와 직렬화 코드를 공유한다면, 리플렉션·Reflection.Emit에 기대는 방식은 클라이언트에서 깨진다. 공유 코드는 소스 생성 방식으로 짠다(Unity와 .NET).

주의 사항

  • JIT가 느린 것은 시작 구간뿐이다. 오래 도는 프로그램에서는 실행 정보로 다시 최적화하는 JIT가 오히려 빠를 수 있다. 어느 지점에서 뒤집히는지는 재 봐야 안다.
  • AOT로 바꾼다고 처리량이 오르지는 않는다. 오르는 것은 시작 속도와 메모리다. 정상 구간의 처리량은 같거나 오히려 떨어질 수 있다.
  • trim 경고를 무시하지 않는다. Native AOT로 게시할 때 나오는 경고는 실행 중에 깨질 자리를 미리 알려 주는 것이다. 경고가 남은 채 배포하면 그 기능을 처음 쓰는 순간 실패한다.
