먼저 읽을 것: 해시 테이블 · struct와 class 고르기

핵심 요약

"같다"는 판단은 셋으로 갈린다. 같은 객체인가(참조 동등성), 내용이 같은가(값 동등성), 그리고 이 타입이 정한 기준으로 같은가(사용자 정의)다. C#에서 이 판단을 내리는 통로도 여럿이다. ==는 컴파일할 때 정적 타입으로 어떤 연산자를 부를지 정하고, Equals는 실행할 때 실제 타입의 재정의를 부른다. 그래서 담은 변수의 타입만 바꿔도 결과가 달라질 수 있다.

해시를 쓰는 컬렉션은 GetHashCode로 후보를 고르고 Equals로 확인한다. 둘의 기준이 어긋나거나, 키로 넣은 뒤 해시가 바뀌면 예외 없이 조용히 못 찾는다. 동등성 문제는 대개 이런 모양으로 드러난다.

동작 원리

통로마다 정해지는 시점이 다르다

통로언제 정해지나기본 동작
==컴파일할 때, 두 피연산자의 정적 타입으로class는 참조 비교. 내장 숫자형·enum·string·record·튜플은 값 비교. 직접 만든 struct는 연산자를 정의하기 전에는 쓸 수 없다
Equals(object)실행할 때, 실제 타입의 재정의로(가상 호출)class는 참조 비교, struct는 ValueType.Equals(필드 비교)
IEquatable<T>.Equals(T)컴파일할 때, 박싱 없이직접 구현한다. 제네릭 컬렉션의 기본 비교자가 이것을 먼저 찾는다
ReferenceEquals항상 참조 비교재정의할 수 없다. "정말 같은 객체인가"를 물을 때
 
string a = new string('x', 3), b = new string('x', 3);
Console.WriteLine(a == b);              // True: string의 == 연산자, 내용 비교

object oa = a, ob = b;
Console.WriteLine(oa == ob);            // False: object의 ==, 참조 비교
Console.WriteLine(oa.Equals(ob));       // True: 실행 중 string.Equals가 불린다

연산자는 오버로드이지 재정의가 아니다. 그래서 object로 담은 순간 string의 ==는 후보에서 사라진다. 제네릭 메서드 안의 T도 같아서, 제약 없는 T끼리 ==는 컴파일조차 되지 않고 where T : class를 붙이면 참조 비교가 된다. 제네릭 코드에서 값을 비교할 때는 EqualityComparer<T>.Default.Equals(a, b)를 쓴다.

해시 컬렉션은 해시로 고르고 Equals로 확인한다

GetHashCode의 약속어기면
Equals가 같다고 하면 해시도 같다같은 키로 찾아도 다른 버킷을 본다. 넣은 것을 못 찾고 같은 키가 둘 들어간다
컬렉션에 들어 있는 동안 해시가 바뀌지 않는다그림처럼 넣은 자리를 다시 찾지 못한다
다르면 해시가 달라도, 같아도 된다충돌은 정상이다. 다만 많으면 한 버킷에 몰려 느려진다
계산이 빠르고 고르게 흩어진다필드를 단순 XOR하면 (1, 2)와 (2, 1)이 같아진다. HashCode.Combine(.NET Core 2.1)을 쓴다

컬렉션 내부가 해시로 버킷을 고르는 구조는 해시 테이블에서 다뤘다. 여기서 볼 것은 키 타입의 책임이다. 키로 쓰는 타입은 해시에 쓰이는 필드가 바뀌지 않아야 한다. 가장 쉬운 방법은 키를 불변으로 만드는 것이다.

.NET의 string.GetHashCode()는 프로세스마다 다른 무작위 시드를 쓴다(.NET Core부터). 해시 충돌 공격을 막으려는 것이다. 그래서 문자열 해시값을 파일이나 DB에 저장하거나 서버끼리 비교하면 재시작 뒤에 맞지 않는다. 저장할 해시는 정해진 알고리즘(xxHash, FNV 등)으로 직접 계산한다.

struct의 기본 Equals는 느리다

struct가 Equals를 재정의하지 않으면 ValueType.Equals가 불린다. 부르려면 먼저 박싱이 필요하고(박싱), 비교는 두 갈래다. 필드에 참조가 없고 빈틈 없이 채워진 struct는 바이트를 통째로 비교하는 빠른 길로 가지만, 그 밖에는 리플렉션으로 필드를 하나씩 꺼내 비교한다. 기본 GetHashCode도 필드 일부만 보고 계산하는 경우가 있어 분포가 나쁠 수 있다. 키로 쓰는 struct는 직접 구현하거나 record struct로 정의한다.

record는 값 동등성을 만들어 준다

record(C# 9)와 record struct(C# 10)는 모든 필드를 비교하는 Equals, 그에 맞는 GetHashCode, IEquatable<T>, ==와 !=를 컴파일러가 만든다. 네 통로가 늘 같은 답을 낸다. class 기반 record는 EqualityContract라는 숨은 프로퍼티로 실제 타입까지 비교해, 기반 record와 파생 record가 필드가 같아도 같다고 하지 않는다.

주의할 점은 "모든 필드"다. record가 List<T> 같은 참조 형식 필드를 들고 있으면 그 필드는 참조로 비교된다. 내용이 같은 두 리스트를 든 record는 같지 않다.

선택 기준

하려는 일쓰는 것
정말 같은 객체인지 확인한다ReferenceEquals, 또는 is로 null 확인
값처럼 다루는 데이터, 키record·readonly record struct. 직접 구현할 일이 없다
직접 만든 struct를 자주 비교한다IEquatable<T>, Equals(object), GetHashCode, ==·!=를 같은 기준으로 함께 구현
타입은 그대로 두고 비교 기준만 바꾼다IEqualityComparer<T>를 컬렉션 생성자에 넘긴다
문자열 키StringComparer.Ordinal 또는 OrdinalIgnoreCase를 명시한다(문자열)

게임 서버에서는

  • 엔티티 ID 키는 readonly record struct로. 박싱 없는 비교와 좋은 해시가 함께 생긴다. 틱마다 수만 번 하는 엔티티 조회에서 차이가 난다.
  • 키를 가변 객체로 두지 않는다. 플레이어 객체를 HashSet<Player>에 넣었는데 Player가 이름이나 레벨로 Equals를 재정의했다면, 레벨이 오르는 순간 집합에서 찾지 못한다. 정체성이 있는 객체는 동등성을 재정의하지 않고 참조 비교로 두거나, 바뀌지 않는 ID로 비교한다.
  • 계정 이름 같은 문자열 키는 비교 기준을 정해 둔다. 대소문자를 무시할지, 어떤 정규화를 할지를 딕셔너리 생성 시점에 비교자로 고정한다. 곳곳에서 ToLower()를 부르면 할당이 생기고 문화권 규칙이 섞인다.
  • 문자열 해시를 영구 키로 쓰지 않는다. 위에서 말한 무작위 시드 때문에 재시작마다 값이 바뀐다. 샤딩 키, 캐시 키 계산에 GetHashCode를 쓰면 서버마다, 재시작마다 다른 곳으로 간다.

주의 사항

  • 넷을 함께 맞춘다. Equals(T), Equals(object), GetHashCode, ==·!= 중 하나만 바꾸면 통로마다 다른 답을 낸다. 컬렉션은 Equals와 해시를, 눈으로 보는 코드는 ==를 쓴다.
  • 해시가 같다고 같은 것이 아니다. 해시는 후보를 좁힐 뿐이다. 해시만 비교해 같다고 판단하는 코드는 충돌 하나에 틀린다.
  • 부동소수점 비교는 동등성에 맞지 않는다. NaN은 자기 자신과도 ==가 거짓이지만 Equals는 참이다. 좌표를 키로 쓰려면 격자 칸 번호 같은 정수로 바꿔 쓴다(수의 표현).
  • 상속과 값 동등성은 잘 맞지 않는다. 기반 클래스에서 재정의한 Equals는 파생 타입의 추가 필드를 모른다. 대칭성(a가 b와 같으면 b도 a와 같다)이 깨지기 쉽다. 값 동등성이 필요한 타입은 sealed로 두거나 record를 쓴다.
