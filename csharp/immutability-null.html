먼저 읽을 것: 값 형식과 참조 형식 · struct와 class 고르기

핵심 요약

C#에서 "바뀌지 않는다"는 표시는 셋이고, 고정하는 대상과 시점이 다르다. const는 컴파일할 때 값이 정해져 쓰는 쪽 코드에 값 자체가 박힌다. readonly 필드는 초기화식과 생성자 안에서만 대입할 수 있고(생성자 안에서는 여러 번도 된다) 생성자가 끝나면 고정된다. 참조 형식이면 참조만 고정되고 가리키는 객체는 그대로 바뀔 수 있다. 객체 전체를 못 바꾸게 하려면 타입을 불변으로 설계하거나 불변 컬렉션을 쓴다.

null도 둘로 갈린다. int?는 값과 "있음" 여부를 함께 담는 구조체 Nullable<int>로, 실행 중에도 다른 타입이다. string?은 C# 8의 nullable 참조 형식 표시로, 컴파일러의 흐름 분석일 뿐 실행 중에는 아무것도 바뀌지 않는다. 경고가 없다고 null이 들어오지 않는 것은 아니다.

그래서 const는 원주율이나 바이트 수처럼 절대 바뀌지 않는 값에만 쓴다. 최대 레벨, 패킷 버전, 서버 주소처럼 언젠가 바뀔 값을 공개 const로 두면, 그 값을 쓰는 다른 어셈블리는 다시 빌드할 때까지 옛 값을 쓴다. 대신 JIT 입장에서는 static readonly도 타입 초기화가 끝난 뒤에는 상수로 취급해 접어 넣을 수 있어서, 성능 차이는 대개 없다(JIT와 AOT).

C++ const와의 비교는 const와 참조에서 다뤘다. C#에는 "이 메서드는 객체를 바꾸지 않는다"를 적는 const 멤버 함수가 없고, 구조체의 readonly 멤버와 readonly struct가 그 일을 일부 맡는다(struct와 class 고르기).

readonly는 얕다

class Party {
    private readonly List<Player> members = new();
    public void Add(Player p) => members.Add(p);   // 된다. 리스트 내용은 바뀐다
    public void Reset() => members = new();          // 컴파일 오류. 다른 리스트로 바꾸지 못할 뿐이다
}

참조 형식 필드의 readonly는 "이 필드가 다른 객체를 가리키게 바꾸지 못한다"까지다. 리스트를 readonly로 두어도 원소는 얼마든지 더하고 뺀다. 밖으로 내보낼 때 IReadOnlyList<T>로 노출해도 마찬가지다. 받는 쪽이 고치지 못하게 막을 뿐, 원래 주인은 계속 고치고 받는 쪽은 그 변화를 본다. 정말 고정하려면 아래 표의 불변 타입을 쓴다.

int?와 string?은 이름만 비슷하다

구분int? (nullable 값 형식)string? (nullable 참조 형식)
실체Nullable<int> 구조체. 값과 HasValue를 함께 담는다그냥 string 참조. 원래부터 null이 될 수 있다

실행 중int와 다른 타입이다string과 완전히 같다
어기면값이 없는데 .Value를 읽으면 예외경고만 나고 실행은 된다

int?는 박싱할 때 특이하게 바뀐다. 값이 있으면 Nullable<int> 상자가 아니라 int가 박싱되고, 값이 없으면 상자 대신 진짜 null 참조가 나온다(박싱). 그래서 object o = (int?)null; o == null이 참이다.

nullable 참조 형식은 프로젝트에서 <Nullable>enable</Nullable>로 켜고, 컴파일러가 흐름을 따라가며 "여기서 null일 수 있다"고 경고한다. 실행 중에는 아무 검사도 없으므로 아래 자리에서 표시와 실제가 어긋난다.

  • 이 기능을 켜지 않은 라이브러리나 옛 코드가 돌려준 값은 컴파일러가 null 여부를 모른다(경고 없이 들어온다).
  • JSON 역직렬화나 리플렉션으로 만든 객체는 생성자를 거치지 않거나 필드를 건너뛰어, string으로 선언된 속성이 null인 채 남을 수 있다.
  • default(T)로 만든 구조체, 새로 만든 참조 형식 배열(new string[10])의 원소는 모두 null이다.
  • null 허용 연산자 !를 붙이면 컴파일러가 그 식을 더 보지 않는다. "확실히 null이 아니다"는 약속을 사람이 대신 하는 것이다.

게임 서버에서는

  • 기획 데이터 표는 불변으로 두고 통째로 바꾼다. 아이템·몬스터 표를 FrozenDictionary로 만들어 두면 조회가 빠르고, 여러 스레드가 락 없이 읽어도 안전하다. 핫 리로드할 때는 새 표를 다 만든 뒤 참조 하나를 바꿔 끼운다. 읽던 스레드는 옛 표를 끝까지 읽고, 다음 조회부터 새 표를 본다(게임 서버 스레딩 모델).
  • 패킷 버전과 프로토콜 번호를 const로 공유하지 않는다. 공용 어셈블리에 const int ProtocolVersion을 두면, 그 어셈블리만 갱신한 서버 모듈은 옛 번호를 계속 보낸다. 바뀔 수 있는 번호는 static readonly로 두거나 공용 코드를 함께 다시 빌드한다.
  • 패킷 경계에서는 nullable 표시를 믿지 않는다. 역직렬화한 패킷의 string Name은 선언과 달리 null일 수 있다. 처리기에 넘기기 전에 검증 단계에서 null과 길이를 직접 확인한다(게임에서 프로토콜 고르기).
  • !는 리뷰 대상이다. 경고를 없애려고 붙인 ! 하나가 나중에 그 자리의 NullReferenceException이 된다. 붙일 때는 왜 null이 아닌지를 주석으로 남기거나, 차라리 ?? throw로 바로 실패하게 한다.

주의 사항

  • readonly 구조체 필드에서 메서드를 부르면 방어적 복사가 일어날 수 있다. readonly 필드에 담긴 구조체가 readonly struct가 아니면, 컴파일러는 원본이 바뀌지 않게 사본을 만든 뒤 그 사본의 메서드를 부른다. 큰 구조체면 그만큼 느려진다(struct와 class 고르기).
  • IReadOnlyList는 불변이 아니다. 읽기 전용 "보기"일 뿐이라 원래 리스트가 바뀌면 같이 바뀐다. 다른 스레드에 넘기면 순회 중 수정 예외가 날 수 있다.
  • nullable 참조 형식을 켰다고 NullReferenceException이 사라지지 않는다. 실행 중 검사는 그대로 없다. 공개 API의 입구에서는 ArgumentNullException.ThrowIfNull로 직접 확인한다.
  • record의 불변은 얕다. record Party(List<Player> Members)의 Members는 다른 리스트로 못 바꿀 뿐 내용은 바뀌고, with로 만든 사본도 같은 리스트를 가리킨다.
