먼저 읽을 것: async와 await의 실체 · 게임 서버 스레딩 모델

핵심 요약

await는 멈추기 직전에 지금의 동기화 컨텍스트(SynchronizationContext.Current)를 기억해 둔다. 컨텍스트가 있으면 이어지는 코드를 그 컨텍스트에 맡겨 원래 있던 곳에서 실행하고, 없으면 완료를 받은 스레드 풀 스레드에서 그대로 이어 간다. UI 앱에서는 UI 스레드로, ASP.NET Core와 콘솔 서버에서는 아무 풀 스레드로 돌아간다.

문제는 돌아갈 곳이 막혀 있을 때다. 한 스레드짜리 컨텍스트에서 .Result로 완료를 기다리면, 그 스레드는 막혀 있고 이어지는 코드는 바로 그 스레드로 돌아가려 한다. 서로를 기다리는 데드락이다. 컨텍스트가 없는 서버에서는 이 데드락은 안 생기지만, 같은 코드가 풀 스레드를 막아 스레드 풀 고갈을 만든다.

정확히는 둘을 본다. SynchronizationContext.Current가 있으면 그 컨텍스트의 Post로 이어 실행을 넘기고, 없으면 지금의 TaskScheduler를 본다. 기본 스케줄러면 스레드 풀이다. 컨텍스트가 하는 일은 "이 콜백을 내 스레드에서 실행해 달라"는 요청을 받아 자기 큐에 넣는 것뿐이다. 그 큐를 비우는 루프(UI 메시지 루프, Unity 플레이어 루프)가 실제 실행을 맡는다.

AsyncLocal<T>에 담은 값이 await를 넘어 따라오는 것은 이와 다른 장치인 ExecutionContext 덕분이다. 실행 스레드를 정하는 것은 동기화 컨텍스트, 논리적 흐름의 값을 나르는 것은 실행 컨텍스트다.

.Result 데드락은 막은 스레드와 돌아갈 스레드가 같아서 생긴다

조건은 셋이 겹칠 때다. 한 번에 한 스레드만 실행하는 컨텍스트가 있고, 그 스레드에서 비동기 작업을 동기로 기다리고, 그 작업 안의 await가 컨텍스트를 붙잡아 돌아오려 한다. 하나라도 빠지면 데드락은 생기지 않는다. 그래서 같은 코드가 콘솔에서는 되고 UI 앱이나 옛 ASP.NET에서는 멈춘다.

ConfigureAwait(false)는 "돌아오지 않아도 된다"는 표시다

public async Task<Item[]> LoadAsync(int id)
{
    var bytes = await _store.ReadAsync(id).ConfigureAwait(false);   // 컨텍스트를 붙잡지 않는다
    return Parse(bytes);                                            // 아무 풀 스레드에서 돈다
}

ConfigureAwait(false)를 붙이면 그 await는 컨텍스트를 기억하지 않고, 완료를 받은 스레드에서 바로 이어 간다. 돌아가는 비용이 없고, 위의 데드락 고리에서 ②가 사라진다. 다만 그 await 하나에만 적용되고, 대상이 이미 끝나 있어 멈추지 않았다면 아무 효과가 없다. 메서드 안의 모든 await에 붙여야 일관된다.

코드의 자리ConfigureAwait(false)이유
범용 라이브러리(NuGet 패키지, 공용 모듈)붙인다누가 어떤 컨텍스트에서 부를지 모른다. UI 앱에서 불려도 데드락과 쓸데없는 복귀가 없어야 한다
ASP.NET Core·콘솔 서버의 앱 코드붙이지 않아도 된다원래 컨텍스트가 없어 효과가 없다
UI·Unity에서 await 뒤에 화면이나 게임 객체를 만진다붙이지 않는다메인 스레드로 돌아와야 만질 수 있다

.NET 8부터는 ConfigureAwait(ConfigureAwaitOptions.ForceYielding)처럼 옵션을 받는 형태도 있다. 끝나 있어도 일부러 양보하거나, 예외를 던지지 않고 기다리기만 하는 동작을 고를 수 있다.

서버에서는 데드락 대신 스레드 풀 고갈이 온다

ASP.NET Core와 콘솔 서버에는 컨텍스트가 없어서 .Result가 데드락을 만들지 않는다. 대신 기다리는 동안 풀 스레드 하나가 막힌다. 동시 요청이 몰리면 막힌 스레드가 늘고, 정작 그 Task들을 끝낼 이어 실행이 들어갈 스레드가 모자란다. .NET 스레드 풀은 최솟값을 넘어서면 스레드를 천천히 늘린다. .NET 6부터는 풀 스레드가 Task를 동기로 기다리는 것을 감지하면 스레드를 더 빨리 넣어 주지만, 몰리는 순간에는 여전히 몇 초 동안 모든 요청이 함께 느려진다(프로세스 경계, 스레드 풀과 실행 모델). 비동기를 동기로 감싸는 것(sync over async)이 서버에서 위험한 이유다.

게임 서버에서는

  • 로직 스레드로 돌아오는 컨텍스트를 직접 둘 수 있다. 로직 스레드 전용 SynchronizationContext를 만들어 Post가 콜백을 작업 큐에 넣게 하고, 틱마다 그 큐를 비운다. 로직 스레드에서 시작한 await는 그러면 다음 틱에 로직 스레드에서 이어진다. Unity의 메인 스레드 컨텍스트와 같은 구조다(서버 틱 루프).
  • 더 단순한 길은 결과를 메시지로 받는 것이다. 로직 스레드는 기다리지 않고 요청만 걸어 둔다. DB 작업은 스레드 풀에서 await로 돌고, 끝나면 결과를 Channel이나 작업 큐에 넣는다. 로직 스레드는 다음 틱에 꺼내 반영한다. 어느 스레드에서 무엇이 도는지가 코드에 드러나서 디버깅이 쉽다.
  • 시작할 때 한 번만 쓰는 동기 대기는 허용 범위다. Main에서 설정을 읽는 .GetAwaiter().GetResult()는 컨텍스트도 없고 동시 요청도 없어 문제가 없다. 요청을 처리하는 경로에서만 금지한다. 가능하면 static async Task Main으로 처음부터 비동기로 짠다.
  • Unity 클라이언트와 공유하는 코드는 둘 다 고려한다. 같은 네트워크 라이브러리가 서버(컨텍스트 없음)와 Unity(메인 스레드 컨텍스트)에서 함께 쓰이면, 라이브러리 안에서는 ConfigureAwait(false)를 붙이고 게임 객체를 만지는 쪽만 메인 스레드로 돌아오게 한다.

주의 사항

  • ConfigureAwait(false)는 데드락의 근본 해결이 아니다. 내 코드에 다 붙여도, 내가 부르는 라이브러리 하나가 컨텍스트를 붙잡으면 같은 데드락이 난다. 근본 해결은 동기로 기다리지 않는 것이다.
  • ConfigureAwait(false) 뒤에는 컨텍스트가 필요한 일을 하지 않는다. UI 컨트롤, Unity 객체, 로직 스레드 전용 상태를 그 뒤에서 만지면 다른 스레드에서 만지게 된다.
  • Task.Run 안에서 .Result를 쓰는 우회도 비용이 있다. 컨텍스트가 없는 풀 스레드에서 기다리니 데드락은 피하지만, 풀 스레드 하나가 그동안 막힌다.
  • await 뒤 스레드가 바뀌었는지 가정하지 않는다. 동기로 끝나면 같은 스레드에서 이어지고, 멈췄다 이어지면 다른 스레드일 수 있다. 스레드 로컬 값([ThreadStatic])은 await를 넘어 믿을 수 없다.
