먼저 읽을 것: I/O 모델 · 스레드 풀과 실행 모델 · 컴파일러가 바꿔 주는 것

핵심 요약

컴파일러는 async 메서드를 상태 기계로 바꾼다. await마다 멈출 수 있는 지점이 생기고, 어디까지 실행했는지와 await를 넘어 살아야 하는 지역 변수가 상태 기계의 필드에 담긴다. 기다릴 대상이 아직 안 끝났으면 메서드는 그 자리에서 빠져나오고, 대상이 끝나면 저장해 둔 지점부터 이어서 실행한다.

async는 스레드를 만들지 않는다. I/O를 기다리는 동안에는 그 일을 맡아 도는 스레드가 아예 없다. 그래서 요청 하나가 빨라지지는 않고, 같은 스레드 수로 더 많은 요청을 동시에 받을 수 있게 된다. 비동기를 쓰는 이유는 속도가 아니라 규모다.

동작 원리

멈추면 메서드를 빠져나오고, 끝나면 이어서 실행한다

await x를 만나면 컴파일러가 넣어 둔 코드가 다음 순서로 돈다.

  1. x.GetAwaiter()로 기다리는 객체(awaiter)를 얻고 IsCompleted를 묻는다.
  2. 이미 끝났으면 멈추지 않고 GetResult()로 결과를 받아 바로 다음 줄로 간다. 이것이 동기 완료 빠른 경로다.
  3. 안 끝났으면 상태 번호를 적고, awaiter에 "끝나면 이 상태 기계의 MoveNext를 불러 달라"고 맡긴 뒤 메서드에서 빠져나온다.
  4. 대상이 끝나면 맡겨 둔 콜백이 MoveNext를 부르고, 상태 번호로 그 지점에 뛰어 이어 간다.

await할 수 있는 것은 Task만이 아니다. GetAwaiter()를 가지고, 그 결과가 IsCompleted, OnCompleted, GetResult를 가지면 무엇이든 된다(awaiter 패턴). ValueTask, Task.Yield(), 소켓의 비동기 메서드가 이 패턴으로 돈다.

상태 기계는 처음 멈출 때 힙으로 간다

릴리스 빌드에서 상태 기계는 구조체로 만들어진다. 끝까지 한 번도 멈추지 않으면 스택에서 쓰이고 사라지므로 상태 기계 자체의 할당이 없다. 처음으로 실제로 멈추는 순간, 런타임이 이 구조체를 힙의 상자 객체로 옮긴다(박싱). 멈춘 뒤에도 살아 있어야 하기 때문이다. 디버그 빌드는 디버깅 편의상 처음부터 클래스로 만든다.

그래서 await를 넘어 사는 지역 변수는 결국 힙에 있다. Span<T> 같은 ref struct를 await 앞뒤에 걸쳐 쓸 수 없는 이유다(ref와 Span). 멈추지 않고 끝나는 경로가 많을수록 할당이 줄고, 이 성질을 반환 타입까지 넓힌 것이 Task와 ValueTask다. 숨은 클래스로 바뀌는 다른 문법은 컴파일러가 바꿔 주는 것에서 다룬다.

I/O를 기다리는 동안 스레드는 없다

소켓 수신을 비동기로 걸면, 요청은 OS와 장치가 처리하고 끝나면 완료 통지가 온다. Windows는 IOCP, Linux는 epoll이 그 통지를 전하고, .NET 런타임이 그것을 받아 스레드 풀에서 이어지는 코드를 돌린다(완료 알림 기반 서버). 기다리는 시간 동안 아무 스레드도 그 요청 때문에 잠들어 있지 않다.

첫 await 전까지는 호출한 스레드에서 동기로 돈다

async를 붙였다고 메서드가 다른 스레드에서 시작하지 않는다. 첫 await에서 실제로 멈출 때까지는 부른 스레드가 그대로 실행한다. 그 앞에 무거운 계산이나 동기 I/O가 있으면 부른 쪽이 그만큼 막힌다. "async 메서드를 불렀는데 왜 호출이 안 돌아오나"의 흔한 원인이다.

선택 기준

I/O는 await, CPU 계산은 Task.Run

일의 종류쓰는 것이유
소켓, 파일, DB, HTTP비동기 API를 바로 await기다리는 동안 스레드를 쓰지 않는다
무거운 계산(길찾기, 압축, 직렬화)Task.Run으로 스레드 풀에 넘긴다계산은 어딘가의 스레드가 해야 한다. 지금 스레드를 막지 않으려고 옮긴다
동기 API만 있는 I/O되도록 비동기 API로 바꾼다Task.Run으로 감싸면 막히는 스레드가 풀 스레드로 바뀔 뿐 줄지 않는다

Task.Run(() => db.Query())는 비동기처럼 보이지만, 풀 스레드 하나가 쿼리 내내 막힌다. 서버에서 이런 "가짜 비동기"가 많으면 동기 코드와 똑같이 스레드 풀이 고갈된다. 비동기는 맨 아래 I/O까지 이어져야 효과가 있다(async all the way).

게임 서버에서는

  • await 뒤는 다른 스레드다. 서버에는 동기화 컨텍스트가 없어서, 이어지는 코드는 완료를 받은 스레드 풀 스레드에서 돈다. 로직 스레드에서 await db.LoadAsync()를 한 뒤 게임 상태를 고치면 단일 쓰기 규칙이 깨진다. 결과는 작업 큐에 메시지로 넣거나, 로직 스레드로 돌아오게 만든다(게임 서버 스레딩 모델, 동기화 컨텍스트).
  • 틱 루프 안에서는 기다리지 않는다. 틱 루프는 전용 스레드에서 동기로 돌고, DB·외부 API처럼 기다려야 하는 일만 비동기로 걸어 둔다. 결과가 오면 다음 틱에 반영한다(서버 틱 루프).
  • 패킷마다 도는 경로의 할당을 본다. 실제로 멈추는 await마다 상태 기계 상자와 Task가 할당된다. 초당 수십만 번 도는 처리기라면 동기로 끝나는 코드로 짜거나, ValueTask와 풀링 빌더로 할당을 줄인다.
  • C++ 코루틴과 같은 생각, 다른 책임. 둘 다 함수를 상태 기계로 바꾼다. C#은 Task, 스레드 풀, 컨텍스트, 그리고 멈춘 동안의 수명을 지켜 주는 GC까지 런타임이 함께 준다(C++20 코루틴).

주의 사항

  • async는 빠르게 만드는 장치가 아니다. 요청 하나의 지연은 그대로이거나 조금 늘어난다. 얻는 것은 적은 스레드로 많은 동시 요청을 받는 능력이다.
  • 비동기 메서드를 동기로 기다리지 않는다. .Result, .Wait()는 스레드를 막아 비동기의 이득을 없애고, 환경에 따라 데드락을 만든다(동기화 컨텍스트).
  • async를 빼고 Task를 그대로 돌려줄 때는 조심한다. return inner.DoAsync();처럼 await 없이 넘기면 상태 기계가 안 생겨 싸다. 대신 using이나 try 범위가 Task가 끝나기 전에 닫히고, 예외 스택에서 이 메서드가 빠진다. 단순히 넘기기만 하는 메서드에만 쓴다.
  • await 앞의 동기 구간을 짧게 둔다. 첫 await까지는 부른 스레드가 실행한다. 무거운 준비 작업이 있으면 그것까지 부른 쪽을 막는다.
