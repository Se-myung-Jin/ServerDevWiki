먼저 읽을 것: IDisposable과 결정적 해제 · 취소와 시한

핵심 요약

Generic Host는 .NET 서버 프로세스의 뼈대다. 설정을 읽고, 로깅을 붙이고, 객체를 만들어 주는 의존성 주입(DI) 컨테이너를 세우고, 등록된 백그라운드 서비스를 순서대로 시작했다가 종료 신호가 오면 거꾸로 멈춘다. 웹 서버(ASP.NET Core)도 같은 틀 위에 있고, 소켓을 직접 다루는 게임 서버도 이 틀에 올리면 시작과 종료를 직접 짤 일이 줄어든다.

DI 컨테이너는 객체마다 수명을 정해 둔다. 하나만 만들어 계속 쓰는 Singleton, 범위마다 하나인 Scoped, 달라고 할 때마다 새로 만드는 Transient다. 함정은 수명이 다른 것을 섞을 때 생긴다. 오래 사는 객체가 짧게 살아야 할 객체를 생성자로 받으면, 짧은 쪽이 오래 사는 쪽에 붙잡혀 함께 오래 산다.

동작 원리

호스트가 묶는 것

var builder = Host.CreateApplicationBuilder(args);   // .NET 7부터. 설정·로깅·DI가 기본으로 붙는다

builder.Services.Configure<GameOptions>(builder.Configuration.GetSection("Game"));
builder.Services.AddSingleton<SessionManager>();
builder.Services.AddSingleton<IItemTable, FrozenItemTable>();
builder.Services.AddHostedService<NetworkListener>();   // 소켓 받기
builder.Services.AddHostedService<GameLoop>();          // 틱 루프

using var host = builder.Build();
await host.RunAsync();   // 시작하고, 종료 신호가 올 때까지 기다리고, 멈추고, 정리한다
묶는 것기본으로 하는 일
설정appsettings.json, 환경별 appsettings.{Environment}.json, 환경 변수, 명령줄 인자를 차례로 겹쳐 읽는다. 뒤의 것이 앞의 값을 덮는다
로깅콘솔 등 기본 출력에 ILogger<T>를 연결한다
DI 컨테이너등록된 타입을 생성자 인자에 맞춰 만들어 준다
수명 관리호스팅 서비스를 시작·정지하고, Ctrl+C와 SIGTERM을 종료 요청으로 받는다(시그널과 프로세스 종료)

시작과 종료의 순서

BackgroundService는 오래 도는 일을 맡는다

public sealed class GameLoop : BackgroundService
{
    private readonly SessionManager _sessions;
    private readonly ILogger<GameLoop> _log;

    public GameLoop(SessionManager sessions, ILogger<GameLoop> log)
        => (_sessions, _log) = (sessions, log);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();   // 첫 await 전까지는 시작 경로에서 동기로 돈다. 바로 양보한다
        while (!stoppingToken.IsCancellationRequested)
        {
            RunTick();
            await Task.Delay(TickInterval, stoppingToken);   // 종료 요청에 바로 깨어난다
        }
    }
}

ExecuteAsync는 호스트가 시작할 때 불리고, 돌려준 Task가 끝날 때까지 서비스가 살아 있다. 함정이 하나 있다. async 메서드는 첫 await까지 부른 스레드에서 동기로 돈다(async와 await의 실체). 첫 await 전에 오래 걸리는 일이 있으면 다음 서비스의 시작이 그만큼 밀린다. 틱 루프처럼 계속 도는 일은 첫 줄에서 양보하거나, 전용 스레드를 만들어 넘긴다(서버 틱 루프).

ExecuteAsync 안에서 예외가 새어 나가면 .NET 6부터 기본 동작은 호스트 전체를 멈추는 것이다(BackgroundServiceExceptionBehavior.StopHost). 틱 루프가 예외 하나로 끝났는데 프로세스는 살아서 접속만 받는 상태보다 낫다는 판단이다. 서비스 하나의 실패를 견디게 하려면 루프 안에서 잡아 기록하고 이어 간다(비동기에서 예외 다루기). 받은 stoppingToken은 루프 안의 모든 비동기 호출에 넘긴다(취소와 시한).

DI 수명 세 가지

수명언제 만들어지나언제 정리되나맞는 것
Singleton처음 요청할 때 하나호스트가 끝날 때 컨테이너가 Dispose세션 관리자, 기획 데이터 표, 설정, 상태 없는 서비스
Scoped범위마다 하나. 웹이라면 요청 하나가 범위다그 범위가 Dispose될 때DB 컨텍스트(EF Core의 DbContext, ORM과 저장 설계), 작업 단위
Transient요청할 때마다 새로그것을 만든 범위가 끝날 때(Dispose를 구현했다면)가볍고 상태가 없는 도우미

오래 사는 쪽이 짧은 쪽을 붙잡는다

public sealed class RankingService(IServiceScopeFactory scopes)   // Singleton
{
    public async Task SaveAsync(Ranking r, CancellationToken ct)
    {
        await using var scope = scopes.CreateAsyncScope();        // 일 하나 = 범위 하나
        var db = scope.ServiceProvider.GetRequiredService<GameDbContext>();
        db.Rankings.Add(r);
        await db.SaveChangesAsync(ct);
    }                                                             // 범위가 끝나며 DbContext도 정리된다
}

웹 서버는 요청마다 프레임워크가 범위를 만들어 주지만, 소켓을 직접 다루는 게임 서버에는 그런 범위가 없다. 범위를 만들지 않고 루트 컨테이너에서 Scoped를 꺼내면 사실상 Singleton이 된다. 패킷 처리 하나, 저장 작업 하나처럼 "일 하나"를 직접 정해 범위를 만든다.

Transient도 조심할 것이 있다. 컨테이너는 자기가 만든 IDisposable을 기억해 두었다가 범위가 끝날 때 정리한다. 루트 컨테이너에서 IDisposable인 Transient를 계속 꺼내면, 그 객체들은 정리될 날을 기다리며 루트 컨테이너에 쌓인다. 서버가 끝날 때까지 회수되지 않는 누수다(GC 언어의 메모리 누수).

설정은 옵션 객체로 받는다

주입하는 타입값이 언제 정해지나쓰는 곳
IOptions<T>처음 읽을 때 한 번. 이후 바뀌지 않는다서버가 도는 동안 바뀌지 않는 값
IOptionsSnapshot<T>범위마다 다시 읽는다. Scoped요청마다 최신 값이 필요한 웹 코드
IOptionsMonitor<T>설정 파일이 바뀌면 갱신되고 OnChange로 알린다. Singleton오래 사는 서비스가 핫 리로드 값을 볼 때

.NET 8부터는 같은 인터페이스를 이름으로 여러 개 등록하는 키 지정 서비스(AddKeyedSingleton, [FromKeyedServices("redis")])도 있다. 저장소 구현을 "주 DB", "로그 DB"처럼 나눠 받을 때 쓴다.

선택 기준

무엇을어떻게
서버 내내 하나인 관리자, 표, 클라이언트(HttpClient 팩토리 포함)Singleton. 여러 스레드가 함께 쓰므로 스레드 안전해야 한다
DB 컨텍스트처럼 일 하나 동안만 살아야 하는 것Scoped. 범위는 직접 만든다
세션, 존, 몬스터처럼 실행 중에 수없이 생기고 사라지는 것DI로 만들지 않는다. 팩토리를 Singleton으로 두고 팩토리가 new로 만든다
시작과 종료가 있는 오래 도는 일BackgroundService로 등록한다

게임 서버에서는

  • 게임 객체는 컨테이너 밖에서 만든다. 세션이나 몬스터를 GetService로 만들면 생성마다 컨테이너 조회 비용이 들고, IDisposable이면 루트 컨테이너에 쌓인다. 의존성은 팩토리가 생성자에서 한 번 받아 두고, 게임 객체에는 필요한 것만 넘긴다.
  • 틱 루프와 리스너를 호스팅 서비스로 둔다. 시작 순서, 종료 신호, 종료 시한을 호스트가 맡는다. 정상 종료 때 새 접속을 막고 저장을 마치는 절차는 StopAsync에 둔다(드레이닝).
  • 기획 데이터와 밸런스 값은 IOptionsMonitor나 교체 가능한 표로 받는다. 파일이 바뀌면 새 표를 만들어 참조를 바꿔 끼운다. 이미 시작된 전투가 중간에 값이 바뀌어도 괜찮은지는 따로 정한다(불변과 null 다루기).
  • 시험에서는 바깥 의존을 바꿔 끼운다. 결제 API, 시계, 난수처럼 바깥에 기대는 것을 인터페이스로 등록해 두면, 시험에서 가짜 구현을 넣어 시한·실패 경로를 재현할 수 있다. 시계는 .NET 8의 TimeProvider를 주입한다.

주의 사항

  • 생성자에서 오래 걸리는 일을 하지 않는다. 컨테이너는 생성자를 동기로 부른다. 생성자에서 DB를 읽으면 그 서비스를 처음 요청한 쪽이 통째로 기다린다. 무거운 준비는 호스팅 서비스의 시작 단계에서 비동기로 한다.
  • 서비스 로케이터로 쓰지 않는다. 아무 데서나 IServiceProvider를 받아 필요한 것을 꺼내면 의존성이 생성자에 드러나지 않는다. 범위를 만드는 곳(팩토리, 디스패처) 말고는 생성자로 받는다.
  • ValidateScopes와 ValidateOnBuild를 개발 환경에서 켜 둔다. 수명 함정과 등록 누락을 시작할 때 잡는다. 운영에서는 시작 비용 때문에 기본이 꺼져 있다.
  • 종료 시한을 넘기는 정리는 잘린다. 저장이 오래 걸리면 시한과 컨테이너 쪽 유예 시간을 함께 늘린다. 둘이 어긋나면 정리 도중에 강제로 끝난다(시그널과 프로세스 종료).
