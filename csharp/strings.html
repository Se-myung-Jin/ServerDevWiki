먼저 읽을 것: 값 형식과 참조 형식 · 불변과 null 다루기

핵심 요약

C#의 string은 힙에 놓이는 불변 객체다. Replace, Substring, +처럼 고치는 것처럼 보이는 연산은 모두 새 문자열을 할당한다. 루프에서 문자열을 이어 붙이면 단계마다 지금까지의 내용을 통째로 복사해, 복사량이 반복 횟수의 제곱으로 는다. 반복해서 붙일 때는 StringBuilder를 쓰고, 서버의 뜨거운 경로에서는 아예 문자열을 만들지 않고 Span<char>이나 UTF-8 바이트로 다룬다.

두 번째 함정은 비교다. string API 중 일부는 비교 방식을 적지 않으면 현재 문화권 규칙으로 비교한다. 느리고, 서버 설정에 따라 결과가 바뀐다. 식별자와 프로토콜 문자열은 항상 StringComparison.Ordinal로 비교한다.

동작 원리

이어 붙일 때마다 새 문자열이 생긴다

한 문장 안에서 몇 개를 붙이는 a + b + c는 문제가 아니다. 컴파일러가 string.Concat(a, b, c) 한 번으로 바꿔, 길이를 미리 계산해 한 번만 할당한다. 문제는 루프에서 결과를 누적할 때다.

상황쓸 것
몇 개를 한 번에 붙인다+ 그대로, 또는 보간 문자열
목록을 구분자로 잇는다string.Join
반복 횟수를 모르는 누적StringBuilder(크기를 알면 용량을 미리 준다)
최종 길이를 정확히 안다string.Create(length, state, (span, s) => ...)로 할당 한 번에 직접 채운다
문자열이 아예 필요 없다(로그 버퍼, 패킷)Span<char>·Span<byte>에 TryFormat으로 바로 쓴다

보간 문자열은 C# 10부터 처리기로 바뀐다

예전의 $"hp={hp}"는 string.Format으로 바뀌어, 형식 문자열을 실행 중에 해석하고 값 형식 인자를 object로 박싱했다. C# 10부터는 컴파일러가 DefaultInterpolatedStringHandler로 바꿔, 조각마다 AppendLiteral·AppendFormatted<T>를 부르는 코드를 만든다. 형식 해석과 박싱이 사라지고 버퍼는 풀에서 빌린다(컴파일러가 바꿔 주는 것).

같은 장치를 라이브러리가 쓸 수 있다. 처리기를 받는 메서드는 보간 문자열을 문자열로 만들기 전에 받는다. Debug.Assert의 메시지나 일부 로깅 API는 이것으로 조건이 거짓일 때나 로그 수준이 꺼져 있을 때 문자열을 아예 만들지 않는다. 그렇지 않은 일반 Log(string)에 보간 문자열을 넘기면 로그가 꺼져 있어도 문자열은 만들어진다.

인터닝은 중복을 없애는 대신 수명을 늘린다

인터닝은 같은 내용의 문자열을 프로세스 안에 하나만 두는 장치다. 소스의 문자열 리터럴은 런타임이 인턴 풀에 넣어, 같은 리터럴은 같은 객체를 가리킨다. 실행 중에 만든 문자열은 string.Intern으로 직접 넣는다. 다만 리터럴 인턴은 런타임의 동작이지 언어가 보장하는 것은 아니므로(CompilationRelaxations.NoStringInterning), 참조가 같다는 것에 기대는 코드는 쓰지 않는다.

인턴 풀에 들어간 문자열은 프로세스가 끝날 때까지 회수되지 않는다. 아이템 등급 이름처럼 종류가 정해진 값에는 맞지만, 사용자 이름이나 채팅 내용처럼 종류가 끝없는 값을 인턴하면 메모리가 계속 는다. 그리고 인턴하려면 그 문자열을 먼저 만들어야 하므로 할당은 이미 일어난 뒤다. 할당을 줄이고 싶은 것이라면 인터닝이 아니라 아래의 Span과 UTF-8 쪽이 답이다.

비교 방식을 적는다

비교무엇을 보나쓰는 곳
OrdinalUTF-16 코드 단위를 숫자로 비교한다. 가장 빠르다키, 명령어, 프로토콜 문자열, 파일 경로
OrdinalIgnoreCase대소문자만 무시한 서수 비교대소문자 구분 없는 명령어, HTTP 헤더 이름
CurrentCulture현재 문화권의 정렬 규칙사용자에게 보여 줄 목록 정렬
InvariantCulture문화권과 무관한 고정 규칙(언어 규칙은 적용된다)문화권과 무관하게 일정해야 하는 언어적 정렬

==와 Equals(string), Contains(string)은 기본이 서수 비교다. 반면 StartsWith(string), EndsWith(string), IndexOf(string), CompareTo는 비교 방식을 주지 않으면 현재 문화권으로 비교한다. 그 결과가 서버 문화권 설정에 따라 바뀌고 SIMD 최적화도 받지 못한다는 점은 문자열 검색과 계산 한계에서 다뤘다. 대소문자 무시 비교를 ToLower()로 만들지 않는다. 문자열을 하나 더 만들고, 터키어의 i처럼 문화권마다 결과가 다르다.

문자열은 UTF-16이다

.NET 문자열은 char(UTF-16 코드 단위) 배열이다. 한글 한 글자는 char 하나지만, 이모지나 일부 한자는 서로게이트 쌍 char 두 개다. 그래서 Length는 글자 수가 아니라 코드 단위 수이고, 임의의 위치에서 자르면 쌍이 깨질 수 있다. 사용자가 보는 글자 수가 필요하면 StringInfo로 센다.

네트워크와 파일은 대개 UTF-8이다. 받은 바이트를 Encoding.UTF8.GetString으로 바꾸면 그때마다 문자열이 할당된다. C# 11의 UTF-8 리터럴 "MOVE"u8은 ReadOnlySpan<byte>를 바로 만들어, 받은 바이트와 할당 없이 비교할 수 있다. System.Text.Json의 Utf8JsonReader도 문자열을 만들지 않고 UTF-8 그대로 읽는다(ref와 Span).

게임 서버에서는

  • 틱마다 도는 경로에서 문자열을 만들지 않는다. 매 틱 $"Player {id} moved to {pos}"로 디버그 문자열을 만들어 두는 코드는 로그가 꺼져 있어도 할당을 낸다. 수천 명이면 GC가 바빠진다(GC 동작과 세대). 로그 수준 검사를 먼저 하거나, 처리기 기반 로깅이나 소스 생성 로깅(LoggerMessage)을 쓴다.
  • 채팅·명령어 파싱은 Span으로 자른다. Split은 조각마다 문자열을 할당한다. ReadOnlySpan<char>의 IndexOf와 슬라이스로 자르고, 숫자는 int.Parse(span)으로 바로 읽는다. 명령어 비교도 span.Equals("/w", StringComparison.Ordinal)처럼 서수로 한다.
  • 키 문자열 비교는 서수로 고정한다. Dictionary<string, T>는 기본이 서수 비교라 안전하지만, 대소문자를 무시하려면 StringComparer.OrdinalIgnoreCase를 넘긴다. 문화권 비교자를 쓰면 서버를 다른 지역 설정으로 띄운 날 같은 키가 다르게 판정된다.
  • 캐릭터 이름 길이는 바이트로도 제한한다. DB 컬럼과 패킷 필드는 바이트 단위인데 Length는 UTF-16 코드 단위다. 이모지가 섞이면 같은 Length라도 UTF-8 바이트 수가 크게 달라진다. 저장·전송 형식 기준으로 검사한다.

주의 사항

  • StringBuilder가 언제나 빠른 것은 아니다. 몇 개를 한 번 붙이는 자리에서는 string.Concat이 길이를 미리 알아 한 번에 할당하므로 더 빠르다. 루프에서 누적할 때만 쓴다.
  • Substring은 복사한다. 잘라 낸 길이만큼 새 문자열을 할당한다. 잠깐 보고 버릴 조각이면 AsSpan(start, length)로 본다.
  • 인터닝을 메모리 절약 기법으로 쓰지 않는다. 종류가 무한한 값을 넣으면 회수되지 않는 누수가 된다.
  • string.Empty와 ""는 같다. 둘 다 같은 객체를 가리키고 성능 차이도 없다. 빈 문자열 검사는 string.IsNullOrEmpty나 Length == 0으로 한다.
