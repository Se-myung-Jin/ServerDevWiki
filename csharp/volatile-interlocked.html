먼저 읽을 것: 원자적 연산과 메모리 순서 · C#의 lock

핵심 요약

volatile과 Interlocked는 서로 다른 문제를 푼다. volatile은 순서를 정한다. 값을 레지스터에 담아 두고 다시 읽지 않는 최적화를 막고, 읽기와 쓰기 앞뒤의 재배치를 한 방향씩 막는다. 하지만 원자성은 주지 않는다. count++는 volatile이어도 읽고, 더하고, 쓰는 세 단계라 그 사이에 다른 스레드가 끼어든다.

Interlocked는 읽고 고치고 쓰는 일을 CPU 명령 하나로 끝낸다. 증가, 더하기, 교환, 비교 후 교환이 쪼개지지 않고, 앞뒤 메모리 접근이 그 지점을 넘지 못하는 전체 펜스까지 함께 건다. 카운터와 상태 전환은 Interlocked, 한쪽만 쓰는 플래그는 volatile, 여러 값을 함께 바꾸는 일은 lock이다.

동작 원리

증가는 세 단계라 volatile로 지켜지지 않는다

volatile이 막는 것과 못 막는 것

C# 규격에서 volatile 필드의 읽기는 획득(acquire), 쓰기는 해제(release) 의미를 가진다. 획득 읽기 뒤의 접근은 그 읽기보다 앞으로 당겨지지 않고, 해제 쓰기 앞의 접근은 그 쓰기보다 뒤로 밀리지 않는다. 그래서 "데이터를 다 쓴 뒤 플래그를 세운다, 플래그를 본 뒤 데이터를 읽는다"는 한 방향 넘겨주기가 성립한다.

volatile이 하는 일volatile이 못 하는 일
루프 안의 읽기를 레지스터에 담아 두고 건너뛰지 못하게 한다읽고 고치고 쓰기를 하나로 묶기(++, +=)
읽기 뒤의 접근을 앞으로, 쓰기 앞의 접근을 뒤로 옮기지 못하게 한다쓰기 뒤에 오는 다른 변수의 읽기가 앞으로 당겨지는 것(쓰기→읽기 재배치)
한쪽이 쓰고 한쪽이 읽는 플래그여러 변수를 한꺼번에 일관되게 바꾸기

표의 둘째 줄 오른쪽이 잘 알려지지 않은 구멍이다. 해제 쓰기 다음의 획득 읽기는 서로 순서가 바뀔 수 있다. 두 스레드가 각자 자기 플래그를 세우고 상대 플래그를 읽는 방식(Dekker식 상호 배제)은 volatile만으로 짜면 둘 다 상대의 0을 읽을 수 있다. 이런 곳에는 전체 펜스를 거는 Interlocked나 lock을 쓴다.

volatile을 붙일 수 있는 타입도 정해져 있다. 참조 형식, int 이하 크기의 정수, char, float, bool, 그 크기의 열거형, IntPtr이다. long과 double에는 붙일 수 없다(CS0677). CLI 규격이 원자적 읽기·쓰기를 보장하는 것은 포인터 크기 이하의 정렬된 값뿐이고, 32비트 프로세스에서 8바이트 값은 두 번에 나눠 읽고 쓸 수 있기 때문이다.

필드 선언 대신 접근하는 자리에 순서를 적고 싶으면 Volatile.Read(ref x), Volatile.Write(ref x, v)를 쓴다. 어느 접근에 획득·해제가 걸리는지 코드에 드러나고, 필드의 다른 접근은 일반 접근으로 둘 수 있다.

Interlocked는 한 명령으로 끝낸다

Interlocked 연산은 모두 전체 펜스다. 그 연산 앞의 읽기·쓰기는 뒤로, 뒤의 읽기·쓰기는 앞으로 넘어가지 못한다. 펜스만 필요하면 Interlocked.MemoryBarrier()를 부른다. 비용은 x86에서 경합이 없으면 수 ns지만, 여러 코어가 같은 변수를 두드리면 그 캐시 라인을 두고 다투느라 몇 배로 는다(캐시 일관성과 false sharing).

한 명령으로 안 되는 갱신은 CompareExchange 루프로 만든다. 읽고, 새 값을 계산하고, 그사이 아무도 안 바꿨을 때만 넣는다. 실패하면 다시 읽고 다시 한다. 

// 지금까지의 최댓값을 락 없이 갱신한다
static void UpdateMax(ref int target, int value)
{
    int current = Volatile.Read(ref target);
    while (value > current)
    {
        int seen = Interlocked.CompareExchange(ref target, value, current);
        if (seen == current) return;   // 내가 바꿨다
        current = seen;                // 누가 먼저 바꿨다. 그 값으로 다시 비교한다
    }
}

루프 안의 계산은 짧고 부작용이 없어야 한다. 실패하면 몇 번이고 다시 돌기 때문이다. 같은 값으로 되돌아온 변화를 놓치는 ABA 문제와 락 없는 자료구조의 구조는 동시성 자료구조에서 다룬다.

한 번만 초기화하기

"없으면 만들고, 있으면 쓴다"를 락 없이 빠르게 하려는 것이 이중 검사 잠금이다. .NET에서는 필드를 volatile로 두거나 Volatile.Read/Write로 접근하면 올바르게 동작한다. 순서를 지키지 않으면 다른 스레드가 생성자가 끝나기 전의 객체 참조를 볼 수 있다. 

// 직접 짠 이중 검사 잠금
private static volatile Config? _config;
private static readonly object _gate = new();

public static Config Get()
{
    var c = _config;                  // 획득 읽기
    if (c != null) return c;
    lock (_gate)
    {
        _config ??= Config.Load();    // 해제 쓰기: 생성이 끝난 뒤에 보인다
        return _config;
    }
}

// 같은 일을 표준 라이브러리로
private static readonly Lazy<Config> _lazy = new(Config.Load);   // 기본이 스레드 안전
public static Config Get2() => _lazy.Value;

직접 짤 이유는 거의 없다. Lazy<T>는 기본 모드에서 생성을 한 번만 하고, 생성 중 예외까지 기억한다. 생성이 여러 번 돌아도 괜찮고 하나만 남기면 된다면 LazyInitializer.EnsureInitialized가 Interlocked로 더 가볍게 처리한다. 정적 필드라면 정적 생성자나 필드 초기화식이 런타임의 타입 초기화 보장으로 한 번만 돈다.

게임 서버에서는

  • 통계 카운터는 스레드별로 세었다가 합친다. 패킷 수, 바이트 수를 모든 I/O 스레드가 같은 변수에 Interlocked.Add하면, 그 변수가 든 캐시 라인을 코어들이 번갈아 빼앗는다. 스레드마다 따로 세고 지표를 낼 때만 합친다. 카운터를 배열에 두려면 원소 사이를 캐시 라인 크기(64바이트, 인접 라인 미리 읽기까지 막으려면 128바이트)만큼 띄운다. 
    [StructLayout(LayoutKind.Explicit, Size = 128)]
struct PaddedCounter
{
    [FieldOffset(64)] public long Value;   // 앞뒤 원소와 다른 캐시 라인에 놓인다
}
private readonly PaddedCounter[] _sent = new PaddedCounter[Environment.ProcessorCount];
  • 세션 상태 전환은 CompareExchange로 한 번만. 연결 끊김은 수신 실패, 송신 실패, 하트비트 시간 초과에서 동시에 감지될 수 있다. 상태 필드를 CompareExchange(ref _state, Closing, Open)으로 바꾼 쪽만 정리 절차를 밟게 하면 이중 정리와 이중 반납이 사라진다(끊긴 연결 알아차리기).
  • 송신 중 표시도 같은 방식이다. 세션마다 진행 중인 송신을 하나로 두려면 Exchange나 CompareExchange로 "송신 중" 플래그를 세운 스레드만 송신을 시작한다(완료 알림 기반 서버).
  • C++ volatile과 이름만 같다. C#의 volatile은 획득·해제 순서를 보장하지만 C++의 volatile은 순서를 보장하지 않는다. C++에서는 std::atomic이 그 자리다(C++ 동시성).

주의 사항

  • volatile 필드를 ref로 넘기면 volatile이 아니다. 메서드 안에서는 일반 접근이 된다. 컴파일러가 경고(CS0420)를 내는데, Interlocked 메서드에 넘기는 경우는 그 메서드가 스스로 펜스를 걸므로 괜찮다.
  • x86에서 잘 돈다고 맞는 코드가 아니다. x86은 메모리 순서가 강해서 순서 실수가 드러나지 않는다. ARM 서버(Graviton 등)에서 같은 코드가 가끔 틀린 값을 읽는다.
  • 32비트 프로세스에서 long은 찢어진다. 한 스레드가 64비트 값을 쓰는 동안 다른 스레드가 위쪽 절반은 새 값, 아래쪽 절반은 옛 값으로 읽을 수 있다. 64비트 프로세스에서는 포인터 크기가 8바이트라 정렬된 long 읽기·쓰기가 원자적이다. 같은 코드가 32비트로도 빌드된다면 공유하는 long은 Interlocked로 다룬다. 원자적이어도 증가처럼 읽고 쓰는 일은 여전히 Interlocked가 필요하다.
  • Interlocked로 두 변수를 따로 바꾸지 않는다. 각 연산은 원자적이어도 둘 사이에 다른 스레드가 끼어든다. 둘이 함께 맞아야 하면 lock을 쓰거나, 두 값을 객체 하나에 담아 참조를 Exchange로 바꿔 끼운다.
