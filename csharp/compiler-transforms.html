먼저 읽을 것: 값 형식과 참조 형식 · 박싱

핵심 요약

C# 컴파일러는 소스를 IL로 옮기기 전에 높은 수준의 문법을 더 단순한 C#으로 먼저 풀어 쓴다. 이것을 낮춤(lowering)이라 한다. 람다가 바깥 지역 변수를 쓰면 그 변수를 필드로 가진 클래스가 생기고, yield return이 있는 메서드는 상태 기계 클래스가 되고, async 메서드는 상태 기계 구조체가 된다. using, lock, foreach, 보간 문자열도 모두 다른 코드로 바뀐다.

코드에는 new가 한 번도 없는데 할당이 생기거나, 지역 변수가 메서드보다 오래 살거나, 인자 검사가 늦게 터지는 일이 여기서 나온다. 낮춘 결과를 직접 보면 이유가 바로 보인다. SharpLab(sharplab.io)이나 디컴파일러(ILSpy, dotPeek)에 코드를 넣으면 컴파일러가 만든 클래스와 필드가 그대로 나온다.

동작 원리

클로저는 지역 변수를 클래스의 필드로 옮긴다

결과는 셋이다. 지역 변수가 힙의 객체 필드가 되어 메서드가 끝나도 람다가 살아 있는 동안 함께 산다. 람다를 만드는 자리에서 그 객체와 대리자가 할당된다. 같은 변수를 쓰는 람다들은 같은 객체의 필드를 함께 본다. C++ 람다의 값 캡처와 정반대인 이 성질은 람다와 함수 객체에서 비교했다.

할당이 생기는 시점이 예상보다 이르다는 점을 알아 둔다. 디스플레이 클래스 객체는 람다를 만드는 줄이 아니라 캡처된 변수가 선언된 범위에 들어서는 순간 만들어진다. 메서드 첫머리에 선언한 변수를 드물게 도는 분기 안의 람다 하나가 캡처해도, 그 분기를 타지 않는 호출까지 매번 객체를 할당한다. 변수 선언을 그 분기 안으로 옮기거나 람다를 별도 메서드로 빼면 사라진다.

인스턴스 멤버만 쓴다(this)인스턴스 메서드와 대리자람다를 만들 때마다 대리자 하나
지역 변수나 매개변수를 쓴다디스플레이 클래스 + 대리자범위에 들어설 때 객체 하나, 람다를 만들 때 대리자 하나

반복자는 상태 기계 클래스가 된다

yield return이 있는 메서드는 불러도 본문이 한 줄도 실행되지 않는다. 컴파일러가 만든 클래스의 객체를 돌려줄 뿐이고, 그 클래스가 IEnumerable<T>와 IEnumerator<T>를 함께 구현한다. 지역 변수와 매개변수는 그 클래스의 필드가 되고, "몇 번째 yield까지 왔나"가 정수 필드 하나에 담긴다. MoveNext()를 부를 때마다 그 번호로 뛰어 다음 yield까지 실행하고 멈춘다. 

IEnumerable<Monster> InRange(List<Monster> all, Vector2 pos, float r)
{
    if (all is null) throw new ArgumentNullException(nameof(all));   // 이 검사는 순회할 때 돈다
    foreach (var m in all)
        if (Vector2.Distance(m.Pos, pos) <= r) yield return m;
}

var q = InRange(null, p, 5);   // 여기서는 예외가 나지 않는다
foreach (var m in q) { }       // 여기서 ArgumentNullException

인자 검사가 늦게 터지는 것을 막으려면 검사만 하는 일반 메서드를 겉에 두고, 그 안에서 반복자 지역 함수를 돌려준다. 그러면 검사는 호출 시점에, 순회는 나중에 일어난다. 반복자를 두 번 순회하면 본문도 두 번 처음부터 실행된다. 이 성질이 그대로 LINQ와 지연 실행의 바탕이다.

async는 상태 기계 구조체가 된다

async 메서드도 같은 방식으로 상태 기계가 된다. 다른 점은 릴리스 빌드에서 그 상태 기계가 구조체라는 것이다. 첫 await가 이미 끝난 작업을 만나면 멈추지 않고 그대로 진행하므로, 메서드가 끝까지 동기로 끝나면 상태 기계는 스택에서만 살다 사라진다. 실제로 기다려야 하는 순간에야 상태 기계가 힙의 상자로 옮겨진다. 디버그 빌드는 디버깅 편의를 위해 클래스로 만든다. 어느 지역 변수가 필드로 옮겨지는지, 재개가 어디서 일어나는지는 async와 await의 실체에서 다룬다.

소스 생성기는 다른 장치다

낮춤은 컴파일러 안에서 언어 규칙대로 일어나고 사용자가 바꿀 수 없다. 소스 생성기(source generator)는 컴파일 도중에 사용자가 만든 코드 생성기가 돌아 새 소스 파일을 덧붙이는 장치다. 기존 코드를 고치지는 못한다. 리플렉션으로 하던 일(직렬화, 패킷 처리기 등록, 로그 메시지 정의)을 빌드 때 코드로 만들어 두는 데 쓴다. AOT 환경에서 리플렉션이 막히는 문제를 피하는 길이기도 하다(JIT와 AOT).

게임 서버에서는

  • 틱 루프 안의 람다는 할당을 센다. 매 틱 monsters.Where(m => m.Zone == zoneId)처럼 지역 값을 캡처한 람다를 만들면 틱마다 디스플레이 클래스와 대리자가 할당된다. 수천 개 객체에 대해 돌면 그만큼 GC 압력이 된다. 캡처할 값을 매개변수로 받는 static 람다나 일반 반복문으로 바꾼다(GC 동작과 세대).
  • 콜백 등록이 객체를 붙잡는다. 디스플레이 클래스는 캡처한 변수가 가리키는 객체까지 함께 붙잡는다. 세션을 캡처한 람다를 오래 사는 이벤트나 타이머에 등록하고 해제하지 않으면, 끊긴 세션이 람다를 통해 계속 살아 있다(GC 언어의 메모리 누수).
  • 열거는 구체 타입으로 돈다. 세션 목록을 IEnumerable<Session>으로 넘겨받아 foreach하면 열거자가 박싱되어 순회마다 할당이 생긴다. 핫 패스에서는 List<T>나 배열, ReadOnlySpan<T>로 받는다(박싱).
  • 할당을 의심하면 낮춘 코드를 본다. 프로파일러가 "알 수 없는 <>c__DisplayClass 객체"를 많이 보여 준다면 바로 이 변환이다. 해당 메서드를 SharpLab에 넣으면 어느 줄이 무엇을 만드는지 보인다(.NET 진단 도구).

주의 사항

  • for 루프 변수 캡처는 지금도 하나다. foreach의 반복 변수는 C# 5부터 반복마다 새로 만들어지지만, for (int i = 0; …)의 i는 루프 전체에 하나뿐이다. 람다 여러 개가 모두 마지막 값을 본다. 루프 안에서 지역 변수에 복사해 캡처한다.
  • 반복자의 finally는 순회를 끝내야 돈다. yield 사이의 using이나 finally는 열거자를 Dispose할 때 실행된다. foreach는 이것을 해 주지만, 열거자를 직접 받아 MoveNext만 부르다 버리면 정리가 돌지 않는다.
  • 낮춤은 컴파일러 버전마다 조금씩 바뀐다. 메서드 그룹을 대리자로 바꿀 때의 캐시(C# 11), 보간 문자열 처리기(C# 10), lock의 Lock 타입(C# 13)처럼 버전이 오르며 할당이 줄어든 자리가 많다. 오래된 지식으로 판단하지 말고 쓰는 버전에서 확인한다.
  • 디버그 빌드로 할당을 재지 않는다. async 상태 기계가 클래스가 되는 등 릴리스와 모양이 다르다. 할당과 성능은 릴리스 빌드로 잰다.
