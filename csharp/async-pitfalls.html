먼저 읽을 것: async와 await의 실체 · 동기화 컨텍스트

핵심 요약

async Task 메서드 안에서 난 예외는 그 자리에서 던져지지 않고 돌려준 Task 안에 담긴다. 누군가 그 Task를 await해야 예외가 꺼내져 다시 던져진다. 그래서 예외가 어디로 가는지는 "누가 이 Task를 기다리나"가 정한다.

async void에는 예외를 담을 Task가 없다. 예외는 메서드가 이미 돌아간 뒤에 컨텍스트나 스레드 풀로 바로 던져지고, 서버에서는 처리되지 않은 예외로 프로세스 전체가 끝난다. 반대로 아무도 기다리지 않은 Task의 예외는 조용히 사라진다. 하나는 너무 크게, 하나는 너무 조용하게 실패한다.

동작 원리

예외는 Task에 담겼다가 await에서 꺼내진다

await는 담긴 예외를 원래 스택 정보와 함께 다시 던진다(ExceptionDispatchInfo). 그래서 로그의 스택이 실제로 던진 자리를 가리킨다. 반면 .Wait()와 .Result는 예외를 AggregateException에 한 겹 싸서 던진다. 같은 실패가 기다리는 방식에 따라 다른 타입으로 보인다. 동기로 꼭 꺼내야 하면 .GetAwaiter().GetResult()가 싸지 않은 원래 예외를 준다.

async void는 기다릴 수도 잡을 수도 없다

async void 메서드는 부른 쪽에 아무것도 돌려주지 않는다. 부른 쪽은 끝났는지 알 수 없고, 예외가 나도 받을 길이 없다. 안에서 처리되지 않은 예외는 시작할 때 있던 동기화 컨텍스트에 던져지고, 컨텍스트가 없으면 스레드 풀에 던져진다. .NET에서 스레드 풀 스레드의 처리되지 않은 예외는 프로세스를 끝낸다.

쓰는 자리는 이벤트 처리기 하나다. 대리자 형식이 void를 요구하기 때문이다. 그때도 본문 전체를 try로 감싸 안에서 끝낸다. 눈에 안 띄게 생기는 경우가 더 위험하다. Action을 받는 자리에 async 람다를 넘기면 그 람다는 async void가 된다. List<T>.ForEach(async x => ...), Parallel.ForEach, System.Threading.Timer 콜백이 대표다.

기다리지 않은 Task의 예외는 사라진다

바로 await그 자리에서 다시 던져진다
변수에 담았다가 나중에 await그때 던져진다. 그 전까지는 Task 안에 있다
버렸다(_ = DoAsync(); 또는 반환값 무시)아무도 꺼내지 않는다. 기록도 없이 사라진다
async void였다컨텍스트나 스레드 풀로 던져진다. 서버라면 프로세스가 끝난다

버린 Task의 예외는 그 Task가 GC로 정리될 때 TaskScheduler.UnobservedTaskException 이벤트로 한 번 알려진다. .NET Framework 4.0에서는 이것이 프로세스를 끝냈지만, 4.5부터 기본이 바뀌어 지금은 이벤트만 발생하고 넘어간다. 언제 발생할지는 GC가 정하므로 실패한 시점과 한참 떨어져서 온다. 기록용 안전망일 뿐 처리 수단은 아니다.

WhenAll은 첫 예외만 던지고 나머지는 Task에 남긴다

var all = Task.WhenAll(SaveInventory(p), SaveQuest(p), SaveMail(p));
try
{
    await all;                                       // 실패가 여럿이어도 첫 번째만 던져진다
}
catch
{
    foreach (var e in all.Exception!.InnerExceptions) // 전부 보려면 Task에서 꺼낸다
        _log.Error(e, "save failed for {Player}", p.Id);
    throw;
}

Task.WhenAll은 모든 작업이 끝날 때까지 기다린 뒤, 실패한 것들의 예외를 하나의 AggregateException으로 모아 돌려준 Task에 담는다. await는 그중 첫 예외만 꺼내 던진다. 나머지는 사라지지 않았지만 로그에 남기려면 위처럼 Task의 Exception을 직접 읽어야 한다.

선택 기준

던지고 잊는 작업은 관찰하는 래퍼로 띄운다

static async void Forget(Task task, ILogger log)   // 의도한 async void는 여기 한 곳뿐이다
{
    try { await task; }
    catch (OperationCanceledException) { }        // 취소는 실패가 아니다
    catch (Exception e) { log.Error(e, "background task failed"); }
}

Forget(FlushStatsAsync(), _log);                  // 결과는 필요 없지만 실패는 기록된다
상황하는 일
결과와 실패가 모두 필요하다그냥 await한다
결과는 필요 없고 실패만 알면 된다위의 관찰 래퍼로 띄운다. 예외를 삼키지 않고 기록한다
서버가 꺼질 때까지 이어져야 한다Task를 목록에 보관하고 종료 때 함께 기다린다(BackgroundService)
이벤트 처리기라 async void가 강제된다본문 전체를 try로 감싼다

예외 필터(catch (Exception e) when (...))는 스택을 되감기 전에 조건을 본다. 조건이 거짓이면 그 catch는 없는 것과 같아서, 원래 스택이 그대로 남은 채 위로 올라간다. when (e is not OperationCanceledException)처럼 취소를 실패와 가르거나, when (Log(e))로 기록만 하고 처리는 위에 맡길 때 쓴다.

게임 서버에서는

  • 패킷 처리기를 async void로 두면 클라이언트 하나가 서버를 끈다. 처리기를 이벤트처럼 async void로 등록하면, 잘못된 패킷 하나가 일으킨 예외가 스레드 풀로 던져져 접속자 전원이 끊긴다. 처리기는 Task를 돌려주게 하고, 디스패처가 await하면서 예외를 잡아 그 세션만 끊는다.
  • 저장처럼 버려지기 쉬운 작업을 관찰한다. 로그아웃 저장, 통계 전송, 로그 기록을 _ = SaveAsync();로 던지면, 실패해도 아무도 모르고 데이터만 사라진다. 관찰 래퍼로 띄워 실패를 기록하고, 종료 절차에서는 진행 중인 저장을 모아 기다린다.
  • 최후의 안전망을 둔다. AppDomain.CurrentDomain.UnhandledException과 TaskScheduler.UnobservedTaskException에 기록 처리기를 건다. 앞의 것은 프로세스가 끝나는 것을 막지 못하므로 덤프와 로그를 남기는 용도다(크래시 덤프와 심볼).
  • 여러 저장을 함께 기다리면 실패를 전부 남긴다. 인벤토리·퀘스트·우편 저장을 WhenAll로 묶었다면, 첫 예외만 기록하면 나머지 실패는 묻힌다. Task의 InnerExceptions를 모두 기록한다.

주의 사항

  • async 람다를 받는 자리의 형식을 확인한다. Func<Task>를 받는지 Action을 받는지에 따라 같은 람다가 async Task도 되고 async void도 된다. 분석기 경고(VSTHRD101 등)를 켜 둔다.
  • try 안에서 await해야 잡힌다. try { return DoAsync(); }처럼 Task를 기다리지 않고 돌려주면, 예외는 try를 벗어난 뒤에 꺼내져 이 catch를 지나치지 않는다.
  • .Result와 await는 같은 실패를 다른 모양으로 보여 준다. 앞의 것은 AggregateException, 뒤의 것은 원래 예외다. catch 절의 타입이 맞지 않아 놓치는 일이 생긴다.
  • 취소 예외를 오류로 세지 않는다. OperationCanceledException은 요청대로 멈췄다는 뜻이다. 오류 지표에 섞으면 접속 종료가 많은 날 오류율이 튄다(취소와 시한).
