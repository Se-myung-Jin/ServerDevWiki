먼저 읽을 것: 값 형식과 참조 형식

핵심 요약

박싱은 값 형식을 object나 인터페이스처럼 참조로 다뤄야 할 때, 힙에 객체를 하나 만들어 값을 복사해 넣는 일이다. 참조로 가리킬 실체가 필요하기 때문이다. 언박싱은 그 객체에서 타입을 확인한 뒤 값을 다시 꺼내 복사한다.

한 번의 비용은 작다. 문제는 코드에 드러나지 않는 자리에서 루프마다, 패킷마다 일어난다는 점이다. 박스는 할당이고, 할당은 나중에 GC가 치워야 한다. 비용은 변환 연산이 아니라 쌓이는 쓰레기에서 나온다.

동작 원리

박싱은 할당 하나와 복사 하나다

언박싱은 박싱한 그 타입으로만 된다. int를 담은 박스를 (long)o로 꺼내면 숫자 변환이 아니라 InvalidCastException이다. (long)(int)o처럼 먼저 원래 타입으로 꺼낸 뒤 바꾼다. null을 값 형식으로 꺼내면 NullReferenceException이고, int?로 꺼내면 null이 된다.

박스는 원래 값과 연결되어 있지 않다. 박싱한 뒤 원래 변수를 고쳐도 박스 안의 값은 그대로이고, 인터페이스로 받은 박스의 메서드가 상태를 고쳐도 원래 변수는 모른다. 가변 struct를 인터페이스로 넘겼다가 "고쳤는데 안 바뀐" 버그가 여기서 나온다.

제네릭 제약이 박싱을 없앤다

// 박싱된다: struct가 IComparable 참조로 바뀐다
static int CompareBoxed(IComparable a, object b) => a.CompareTo(b);

// 박싱되지 않는다: T가 값 형식이면 JIT가 그 타입 전용 코드를 만들고
// constrained 호출로 struct의 구현을 바로 부른다
static int Compare<T>(T a, T b) where T : IComparable<T> => a.CompareTo(b);

제약이 있으면 컴파일러는 constrained. 접두사를 붙여 메서드를 부른다. 값 형식이 그 메서드를 직접 구현했으면 박스 없이 그 구현으로 바로 간다. JIT가 값 형식마다 전용 코드를 만들기 때문에 가능하다(제네릭). 같은 struct를 인터페이스 타입 변수에 담는 순간 이 이득이 사라진다.

박싱은 대부분 신경 쓸 필요가 없다. 초기화 코드, 관리 도구, 요청이 드문 API에서 박스 몇 개는 아무 일도 아니다. 찾아서 없앨 곳은 틱 루프, 패킷 처리, 로그 같은 뜨거운 경로뿐이다.

게임 서버에서는

  • 로그가 가장 흔한 범인이다. Log.Debug("pos {0} {1}", x, y) 형태의 params object[] 로그는 로그 수준이 꺼져 있어도 배열 할당과 박싱을 먼저 하고 들어간다. 수준을 먼저 확인하거나, 제네릭 오버로드나 보간 핸들러를 받는 로거(Microsoft.Extensions.Logging의 소스 생성 LoggerMessage 등)를 쓴다.
  • struct 키는 IEquatable<T>를 구현한다. Dictionary<EntityId, Entity>의 키 struct가 이것을 구현하지 않으면 조회마다 키를 박싱해 비교한다. 엔티티 조회는 틱마다 수만 번이다. readonly record struct EntityId(int Value)로 정의하면 컴파일러가 IEquatable<T>까지 만들어 준다.
  • 공통 인터페이스로 묶은 struct 컴포넌트. List<IComponent>에 struct 컴포넌트를 담으면 원소마다 박스다. struct로 만든 의미가 사라진다. 타입별 배열에 담고 제네릭으로 처리한다(메모리 배치와 자료구조).
  • enum 키 딕셔너리는 이제 괜찮다. 오래된 .NET Framework에서는 enum 키 Dictionary가 비교에서 박싱하는 경우가 있었다. 지금 런타임은 enum 비교자를 따로 만들어 박싱하지 않는다. 옛 정보를 보고 enum 키를 정수로 바꿀 필요는 없다.

주의 사항

  • 박스는 복사본이다. 박싱한 값을 고쳐도 원래 변수는 바뀌지 않고, 원래 변수를 고쳐도 박스는 그대로다.
  • 언박싱은 정확히 같은 타입으로만. int 박스를 long으로 꺼내면 예외다. 숫자 변환은 꺼낸 뒤에 한다.
  • struct가 인터페이스를 구현했다는 것만으로는 안전하지 않다. 그 인터페이스 타입으로 다루는 순간 박싱된다. 제네릭 제약을 거쳐야 박싱이 없다.
  • 작은 struct라고 박싱이 싼 것은 아니다. 1바이트 bool도 박스는 객체 하나다. 비용은 크기가 아니라 할당 횟수다.
