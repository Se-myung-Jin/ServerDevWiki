먼저 읽을 것: 값 형식과 참조 형식 · 인터페이스와 추상 클래스

핵심 요약

대리자(delegate)는 "어떤 메서드를, 어떤 객체에 대해 부를지"를 담은 객체다. 선언한 대리자 타입은 컴파일러가 MulticastDelegate를 상속한 클래스로 만들고, 그 인스턴스는 대상 객체(Target)와 메서드(Method)를 든다. 그래서 대리자를 들고 있으면 그 대상 객체도 살아 있다. 대리자 여러 개를 +=로 묶으면 호출 목록이 되어 한 번 부를 때 차례로 모두 불린다.

event는 그 대리자 필드에 대한 접근을 좁힌 것이다. 바깥에서는 구독(+=)과 해제(-=)만 할 수 있고, 대입해서 남의 구독을 지우거나 직접 호출하는 일은 선언한 클래스만 할 수 있다. 대리자는 "무엇을 부를지"이고, 이벤트는 "누가 부를 수 있는지"를 정한 규칙이다.

동작 원리

대리자는 대상과 메서드를 함께 든다

delegate void DamageHandler(int amount);를 선언하면 컴파일러는 MulticastDelegate를 상속하고 Invoke 메서드를 가진 클래스를 만든다. 인스턴스 메서드로 만든 대리자는 그 객체를 Target에, 정적 메서드로 만든 대리자는 null을 Target에 둔다. 메서드 그룹이든 람다든 결과는 같은 대리자 객체이고, 람다가 바깥 변수를 쓰면 대상이 컴파일러가 만든 클로저 객체가 된다(컴파일러가 바꿔 주는 것).

대리자는 문자열처럼 불변이다. a += b는 a = (Handler)Delegate.Combine(a, b)가 되어, a와 b의 목록을 이어 붙인 새 대리자를 만든다. -=는 Delegate.Remove로 목록 끝에서부터 같은 대상·같은 메서드인 항목 하나를 뺀 새 대리자를 만든다. 다 빠지면 null이 된다. 그래서 구독할 때마다 할당이 생기고, 같은 모양의 람다를 다시 적으면 다른 대리자라 빠지지 않는다.

멀티캐스트 호출의 규칙

상황무슨 일이 생기나
목록이 여럿인 대리자를 부른다추가된 순서대로 하나씩 부른다. 같은 스레드에서 동기로 돈다
반환값이 있다(Func<int>)마지막으로 불린 것의 반환값만 돌아온다. 앞의 값은 버려진다
중간 하나가 예외를 던진다그 자리에서 멈추고 예외가 부른 쪽으로 올라간다. 뒤에 남은 구독자는 불리지 않는다
구독자가 하나도 없다필드가 null이라 그냥 부르면 NullReferenceException이다
각각의 결과나 예외가 필요하다GetInvocationList()로 목록을 꺼내 하나씩 부른다. 배열을 새로 할당한다

event는 필드에 문지기를 세운다

public class Monster
{
    public Action<int>? HpChangedField;     // 공개 대리자 필드: 바깥에서 무엇이든 할 수 있다
    public event Action<int>? HpChanged;    // 이벤트: 바깥에서는 += 와 -= 만 된다

    void SetHp(int hp) => HpChanged?.Invoke(hp);   // 부르는 것은 선언한 클래스만
}

monster.HpChangedField = null;          // 컴파일된다. 다른 구독자가 모두 사라진다
monster.HpChangedField?.Invoke(0);      // 컴파일된다. 바깥에서 가짜 신호를 보낸다
monster.HpChanged = null;               // 컴파일 오류 CS0070
monster.HpChanged += OnHp;              // 된다

event를 붙인 필드 선언(필드 같은 이벤트)은 컴파일러가 숨은 대리자 필드와 add·remove 접근자 한 쌍으로 바꾼다. 바깥의 +=는 add, -=는 remove 호출이 된다. 컴파일러가 만든 접근자는 Interlocked.CompareExchange 루프로 필드를 바꾸므로 여러 스레드가 동시에 구독해도 항목이 사라지지 않는다. 접근자를 직접 쓰면 구독 목록을 딕셔너리에 따로 두거나, 구독할 때 검증하는 일을 넣을 수 있다.

부르는 쪽에서는 HpChanged?.Invoke(hp)로 부른다. 필드를 한 번 읽어 지역에 담은 뒤 그 값으로 null 확인과 호출을 하므로, 확인과 호출 사이에 다른 스레드가 마지막 구독을 해제해도 NullReferenceException이 나지 않는다. 대신 방금 해제한 구독자가 한 번 더 불릴 수는 있다. 해제한 뒤에 불려도 괜찮게 처리기를 짜야 한다.

Action, Func, 사용자 정의 대리자

종류모양쓰는 곳
Action<T…>반환값 없음, 매개변수 0~16개콜백, 이벤트 처리기 대부분
Func<T…, TResult>마지막 형식 인자가 반환값계산을 넘길 때, LINQ
Predicate<T>, Comparison<T>옛 API의 전용 대리자List<T>.Find, Sort
직접 선언한 대리자이름 있는 매개변수, ref·in·out 매개변수뜻을 이름으로 드러내야 할 때, ref로 넘겨야 할 때(Action은 ref 매개변수를 못 쓴다)
EventHandler<TEventArgs>(object? sender, TEventArgs e).NET 관례를 따르는 공개 라이브러리 이벤트

시그니처가 같아도 대리자 타입이 다르면 서로 대입되지 않는다. Action<int> 자리에 같은 모양의 DamageHandler를 바로 넣을 수 없고, new Action<int>(handler)처럼 감싸야 한다. 그래서 공개 API는 대개 Action·Func로 통일한다.

할당과 호출 비용

만드는 방법할당
캡처 없는 람다, static 람다(C# 9)처음 한 번 만들어 컴파일러가 만든 정적 필드에 두고 재사용한다
정적 메서드 그룹(list.ForEach(Log))C# 10까지는 쓸 때마다 새로 만들었다. C# 11부터 캡처 없는 람다처럼 캐시한다
인스턴스 메서드 그룹, this를 쓰는 람다만들 때마다 대리자 하나. 대상이 인스턴스마다 다르기 때문이다
지역 변수를 캡처한 람다클로저 객체와 대리자. 시점은 컴파일러가 바꿔 주는 것에서 다뤘다
+=, -=목록을 합친 새 대리자. 구독자가 많으면 배열도 새로 만든다

부르는 비용은 간접 호출 한 번이다. 대리자 안에 든 함수 주소로 뛰므로 JIT는 무엇이 불릴지 모르고 인라인하지 못한다. 가상 호출과 같은 종류의 비용이다(인터페이스와 추상 클래스). .NET 8 이후의 동적 PGO가 한 호출 지점에 늘 같은 대리자가 오는 것을 보면 그 대상을 직접 부르는 갈래를 넣기도 하지만, 기대어 설계할 일은 아니다. 대상 없이 함수 주소만 담는 더 가벼운 장치로 함수 포인터(delegate*, C# 9)가 있는데, unsafe 코드에서만 쓴다(unsafe와 네이티브 상호 운용).

선택 기준

상황쓸 것이유
메서드 하나에 동작을 넘긴다(정렬 비교, 필터)Func·Action 매개변수, 성능이 중요하면 제네릭 구조체 전략한 번 쓰고 끝난다. 뜨거운 경로면 where TComparer : struct, IComparer<T>로 받아 인라인을 살린다(제네릭)
여러 곳에 "일이 일어났다"를 알린다event구독자가 서로를 지울 수 없고, 아무나 신호를 보낼 수 없다
구독자가 하나뿐이고 반드시 있다인터페이스나 생성자로 받은 대리자 하나멀티캐스트도 null 확인도 필요 없다
구독자 각각의 결과나 실패가 중요하다구독자 목록을 직접 들고 반복문으로 부른다멀티캐스트는 마지막 반환값만 주고 예외에서 멈춘다

게임 서버에서는

  • 틱 경로의 흐름은 직접 호출로 쓴다. 이동 → 충돌 → 피격처럼 매 틱 수만 번 도는 흐름을 이벤트 사슬로 엮으면 호출마다 간접 호출이 붙고, 누가 언제 불리는지 코드에서 따라가기 어렵다. 순서가 정해진 처리는 시스템 메서드를 차례로 부르고, 이벤트는 퀘스트 진행, 업적, 로그처럼 드물고 느슨하게 붙는 쪽에 쓴다(이벤트 버스, 서버 틱 루프).
  • 구독은 토큰으로 돌려받는다. 월드나 길드처럼 오래 사는 객체의 이벤트를 세션이 구독하고 풀지 않으면 세션이 끊겨도 회수되지 않는다(GC 언어의 메모리 누수). IDisposable 구독 토큰을 돌려주는 등록 함수를 두고, 세션의 정리 경로에서 토큰을 한꺼번에 놓는다(IDisposable과 결정적 해제).
  • 처리기 하나의 예외가 나머지를 막지 않게 한다. 몬스터 처치 이벤트에 퀘스트, 업적, 드롭, 로그가 붙어 있을 때 업적 처리기가 예외를 던지면 그 뒤의 드롭 처리기가 불리지 않는다. 처리기 목록을 직접 돌며 하나씩 try로 감싸 기록하고 다음으로 넘어가게 한다.
  • 이벤트를 부르는 순간은 동기다. 구독자가 무거운 일을 하면 이벤트를 부른 로직 스레드가 그만큼 멈춘다. 처리기 안에서 DB에 쓰거나 외부를 부르는 일은 작업 큐로 넘기고 바로 돌아오게 한다(게임 서버 스레딩 모델).
  • C++의 std::function과 같은 자리지만 수명 규칙이 반대다. 둘 다 타입을 지우고 간접 호출한다. C++ 람다는 참조로 캡처하면 대상이 먼저 사라져 끊기고, C# 대리자는 대상을 붙잡아 너무 오래 살린다(람다와 함수 객체).

주의 사항

  • 람다로 구독하면 해제할 수단을 남긴다. e += x => Log(x);로 구독한 뒤 같은 람다를 다시 적어 -=해도 빠지지 않는다. 다른 대리자 객체이기 때문이다. 람다를 변수에 담아 두거나 메서드로 구독한다.
  • 공개 대리자 필드를 이벤트 대신 쓰지 않는다. 바깥 코드가 = 한 번으로 다른 구독자를 모두 지우고, 아무 때나 호출해 가짜 신호를 보낼 수 있다.
  • async 람다로 구독하면 async void가 된다. Action 이벤트에 async x => await ...를 붙이면 예외를 받을 곳이 없다(비동기에서 예외 다루기).
  • 구독 순서에 기대지 않는다. 지금은 추가 순서대로 불리지만, 나중에 누가 접근자를 바꾸거나 구독 지점이 옮겨지면 순서가 달라진다. 순서가 결과에 영향을 주면 이벤트가 아니라 명시적인 호출 순서로 짠다.
