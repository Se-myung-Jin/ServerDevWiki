먼저 읽을 것: async와 await의 실체 · 비동기에서 예외 다루기

핵심 요약

.NET의 취소는 강제 중단이 아니라 협조적인 요청이다. 취소를 거는 쪽은 CancellationTokenSource를 쥐고, 일하는 쪽은 그 소스가 내준 CancellationToken만 받는다. 일하는 쪽이 토큰을 확인하거나 아래 호출에 넘겨야 멈춘다. 아무도 토큰을 보지 않으면 취소를 걸어도 끝까지 돈다.

그래서 취소는 사슬이다. 받은 토큰을 맨 아래 I/O 호출까지 넘겨야 사슬이 이어진다. 중간 메서드 하나가 토큰을 넘기지 않으면 거기서 끊기고, 그 아래 일은 클라이언트가 이미 떠났는데도 계속 자원을 쓴다. 시한(timeout)도 같은 장치로 건다. 일정 시간이 지나면 저절로 취소되는 소스일 뿐이다.

동작 원리

소스는 거는 쪽이, 토큰은 받는 쪽이 쥔다

소스는 취소를 걸 수 있고, 토큰은 확인만 할 수 있다. 토큰을 넘겨받은 쪽이 남의 작업까지 취소해 버리는 일을 막으려고 둘을 나눴다. 한 번 취소된 토큰은 다시 취소 전으로 돌아가지 않는다. 다음 작업에는 새 소스를 만든다. .NET 6부터는 아직 취소되지 않은 소스를 TryReset()으로 재사용할 수 있다.

받는 쪽은 넘기거나, 확인하거나, 등록한다

방법코드쓰는 곳
아래 호출에 넘긴다await stream.ReadAsync(buf, ct)대부분. 비동기 API가 알아서 확인하고 OperationCanceledException으로 끝낸다
반복 중에 확인한다ct.ThrowIfCancellationRequested()오래 도는 계산 루프. 반복마다 한 번 확인한다
플래그만 본다if (ct.IsCancellationRequested) break;예외 없이 정리하고 빠져나와야 할 때
콜백을 등록한다using var reg = ct.Register(() => conn.Abort());토큰을 받지 않는 막히는 호출을 풀어야 할 때

예외로 끝내는 쪽을 기본으로 한다. 플래그만 보고 조용히 돌아오면, 부른 쪽은 일이 다 끝났는지 중간에 멈췄는지 구분할 수 없다. Register로 등록한 콜백은 Cancel()을 부른 스레드에서 그 자리에서 실행되고, 이미 취소된 토큰이면 등록하는 순간 실행된다. 콜백 안에서 오래 걸리는 일이나 락을 잡는 일을 하면 취소를 건 쪽이 함께 멈춘다.

시한과 연결된 토큰

async Task<Profile> LoadProfileAsync(int id, CancellationToken sessionCt)
{
    using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(5));   // 시한
    using var linked = CancellationTokenSource.CreateLinkedTokenSource(sessionCt, timeout.Token);
    try
    {
        return await _db.QueryProfileAsync(id, linked.Token);
    }
    catch (OperationCanceledException) when (timeout.IsCancellationRequested && !sessionCt.IsCancellationRequested)
    {
        throw new TimeoutException($"profile {id} load timed out");             // 시한과 세션 종료를 가른다
    }
}

취소될 이유가 여럿이면 CreateLinkedTokenSource로 묶는다. 묶인 소스 중 하나라도 취소되면 연결된 토큰이 취소된다. 연결된 소스는 원래 토큰들에 콜백을 등록해 두므로, 다 쓰면 반드시 Dispose한다. 오래 사는 토큰(서버 종료 토큰, 세션 토큰)에 연결된 소스를 정리하지 않으면 등록이 쌓여 메모리가 샌다. 시한 소스도 안에 타이머를 들고 있어 마찬가지다.

잡은 쪽에서는 왜 멈췄는지를 가려야 한다. 위처럼 예외 필터로 "시한이 지났고 세션은 살아 있다"를 확인하면, 클라이언트가 나간 정상 취소와 DB가 느린 시한 초과를 다르게 기록할 수 있다. TaskCanceledException은 OperationCanceledException의 파생이라 뒤의 것으로 잡으면 둘 다 잡힌다.

기다림만 끝내는 것과 작업을 멈추는 것은 다르다

.NET 6의 task.WaitAsync(timeout, ct)는 그 Task를 기다리는 일을 시한이나 취소로 끝낸다. 하지만 Task가 하던 작업은 멈추지 않는다. 토큰을 받지 않는 오래된 API를 감쌀 때 "적어도 나는 더 기다리지 않는다"를 보장할 뿐이고, 뒤에서 도는 작업은 그대로 자원을 쓴다. 진짜로 멈추려면 토큰이 그 작업 안까지 들어가야 한다.

시한을 시험하기 어렵다면 .NET 8의 TimeProvider를 쓴다. new CancellationTokenSource(delay, timeProvider)와 Task.Delay(delay, timeProvider)가 시간을 주입받으므로, 시험에서 가짜 시계를 앞으로 돌려 시한 경로를 바로 확인할 수 있다(시계와 타이머).

선택 기준

상황쓰는 것
비동기 메서드를 새로 만든다마지막 매개변수로 CancellationToken ct = default를 받고, 안의 모든 비동기 호출에 넘긴다
외부 호출에 상한 시간을 둔다시한 소스와 받은 토큰을 연결해 넘긴다. 시한은 호출하는 쪽이 정한다
토큰을 받지 않는 오래된 APIWaitAsync로 기다림만 끝내고, 작업이 계속 돈다는 점을 감안한다
막혀 있는 호출을 풀어야 한다Register로 소켓이나 연결을 닫는 콜백을 건다
스레드를 강제로 끝내고 싶다방법이 없다. .NET Core에서 Thread.Abort는 지원하지 않는다. 협조하도록 고친다

게임 서버에서는

  • 세션마다 취소 소스를 하나 둔다. 연결이 끊기면 그 소스를 취소한다. 세션의 수신 루프, 진행 중인 DB 조회, 외부 인증 호출이 모두 그 토큰을 받고 있으면 한 번에 정리된다. 끊긴 세션 때문에 남은 작업이 자원을 붙잡는 일이 없어진다(끊긴 연결 알아차리기).
  • 서버 종료도 같은 장치로 전한다. Generic Host의 IHostApplicationLifetime.ApplicationStopping, BackgroundService의 stoppingToken이 종료 신호를 토큰으로 준다. 세션 토큰을 이 토큰과 연결해 두면 종료 때 모든 세션 작업에 멈춤이 전해진다(시그널과 프로세스 종료).
  • 모든 외부 호출에 시한을 건다. DB, 결제, 인증 API에 시한이 없으면 상대가 느려지는 순간 기다리는 요청이 끝없이 쌓인다. 시한으로 끊어 실패를 빨리 돌려주는 것이 큐와 스레드를 지키는 길이다(큐와 백프레셔).
  • 수신 대기를 취소했다면 그 연결은 닫는다. 소켓 수신을 토큰으로 취소하면 진행 중이던 I/O가 중단된다. 그 시점에 받다 만 바이트가 어디까지 들어왔는지 알 수 없으므로, 그 연결은 다시 쓰지 않고 정리한다.

주의 사항

  • 받은 토큰을 아래로 넘기지 않으면 사슬이 끊긴다. 보조 메서드 하나가 CancellationToken 매개변수를 빠뜨리면 그 아래 전부가 취소를 모른다. 분석기(CA2016)가 넘길 수 있는데 넘기지 않은 호출을 알려 준다.
  • 소스를 Dispose한다. 시한 소스와 연결된 소스는 타이머와 등록을 들고 있다. using으로 만든다.
  • 취소를 오류로 기록하지 않는다. 요청대로 멈춘 것이다. 실패 지표에 섞으면 접속이 많이 끊긴 날 오류율이 거짓으로 튄다.
  • 취소 뒤의 정리 작업에는 같은 토큰을 넘기지 않는다. 이미 취소된 토큰을 넘기면 정리 호출도 바로 취소된다. 롤백이나 저장 같은 정리는 토큰 없이, 또는 별도의 짧은 시한 토큰으로 한다.
