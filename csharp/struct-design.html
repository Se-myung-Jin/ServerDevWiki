먼저 읽을 것: 값 형식과 참조 형식 · 박싱

핵심 요약

struct는 할당을 복사로 바꾸는 선택이다. 그래서 조건이 좁다. 작고, 만든 뒤 바뀌지 않고, 많이 만들고, 통째로 하나의 값인 것만 struct가 맞다. 좌표, 벡터, 색, 금액, 엔티티 ID가 그렇다. 정체성이 있고 여러 곳이 함께 가리키며 상태가 바뀌는 것은 class다.

struct는 기본으로 readonly struct로 만든다. 바뀌는 struct는 사본을 고치고 원본은 그대로인 버그를 부르고, 컴파일러가 원본을 지키려고 몰래 사본을 만드는 방어적 복사를 일으킨다. 복사를 줄이려고 붙인 in이 오히려 복사를 늘리는 이유도 이것이다.

동작 원리

네 조건이 모두 맞아야 한다

조건어기면
작다(대략 16바이트 안팎)넘기고 반환하고 대입할 때마다 통째로 복사한다. 크기가 커지면 할당을 아낀 것보다 복사가 비싸진다

16바이트 기준은 .NET 설계 지침에서 왔다. 64비트에서 레지스터 두 개, 참조 두 개 크기다. 이 정도면 복사가 레지스터 몇 번의 이동으로 끝난다. 절대 기준은 아니다. 32바이트 struct라도 배열에 담아 순회만 하고 넘기지 않는다면 struct가 낫고, 8바이트라도 인터페이스로 자주 다룬다면 박싱 때문에 class가 낫다. 넘기는 방식과 횟수가 크기만큼 중요하다.

가변 struct는 사본을 고친다

struct Stat { public int Atk; public void Buff() => Atk += 10; }

var list = new List<Stat> { new Stat { Atk = 5 } };
list[0].Atk = 20;      // 컴파일 오류 CS1612: 인덱서가 돌려준 사본을 고치려 한다
list[0].Buff();        // 컴파일된다. 사본의 Atk만 15가 되고 리스트 안은 5 그대로다

var arr = new Stat[1];
arr[0].Buff();         // 배열 원소는 사본이 아니라 그 자리다. 실제로 바뀐다

필드 대입은 컴파일러가 막아 주지만 메서드 호출은 막지 못한다. 인덱서와 프로퍼티는 값을 반환하므로 사본이 나오고, 배열 원소와 지역 변수, ref 반환만 원래 자리를 가리킨다. 같은 코드가 List에서는 아무 일도 안 하고 배열에서는 동작한다. readonly struct로 만들면 상태를 고치는 메서드 자체를 쓸 수 없어 이 부류가 컴파일에서 막힌다.

방어적 복사

방어적 복사는 읽기 전용이어야 하는 자리에서 일어난다. in 매개변수, readonly 필드, ref readonly 반환값이다. 일반 struct의 메서드나 직접 쓴 프로퍼티 접근자를 부르면 매번 사본이 생긴다. C# 8부터는 struct 전체가 아니라 멤버 하나에 readonly를 붙여 "이 멤버는 상태를 고치지 않는다"고 표시할 수 있고, 자동 구현 프로퍼티의 get은 컴파일러가 알아서 readonly로 다룬다.

in에는 함정이 하나 더 있다. 변수가 아닌 값(상수, 프로퍼티 결과, 식)을 넘기면 컴파일러가 임시 변수를 만들어 그 참조를 넘긴다. 호출하는 쪽에서는 보이지 않는다. C# 12의 ref readonly 매개변수는 호출하는 쪽이 변수를 넘기도록 경고해 이 일을 드러낸다.

게임 서버에서는

  • ID는 int가 아니라 struct로 감싼다. readonly record struct PlayerId(long Value)와 ItemId를 따로 두면 플레이어 ID 자리에 아이템 ID를 넘기는 실수가 컴파일 오류가 된다. 크기와 비용은 long과 같다.
  • 패킷 필드 묶음은 작은 readonly struct로. 수신 처리에서 위치·방향·속도를 struct로 꺼내 넘기면 패킷마다 할당이 없다. 바이트와 오가는 배치 규칙은 C++ 쪽과 같은 질문이다(객체 배치와 타입 특성).
  • 큰 struct를 Dictionary 값으로 두지 않는다. 값을 꺼낼 때마다 통째로 복사되고, 고치려면 꺼내서 고친 뒤 다시 넣어야 한다. .NET 6의 CollectionsMarshal.GetValueRefOrNullRef로 참조를 얻을 수 있지만, 그 사이 딕셔너리를 바꾸면 참조가 무효가 된다. 대개 class로 두는 편이 낫다.
  • 틱마다 만드는 임시 계산 결과는 struct가 맞다. 판정 결과, 거리와 대상 묶음처럼 만들고 바로 버리는 것을 class로 두면 그 수만큼 0세대 쓰레기가 생긴다(GC 동작과 세대).

주의 사항

  • struct가 늘 빠른 것은 아니다. 할당을 없애는 대신 복사를 늘리는 맞바꿈이다. 크기와 넘기는 횟수에 따라 어느 쪽이 큰지 뒤집힌다.
  • in은 readonly struct와 짝일 때만 이득이다. 일반 struct에 붙이면 멤버를 부를 때마다 방어적 복사가 생긴다.
  • 가변 struct는 List에서 고쳐지지 않는다. 인덱서가 사본을 준다. 메서드로 고치면 컴파일 오류도 없이 사본만 바뀐다.
  • struct를 인터페이스로 다루면 struct의 이점이 사라진다. 박싱으로 할당이 생기고, 박스 안을 고쳐도 원래 값은 바뀌지 않는다.
  • 기본값이 유효한 상태여야 한다. 배열 원소와 default는 생성자를 거치지 않고 모든 필드가 0이다. 0이 말이 안 되는 struct(예: 0이 아니어야 하는 나눗수)는 그 경우를 처리해야 한다.
