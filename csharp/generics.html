먼저 읽을 것: 박싱 · struct와 class 고르기

핵심 요약

C# 제네릭은 중간 언어(IL)에 타입 매개변수가 그대로 남고, 실제 기계어는 실행 중에 JIT가 만든다. 이때 값 형식 인자마다 전용 코드를 만들고, 참조 형식 인자는 코드 한 벌을 공유한다. 값 형식 전용 코드 덕분에 List<int>는 박싱 없이 int를 그대로 담고, 비교와 산술이 인라인된다.

무엇을 할 수 있는지는 where 제약으로 미리 선언한다. 제약은 문법만의 문제가 아니다. 인터페이스 제약 하나가 값 형식의 인터페이스 호출에서 박싱을 없애고, C# 11의 정적 추상 멤버는 T + T 같은 연산을 제네릭으로 쓰게 해 준다. C++ 템플릿과의 비교는 템플릿과 컴파일 시점 계산에서 다뤘다.

동작 원리

값 형식은 따로, 참조 형식은 함께

참조 형식끼리는 값이 모두 포인터 하나이고 GC가 다루는 방식도 같아서 기계어가 같아도 된다. 다만 공유 코드 안에서 new T(), typeof(T), T[] 생성처럼 실제 타입을 알아야 하는 일은, 런타임이 호출할 때 넘겨준 타입 정보(제네릭 사전)를 한 번 더 찾아본다. 그래서 공유 코드는 전용 코드보다 조금 느리다.

값 형식 전용 코드에서는 JIT가 T를 정확히 안다. if (typeof(T) == typeof(int)) 같은 분기는 컴파일 시점 상수로 접혀 해당하지 않는 갈래가 사라지고, EqualityComparer<T>.Default.Equals도 직접 비교로 바뀌어 인라인된다. 대가는 코드 크기다. 값 형식 인자가 많을수록 기계어가 그만큼 는다.

인터페이스 제약이 박싱을 없애는 원리는 이렇다. void Sort<T>(T[] a) where T : IComparable<T>에서 a[i].CompareTo(a[j])는 IL에서 constrained. 접두사가 붙은 호출이 된다. T가 값 형식이면 JIT가 그 타입의 CompareTo를 직접 부르는 코드를 만든다. 같은 일을 IComparable 매개변수로 받으면 구조체를 인터페이스로 넘기는 순간 박싱된다(박싱).

정적 추상 멤버로 연산자를 제네릭으로 쓴다

// C# 11, .NET 7: 인터페이스에 static abstract 멤버를 둘 수 있다
static T Sum<T>(ReadOnlySpan<T> values) where T : INumber<T>
{
    T total = T.Zero;
    foreach (var v in values) total += v;   // int면 정수 덧셈, double이면 실수 덧셈으로 컴파일된다
    return total;
}

예전에는 수치 코드를 제네릭으로 쓸 방법이 없어 int용, float용을 따로 만들거나 dynamic이나 박싱을 썼다. 정적 추상 멤버는 "이 타입에는 이런 정적 메서드와 연산자가 있다"를 인터페이스로 요구한다. 호출은 값 형식 전용 코드 안에서 정적으로 정해지므로 가상 호출이 없다.

변성은 인터페이스와 대리자의 타입 매개변수에만 붙고, 타입 인자가 참조 형식일 때만 성립한다. IEnumerable<int>는 IEnumerable<object>로 바뀌지 않는다. 바꾸려면 원소마다 박싱이 필요하기 때문이다. 배열은 예외적으로 공변이라 Entity[] a = new Monster[1]이 컴파일되지만, 여기에 Player를 넣으면 실행 중에 ArrayTypeMismatchException이 난다. 그 검사 때문에 참조 형식 배열에 쓸 때마다 타입 확인 비용이 든다.

게임 서버에서는

  • 제네릭 정적 필드는 닫힌 타입마다 따로 있다. class Pool<T> { static readonly Stack<T> items; }는 Pool<Monster>와 Pool<Item>이 각자 스택을 갖는다. 타입별 객체 풀이나 패킷 처리기 등록표를 사전 조회 없이 만드는 흔한 방법이다. 반대로 "모든 T가 공유하는 카운터"를 여기 두면 의도와 달리 타입마다 갈라진다.
  • 값 형식 컴포넌트·이벤트는 제네릭으로 받는다. Publish(IEvent e)는 구조체 이벤트를 매번 박싱한다. Publish<T>(in T e) where T : struct, IEvent로 받으면 박싱이 없다. ECS의 컴포넌트 저장소도 같은 이유로 ComponentArray<T> where T : unmanaged 꼴이 된다(ECS 저장 구조).
  • AOT로 빌드하면 실행 중에 새 제네릭을 만들 수 없다. Native AOT와 IL2CPP는 빌드 때 쓰일 인스턴스를 모두 찾아 미리 컴파일한다. MakeGenericType이나 리플렉션으로 처음 보는 값 형식 조합을 만들면 해당 코드가 없어 실패한다. 직렬화기 같은 라이브러리가 소스 생성기로 옮겨 가는 이유다(JIT와 AOT).

주의 사항

  • 제약 없는 T를 인터페이스로 캐스트하면 박싱된다. ((IComparable)value).CompareTo(...)는 값 형식이면 상자를 만든다. 필요한 능력은 제약으로 선언한다.
  • new() 제약은 생각보다 느리다. 뜨거운 경로에서 많이 만든다면 팩토리 대리자(Func<T>)나 정적 추상 팩토리 멤버를 받는다.
  • 값 형식 인자를 마구 늘리면 코드가 불어난다. 값 형식마다 전용 기계어가 생기므로, 큰 제네릭 메서드를 수십 가지 구조체로 쓰면 JIT 시간과 코드 크기가 함께 는다. 타입과 상관없는 부분은 비제네릭 메서드로 빼낸다.
  • 배열 공변성에 기대지 않는다. 컴파일은 되지만 쓰는 순간 실행 중 예외가 날 수 있다. 읽기 전용으로 넘길 때는 공변으로 선언된 IReadOnlyList<T>를 쓴다.
