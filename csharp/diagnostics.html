먼저 읽을 것: 크래시 덤프와 심볼 · C#의 lock

핵심 요약

.NET 진단 도구는 붙이는 비용과 보여 주는 깊이가 함께 오른다. 카운터는 거의 공짜로 지금 상태의 숫자를 보여 주고, 추적은 몇 % 느려지는 대신 어느 코드가 시간을 쓰는지 기록하고, 덤프는 프로세스를 잠시 멈추고 그 순간의 메모리를 통째로 남긴다. 무거운 도구를 먼저 붙이면 측정이 결과를 바꾸고, 운영 서버라면 그 자체가 장애가 된다.

순서는 가벼운 것부터다. dotnet-counters로 GC, 스레드 풀, 락 경합, 예외 중 무엇이 튀는지 좁히고, 그 범위만 dotnet-trace로 기록하고, 메모리나 멈춤의 원인이 그래도 안 보이면 그때 dotnet-gcdump나 dotnet-dump를 뜬다. "느리다"는 제보에서 어느 층을 볼지 정하는 순서는 느린 서버 진단에서 다루고, 여기서는 .NET 프로세스 안을 들여다보는 도구를 본다.

동작 원리

비용과 깊이가 함께 오른다

네 도구는 모두 같은 통로를 쓴다. .NET 런타임은 프로세스마다 진단 포트(Linux는 /tmp의 유닉스 도메인 소켓, Windows는 이름 붙은 파이프)를 열어 두고, 바깥 도구가 여기에 붙어 EventPipe로 이벤트를 받거나 덤프를 요청한다. 디버거를 붙이는 것이 아니라서 운영 중인 프로세스에도 붙일 수 있고, 관리자 권한 없이 같은 사용자로 붙는다.

카운터: 무엇이 튀는지 먼저 본다

dotnet-counters ps                                   # 붙을 프로세스 찾기
dotnet-counters monitor -p 12345 --counters System.Runtime
dotnet-counters collect -p 12345 --format csv -o run.csv   # 파일로 남겨 두고 비교
카운터(System.Runtime)무엇을 말하나튀면 볼 곳
할당률(alloc-rate), 0세대 GC 횟수초당 얼마나 할당하나할당하는 곳을 trace로 찾는다(GC 동작과 세대)
2세대 GC 횟수, 힙 크기, 단편화오래 사는 것이 쌓이나gcdump로 무엇이 남았는지 본다(GC 언어의 메모리 누수)
GC에 쓴 시간 비율, 멈춤 시간GC가 지연의 원인인가GC 모드와 큰 객체 할당(GC 모드와 멈춤)
스레드 풀 큐 길이, 스레드 수일이 밀리나큐가 오르는데 CPU가 낮으면 어디선가 동기로 기다린다(스레드 풀과 실행 모델)
Monitor 락 경합 횟수같은 락을 두고 다투나어느 락인지 trace로(C#의 lock)
예외 발생 수초당 예외가 얼마나 나나예외를 흐름 제어에 쓰는 곳을 찾는다

카운터는 런타임이 원래 세는 숫자를 1초쯤마다 내보내는 것이라 붙여도 성능이 거의 달라지지 않는다. 숫자 하나로 원인을 확정하지는 못한다. 다음에 무엇을 붙일지를 정하는 것이 카운터의 일이다. .NET 9부터는 런타임 지표가 System.Diagnostics.Metrics 기반의 계측(Meter)으로도 나와, 같은 값을 OpenTelemetry로 Prometheus 같은 수집기에 보낼 수 있다. 이때 지표 이름이 바뀐다. 아래 표의 alloc-rate 같은 이름은 예전 EventCounters 이름이고, Meter 쪽은 dotnet.gc.heap.total_allocated, dotnet.monitor.lock_contentions처럼 OpenTelemetry 규칙을 따른다. 대시보드를 만들 때는 어느 쪽 이름인지 확인한다.

추적: 어디서 시간을 쓰는지 기록한다

dotnet-trace collect -p 12345 --profile cpu-sampling --duration 00:00:30
dotnet-trace collect -p 12345 --profile gc-verbose --duration 00:00:30   # 할당 표본까지
dotnet-trace convert trace.nettrace --format speedscope                  # 브라우저에서 불꽃 그래프로

cpu-sampling 프로필은 일정 간격으로 모든 스레드의 스택을 떠서 어느 함수에 시간이 몰렸는지 보여 준다. 결과 .nettrace는 PerfView, Visual Studio에서 열거나 Speedscope 형식으로 바꿔 불꽃 그래프로 본다. gc-verbose는 GC 이벤트와 함께 할당을 표본으로 기록해 "누가 이만큼 할당하나"에 답한다. 기록하는 동안 수 % 정도 느려지므로, 시간을 30초~1분으로 정하고 문제가 보이는 시간대에 뜬다.

표본 추적은 CPU를 쓰는 코드를 보여 준다. 잠들어 기다리는 시간은 거의 안 잡힌다. 응답은 느린데 CPU가 한가하다면 CPU 프로필에서 범인이 안 보이는 것이 정상이고, 그때는 스레드 풀 이벤트나 덤프의 스택으로 누가 무엇을 기다리는지 본다.

덤프: 그 순간을 통째로 남긴다

도구담는 것비용답하는 질문
dotnet-gcdump collect관리 힙 객체 그래프의 요약(타입별 개수·크기, 누가 붙잡나)전체 GC를 한 번 일으켜 그동안 멈춘다. 파일은 작다무엇이 메모리를 채웠나
dotnet-dump collect프로세스 메모리(종류 선택), 모든 스레드쓰는 동안 프로세스 정지. 힙 크기만큼 파일과 시간왜 멈췄나, 이 객체의 실제 값은 무엇인가

메모리가 계속 오른다면 gcdump를 시간 간격을 두고 두 번 떠서 비교한다. 늘어난 타입과 그것을 붙잡은 뿌리가 보인다. 멈춤과 교착은 dotnet-dump를 떠서 dotnet-dump analyze로 연다. clrstack -all, syncblk, dumpheap -stat 같은 SOS 명령과 죽을 때 덤프를 남기는 설정은 크래시 덤프와 심볼에서 다뤘다.

벤치마크: 두 구현을 비교할 때

[MemoryDiagnoser]                 // 호출마다 할당한 바이트와 GC 횟수를 함께 보여 준다
public class SerializeBench
{
    private readonly MovePacket _p = new(1, 2.5f, 3f);
    private readonly byte[] _buffer = new byte[64];

    [Benchmark(Baseline = true)] public byte[] Json()   => JsonSerializer.SerializeToUtf8Bytes(_p);
    [Benchmark]                  public int    Binary() => _p.WriteTo(_buffer);
}
// dotnet run -c Release 로 실행한다

Stopwatch로 반복문을 감싸 재면 JIT가 아직 덜 최적화한 첫 호출, 우연히 끼어든 GC, CPU 주파수 변화가 그대로 결과에 섞인다(JIT와 AOT). BenchmarkDotNet은 워밍업, 반복 횟수 조정, 통계 처리를 대신하고 할당량까지 보여 준다. 최적화되지 않은 Debug 빌드로 돌리면 기본으로 실행을 거부한다. 측정이 왜곡되기 때문이다.

어떻게 붙이나

환경방법
개발 PC, VMdotnet tool install -g dotnet-counters처럼 전역 도구로 깔고 PID로 붙는다
컨테이너 안도구의 단일 실행 파일을 이미지에 넣거나 docker exec로 들어가 실행한다. SDK 없는 런타임 이미지도 된다
컨테이너 밖(사이드카)앱과 사이드카가 /tmp를 같은 볼륨으로 공유해 진단 소켓을 함께 본다. 또는 DOTNET_DiagnosticPorts로 소켓 위치를 정한다
여러 서버를 상시dotnet-monitor를 사이드카로 두고 HTTP로 카운터·추적·덤프를 요청한다. "CPU가 1분 넘게 80% 이상이면 추적 30초" 같은 규칙으로 자동 수집한다
코드 안에서Microsoft.Diagnostics.NETCore.Client의 DiagnosticsClient로 자기 자신이나 다른 프로세스에 덤프·추적을 요청한다

게임 서버에서는

  • 틱 시간은 직접 계측해 카운터와 나란히 본다. 런타임 카운터에는 게임 루프가 없다. Meter로 틱 시간 히스토그램, 틱 초과 횟수, 접속자 수, 세션 송신 큐 길이를 내보내면 GC 멈춤이나 락 경합과 같은 화면에서 맞춰 볼 수 있다(서버 틱 루프). 
    static readonly Meter GameMeter = new("Game.Server");
static readonly Histogram<double> TickMs = GameMeter.CreateHistogram<double>("game.tick.duration", "ms");

TickMs.Record(elapsed.TotalMilliseconds, new KeyValuePair<string, object?>("zone", zoneId));
// dotnet-counters monitor -p <PID> --counters Game.Server 로 바로 보인다
  • 할당률을 틱 단위로 본다. 초당 할당량을 틱레이트로 나누면 틱 하나가 할당하는 양이 나온다. 이 값이 이벤트 때 몇 배로 뛰면 그 시간대만 gc-verbose 추적을 떠서 누가 할당하는지 찾는다.
  • 스레드 풀 고갈은 큐 길이와 CPU를 함께 본다. 큐 길이와 스레드 수가 함께 오르는데 CPU는 한가하면, 스레드 풀 스레드에서 동기로 기다리는 코드(.Result, 동기 DB 호출)가 있다. 그 순간 덤프를 떠 clrstack -all을 보면 같은 대기 지점에 스레드 수십 개가 서 있다.
  • 운영 서버의 덤프는 시간을 고른다. 수십 GB 힙의 전체 덤프는 수십 초 동안 서버를 세우고, gcdump도 전체 GC 한 번만큼 멈춘다. 장애로 이미 멈춘 서버가 아니면 접속이 적은 시간대에, 또는 트래픽을 빼 둔 서버에서 뜬다.

주의 사항

  • 도구를 붙인 뒤의 숫자는 붙이기 전과 다르다. 추적은 몇 % 느려지고, gcdump는 GC를 일으켜 힙 상태 자체를 바꾼다. 비교할 때는 같은 조건으로 잰다.
  • 평균만 보지 않는다. 카운터의 평균 GC 시간이 낮아도 가끔 긴 멈춤이 사용자에게는 렉이다. 지연은 분포로 본다(느린 서버 진단).
  • Release 빌드로 잰다. Debug 빌드는 최적화가 꺼지고 지역 변수의 수명이 늘어나 GC 동작까지 다르다.
  • 덤프와 추적에는 개인 정보가 들어 있다. 메모리에 있던 토큰과 계정 정보가 그대로 담긴다. 보관 장소와 접근 권한을 정해 둔다.
