핵심 요약

ref는 값을 복사하지 않고 그 값이 있는 자리를 넘긴다. C++ 포인터와 비슷하지만 산술이 안 되고, null이 되지 않으며, 가리키는 객체를 GC가 옮기면 함께 따라간다. 런타임은 이것을 관리 포인터(managed pointer)라고 부른다. 대가로 둘 수 있는 곳이 좁다. 지역 변수, 매개변수, 반환값까지다.

Span<T>는 "어디서부터 몇 개"를 담은 ref 하나와 길이로 된 구조체다. 배열의 일부, 스택 버퍼, 네이티브 메모리를 같은 타입으로 복사 없이 가리킨다. 그 안의 참조가 스택을 가리킬 수도 있어서 Span 자신도 힙에 놓일 수 없다. 이런 타입을 ref struct라 하고, 필드·박싱·await 너머·람다 캡처가 막힌다. 그 제약이 Span을 쓸 수 있는 자리를 정한다.

동작 원리

Span은 어디를 가리키든 같은 모양이다

Span<T>를 받는 함수 하나는 배열, 배열의 일부, stackalloc 버퍼, 네이티브 메모리를 모두 받는다. 문자열은 ReadOnlySpan<char>로 본다. 잘라 보기(Slice)는 시작 위치와 길이만 바꾼 새 Span을 만들 뿐이라 할당도 복사도 없다. 그래서 파싱처럼 버퍼를 잘게 나눠 보는 일에서 할당이 통째로 사라진다. Substring은 새 문자열을 할당하지만 AsSpan(start, length)는 할당하지 않는다(문자열).

ref가 C++ 포인터와 다른 점은 GC와의 관계다. GC가 객체를 압축하며 옮기면 그 객체 안을 가리키던 ref도 새 주소로 고쳐진다. 그래서 고정(pin)할 필요가 없다. 대신 런타임이 모든 ref의 위치를 알아야 하므로, 힙 객체의 필드나 배열 원소처럼 추적하기 어려운 자리에는 둘 수 없다. 이 규칙이 그대로 Span의 제약이 된다.

표의 항목은 모두 "힙에 놓이면 안 된다"는 한 규칙에서 나온다. C# 13의 완화도 이 규칙을 지키는 범위 안이다. async 메서드 안에서 Span을 만들어 쓰는 것은 되지만, 그 Span이 await를 지나 살아남으면 상태 기계 필드로 옮겨져야 하므로 여전히 오류다. await 앞에서 쓰고 끝내는 구조로 짠다. 상태 기계가 무엇을 필드로 옮기는지는 컴파일러가 바꿔 주는 것에서 다룬다.

크기가 정해진 작은 버퍼를 힙 할당 없이 객체나 구조체 안에 들고 다니려면 C# 12의 인라인 배열([InlineArray(N)])을 쓴다. struct 안에 같은 타입 원소 N개를 연속으로 품고, Span으로 바로 볼 수 있다. 예전에 unsafe 고정 버퍼(fixed byte buf[16])로 하던 일을 안전하게 한다.

비동기 소켓 API가 Memory<byte>를 받는 이유가 이것이다. 수신을 걸어 두고 await하는 동안 버퍼를 들고 있어야 하기 때문이다. 받은 뒤의 파싱은 .Span으로 꺼내 동기로 처리한다. 파이프라인의 ReadOnlySequence<byte>도 같은 역할 분담이다(메시지 경계와 프레이밍).

할당 없이 버퍼를 얻는 두 길

// 작고 크기 상한이 분명하면 스택에서
Span<byte> header = stackalloc byte[8];

// 크거나 크기가 들쭉날쭉하면 풀에서 빌린다
byte[] rented = ArrayPool<byte>.Shared.Rent(size);   // size 이상의 배열이 온다
try
{
    Span<byte> buf = rented.AsSpan(0, size);        // 요청한 길이만큼만 본다
    Fill(buf);
}
finally
{
    ArrayPool<byte>.Shared.Return(rented);         // 돌려준 뒤에는 절대 쓰지 않는다
}

// 패킷 헤더 읽기: 엔디안을 명시하고, 길이 검사를 먼저 한다
static bool TryReadHeader(ReadOnlySpan<byte> data, out ushort type, out int length)
{
    type = 0; length = 0;
    if (data.Length < 6) return false;
    type   = BinaryPrimitives.ReadUInt16LittleEndian(data);
    length = BinaryPrimitives.ReadInt32LittleEndian(data.Slice(2));
    return true;
}

stackalloc은 Span에 받으면 unsafe 없이 쓸 수 있다. 다만 스택은 스레드마다 기본 1MB 안팎이라 수 KB를 넘는 크기나 바깥 입력으로 정해지는 크기에는 쓰지 않는다. 넘치면 예외로 잡을 수 없는 스택 오버플로로 프로세스가 끝난다(호출 스택). 그보다 크면 ArrayPool에서 빌린다. Rent는 요청보다 큰 배열을 줄 수 있으니 길이를 따로 들고 다니고, 돌려준 배열을 계속 쓰면 다른 코드가 빌려 간 데이터를 덮어쓴다.

컴파일러가 수명을 검사한다

ref와 Span이 안전한 것은 컴파일러가 "이 참조가 가리키는 대상이 어디까지 살아 있나"를 따지기 때문이다. 지역 변수를 가리키는 ref를 반환하거나, stackalloc 버퍼로 만든 Span을 바깥으로 내보내면 컴파일 오류다. C# 11은 ref struct가 ref 필드를 가질 수 있게 하고, 매개변수에 scoped를 붙여 "이 참조는 함수 밖으로 새지 않는다"고 약속하는 방법을 더했다. 약속을 적어 두면 호출하는 쪽은 스택 버퍼도 넘길 수 있다. 

ref int Bad()
{
    int x = 1;
    return ref x;             // 오류: 지역 변수의 자리를 메서드 밖으로 내보낸다
}

ref int FirstAlive(Span<int> hp)
{
    for (int i = 0; i < hp.Length; i++)
        if (hp[i] > 0) return ref hp[i];   // 된다: 호출자가 준 메모리 안의 자리다
    throw new InvalidOperationException();
}

FirstAlive(hpArray) -= 10;   // 반환된 자리에 바로 쓴다. 원소를 복사하지 않는다

API를 받는 쪽으로 만들 때는 배열보다 ReadOnlySpan<T>를 받는다. 배열, 문자열, 일부 구간을 모두 받을 수 있어 호출하는 쪽이 사본을 만들 필요가 없다. C# 14는 배열에서 Span<T>·ReadOnlySpan<T>로 가는 암묵 변환을 언어 규칙으로 끌어올려(first-class span), 배열에도 Span 확장 메서드를 바로 부르고 오버로드 선택이 Span 쪽을 고르게 했다.

게임 서버에서는

  • 패킷 파싱은 Span으로, 저장은 사본으로. 수신 버퍼를 ReadOnlySpan<byte>로 받아 필드를 읽으면 파싱 중 할당이 없다. 하지만 그 Span은 다음 수신이 같은 버퍼를 덮어쓰면 의미가 없어진다. 로직 스레드 큐로 넘길 데이터는 값으로 꺼내거나 풀에서 빌린 버퍼에 복사해서 넘긴다(게임 서버 스레딩 모델).
  • 엔디안과 정렬은 BinaryPrimitives가 맡는다. MemoryMarshal.Read<T>나 MemoryMarshal.Cast로 바이트를 구조체로 바로 보면 빠르지만, 바이트 순서와 구조체 배치가 송신 쪽과 같다는 가정을 깐다. 필드 단위로 BinaryPrimitives.Read…LittleEndian을 쓰면 그 가정이 코드에 드러난다(엔디안과 바이트 오더). C++에서 같은 일을 할 때의 함정은 캐스팅에 있다.
  • 구조체 배열은 ref로 고친다. monsters[i].Hp -= 10은 배열이라 제자리에서 고쳐지지만, List<Monster>의 인덱서는 사본을 돌려줘 같은 코드가 컴파일 오류다. CollectionsMarshal.AsSpan(list)로 내부 배열을 Span으로 받아 ref var m = ref span[i];로 고친다. 그동안 리스트에 원소를 넣거나 빼면 내부 배열이 바뀌어 그 Span은 옛 배열을 가리킨다.
  • 임시 버퍼는 틱마다 할당하지 않는다. 직렬화, 압축, 주변 대상 목록처럼 틱마다 쓰는 버퍼를 new byte[]로 만들면 그만큼 GC가 돈다. 작은 것은 stackalloc, 큰 것은 ArrayPool이나 멤버로 둔 재사용 버퍼를 쓴다(GC 동작과 세대).

주의 사항

  • Span이 가리키는 메모리까지 스택에 있는 것은 아니다. 스택에 있는 것은 Span 자신(참조와 길이)이다. 대상은 힙 배열일 수도, 네이티브 메모리일 수도 있다.
  • ArrayPool에서 빌린 배열의 길이를 믿지 않는다. Rent(100)이 128짜리를 줄 수 있다. rented.Length로 순회하면 앞 사용자가 남긴 쓰레기까지 읽는다. 민감한 데이터를 담았다면 Return(array, clearArray: true)로 지운다.
  • stackalloc 크기를 입력으로 정하지 않는다. 패킷의 길이 필드로 stackalloc 크기를 정하면, 큰 값 하나로 스택 오버플로가 나 프로세스가 끝난다. 상한을 두고 넘으면 풀로 간다.
  • ref는 C++ 포인터가 아니다. 산술도, 필드 저장도, null도 없다. 그 좁음이 GC와 함께 안전을 만든다. 포인터 산술이 필요하면 unsafe로 가야 하고, 그 순간 C++과 같은 종류의 실수가 돌아온다(미정의 동작).
