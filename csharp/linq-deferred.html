먼저 읽을 것: 컴파일러가 바꿔 주는 것

핵심 요약

var q = list.Where(…).Select(…);는 결과를 만들지 않는다. "원본을 이렇게 걸러 이렇게 바꾼다"는 계산 방법을 담은 반복자 객체의 사슬을 만들 뿐이다. 실제 계산은 foreach로 돌거나 ToList, Count, First를 부르는 순간에 일어난다. 이것이 지연 실행이다.

그래서 같은 질의를 두 번 쓰면 원본을 두 번 다시 훑는다. 원본이 바뀌었으면 다른 결과가 나오고, 원본이 DB면 질의가 두 번 나간다. 람다가 캡처한 변수도 만든 시점이 아니라 실행 시점의 값으로 읽힌다. 편리함의 대가로 사슬 단계마다 객체와 대리자가 할당되므로, 게임 서버의 틱 루프에서는 쓸 자리를 가린다.

동작 원리

꺼낼 때 하나씩 끌어당긴다

Where와 Select는 yield return으로 만든 반복자와 같은 구조다(컴파일러가 바꿔 주는 것). 원소를 하나 받아 하나 내보내므로 메모리를 따로 쓰지 않고, 필요한 만큼만 계산한다. 하지만 모든 연산자가 그렇지는 않다.

연산자언제 도나메모리
Where, Select, Take, Skip, Concat열거할 때, 원소 하나씩거의 없다(스트리밍)
OrderBy, GroupBy, Reverse열거할 때. 단, 첫 원소를 내기 전에 앞 단계를 끝까지 읽는다원소 전체를 버퍼에 담는다
Distinct열거할 때, 원소 하나씩. 처음 보는 원소를 바로 내보낸다지금까지 본 원소를 집합에 기억해 둔다. 서로 다른 원소가 많을수록 커진다
ToList, ToArray, ToDictionary그 자리에서 즉시결과를 새 컬렉션에 담는다
Count(), Sum, Any, First, Max그 자리에서 즉시값 하나. Any와 First는 찾으면 멈춘다

사슬 중간에 OrderBy가 하나 끼면 뒤에 Take(3)을 붙여도 앞 단계 전체를 읽어 정렬한 뒤에야 세 개가 나온다. "필요한 만큼만"이라는 지연 실행의 이점이 그 지점에서 끊긴다.

질의는 결과가 아니라 계산 방법이다

int minLevel = 10;
var strong = players.Where(p => p.Level >= minLevel);   // 아직 아무것도 하지 않는다

minLevel = 50;                       // 람다는 변수 자체를 캡처했다
int n = strong.Count();              // 50 이상으로 센다. 원본을 한 번 훑는다
foreach (var p in strong) Send(p);   // 원본을 또 훑는다. 그 사이 players가 바뀌었으면 n과 다르다

var snapshot = strong.ToList();      // 한 번만 계산해 담아 둔다

여러 번 열거하면 계산이 반복되는 것만이 문제가 아니다. 원본이 그 사이에 바뀌면 같은 질의가 다른 결과를 내고, 원본이 한 번만 읽히는 스트림이면 두 번째 열거는 예외 없이 빈 결과를 낸다. 열거하는 도중에 원본 List<T>를 고치면 InvalidOperationException이 난다. 여러 번 쓸 결과면 ToList로 담는다. 메서드 밖으로 질의를 그대로 돌려주면, 호출한 쪽이 연결이나 트랜잭션이 닫힌 뒤에 열거할 수도 있다.

IQueryable은 식을 넘기고 번역은 남이 한다

IEnumerable<T>의 LINQ는 람다를 대리자(컴파일된 코드)로 받아 메모리에서 실행한다. IQueryable<T>의 LINQ는 같은 람다를 식 트리(Expression<Func<…>>)로 받는다. 코드가 아니라 "p.Level ≥ 50"이라는 구조를 데이터로 넘기는 것이고, EF Core 같은 제공자가 그것을 SQL로 번역해 DB에서 실행한다.

구분IEnumerable<T>IQueryable<T>
람다가 되는 것대리자(실행할 코드)식 트리(해석할 데이터)
어디서 도나이 프로세스의 메모리제공자가 번역한 곳(대개 DB)
번역 못 하는 메서드를 쓰면해당 없음EF Core 3.0부터는 마지막 Select만 메모리에서 계산하고, 그 밖의 자리(Where 등)면 실행할 때 예외

경계를 넘는 순간을 코드에 드러낸다. AsEnumerable()이나 ToList() 앞은 SQL, 뒤는 메모리다. 이 경계를 모르고 ToList()를 앞에 붙이면 필터 없이 테이블 전체를 읽어 온 뒤 메모리에서 거른다. 데이터가 적을 때는 멀쩡하다가 운영 데이터에서 무너진다.

할당 비용

LINQ 한 줄의 비용은 원소를 처리하는 계산보다 주변에서 나온다. 연산자마다 반복자 객체가 하나, 람다마다 대리자가 하나, 바깥 변수를 캡처하면 디스플레이 클래스가 하나 생긴다. 열거할 때는 원소마다 대리자를 거치는 간접 호출이 붙는다. ToList는 결과 리스트와 그 내부 배열을 만든다.

.NET은 버전마다 이 비용을 줄여 왔다. 원본이 배열이나 List<T>이면 Count()가 원소를 세지 않고 길이를 바로 읽고, 이어진 Where와 Select는 반복자 하나로 합쳐지고, 숫자 배열의 Sum·Min·Max는 SIMD로 돈다(SIMD와 벡터 연산). 그래도 사슬을 만들고 대리자를 부르는 비용 자체는 남는다. .NET 9의 CountBy와 AggregateBy는 키별 개수나 누적만 필요할 때 GroupBy처럼 그룹마다 원소 목록을 만들지 않아 할당이 적다.

선택 기준

자리쓰는 것이유
서버 기동, 기획 데이터 로딩, 운영 도구, 관리자 APILINQ한 번 돌거나 드물게 돈다. 읽기 쉬움이 더 크다
요청 처리(로그인, 상점) 중 몇십 개 원소LINQ. 결과를 여러 번 쓰면 ToList할당이 요청 하나에 몇 개 늘 뿐이다
틱마다, 대상 수천 개에 대해 도는 코드for/foreach 반복문, Span틱마다 반복자·대리자·클로저가 쌓여 GC를 부른다
같은 결과를 여러 번 쓴다ToList/ToArray로 한 번 담기원본을 다시 훑지 않고 결과가 고정된다
DB 질의IQueryable로 조건을 다 붙인 뒤 마지막에 한 번 실행필터가 SQL로 내려가야 필요한 행만 온다

게임 서버에서는

  • 틱 루프에서는 반복문으로 쓴다. zone.Monsters.Where(m => m.IsAlive && m.Target == id).ToList()를 틱마다 몬스터마다 부르면 그때마다 반복자, 대리자, 디스플레이 클래스, 리스트가 생긴다. 재사용하는 리스트에 반복문으로 채우면 할당이 0이 된다. 같은 성능 문제를 피하려고 구조체 기반으로 만든 LINQ 대체 라이브러리도 있지만, 먼저 그 경로가 정말 뜨거운지 프로파일러로 확인한다(서버 틱 루프).
  • 질의를 필드에 담아 두지 않는다. IEnumerable<Player> nearby = …Where(…)를 멤버로 들고 있으면 꺼낼 때마다 원본을 다시 훑고, 람다가 캡처한 객체를 계속 붙잡는다. 결과가 필요하면 결과를 담는다.
  • DB 접근 계층은 실행 지점을 숨기지 않는다. 저장소 메서드가 IQueryable을 그대로 돌려주면 호출하는 쪽에서 언제 SQL이 나가는지, 몇 번 나가는지 알 수 없다. 메서드 안에서 실행해 결과를 돌려준다(쿼리 실행 계획).
  • 정렬 결과를 결정적으로 만든다. 랭킹이나 보상 지급 순서를 OrderBy로 정할 때 키가 같은 원소의 순서도 정해 둔다. OrderBy는 안정 정렬이지만 원본 순서가 Dictionary 순회처럼 매번 다르면 결과도 매번 다르다. ThenBy로 고유 키를 더한다(정렬).

주의 사항

  • 질의를 만드는 줄은 아무것도 검사하지 않는다. 원본이 null이 아니면 예외 없이 지나가고, 람다 안의 오류와 연결 문제는 열거할 때 터진다. 스택 추적이 엉뚱한 곳을 가리키는 이유다.
  • Count() > 0 대신 Any()를 쓴다. 컬렉션이 아닌 질의에서 Count()는 끝까지 세고, Any()는 하나 찾으면 멈춘다.
  • 원본을 열거하는 중에 고치지 않는다. 질의 결과를 foreach하며 원본 리스트에서 Remove하면 예외가 난다. 지울 것을 ToList로 먼저 모은 뒤 지운다.
  • 애매하면 담아 둔다. 여러 번 실행되는 것은 눈에 안 보이고, 메모리를 조금 더 쓰는 것은 보인다. 다만 수십만 행처럼 큰 결과는 담는 비용을 따져 스트리밍으로 둔다.
