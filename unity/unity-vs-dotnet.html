먼저 읽을 것: GC 동작과 세대, 동등성과 해시, JIT와 AOT, Unity 코루틴

핵심 요약

같은 C#이라도 Unity에서 도는 코드는 서버의 .NET과 다른 런타임 위에 있다. 세 가지가 특히 다르다. 첫째, 실행 방식이다. 모바일과 콘솔 빌드는 대부분 IL2CPP로 C# 코드를 C++로 바꿔 미리 컴파일한다. 그래서 실행 중에 코드를 만드는 기능이 막히고, 쓰지 않는 것처럼 보이는 코드는 빌드에서 잘려 나간다.

둘째, GC다. Unity의 수거기(Boehm-Demers-Weiser)는 세대를 나누지 않고 압축도 하지 않는다. .NET에서 "금방 죽는 객체는 싸다"던 전제가 성립하지 않아, 프레임마다 생기는 작은 할당이 그대로 멈춤과 단편화가 된다. 셋째, null 검사다. UnityEngine.Object는 ==를 오버로드해 파괴된 오브젝트를 null처럼 보이게 하는데, ?.와 ??와 is null은 이 오버로드를 타지 않는다.

동작 원리

스크립팅 백엔드: Mono와 IL2CPP

IL2CPP는 서버 .NET의 Native AOT와 같은 종류의 제약을 갖는다(JIT와 AOT).

  • 실행 중 코드 생성이 안 된다. System.Reflection.Emit, 식 트리를 컴파일해 빠른 접근자를 만드는 라이브러리가 동작하지 않거나 느린 해석 경로로 떨어진다.
  • 코드 스트리핑이 리플렉션을 깨뜨린다. 빌드 크기를 줄이려고 정적으로 참조되지 않는 타입과 멤버를 지운다. 이름으로 찾아 부르거나 리플렉션으로 채우는 직렬화기는 필요한 생성자나 속성이 사라져 실행 중에 실패한다. link.xml이나 [Preserve] 특성으로 지키지 말라고 알려 줘야 한다.
  • 제네릭은 미리 만들어 둔 조합만 빠르다. 예전에는 값 형식을 인자로 쓰는 제네릭 가상 메서드처럼 빌드 때 보이지 않던 조합이 실행 중 "AOT 코드가 없다" 오류를 냈다. 최근 판은 공유 구현으로 대부분 돌아가게 만들었지만, 그 경로는 전용 코드보다 느리다.

그래서 직렬화처럼 리플렉션에 기대는 일은 빌드 때 코드를 만들어 두는 방식이 맞다. 서버 쪽의 소스 생성기와 같은 생각이다(리플렉션과 소스 생성기).

GC: 세대도 압축도 없다

.NET의 세대별 수거는 갓 만든 객체가 모인 0세대만 훑고 끝낼 수 있어서, 짧게 사는 객체가 많아도 비용이 작다(GC 동작과 세대). Unity의 수거기는 세대가 없어 수거할 때마다 살아 있는 관리 힙 전체를 훑는다. 힙이 커질수록 한 번의 수거가 비싸지고, 짧게 사는 객체든 오래 사는 객체든 비용이 같다.

또 보수적 수거기다. 스택이나 레지스터의 어떤 값이 힙 객체 주소처럼 보이면, 진짜 참조인지 확신하지 못해도 그 객체를 살려 둔다. 산 객체를 실수로 지우는 일은 없지만, 죽은 객체를 오래 남기는 일은 생긴다. 그리고 압축이 없어 힙이 조각나고, 한 번 늘어난 힙은 잘 줄어들지 않는다.

증분 GC(2019 판부터, 새 프로젝트는 기본으로 켜짐)는 한 번의 수거를 여러 프레임에 조금씩 나눠 한 프레임의 멈춤을 줄인다. 전체 작업량은 줄지 않는다. 표시하는 도중에 참조가 많이 바뀌면 다시 훑을 것이 쌓여 결국 한 번에 몰아서 하게 되고, 참조를 쓸 때마다 GC에 알리는 코드(쓰기 장벽)가 끼어들어 일반 코드도 조금 느려진다. 그래서 Unity에서 목표는 수거를 빠르게 만드는 것이 아니라 프레임마다 생기는 할당을 0에 가깝게 만드는 것이다.

null 검사가 두 가지다

GameObject나 컴포넌트 같은 UnityEngine.Object는 관리 쪽 C# 객체와 엔진 안의 네이티브 객체가 짝을 이룬다. Destroy를 부르면 네이티브 쪽이 사라지고, C# 객체는 누가 참조하는 한 남는다. Unity는 이 상태를 알려 주려고 ==를 오버로드해, 파괴된 오브젝트와 null을 비교하면 true를 돌려주게 했다. 이런 객체를 흔히 "가짜 null"이라고 부른다.

표현파괴된 오브젝트에 대해이유
obj == null, !objtrue. 파괴를 잡는다Unity의 연산자 오버로드를 탄다
obj?.DoSomething()호출된다. 네이티브 쪽을 건드리는 순간 MissingReferenceException언어 규칙상 참조 자체만 본다
obj ?? fallbackobj를 고른다위와 같다
obj is null, ReferenceEquals(obj, null)false오버로드를 건너뛰는 진짜 참조 비교다

서버 C#에서 권장하던 습관(?., ??, is null)이 Unity 오브젝트 앞에서는 파괴 검사를 건너뛴다(불변과 null 다루기, 동등성과 해시). Unity 오브젝트에는 ==나 if (obj)를 쓰고, 일반 C# 객체에는 지금처럼 쓴다. 분석기를 켜 두면 이 자리를 짚어 준다. 오버로드된 ==는 네이티브 쪽이 살아 있는지 확인하므로 일반 참조 비교보다 비싸다는 점도 함께 기억해 둔다.

메인 스레드와 잡 시스템

Unity의 엔진 API(오브젝트 생성, 컴포넌트 접근, 트랜스폼 변경)는 대부분 메인 스레드에서만 부를 수 있다. 다른 스레드에서 부르면 예외가 나거나 경고가 찍힌다. Task.Run으로 계산을 넘겼다면 결과를 반영하는 부분은 메인 스레드로 돌아와서 한다(Unity 코루틴의 async 비교 참고). 대량 계산을 여러 코어에 나누는 공식 경로는 잡 시스템이다. 값 형식 데이터만 담은 작업을 예약하면 엔진의 작업자 스레드들이 나눠 돌리고, Burst 컴파일러가 그 코드를 SIMD 명령까지 써서 기계어로 만든다. 관리 객체를 쓸 수 없는 대신 경합 검사를 엔진이 해 준다.

게임 서버에서는

  • 클라이언트와 공유하는 코드는 낮은 쪽에 맞춘다. 패킷 정의, 입력 검증, 데미지 공식, 기획 데이터 로더를 클라이언트와 서버가 함께 쓰는 경우가 많다. 이런 공유 어셈블리는 .NET Standard 2.1을 타깃으로 하고 C# 언어 버전을 9로 묶는다. 서버에서만 빌드해 보면 통과하던 코드가 Unity에 들어가는 순간 문법 오류나 없는 API로 막힌다. CI에서 공유 프로젝트를 두 조건 모두로 빌드해 두면 이 사고를 미리 잡는다(배포 파이프라인).
  • 서버에서 멀쩡하던 코드가 클라이언트에서 할당 폭탄이 된다. 서버 GC는 패킷마다 LINQ로 걸러 만든 작은 리스트쯤은 0세대에서 싸게 치운다. 같은 코드가 클라이언트에서 매 프레임 돌면 Boehm GC의 전체 수거를 앞당기고 끊김이 된다. 공유 코드의 매 프레임 경로는 할당 없이 짠다는 규칙을 양쪽 팀이 함께 지킨다.
  • 직렬화는 리플렉션 없이 돌아가는 방식을 고른다. 서버에서는 잘 되던 리플렉션 기반 직렬화가 IL2CPP 빌드에서 스트리핑으로 깨질 수 있다. 프로토콜은 빌드 때 코드를 만들어 두는 형식(Protobuf, 코드 생성을 쓰는 MessagePack 등)이 양쪽에서 안전하다(게임에서 프로토콜 고르기). 버전이 섞일 때의 규칙은 클라이언트와 서버의 판 호환에서 다룬다.
  • 공유 코드에 ==와 ?. 규칙을 섞지 않는다. 공유 어셈블리는 UnityEngine을 참조하지 않게 둔다. 그래야 서버 C# 습관이 그대로 맞고, Unity 오브젝트를 다루는 코드는 클라이언트 쪽에만 남는다.
  • 클라이언트의 끊김 제보를 볼 때 GC를 의심할 줄 안다. 일정한 간격으로 수십 ms씩 끊긴다면 네트워크가 아니라 클라이언트 GC일 수 있다. 그 순간 서버에는 그 클라이언트의 입력이 잠깐 끊겼다 몰려 들어오는 모양으로 보인다(실행 루프와 FixedUpdate).

주의 사항

  • "짧게 사는 객체는 싸다"는 .NET의 원칙을 Unity에 그대로 옮기지 않는다. 클라이언트에서는 임시 객체가 곧 수거 비용이다.
  • Unity 오브젝트에 ?., ??, is null을 쓰면 파괴 검사를 건너뛴다. 일반 C# 객체에는 문제없다.
  • 에디터(Mono)에서 되는 코드가 IL2CPP 빌드에서 깨질 수 있다. 리플렉션, 동적 코드 생성, 스트리핑에 걸리는 코드는 실제 빌드로 확인한다.
  • 버전마다 지원 범위가 바뀐다. C# 언어 버전, API 호환 수준, GC 기본값은 쓰는 Unity 판의 문서로 확인한다.
