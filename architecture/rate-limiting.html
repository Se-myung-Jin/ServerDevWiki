먼저 읽을 것: 큐와 백프레셔, Redis 활용

핵심 요약

레이트 리밋은 정해진 시간 동안 받을 요청 수에 상한을 두는 장치다. 넘친 요청은 거절하거나 늦춘다. 목적은 둘이다. 한 사용자가 남의 몫까지 쓰지 못하게 막고, 뒤쪽 서버와 DB가 감당할 수 있는 양만 들여보낸다.

알고리즘은 "얼마 동안 몇 번"을 어떻게 세느냐로 나뉜다. 가장 많이 쓰는 것은 토큰 버킷이다. 평균 속도와 순간 허용량을 따로 정할 수 있어서다.

게임 서버에는 하나가 더 있다. 점검 직후나 신규 서버 오픈처럼 수만 명이 한꺼번에 로그인하는 순간이다. 이때는 거절하면 재시도가 폭주를 키운다. 대신 입장 대기열로 순번을 매겨 받을 수 있는 속도로 들인다.

고정 윈도 카운터분 단위 칸마다 횟수를 센다칸 경계에서 상한의 두 배까지 들어온다키당 숫자 하나

누수 버킷큐에 넣고 일정 속도로만 내보낸다몰림을 펴서 고른 속도로 바꾼다큐 크기만큼

동작 원리

고정 윈도는 경계에서 두 배가 들어온다

고정 윈도는 키마다 숫자 하나면 되고 구현이 가장 쉽다. 채팅 도배 막기처럼 경계에서 조금 넘쳐도 괜찮은 곳에는 충분하다. 경계가 문제라면 둘 중 하나를 고른다.

  • 슬라이딩 로그: 요청 시각을 다 적어 두고 최근 60초 안의 개수를 센다. 정확하지만 상한이 크면 키마다 기록이 많아진다.
  • 슬라이딩 윈도 카운터: 이번 칸이 40% 지났다면 지난 칸 횟수 × 0.6 + 이번 칸 횟수로 최근 1분을 근사한다. 숫자 두 개로 경계 문제가 거의 사라진다. 요청이 칸 안에 고르게 왔다고 가정하므로 오차는 남는다.

토큰 버킷: 평균 속도와 순간 허용량을 따로 정한다

토큰을 실제로 매번 채울 필요는 없다. 남은 토큰 수와 마지막으로 계산한 시각만 들고 있다가, 요청이 오면 지난 시간 × r만큼 더하고 b에서 자른다. 그래서 키마다 숫자 두 개면 된다. 요청마다 꺼내는 토큰 수를 다르게 하면 비싼 요청에 더 많은 몫을 매길 수 있다.

누수 버킷은 두 가지 뜻으로 쓰인다. 하나는 측정기로서의 누수 버킷인데, 토큰 버킷과 같은 계산을 거꾸로 본 것이다. 다른 하나는 요청을 큐에 담아 일정 속도로만 흘려보내는 방식이다. 이쪽은 거절 대신 지연으로 몰림을 편다. 뒤쪽이 일정한 속도만 받을 수 있을 때 쓰고, 큐가 차면 결국 거절한다.

IP로만 묶으면 같은 IP 뒤에 여러 사람이 있는 경우를 놓친다. 모바일 통신사의 CGNAT, PC방, 회사망이 그렇다(NAT). IP 리밋은 넉넉하게 두고, 로그인 뒤에는 계정으로 묶는다. 하나의 리밋만 두지 말고 짧은 것(초당)과 긴 것(시간당)을 겹쳐 두면 순간 도배와 꾸준한 남용을 함께 막는다.

여러 서버가 같은 한도를 나눠 쓰려면

게이트웨이가 열 대면, 서버마다 따로 세는 리밋은 사실상 상한의 열 배가 된다. 한도를 정확히 지켜야 하면 카운터를 한곳에 둔다. 보통 Redis다. 고정 윈도는 INCR과 만료로 끝난다(Redis 활용). 토큰 버킷은 읽고 계산하고 쓰는 과정을 Lua 스크립트 하나로 묶어 원자적으로 실행한다. 

-- KEYS[1] = 버킷 키, ARGV[1] = 용량 b, ARGV[2] = 초당 채움 r, ARGV[3] = 쓸 토큰 수
local cap  = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local need = tonumber(ARGV[3])
local t    = redis.call('TIME')                 -- 서버마다 다른 시계 대신 Redis 시계
local now  = tonumber(t[1]) + tonumber(t[2]) / 1000000

local b      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or cap
local ts     = tonumber(b[2]) or now

tokens = math.min(cap, tokens + (now - ts) * rate)
local ok = 0
if tokens >= need then
  tokens = tokens - need
  ok = 1
end
redis.call('HSET', KEYS[1], 'tokens', tostring(tokens), 'ts', tostring(now))
redis.call('EXPIRE', KEYS[1], math.ceil(cap / rate) + 1)   -- 다 찼을 시각이 지나면 지운다
return ok

대가는 요청마다 Redis 왕복 한 번이다. 이것이 부담이면 정확도를 조금 내준다. 서버마다 전체 한도의 1/N을 로컬에서 세거나, 로컬에서 세다가 주기적으로 중앙과 맞춘다. 남용을 막는 리밋은 대개 이 정도 오차로 충분하다. 돈이나 재고처럼 정확해야 하는 상한은 리밋이 아니라 원자적 갱신으로 지킨다.

거절할 때는 언제 다시 오라고 알려 준다

HTTP라면 429 Too Many Requests와 Retry-After 헤더로 답한다. 클라이언트는 그 시간만큼 기다렸다가 다시 보낸다. 답을 주지 않으면 클라이언트는 바로 재시도하고, 거절이 다시 부하가 된다. 재시도에 지터를 섞는 이유는 서비스 호출에서 다룬다.

.NET 7부터는 System.Threading.RateLimiting에 고정 윈도, 슬라이딩 윈도, 토큰 버킷, 동시 실행 수 리미터가 들어 있다. 키별로 나누는 PartitionedRateLimiter도 있다. ASP.NET Core는 AddRateLimiter와 UseRateLimiter로 미들웨어를 건다. 거절 상태 코드의 기본값은 503이므로 RejectionStatusCode를 429로 바꿔 둔다.

입장 대기열: 거절 대신 순번을 준다

  • 순번은 연결이 아니라 계정에 붙인다. 대기 중 앱이 꺼지거나 와이파이가 바뀌어도, 일정 시간 안에 돌아오면 같은 순번을 이어 간다. 연결에 붙이면 끊길 때마다 맨 뒤로 가고, 플레이어는 재접속을 반복한다. Redis 정렬 집합에 계정 ID를 넣고 점수에 들어온 순서를 두면 순번 조회가 ZRANK 한 번이다.
  • 입장 속도는 두 값 중 작은 쪽에 맞춘다. 하나는 게임 서버의 빈자리(상한 − 현재 접속)이고, 다른 하나는 로그인 처리량이다. 로그인 한 번에 캐릭터 로드와 DB 조회가 따르므로, 빈자리가 많아도 DB가 받을 수 있는 속도 이상으로 들이면 안 된다.
  • 예상 시간은 순번 ÷ 최근 입장 속도로 계산한다. 약간 넉넉하게 보여 준다. 예상보다 빨리 들어가는 것은 불만이 없지만, 늦어지면 재접속이 늘어난다.
  • 대기열 자체가 부하가 되지 않게 한다. 수만 명이 1초마다 상태를 물으면 대기열 서버가 먼저 무너진다. 다음 조회 시각을 서버가 응답에 담아 정한다. 순번이 멀수록 길게 하고, 클라이언트마다 조금씩 어긋나게 한다.
  • 입장 토큰은 짧게, 한 번만 쓴다. 계정 ID, 만료 시각, 서명을 담는다. 게임 서버는 대기열에 묻지 않고 서명만 확인해도 된다. 토큰을 다른 계정이 쓰거나 대기열을 건너뛰는 시도를 막는다(인증과 세션).
  • 막 튕긴 플레이어는 대기열을 건너뛰게 한다. 게임 중 연결이 끊긴 플레이어가 수천 번째 순번을 받으면 크게 반발한다. 최근 몇 분 안에 접속해 있던 계정은 재접속 유예로 바로 들인다(끊긴 연결 알아차리기).

서버 안에서 큐가 넘칠 때 무엇을 버리고 어떻게 압력을 앞으로 전할지는 큐와 백프레셔에서 다룬다. 입장 대기열은 그보다 바깥, 사람이 기다리는 자리의 큐다.

게임 서버에서는

  • 패킷 종류마다 리밋을 따로 둔다. 채팅, 귓속말, 거래 신청, 친구 요청, 거래소 검색은 사람이 낼 수 있는 속도가 다르다. 종류별로 토큰 버킷을 두면 정상 플레이는 건드리지 않고 도배와 매크로만 걸린다. 이동 패킷은 횟수보다 속도와 거리 검증으로 다룬다.
  • 세션 안의 리밋은 로직 스레드 안에서 센다. 세션 객체마다 버킷을 들고 있으면 락도 Redis도 필요 없다. 시간은 벽시계가 아니라 단조 시계로 잰다(시계와 타이머).
  • 넘친 요청은 조용히 버리고, 기록은 남긴다. 리밋을 크게 넘기는 계정은 봇이나 변조 클라이언트일 가능성이 높다. 넘친 횟수를 계정별로 모아 탐지 신호로 넘긴다(게임 보안). 한 번 넘었다고 바로 끊으면 정상 플레이어도 걸린다.
  • 네트워크가 막혔다 풀리면 정상 클라이언트도 몰아서 보낸다. 몇 초간 끊겼던 연결이 살아나면 쌓였던 패킷이 한꺼번에 온다. 버킷 크기를 그 정도는 받아 주게 잡지 않으면 오탐이 난다.
  • 서버 사이 호출에도 리밋을 둔다. 한 서비스의 재시도 폭주가 DB 커넥션을 다 잡으면 다른 기능까지 멈춘다. DB 앞에는 동시 실행 수 리미터를 두고, 남는 요청은 빨리 실패시킨다(서비스 호출).
// 세션마다 하나. 로직 스레드에서만 만지므로 락이 없다.
public sealed class TokenBucket
{
    private readonly double _capacity, _perSecond;
    private double _tokens;
    private long _last;   // Stopwatch 틱(단조 시계)

    public TokenBucket(double capacity, double perSecond)
    {
        _capacity = capacity;
        _perSecond = perSecond;
        _tokens = capacity;
        _last = Stopwatch.GetTimestamp();
    }

    public bool TryTake(double n = 1)
    {
        long now = Stopwatch.GetTimestamp();
        _tokens = Math.Min(_capacity,
            _tokens + Stopwatch.GetElapsedTime(_last, now).TotalSeconds * _perSecond);
        _last = now;
        if (_tokens < n) return false;
        _tokens -= n;
        return true;
    }
}

// 채팅: 순간 5개, 평균 초당 1개
if (!session.ChatLimit.TryTake())
{
    session.Abuse.Count(PacketKind.Chat);  // 탐지 신호로 모은다
    return;                                // 응답 없이 버린다
}

주의 사항

  • 리밋은 남용을 막는 장치이지 용량 계획이 아니다. 전체 요청이 서버 용량을 넘으면 사용자별 리밋을 다 지켜도 넘친다. 전체 상한은 입장 제어와 백프레셔가 맡는다.
  • 거절도 공짜가 아니다. 요청을 받아 리밋을 확인하고 답하는 데까지는 비용이 든다. 아주 큰 폭주는 앞단(엣지, 로드 밸런서)에서 걸러야 서버까지 오지 않는다.
  • 카운터 저장소가 죽었을 때의 동작을 정해 둔다. Redis가 응답하지 않을 때 모두 통과시킬지(가용성), 모두 막을지(보호)를 기능마다 정한다. 로그인은 대개 열어 두고 로컬 리밋으로 버틴다.
  • 서버 시계로 세지 않는다. 여러 서버가 각자 시각으로 토큰을 채우면 시계가 앞선 서버만큼 더 허용된다. 중앙에서 셀 때는 중앙의 시계를 쓴다.
  • 대기열 우선순위는 신중하게 정한다. 결제 등급에 따라 대기열을 건너뛰게 하면 운영 정책과 공정성 문제가 된다. 건너뛰기는 재접속 유예처럼 누구나 이해하는 규칙에만 둔다.
