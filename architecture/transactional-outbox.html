먼저 읽을 것: 트랜잭션과 ACID, 멱등 소비자

핵심 요약

처리 하나가 DB에도 쓰고 메시지 브로커에도 보내야 할 때가 있다. 두 시스템은 한 트랜잭션을 함께 쓰지 못한다. 그래서 어느 쪽을 먼저 해도 중간에 실패하면 둘이 어긋난다. 이것을 이중 쓰기 문제라고 부른다.

트랜잭셔널 아웃박스는 보낼 메시지를 브로커로 바로 보내지 않는다. 업무 데이터를 고치는 같은 DB 트랜잭션 안에서 outbox 테이블에 한 행으로 적는다. 브로커로 보내는 일은 별도의 릴레이가 그 테이블을 읽어 맡는다. 두 시스템에 걸친 쓰기가 한 DB 안의 쓰기로 바뀐다.

대가는 중복이다. 릴레이는 보낸 뒤 표시하기 전에 죽을 수 있으므로 같은 메시지를 다시 보낸다. 아웃박스가 주는 것은 적어도 한 번이고, 받는 쪽은 멱등해야 한다.

동작 원리

어느 쪽을 먼저 해도 구멍이 남는다

DB와 브로커는 서로 다른 시스템이다. 한쪽의 커밋이 다른 쪽의 커밋을 기다려 주지 않는다. 처리 중간에 프로세스가 죽거나 네트워크가 끊기는 순간을 생각하면 순서마다 구멍이 하나씩 있다.

순서중간에 실패하면게임 서버에서 보이는 모습
DB 커밋 후 전송상태는 바뀌었는데 그 사실이 밖으로 나가지 않는다골드는 줄었는데 경매 서비스에는 입찰이 없다
전송 후 DB 커밋일어나지 않은 일이 밖에 알려진다커밋이 실패해 아이템은 그대로인데 "판매 완료" 알림이 나갔다
트랜잭션 안에서 전송전송은 롤백되지 않는다. 롤백되면 두 번째와 같다위와 같다. 게다가 브로커 응답을 기다리는 동안 락을 쥐고 있다

두 시스템을 한 트랜잭션으로 묶는 방법으로 2단계 커밋이 있다. 하지만 Kafka나 RabbitMQ 같은 흔한 브로커는 DB와 함께 2단계 커밋에 참가하지 않는다. 참가하더라도 조정자를 기다리는 동안 락이 잡혀 있는 비용이 크다. 아웃박스는 2단계 커밋 없이 이 문제를 푼다.

보낼 메시지를 같은 트랜잭션에 함께 쓴다

CREATE TABLE outbox (
  id            BIGINT       PRIMARY KEY,        -- 분산 ID나 시퀀스
  aggregate_id  BIGINT       NOT NULL,           -- 순서를 지킬 단위(캐릭터 ID 등)
  type          VARCHAR(64)  NOT NULL,           -- 'ItemSold', 'GoldGranted'
  payload       JSON         NOT NULL,
  created_at    TIMESTAMP    NOT NULL,
  published_at  TIMESTAMP    NULL                -- NULL이면 아직 안 보냈다
);
CREATE INDEX ix_outbox_unpublished ON outbox (published_at, id);
await using var tx = await conn.BeginTransactionAsync(ct);

await conn.ExecuteAsync(
    "UPDATE inventory SET owner_id = @buyer WHERE item_uid = @item AND owner_id = @seller",
    new { buyer, item, seller }, tx);
await conn.ExecuteAsync(
    "UPDATE character SET gold = gold - @price WHERE id = @buyer AND gold >= @price",
    new { buyer, price }, tx);

// 브로커로 보내지 않는다. 같은 트랜잭션에 적기만 한다
await conn.ExecuteAsync(
    "INSERT INTO outbox (id, aggregate_id, type, payload, created_at) " +
    "VALUES (@id, @agg, 'ItemSold', @payload, @now)",
    new { id = ids.Next(), agg = seller, payload = Json(new { tradeId, item, price }), now }, tx);

await tx.CommitAsync(ct);   // 여기서 둘 다 확정된다

메시지 ID는 아웃박스 행을 만들 때 정해 두고 끝까지 바꾸지 않는다. 릴레이가 같은 행을 두 번 보내도 ID가 같아야 받는 쪽이 중복을 알아본다(분산 ID 생성).

릴레이는 두 가지 방식으로 읽는다

방식어떻게 읽나장점약점
폴링 발행자주기적으로 published_at IS NULL인 행을 골라 보내고 표시한다DB와 코드만 있으면 된다. 이해하고 고치기 쉽다폴링 간격만큼 늦다. 자주 돌리면 DB에 읽기 부하가 생긴다
변경 로그 기반(CDC)DB의 복제 로그(MySQL binlog, PostgreSQL 논리 디코딩)를 따라가며 outbox 삽입을 잡는다. Debezium의 outbox 라우터가 대표적이다지연이 짧고 테이블을 조회하지 않는다. 커밋 순서대로 나온다CDC 도구를 운영해야 한다. 로그 보관 설정과 장애 복구를 따로 챙긴다

CDC가 읽는 로그는 로그와 지속성에서 본 바로 그 로그다. 커밋된 것만, 커밋 순서대로 나온다는 성질을 그대로 빌린다.

폴링 발행자를 여러 개 띄우면 같은 행을 둘이 동시에 집을 수 있다. 행 잠금으로 나눠 가진다. 

-- PostgreSQL, MySQL 8.0 이상. SQL Server는 WITH (UPDLOCK, READPAST)
SELECT id, type, payload FROM outbox
WHERE published_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
-- 보낸 뒤 같은 트랜잭션에서 UPDATE outbox SET published_at = now() WHERE id IN (...)

"마지막으로 보낸 ID 다음부터"는 행을 빠뜨린다

폴링 릴레이를 "마지막으로 보낸 id보다 큰 행"으로 짜고 싶어진다. 그런데 ID를 받은 순서와 커밋된 순서는 다르다. 트랜잭션 A가 id 101을 받고 커밋이 늦는 사이, B가 id 102를 받고 먼저 커밋할 수 있다. 릴레이가 그 순간 102까지 보내고 기준점을 102로 옮기면, 뒤늦게 커밋된 101은 영원히 건너뛴다.

그래서 기준점 대신 보냈는지 여부로 고른다. 위 예처럼 published_at을 두고 그 컬럼에 인덱스를 건다. CDC는 커밋 순서대로 읽으므로 이 문제가 없다.

순서는 단위를 정해야 지켜진다

outbox 전체의 순서를 지키려면 릴레이 하나가 한 줄로 보내야 한다. 그러면 처리량이 릴레이 하나에 묶인다. 실제로 필요한 순서는 대개 한 대상 안의 순서다. 같은 캐릭터의 "지급 → 회수"가 뒤집히면 안 되지만, 서로 다른 캐릭터의 메시지 순서는 상관없다.

그래서 aggregate_id를 브로커의 파티션 키로 쓴다. Kafka는 같은 키를 같은 파티션에 넣고 파티션 안 순서를 지킨다(메시지 모델 세 갈래). 재전송 때문에 순서가 잠깐 뒤섞일 수 있으므로, 순서가 중요한 소비자는 메시지에 대상별 버전 번호를 함께 받아 늦게 온 옛 메시지를 버린다.

보낸 행은 치워야 한다

outbox는 쌓이기만 하는 테이블이다. 보낸 행을 주기적으로 지우거나, 날짜로 파티션을 나눠 오래된 파티션을 통째로 떼어 낸다. 대량 DELETE는 락과 로그를 크게 만들므로 작은 묶음으로 나눠 지운다. 감사용으로 남겨야 하는 기록이면 outbox가 아니라 별도 원장 테이블에 둔다(CQRS와 이벤트 소싱).

받는 쪽에는 인박스를 둔다

아웃박스가 보내는 쪽 이중 쓰기를 막는다면, 인박스는 받는 쪽 중복을 막는다. 소비자는 처리한 메시지 ID를 inbox 테이블에 적는다. 업무 결과와 같은 트랜잭션으로 적고, ID에 유니크 키를 건다. 같은 메시지가 다시 오면 삽입이 실패하므로 처리하지 않고 확인응답만 보낸다. 자세한 방법은 멱등 소비자에서 다룬다.

.NET에서는 MassTransit, NServiceBus 같은 메시징 라이브러리가 EF Core와 엮은 아웃박스를 기능으로 제공한다. 직접 만들 때도 구조는 위와 같다.

게임 서버에서는

  • 재화와 아이템이 움직이면 아웃박스로 알린다. 거래가 커밋되면 경매 서비스, 우편 서비스, 감사 로그 수집기가 그 사실을 알아야 한다. 이 알림을 커밋 뒤 직접 보내면, 서버가 그 사이에 죽을 때 "골드는 빠졌는데 경매에는 기록이 없는" 상태가 남는다. CS 문의로 돌아오는 대표적인 불일치다.
  • 모든 로그를 아웃박스에 넣지는 않는다. 이동, 채팅, 전투 같은 행동 로그는 양이 많고 몇 건 잃어도 된다. 이런 로그까지 outbox에 넣으면 게임 DB의 쓰기가 몇 배로 는다. 돈과 아이템이 걸린 사건만 아웃박스로 보내고, 나머지는 로그 수집기로 바로 보낸다.
  • 샤드마다 outbox와 릴레이를 둔다. outbox는 업무 테이블과 같은 DB에 있어야 한 트랜잭션에 들어간다. 월드 DB가 여럿이면 outbox도 DB마다 있고, 릴레이도 DB마다 하나씩 붙인다.
  • 외부 결제·플랫폼 서버에 알리는 일도 같다. 지급을 커밋한 뒤 플랫폼에 "소비 완료"를 알려야 하는 흐름이 있다. 이 호출을 outbox 행으로 남기고 릴레이가 재시도하게 하면, 서버가 재시작해도 알림이 빠지지 않는다. 받는 쪽 API가 같은 요청 ID를 중복으로 처리하는지 먼저 확인한다.
  • 밀린 행 수를 지표로 둔다. outbox는 그 자체로 큐다. 릴레이가 멈춰도 거래는 계속 성공하므로 아무도 모른다. published_at IS NULL인 행 수와 가장 오래된 행의 나이를 경보로 건다(백프레셔).

주의 사항

  • 아웃박스는 중복을 없애지 않는다. 한 트랜잭션으로 묶이는 것은 "업무 변경과 보낼 메시지를 함께 남기는 것"까지다. 전송은 그 밖에서 일어나므로 재전송이 남는다. 소비자가 멱등하지 않으면 아웃박스를 들여도 이중 지급이 생긴다.
  • 트랜잭션 안에서 브로커를 부르지 않는다. 아웃박스를 쓰면서도 "빨리 보내려고" 커밋 전에 직접 전송을 섞으면 처음 문제로 돌아간다. 빨라야 하면 커밋 직후 릴레이를 깨우는 신호만 보낸다.
  • payload에는 그 시점의 사실을 담는다. 메시지에 ID만 담고 받는 쪽이 DB를 다시 읽게 하면, 그 사이 값이 바뀌어 다른 사실을 읽는다. 받는 쪽이 판단에 쓸 값은 커밋할 때의 값으로 함께 넣는다.
  • 보내지 못한 행을 버리지 않는다. 형식이 틀려 계속 실패하는 행이 있으면 릴레이가 그 행에서 막힌다. 재시도 횟수를 세고, 넘으면 따로 옮겨 사람이 본다(데드 레터와 서킷 브레이커).
