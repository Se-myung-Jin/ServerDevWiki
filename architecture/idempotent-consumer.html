먼저 읽을 것: 전달 보장과 exactly-once · 트랜잭션과 ACID · 동시성 제어와 데드락

핵심 요약

최소 한 번 전달을 고르면 같은 메시지는 언젠가 다시 온다. 중복을 막을 수는 없으니 흡수한다. 같은 메시지를 두 번 처리해도 결과가 한 번 처리한 것과 같게 만드는 소비자가 멱등 소비자다.

세 가지가 갖춰져야 한다. 같은 메시지임을 알아볼 안정된 ID, 그 ID를 처리했다는 기록을 업무 결과와 같은 트랜잭션에 쓰기, 동시에 들어온 중복을 유니크 제약으로 막기다. "조회해서 없으면 처리"만으로는 동시에 온 두 사본을 막지 못한다.

동작 원리

중복은 세 곳에서 온다

어디서무슨 일이 일어나나
보내는 쪽 재시도발행 확인을 못 받은 쪽이 같은 메시지를 다시 보낸다. 실제로는 브로커에 이미 들어가 있었을 수 있다
브로커 재전달소비자가 처리는 끝냈는데 확인 전에 죽거나, 처리 시간이 길어 잠금(가시성 시간 초과)이 풀려 다른 소비자에게 다시 간다
소비자 재처리배포나 리밸런싱으로 커밋하지 않은 오프셋부터 다시 읽는다. 운영자가 오프셋을 되감아 다시 돌리기도 한다

셋 다 유실을 막으려는 장치가 만든 중복이다. 재전송을 끄면 유실이 돌아오므로, 이 방어선은 소비자 코드에 남는다(전달 보장과 exactly-once).

ID는 만들 때 정하고 끝까지 바꾸지 않는다

중복을 알아보려면 첫 전송과 재전송이 같은 ID를 가져야 한다. 그래서 ID는 메시지를 처음 만드는 쪽이 정한다. 재시도할 때마다 새 GUID를 만들거나, 받는 쪽에서 번호를 매기면 재전송된 메시지가 새 메시지로 보인다. 브로커가 붙이는 전달 번호나 오프셋도 재발행되면 바뀌므로 업무 ID로 쓰지 않는다.

가장 좋은 ID는 업무가 이미 가진 번호다. 보상 지급이면 "시즌 12 랭킹 보상, 캐릭터 1001", 결제면 스토어의 거래 번호, 매치 결과면 매치 ID다. 이런 번호가 없으면 만드는 시점에 분산 ID를 하나 붙인다.

처리 기록과 업무 결과는 함께 커밋한다

처리한 메시지 ID를 기록해 두고 이미 있으면 건너뛴다. 이 기록을 업무 결과와 따로 커밋하면 틈이 남는다. 우편을 넣고 기록하기 전에 죽으면 다음 전달이 우편을 또 넣는다. 반대 순서면 기록만 남고 우편이 빠진다. 둘을 같은 트랜잭션에 쓰면 이 틈이 없다. 받는 쪽의 이 구조를 인박스 패턴이라고 부르며, 보내는 쪽의 트랜잭셔널 아웃박스와 짝을 이룬다. 

CREATE TABLE processed_message (
    message_id  VARCHAR(64) PRIMARY KEY,   -- 유니크 제약이 중복 판정을 한다
    handled_at  TIMESTAMP NOT NULL
);
public async Task HandleAsync(RewardGranted msg, CancellationToken ct)
{
    await using var conn = await _dataSource.OpenConnectionAsync(ct);
    await using var tx = await conn.BeginTransactionAsync(ct);

    // PostgreSQL. MySQL은 INSERT IGNORE, SQL Server는 유니크 위반(2627)을 잡는다
    int inserted = await conn.ExecuteAsync(
        "INSERT INTO processed_message (message_id, handled_at) VALUES (@Id, now()) ON CONFLICT DO NOTHING",
        new { msg.Id }, tx);
    if (inserted == 0)
    {
        await tx.RollbackAsync(ct);
        return;                       // 이미 처리했다. 호출한 쪽은 그대로 ACK한다
    }

    await conn.ExecuteAsync(
        "INSERT INTO mail (character_id, item_id, count, source_id) VALUES (@CharacterId, @ItemId, @Count, @Id)",
        msg, tx);
    await tx.CommitAsync(ct);         // 커밋이 끝난 뒤에 브로커에 ACK한다
}

조회 후 삽입은 동시에 온 중복을 놓친다

"SELECT로 처리 기록을 찾고, 없으면 처리한다"를 두 단계로 나누면 두 소비자가 같은 순간 조회해 둘 다 "없다"고 보는 틈이 생긴다. 재전달은 잠금 시간 초과처럼 첫 처리가 끝나기 전에 일어나는 경우가 많아서, 이 틈은 생각보다 자주 열린다. 애플리케이션 코드로는 이 틈을 닫지 못한다.

판정을 DB에 맡긴다. 처리 기록의 ID에 유니크 제약을 걸면 두 번째 INSERT는 첫 트랜잭션이 끝날 때까지 기다렸다가 충돌로 실패한다. 업무 테이블 자체에 유니크 키를 두는 것도 같은 효과다. 위 예에서 mail.source_id에 유니크 제약을 걸면 처리 기록 테이블 없이도 같은 보상이 두 번 들어가지 않는다(동시성 제어와 데드락).

본래 멱등한 연산으로 바꿀 수도 있다

기록 없이도 멱등한 연산이 있다. SET level = 31은 두 번 해도 같다. SET gold = gold + 100은 두 번 하면 200이 늘어난다. 가능하면 "얼마나 바꿔라" 대신 "이 값이 되게 하라"로 메시지를 설계한다.

다만 값을 덮어쓰는 메시지는 순서가 문제다. 레벨 31 메시지가 재전달되어 레벨 32 메시지보다 늦게 도착하면 31로 되돌아간다. 메시지에 버전을 실어 보내고, 더 새로운 것만 반영한다. 

UPDATE character_summary
SET level = @Level, version = @Version
WHERE character_id = @CharacterId AND version < @Version;   -- 옛 메시지는 0행

기록은 영원히 둘 필요가 없지만 충분히 길게 둔다

처리 기록은 쌓인다. 재전달이 일어날 수 있는 기간보다 길게만 두면 된다. 브로커 보존 기간, 데드 레터 큐에서 사람이 다시 넣는 기간, 오프셋을 되감을 수 있는 기간 가운데 가장 긴 것을 기준으로 잡고, 그보다 오래된 기록은 날짜 파티션째 지운다. 너무 짧게 잡으면 늦게 온 재전달이 새 메시지로 통과한다.

게임 서버에서는

  • 보상과 우편은 지급 출처를 유니크 키로 둔다. "이벤트 7, 캐릭터 1001"처럼 같은 보상이 두 번 생길 수 없는 조합을 키로 삼으면, 재전달이든 운영자의 재실행이든 같은 키에서 걸린다.
  • 결제 콜백은 스토어 거래 번호로 거른다. 앱 스토어나 결제 대행사는 응답을 못 받으면 같은 콜백을 여러 번 보낸다. 거래 번호에 유니크 제약을 걸고, 이미 처리된 번호면 성공으로 응답한다. 실패로 응답하면 상대가 계속 다시 보낸다.
  • 세션 서버의 결과 보고는 매치 ID로 받는다. 매치가 끝나고 결과를 보고하는 도중 세션 서버가 죽고 다시 보고하면, 매치 ID로 두 번째를 버린다. 랭크 점수가 두 번 오르는 사고를 막는다.
  • DB 밖으로 나가는 일은 트랜잭션에 넣을 수 없다. 외부 API 호출이나 클라이언트 알림은 롤백되지 않는다. 외부 API에는 멱등 키를 넘기고(결제 대행사 API 상당수가 멱등 키 헤더를 받는다), 클라이언트 알림은 커밋 뒤에 보낸다.

주의 사항

  • 멱등 처리는 브로커 설정이 아니라 소비자 코드의 일이다. 브로커를 바꿔도 보장은 최소 한 번에서 더 올라가지 않는다.
  • "이미 처리함"은 성공으로 다룬다. 중복을 오류로 던지면 브로커가 실패로 보고 계속 다시 보내고, 결국 데드 레터 큐로 간다. 건너뛰고 확인한다.
  • ACK는 커밋 뒤에 보낸다. 커밋 전에 확인하면 커밋이 실패했을 때 메시지가 사라진다. 커밋 뒤 확인 전에 죽는 틈은 위의 처리 기록이 흡수한다.
  • 한 번만 처리하는 것과 한 번만 전달받는 것은 다르다. 중복 전달은 계속 오고, 결과만 한 번이 된다. 처리 비용이 큰 메시지라면 앞단에서 중복 감지를 더해 부하를 줄일 수 있지만, 그것이 이 방어선을 대신하지는 못한다.
