먼저 읽을 것: 게임 서버 스레딩 모델 · 확장과 샤딩

핵심 요약

액터는 상태와 그 상태를 고치는 코드를 한데 가둔 단위다. 바깥에서는 상태를 직접 읽거나 고칠 수 없고, 메시지를 보내야 한다. 액터는 자기 메일박스에 쌓인 메시지를 한 번에 하나씩 처리한다. 그래서 액터 안에서는 락이 필요 없다.

대가는 경계다. 한 액터 안에서 끝나던 일이 액터 둘에 걸치면 원자성이 사라지고, 서로를 기다리는 호출은 데드락이 된다. 가상 액터(Orleans의 그레인)는 여기에 한 가지를 더 바꾼다. 액터를 만들고, 어느 서버에 두고, 죽은 서버의 액터를 다른 곳에서 살리는 일을 응용 대신 런타임이 맡는다.

동작 원리

상태는 안에 두고 메시지로만 주고받는다

게임 서버 스레딩 모델의 "조각별 직렬 실행"을 개체 단위로 끝까지 밀고 간 것이 액터다. 존 하나에 큐 하나를 두던 것을 플레이어 하나, 길드 하나, 경매 품목 하나마다 둔다. 상태를 고치는 실행 흐름이 언제나 하나라서 경합이 없다. 수만 개의 액터가 있어도 실제 스레드는 스레드 풀 몇 개이고, 런타임이 메일박스가 빈 액터는 건너뛰고 메시지가 있는 액터만 스레드에 올린다.

기다리는 동안에도 액터는 막혀 있다

"한 번에 하나"는 메시지를 받아서 끝낼 때까지를 말한다. 처리 도중 DB 저장을 await하면 그 응답이 올 때까지 액터는 다음 메시지를 꺼내지 않는다. 스레드는 놓아주지만 액터는 붙잡혀 있다. DB가 100ms 걸리면 그 플레이어 액터는 초당 열 건밖에 처리하지 못한다.

서로를 부르는 데드락도 같은 규칙에서 나온다. 데드락의 네 조건 가운데 순환 대기가 액터 호출 사이에서 생긴다. 락을 쓰지 않았는데도 생긴다는 점이 함정이다. Orleans는 이런 호출이 응답 시한(기본 30초)을 넘기면 예외로 끝낸다.

풀어 주는 장치가 재진입이다. Orleans에서 그레인에 [Reentrant]를 붙이거나 메서드에 [AlwaysInterleave]를 붙이면, 한 요청이 await로 기다리는 사이 다른 요청이 끼어들어 실행된다. 여전히 한 번에 한 흐름만 실행되므로 락은 필요 없다. 대신 await 앞에서 읽은 값이 뒤에서 그대로라는 보장이 사라진다. 비동기 코드의 원자성 문제가 액터 안으로 돌아오는 셈이다.

가상 액터는 수명과 위치를 런타임에 넘긴다

Orleans는 Microsoft Research에서 만들었고, Halo 4의 클라우드 서비스를 돌리는 데 쓰였다. 이 모델에서 그레인은 "언제나 있는" 논리적 개체다. 코드는 키로 그레인을 부를 뿐 만들거나 지우지 않는다.

하는 일액터를 직접 다룰 때(Akka.NET 등)가상 액터(Orleans)
만들고 없애기응용이 만들고 멈춘다처음 호출될 때 활성화하고, 한동안 호출이 없으면 비활성화해 메모리에서 내린다
어디에 둘지응용이 정한다런타임이 배치 전략(무작위, 호출자와 같은 서버, 부하 기준 등)으로 정한다
찾기액터 주소(참조)를 들고 있어야 한다키만 있으면 부른다. 위치는 런타임의 그레인 디렉터리가 안다
서버가 죽으면감독자가 다시 만들고 상태 복구도 응용이 한다다음 호출 때 살아 있는 서버에서 다시 활성화된다. 상태는 저장소에서 다시 읽는다
 
public interface IPlayerGrain : IGrainWithIntegerKey
{
    Task<int> AddGold(int amount);
}

public sealed class PlayerGrain(
    [PersistentState("player")] IPersistentState<PlayerState> state) : Grain, IPlayerGrain
{
    public async Task<int> AddGold(int amount)
    {
        state.State.Gold += amount;     // 이 그레인 안에서는 한 번에 요청 하나
        await state.WriteStateAsync();  // 저장을 기다리는 동안 다음 요청은 줄을 선다
        return state.State.Gold;
    }
}

// 부르는 쪽: 어느 서버에 있는지 모르고 키로 부른다
var player = grainFactory.GetGrain<IPlayerGrain>(playerId);
await player.AddGold(100);

위치가 감춰졌다는 것은 비용도 감춰졌다는 뜻이다. 같은 호출이 같은 프로세스 안에서 끝날 수도, 직렬화되어 다른 서버로 갈 수도 있다. 코드만 봐서는 어느 쪽인지 모른다. 자주 주고받는 그레인끼리 같은 서버에 두는 배치 전략을 고르는 일은 다시 응용의 몫이다.

단일 활성화도 절대적이지 않다. Orleans는 키 하나에 활성화 하나를 지키려 하지만, 서버가 죽었다고 잘못 판정되거나 클러스터 멤버십이 흔들리는 짧은 순간에는 같은 그레인이 두 곳에서 살아날 수 있다. 그래서 그레인 상태 저장은 ETag로 낙관적 동시성 검사를 한다. 늦게 쓰는 쪽은 충돌로 실패한다(동시성 제어와 데드락). "액터니까 하나뿐"이라고 믿고 재화를 다루면 안 된다.

감독 트리는 실패를 위로 올린다

Erlang/OTP와 Akka.NET은 다른 갈래다. 액터가 자식 액터를 만들고, 자식이 예외로 죽으면 부모(감독자)가 처리 방침을 정한다. 다시 시작할지, 무시하고 계속할지, 멈출지, 자기 부모에게 넘길지다. 죽은 액터 하나만 다시 시작하는 방식(one-for-one)과 형제를 모두 다시 시작하는 방식(all-for-one)이 있다.

"고치려 하지 말고 죽게 둔다(let it crash)"는 말이 여기서 나왔다. 오류 처리 코드를 곳곳에 넣는 대신, 깨끗한 상태로 다시 시작하는 일을 구조가 맡는다. 가상 액터는 이 트리 대신 "다음 호출 때 다시 활성화"로 같은 문제를 푼다.

선택 기준

상황액터가 맞나이유
플레이어, 길드, 채팅방처럼 상태가 개체마다 닫혀 있다맞는다개체 하나에 액터 하나. 개체가 늘면 액터가 늘고 서버를 넘어 퍼진다
로비, 친구, 우편, 업적처럼 개체별 요청이 많고 서로 얽힘이 적다잘 맞는다가상 액터의 활성화·비활성화가 접속자 수에 맞춰 메모리를 쓴다
두 플레이어 사이의 거래처럼 여러 액터를 함께 고쳐야 한다장치가 더 필요하다액터 둘에 걸친 원자성은 없다. 거래 액터를 따로 두거나 사가, 분산 트랜잭션 기능을 쓴다
인기 경매 품목, 월드 보스처럼 한 개체에 요청이 몰린다상한이 생긴다액터 하나는 더 나뉘지 않는다. 확장과 샤딩에서 말한 "나눌 수 없는 것"이 그대로 남는다
틱마다 수백 개 엔티티가 서로 부딪히는 전투 시뮬레이션맞지 않는다엔티티마다 메시지를 주고받으면 비용이 크다. 존 하나를 한 스레드가 도는 편이 낫다(서버 틱 루프)

게임 서버에서는

  • 전투는 존 스레드, 메타 기능은 액터로 나누는 구성이 흔하다. 위치와 충돌은 틱 루프 안에서 한꺼번에 계산하고, 친구·길드·우편·랭킹 요청처럼 개체별로 닫힌 것은 액터로 보낸다.
  • 액터 안에서 오래 기다리지 않는다. 외부 결제 API 호출처럼 느린 일을 액터 메서드에서 그대로 await하면 그 플레이어의 모든 요청이 줄을 선다. 느린 일은 작업 큐로 넘기고 결과를 메시지로 받는다(메시지 모델 세 갈래).
  • 호출 방향을 정해 고리를 끊는다. 플레이어 → 길드 → 플레이어처럼 되돌아오는 호출이 데드락과 재진입 버그를 만든다. 위에서 아래로만 부르고, 거꾸로 알릴 일은 응답을 기다리지 않는 단방향 메시지로 보낸다.
  • 비활성화는 저장 시점이 된다. 그레인이 내려가기 전에 상태를 저장해야 한다. 서버가 그대로 죽으면 비활성화 훅은 불리지 않으므로, 중요한 변경은 그때그때 저장한다(ORM과 저장 설계).

주의 사항

  • 가상 액터는 액터 모델의 다른 이름이 아니다. 액터 모델은 상태를 가두고 메시지로 주고받는 방식이고, 가상 액터는 그 액터의 수명과 위치를 누가 맡느냐를 바꾼 것이다.
  • 액터 안에 락이 없다고 시스템에 경쟁이 없는 것은 아니다. 액터 사이의 변경, 재진입 중 끼어든 요청, 드물게 생기는 중복 활성화가 남는다.
  • 메시지는 공유 참조를 넘기면 안 된다. 같은 프로세스 안에서 가변 객체를 메시지로 넘기면 두 액터가 같은 객체를 고친다. 불변 객체를 넘기거나 복사한다(불변과 null 다루기).
