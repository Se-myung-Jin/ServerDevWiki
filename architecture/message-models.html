먼저 읽을 것: 이벤트 버스와 메시지 전달 · Redis 활용 · 액터 모델과 가상 액터

핵심 요약

서버끼리 메시지를 주고받을 때 쓰는 메시지 브로커는 두 질문으로 나뉜다. 메시지 하나가 누구에게 가는가(소비자 하나인가, 구독자 전원인가), 그리고 읽은 뒤에도 남는가다.

모델메시지 하나는읽은 뒤대표
작업 큐소비자 중 하나가 가져간다확인하면 지워진다RabbitMQ 큐, Amazon SQS, Azure Service Bus 큐
Pub/Sub구독자 전원이 받는다제품마다 다르다. 저장하지 않는 것도 있다Redis Pub/Sub, NATS(Core), Amazon SNS
이벤트 로그읽는 쪽이 자기 위치부터 읽는다보존 기간 동안 남는다. 다시 읽을 수 있다Kafka, Redis Streams, RabbitMQ Streams

운영체제의 프로세스 간 통신에 나오는 "메시지 큐"는 커널이 같은 기계 안에서 중개하는 것이고, 프로세스 안의 큐는 이벤트 버스가 다룬다. 이 문서는 기계를 넘나드는 브로커를 다룬다.

동작 원리

작업 큐는 일감을 나눠 준다

소비자가 여럿 붙어도 메시지 하나는 그중 하나에게만 간다. 이것을 경쟁 소비자 구조라고 한다. 소비자를 늘리면 처리량이 늘고, 하나가 죽으면 확인하지 않은 메시지가 다른 소비자에게 다시 간다. 처리가 끝나 확인(ACK)한 메시지는 큐에서 지워진다.

우편 발송, 보상 지급, 이미지 처리처럼 "누가 하든 한 번 하면 되는 일"에 맞는다. 브로커가 소비자마다 미리 몇 개까지 넘겨줄지(RabbitMQ의 prefetch)를 정하지 않으면, 느린 소비자 하나가 메시지를 잔뜩 쥔 채 늘어진다.

Pub/Sub은 같은 소식을 모두에게 보낸다

발행자는 주제(토픽, 채널)에 보내고, 구독한 쪽 전원이 사본을 받는다. 발행자는 구독자가 몇인지 모른다. 이름이 같아도 저장 여부는 제품마다 갈린다.

  • 저장하지 않는 쪽: Redis Pub/Sub, NATS Core. 그 순간 붙어 있던 구독자에게만 간다. 끊겨 있던 구독자는 영영 못 받는다(Redis 활용).
  • 구독마다 큐를 만드는 쪽: Azure Service Bus 토픽, SNS에서 SQS로 퍼뜨리는 구성, RabbitMQ의 fanout 교환기와 큐. 구독 하나가 자기 큐를 갖고, 그 안에서는 작업 큐처럼 동작한다.

이벤트 로그는 지우지 않고 위치만 기억한다

Kafka는 토픽을 파티션으로 나누고, 파티션마다 메시지를 끝에 붙이기만 한다. 메시지마다 파티션 안에서의 번호인 오프셋이 있다. 소비자는 어디까지 읽었는지 오프셋을 커밋해 둔다. 메시지는 읽혔다고 지워지지 않고, 보존 기간이나 크기 한도에 따라 지워진다.

남아 있으니 다시 읽을 수 있다. 새 소비자를 붙여 처음부터 따라가게 하거나, 집계 버그를 고친 뒤 지난주 오프셋으로 되감아 다시 계산할 수 있다. 큐와 Pub/Sub은 이 요구를 채우지 못한다. DB의 WAL도 로그지만 목적이 다르다. WAL은 커밋을 잃지 않으려고 남기고, 이벤트 로그는 다시 읽어 전달하려고 남긴다.

컨슈머 그룹 하나로 큐와 Pub/Sub을 함께 흉내 낸다

Kafka의 컨슈머 그룹은 같은 이름을 쓰는 소비자 묶음이다. 한 그룹 안에서는 파티션 하나를 소비자 하나가 맡아 일을 나누고(큐처럼), 서로 다른 그룹은 같은 메시지를 각자 다 읽는다(Pub/Sub처럼). 정산 서비스와 통계 서비스가 서로 다른 그룹으로 같은 거래 토픽을 읽는 식이다.

한 그룹 안의 병렬도는 파티션 수를 넘지 못한다. 파티션이 6개인데 소비자를 10개 띄우면 4개는 논다. 소비자가 얼마나 뒤처졌는지는 컨슈머 랙으로 잰다. 파티션 수는 나중에 늘릴 수 있지만, 늘리면 키가 가는 파티션이 바뀌어 아래의 순서 보장이 흔들린다. 처음부터 넉넉히 잡는다.

순서는 생각보다 좁게 지켜진다

제품순서가 지켜지는 범위
Kafka파티션 안에서만. 같은 키는 같은 파티션으로 가므로 키별 순서가 지켜진다. 토픽 전체 순서는 없다
RabbitMQ 큐큐에 들어간 순서로 내보내지만, 소비자가 여럿이거나 재전달이 생기면 처리 순서는 바뀐다
Amazon SQS표준 큐는 순서를 보장하지 않는다. FIFO 큐는 메시지 그룹 ID 안에서만 지킨다
Redis Streams스트림 하나 안에서 ID 순서. 소비자 그룹에서 여럿이 나눠 가져가면 처리 순서는 소비자마다 다르다

순서가 필요한 단위를 키로 삼는다. 같은 캐릭터의 재화 변경은 캐릭터 ID를 키로 보내면 한 파티션에 모여 순서대로 처리된다. 순서를 넓게 요구할수록 동시에 처리할 수 있는 폭이 좁아진다.

선택 기준

하려는 일모델이유
접속 중인 서버 모두에게 "이 캐릭터 캐시를 지워라", "공지 띄워라"저장하지 않는 Pub/Sub그때 없던 서버는 어차피 새로 읽는다. 저장과 재생은 운영 부담만 늘린다
우편 지급, 보상 정산, 외부 API 호출처럼 한 번 처리하면 되는 일작업 큐소비자를 늘려 나눠 처리하고, 실패하면 다시 받는다
거래 기록을 정산, 통계, 이상 탐지가 각자 읽는다이벤트 로그읽는 쪽이 늘어도 보내는 쪽은 그대로다. 각자 속도로 따라간다
규칙이 바뀌어 지난 이벤트를 다시 계산해야 한다이벤트 로그읽고 나서도 남아 있는 것은 이 모델뿐이다

제품을 고를 때는 모델 말고도 운영을 본다. Kafka는 처리량과 재생이 강한 대신 클러스터 운영이 무겁다. RabbitMQ는 라우팅 규칙이 풍부하고 작업 큐에 익숙한 구조다. 이미 Redis를 쓰고 있다면 Streams로 시작할 수 있지만 메시지가 메모리에 쌓인다. 클라우드 큐는 운영을 맡기는 대신 제품마다 크기, 보존 기간, 순서 제약이 다르다. 숫자 한도는 버전마다 바뀌므로 쓰는 제품의 문서에서 확인한다.

게임 서버에서는

  • 귓속말과 길드 채팅은 받는 사람이 어느 서버에 있는지가 문제다. 접속 위치를 기록해 둔 디렉터리(Redis 등)를 보고 그 서버에만 보내거나, 채팅 서버 전원에게 Pub/Sub으로 뿌리고 각자 자기 접속자만 고른다. 서버가 적으면 뿌리기가 단순하고, 많아지면 라우팅이 싸다. 놓쳐도 되는 메시지인지가 저장 여부를 정한다.
  • 게임 로그와 행동 이벤트는 이벤트 로그로 모은다. 게임 서버는 토픽에 쓰기만 하고, 분석 적재, 어뷰징 탐지, 운영 툴이 각자 컨슈머 그룹으로 읽는다. 분석 쪽이 멈춰도 게임 서버는 영향을 받지 않는다.
  • 느린 일은 작업 큐로 뺀다. 시즌 보상 정산, 대량 우편, 결제 검증처럼 틱 안에서 기다리면 안 되는 일을 큐에 넣고 결과를 메시지로 돌려받는다(큐와 백프레셔). 큐가 밀리는 것을 지표로 본다.
  • DB를 고치고 메시지를 보내는 일은 한 번에 묶이지 않는다. 재화를 바꾼 뒤 "보상 지급됨"을 보내다가 죽으면 둘 중 하나만 남는다. 이 문제는 트랜잭셔널 아웃박스가 다룬다.

주의 사항

  • "Pub/Sub이니까 안전하게 전달된다"고 보면 안 된다. 저장하지 않는 Pub/Sub은 받는 쪽이 끊긴 순간의 메시지를 버린다. 놓치면 안 되는 일은 큐나 로그로 보낸다.
  • 브로커가 있어도 중복은 온다. 대부분의 브로커는 최소 한 번 전달이다. 받는 쪽은 같은 메시지를 두 번 받아도 결과가 같게 짠다(전달 보장과 exactly-once, 멱등 소비자).
  • 메시지 형식도 버전이다. 보내는 쪽과 받는 쪽이 따로 배포되므로, 필드를 지우거나 뜻을 바꾸면 옛 소비자가 깨진다. 필드는 더하기만 하고 모르는 필드는 무시하게 만든다(프로토콜 호환성).
