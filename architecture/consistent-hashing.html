먼저 읽을 것: 해시 테이블, 확장과 샤딩

핵심 요약

키를 서버 여러 대에 나누는 가장 쉬운 방법은 hash(key) % N이다. 서버 수 N이 그대로면 잘 돈다. 하지만 N이 하나만 바뀌어도 거의 모든 키의 자리가 바뀐다. 캐시라면 한꺼번에 비고, 상태 있는 서버라면 거의 모든 데이터가 이사한다.

일관된 해싱은 서버와 키를 같은 원 위에 올려 두고, 키를 시계 방향으로 처음 만나는 서버에 맡긴다. 서버가 하나 늘면 그 서버 바로 앞 구간의 키만 옮겨진다. 평균적으로 옮겨지는 비율이 거의 전부에서 약 1/N으로 준다.

동작 원리

나머지 연산은 서버 수가 바뀌면 거의 다 옮긴다

문제는 새 서버가 받는 몫이 아니다. 새 서버와 상관없는 기존 서버끼리도 키를 주고받는다는 점이다. 캐시 서버라면 늘리는 순간 적중률이 바닥으로 떨어지고, 비어 있는 캐시를 채우려는 요청이 DB로 몰린다(DB 앞의 캐시).

해시 링: 시계 방향으로 처음 만나는 서버가 맡는다

해시 공간을 0부터 264−1까지로 보고 끝을 처음과 이어 원으로 만든다. 서버도 이름(또는 주소)을 해시해 원 위에 놓는다. 키를 찾을 때는 키의 해시 위치에서 시계 방향으로 가장 가까운 서버를 고른다. 위치를 정렬된 배열에 담아 두면 이진 탐색 한 번으로 찾는다.

서버 몇 대만 올리면 구간이 고르지 않다: 가상 노드

서버를 원 위에 한 점씩만 두면 점 사이 간격이 제멋대로다. 세 대라면 한 대가 원의 절반을 맡는 일도 흔하다. 그래서 서버 하나를 원 위의 여러 점으로 나눠 놓는다. 이것을 가상 노드라고 한다. "cache-1#0", "cache-1#1"처럼 이름에 번호를 붙여 해시하면 된다.

  • 쏠림이 준다. 서버마다 점이 수십~수백 개면 구간 길이가 평균에 모여, 서버별 부하 차이가 작아진다.
  • 가중치를 줄 수 있다. 메모리가 두 배인 서버에는 점을 두 배로 준다.
  • 빠질 때 부담이 흩어진다. 서버 하나가 죽으면 그 서버의 구간들이 여러 이웃 서버로 나뉘어 간다. 점이 하나뿐이면 다음 서버 한 대가 몫을 통째로 떠안는다.

값은 위치 배열이 커지는 만큼 든다. 서버 100대 × 점 200개면 위치가 2만 개다. 이진 탐색으로 찾으니 조회는 여전히 빠르고, 메모리도 크지 않다. Cassandra는 노드당 토큰 수를 num_tokens로 정하며, 4.0부터 기본값을 256에서 16으로 낮췄다. 토큰을 무작정 늘리면 복구와 관리 비용이 커지기 때문이다.

복제본은 링의 다음 서버들에 둔다

Dynamo 계열 저장소는 키를 맡은 서버에서 시계 방향으로 이어지는 서버 몇 대에 복제본을 둔다. 가상 노드를 쓰면 이어지는 점이 같은 물리 서버일 수 있으므로, 서로 다른 물리 서버가 나올 때까지 건너뛰며 고른다. 랙이나 가용 영역이 겹치지 않게 고르는 규칙을 더하기도 한다. 복제 일관성 조절은 RDBMS와 NoSQL의 R+W>N에서 다룬다.

링이 아닌 방법: 랑데부 해싱과 점프 해시

랑데부 해싱(HRW, Highest Random Weight)은 키 하나마다 모든 서버와 짝지어 hash(key, server) 점수를 매기고, 점수가 가장 높은 서버를 고른다. 서버가 빠지면 그 서버가 1등이던 키만 2등 서버로 간다. 링도 가상 노드도 필요 없고 분포도 고르다. 대신 조회마다 서버 수만큼 해시를 계산하므로 O(N)이다. 서버가 수십 대 이하라면 충분히 싸다. 상위 k개를 고르면 복제본 자리도 바로 나온다.

점프 일관 해시(jump consistent hash)는 키와 버킷 수만 받아 0부터 N−1 사이의 번호를 돌려주는 짧은 함수다. 메모리를 쓰지 않고 O(log N)에 끝나며 분포가 아주 고르다. 다만 버킷은 번호로만 존재한다. 끝에 하나를 더하거나 끝의 것을 빼는 일만 된다. 중간의 3번 서버만 빼는 일은 못 한다. 그래서 "서버"가 아니라 "샤드 번호"를 고르는 데 쓰고, 샤드 번호를 실제 서버에 잇는 표를 따로 둔다.

고정 슬롯 방식은 다른 답이다

키 공간을 처음부터 많은 슬롯으로 잘라 두고, 슬롯을 서버에 배정하는 표를 두는 방법도 있다. Redis Cluster가 이렇다. 키는 CRC16을 16384로 나눈 나머지로 슬롯이 정해지고, 슬롯이 어느 노드에 있는지는 클러스터가 관리하는 배정표가 정한다(Redis 활용). 엄밀히는 일관된 해싱이 아니다.

슬롯 수가 고정이라 키 → 슬롯은 영원히 같다. 서버를 늘릴 때는 "어느 슬롯을 옮길지"를 사람이나 도구가 정하고, 그 슬롯만 옮긴다. 옮기는 양과 시점을 직접 고를 수 있다는 것이 장점이다. 대신 배정표를 모두가 같은 판으로 봐야 하고, 옮기는 중인 슬롯의 요청을 어떻게 넘길지도 정해야 한다. DB 확장에서 말한 "논리 샤드를 넉넉히 두기"도 같은 생각이다.

해시 함수는 프로세스 밖에서도 같아야 한다

.NET의 string.GetHashCode()는 프로세스마다 무작위 시드로 계산한다. 해시 플러딩 공격을 막으려는 설계라서, 같은 문자열도 서버 A와 서버 B, 어제와 오늘 값이 다르다. 이 값으로 링 위치를 정하면 서버마다 다른 서버를 가리킨다. HashCode.Combine도 같다.

여러 서버가 같은 답을 내야 하는 곳에는 정의가 고정된 해시를 쓴다. 분산이 고르고 빠른 비암호 해시(xxHash, MurmurHash3, FNV-1a 등)면 충분하다. .NET에서는 System.IO.Hashing 패키지의 XxHash64, XxHash3를 쓸 수 있다. 문자열은 항상 같은 인코딩(UTF-8)으로 바꾼 뒤 해시한다. 

using System.IO.Hashing;
using System.Text;

// 가상 노드를 둔 해시 링. 서버 목록이 바뀌면 새로 만들어 참조를 바꿔 끼운다.
public sealed class HashRing
{
    private readonly ulong[] _points;   // 링 위의 위치, 오름차순
    private readonly string[] _owners;  // 같은 칸의 서버 이름

    public HashRing(IEnumerable<string> servers, int pointsPerServer = 160)
    {
        var list = new List<(ulong Point, string Server)>();
        foreach (var s in servers)
            for (int i = 0; i < pointsPerServer; i++)
                list.Add((Hash($"{s}#{i}"), s));
        list.Sort((a, b) => a.Point.CompareTo(b.Point));
        _points = list.Select(x => x.Point).ToArray();
        _owners = list.Select(x => x.Server).ToArray();
    }

    public string ServerFor(string key)
    {
        int i = Array.BinarySearch(_points, Hash(key));
        if (i < 0) i = ~i;               // 같은 위치가 없으면 다음 위치
        if (i == _points.Length) i = 0;  // 끝을 넘으면 처음으로 돈다
        return _owners[i];
    }

    // string.GetHashCode()는 프로세스마다 달라 쓰면 안 된다.
    private static ulong Hash(string s) =>
        XxHash64.HashToUInt64(Encoding.UTF8.GetBytes(s));
}

링은 만든 뒤 고치지 않는다. 서버 목록이 바뀌면 새 링을 만들어 참조 하나를 바꿔 끼운다. 읽는 쪽은 락 없이 그때 잡은 링을 끝까지 쓴다. 기획 데이터 핫 리로드와 같은 방식이다.

키가 옮겨지면 데이터도 옮겨야 한다

일관된 해싱이 줄여 주는 것은 옮겨지는 키의 비율이다. 옮겨지는 키가 들고 있던 데이터는 여전히 누군가 옮겨야 한다.

  • 캐시: 옮겨진 키는 새 서버에서 처음엔 비어 있다. 1/N이라도 큰 클러스터에서는 순간 DB 부하가 눈에 띈다. 서버는 한 번에 한 대씩 늘리고, 몰리는 시간을 피한다.
  • 저장소: 새 서버가 이웃에게서 자기 구간 데이터를 받아 오는 동안, 그 구간의 읽기와 쓰기를 어디로 보낼지 정해야 한다. 옛 주인과 새 주인 둘 다에 쓰다가 넘기는 식이다.
  • 상태 있는 서버: 메모리에 객체를 들고 있는 서버라면 키를 옮기는 일은 곧 객체 인계다. 옛 서버가 내려놓고 새 서버가 들기 전까지 둘 다 쓰지 않게 막아야 한다(월드 분할의 존 이동 인계).
  • 모두가 같은 링을 봐야 한다. 서버 목록이 바뀌는 순간 어떤 클라이언트는 새 링, 어떤 클라이언트는 옛 링을 본다. 그 틈의 요청은 엉뚱한 서버로 간다. 받는 쪽이 "내 키가 아니다"라고 돌려보내는 장치(Redis Cluster의 MOVED 같은)를 두면 틈이 메워진다.

번호로 늘기만 하는 샤드점프 해시메모리 없이 가장 고르다. 중간 샤드 제거는 안 된다
옮길 양과 시점을 직접 통제해야 한다고정 슬롯 + 배정표키 → 슬롯이 영원히 같고, 슬롯 단위로 골라 옮긴다

게임 서버에서는

  • 캐릭터 ID로 서비스 서버를 고른다. 채팅, 친구, 우편처럼 캐릭터별로 상태가 닫힌 서비스는 캐릭터 ID를 해시해 담당 서버를 고르면, 위치 표 없이 어느 서버에서나 같은 답이 나온다. 서버 증설 때 일부 캐릭터만 이사한다.
  • 원본이 필요한 곳은 위치 표가 낫다. 캐릭터가 지금 어느 존에 있는지는 해시로 정해지는 값이 아니다. 플레이어가 움직이는 대로 바뀌므로 토폴로지에서 다룬 위치 표에 둔다. 해시는 "정해진 담당"에, 위치 표는 "지금 있는 곳"에 쓴다.
  • 핫 키는 해싱으로 풀리지 않는다. 길드 하나, 월드 보스 하나에 요청이 몰리면 그 키는 어느 방식으로 나눠도 한 서버에 간다. 키를 쪼개거나(카운터 분할), 읽기 복제본을 두거나, 로컬 캐시로 흡수한다(동시성 제어의 핫 로우).
  • 서버 이름을 해시 입력으로 쓸 때 조심한다. IP를 넣으면 서버를 재배치할 때 IP가 바뀌어 링 위치가 다 바뀐다. 바뀌지 않는 논리 이름(chat-03)을 쓴다.
  • 링을 바꾸는 순간을 로그로 남긴다. "어제 저녁부터 일부 유저 친구 목록이 비어 보인다" 같은 문의는 링이 바뀐 시각과 맞춰 봐야 풀린다.

주의 사항

  • 1/N은 평균이다. 가상 노드 없이 몇 대만 두면 새 서버가 원의 절반을 가져가기도 한다. 늘린 뒤 서버별 키 수와 부하를 실제로 확인한다.
  • 모든 클라이언트가 같은 해시, 같은 서버 목록, 같은 가상 노드 수를 써야 한다. 하나라도 다르면 같은 키가 서로 다른 서버로 간다. 클라이언트 라이브러리를 섞어 쓸 때 특히 잘 깨진다.
  • 서버가 잠깐 끊겼다고 바로 링에서 빼지 않는다. 빼고 다시 넣을 때마다 키가 두 번 이사한다. 빼는 기준을 짧은 끊김보다 길게 잡는다.
  • 해시는 부하가 아니라 키 개수를 나눈다. 키마다 요청량이 크게 다르면 키 수가 고르게 나뉘어도 부하는 고르지 않다.
