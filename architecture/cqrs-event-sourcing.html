먼저 읽을 것: 메시지 모델 세 갈래, 트랜잭셔널 아웃박스

핵심 요약

CQRS(Command Query Responsibility Segregation)는 상태를 바꾸는 쪽과 읽는 쪽의 모델을 따로 둔다. 쓰기 모델은 규칙을 검사하고 바꾸는 데 맞추고, 읽기 모델은 화면과 조회에 맞춘 모양으로 따로 만든다.

이벤트 소싱은 현재 상태 대신 상태를 바꾼 일, 곧 이벤트를 순서대로 저장한다. 상태가 필요하면 이벤트를 처음부터 다시 적용해 만든다. 무엇이 언제 왜 바뀌었는지가 저장의 본체가 된다.

둘은 자주 함께 불리지만 서로를 요구하지 않는다. 이벤트 소싱을 쓰면 조회가 어려워져 CQRS의 읽기 모델이 따라오는 일이 많을 뿐이다. 둘 다 읽기와 쓰기가 같은 모양이어도 충분한 시스템에 들이면 복잡도만 크게 는다.

동작 원리

CQRS는 모델을 나눈다

나누는 대상은 저장소가 아니라 모델이다. 같은 DB 안에서 쓰기는 정규화된 테이블에, 읽기는 조회용 뷰나 요약 테이블에 두는 것도 CQRS다. 읽기 모델을 다른 저장소(Redis, 검색 엔진)에 두면 조회 부하를 떼어 낼 수 있다. 대신 쓰기에서 읽기로 변경을 옮기는 경로가 생기고, 그 경로만큼 늦다.

"방금 보상을 받았는데 지갑에는 아직 안 보인다"는 일이 생긴다. 복제 지연과 같은 종류의 문제이고 대책도 비슷하다. 자기가 방금 바꾼 값은 쓰기 쪽에서 읽거나, 명령의 응답에 바뀐 값을 함께 돌려준다.

이벤트 소싱은 상태 대신 일어난 일을 저장한다

일반적인 저장은 "골드 = 1,350"을 덮어쓴다. 이벤트 소싱은 "+1,000 퀘스트 보상", "−300 상점 구매" 같은 이벤트를 차례로 쌓고 덮어쓰지 않는다. 현재 상태는 이벤트를 처음부터 적용한 결과다. 같은 이벤트를 어느 지점까지만 적용하면 그때의 상태도 다시 만들 수 있다.

얻는 것은 세 가지다. 모든 변경에 이유와 시각이 남는다. 과거 시점의 상태를 다시 만들 수 있다. 새로운 읽기 모델이 필요해지면 이벤트를 처음부터 다시 흘려 만든다. 반대로 "골드가 1,000 넘는 캐릭터" 같은 조회는 이벤트만으로는 할 수 없어 읽기 모델이 따로 필요하다. 이벤트 소싱 옆에 CQRS가 붙는 이유가 여기 있다.

이벤트는 이미 일어난 사실이다

이벤트와 커맨드는 모양이 비슷해도 뜻이 다르다. 커맨드는 "골드를 지급하라"는 요청이라 검사에서 거절될 수 있다. 이벤트는 "골드가 지급됐다"는 과거의 사실이라 거절되지 않는다. 이벤트 소싱이 저장하는 것은 검사를 통과한 뒤의 이벤트다. 그래서 재생할 때는 규칙을 다시 검사하지 않고 적용만 한다. 규칙이 바뀌어도 과거 사실은 그대로 재현된다.

같은 이유로 아웃박스의 메시지와도 다르다. 아웃박스 메시지는 밖에 알리려고 만든 사본이라 보낸 뒤 지워도 된다. 이벤트 소싱의 이벤트는 상태의 원본이라 지우면 상태를 다시 만들 수 없다.

재생하면 바깥으로 나간 일도 다시 나간다

이벤트를 적용하는 코드가 "골드 지급됨 → 플레이어에게 푸시 알림"까지 한다면, 읽기 모델을 다시 만들려고 이벤트를 처음부터 흘리는 순간 알림 수만 건이 다시 나간다. 외부 결제 서버 호출이 섞여 있으면 더 나쁘다.

그래서 상태를 바꾸는 적용 코드와 바깥으로 나가는 부수 효과를 떼어 둔다. 부수 효과는 별도의 구독자가 맡고, 구독자는 처리한 위치를 기억해 재생 중에는 이미 처리한 이벤트를 건너뛴다. 멱등 소비자와 같은 장치다.

이벤트 형식은 바꾸기 어렵다

쌓인 이벤트는 고치지 않는다. 그래서 필드를 바꾸면 옛 형식과 새 형식이 함께 남는다. 이벤트마다 형식 버전을 두고, 읽을 때 옛 형식을 새 형식으로 바꿔 주는 변환기(업캐스터)를 둔다. 필드를 지우거나 뜻을 바꾸기보다 새 필드를 더하는 쪽이 안전하다. 메시지 형식 호환 원칙과 같다(프로토콜 호환).

감사 로그와 이벤트 소싱도 구분한다. 감사 로그는 상태를 저장하면서 곁에 남기는 기록이다. 로그가 틀려도 상태는 맞다. 이벤트 소싱에서는 이벤트가 원본이라, 이벤트가 틀리면 상태가 틀린다.

게임 서버에서는

  • 재화 원장이 가장 흔한 형태다. 게임 서버가 도메인 전체를 이벤트 소싱으로 만드는 일은 드물다. 대신 재화와 아이템에 대해 추가만 하는 원장 테이블을 두는 일은 흔하다. 원장에는 (character_id, seq, delta, reason, ref_id)를 쌓고, 잔액 컬럼은 같은 트랜잭션에서 함께 갱신한다. 원장이 원본이고 잔액은 빨리 읽으려고 둔 투영이다.
  • 원장이 있어야 맞춰 볼 수 있다. 두 보상 수령 요청이 거의 동시에 들어와 둘 다 옛 잔액을 읽고 지급하면 재화가 부푼다. 잔액만 덮어쓰는 구조에서는 무슨 일이 있었는지 남지 않는다. 원장이 있으면 잔액과 delta 합계를 매일 대조해 어긋남을 찾고, 어느 요청이 겹쳤는지 짚어 낸다. 원인은 동시성 제어로 막고, 원장은 막지 못한 것을 찾는다.
  • 특정 유저 복구에도 쓴다. 원장이 있으면 "어제 15시 이후 이 캐릭터의 변경"만 골라 상쇄 기록을 넣을 수 있다. DB 전체를 되돌리지 않는다(백업과 복구).
  • 랭킹과 통계는 읽기 모델로 뗀다. 게임 DB에서 매번 점수 순으로 정렬하지 않는다. 점수 변경 이벤트를 받아 Redis 정렬 집합이나 집계 테이블을 갱신한다(Redis 활용). 랭킹이 몇 초 늦는 것은 대개 받아들일 수 있다.
  • 리플레이는 입력을, 이벤트 소싱은 결과를 쌓는다. 결정론적 리플레이는 입력 커맨드만 저장하고 같은 시뮬레이션을 다시 돌린다(커맨드 패턴과 리플레이). 이벤트 소싱은 검사를 마친 결과를 저장하므로 시뮬레이션 코드가 바뀌어도 같은 상태가 나온다. 무엇을 다시 만들고 싶은지에 따라 고른다.

주의 사항

  • 잘 맞지 않는 곳에 쓰면 복잡도만 는다. CQRS는 모델이 둘이 되고 그 사이 동기화 경로가 생긴다. 이벤트 소싱은 스냅샷, 형식 버전, 재생 도구를 모두 직접 챙겨야 한다. 단순한 CRUD 화면에 들이면 얻는 것 없이 버그 자리만 는다. 시스템 전체가 아니라 필요한 영역에만 쓴다.
  • 읽기 모델은 늦다. 읽기 모델로 규칙을 검사하면 안 된다. "잔액 뷰에 1,000이 있으니 구매 허용"은 투영이 늦은 사이에 깨진다. 검사는 언제나 쓰기 쪽 원본으로 한다.
  • 이벤트를 지우거나 고치는 순간 원본이 사라진다. 잘못 들어간 이벤트도 고치지 않고 상쇄 이벤트를 더한다. 개인정보 삭제 요구처럼 지워야 하는 값은 이벤트 밖에 따로 두고 참조만 남기는 식으로 미리 설계한다.
  • "이벤트"라는 말이 셋이다. 이벤트 소싱의 이벤트(상태의 원본), 아웃박스로 보내는 알림, 이벤트 로그(Kafka 토픽)는 서로 다른 것이다. 무엇을 지워도 되는지가 다르므로 섞어 부르지 않는다.
