먼저 읽을 것: 참조 지역성

핵심 요약

CPU와 메모리의 속도 차를 메우려고 작고 빠른 저장소를 여러 단계로 쌓은 것이 메모리 계층이다. 아래로 갈수록 용량이 커지고, 그 대가로 지연은 자릿수가 하나씩 늘어난다.

캐시는 바이트가 아니라 캐시 라인 단위로 움직인다. Intel·AMD의 x86-64에서 그 라인은 64바이트이고, 이 문서는 그 값을 예로 든다. 4바이트를 읽어도 64바이트 전체를 가져온다.

동작 원리

한 단계 내려가면 지연의 자릿수가 하나 늘어난다

L1과 메인 메모리 사이가 두 자릿수고, 메인 메모리와 SSD 사이는 또 두 자릿수다. 정확한 값보다 이 간격이 판단할 때 쓰는 기준이다.

단계마다 누가 쓰는지도 다르다. L1과 L2는 코어마다 따로 있고, L3는 여러 코어가 함께 쓴다. L1은 다시 명령어용(L1i)과 데이터용(L1d)으로 나뉜다. 그래서 "캐시 미스가 많다"고만 하면 어느 단계의 어느 캐시인지가 드러나지 않는다.

맨 위의 레지스터는 아래 단계와 성격이 다르다. 캐시는 하드웨어가 알아서 채우므로 프로그램은 주소만 지정하면 된다. 레지스터는 주소가 없고 개수가 정해져 있어, 무엇을 올릴지 컴파일러가 정한다. x86의 범용 레지스터는 32비트에서 8개, 64비트에서 16개다(32비트와 64비트).

개수가 모자라면 컴파일러가 값을 스택으로 내보낸다(spill). 그 스택도 결국 L1에 들어와 있으므로, 레지스터가 부족하다고 곧장 메인 메모리까지 떨어지지는 않는다.

캐시는 주소를 셋으로 나눠 읽는다

주소는 태그 + 인덱스 + 오프셋으로 나뉜다. 인덱스로 먼저 집합(set)을 찾는다. 그 집합 안에서 태그로 일치 여부를 확인하고, 맞으면 오프셋으로 라인 안의 바이트를 고른다.

한 집합에 라인이 몇 개 들어가는지가 연관도(associativity)다. direct-mapped(1-way)는 싸지만 충돌이 잦아서, 실제 구현은 4~16-way set associative를 쓴다.

쓰기는 캐시에만 하고 나중에 내려보낸다

여기까지는 읽기 이야기다. 쓰기는 정책이 둘로 나뉜다.

정책쓸 때 하는 일대가
write-through캐시와 다음 단계에 함께 쓴다쓸 때마다 느린 쪽을 기다린다
write-back캐시에만 쓰고, 그 라인이 밀려날 때 내려보낸다어느 라인이 고쳐졌는지 dirty bit로 따로 기억해야 한다

현행 CPU는 write-back을 쓴다. 같은 라인에 여러 번 써도 아래 단계로 내려가는 것은 밀려날 때 한 번이다. 그래서 메모리에 접근하는 횟수가 쓰기 횟수보다 훨씬 적어진다.

쓰기에서 미스가 났을 때도 라인 단위가 그대로 적용된다. write-allocate는 그 라인을 먼저 가져온 다음 고치는 방식이고, write-back과 짝으로 쓴다. 64바이트 중 4바이트만 고칠 때에도 64바이트를 전부 가져온다는 뜻이다.

미스는 원인마다 대응이 다르다

종류원인대응

미스 횟수만 세면 셋이 구분되지 않는데, 표에서 보듯 대응은 서로 다르다.

고전적으로는 이 셋으로 나눈다. 멀티코어에서는 한 가지가 더해진다. 다른 코어가 같은 라인에 쓰면 이쪽 라인이 무효화되어 생기는 미스(coherence miss)다. 앞의 셋과 달리 자기 접근 패턴만 고쳐서는 줄어들지 않는다. 캐시 일관성과 false sharing에서 다룬다.

선택 기준

복잡도가 같은데 실측이 다르면 먼저 배치를 본다

연결 리스트와 배열은 순회가 둘 다 O(n)이다. 복잡도만으로는 격차가 설명되지 않는다. 접근 횟수로도 마찬가지다. 원소 수가 같으니 접근 횟수도 같다.

달라지는 것은 한 번의 접근이 다음 접근을 얼마나 미리 해결해 주느냐다. 배열은 라인 하나를 가져오면 인접 원소가 함께 실려 온다. 연결 리스트는 노드가 흩어져 있어 라인의 대부분을 버리고, 다음 노드에서 또 미스가 난다.

연속 배치는 순회가 빨라지는 대신 중간 삽입이 느려진다

인접한 데이터를 곧 쓸 것이라면 이미 캐시에 와 있다. 흩어져 있으면 같은 64바이트를 실어 오고도 4바이트만 쓰고 버린다. 대신 연속 배치는 중간 삽입·삭제에서 원소 이동 비용이 그대로 발생한다.

순회가 주된 작업이면 연속 배치를 고르고, 중간 삽입·삭제가 잦으면 고르지 않는다.

게임 서버에서는

  • 틱 예산은 사이클로 따진다. 30Hz 서버의 한 틱은 약 33ms다. 메인 메모리 미스 한 번이 수백 사이클이니, 엔티티 수만 개를 흩어진 객체로 순회하면 미스만으로 틱 예산의 상당 부분을 쓸 수 있다.
  • "캐시"라는 말을 구분한다. 서버 개발자가 매일 쓰는 Redis 캐시나 DB 버퍼 풀도 같은 계층 원리(작고 빠른 층이 크고 느린 층 앞에 선다)를 따른다. 하지만 지연 단위가 전혀 다르다. CPU 캐시는 나노초 단위이고, Redis는 네트워크 왕복을 포함해 수십~수백 마이크로초 단위다. 대화에서 어느 층 이야기인지 먼저 맞춘다.
  • 라인 크기를 숫자로 박지 않는다. false sharing을 피하려고 패딩을 넣을 때 64를 상수로 박으면 다른 CPU에서 틀릴 수 있다. 아래 주의 사항의 방법으로 확인한다.

주의 사항

  • 2의 거듭제곱 크기 2차원 배열을 열 방향으로 순회하면 캐시가 제 역할을 못 한다. 모든 접근이 같은 집합에 떨어져 서로를 밀어낸다. 배열 한 줄에 패딩을 몇 바이트 넣어 stride를 틀어 주면 접근이 여러 집합으로 흩어진다. conflict miss의 전형이고, 복잡도만으로는 드러나지 않는다.
  • 32비트냐 64비트냐는 라인 크기와 관계가 없다. 32/64비트는 주소와 범용 레지스터의 폭이고, 라인 크기는 캐시가 한 번에 옮기는 양이다. 같은 CPU에서 32비트 코드를 실행해도 라인은 그대로 64바이트다. 다만 64비트에서는 포인터가 8바이트가 되어 한 라인에 들어가는 원소 수가 줄어든다. 라인이 작아진 것이 아니라 원소가 커진 것이다.
  • 64바이트는 x86-64의 값이지 모든 CPU의 값이 아니다. 정하는 것은 운영체제가 아니라 CPU다. 같은 Windows나 Linux라도 어느 칩에서 실행되는지에 따라 달라진다.
CPU 계열주로 쓰이는 곳캐시 라인
Intel·AMD x86-64데스크톱·서버의 Windows·Linux모든 단계가 64바이트
ARM Cortex-A 계열Android 기기 대부분64바이트 (ARM 코어 문서에 적힌 값)
Apple 자체 코어macOS·iOSL1 데이터는 64바이트. 아래 단계는 더 크다고 알려져 있으나 공식 수치가 없다
  • x86-64 안에서도 늘 64바이트였던 것은 아니다. Pentium 4의 L2는 128바이트 라인을 썼고, 그 라인은 다시 64바이트 두 조각(섹터)으로 나뉘어 있었다.
  • 그래서 라인 크기를 코드에 숫자로 고정하지 않는다. 실행 중에 확인할 수 있다. Linux·Android는 /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size를 읽고, Windows는 GetLogicalProcessorInformation이 돌려주는 LineSize를 본다.
  • "캐시"는 CPU 캐시만 가리키는 말이 아니다. 웹 캐시와 DB 캐시가 따로 있고, 같은 낱말이 서로 다른 층을 가리킨다. 어느 층 이야기인지 먼저 구분한다.
