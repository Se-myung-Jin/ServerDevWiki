핵심 요약

파이프라인은 명령 처리를 여러 단계로 나눠, 앞 명령이 끝나기 전에 다음 명령을 겹쳐 넣는 구조다. 다음 명령을 미리 넣으려면 분기 결과를 알아야 하는데 아직 모르므로, CPU는 분기 예측으로 갈 쪽을 짐작해 계속 채운다.

예측이 틀리면 채워 둔 명령을 전부 버리고 맞는 쪽에서 다시 채운다. 이 낭비가 분기 예측 실패 비용이고, 현행 x86 코어에서는 대략 15~20사이클 수준이다. 정확한 값은 마이크로아키텍처마다 다르다.

동작 원리

예측이 틀리면 채워 둔 것을 전부 버린다

파이프라인이 깊을수록 예측 실패의 비용이 커진다. 분기가 판정될 때까지 미리 넣어 둔 단계가 많아서다.

예측기는 분기의 기록과 패턴을 본다

예측은 짐작이 아니라 기록에 근거한다. CPU 안에 분기마다 지난 결과를 적어 두는 표가 있고, 현대 예측기는 여기에 직전 분기들이 어떻게 갔는지의 패턴까지 함께 본다. 그래서 한쪽으로 기운 분기는 물론이고, "참·거짓이 번갈아 나온다"나 "8번에 한 번 거짓"처럼 규칙이 있는 분기도 잘 맞힌다. 맞히지 못하는 것은 패턴이 없는(무작위인) 분기다.

그래서 같은 코드가 입력에 따라 다르게 동작한다. 코드를 고치지 않아도 데이터가 바뀌면 예측률이 바뀐다.

조건 분기만 예측하는 것이 아니다. 가상 메서드·인터페이스 호출, switch의 점프 테이블처럼 갈 주소가 실행 중에 정해지는 간접 분기도 대상 주소를 예측한다. 한 호출 지점에 들어오는 타입이 하나뿐이면 잘 맞고, 여러 타입이 무작위로 섞이면 자주 틀린다.

예측 기록을 담는 표는 코어의 자원이라, 같은 코어의 SMT 스레드가 함께 쓴다. 한 스레드가 표를 자기 분기로 채우면 다른 쪽 예측이 나빠진다. 커널 진입이나 문맥 교환 때 보안 대책(Spectre 완화)으로 예측 기록을 비우는 경우도 있어서, 그 직후에는 예측률이 떨어진다.

선택 기준

데이터를 예측 가능하게 만드는 것이 먼저다

데이터가 정렬돼 있으면 if (x >= 128) 같은 조건 분기가 한동안 거짓, 이후 계속 참이라 예측이 잘 맞는다. 무작위 데이터에서는 절반 가까이 틀린다. 같은 코드인데 입력이 정렬됐느냐에 따라 실행 시간이 몇 배씩 벌어지기도 한다.

분기를 없애는 방법(조건부 이동 cmov, 산술로 치환, 조건을 루프 밖으로 빼기)은 코드를 읽기 어렵게 만들고, 분기가 실제로 예측 불가능할 때만 이득이 된다. .NET 8부터는 JIT가 단순한 조건식을 스스로 cmov로 바꾸기도 하므로, 손으로 바꾸기 전에 먼저 재 본다.

게임 서버에서는

  • 엔티티를 종류별로 모아서 돈다. 몬스터·NPC·투사체가 한 리스트에 섞여 있고 루프 안에서 타입별로 분기하거나 가상 메서드를 부르면, 매 원소마다 분기 대상이 바뀌어 예측이 자주 틀린다. 종류별 배열로 나눠 돌면 분기와 호출 대상이 일정해진다. 데이터 지향 설계(ECS)가 빠른 이유 중 하나다.
  • 패킷 디스패치는 대개 신경 쓰지 않아도 된다. opcode switch도 간접 분기라 무작위 opcode에서는 틀리지만, 핸들러 하나의 처리 비용에 비하면 보통 작다. 측정에서 병목으로 나올 때만 본다.

주의 사항

  • 느린 것은 if 문이 아니라 예측 불가능한 분기다. 예측이 맞으면 분기는 사실상 공짜다. "if를 줄이자"는 최적화는 대부분 효과가 없다.
  • 마이크로 벤치마크의 입력이 결과를 정한다. 같은 값만 반복하는 테스트 데이터는 예측이 100% 맞아 실제보다 빠르게 나온다. 운영 데이터와 분포가 비슷한 입력으로 잰다.
