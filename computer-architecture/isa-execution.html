먼저 읽을 것: 파이프라인과 분기 예측

핵심 요약

오늘날 CISC와 RISC의 구분은 명령어 인코딩 방식의 차이에 가깝다. x86은 길이가 변하는 복잡한 명령을 받지만, 받자마자 내부에서 단순한 micro-op으로 나눈다.

그다음부터는 둘이 거의 같다. 한 사이클에 여러 개를 내보내고(superscalar), 의존 관계가 풀리는 순서로 실행하다가(out-of-order), 결과는 프로그램 순서대로 다시 확정(커밋)한다.

동작 원리

명령은 나뉘어 순서를 바꿔 실행되다가 다시 순서대로 커밋된다

핵심은 실행 순서와 커밋 순서가 다르다는 것이다. 뒤 명령이 먼저 끝나도 앞 명령이 끝날 때까지는 결과를 확정하지 않는다. 그래서 그 코어 안에서는 겉으로 순서대로 실행된 것처럼 보인다.

다른 코어에서 볼 때는 이 순서가 보장되지 않는다. 그래서 원자적 연산과 메모리 순서가 따로 필요하다.

병렬로 실행할 수 있는 폭은 의존 사슬이 정한다

실행 포트가 여러 개라도, 앞 결과를 다음 명령이 바로 써야 하면 줄을 서야 한다. 이 줄의 길이가 의존 사슬이고, 명령 수가 아니라 이 길이가 실제 처리 시간을 정하는 경우가 많다.

두 명령이 같은 레지스터를 쓴다고 다 줄을 서는 것은 아니다. CPU는 레지스터 이름 바꾸기(register renaming)로 이름만 겹친 경우를 내부에서 다른 레지스터로 갈라 놓는다. 그래서 남는 것은 앞의 결과값이 실제로 필요한 경우뿐이고, 그것이 곧 의존 사슬이다. 이름 때문에 생긴 줄은 하드웨어가 없애 주지만, 값 때문에 생긴 줄은 코드를 고쳐야 없어진다.

선택 기준

명령 수를 줄이느냐, 의존 사슬을 끊느냐

같은 계산을 빠르게 만드는 두 방법은 서로 반대 방향이다.

방법얻는 것대가
명령 수를 줄인다코드가 작아지고 명령 캐시에 유리하다남은 명령이 한 줄로 이어져 있으면 포트 폭을 살리지 못한다
의존 사슬을 끊는다 (누산기 여러 개)독립된 사슬들이 실행 포트를 동시에 쓴다명령 수와 코드가 늘어난다
 
// 사슬 하나: 매 덧셈이 직전 sum 결과를 기다린다
double sum = 0;
for (int i = 0; i < a.Length; i++)
    sum += a[i];

// 사슬 넷: 네 누산기가 서로 독립이라 덧셈이 겹쳐 실행된다
double s0 = 0, s1 = 0, s2 = 0, s3 = 0;
int j = 0;
for (; j + 3 < a.Length; j += 4)
{
    s0 += a[j]; s1 += a[j + 1]; s2 += a[j + 2]; s3 += a[j + 3];
}
for (; j < a.Length; j++) s0 += a[j];
double sum4 = (s0 + s1) + (s2 + s3);

어느 쪽이 나은지는 사슬이 실제로 병목이었는지에 달렸다. 재 보지 않고 고르면 명령만 늘려 놓고 아무 효과도 얻지 못한다. 그리고 실수에서는 누산기를 나누면 합산 순서가 바뀌어 결과가 미세하게 달라진다(수의 표현). 그래서 컴파일러와 JIT는 실수 합산을 스스로 이렇게 바꾸지 않는다. 결과의 마지막 자리가 달라져도 되는 곳에서만 손으로 쓴다.

게임 서버에서는

  • ARM이냐 x86이냐는 실측으로 고른다. Graviton 같은 ARM 서버와 x86 서버는 둘 다 같은 방식(superscalar, out-of-order)으로 실행한다. "RISC라서 빠르다", "CISC라서 느리다"가 아니라 같은 서버 코드를 돌려 본 처리량과 가격으로 판단한다.
  • 프로파일링에서는 명령 수보다 IPC를 본다. Linux perf stat이 보여 주는 사이클당 명령 수(IPC)가 낮으면, 명령이 많아서가 아니라 캐시 미스나 의존 사슬 때문에 기다리고 있다는 뜻이다.

주의 사항

  • "명령어 수가 적으면 빠르다"는 성립하지 않는다. 명령 하나가 몇 사이클을 쓰는지(지연), 다른 명령과 겹쳐 실행될 수 있는지(처리량)가 따로 정해진다. 명령 수는 대리 지표일 뿐이다.
  • "x86은 CISC라 느리다"도 사실이 아니다. 디코드 단계에서 micro-op으로 바뀌고 나면 실행 구조는 RISC 쪽과 크게 다르지 않다. 실제 차이는 디코드 비용과 명령 밀도 같은 다른 곳에 있다.
  • 그 디코드 비용도 매번 드는 것은 아니다. x86 CPU는 디코드한 micro-op을 별도 캐시(micro-op cache)에 담아 두었다가, 같은 코드를 다시 실행할 때는 디코드를 건너뛴다. 이 캐시에 들어가는 크기의 루프라면 디코드 비용은 사실상 처음 한 번만 든다.
