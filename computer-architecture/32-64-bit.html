먼저 읽을 것: 메모리 계층과 캐시

핵심 요약

"64비트"라고 한 단어로 부르지만, 주소 공간 · 범용 레지스터 폭 · 포인터 크기가 함께 움직일 뿐 셋은 서로 다른 값이다.

64비트가 되면 주소 공간과 레지스터는 넓어진다. 대신 포인터가 두 배(8바이트)가 되어, 캐시 라인 하나에 들어가는 포인터 수가 절반으로 줄어든다.

표의 값은 x86 계열 기준이다. 64비트라도 지금 CPU는 주소의 하위 48비트만 쓴다. 주소 공간은 위아래 두 영역으로 나뉘어 커널이 한쪽을 쓰므로, 프로세스가 쓰는 것은 256TB의 절반이다. 일부 최신 서버 CPU는 페이지 테이블을 한 단계 더 두어(5단계 페이징) 57비트까지 넓히므로, 이 값도 고정된 것이 아니다.

넓어져서 좋아지는 것

  • 4GB 벽이 사라진다. 물리 메모리가 남아 있는데 주소 공간이 먼저 바닥나는 일이 없어진다.
  • 함수 인자가 레지스터로 넘어간다. 레지스터가 두 배라 기본 호출 규약이 인자를 레지스터로 넘기고, 스택 접근이 줄어든다.
  • 64비트 정수 연산이 한 명령으로 끝난다. 32비트에서는 long(C#)·int64_t 덧셈 하나가 명령 두 개로 쪼개진다.
  • SSE2가 기본이다. x86-64는 SSE2를 보장하므로 부동소수점 연산에 오래된 x87 대신 SSE를 쓴다.

대신 포인터가 캐시를 더 차지한다

포인터가 두 배가 되면서 참조가 많은 자료구조(트리, 연결 리스트, 객체 그래프)는 같은 데이터를 담는 데 메모리를 더 쓴다. 캐시 라인에 들어가는 원소 수가 줄어 캐시 효율이 떨어지고, 포인터의 정렬 요구가 커진 만큼 구조체 패딩도 늘어난다.

32/64비트는 캐시 라인 크기와는 관계가 없다. 라인은 그대로 64바이트고, 그 안에 들어가는 원소가 커진 것이다.

선택 기준

64비트가 언제나 빠른 것은 아니다. 레지스터와 호출 규약 덕분에 대부분의 코드는 빨라지지만, 포인터 밀도가 높은 워크로드는 캐시 손해가 이득보다 클 수 있다.

그래서 "64비트 레지스터 + 32비트 포인터"를 노린 절충이 나왔다. JVM의 compressed oops는 힙이 약 32GB 이하일 때 객체 참조를 32비트로 저장한다. Linux의 x32 ABI는 64비트 모드에서 포인터만 32비트로 쓴다. 대신 포인터가 좁아진 만큼 다룰 수 있는 메모리에 상한이 생긴다. x32 ABI는 실제로는 거의 쓰이지 않는다.

새로 만드는 서버라면 고민할 것 없이 64비트로 빌드한다. 판단할 일은 포인터 밀도가 높은 자료구조를 값 배열로 바꿀지다.

게임 서버에서는

  • .NET의 "32비트 선호" 설정을 확인한다. .NET Framework 프로젝트의 AnyCPU 빌드에는 "32비트 선호(Prefer 32-bit)" 옵션이 있다. 이 옵션이 켜져 있으면 64비트 OS에서도 32비트 프로세스로 뜬다. 그러면 메모리가 넉넉한 서버에서 OutOfMemoryException이 난다. 시작할 때 Environment.Is64BitProcess를 로그로 남겨 두면 바로 확인할 수 있다.
  • C# 객체는 64비트에서 커진다. 참조가 8바이트가 되고, 객체 헤더(동기화 블록 + 타입 포인터)도 8바이트에서 16바이트가 된다. 작은 객체를 대량으로 만드는 서버에서는 이 차이가 메모리 사용량과 GC 부담으로 그대로 드러난다. 작은 데이터를 struct 배열로 두는 것이 효과가 큰 이유 중 하나다.
  • C#의 정수 크기는 플랫폼과 무관하다. C#의 int는 항상 32비트, long은 항상 64비트다. 플랫폼에 따라 달라지는 것은 IntPtr/nint뿐이다. 아래 주의 사항의 data model 문제는 C/C++로 작성된 네이티브 라이브러리를 P/Invoke로 부를 때 다시 나온다.

주의 사항

C/C++의 data model이 플랫폼마다 다르다.

모델intlong포인터쓰는 곳
ILP3232323232비트 전반
LP64326464Linux · macOS 64비트
LLP64323264Windows 64비트
  • long에 포인터를 담는 코드는 Linux에서는 돌아가지만 Windows 64비트에서는 상위 32비트가 잘려 깨진다. 포인터를 정수로 담아야 하면 intptr_t/uintptr_t(C#은 nint/IntPtr)를 쓰고, 고정 폭이 필요하면 int32_t/int64_t를 쓴다.
  • P/Invoke 선언에서 네이티브 long을 C# long으로 옮기면 Windows에서 크기가 어긋난다. Windows의 네이티브 long은 C# int에 해당한다.
  • 포인터 크기는 설치된 RAM이 아니라 빌드 대상 아키텍처가 정한다. 같은 64비트 OS에서도 32비트로 빌드한 프로세스의 포인터는 4바이트다.
