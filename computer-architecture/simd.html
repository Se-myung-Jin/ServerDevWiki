먼저 읽을 것: 메모리 계층과 캐시 · 명령어 집합과 실행 모델

핵심 요약

SIMD(Single Instruction, Multiple Data)는 넓은 레지스터 하나에 값 여러 개를 나란히 담고, 명령 하나로 그 값들을 한꺼번에 계산하는 방식이다. 128비트 레지스터라면 32비트 정수 네 개를 한 번에 더한다. 명령 수가 줄어드는 만큼 빨라진다.

조건이 있다. 같은 연산을 할 값들이 메모리에 연달아 놓여 있어야 한 번에 레지스터로 읽어 올 수 있다. 그래서 SIMD의 효과는 계산 코드보다 자료 배치가 먼저 정한다. 원소마다 분기가 갈리는 코드도 잘 맞지 않는다.

동작 원리

한 칸씩 더하기와 네 칸을 한 번에 더하기

SIMD 레지스터 하나에 몇 칸이 들어가는지는 레지스터 폭을 원소 크기로 나눈 값이다. 이 칸 하나를 레인(lane)이라고 부른다. 레인끼리는 서로 독립이라, 한 레인의 계산이 옆 레인에 넘어가지 않는다.

분기는 마스크로 바꾼다

SIMD에는 "이 레인만 if 안으로 들어간다"가 없다. 모든 레인이 같은 명령을 실행한다. 그래서 조건문은 비교 결과를 마스크(조건이 참인 레인은 비트가 모두 1, 거짓이면 0)로 만들고, 양쪽 결과를 다 계산한 뒤 마스크로 골라 담는 식으로 바꾼다. 예측이 어려운 분기를 이렇게 없애면 분기 예측 실패도 함께 사라진다. 대신 양쪽을 다 계산하므로, 한쪽이 무거우면 손해다.

자동 벡터화는 조건이 까다롭다

컴파일러가 평범한 반복문을 SIMD 명령으로 바꿔 주는 것을 자동 벡터화라고 한다. C++ 컴파일러(GCC, Clang, MSVC)는 최적화를 켜면 시도하지만, 아래 조건을 만족해야 한다.

  • 반복 사이에 의존이 없다. a[i] = a[i-1] + x처럼 앞 결과를 쓰면 나란히 계산할 수 없다.
  • 포인터가 서로 겹치지 않는다는 것을 알 수 있다. 입력과 출력이 같은 메모리를 가리킬 가능성이 있으면 컴파일러는 포기하거나 검사 코드를 넣는다.
  • 접근이 연속이다. 간접 참조(a[idx[i]])나 큰 간격의 접근은 모아 오는 비용이 커서 이득이 줄어든다.
  • 반복 안에 함수 호출과 복잡한 분기가 없다. 인라인되지 않는 호출이 있으면 거기서 막힌다.

.NET의 JIT는 사용자 반복문을 자동으로 벡터화하는 일이 거의 없다. C#에서 SIMD를 쓰려면 벡터 타입으로 직접 쓰거나, 이미 SIMD로 짜인 라이브러리 함수를 부른다.

Vector<T> (System.Numerics)크기가 실행하는 CPU에 맞춰 정해진다. Vector<T>.Count로 레인 수를 알아낸다. 한 코드로 여러 CPU에 맞출 때 쓴다
Vector128<T>, Vector256<T>, Vector512<T>폭이 고정된 타입. Vector128.IsHardwareAccelerated로 가속 여부를 확인하고, 아니면 스칼라 경로로 간다. Vector512는 .NET 8부터
System.Runtime.Intrinsics.X86 / ArmAvx2.IsSupported처럼 CPU 기능을 확인하고 특정 명령을 직접 부른다. 가장 빠르지만 플랫폼마다 따로 짜야 한다
이미 벡터화된 라이브러리Span<T>.IndexOf, SequenceEqual, 서수 비교 문자열 검색, UTF-8 변환, Base64, 배열에 대한 LINQ Sum·Min·Max, TensorPrimitives(.NET 8)
 
// 두 float 배열을 원소별로 더한다. 남는 꼬리는 스칼라로 처리한다.
static void Add(ReadOnlySpan<float> a, ReadOnlySpan<float> b, Span<float> dst)
{
    int i = 0;
    if (Vector256.IsHardwareAccelerated)
    {
        for (; i <= a.Length - Vector256<float>.Count; i += Vector256<float>.Count)
        {
            var va = Vector256.Create(a.Slice(i));
            var vb = Vector256.Create(b.Slice(i));
            (va + vb).CopyTo(dst.Slice(i));
        }
    }
    for (; i < a.Length; i++)   // 레인 수로 나눠떨어지지 않는 나머지
        dst[i] = a[i] + b[i];
}

SIMD 코드에는 늘 나머지 처리가 붙는다. 원소 수가 레인 수로 나눠떨어지지 않으면 마지막 몇 개는 스칼라로 하거나, 마지막 묶음을 겹쳐 한 번 더 처리한다. 이 경계에서 배열 끝을 넘어 읽는 버그가 잘 난다.

문자열 검색 같은 표준 라이브러리 함수가 직접 짠 알고리즘보다 빠른 이유가 여기에 있다. 한 글자씩 비교하는 대신 16~32바이트를 한 번에 비교하고, 맞는 레인이 있는지만 마스크로 확인한다(문자열 검색과 계산 한계).

게임 서버에서는

  • 먼저 라이브러리가 해 주는지 본다. 패킷 버퍼에서 구분자 찾기, 바이트 비교, 체크섬, 문자열 처리는 Span API가 이미 SIMD로 돈다. 직접 루프를 짜기 전에 같은 일을 하는 API가 있는지 찾는 것이 가장 싸다.
  • 대량 숫자 계산에서만 직접 쓸 가치가 있다. 수천 개 대상의 거리 검사, 일괄 버프 계산, 물리 근사처럼 같은 식을 많은 원소에 적용하는 곳이다. 이때는 위치를 필드별 배열(SoA)로 두어야 효과가 난다. 객체 그래프를 따라가며 분기가 갈리는 일반 게임 로직은 SIMD로 얻을 것이 적다.
  • 결과가 CPU마다 달라질 수 있다. 부동소수점 덧셈은 순서를 바꾸면 결과가 조금 달라진다(수의 표현). 레인 수가 다른 CPU에서 합계를 다른 순서로 묶으면 마지막 비트가 다르다. 서버와 클라이언트가 같은 결과를 내야 하는 결정적 시뮬레이션에서는 이 차이가 동기화 어긋남이 된다.

주의 사항

  • 넓은 것이 항상 빠르지는 않다. 일부 Intel 서버 CPU는 AVX-512의 무거운 명령을 실행하는 동안 클럭을 낮춘다. 그 코어에서 같이 도는 다른 코드까지 느려진다. 그래서 이런 CPU에서는 .NET이 기본으로 512비트 경로를 쓰지 않는다. 폭을 바꿀 때는 실제 서버에서 잰다.
  • 메모리가 병목이면 소용없다. 계산이 8배 빨라져도 데이터가 캐시에 없으면 메모리를 기다리는 시간이 그대로다(메모리 계층과 캐시). 큰 배열을 한 번 훑고 끝나는 계산은 대역폭이 상한이다.
  • 정렬을 요구하는 명령이 있다. 정렬이 안 맞는 주소에 정렬 전용 로드를 쓰면 x86에서도 예외가 난다(정렬과 패딩). 벡터 타입의 일반 로드는 정렬되지 않은 주소도 받는다.
  • 가속 여부를 확인하지 않으면 느려질 수 있다. 하드웨어 가속이 없는 환경에서 벡터 타입은 소프트웨어로 흉내 내므로 스칼라보다 느리다. IsHardwareAccelerated로 갈라 둔다.
