먼저 읽을 것: 캐시 일관성과 false sharing

핵심 요약

원자적 연산은 읽기·수정·쓰기를 다른 코어가 끼어들 수 없는 하나의 동작으로 처리한다. CPU는 그동안 해당 캐시 라인의 소유권을 쥐고 있어서, 다른 코어가 그 라인을 건드리지 못한다.

그런데 원자성만으로는 부족하다. 컴파일러와 CPU는 성능을 위해 메모리 접근 순서를 바꿀 수 있고, 다른 스레드는 그 바뀐 순서를 관측한다. 메모리 배리어(acquire·release 등)가 특정 지점에서 순서를 강제한다.

동작 원리

count++는 세 단계라서 끊긴다

count++는 읽기 → 증가 → 쓰기 세 단계로 실행된다. 두 코어가 동시에 같은 값을 읽고 각자 1을 더해 쓰면, 증가 하나가 사라진다(lost update). 싱글 코어에서도 단계 사이에 스레드가 선점되면 같은 일이 생긴다. 

_count++;                          // 읽기 · 증가 · 쓰기. 두 스레드가 겹치면 하나가 사라진다
Interlocked.Increment(ref _count); // x86에서는 lock xadd 한 명령. 재시도도 없다

CAS는 읽고 쓰는 사이의 틈을 없앤다

CAS(Compare-And-Swap)는 "값이 아직 내가 읽은 그대로면 새 값으로 바꿔라"를 끊기지 않는 한 번의 동작으로 처리한다. 더하기처럼 전용 명령이 없는 갱신은 CAS를 성공할 때까지 반복하는 CAS 루프로 만든다. 

// 최대 동시 접속자 수 기록: '더하기'가 아닌 갱신이라 CAS 루프로 만든다
int seen, next;
do
{
    seen = _peakCcu;
    next = Math.Max(seen, currentCcu);
} while (Interlocked.CompareExchange(ref _peakCcu, next, seen) != seen);

원자적 연산을 만드는 방법은 아키텍처마다 다르다

아키텍처방식특징
x86 명령에 lock 접두사를 붙인다. lock cmpxchg(CAS), lock xadd(더하기) 더하기·교환은 한 명령으로 끝나고 실패가 없다
ARM (오래된 방식) LL/SC: 읽기(LDXR)와 쓰기(STXR)를 짝으로 묶고, 그 사이에 다른 코어가 그 주소를 건드렸으면 쓰기를 실패시킨다 값이 같은지가 아니라 건드렸는지를 본다. 문맥 교환만 있어도 실패할 수 있어 항상 루프로 감싼다
ARMv8.1 이후 (LSE) CAS, LDADD 같은 원자 명령 x86처럼 한 명령으로 끝난다. 경합이 심할 때 LL/SC보다 유리하다

재시도 루프가 생기는 것은 CAS로 임의의 갱신을 만들 때와 LL/SC를 쓸 때다. x86의 lock xadd나 ARM LSE의 LDADD처럼 전용 명령이 있는 연산에는 재시도가 없다.

CPU와 컴파일러는 순서를 바꾼다

CPU는 느린 메모리 쓰기를 store buffer에 쌓아 두고 다음 명령으로 넘어간다. 그래서 내 코어에서는 쓴 순서대로 보여도, 다른 코어에는 다른 순서로 보일 수 있다. 어떤 재정렬을 허용하는지가 아키텍처의 메모리 모델이다.

재정렬 (앞 접근 → 뒤 접근)x86·x64 (TSO, 강한 모델)ARM64 (약한 모델)
읽기 → 읽기안 바뀐다바뀔 수 있다
쓰기 → 쓰기안 바뀐다바뀔 수 있다
읽기 → 쓰기안 바뀐다바뀔 수 있다
쓰기 → 읽기바뀔 수 있다바뀔 수 있다

여기에 컴파일러(C#은 JIT)의 재정렬이 더해진다. 컴파일러는 싱글 스레드에서 결과가 같다면 읽기를 루프 밖으로 빼거나 값을 레지스터에 담아 두고 다시 읽지 않는다. 이것은 CPU 메모리 모델과 무관하게 x86에서도 일어난다.

acquire와 release가 접근이 넘어가는 방향을 막는다

쓰는 쪽은 데이터를 다 쓴 뒤 플래그를 release로 쓰고, 읽는 쪽은 플래그를 acquire로 읽는다. 그러면 읽는 쪽이 플래그를 본 순간, 쓰는 쪽이 그 전에 쓴 데이터도 모두 보인다. 이 짝으로 "여기까지는 끝났다"를 다른 스레드에 전한다. 

// 깨지는 코드: ARM에서는 _ready가 _payload보다 먼저 보일 수 있다
_payload = 42;
_ready = true;
// 다른 스레드
if (_ready) Use(_payload);         // 0을 볼 수 있다

// 고친 코드
_payload = 42;
Volatile.Write(ref _ready, true);  // release: 앞의 쓰기가 뒤로 밀리지 않는다
// 다른 스레드
if (Volatile.Read(ref _ready))     // acquire: 뒤의 읽기가 앞으로 당겨지지 않는다
    Use(_payload);

acquire·release보다 강한 순서가 sequential consistency다. 모든 스레드가 모든 원자 연산을 같은 한 줄의 순서로 보게 만든다. C++ std::atomic의 기본값이 이것이다. 가장 안전한 대신 가장 비싸다. 예를 들어 x86에서는 쓰기마다 전체 배리어(mfence나 xchg)가 붙는다. 기본값을 낮추려면 무엇을 포기하는지 먼저 알아야 한다.

필요한 것C#에서 쓸 것비고
카운터 증가, 값 교환Interlocked.Increment · Add · Exchange전체 배리어를 겸한다

  • lock-free는 경합이 심해지면 락보다 느려질 수 있다. CAS 재시도가 늘고, 라인 소유권이 코어 사이를 계속 오간다. ABA 문제와 안전한 메모리 회수라는 난제도 따라온다. 다만 .NET에서는 GC가 참조가 남아 있는 객체를 재사용하지 않으므로, 참조 기반 자료구조의 ABA와 메모리 회수 문제가 C++보다 훨씬 작다.
  • 배리어를 다 붙이면 느려지고, 빼면 재현되지 않는 버그가 된다. 이 사이의 폭이 좁아서 lock-free를 제대로 구현하기 어렵다. 직접 만들기 전에 ConcurrentQueue, Channel 같은 검증된 구현(동시성 자료구조)을 먼저 쓴다.

게임 서버에서는

  • 종료 플래그 무한 루프. while (!_stop) { ... }에서 _stop이 일반 필드면, Release 빌드의 JIT가 읽기를 루프 밖으로 빼서 다른 스레드가 true로 바꿔도 끝나지 않을 수 있다. 디버그 빌드에서는 재현되지 않는 전형적인 버그다. volatile이나 CancellationToken을 쓴다.
  • 통계 카운터. 여러 IO 스레드가 같은 카운터를 ++하면 값이 조금씩 모자라게 나온다. Interlocked로 바꾸거나, 스레드별로 세었다가 합친다(false sharing도 함께 고려한다).
  • 설정·테이블 핫 리로드. 새 데이터 객체를 완성한 뒤 참조 하나를 Volatile.Write나 Interlocked.Exchange로 바꿔 끼우면, 읽는 쪽은 락 없이 항상 완성된 옛 버전이나 새 버전 중 하나를 본다.
  • ARM 서버 이전. AWS Graviton 같은 ARM64 서버로 옮기면, x86에서 우연히 동작하던 배리어 누락이 드러날 수 있다. 이전 전에 플래그·공개 패턴을 점검한다.

주의 사항

  • x86에서 테스트가 통과했다는 것은 정확성의 근거가 되지 못한다. 메모리 모델이 강해서 재정렬 버그가 드러나지 않을 뿐이다. ARM 서버나 모바일로 옮기는 순간 나타난다.
  • x86이라도 배리어가 필요 없는 것은 아니다. 하드웨어는 쓰기→읽기 순서를 바꾸고, 컴파일러와 JIT는 그 외의 순서도 바꾼다. "x86이니까 괜찮다"는 판단은 하드웨어만 본 것이다.
  • 원자적 연산은 정렬된 주소에서만 원자적이다. 캐시 라인에 걸친 원자 연산은 매우 느리거나 플랫폼에 따라 실패한다(정렬과 패딩).
  • 원자적인 연산 두 개는 원자적인 연산 하나가 아니다. Interlocked로 두 변수를 각각 바꾸면, 다른 스레드는 그 사이의 어중간한 상태를 볼 수 있다. 함께 바뀌어야 하면 락을 쓴다.
